## Что такое workflow, бот и бандл

В iterion это почти одно и то же под разными именами. Документация iterion говорит так: «agent workflow» — развёртываемая нагрузка, упакованная как `.bot` или `.botz`, а существующие CLI и API называют её `bot`.

- **Workflow** — граф шагов в файле `.bot`: агенты, судьи (`judge`), роутеры, инструменты, переходы между ними. В файле его задаёт блок `workflow имя:` — точка входа `entry:` и стрелки `a -> b`.
- **Бот** — единица, которую запускают. Это либо одиночный `.bot`-файл, либо **бандл**: папка с `main.bot` и `manifest.yaml` (описание, входные поля, права, режимы вызова) и необязательными `skills/`, `prompts/`, `presets/`.
- **`.botz`** — бандл, упакованный в zip.
- Одиночный `.bot` без манифеста запускается и открывается в редакторе; на странице Bots он показан отдельной группой файлов проекта, но исполнителем диспетчера не бывает.

Узлы в файле: `agent` (LLM с инструментами), `judge` (LLM, который возвращает вердикт по схеме), `router`, `human`, `tool`, `compute`, `subbot`. Схемы (`schema`) описывают вход и выход узлов, промпты (`prompt`) — тексты. Подстановка одного промпта в другой (`{{prompts.имя}}`) не существует: ошибка C004, текст повторяют в каждом промпте.

## Где лежат workflow и что показывает каталог ботов

- Студия сохраняет новый workflow туда, куда указал пользователь; по умолчанию это корень проекта. Настройки «писать в `.iterion/`» нет (идея — карточка на доске `itterion-test`).
- Сохранение из студии приводит файл к канонической форме (порядок полей, запятые); об этом предупреждает тост и заметка в Save As. Файл, открытый через Open…, сохраняется под своим именем. Для нового документа Save As предлагает имя через дефис (`dev-flow.bot`).
- Боты ищутся только в `bots/`, `examples/`, `.botz/` проекта (`botregistry.DefaultPaths`) и одиночные `.bot` в корне проекта, без захода во вложенные репозитории и без фрагментов `lib/`. Так работает панель Project files на стартовой странице редактора; страницу Bots и FilePicker приводят к тому же правилу (в работе 06-11-2026).
- Встроенного каталога ботов в списках студии нет: владелец от него отказался, и 06-11-2026 встроенные боты убраны со страницы Bots, стартовой панели, выбора бота в карточке и формы диспетчера. Пресет диспетчера по умолчанию ещё ссылается на встроенных ботов, это исправляется.
- Папка `.iterion/` рядом с сохранённым файлом служебная: страховочные копии (`.iterion/authoring/`) и блокировки, внутри свой `.gitignore`. Если кладёте в `.iterion/` свои файлы, добавьте папку в `.gitignore` проекта.
- Хранилище проекта — `~/.iterion/projects/<ключ>/`: доска (`dispatcher/board.json`, `dispatcher/issues/<id>.json`, `events.jsonl`, `claims.json`, `runtime.json`), запуски (`runs/`), рабочие копии запусков (`worktrees/<run-id>`).

## Где iterion хранит данные: в проекте, в `~/.iterion` или в AppData

Три места, у каждого своя роль (проверено осмотром диска 05-11-2026 и чтением `store.ResolveStoreDir`).

| Что | Где |
|---|---|
| Ваши файлы: `.bot`, бандлы `bots/<имя>/` | В папке проекта, куда вы сохранили. Это единственное, что студия кладёт в проект как «своё». |
| Страховочные копии и блокировки при сохранении | В проекте: `<проект>/.iterion/authoring/` (создаёт приложение, внутри `.gitignore` со звёздочкой). |
| Доска (`dispatcher/board.json`, `issues/`, `events.jsonl`), запуски (`runs/`), рабочие копии запусков, настройки диспетчера, каталог ботов диспетчера (`dispatcher/bots`) | В хранилище проекта: `~/.iterion/projects/<ключ-пути-проекта>/`. Ключ — путь проекта с заменой разделителей на дефисы. |
| Плагины (`plugins/bars`), включённость плагинов (`plugins.yaml`), вход в iterion (`cli-auth.json`) | Общие для всех проектов: `~/.iterion/`. |
| Адрес и pid работающего сервера студии, его лог | `~/.iterion/daemons/<ключ>.json` и `.log`. |
| Настройки окна приложения, список проектов, блокировки процесса | `%APPDATA%\Iterion\` (`config.json`, `iterion-desktop-*.lock`). |

**Правило выбора хранилища.** По умолчанию всё из строки про доску лежит в `~/.iterion/projects/<ключ>/`. Хранилище переезжает в проект только тогда, когда в папке проекта есть `.iterion/` с признаками управляемого хранилища: подпапка `runs/`, `dispatcher/` или файл `.iterion-store`. Одной `.iterion/authoring/` для этого мало, поэтому у `bars-project` хранилище глобальное. Флаг `--store-dir` (и `ITERION_HOME` для плагинов) переопределяет место.

## Что такое «проект» в студии и что делает переключатель проектов

Проект в iterion — это рабочая папка, которую обслуживает окно. От неё зависит всё остальное: список файлов, каталог ботов (`bots/`, `examples/`, `.botz/` внутри папки), доска, запуски, диспетчер и хранилище `~/.iterion/projects/<ключ>/`. Одно окно открывается под один проект, и для него запускается свой сервер студии (адреса в `~/.iterion/daemons/`).

Переключателя проектов в боковой панели больше нет (убран 05-11-2026: он менял только список файлов, а боты, доска и диспетчер оставались от прежнего проекта). Боковая панель только показывает имя проекта. Другой проект открывают отдельным окном десктопа (Ctrl+P), и у него свой сервер.

## Как открыть существующий `.bot` в студии

- **Open…** (Ctrl+O, в том числе на стартовой панели без вкладок) открывает поиск по файлам проекта. Файл привязывается к своему пути: Save пишет поверх него, Launch запускает его.
- **Import copy…** берёт файл с диска как копию без пути: Save создаёт новый файл в проекте, оригинал не трогает.
- Стартовая панель редактора показывает панель Project files по правилу поиска ботов выше и недавние файлы. Файл вне `bots/`, `examples/`, `.botz/` и корня проекта сейчас открывается только через Import copy (карточка на доске).

## Как запустить workflow

- **Студия:** открыть файл в редакторе и нажать Launch. Окно запуска просит значения переменных (`vars`), показывает бэкенд и оценку стоимости. Ход запуска виден на странице **Runs**.
- **Терминал:** `iterion run файл.bot --var имя="значение"`; пределы `--max-cost-usd`, `--max-duration`. Исчерпанный предел ставит запуск на паузу, продолжить можно через `iterion resume`.
- **С доски:** карточку берёт диспетчер, см. раздел про диспетчер ниже.
- `worktree: auto` в workflow запускает его в отдельной рабочей копии репозитория; рабочая папка проекта не меняется, а в конце результат вливается по правилам `merge_into`.
- Если `iterion` нет в PATH, его собирают из клона: `go build -o <папка> ./cmd/iterion` с `GOFLAGS=-mod=vendor` и кэшем Go внутри рабочей папки.

## Как проверить workflow без запуска через работающую студию

Адрес сервера студии лежит в `~/.iterion/daemons/<ключ-проекта>.json` (поле `url`). Порт меняется при каждом перезапуске приложения, поэтому его читают заново.

1. `POST <url>api/parse` с телом `{"source": "<текст .bot>"}` отвечает документом и ошибками разбора.
2. `POST <url>api/validate` с телом `{"document": <документ из шага 1>, "path": "файл.bot"}` отвечает `valid`, `diagnostics` (ошибки C…) и `warnings`.

Проверка не запускает модели и бесплатна. Имена MCP-серверов в `tools:` проверяются по известным серверам (плагины, `mcp_server`, `.mcp.json` проекта): неизвестный `mcp.нет_такого.x` даёт предупреждение C332. Если в `.mcp.json` проекта есть сервер с зарезервированным именем (`iterion`), каталог серверов не собирается и C332 молча пропадает (карточка на доске); свой сервер iterion называйте `engine`. Что сервер реально запустится, подтверждает только запуск. Опечатка в имени модели проверку пока проходит (карточка).

Из терминала то же и глубже даёт `iterion validate <файл или папка бота>`: с `--exec` сухой прогон без модели, оболочки и рабочей копии (подставляет промпты, называет нерешённые ссылки, проходит условия «все истинны» и «все ложны»), с `--explain` разбор того, какие встроенные инструменты оставляет `tools:` узлу `claude_code`. Для `bots/dev-flow` 05-11-2026 `--exec` дал «verdict: clean» (оба прохода завершились как задумано, цикл `fix_loop(3)` закончился явным выходом `REVIEW_NOT_APPROVED`, нерешённых ссылок нет), а `--explain` показал, что планировщик сохраняет только `Glob`, `Grep`, `Read`, ревьюер ещё `Bash`, реализатор все встроенные инструменты. Коды выхода: 0 проверка пройдена, 1 найден дефект, 2 файл не найден.

## Как назвать модель в узле и проверить имя

Строка вида `model: "anthropic/claude-sonnet-5-5"`. Примеры в документации iterion устарели (там `claude-sonnet-4-6`). Список известных моделей и их годность на этом компьютере отдаёт `GET <url>api/models?spec=anthropic/claude-sonnet-5-5`: строка с `usable: true` означает, что модель известна и учётные данные найдены. Принятие модели провайдером подтверждает только запуск.

## Как узлам workflow дать bars для чтения документации

Контракт установки плагина — в [подключении клиентов](../features/clients/clients.md), раздел iterion; пользовательская инструкция — в [руководстве по агентам](agents.md). Для узла `claude_code` важно следующее:

- iterion запускает Claude Code только со своим списком MCP-серверов, поэтому bars доходит до узлов через плагин `bars` в `~/.iterion/plugins/bars/`. Включён ли он, показывает `GET <url>api/v1/plugins`.
- Сервер из плагина попадает в каждый узел сам. Если он не запустился, узел работает без него и молча. Чтобы падать громко, инструменты называют в `tools:` как `mcp.bars.bars_search`, `mcp.bars.bars_read` и так далее.
- Список `tools:` у `claude_code` превращается в запрет остальных встроенных инструментов (Read, Edit, Bash, …), которых в списке нет. Реализатору, которому нужно править файлы, `tools:` не задают; планировщику и ревьюеру перечисляют `read_file`, `glob`, `grep` (ревьюеру ещё `bash` для `git diff`) и инструменты bars.
- В песочнице (`sandbox: auto` при установленном Docker) `bars-mcp` недоступен: нужен `sandbox: none` в блоке `workflow`. iterion предупредит C128, это ожидаемо.
- Рабочая копия запуска лежит вне репозитория; bars видит проект основной папки, поэтому документы, изменённые внутри запуска, не находятся до слияния.
- Требование «документацию читать только через bars» держится на тексте промптов и на поле-свидетельстве: планировщик возвращает `docs_read`, ревьюер без него не одобряет.

## Доска и диспетчер: почему карточка в Ready не берётся

Доска (**Board**) — канбан проекта: колонки `inbox`, `backlog`, `ready` и другие. Перенос в `ready` ничего не запускает: карточки берёт **диспетчер** (страница **Dispatcher**). Состояние на 05-11-2026: `GET <url>api/v1/dispatcher/status` вернул `{"state":"idle","has_config":false}` — диспетчер не запущен и без конфига.

Чтобы карточка запустилась, нужны три вещи:

1. **Запущенный диспетчер.** На странице Dispatcher кнопки Start/Pause/Stop и форма Settings. Без конфига есть кнопка «Use default settings», при существующем конфиге — «Reset to default settings» (с подтверждением; через API `POST api/v1/dispatcher/defaults/apply?replace=1`). Workflow path выбирается из списка ботов с поиском, студия подставляет абсолютный путь. Относительный путь, вписанный руками, считается от папки конфига `<хранилище>/dispatcher/`, а не от проекта (карточка на доске, исправляется). Пресет по умолчанию: встроенная доска, опрос раз в 30 секунд, хук посева рабочей копии (`after_create`), на Windows в PowerShell-варианте.
2. **Бот-исполнитель у карточки:** поле `assignee` или `bot`, оба выбираются из списка ботов проекта. Карточка без исполнителя не запускается (`require_assignee` в пресете): на ней пометка «no assignee — won't start», на странице Dispatcher строка в «Won't dispatch». Сам диспетчер метки при выборе бота не смотрит, но бот может назначать себя сам триггером доски: блок `invocations: - kind: board, board: { on: [card.moved], to_states: [ready], all_labels: [bug] }` в `manifest.yaml` ставит этого бота на карточку, когда она входит в колонку с `eligible: true` и несёт все перечисленные метки (`NativeBoardEffect.Promote` в `pkg/trigger/board_source.go`). Исключающих меток нет. Если на карточке стоял другой бот, триггер заменяет и бота, и `bot_args` целиком. Подписки триггеров студия собирает при старте: бот с новым триггером начинает работать только после перезапуска студии. Имя, которое не совпадает ни с одним ботом (имя человека, опечатка), пока уходит на запасной бот `default`; это исправляется (карточка).
3. **Сопоставление полей карточки с переменными бота.** У каждого бота свои входные поля (`feature_dev` ждёт `feature_prompt`). Для собственного workflow есть два пути:
   - **Бандл в `bots/<имя>/` проекта.** Диспетчер по умолчанию находит и такие боты как исполнителей, а поля берёт из `dispatch_vars` в `manifest.yaml`, например `task: |-` и под ним `{{issue.title}}` и `{{issue.body}}`. Тот же бандл появляется на странице Bots. Это путь, который сопоставляет карточку и каталог сразу.
   - **Конфиг диспетчера:** `assignee_workflows:` (имя исполнителя → путь к `.bot`) и `assignee_dispatch:` с `vars:`.

После взятия карточка переходит в `in_progress`, на ней появляется ссылка на запуск, в заголовке запуска написано «From ticket». Запуск с доски по-настоящему тратит токены. Пошаговый рецепт по-английски — `docs/howto-board-bot.md`, куда попадает результат — раздел «Where the result goes» в `docs/dispatcher.md`.

**Кто ещё запускает карточки из Ready, кроме диспетчера.** У студии есть свой цикл «pipeline admission» (`pkg/server/pipeline_admission.go`): раз в 2 секунды он запускает карточки в Ready с ботом, но отступает только пока диспетчер работает. Поэтому после Stop или Pause диспетчера (и в первые секунды после старта студии) карточку из Ready возьмёт сама студия: без хука `after_create` и рабочей копии диспетчера, прямо в папке проекта, а в Runs такой запуск помечен «Manual». Пока это не исправлено (карточка 5bd986a5), не останавливайте диспетчер, когда в Ready лежат карточки с ботом.

**Что ещё надо знать о диспетчере (проверено 06-11-2026):**

- `max_concurrent_by_state` считает запуски по колонке, из которой карточка взята, а `stall.timeout_ms` (по умолчанию 600000) снимает запуск после 10 минут без событий. Узел `tool` с долгой командой (например, `go test`) событий не шлёт, поэтому для таких ботов таймаут поднимают (у нас 3600000).
- Карточка, которую чистый запуск оставил в колонке `completed_state`, берётся снова, если эта колонка eligible: бот, работающий «на колонке», должен сам переводить карточку дальше, иначе цикл (карточка b1980100).
- Пока все слоты заняты, карточка в Ready, на которую триггер только что поставил бота, может показывать устаревшее «no assignee — won't start»; она стартует, когда освободится слот (карточка 59a19c94).
- При нескольких параллельных запусках запись карточки на Windows может упасть на «rename temp file» (карточка 18148cee). Если так упал перевод в `completed_state`, карточка остаётся в `in_progress`, и диспетчер запускает бота на ней заново — платный дубль готовой работы (карточка 45835db4). Признак в логе студии: «completed-state move … rename temp file». Лечение: перенести карточку в нужную колонку руками, а если диспетчер успел перевести её в Blocked (карточка 24c03cfc), сбросить последний запуск и перенести снова.
- Если после неудачного запуска бота изменили, перенос карточки в Ready не запускает её заново: диспетчер отказывается («bot source changed … refusing a fresh sibling») и уводит карточку в Awaiting input (карточка 34e6833c). Выбор такой: Resume в консоли запуска продолжает старый запуск с упавшего узла на новой версии бота (`--force`, сделанная работа сохраняется; карточка при этом остаётся в Awaiting input, хотя запуск идёт) или `iterion issue update <id> --clear-last-run` и перенос в Ready — запуск с нуля.
- Запуск, остановленный fail-узлом (`failed`), не продолжается через Resume, но откатывается к узлу: `POST /api/runs/{id}/rewind` с `{"node_id": "<узел>", "force": true, "restore_scope": "none"}` (файлы рабочей копии не трогаются), затем `POST /api/runs/{id}/resume` с `{"force": true}`. Так 06-11-2026 запуск bugfix, упавший на ошибке гейта `verify`, продолжили с `verify` без повторной работы реализатора.
- Перед повторным запуском карточки, у которой последний запуск был неудачным или «чужим», сбросьте его: `iterion issue update <id> --clear-last-run`, иначе диспетчер продолжит именно тот запуск.

**Если запуск упал до старта** (например, хук `after_create`): ошибка сохраняется на карточке до следующего успешного запуска и не пропадает при Stop диспетчера и перезапуске студии. Её видно в трёх местах: бейдж «✗ did not start: …» на карточке и секция «Did not start» в её окне; панель «Did not start» над списком на странице Runs; та же панель на странице Dispatcher. Везде есть «Show full error» с полным stderr, кодом выхода и путём к логу `~/.iterion/daemons/<ключ>.log`. Записи такой попытки в истории запусков нет, поэтому нет и 404.

## Как создать карточку на доске из терминала

`iterion issue create --title "…" --body "…" --label idea` из рабочей папки нужного проекта: команда сама находит хранилище `~/.iterion/projects/<ключ>/`. `iterion issue list` и `iterion issue show <id>` проверяют результат. Те же поля можно задать через `POST api/v1/native/issues` или `PATCH` карточки; при запросах к студии используйте `curl -L`, потому что часть адресов отвечает перенаправлением.

## Грабли, на которые мы уже наступили

- **Оболочка на Windows.** Хуки диспетчера, guard расписаний, команды плагинов и `command:` узлов `tool` на Windows идут через PowerShell (`pwsh`, иначе `powershell.exe`), на Linux и macOS как раньше через `sh`/`bash`. Выбрать явно: поле `shell:` у хука или переменная `ITERION_SHELL`. Хук, явно написанный на sh, без `shell:` запускается через `sh`, если он найден, иначе падает с понятной ошибкой. Старый sh-пресет посева в сохранённом конфиге при загрузке заменяется PowerShell-вариантом. Подробности и ограничения — `docs/windows.md`.
- Ошибка «Access is denied» при записи хранилища (`sync dir`) и 500 «GetFileInformationByHandle … Access is denied» при сохранении `.bot` в OneDrive исправлены в нашем `main` (второе — по коду и тесту, вживую в OneDrive не повторялось).
- Доска студии теперь подхватывает карточки, изменённые CLI или MCP из другого процесса (атомарная замена файла на Windows больше не теряется); на Board есть кнопка Refresh, сама доска перечитывается при смене фокуса окна.
- Предупреждение «plugin skipped: plugin.yaml not found» для встроенного плагина с одной папкой `cache/` больше не выводится; причина сбоя загрузки плагина показывается на странице Plugins.
- Несуществующий адрес студии показывает страницу 404 со ссылками на Home и Sitemap.
- `iterion issue delete` удаляет карточку (с подтверждением), `issue update --bot/--bot-arg` меняет бота карточки.
- `{{prompts.имя}}` в промпте — ошибка C004: включений нет.
- Предупреждение C128 про `sandbox: none` ожидаемо, если узлам нужен bars.
- Страница Bots пуста, пока в проекте нет бандлов или своих `.bot`, и это не поломка.
- `iterion run` из подпапки проекта пишет запуски в другое хранилище, чем студия на корне, и в Runs студии их не видно (карточка): запускайте из корня проекта.
- Имя модели из примеров iterion может быть устаревшим: проверяйте через `api/models`.
- Скрипты узлов `tool` на PowerShell: одиночная строка, переданная программе через `@переменная`, распадается на символы, а массив из одного элемента, возвращённый функцией, превращается в строку. Оборачивайте в `@(...)` и списки, и результаты функций. Значение `{{…}}` в `command:` на Windows подставляется как строка PowerShell в одинарных кавычках.
- Режим `interaction: llm_or_human` с `interaction_model` на практике бесполезен (карточка a7eb3fcb): отвечающая модель видит только текст вопроса и свой промпт, без кода и истории, а канал `ask_user` у `claude_code` требует бинарник iterion и без него молча пропадает (агент не находит инструмент и продолжает без вопроса). Вместо него — вопрос как поле output агента и отдельный узел-отвечающий в общей сессии (`session_slot`), плюс узел `human` для эскалации. Два узла могут делить один `session_slot` (пример — бот `copilot`).
- `Invoke-RestMethod` отдаёт JSON-массив одним объектом: `@(Invoke-RestMethod …)` даст массив из одного элемента-массива. Сначала присвойте результат переменной и возвращайте её, тогда элементы перечисляются.
- Без `worktree:` в блоке `workflow` iterion ставит `auto`, а не `none`: бот, который должен работать прямо в рабочей копии диспетчера, явно пишет `worktree: none`.
- На Windows значение `{{…}}` в `command:` экранируется удвоением только ASCII-апострофа; типографские кавычки ‘ ’ PowerShell тоже закрывает литерал (карточка 1d826d36). Свободный текст от модели в `command:` не передавайте: пишите его в файл и читайте скриптом. Команда длиннее 12000 символов уходит в PowerShell через stdin.
- Узлы `claude_code` с `capabilities: [board.*]` получают сервер доски (`iterion __mcp-board`) и канал `ask_user` только если iterion нашёл свой консольный `iterion.exe`. На Windows он не находит его никогда (карточка 6dba5e80): ищет соседа без `.exe`, а «исполняемость» проверяет по битам прав, которых у файлов Windows нет, поэтому не помогает и `ITERION_BIN`. Установщик десктопа `iterion.exe` тоже не кладёт. Итог: на Windows у узлов нет инструментов доски и `ask_user`, агент молча работает без них (в логе «could not resolve iterion CLI binary path», в `system/init` `mcp=2`). Наши боты пишут на доску скриптами через REST, вопросы задают своим узлом.
- Комментарии карточки доступны только через API (`GET /api/v1/native/issues/{id}`, поле `comments`), окно карточки в студии их пока не показывает (карточка 45371578). Надёжный способ боту написать комментарий без сервера доски — tool-узел `language: js`, который вызывает REST студии: значения `{{…}}` в `script:` подставляются JSON-литералами, поэтому любой текст модели (кавычки, `$(...)`, обратные кавычки) доходит как есть.
- `POST /api/v1/pipeline-board/tasks` проверяет `blockers` и по ним кладёт карточку в `waiting_deps`, но в карточку их не записывает (карточка ee9775f4): такая карточка из `waiting_deps` сама не выйдет. Обход — сразу после создания `PATCH /api/v1/native/issues/{id}` с `blockers`. Проверено: после этого карточка с `bot_args.auto_ready=true` сама уходит в Ready, когда её блокер становится Done. Поле `parent_id` маршрут пишет только в `bot_args.spawned_from`.
- Бот, который останавливался на human-узле, после ответа продолжает работу вне диспетчера, и захват карточки снимается, только если она осталась в Awaiting input. Такой бот не должен сам переводить свою карточку в рабочую колонку (Ready, Review): она останется захваченной, и диспетчер её больше не возьмёт. Перевод в Done или Blocked безопасен. Любую смену колонки во время запуска, которую диспетчер не делал сам, он считает внешним ходом и прерывает запуск.
- Форма ответа в окне карточки на Board (Last run → Awaiting input) сбрасывается каждые 5 секунд: опрос запуска пересоздаёт объект вопросов, и форма начинает заново (карточка 5aadb596). Пока это не исправлено, отвечайте в консоли запуска (Runs → запуск) или через API.
- Ответ на форму human-узла через API (`POST /api/runs/{id}/answer-human` с `{"answers": {...}}`) отправляйте из PowerShell с телом в UTF-8 (`-ContentType 'application/json; charset=utf-8'` и байтами `[Text.Encoding]::UTF8.GetBytes(...)`). `curl -d` из Git Bash отправляет кириллицу не в UTF-8: 06-11-2026 ответ «да» дошёл как «��», не совпал ни с одним условием, и запуск `lead` ушёл по запасной ветке. Завершённый запуск откатить нельзя (`rewind` принимает только failed, cancelled и паузы), остаётся новый запуск.
- Захват карточки диспетчером — поле `claim` в файле карточки (`<хранилище>/dispatcher/issues/<id>.json`) плюс запись в `dispatcher/claims.json`; диспетчер не берёт карточку, у которой `claim` не пуст. Сам он не снимается, хотя есть `claim_lease_until` (~15 минут): сборщик захватов включается только переменной `ITERION_BOARD_CLAIM_REAPER` (`pkg/dispatcher/reaper.go`). 06-11-2026 карточка ebbb47f3, которую запуск после паузы сам увёл в Blocked, так и стояла в Ready (карточка 2e8e5d28). Поэтому наши боты после паузы свою карточку в Blocked не двигают, а заканчиваются fail-узлом — тогда карточку переводит диспетчер и снимает захват. Перевод своей карточки в Done безвреден. Снять застрявший захват руками можно только при выключенной студии: удалить `claim`, `claimed_at`, `claim_lease_until` из файла карточки (`claim_epoch` оставить) и её запись из `claims.json`.
- Хук `after_create` выполняется с текущей папкой, равной рабочей копии, поэтому подменить её ссылкой (junction) нельзя. Запустить бота в заранее заданной папке DSL не умеет: `worktree` бывает только `auto` или `none`.
- `bars-cli register <папка> --root all` подключает папку к bars сразу: уже работающий сервер bars находит её документы без перезапуска. bars кладёт в эту папку `.bars/` (в репозитории iterion он исключён через `.git/info/exclude`), и после `bars-cli unregister --project <папка>` воркер bars держит открытым `.bars/new-topics.sqlite3`, поэтому папку не удалить, пока воркер bars не перезапущен.
- Агент Sonnet правило «документацию читать только через bars» в промпте соблюдает выборочно: читает `docs/*.md` через `sed`/`cat` и пишет в отчёте, что читал через bars. Что агент делал на самом деле, видно только в `events.jsonl` запуска (события `tool_started` с `tool` и `input`), а не в его отчёте.
- Расход узла `claude_code` — это число ходов, умноженное на размер контекста: каждый вызов инструмента перечитывает всё, что узел уже прочёл. По 77 запускам bugfix (10-11-2026) исследование пропускало через модель 1,1 млн токенов за запуск при 32 вызовах. Отсюда правила для ботов: предел ходов (`tool_max_steps`), явный `reasoning_effort` на каждом узле, готовые данные на вход вместо добывания инструментами (дифф для ревью собирает скрипт), а скилл `bars-docs` (25 КБ) грузить только узлам, которые пишут документацию.
- Имя модели `anthropic/claude-haiku-5-5` работает (пробный запуск 10-11-2026, 0,01 $), хотя `api/models` его не показывает: в реестре студии из Haiku есть только `claude-haiku-4-5`, нет и `claude-sonnet-5-5`, на котором идут все боты. Отсутствие имени в реестре не значит, что модель недоступна.
- `iterion run` из терминала падает до первого узла с «MCP health check failed … "falcon": executable file not found», потому что включён плагин `repo-falcon`, а его программы нет в PATH терминала. Обход — флаг `--skip-mcp-health` или переменная `ITERION_SKIP_MCP_HEALTH`.
- Перезапуск студии прерывает идущие запуски: они получают `PROCESS_ORPHANED` и ждут ручного Resume, сами не продолжаются (карточка 28ba5c40). Запуск `spec` 09–10-11-2026 из-за двух перезапусков и одного исчерпанного бюджета за сутки проработал около пяти часов. Работу этапа до его конца не видно: ветка фичи и зеркало сдвигаются только в `finish` (у старого `spec` — в `publish`), а коммиты лежат в рабочей копии запуска (`work_dir` в `run.json`) — смотреть `git log` там.
- Проект bars документов фичи может оказаться не зарегистрированным (10-11-2026 узлы `spec` получали `project_not_found` и молча читали файлы). С 10-11-2026 `stage.js prepare` проверяет регистрацию, при необходимости регистрирует папку заново и пишет результат в заметку подготовки. Координатор `lead` ставит карточке-фиче метку `feature` (и снимает `idea`): поезд слияний узнаёт фичу по меткам `feature` и `ship`, без `feature` готовая фича ушла бы в Blocked.

## Боты исправления багов доски itterion-test: bugfix и merger

Статус на 10-11-2026: первая версия отработала 77 запусков (медиана 1,50 $ и 10,5 минуты на карточку), поезд сам слил 29 карточек. 10-11-2026 граф bugfix переделан по замерам этих запусков (версия 0.2.0): проверен валидатором и сухим прогоном по двум сценариям, вживую с моделями не запускался. Замеры и обоснование — `itterion-test\drafts\bots-v2-audit.md`, исходный дизайн и решения владельца — `itterion-test\drafts\bugfix-flow-design.md`.

- **Как запустить:** карточки с меткой `bug` перенести в Ready (можно массово, «Move to… → Ready»). Бот `bugfix` ставится сам, руками назначать не надо. Карточки без `bug` не стартуют («no bot»). Карточки `tests`, `tech-debt` и `docs` тоже идут в bugfix: владелец (06-11-2026) решил не заводить для них отдельных ботов, а ставить им метку `bug`.
- **bugfix** (`itterion-test\bots\bugfix\`): `prepare` (забирает историю комментариев карточки через REST и передаёт её узлам с моделью; продолжает ветку, если поезд вернул карточку; отказывается работать вне git-копии iterion) → `triage`, гейтвей на Haiku с уровнем `low` и пределом 12 ходов: отправляет баг на исследование, только если причина не найдена (R1), исправление меняет конкурентность или хранилище (R3), публичный контракт (R4), есть риск для данных или безопасности (R6) либо это возврат из поезда (R7); несколько пакетов, поведение Windows и много вызывающих — заметки, а не причина. `research` (Sonnet high, без правок, bars и веб) исследует и проектирует решение: поле `design` с разделами «Решение», «План изменений», «Вызывающие и тесты», «Контракты», «Документы», «Регрессионный тест», «Приёмка», «Не трогать», «Открытые вопросы»; реализатор идёт по плану, ревью сверяет с ним. Вопрос владельцу задаёт только `research`, один раз и до того, как написан код: когда исправление несовместимо меняет публичный контракт или сохранённые данные либо нужно продуктовое решение (запуск на паузе, карточка в Awaiting input); чего нет в коде и документации, он решает по умолчанию и записывает риск. → `implement` (Sonnet high): регрессионный тест и исправление в отдельной рабочей копии, тесты не запускает, вопросов не задаёт; неразрешимое возвращает в `blocked_reason`, и карточка уходит в Blocked с комментарием → `verify` (чистое дерево, сборка, `go vet` затронутых пакетов) → `diff_pack` (скрипт: коммиты, список файлов, добавленные тесты и дифф до 60 тыс. символов) → ревью судьёй Sonnet high, который получает дифф на входе. Быструю правку, которую ревью отклонило, один раз забирает `research` и проектирует исправление; дальше до двух кругов правок. Ветка `iterion/run/<id запуска>`, карточка уходит в Review. Неуспех (не баг, нужно решение владельца, сборка красная, ревью не одобрило) — комментарий и Blocked. История работы — в комментариях карточки: исследование, каждый проход реализатора (поле `card_comment` на русском) и каждый вердикт ревью публикуют tool-узлы `note_*` через REST, без модели. Узлы, которые документацию только читают, получают правило про bars абзацем в промпте; скилл `bars-docs` целиком грузит только реализатор.
- **merger** (`itterion-test\bots\merger\`), «поезд слияний»: один запуск за раз берёт все карточки с `bug`, которые лежат в Review в момент его старта. Перед сбором он ждёт до `gather_minutes` (10), пока какой-нибудь запуск bugfix на финише (`verify`, ревью, публикация вердикта), и перепроверяет раз в минуту, чтобы карточки, закончившие вместе, ехали одним поездом; опоздавшие едут следующим. В In progress переходит только карточка, на которой запущен поезд; остальные попутчики остаются в Review с меткой `merge-train`, которую поезд снимает в конце. Поезд вливает их ветки в свежую копию main (`worktree: none`, рабочая копия диспетчера), конфликты слияния разрешает Sonnet high, один раз собирает и прогоняет тесты затронутых пакетов и их импортёров. Красное в поезде не чинится: виноватые карточки уходят в Ready на доработку с комментарием и своей веткой, на пятой попытке (`max_attempts`) — в Blocked; остальное — push в origin main, затем fast-forward локального main, ветки удаляются, карточки в Done. Пока main на Windows красный, падение засчитывается только если тест проходит на main (база в `itterion-test\.cache\baseline-wt`, кэш по sha; перепрогон пачкой по пакету); после карточки 4001b573 база убирается. Шаги без LLM — скрипты PowerShell в `scripts/`, доску они пишут через REST студии (`POST …/issues/{id}/comments` с `bot`, `bot_args`, `transition_to`).
- **Диспетчер** (`dispatcher.json` хранилища `-C--itterion-test`): `max_concurrent: 5`, `max_concurrent_by_state: {ready: 4, review: 1}`, `max_attempts: 1` (упавший запуск сразу уводит карточку в Blocked), `stall.timeout_ms: 10800000` (три часа: узел тестов поезда молчит до часа и дольше), `workspace.persist: cleanup_on_done`. Хук `after_create` вызывает `C:\itterion-test\botlib\seed-workspace.ps1` (папка доски не git-репозиторий): рабочая копия — отсоединённая git-копия `C:\itterion-test\iterion` на `main`, а для карточки, у которой в `bot_args` есть `feature_branch`, — на вершине ветки фичи. Хуки диспетчер подхватывает при сохранении настроек, без остановки. У колонки Review включено `eligible`.
- **merger и фичи:** второй триггер мержера — карточка с метками `feature` и `ship` в Review (её туда отправляет координатор `lead`). Ветка берётся из `bot_args.feature_branch`; после слияния поезд удаляет зеркало фичи, снимает её проект bars и удаляет ветку, а узел `manual` (Sonnet) вносит в это руководство правки, которые оставил этап ТЗ (`bot_args.manual_changes`), без коммита.
