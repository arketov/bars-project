## Что такое workflow, бот и бандл

В iterion это почти одно и то же под разными именами. Документация iterion говорит так: «agent workflow» — развёртываемая нагрузка, упакованная как `.bot` или `.botz`, а существующие CLI и API называют её `bot`.

- **Workflow** — граф шагов в файле `.bot`: агенты, судьи (`judge`), роутеры, инструменты, переходы между ними. В файле его задаёт блок `workflow имя:` — точка входа `entry:` и стрелки `a -> b`.
- **Бот** — единица, которую запускают. Это либо одиночный `.bot`-файл, либо **бандл**: папка с `main.bot` и `manifest.yaml` (описание, входные поля, права, режимы вызова) и необязательными `skills/`, `prompts/`, `presets/`.
- **`.botz`** — бандл, упакованный в zip.
- Одиночный `.bot` без манифеста запускается и открывается в редакторе; на странице Bots он показан отдельной группой файлов проекта, но исполнителем диспетчера не бывает.

Узлы в файле: `agent` (LLM с инструментами), `judge` (LLM, который возвращает вердикт по схеме), `router`, `human`, `tool`, `compute`, `subbot`. Схемы (`schema`) описывают вход и выход узлов, промпты (`prompt`) — тексты. Подстановка одного промпта в другой (`{{prompts.имя}}`) не существует: ошибка C004, текст повторяют в каждом промпте.

## Где лежат workflow и что показывает каталог ботов

- Студия сохраняет новый workflow туда, куда указал пользователь; по умолчанию это корень проекта. Настройки «писать в `.iterion/`» нет (идея — карточка на доске `itterion-test`).
- Сохранение из студии приводит файл к канонической форме (порядок полей, запятые); об этом предупреждает тост и заметка в Save As. Файл, открытый через Open…, сохраняется под своим именем. Для нового документа Save As предлагает имя через дефис (`dev-flow.bot`).
- Боты ищутся только в `bots/`, `examples/`, `.botz/` проекта (`botregistry.DefaultPaths`) и одиночные `.bot` в корне проекта, без захода во вложенные репозитории и без фрагментов `lib/`. Так работает панель Project files на стартовой странице редактора; страницу Bots и FilePicker приводят к тому же правилу (в работе 06-11-2026).
- Встроенного каталога ботов в списках студии нет: владелец от него отказался, и 06-11-2026 встроенные боты убраны со страницы Bots, стартовой панели, выбора бота в карточке и формы диспетчера. Пресет диспетчера по умолчанию ещё ссылается на встроенных ботов, это исправляется.
- Папка `.iterion/` рядом с сохранённым файлом служебная: страховочные копии (`.iterion/authoring/`) и блокировки, внутри свой `.gitignore`. Если кладёте в `.iterion/` свои файлы, добавьте папку в `.gitignore` проекта.
- Хранилище проекта — `~/.iterion/projects/<ключ>/`: доска (`dispatcher/board.json`, `dispatcher/issues/<id>.json`, `events.jsonl`, `claims.json`, `runtime.json`), запуски (`runs/`), рабочие копии запусков (`worktrees/<run-id>`).

## Где iterion хранит данные: в проекте, в `~/.iterion` или в AppData

Три места, у каждого своя роль (проверено осмотром диска 05-11-2026 и чтением `store.ResolveStoreDir`).

| Что | Где |
|---|---|
| Ваши файлы: `.bot`, бандлы `bots/<имя>/` | В папке проекта, куда вы сохранили. Это единственное, что студия кладёт в проект как «своё». |
| Страховочные копии и блокировки при сохранении | В проекте: `<проект>/.iterion/authoring/` (создаёт приложение, внутри `.gitignore` со звёздочкой). |
| Доска (`dispatcher/board.json`, `issues/`, `events.jsonl`), запуски (`runs/`), рабочие копии запусков, настройки диспетчера, каталог ботов диспетчера (`dispatcher/bots`) | В хранилище проекта: `~/.iterion/projects/<ключ-пути-проекта>/`. Ключ — путь проекта с заменой разделителей на дефисы. |
| Плагины (`plugins/bars`), включённость плагинов (`plugins.yaml`), вход в iterion (`cli-auth.json`) | Общие для всех проектов: `~/.iterion/`. |
| Адрес и pid работающего сервера студии, его лог | `~/.iterion/daemons/<ключ>.json` и `.log`. |
| Настройки окна приложения, список проектов, блокировки процесса | `%APPDATA%\Iterion\` (`config.json`, `iterion-desktop-*.lock`). |

**Правило выбора хранилища.** По умолчанию всё из строки про доску лежит в `~/.iterion/projects/<ключ>/`. Хранилище переезжает в проект только тогда, когда в папке проекта есть `.iterion/` с признаками управляемого хранилища: подпапка `runs/`, `dispatcher/` или файл `.iterion-store`. Одной `.iterion/authoring/` для этого мало, поэтому у `bars-project` хранилище глобальное. Флаг `--store-dir` (и `ITERION_HOME` для плагинов) переопределяет место.

## Что такое «проект» в студии и что делает переключатель проектов

Проект в iterion — это рабочая папка, которую обслуживает окно. От неё зависит всё остальное: список файлов, каталог ботов (`bots/`, `examples/`, `.botz/` внутри папки), доска, запуски, диспетчер и хранилище `~/.iterion/projects/<ключ>/`. Одно окно открывается под один проект, и для него запускается свой сервер студии (адреса в `~/.iterion/daemons/`).

Переключателя проектов в боковой панели больше нет (убран 05-11-2026: он менял только список файлов, а боты, доска и диспетчер оставались от прежнего проекта). Боковая панель только показывает имя проекта. Другой проект открывают отдельным окном десктопа (Ctrl+P), и у него свой сервер.

## Как открыть существующий `.bot` в студии

- **Open…** (Ctrl+O, в том числе на стартовой панели без вкладок) открывает поиск по файлам проекта. Файл привязывается к своему пути: Save пишет поверх него, Launch запускает его.
- **Import copy…** берёт файл с диска как копию без пути: Save создаёт новый файл в проекте, оригинал не трогает.
- Стартовая панель редактора показывает панель Project files по правилу поиска ботов выше и недавние файлы. Файл вне `bots/`, `examples/`, `.botz/` и корня проекта сейчас открывается только через Import copy (карточка на доске).

## Как запустить workflow

- **Студия:** открыть файл в редакторе и нажать Launch. Окно запуска просит значения переменных (`vars`), показывает бэкенд и оценку стоимости. Ход запуска виден на странице **Runs**.
- **Терминал:** `iterion run файл.bot --var имя="значение"`; пределы `--max-cost-usd`, `--max-duration`. Исчерпанный предел ставит запуск на паузу, продолжить можно через `iterion resume`.
- **С доски:** карточку берёт диспетчер, см. раздел про диспетчер ниже.
- `worktree: auto` в workflow запускает его в отдельной рабочей копии репозитория; рабочая папка проекта не меняется, а в конце результат вливается по правилам `merge_into`.
- Если `iterion` нет в PATH, его собирают из клона: `go build -o <папка> ./cmd/iterion` с `GOFLAGS=-mod=vendor` и кэшем Go внутри рабочей папки.

## Как проверить workflow без запуска через работающую студию

Адрес сервера студии лежит в `~/.iterion/daemons/<ключ-проекта>.json` (поле `url`). Порт меняется при каждом перезапуске приложения, поэтому его читают заново.

1. `POST <url>api/parse` с телом `{"source": "<текст .bot>"}` отвечает документом и ошибками разбора.
2. `POST <url>api/validate` с телом `{"document": <документ из шага 1>, "path": "файл.bot"}` отвечает `valid`, `diagnostics` (ошибки C…) и `warnings`.

Проверка не запускает модели и бесплатна. Имена MCP-серверов в `tools:` проверяются по известным серверам (плагины, `mcp_server`, `.mcp.json` проекта): неизвестный `mcp.нет_такого.x` даёт предупреждение C332. Если в `.mcp.json` проекта есть сервер с зарезервированным именем (`iterion`), каталог серверов не собирается и C332 молча пропадает (карточка на доске); свой сервер iterion называйте `engine`. Что сервер реально запустится, подтверждает только запуск. Опечатка в имени модели проверку пока проходит (карточка).

Из терминала то же и глубже даёт `iterion validate <файл или папка бота>`: с `--exec` сухой прогон без модели, оболочки и рабочей копии (подставляет промпты, называет нерешённые ссылки, проходит условия «все истинны» и «все ложны»), с `--explain` разбор того, какие встроенные инструменты оставляет `tools:` узлу `claude_code`. Для `bots/dev-flow` 05-11-2026 `--exec` дал «verdict: clean» (оба прохода завершились как задумано, цикл `fix_loop(3)` закончился явным выходом `REVIEW_NOT_APPROVED`, нерешённых ссылок нет), а `--explain` показал, что планировщик сохраняет только `Glob`, `Grep`, `Read`, ревьюер ещё `Bash`, реализатор все встроенные инструменты. Коды выхода: 0 проверка пройдена, 1 найден дефект, 2 файл не найден.

## Как назвать модель в узле и проверить имя

Строка вида `model: "anthropic/claude-sonnet-5-5"`. Примеры в документации iterion устарели (там `claude-sonnet-4-6`). Список известных моделей и их годность на этом компьютере отдаёт `GET <url>api/models?spec=anthropic/claude-sonnet-5-5`: строка с `usable: true` означает, что модель известна и учётные данные найдены. Принятие модели провайдером подтверждает только запуск.

## Как узлам workflow дать bars для чтения документации

Контракт установки плагина — в [подключении клиентов](../features/clients/clients.md), раздел iterion; пользовательская инструкция — в [руководстве по агентам](agents.md). Для узла `claude_code` важно следующее:

- iterion запускает Claude Code только со своим списком MCP-серверов, поэтому bars доходит до узлов через плагин `bars` в `~/.iterion/plugins/bars/`. Включён ли он, показывает `GET <url>api/v1/plugins`.
- Сервер из плагина попадает в каждый узел сам. Если он не запустился, узел работает без него и молча. Чтобы падать громко, инструменты называют в `tools:` как `mcp.bars.bars_rag_search`, `mcp.bars.bars_read` и так далее.
- Список `tools:` у `claude_code` превращается в запрет остальных встроенных инструментов (Read, Edit, Bash, …), которых в списке нет. Реализатору, которому нужно править файлы, `tools:` не задают; планировщику и ревьюеру перечисляют `read_file`, `glob`, `grep` (ревьюеру ещё `bash` для `git diff`) и инструменты bars.
- В песочнице (`sandbox: auto` при установленном Docker) `bars-mcp` недоступен: нужен `sandbox: none` в блоке `workflow`. iterion предупредит C128, это ожидаемо.
- Рабочая копия запуска лежит вне репозитория; bars видит проект основной папки, поэтому документы, изменённые внутри запуска, не находятся до слияния.
- Требование «документацию читать только через bars» держится на тексте промптов и на поле-свидетельстве: планировщик возвращает `docs_read`, ревьюер без него не одобряет.

## Доска и диспетчер: почему карточка в Ready не берётся

Доска (**Board**) — канбан проекта: колонки `inbox`, `backlog`, `ready` и другие. Перенос в `ready` ничего не запускает: карточки берёт **диспетчер** (страница **Dispatcher**). Состояние на 05-11-2026: `GET <url>api/v1/dispatcher/status` вернул `{"state":"idle","has_config":false}` — диспетчер не запущен и без конфига.

Чтобы карточка запустилась, нужны три вещи:

1. **Запущенный диспетчер.** На странице Dispatcher кнопки Start/Pause/Stop и форма Settings. Без конфига есть кнопка «Use default settings», при существующем конфиге — «Reset to default settings» (с подтверждением; через API `POST api/v1/dispatcher/defaults/apply?replace=1`). Workflow path выбирается из списка ботов с поиском, студия подставляет абсолютный путь. Относительный путь, вписанный руками, считается от папки конфига `<хранилище>/dispatcher/`, а не от проекта (карточка на доске, исправляется). Пресет по умолчанию: встроенная доска, опрос раз в 30 секунд, хук посева рабочей копии (`after_create`), на Windows в PowerShell-варианте.
2. **Бот-исполнитель у карточки:** поле `assignee` или `bot`, оба выбираются из списка ботов проекта. Карточка без исполнителя не запускается (`require_assignee` в пресете): на ней пометка «no assignee — won't start», на странице Dispatcher строка в «Won't dispatch». Метки на выбор бота не влияют. Имя, которое не совпадает ни с одним ботом (имя человека, опечатка), пока уходит на запасной бот `default`; это исправляется (карточка).
3. **Сопоставление полей карточки с переменными бота.** У каждого бота свои входные поля (`feature_dev` ждёт `feature_prompt`). Для собственного workflow есть два пути:
   - **Бандл в `bots/<имя>/` проекта.** Диспетчер по умолчанию находит и такие боты как исполнителей, а поля берёт из `dispatch_vars` в `manifest.yaml`, например `task: |-` и под ним `{{issue.title}}` и `{{issue.body}}`. Тот же бандл появляется на странице Bots. Это путь, который сопоставляет карточку и каталог сразу.
   - **Конфиг диспетчера:** `assignee_workflows:` (имя исполнителя → путь к `.bot`) и `assignee_dispatch:` с `vars:`.

После взятия карточка переходит в `in_progress`, на ней появляется ссылка на запуск, в заголовке запуска написано «From ticket». Запуск с доски по-настоящему тратит токены. Пошаговый рецепт по-английски — `docs/howto-board-bot.md`, куда попадает результат — раздел «Where the result goes» в `docs/dispatcher.md`.

**Если запуск упал до старта** (например, хук `after_create`): ошибка сохраняется на карточке до следующего успешного запуска и не пропадает при Stop диспетчера и перезапуске студии. Её видно в трёх местах: бейдж «✗ did not start: …» на карточке и секция «Did not start» в её окне; панель «Did not start» над списком на странице Runs; та же панель на странице Dispatcher. Везде есть «Show full error» с полным stderr, кодом выхода и путём к логу `~/.iterion/daemons/<ключ>.log`. Записи такой попытки в истории запусков нет, поэтому нет и 404.

## Как создать карточку на доске из терминала

`iterion issue create --title "…" --body "…" --label idea` из рабочей папки нужного проекта: команда сама находит хранилище `~/.iterion/projects/<ключ>/`. `iterion issue list` и `iterion issue show <id>` проверяют результат. Те же поля можно задать через `POST api/v1/native/issues` или `PATCH` карточки; при запросах к студии используйте `curl -L`, потому что часть адресов отвечает перенаправлением.

## Грабли, на которые мы уже наступили

- **Оболочка на Windows.** Хуки диспетчера, guard расписаний, команды плагинов и `command:` узлов `tool` на Windows идут через PowerShell (`pwsh`, иначе `powershell.exe`), на Linux и macOS как раньше через `sh`/`bash`. Выбрать явно: поле `shell:` у хука или переменная `ITERION_SHELL`. Хук, явно написанный на sh, без `shell:` запускается через `sh`, если он найден, иначе падает с понятной ошибкой. Старый sh-пресет посева в сохранённом конфиге при загрузке заменяется PowerShell-вариантом. Подробности и ограничения — `docs/windows.md`.
- Ошибка «Access is denied» при записи хранилища (`sync dir`) и 500 «GetFileInformationByHandle … Access is denied» при сохранении `.bot` в OneDrive исправлены в нашем `main` (второе — по коду и тесту, вживую в OneDrive не повторялось).
- Доска студии теперь подхватывает карточки, изменённые CLI или MCP из другого процесса (атомарная замена файла на Windows больше не теряется); на Board есть кнопка Refresh, сама доска перечитывается при смене фокуса окна.
- Предупреждение «plugin skipped: plugin.yaml not found» для встроенного плагина с одной папкой `cache/` больше не выводится; причина сбоя загрузки плагина показывается на странице Plugins.
- Несуществующий адрес студии показывает страницу 404 со ссылками на Home и Sitemap.
- `iterion issue delete` удаляет карточку (с подтверждением), `issue update --bot/--bot-arg` меняет бота карточки.
- `{{prompts.имя}}` в промпте — ошибка C004: включений нет.
- Предупреждение C128 про `sandbox: none` ожидаемо, если узлам нужен bars.
- Страница Bots пуста, пока в проекте нет бандлов или своих `.bot`, и это не поломка.
- `iterion run` из подпапки проекта пишет запуски в другое хранилище, чем студия на корне, и в Runs студии их не видно (карточка): запускайте из корня проекта.
- Имя модели из примеров iterion может быть устаревшим: проверяйте через `api/models`.
