# Сборка bars — как собрать, проверить и что не проверяется

Как собирается Cargo workspace bars ([architecture/components.md](../architecture/components.md)) и какие проверки гоняются перед коммитом. Версии крейтов — [architecture/stack.md](../architecture/stack.md).

## Требования к машине разработчика bars

- Rust `1.99.0`: версия закреплена в `rust-toolchain.toml` вместе с компонентами `rustfmt` и `clippy`. Нижняя граница стека — 1.90 ([architecture/stack.md](../architecture/stack.md)); точный пин нужен, чтобы сборка не менялась от обновления stable.
- Windows: MSVC 17.14+, CMake/Ninja, Vulkan SDK (`VULKAN_SDK`; `scripts/build-installer.ps1` находит его сам, остальные команды ждут переменную) и LLVM для bindgen в `llama-cpp-sys-2` (`LIBCLANG_PATH`, например `C:\Program Files\LLVM\bin`). Всё ставится через winget: `LLVM.LLVM`, `Kitware.CMake`, `Ninja-build.Ninja`, `KhronosGroup.VulkanSDK`. Для нативной GGUF-сборки использовать Developer PowerShell последнего MSVC, `CMAKE_GENERATOR=Ninja`, `CMAKE_BUILD_PARALLEL_LEVEL=1`. MSBuild с вложенным shader generator нестабилен на чистом каталоге. macOS: Xcode Command Line Tools; Metal не проверен.
- git в `PATH`: `bars-protocol` берёт из него идентификатор сборки для сверки в `hello` ([протокол](../architecture/protocol.md)); без git сборка идёт, но проверка сборок молчит (`unknown`).
- Сеть: `ort` скачивает ONNX Runtime с `cdn.pyke.io` при первой сборке `bars-core`.

## Подготовка PowerShell для проверок Windows

Для пересборки bindgen 25-10-2026 найден рабочий `LIBCLANG_PATH=C:/Program Files (x86)/Microsoft Visual Studio/2022/BuildTools/VC/Tools/Llvm/x64/bin`. Пути `C:/Program Files/LLVM/bin` и `C:/BuildTools/VC/Tools/Llvm/x64/bin` на этой машине отсутствовали; наличие готового Cargo-кэша скрывало это до пересборки `llama-cpp-sys-2`. Линковщик по-прежнему выбирается из последнего MSVC через vswhere, независимо от места DLL clang. Отдельный сбой LNK1180 означает нехватку дискового места: в срезе снижения нагрузки был зафиксирован нулевой запас C:, после появления свободного места сборка продолжена без очистки общего target.

Проверено 25-10-2026 полным `scripts/check.ps1 -Jobs 2`: одного наличия Rust, Visual Studio и SDK на диске недостаточно — текущему процессу нужны их пути и окружение линковщика. В обычной оболочке `cargo` мог отсутствовать в PATH; без `VULKAN_SDK` сборка `llama-cpp-sys-2` завершалась ошибкой `NotPresent`. Старый Community приводил к LNK2001 из ORT, включая `__std_max_8u`; выбранный через `vswhere -latest` MSVC в `C:/BuildTools` устранил этот сбой. Ограничение версии и прежнее воспроизведение — в [опыте сборки GGUF](gguf-models.md), раздел «Сборка и найденные ограничения GGUF».

Подготовка в отдельном процессе PowerShell, из корня проекта; путь SDK ниже — проверенный на этой машине, на другой машине нужен её установленный SDK:

```powershell
$env:PATH = "$env:USERPROFILE/.cargo/bin;$env:PATH"
$barsVswhere = Join-Path ${env:ProgramFiles(x86)} 'Microsoft Visual Studio/Installer/vswhere.exe'
$barsVs = & $barsVswhere -latest -products '*' -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64 -property installationPath
& (Join-Path $barsVs 'Common7/Tools/Launch-VsDevShell.ps1') -Arch amd64 -HostArch amd64 -SkipAutomaticLocation
$env:VULKAN_SDK = 'C:/tools/VulkanSDK/1.4.363.0'
$env:LIB = "$env:VULKAN_SDK/Lib;$env:LIB"
$env:PATH = (Join-Path $barsVs 'Common7/IDE/CommonExtensions/Microsoft/CMake/Ninja') + ';' + $env:PATH
$env:CARGO_TARGET_DIR = 'C:/bt/bars'
pwsh -File scripts/check.ps1 -Jobs 2
```

Окружение меняется только у текущего процесса и его потомков. `check.ps1` сам задаёт `LIBCLANG_PATH`, Ninja и ограничение параллельности CMake; он не выбирает MSVC и Vulkan SDK. Для установщика сохраняется штатный `scripts/build-installer.ps1`, который готовит окружение сам.

Автовыбор libclang в `check.ps1` срабатывает только при наличии `C:/Program Files/LLVM/bin`. Если этой папки нет, bindgen может использовать уже установленный x64 libclang из Visual Studio: в 2.2.6 проверен `C:/Program Files (x86)/Microsoft Visual Studio/2022/BuildTools/VC/Tools/Llvm/x64/bin`. Перед запуском задают `LIBCLANG_PATH` на существующую папку с `libclang.dll`; наличие другого MSVC в `C:/BuildTools` само по себе эту переменную не задаёт. Глобальные переменные и установленный LLVM для этого менять не требуется.

`-Jobs` ограничивает задания Cargo, а `$env:RUST_TEST_THREADS = '1'` — одновременно выполняемые Rust-тесты внутри каждого бинарника. Последний параметр использован в зелёном прогоне 2.2.5 вместе с `-Jobs 2`; тесты и их лимиты не отключались. Это проверенный режим диагностики нагрузки, а не новое умолчание скрипта и не доказательство причины прежних нестабильностей. Несколько Cargo-процессов с общим `C:/bt/bars` ожидают замок (`Blocking waiting for file lock on build directory`): ожидание не означает сбой. Общий кэш не очищать и чужие процессы не останавливать. Длительность совмещённого прогона не считать бенчмарком скорости сборки.

При параллельных прогонах 2.2.6 наблюдались LNK1104 на тестовом exe и E0463 о недоступном крейте; их причина отдельно не установлена. Для воспроизведения важны полный текст ошибки, время запуска и текущие незавершённые изменения. Ошибки отсутствующих функций или вариантов enum в новом исходнике не следует автоматически объяснять кэшем. При E0425 наличие функции в исходнике и её имени в `.rmeta`, прочитанных после отказа, не доказывает, что упавший вызов компилятора использовал именно этот срез. Для диагностики сохраняют verbose-лог сборки с фактическим `--extern` и набором features; очистка общего кэша не заменяет выяснение причины. Зелёные целевые тесты не превращают красный общий `check.ps1` в зелёный; закрытие отдельного среза с таким блокером требует явного решения автора, как OQ-192.

Наблюдение 01-11-2026, срез 4.3.4: целевые 11 Rust-тестов текстового рендера прошли, но `cargo build --workspace --example workspace_probe` не увидел новые поля `text`, `scope`, `by_module` и модуль `graph_text` у `bars-protocol`. Полный `scripts/check.ps1 -Jobs 2` прошёл fmt/clippy и остановился на отсутствии `truncate_text_page`/`rematerialize_text_reply` у `bars-graph`. Эти поля и функции были в исходниках; фактические `--extern` упавших вызовов не записаны, причина не установлена. Обновление времени файлов для штатной пересборки не подтверждено успешным результатом: свои повторные процессы остановлены по указанию автора во время ожидания общего кэша. Отрицательные логи сохранены локально, кэш и чужие процессы не трогались; разрешение автора закрыть этот срез не меняет общего правила зелёного гейта.

## Изоляция временных проектов внутри checkout

В 3.5.7 перенаправление `TEMP`/`TMP` прямо в `.bars/task-357/test-temp` изменило результат тестов поиска корня: `discover_root` поднимался к настоящему `.bars/config.toml` checkout, а тесты регистрировали рабочий репозиторий вместо искусственного проекта. Это не отказ нового координатора. Для сохранения всех файлов внутри проекта проверен временный `subst T: <checkout>/.bars/task-357/test-temp` и `TEMP=TMP=T:\`: у тестового пути нет родителя с конфигурацией checkout. Отдельный тест обнаружения корня проходит. Буква должна быть свободна; после выхода своих тестов отображение снимают `subst T: /D`. Сборка продолжает использовать единственный `C:/bt/bars`; это отображение только одноразовых файлов тестов.

## Одновременные IPC-тесты из разных процессов

При отдельном запуске тестового exe сначала проверить `--list`: нужные новые тесты должны присутствовать. Дата файла и одинаковое имя в `C:/bt/bars/debug/deps` не подтверждают нужный срез исходников. В сессии 6.3.2 свежий бинарник другого среза не содержал новых регрессий миграции; фильтр дал `running 0 tests`. Такой запуск не является проверкой, даже если код выхода 0.

Перед прямым запуском готового тестового exe проверять `--list`: в списке должны присутствовать точные имена новых регрессий текущего изменения. Успешный код выхода при нуле подходящих тестов не подтверждает исправление. Свежий mtime бинарника сам по себе тоже недостаточен: 01-11-2026 при параллельных сборках найден `bars_worker`, в котором отсутствовали все пять новых тестов 5.2.2; причина несоответствия не установлена. Следующий полный прогон должен подтвердить исполнение этих имён, а не только наличие exe.

Для адресного повтора после полного гейта сохранять полный набор целей: `cargo test --workspace --lib --tests --bins <имя_теста>`, с тем же `CARGO_TARGET_DIR=C:/bt/bars` и окружением сборки. Фильтр имени сужает исполнение, сохраняя объединение features. В срезе 2.4.1 ограничение `--workspace --test mcp` породило отдельный CMake-вариант с отказом вложенного MSBuild; расхождения features при выборе одного крейта описаны в разделе «Проверки перед коммитом». Эти команды не заменяют полный гейт. Для точного повтора без пересборки допустим уже собранный тестовый exe того же прогона; успешный повтор не закрывает исходный отказ.

Имена IPC в тестовых Harness CLI, MCP и worker включают уникальное имя временного профиля. Два Harness с одинаковым логическим именем получают разные каналы, в том числе в разных процессах. `$env:RUST_TEST_THREADS='1'` ограничивает тесты одного бинарника, но не заменяет изоляцию каналов.

Регрессия `two_test_workers_with_same_label_have_separate_registries` запускает два тестовых воркера с одним ярлыком и проверяет отдельные реестры проектов. С прежним фиксированным каналом клиенты увидели общий реестр из двух проектов; после добавления суффикса та же проверка проходит (OQ-200). Это доказывает механизм коллизии, но не приписывает ему автоматически каждый исторический таймаут или `UnexpectedEof`.

Каналы изолированы, общий Cargo-кэш и исполняемые тестовые файлы — нет. Windows не даёт перелинковать работающий exe: LNK1104 при открытии `bars_worker` требует дождаться окончания использующего его набора. Отсутствие процесса перед стартом полного скрипта не гарантирует свободный exe позже: между fmt, clippy, build и test другой прогон может начать тесты. В сессии 3.3.4 зафиксированы два таких отказа линковки; после завершения остальных Cargo-процессов следующий полный скрипт прошёл. Для заключительного повтора эта сессия не меняла код меню или таймауты; смежные исходники менялись параллельно. Это наблюдение о совместном кэше, не доказательство причины прежних таймаутов. Чужие процессы не останавливать, кэш `C:/bt/bars` не очищать. Сохранять отрицательные логи; успешный повтор не считается исправлением неизвестной причины. Остальные нестабильности времени выполнения — OQ-201.

Отказ `could not execute process … (never executed)` с Windows `os error 32` означает, что соответствующий тестовый exe не запустился; проход соседних наборов его не заменяет. В 2.4.2 так остановился `search_corpus`; отдельный запуск или повтор другого набора не делает исходный гейт зелёным. `AlreadyRunning` на `ipc::bind` — другой класс отказа: в срезе 2.4.2 он зафиксирован у `full_rebuild_keeps_status_window_controls_and_full_ipc_search_responsive`, отдельный повтор того же exe прошёл за 6,57 с, затем прошёл полный скрипт. Причина конкретного отказа bind не установлена (OQ-200); это не таймаут OQ-201.

Не все тесты воркера прошли на уникальные имена: `iss16-concurrency`, `history-restart`, `refresh-blocked-ready` и `default-worker-no-client-profile` берут фиксированные имена канала. Наблюдение 28-10-2026: при параллельном прогоне другой сессии `check.ps1` падал на `AlreadyRunning`, `vanished_project_folder_is_unavailable` — на `os error 145` («Папка не пуста»); по отдельности и при повторе на тихой машине тесты зелёные. Падение с такой причиной сначала проверяют повтором и отдельным запуском (`cargo test -p bars-worker --lib -- <имя>`), а не правкой кода.

## Таймауты тестов воркера в общем наборе

В заключительном полном прогоне шага 3.1.1 от 26-10-2026 fmt, clippy и build прошли, но `full_rebuild_keeps_status_window_controls_and_full_ipc_search_responsive` завершился с `Elapsed(())`, а `hundreds_of_files_at_once_reach_the_index` — ожиданием «все файлы в индексе». Отдельные запуски тех же тестов без изменения кода и лимитов прошли за 3,55 и 4,81 с. Это не зелёный общий скрипт и не доказательство причины отказа; OQ-201 остаётся открытым. Не увеличивать таймауты и не отключать проверки ради зелёного результата.

В более ранних прогонах того же среза два CLI-теста упали при одновременных запусках; отдельно весь CLI-набор прошёл 9/9. Наблюдение относится к гипотезе OQ-200, но не доказывает пересечение каналов. Ещё один прогон остановился на LNK1104 при открытии тестового `bars_worker.exe`. Отрицательные логи и отдельные повторы сохраняются вместе; последующий зелёный прогон другого среза не подменяет результат этой сессии.

## Запуск изолированных Tauri/WebView2-проб Windows

В стенде подписок 3.5.7 создание дополнительных WebView вынесено в асинхронную Tauri-команду: синхронный `WebviewWindowBuilder::build` из command handler зависал на первом окне документа, хотя успевал создать его профиль. `window_updates_probe.js` проверяет свежую правку, сделанную при скрытых окнах; старый текст в DOM не доказывает восстановления. Для ввода нужно дождаться загруженного `.cm-content[contenteditable="true"]`. Сравнивать при ошибке обхода следует пути файлов/папок, а не весь текст дерева: счётчик чанков может законно меняться.

Для учёта IPC в Tauri 2.12.3 перехватывается `fetch` к `ipc.localhost`: `__TAURI_INTERNALS__.invoke` неизменяемый, попытка присваивания не дала реальных счётчиков. Размер повторно закодированного UTF-8 JSON тела — оценка передаваемых данных без заголовков; затраты кодировщика входят в CPU WebView. Метрики процесса включают логические чтения, в том числе IPC, и не доказывают физический дисковый IO. Старый и новый UI для сравнения встраиваются отдельно в собственные копии exe; `ui/dist` после подготовки исходной версии обязательно возвращается к новому UI.

Для адресных host-событий используется `getCurrentWindow().listen`: общий `listen` с target Any получал также видимость чужих окон. Нативное скрытие не всегда меняет `document.hidden`; фактическая видимость должна поступать от host и читаться до запуска опроса. В тестах сериализованной аренды mock `project_observe` обязан завершать запрос штатным подтверждением: бесконечная заглушка блокирует последующие привязки, а не доказывает ошибку доставки событий. На большом корпусе перед инъекцией отказа корня стенд ждёт готовности индекса и отменяет граф; два прежних rename получили `os error 5`, конкретный открытый дескриптор не определён. Порог свежести 2 с этим ожиданием не меняется.

Собранный Rust example не обязательно получает ресурсы и манифест основного exe. ## Где хранятся артефакты сборки target

Локальный Vulkan SDK найден также в `C:/tools/VulkanSDK/1.4.363.0`. Штатный установочный скрипт проверяет `VULKAN_SDK`, `C:/VulkanSDK` и `C:/tools/VulkanSDK`; каталог `Lib` выбранного SDK добавляет в окружение линковщика текущего процесса. Это позволяет использовать готовые C++-артефакты, даже если их кэш сохранил старый путь к import library `vulkan-1.lib`. Глобальные переменные и установленный SDK скрипт не меняет.

Cargo без переопределений пишет в `target/` корня workspace, но на этой машине там ломается llama.cpp, поэтому каталог сборки задаётся явно — единственный кэш `C:\bt\bars`:

```powershell
$env:CARGO_TARGET_DIR = 'C:/bt/bars'
```

`scripts/build-installer.ps1` сохраняет заданный `CARGO_TARGET_DIR`; без него использует `<корень репозитория>/target`. EXE лежат в `<target>/debug/` или `<target>/release/`, NSIS — в `<target>/release/bundle/nsis/`; скрипт копирует установщик в `dist-installer/` либо указанный `-OutDir`. Это разные места: `target` — рабочие артефакты, выходной каталог — копия для передачи.

Если работающий Vite удерживает `rolldown-binding.win32-x64-msvc.node`, `npm ci` может завершиться EPERM при удалении зависимостей. Не останавливать чужой процесс: для уже установленных зависимостей `scripts/build-installer.ps1 -SkipNpmCi` сначала проверяет `npm ls --depth=0`, затем собирает UI. Если предыдущий `npm ci` успел удалить часть пакетов, восстановить `npm install --ignore-scripts --prefer-offline` и проверить неизменность `package-lock.json` перед сборкой. Флаг не разрешает менять версии зависимостей.

На машине разработки release-артефакты лежат в `target/` репозитория. Наличие папки не определяет, куда пишет следующий запуск: это задают `CARGO_TARGET_DIR` и текущий workspace. Не очищать общий Cargo target ради отдельного теста.

## Где хранятся временные файлы тестов и кэш моделей

Фикстура прогресса скачивания проверяет логический размер файла, а не содержимое весов. На Windows её файл помечается разреженным через штатный `fsutil sparse setflag` до `set_len`: значения 50/99/100 % проверяются с прежними размерами, но тест не записывает несколько гигабайт нулей и не требует столько свободного места на C:. Это не относится к настоящим моделям и кэшу сборки.

| Данные | Место и жизненный цикл |
|---|---|
| Временные проекты, индексы и профили Rust-тестов | `tempfile::TempDir` в системном временном каталоге; на Windows обычно `%TEMP%` (`C:/Users/arketov/AppData/Local/Temp` на проверенной машине). Каталог удаляется при штатном уничтожении `TempDir`; аварийное завершение может оставить остатки |
| Изолированный профиль интеграционного стенда | `BARS_USER_HOME` указывает на домашнюю папку стенда внутри собственного временного каталога; настройки клиентов и данные bars создаются в ней. Рабочий профиль пользователя не использовать |
| Скачанные встроенные модели | `<домашняя папка>/.bars/models/`, на проверенной машине `C:/Users/arketov/.bars/models/`; это общий постоянный кэш, а не временные данные теста и не `.bars` проекта. Контракт — [local-models.md](../features/models/local-models.md#где-лежат-скачанные-модели) |

Аппаратные исследования используют один собственный временный каталог вне репозитория, существующие веса только для чтения без копий. После сохранения небольших доказательств убрать собственные временные данные, включая неуспешный выход; общие модели и чужие артефакты не удалять (решение автора OQ-107 в `QUESTIONS.md`). Тесты с настоящей моделью, описанные далее, читают готовый пользовательский кэш без скачивания; не все временные файлы проекта создаются через `TempDir`.

Шаги скрипта: `cargo fmt --all --check`; `cargo clippy --workspace --all-targets -- -D warnings`; `cargo build --workspace`; `cargo test --workspace --lib --tests --bins --no-fail-fast`; затем в `ui/` `npm run check` и `npm test`. Каждый cargo-шаг идёт с `-j 3` (число меняет `-Jobs`).

Почему не просто `cargo test --workspace`: при числе заданий по умолчанию линковщик Windows падает на примерах и тестах `bars-core` с `link.exe failed: exit code 1` без текста ошибки; на 8,9 из 31,6 ГБ свободной памяти это воспроизведено дважды (аудит внутренней части 23-10-2026, ВН-03). Причина не установлена, вероятная — нехватка памяти при одновременной линковке больших бинарников с отладочной информацией. С `-j 3` сборка проходит; `--lib --tests --bins` не собирает примеры, которые никто не запускает. Примеры с тяжёлыми стендами запускаются отдельно, своими скриптами из `scripts/`.

Если `CARGO_TARGET_DIR` не задан, скрипт сам ставит `C:/bt/bars` — единственный кэш сборки (раздел «Длинный путь генератора Vulkan на Windows»): в `target\` репозитория длинный путь ломает `llama-cpp-sys-2`. Так же по умолчанию поступают `probe-*.ps1`, `run-memory-acceptance.ps1`, `test-client-profile-isolation.ps1`, а `test-client-refresh.ps1`, `test-docs-delivery.ps1` и `test-mcp-disk-read.mjs` берут бинарники из `C:/bt/bars/debug`. Частичный `cargo test -p bars-worker --lib` в сессии OQ-206 получил ошибку `Arc<Dataset>: Serialize`; общий workspace собрался и прошёл без изменения сериализации. При таком расхождении сначала сверяется набор фич. Команды проверки идут с `--workspace`: сборка с `-p <крейт>` объединяет фичи иначе и собирает llama.cpp ещё раз в том же кэше. Скрипт также выставляет `LIBCLANG_PATH` (если есть `C:\Program Files\LLVM\bin`), `CMAKE_GENERATOR=Ninja` и `CMAKE_BUILD_PARALLEL_LEVEL=1`. На рабочем кэше `C:/bt/bars` скрипт проходит все шаги: 24-10-2026 зелёный прогон занял около 4 минут (тесты Rust 129 с, окно 68 с). Остановка на красном шаге проверена на падении `cargo test`. На чистом каталоге скрипт до конца не прогонялся.

Тесты с настоящей моделью и тяжёлый тест корпуса ниже в скрипт не входят.

## Стенды bars-worker: фича test-support и окружение

Примеры `bars-worker`, которые берут подделку модели (`worker::models::fake::FakeProvider`), собираются с `--features test-support`: без неё `fake` недоступен (E0432). Пример: `cargo build --release -j 3 -p bars-worker --features test-support --example bench_window_poll`. Наблюдение 28-10-2026: на готовом кэше `C:/bt/bars` достаточно задать только `CARGO_TARGET_DIR`; дополнительные `LIBCLANG_PATH`, `CMAKE_GENERATOR` и пути VS меняют входы сборочных скриптов, и `llama-cpp-sys-2` пересобирается с ошибкой «Unable to find libclang». Остановка периодических задач стенда через `Notify::notify_waiters` не будит задачу, занятую вызовом, и сценарий зависает: используйте `JoinHandle::abort()` (так сделан стенд `bench_window_poll`).

## Бинарник примера занят другой сессией

Пример, запущенный другой сессией (например, `bench_quality.exe` в `C:\bt\bars\release\examples\`), нельзя пересобрать: линковщик падает с `LNK1104: cannot open file`. Чужой процесс не останавливать. Рабочий способ 24-10-2026: временная копия примера под другим именем — первая строка `//!` заменяется своим комментарием (через `include!` файл с внутренним doc-комментарием не собирается), остальное копируется как есть. До коммита удалить и копию, и её артефакты `C:\bt\bars\release\examples\<имя>*`. Повторение прогона на пересобранном бинарнике меняет его хеш в `config.json` прогона: продолжить старый прогон в той же папке результатов уже нельзя.

## Коммит при чужих правках в рабочем дереве

Несколько сессий агентов работают в одном checkout, и в общем файле (например, `QUESTIONS.md`) могут лежать чужие незакоммиченные правки рядом со своими. Если ханки перемежаются, `git add -p` агенту недоступен (интерактивный). Рабочий способ: собрать версию файла из `HEAD` плюс только свои вставки и положить её в индекс, не трогая рабочую копию — `git hash-object -w <файл>`, затем `git update-index --cacheinfo 100644,<blob>,<путь>`. Чужие правки остаются в рабочем дереве незакоммиченными. Перед коммитом проверить `git diff --cached` этого файла.

Если чужие изменения уже подготовлены в основном индексе, проверен отдельный `GIT_INDEX_FILE` для своего коммита: он заполняется текущим `HEAD` и только собственными изменениями. Основной индекс заранее сохраняет обе группы, чтобы после коммита своих файлов в нём остались именно чужие подготовленные изменения, а не обратный дифф собственного коммита. База `HEAD` сверяется перед коммитом; изменение базы требует новой подготовки. В 3.1.4 так отправлены 23 своих файла при сохранении 33 чужих подготовленных файлов; рабочие версии общих документов не подменялись.

При фильтрации общего diff в 3.1.5 удаление чужих ханков из `git diff --unified=0` сохранило исходные координаты вставок и сместило новые объявления в индексе. `git apply --check` при этом прошёл: проверка применимости не доказывает правильное место вставки. Подошёл diff с контекстом, после которого содержимое индекса прочитано через `git show :<путь>` и проверен синтаксис подготовленных TypeScript/Svelte. Рабочие файлы при исправлении staging не менялись. При сборке patch в PowerShell добавленные CRLF в конце ханков также вызвали предупреждения о пробелах; итоговый patch записан с LF, `git diff --cached --check` прошёл. Эти проверки дополняют полный гейт исходников, а не заменяют его.
Другая сессия может закоммитить общий файл вместе с твоей незакоммиченной правкой: перед сборкой версии из `HEAD` проверь, нет ли уже твоей строки в `HEAD`. Полный `scripts/check.ps1` при параллельных сессиях красный не по вине шага (наблюдение 28-10-2026): `index_corpus` сравнивает число документов репозитория, пока другие сессии их добавляют; два теста воркера падают с `database is locked` и `AlreadyRunning` при одновременных прогонах Cargo; чужая недописанная правка Rust ломает сборку воркера (`clippy` остановился на чужом `tray.rs`, `npm run check` — на чужом незавершённом `screen-menu.test.ts`); тест `full_rebuild_keeps_status_window_controls_and_full_ipc_search_responsive` берёт фиксированное имя канала (ISS-99); при работающем `bars.exe` и чужих прогонах к ним добавляются `mcp_history_worker_restart_leaves_interrupted_ipc_unknown_and_repeat_is_new` и `pipe_dacl_allows_only_the_current_user` (наблюдение 28-10-2026, сессия 3.4.5: по отдельности проходят). Повтор через несколько минут обычно проходит, когда другая сессия закончила правку. Тогда UI-шаги запускаются отдельно (`npm run check`, `npm test` в `ui`), а в итоге сессии прямо сказано, что полного зелёного прогона нет.

Наблюдение 01-11-2026, срез 3.4.6: общий Cargo-кэш ожидался несколькими параллельными прогонами; начальный тестовый шаг увидел `usize: FromSql`, следующий build — ещё отсутствовавшие `truncate_text_page` и `rematerialize_text_reply` соседней реализации. Позднейшее появление функций на диске не отменяет зафиксированный отказ: разные шаги одного check.ps1 могут читать разные состояния общей рабочей копии. Проверки UI и изолированного WebView2 записаны отдельно; полного зелёного гейта этот срез не получил. Автор отдельно разрешил завершить и отправить 3.4.6 с этим ограничением.

Ещё одна ловушка того же рода (наблюдение 28-10-2026, сессия 4.1.2): чужой `git pull --rebase --autostash` убирает все незакоммиченные правки рабочего дерева в autostash-коммит, и свои файлы внезапно возвращаются к `HEAD`, хотя `git stash list` пуст. Правки не потеряны: `git fsck --no-reflogs --lost-found` показывает висячие коммиты «On main: autostash», нужный выбирается по времени и по содержимому (`git show <коммит>:<файл>`), а файлы возвращаются `git restore --source=<коммит> --worktree -- <пути>`. Общие файлы, где рядом правили другие, собираются заново от `HEAD` (раздел выше). Чтобы не зависеть от этого, закоммить свои файлы сразу после зелёной проверки.

При изменении исходников во время общего прогона результат fmt/clippy не является атомарной проверкой того же набора файлов, который позже читает build. Ошибки E0425/E0560 о недоступном объявлении при его наличии в текущем исходнике сами по себе не доказывают повреждение Cargo-кэша: нужно сверить время правки и читаемый источник, сохранить отрицательный результат и повторить проверку стабилизированного среза. В 2.3.9 (01-11-2026) наблюдались такие расхождения у новых полей протокола и функций текстового вывода графа; единая причина не установлена. Целевые тесты окна не заменяют полный зелёный гейт.

Если HEAD изменился при подготовке отдельного индекса или git commit отказал с cannot lock ref HEAD, сначала перечитать HEAD и проверить, не включила ли другая сессия нужные изменения в общий коммит. Прежний индекс не переносится вслепую на новую базу. В 2.3.9 защитная сверка остановила такой коммит, а проверка HEAD подтвердила, что код уже вошёл в общий ac52757; повторный эквивалентный коммит не потребовался.

## Интерфейс окна: сборка и проверки

Окно — Svelte 5 + TypeScript + Vite в `ui/` ([architecture/components.md](../architecture/components.md)). Нужен Node.js 20 или новее (проверено на 24).

```bash
cd ui
npm install        # один раз
npm run build      # ui/dist: его встраивает Tauri при сборке bars
npm test           # vitest: логика дерева, форматирование, Markdown, настройки, согласие
npm run check      # svelte-check: типы TypeScript и Svelte
npm run dev        # просмотр в браузере на порту 1420: вместо воркера отвечает заглушка src/lib/mock.ts
```

`cargo build` и `clippy` не требуют `npm run build`: если `ui/dist/index.html` нет, сборочный скрипт `bars-app` кладёт туда заглушку «Интерфейс не собран». Настоящий интерфейс в `bars` попадает только после `npm run build` и пересборки `bars-app`.

Заглушка воркера выбирает сцену параметром адреса: `?scene=empty|indexing|consent|reindex-required|missing|provider|worker-down`; без параметра — обычный проект с тремя результатами. `reindex-required` — ожидание согласия без активного задания: баннер смены модели, ошибка `reindex_required` при смысловом поиске; `consent` — отдельная сцена с заданием. Физический граф использует документы дерева заглушки, поэтому все три результата поиска присутствуют в виде запроса. Связи и оценки демонстрационные; правила и ручная проверка — в [описании физического графа](../features/graphrag/physical-graph.md).

## Тяжёлый тест поискового корпуса

`search_corpus` переэмбеддит всю текущую документацию. По наблюдению автора 18-10-2026 жёсткий CPU-прогон слишком долго блокировал процессор и был остановлен; это не ошибка корректности поиска. Тест запускается только явно (`#[ignore]`): `cargo test --release -p bars-core --test search_corpus -- --ignored --nocapture`. По умолчанию требует фактический DirectML, без тихого продолжения на CPU; пачка 1, кооперативный бюджет индексации 60 с между документами. На CPU — только отдельный явный `BARS_CORPUS_TEST_DEVICE=cpu`. Новые веса не скачиваются. Остановленный CPU-прогон не считать успешной приёмкой.

Холодная release-сборка `bench_quality` в `C:/bt/bars` занимает около 16 минут из-за llama.cpp; сразу после неё первый запуск может ответить «Device or resource busy», повтор проходит.

Для GraphRAG на готовом индексе используются сохранённые embeddings ([опыт на готовых embeddings](graph-embedding-2026-10-18.md), `scripts/graph-embedding-probe.mjs`): замер не требует полной переиндексации и не заменяет регрессию модели.

## Состав сборки и особенности зависимостей

Cargo workspace из семи крейтов (`crates/*`: `bars-app`, `bars-cli`, `bars-core`, `bars-graph`, `bars-mcp`, `bars-protocol`, `bars-worker`); их роли — [architecture/components.md](../architecture/components.md). Сборка вместе проверяет Т-3: Rust, Tauri, fastembed-rs и встроенный llama.cpp линкуются в одном workspace, Python нет.

Фича `directml` у fastembed включается только на Windows (`cfg(windows)`), потому что на macOS её нет.

Для выбора DirectML `bars-core` на Windows зависит от крейта `ort` напрямую, с той же версией `=2.0.0-rc.13`, что у fastembed.

## Тесты со встроенной моделью

Тесты `crates/bars-core/tests/builtin_embedder.rs` гоняют настоящую bge-m3: векторы на CPU и на DirectML, порядок векторов после сортировки по длине, индексация маленького проекта. Они берут модель только из `~/.bars/models` и ничего не скачивают: если модели там нет или в окружении задан `HF_HOME`, тест печатает «пропущено» и проходит. Поэтому «все тесты зелёные» на машине без модели не говорит про bge-m3. Прогон занимает около 30 секунд:

```bash
cargo test -p bars-core --test builtin_embedder -- --nocapture --test-threads=1
```

Остальные тесты индексации используют подделку модели из хешей и модель не требуют.
