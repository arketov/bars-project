# Перепроверка идей развития bars

Дата: 18-10-2026. Повод: автор усомнился в глубине первого интернет-исследования. Проверяется [исследование DEV-01…05](development-ideas.md). Этот документ фиксирует основания и исправления, не расширяет утверждённые требования.

Область этой проверки — надёжность и диагностика текущего поиска. Она не подтверждает полноту обзора новых возможностей. После уточнения автора граф, отдельный поиск связей и GraphRAG вынесены в [самостоятельное исследование](graph-and-relations.md); их прежний общий отсев вместе с генерацией исправлен.

## Что в первом проходе было недостаточно

Ссылки на W3C, SQLite и OpenTelemetry подтверждали технические принципы. Они не доказывали востребованность функций bars. Возможности проверялись по документации, а не реализации; наличие инструкции по будущему опыту не равнозначно проведённой проверке. Формулировка «обоснована польза» нуждалась в уточнении: подтверждён сценарий проблемы, но частота и выигрыш для пользователя не измерены.

Повторный проход добавляет прямые примеры из поисковых продуктов, статью с экспериментами и ограничениями, проверку текущего Rust-кода и связанного кода окна. Поиск чужих решений использовался для проверки конкретных предположений; рекламные обзоры и поисковые сниппеты не приняты за доказательства.

## Проверенные пути реализации bars

Rust-проект активирован в Serena. Работа LSP подтверждена запросом символов настоящего `hybrid.rs`; прочитаны тела нужных символов, найдены ссылки на `candidate_trace`. Код не менялся. Svelte/TypeScript проверены чтением соответствующих участков, без заявления о работающем для них LSP.

| Проверка | Место реализации | Наблюдение и граница вывода |
|---|---|---|
| Версия результата | [methods.rs](../../crates/bars-protocol/src/methods.rs), `SearchHit`, `SearchOutput` | Есть текст и диапазон строк; нет хеша источника или версии документа. |
| Чтение файла | [handler/mod.rs](../../crates/bars-worker/src/handler/mod.rs), `document`, `read` | Читается текущий файл; ожидаемый хеш не передаётся, версии не сравниваются. |
| Соединение выдачи и чтения | [app.svelte.ts](../../ui/src/lib/app.svelte.ts), `openDocument` | Ответ `read` помещается в viewer вместе с прежним `hit`. |
| Подсветка | [Viewer.svelte](../../ui/src/lib/Viewer.svelte), [markdown.ts](../../ui/src/lib/markdown.ts), `renderDocument` | Подсветка рассчитывается пересечением диапазонов старого `hit` с текущим текстом. Удалённый файл уже обработан отдельным предупреждением. |
| Представление для хеша | [indexer.rs](../../crates/bars-core/src/indexing/indexer.rs), вычисление `hash`; [walk.rs](../../crates/bars-core/src/indexing/walk.rs), `read_utf8_path` | Индекс считает BLAKE3 от прочитанного UTF-8-текста; чтение сохраняет BOM и переводы строк. Для DEV-01 важно сравнивать одинаковые представления и хешировать возвращаемый буфер. |
| Существующая диагностика | [hybrid.rs](../../crates/bars-core/src/search/hybrid.rs), `candidate_trace`; [bench_quality.rs](../../crates/bars-core/examples/bench_quality.rs), вызов из `run` | В текущем незакоммиченном изменении уже собираются FTS/vector/fused-кандидаты. Это не новый отсутствующий механизм и не доказательство выпуска функции. |

DEV-02 — ограниченное расширение этого пути. |

Простой отказ от rerank не превращает путь в модельно независимый. |

Рассогласование версий следует из этих путей статически: вставка строк перед найденным фрагментом меняет его позицию, а viewer продолжает использовать прежний диапазон. Это доказательство возможности ошибки, не зарегистрированное воспроизведение в работающем окне. Тестовый запуск renderer не выполнен: `ui/node_modules/marked` отсутствует; зависимости ради исследования не устанавливались.

## Первичные интернет-источники и пределы их применимости

Все страницы открыты и релевантные разделы проверены 18-10-2026. Ни один из продуктов или алгоритмов не устанавливался и не запускался локально. README ветки разработки другого продукта — пример описанного поведения, не доказательство его стабильности во всех релизах.

| Источник | Что действительно подтверждает | Чего не подтверждает |
|---|---|---|
| [W3C Web Annotation, Text Position Selector](https://www.w3.org/TR/annotation-model/#text-position-selector), также States | Изменения источника делают позиционные привязки хрупкими; состояние источника имеет значение. | Что BLAKE3-поле — обязательное решение bars или что нужно хранить все старые версии. |
| [Meilisearch Search API](https://www.meilisearch.com/docs/reference/api/search/search-with-post), `showRankingScoreDetails`, `showPerformanceDetails` | Поисковый продукт предоставляет детали оценки и времени по запросу. | Что нужен отдельный экран bars или что сбор диагностики бесплатен. |
| [QMD README](https://github.com/tobi/qmd#options), `--explain`; [режимы поиска](https://github.com/tobi/qmd#search-commands) | Близкий локальный поиск по документации описывает объяснение и самостоятельный BM25-путь. | Что нужно копировать его стек, команды, MCP-поверхность или менять OQ-52. |
| [SQLite FTS5, BM25](https://sqlite.org/fts5.html#the_bm25_function) | Полнотекстовый поиск ранжируется самостоятельно; меньшие значения BM25 означают лучшие совпадения. | Что FTS-режим bars реализуется одной галочкой без изменений протокола и обработки порогов. |
| [Typesense Search, Group Results](https://typesense.org/docs/29.0/api/search.html#group-results) | Группировка результатов — самостоятельный практический вариант уменьшения перекоса выдачи. | Что одинаковый заголовок означает дубль или что один результат на документ оптимален. |
| [Elasticsearch Diversify Retriever](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrievers/diversify-retriever) | MMR используется для выбора менее избыточного набора результатов, с параметром баланса. | Что любой MMR повышает recall, автоматически ускоряет rerank или улучшает bars. |
| [Pickett et al., Better RAG using Relevant Information Gain, v1](https://arxiv.org/html/2407.12101v1), таблица 2, разделы 3 и 6 | Есть измеренное сравнение обычного и разнообразного отбора; рассматриваются подбор параметра и ограничения переноса. | Что числа на RGB и ChatGLM переносятся на русскоязычные docs, модели bars и выдачу без генерации. |
| [Elasticsearch Ranking Evaluation](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-rank-eval), ratings и `unrated_docs` | Для оценки поиска нужны запросы и ручная разметка; неразмеченный документ отличается от отрицательно оценённого. | Что кнопка сохранения сама создаёт корректную разметку или воспроизводимый снимок корпуса. |

OpenTelemetry из первого прохода остаётся источником общего устройства трассировки. Для продуктовой целесообразности DEV-02 примеры Meilisearch и QMD прямее. Добавлять инфраструктуру OpenTelemetry в bars этим исследованием не предлагается.

## Проверка контрпримеров и собственной интерпретации

У статьи Pickett et al. есть важный предел: таблица 2 сообщает лучшие значения после подбора параметров, а раздел 6 ограничивает перенос результатов одним бенчмарком и одной LLM. Поэтому таблица не задаёт готовое умолчание bars.

Также нельзя брать худший результат MMR на косинусе относительно KNN с cross-encoder как доказательство вреда разнообразия: меняется и способ оценки. При сравнении с одинаковым scorer в таблице 2 MMR повышает NDCG, а на простой QA с cross-encoder процент правильных ответов одинаков. В промежуточном сообщении о перепроверке такое различие было сформулировано слишком кратко; корректный вывод — эффект зависит от метрики, конфигурации и задачи, а ухудшение от одного только MMR здесь не установлено.

DEV-01 тоже имеет контрпример к чрезмерному обещанию: совпадающий хеш не делает документ правильным и не гарантирует неизменность файла после чтения. Он подтверждает только соответствие возвращённого текста индексированной версии. А несовпадение хеша всего документа может быть вызвано правкой другого раздела: это повод снять гарантию старой позиции, не автоматически скрыть найденный текст.

DEV-02 не может по отсутствию FTS-кандидатов заключить отсутствие ответа: семантическое совпадение не обязано содержать те же слова. После ограничения числа кандидатов и порога можно объяснить судьбу обработанного набора, но нельзя утверждать полноту поиска по всем возможным опорам.

DEV-05 не создаёт воспроизводимость одним хешем. Для неё нужны доступный снимок корпуса, конфигурация и модель; иначе результат экспорта — диагностический случай с явно указанными пробелами. Реальные жалобы полезны для развития, но нельзя подмешивать их в неизменяемый проверочный набор и затем заявлять независимое улучшение.

## Итоговые исправления рекомендаций

1. **DEV-01 сохранена.** Основание усилено проверкой цепочки от протокола до viewer; новизна сужена до изменения существующего файла. Отдельно оговорены один буфер для чтения/хеша и представление текста.
2. **DEV-02 сужена.** Переиспользовать существующую диагностическую работу; сначала объяснение или экспорт конкретного запроса. Новая подсистема и отдельный экран не обоснованы.
3. **DEV-03 оставлена экспериментом.** Сначала сравнить простую группировку, исходный поиск и MMR. Никаких новых умолчаний по статье или примерам чужих продуктов.
4. **DEV-04 оставлена резервом.** Реализуемость подтверждается, но полезность режима зависит от частоты блокировок и цены изменения контракта. Автоматический скрытый fallback не предлагается.
5. **DEV-05 понижена.** Пока часть диагностического экспорта и существующего бенча; самостоятельная пользовательская функция не оправдана.

Перепроверка дала более точные основания, но не заменяет опыт на работающем приложении. Частота проблем, затраты реализации и измеримый выигрыш остаются непроверенными. Главный результат — две узкие рекомендации вместо заявления о пяти уже доказанных улучшениях.
