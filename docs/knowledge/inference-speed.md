# Ускорение инференса bars — замеры, отбор методов и протокол

Статус 01-11-2026: выполнен исследовательский отбор ускорителей 8.1.2 на RTX 3090 готовыми upstream-бинарниками. Получены численные результаты и память; причинный выигрыш скорости при меняющейся фоновой нагрузке не доказан. TensorRT остановлен защитой памяти. Это отрицательные и неопределённые результаты отбора, а не приёмка CUDA в продукте. Новые ускорители автоматически включать по этим данным нельзя.

Результат 18-10-2026: FP16 rerank с batch16 на DirectML ускорил полный поиск в 1,6–1,7 раза без обнаруженных потерь на 138 вопросах; проверены настоящий worker, конкуренция и поиск при индексации. Требования — Т-3, Т-17, НФТ-2; действующий продуктовый контракт — [встроенные модели](../features/models/local-models.md), раздел «Приёмка продуктового FP16 rerank».

Связанные исследования: [устройства, DirectML и библиотеки](inference-devices.md), память — [memory.md](memory.md), конкуренция за модель — [поиск при индексации](search-during-indexing.md), исторические числа — [спайк поиска](spike-search.md). Сравнение факторов CPU/K/длины, ограничения ноутбука и воспроизведение из сохранившихся файлов — [скорость rerank](rerank-speed.md).

## RTX 3090: отбор ускорителей 8.1.2

### Метод и границы исследования 01-11-2026

Машина: i7-11700KF, 16 логических CPU, RTX 3090 24 ГиБ, 32 ГиБ RAM, драйвер 616.92, установленная CUDA 12.8. Точные ОС, версии и SHA-256 — [доказательства оборудования](accelerators-2026-11-01/hardware.json), [веса](accelerators-2026-11-01/artifacts.json) и [runtime](accelerators-2026-11-01/runtimes.json). Системные установки CUDA, пользовательский bars и рабочие индексы не менялись.

Автор запретил сборки и тесты, отдельно разрешил замеры готовыми бинарниками. Начатая компиляция прервана; её результаты не использованы. GGUF измеряется готовым `llama-server` b11953 (`a7af149a2`, 0.7.0-dev), отдельно Vulkan и CUDA 12.4 с установленным runtime 12.8. Это другая нативная ревизия, чем vendored llama.cpp закреплённой Rust-обёртки: перенос на `GgufEmbedder` не доказан. ONNX — прямой C API двух готовых ORT 1.24.4: DirectML из NuGet и CUDA из официального GPU-архива. Одинаковая версия убирает смешение версии runtime и устройства; продуктовый статический ORT 1.28 этим не принят.

Нативный мост — готовый Koffi 2.14.1; подготовка пар — `@huggingface/tokenizers` 0.2.0, XLM-R, longest-first до 512 токенов. Все EP получают одинаковые пары и массивы токенов. Совпадение всего preprocessing со штатным fastembed Rust не утверждается. Модели одинаковы: Qwen3-Embedding-4B Q4_K_M для GGUF, закреплённый bge-reranker-v2-m3 FP16 для ONNX. Сравнивать между ними значения scores или скорость нельзя.

24 русских вопроса и по 15 прежних кандидатов bars восстановлены из read-only снимка индекса 18-10-2026: сверены ID, путь, заголовок и диапазон строк; rerank получает прежний формат `path\nheading\ntext`. Это известная регрессия, не новый holdout. Для GGUF взяты четыре вопроса и первые документы: восемь текстов по 30–415 токенов; контекст 8192, Last pooling, нормирование L2. Длинный вход до 8192 этим набором не проверен.

Первый проход каждого входа — прогрев, отдельно от измерений. GGUF: пять повторов × восемь входов, 40 наблюдений на конфигурацию; основные серии `*-controlled` выполнялись последовательно, монитор учитывает собственный и фоновый CPU. Полные ONNX-серии: три повтора × 24 вопроса, 72 наблюдения; fixed/graph — четыре вопроса × четыре документа, 12 наблюдений. Таймер GGUF включает loopback HTTP и разбор JSON; ONNX — токенизацию, подготовку, Run и CPU-ответ. Это разные границы измерения. Отказы и неполные серии не превращаются в успешные результаты.

Машина общая. Фоновая CPU-нагрузка в измеренных окнах менялась примерно от 20 до 56%; у коротких серий недостаточно двухсекундных отсчётов. Первый и повторный CUDA GGUF baseline дали 37,12 и 29,60 мс, DirectML ONNX batch16 — 193,26 и 216,67 мс, CUDA — 177,58 и 141,20 мс. Такой дрейф запрещает приписывать небольшую разницу ускорителю. Эти времена сохранены как наблюдения, но **не являются чистым сравнением скорости, SLA или обоснованием самого быстрого backend**. Повторение baseline не устранило ограничение.

### GGUF: flash attention, KV-cache и microbatch

В логах подтверждены Vulkan0/CUDA0, offload 37/37 слоёв, фактическое состояние flash attention и тип KV. Готовый server уменьшает `n_batch` до `n_ubatch` в embedding-режиме: записываются фактические значения 128/512/2048. Это последовательная обработка текстов с одной sequence, не многодокументный batching production API.

| Фактор | Опора сравнения | Минимальный cosine вектора Vulkan / CUDA | Максимальное изменение query–document cosine Vulkan / CUDA |
|---|---|---:|---:|
| Flash attention on, F16 KV | Тот же backend, flash off, F16 | 0,999889 / 0,998647 | 0,002946 / 0,008148 |
| Q8_0 KV | Тот же backend, flash on, F16 KV | 0,999825 / 0,998278 | 0,003491 / 0,007120 |
| Q4_0 KV | Тот же backend, flash on, F16 KV | 0,972555 / 0,977061 | 0,041348 / 0,029186 |
| Microbatch 128 | Тот же backend, flash on, microbatch 512 | 0,999829 / 0,998602 | 0,003376 / 0,004259 |
| Microbatch 2048 | Тот же backend, flash on, microbatch 512 | 1 / 1 | 0 / 0 |

CUDA flash-off/F16 против Vulkan flash-off/F16: минимум cosine 0,998720, максимум изменения query–document cosine 0,004989. Прямого равенства векторов между backend нет. Microbatch 2048 не проверен на текстах длиннее 512 токенов: все входы этого набора и так помещаются в 512.

Размер KV, сообщённый runtime для одинакового контекста 8192: F16 — 1152 МиБ, Q8_0 — 612 МиБ, Q4_0 — 324 МиБ. Это размер KV, не вся VRAM процесса; в продукте контекст растёт по потребности. Sampled private Vulkan flash-on/F16 — 3,78 ГиБ, Q4 — 2,97 ГиБ; CUDA — 4,45 и 3,51 ГиБ. Двухсекундный монитор может пропустить пик. GPU-счётчик — суммарное использование карты вместе с чужими процессами; его нельзя назвать собственной VRAM модели.

Отбор: Q4 KV не становится умолчанием из-за дрейфа векторов. Q8 экономит KV, но тоже меняет результаты; сокращение памяти не доказывает сохранение поиска. Безусловное включение flash attention и смена microbatch по этому набору не обоснованы: чистый выигрыш не доказан, полный retrieval на изменённых векторах не выполнен. Это инженерный вывод исследования, не решение автора изменить настройки.

### ONNX: пачки, I/O Binding и CUDA Graphs

Наблюдения под общей нагрузкой; столбец времени не доказывает ускорение.

| Режим bge-reranker FP16 | Наблюдаемая медиана, мс | Sampled private, ГиБ |
|---|---:|---:|
| DirectML batch1 / batch4 / batch16 | 1646,68 / 661,54 / 193,26 | 1,89 / 2,10 / 2,49 |
| CUDA batch1 / batch4 / batch16 | 169,20 / 146,11 / 177,58 | 3,87 / 3,87 / 4,11 |
| DirectML batch16, I/O Binding | 194,97 | 2,48 |
| CUDA batch16, I/O Binding | 139,96 | 4,00 |
| CUDA fixed 4×512, обычный Run / CPU Binding / Graphs | 48,71 / 42,74 / 39,83 | 2,51 / 3,05 / 2,51 |

Последняя строка — другой workload, её нельзя сравнивать с полными 15 кандидатами. CPU Binding заново связывает входы и выход каждой пачки; он не устраняет передачу токенов на GPU. В данном опыте нет устойчивого основания добавлять этот адаптер в fastembed ради скорости. Уменьшение пачки остаётся защитой памяти, не доказанным универсальным ускорением.

CUDA Graphs измерен с одной формой 4×512 и постоянными GPU-адресами. Между запросами меняются query и документы, выполняются H2D-копии в те же буферы и D2H-копия логитов; обе передачи входят в таймер. Все логиты совпали с обычным CUDA Run на той же форме, максимальная разница — 0. Профиль replay содержит значительно меньше повторных Node-событий, чем обычный Run. Это не опыт с бесконечным повтором неизменного входа. Динамические формы, хвост неполной пачки и несколько graph ID не проверялись; API и ограничения — [CUDA EP](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html).

В полном сравнении с DirectML batch16 CUDA batch16 дал максимальную разницу логита 0,033203125 и сигмоиды 0,006287; batch1 — до 0,007580 по сигмоиде. Top‑1 и top‑3 не изменились, потерь MRR по размеченным опорам при порогах 0 и 0,1 на этих 24 вопросах не найдено. Но это **не равенство scores**: `bars-22`, кандидат из `docs/features/window/implementation.md`, перешёл через 0,1: 0,099820668 → 0,100701608. Кандидат вне top‑3, поэтому неизменный top‑3 не означает неизменную фильтрацию Т-24. Порог не подстраивался, значения не округлялись для сокрытия перехода.

CUDA-профиль подтверждает MatMul, FusedMatMul, Softmax и нормализации на CUDA; Shape/Gather/Concat и другие служебные узлы частично остаются на CPU. Успешная регистрация CUDA EP не была единственным доказательством GPU. Для DirectML в этой серии подтверждена регистрация устройства 0, но отдельный профиль размещения его узлов не снят; полной GPU-раскладки по одному имени EP не утверждаем. В CUDA-профиле этого экспорта нет Attention/MultiHeadAttention: отдельное включение ONNX Flash Attention не проверено и не засчитывается. Для другого attention-графа понадобятся отдельный экспорт и качество; KV-оптимизации llama.cpp к bge cross-encoder не относятся.

### TensorRT и пределы ресурсов

Проверялся TensorRT 10.16.1.11, CUDA 12, с явным TensorRT EP, CUDA для неподдержанных узлов, FP16, workspace 2 ГиБ, профилями min 1×1 / opt 4×512 / max 16×512 и собственным engine-cache. Готовые DLL и ресурс builder для SM86 получены из официального ZIP; SHA-256 файлов и действительные подписи NVIDIA сохранены. Система не менялась. Доставка engine, profiles и cache — часть цены метода; [контракт TensorRT EP](https://onnxruntime.ai/docs/execution-providers/TensorRT-ExecutionProvider.html).

Полного прогона нет. После устранения отсутствующих DLL построение engine достигло не менее 6,86 ГиБ private собственного процесса; монитор увидел 1,81 ГиБ свободного системного commit при 3,82 ГиБ свободной физической RAM. Защита с порогом commit 2 ГиБ завершила только собственный процесс. На старте запас commit был 8,64 ГиБ. Это отказ по общему commit, не доказанная нехватка VRAM и не утверждение, что один TensorRT исчерпал весь commit машины. Успешных inference, latency и scores TensorRT нет; незаконченный cache не считается готовой моделью. Защита не ослаблялась.

Попытка использовать готовый ORT 1.28 CUDA12 после этих серий не прошла preflight: commit 2,49 ГиБ при требуемых 6 ГиБ, модель не стартовала. Наличие официального [CUDA12-пакета ORT 1.28](https://github.com/microsoft/onnxruntime/releases/tag/v1.28.0) уточняет исследование поставки: ограничение CUDA13 относится к автоматическому архиву pyke в `ort-sys`, а не ко всем сборкам ORT 1.28. Приёмка конкретного runtime остаётся отдельной работой.

### Вывод для проектирования и воспроизведение

Исследовательский отбор не дал основания автоматически включать новый ускоритель: TensorRT не завершился в текущем ресурсе; для Graphs и I/O Binding не доказан устойчивый выигрыш, а интеграция усложняет работу с формами и буферами; FA и KV меняют векторы. CUDA исполняет bge-граф на GPU, но оценки не тождественны DirectML. Сохранять причину fallback, фактический backend, тип KV и precision; не обещать неизменную пограничную фильтрацию или одинаковое качество без полного retrieval. Эти выводы передаются проектированию 8.1.3; 8.1.4, продуктовый поиск, слабые GPU, ноутбук и установленная сборка не закрыты исследованием.

Общая нагрузка не позволила установить чистую скорость. Ответ автора по OQ-238 не выбирает окно и не принимает скорость; вывод об отсутствии доказанного выигрыша — вывод агента. Неполный TensorRT и ненагруженная скорость не объявляются пройденными.

Стенды — `spikes/accelerators/`: `freeze-inputs.mjs` сохраняет происхождение корпуса из read-only индекса; он не нужен для повтора замеров. `setup-runs.mjs` восстанавливает фактические имена, параметры и порядок серий из сохранённого протокола и проверяет SHA-256 моделей. `prebuilt-gguf.mjs` запускает и завершает собственный server; `prebuilt-onnx.mjs` работает с C API; `run-onnx.mjs` следит за памятью и кодом выхода; `analyze.mjs` пересчитывает таблицы. Fixture, зависимости и native runtime в Git не входят.

Для повтора нужны готовые runtime из `runtimes.json`, model-cache с теми же весами и готовые npm-пакеты Koffi 2.14.1 / Hugging Face tokenizers 0.2.0 в `docs/chats/2026-11-01-rtx-accelerators/fixture-node`; установка пакетов с `--ignore-scripts` не запускает их сборку. `download-prebuilt.ps1` получает llama Vulkan/CUDA и ORT CUDA12, `cudnn-loader.mjs` — нужные cuDNN DLL; подписи range-извлечённых DLL проверяются до их загрузки. DirectML требует также доступную `DirectML.dll`. Ошибка регистрации GPU EP завершает серию; назначение отдельных узлов на CPU внутри успешно созданной ORT-сессии разрешено и проверяется профилем отдельно.

Запустить `node spikes/accelerators/setup-runs.mjs <models-dir> <новая-папка-fixture-внутри-проекта>`. Скрипт напечатает значения `BARS_PROBE_RUNS_DIR`, `BARS_PROBE_EVIDENCE_DIR` и чтение `order.json`. Применить их в своей PowerShell-сессии; переменные отделяют новый результат от архивных доказательств. Внутри новой папки сохраняются прежние согласованные имена baseline, без требования доступа к историческому SQLite-снимку.

Группы запускать последовательно: `node spikes/accelerators/prebuilt-gguf.mjs @($order.gguf)`, затем `node spikes/accelerators/run-onnx.mjs <готовый-DirectML-onnxruntime.dll> @($order.directml)`, затем та же команда с CUDA DLL и `@($order.cuda)`. После завершения — `node spikes/accelerators/analyze.mjs` с теми же двумя переменными. TensorRT из `optional_failures` не запускается автоматически. В текущей папке результатов старые строки и логи не перезаписываются; повтору нужна новая папка fixture. Сборки bars не требуется.

Сырые строки, конфигурации, профили GPU и монитор — [протокол данных](accelerators-2026-11-01/protocol.json), [сводка](accelerators-2026-11-01/summary.json) и [контрольные суммы](accelerators-2026-11-01/checksums.json). Векторы вынесены в `vectors.f32.gz`: lossless IEEE754 little-endian f32, смещение `vector_offset_f32` и длина из строки в `rows.jsonl.gz`; перед записью проверено точное равенство исходного Number и f32. Никакого дополнительного квантования нет. По поручению автора `cargo test`, сборки и `scripts/check.ps1` не запускались после запрета; выполненное Sol-ревью не заменяет эти проверки.

### Ловушки исследовательского стенда на Windows

Опыт сессии 01-11-2026 относится к готовым бинарникам и собственному FFI-стенду, а не к найденным дефектам продуктового bars. Неудачные попытки не используются для сравнения скорости.

| Симптом | Что установлено и как продолжать |
|---|---|
| Архивные `inputs.json` содержат пустые `documents` | Сохранённые кандидаты не равны готовым текстовым парам. Для первоначальной заморозки тексты восстановлены из read-only SQLite с проверкой ID, пути, заголовка и строк; сохранён формат `path\nheading\ntext`. Для повтора использовать уже замороженные входы через `setup-runs.mjs`, не обращаться к текущему изменившемуся индексу. |
| Koffi: `Duplicate type name` на повторном вызове | Создание именованного `koffi.proto` внутри каждого вызова повторно объявляло тип. Прототип создаётся один раз при связывании функции и переиспользуется. Ошибка не означает неисправность ONNX-модели. |
| CUDA ORT: `Cannot load symbol cudnnCreate` | Одной извлечённой `cudnn64_9.dll` в этом опыте оказалось недостаточно; после добавления `cudnn_graph64_9.dll` и проверки подписи NVIDIA вычисление заработало. Наличие файла loader не доказывает готовность всех зависимостей; набор компонентов зависит от runtime и операторов модели. |
| TensorRT: отсутствует `nvinfer_builder_resource_sm86_10.dll` | Основных runtime/parser/plugin DLL недостаточно для построения engine на RTX 3090. После получения подписанного ресурса SM86 стенд дошёл до защиты commit; успешного inference это исправление не доказало. |
| Node fetch зависает на ZIP Range | В этой сессии запросы упирались в таймаут; curl с явными диапазонами сработал. Проверяются `Content-Range`, длина и ZIP64-смещения; для извлечённых DLL сохраняются SHA-256 и проверяются подписи. Это не проверка SHA-256 всего ZIP: в метаданных прямо записано `whole_archive_verified: false`. Сетевую причину зависания не установили. |
| Команда вернула 0 после native crash или ошибки HTTP | Wrapper обязан передавать ненулевой код дочернего процесса/сигнал и ошибку собственного измерения. Наличие файла строк не означает завершения: нужны событие `complete`, ожидаемые входы и повторы, конечные значения и состояние процесса. |
| Анализатор не находит baseline после подготовки | Первоначальные имена генератора не совпадали с именами фактических серий. Повтор теперь восстанавливает конфигурации из сохранённого протокола в новой папке и использует одинаковые `BARS_PROBE_RUNS_DIR` / `BARS_PROBE_EVIDENCE_DIR` у запуска и анализа. Историческая заморозка корпуса и повтор измерения — разные операции. |

Медиана чётной выборки — среднее двух центральных значений, а не верхний центральный элемент. Исправление этой ошибки пересчитало сводку, но не сделало измерения под меняющейся нагрузкой чистым сравнением. Четыре замечания Sol исправлены за три статических прохода; после запрета автора новые сборки, тесты и повтор исполнения исправленного генератора не запускались. Статическое ревью воспроизведения не заменяет его аппаратный повтор.

## Условия замеров 18-10-2026

i7-11700KF (8 ядер / 16 потоков), RTX 3090 24 ГБ, 32 ГБ RAM, Windows, fastembed 7.1.1 / ort 2.0.0-rc.13 ([hardware.json](quality-2026-10-18/hardware.json)). RTX 3090 не доказывает скорость, объём памяти или корректность Intel Arc, малой VRAM и ноутбуков.

Повторное включение этого не является ускорением. ## Embed и индексация

Microbenchmark: 10 коротких запросов и 64 фиксированных текста, один проход. CPU FP32: query median 39–46 мс против 118 мс на DirectML; документы CPU16 1,55 текста/с против DirectML batch4 17,63. Переносить весь embed на CPU незачем: индексация существенно медленнее, а вторая постоянная CPU-сессия требует памяти. FP16 DirectML batch8: query 86 мс, документы 28,40 текста/с, минимум cosine с FP32 около 0,99991; INT8 CPU: query 19 мс, документы 4,86 текста/с, min cosine около 0,974. Близость векторов не доказывает качество поиска.

Настоящий `update_index` копии 176 документов / 946 chunks: чистые FP32 DirectML batch4 — 57,34 с, FP16 DirectML batch8 — 35,81 с. INT8 CPU16 по одному тексту (212,98 с) и FP32 CPU16 batch4 (533,70 с) завершены, но монитор обнаружил постороннюю нагрузку: это функциональные проходы, а не чистое сравнение. Все четыре варианта выполнили полный, неизменённый и инкрементальный проходы без problems; изменение одного документа затронуло 2 embeddings и переиспользовало 4 chunks. Загрузка и прогрев модели исключены; проходы одиночные, не распределение latency.

Качество FP16 embed проверяется отдельно от rerank: свой индекс, свой fingerprint, полный retrieval; смешивать FP16 query с FP32-индексом нельзя. Результаты retrieval, память и отказ INT8 — [memory.md](memory.md#embed-fp16-и-int8).

## Переносимость и границы вывода

В режиме DirectML основной инференс идёт на GPU; токенизация, подготовка входов, SQLite и часть служебных узлов графа остаются на CPU, а выбор EP не означает размещение каждого узла на GPU. У интегрированной GPU память общая: перенос вычислений не освобождает физическую RAM автоматически, runtime, копии весов и рабочие буферы требуют системного commit.

CPU-only rerank сохраняет FP32 batch4: INT8 rerank не проходит критерий качества. Вне Windows Auto остаётся CPU. CUDA отсутствует в поставляемом runtime; OpenVINO, NPU и CoreML аппаратно не проверены. Серии 18-10-2026 НФТ-2 на 5000 chunks не проверяли: реальный индекс содержал 946 chunks. Проверка на естественных 5000 — раздел «Естественные 5 000 чанков».

## Естественные 5 000 чанков

Статус 26-10-2026: НФТ-2 не подтверждено. Полный индекс 5000 чанков построен, стенды ядра и Worker/IPC работают, но серии 25–26-10-2026 шли, пока автор работал на той же машине: нагрузка менялась между сериями и внутри них, загрузка CPU не записывалась. Как замер скорости они недействительны, и автор вычеркнул пункт плана (OQ-198). Что из прогона осталось верным — подраздел «Прогон на ноутбуке 26-10-2026 под нагрузкой».

Метод: заморозить существующие Markdown-документы, нарезать штатной `chunk_document` с min250/max6000, выбрать ровно 5 000 разных `embed_hash` без размножения векторов или уменьшения размера чанков. Если одного зарегистрированного проекта недостаточно, исследовательский корпус составляется из документов проектов с указанием происхождения; это ограничение репрезентативности, а не результат на каждом исходном проекте. Совпадающие пути берутся только из первого источника; путь в `embed_text` сохраняется. Готовые векторы разрешено переиспользовать только по точному `embed_hash` и FP32 fingerprint; недостающие считаются настоящей bge-m3. Рабочие индексы открываются только для чтения.

Измеряемый путь — настоящий `bars_core::search::search`, CPU FP32 bge-m3, `None` вместо reranker, штатные 30 кандидатов/5 результатов/порог 0, весь корпус. Загрузка модели и прогрев записываются отдельно. Серия — 25 заранее фиксированных русских вопросов ×4 прохода: идентификаторы, короткие и длинные формулировки, вопрос вне тематики корпуса. При пороге 0 отсутствие ответа не требует пустой выдачи; без gold это только нагрузка, не проверка качества. Сохраняются все наблюдения, median/p95/max, доля ответов <1 с, хеши выдачи и число вызовов embed; ошибка останавливает серию без успешной сводки. Вложенный таймер embed входит в полный таймер; их нельзя складывать. Повторяемость выдачи — проверка стабильности, не размеченная оценка качества.

Первый запрос после загрузки, тёплый core-поиск и IPC — разные границы. Core-проход не подтверждает задержку окна или MCP; для полной приёмки требуется также настоящий Worker/IPC с тем же CPU и корпусом. НФТ-2 не задаёт процентиль: для исследованной серии консервативно проверяются все наблюдения <1с; p95 отдельно описывает распределение. Холодный диск не имитируется очисткой системного кэша. Фоновые процессы и запас commit фиксируются; при недостатке ресурсов серия остаётся неполной, работающий bars и настройки ОС не меняются.

Стенд — `crates/bars-core/examples/bench_search_cpu.rs`: `freeze`, `validate`, `cache-plan`, `preflight`, `prepare`, `run`. Первые четыре режима не загружают модели. Аппаратные режимы используют существующий Windows Monitor: перед подготовкой резерв 8 ГиБ commit, перед CPU-поиском 6 ГиБ; при запасе менее 1 ГиБ завершается только собственный процесс. Это консервативные границы исследования, не системные требования bars. Подготовка недостающих векторов идёт на DirectML; если он откажет, допускается явный режим CPU (OQ-196): устройство подготовки не входит в измеряемый путь и пишется в маркер готовности. До загрузки проверяется существующий кэш; скачивание весов в задачу не входит. Снимки рабочих индексов освобождаются до инференса. Сжатый корпус и небольшой манифест сохраняются как доказательства, распакованный снимок и временный индекс после проверки убираются.

Стенд Worker/IPC — `crates/bars-worker/examples/bench_worker_search_cpu.rs`. Он восстанавливает документы корпуса в собственную копию проекта, кладёт туда готовый индекс с записанными параметрами нарезки и поднимает настоящий воркер (`serve_with`, `ConfiguredProvider`) с отдельным профилем: `[embed] accelerator = "cpu"`, rerank выключен, остальные настройки поиска заводские. После регистрации воркер должен прийти в покой без единого embed документа: число чанков и векторов остаётся 5000, иначе серия не начинается. Те же 25 вопросов ×4 прохода идут последовательным клиентом по именованному каналу; время меряет клиент, от отправки до полного ответа. Выдача каждого запроса сверяется с выдачей core-прогона по разобранному JSON. Защита памяти та же, резерв commit 6 ГиБ; машина общая, поэтому стенд до 30 минут ждёт запаса, а не снижает порог.

Машина: Intel Core Ultra 5 125H, встроенная Intel Arc, 31,6 ГиБ, Windows 11 (OQ-197). Выделенного окна не было (OQ-195): автор работал, рядом шли bars автора, сборки и агенты других сессий. Записывалась только свободная память, загрузка CPU — нет.

### Проверка и воспроизведение CPU-стенда

`scripts/check-search-cpu.mjs <exe> <evidence-dir> <new-result.json>` самостоятельно восстанавливает собственный временный снимок и убирает его. [11 проверок](search-cpu-2026-10-23/checks.json): исходный корпус, подмена текста, недостаточное число чанков, повтор пути, выход за диапазон, совместимый кэш, уникальность 5000 хешей/баланс кэша, отказ перезаписи и сохранность результата, несовместимая модель и отсутствие ложного результата после отказа. Модели при этих проверках не загружаются.

Для повтора распаковать `corpus.json.gz` и `seed-vectors.sqlite.gz` в новый собственный временный каталог, в копии `inputs.json` заменить пути `seeds` (дополнительные источники — любые read-only индексы с тем же fingerprint). Запустить `validate`, `cache-plan`, затем `prepare <corpus.json> <inputs.json> <new-index.sqlite> <готовый-кэш-моделей> [cpu]`. Только при наличии `<index>.complete.json` — `run <inputs.json> <index.sqlite> <готовый-кэш-моделей> <dir>/core-rows.jsonl`, затем `bench_worker_search_cpu <corpus.json> <inputs.json> <index.sqlite> <готовый-кэш-моделей> <dir>/<new-out>`: воркер сверяет выдачу с `core-rows.jsonl` рядом с новой папкой. Оба стенда собираются в release по действующим [правилам сборки](build.md); новый snapshot через `freeze` изменит корпус и потребует отдельной серии. Сырые данные прогона 26-10-2026 под нагрузкой — [доказательства](search-cpu-2026-10-25/Index.md).

| Rerank 15 кандидатов | В позднем прогоне CPU 8,5 с, DirectML 5,3–5,8 с | Малый корпус не позволяет выбирать K по качеству |
| Запрос при индексации | После приоритета запроса и ограничения пачки максимум embed_query 22,8 → 3,0 с | Полный поиск с SQLite и rerank не измерен |

Начинать нужно с длительности rerank и ожидания модели: ускорение уже короткого embed_query многосекундный cross-encoder не устранит. Объявлять DirectML в целом медленнее CPU по раннему прогону нельзя.

## Справка по методам ускорения

Ниже — общее знание о методах; какие из них применены и что измерено, показано выше. Внешние ссылки — первичные источники на 18-10-2026; поведение upstream не означает доступность функции в закреплённой сборке bars.

- **Профилирование.** Разложение полного запроса: очередь → токенизация → копирование тензоров → embed → SQLite/FTS/векторы → пары → rerank → постобработка → IPC. Измерять этапы и внешнюю задержку клиента: сумма вложенных таймеров считает время дважды. [ORT profiling](https://onnxruntime.ai/docs/performance/tune-performance/profiling-tools.html) отделяет вычисления от накладных расходов. Режимы: холодная загрузка без скачивания, первый Run, повторные Run прогретой сессии.
- **CPU: потоки.** `intra-op` распараллеливает оператор, `inter-op` — независимые операторы; для последовательной цепочки transformer рост inter-op выигрыш не гарантирует. Пулы нескольких сессий конкурируют; spinning снижает задержку пробуждения ценой CPU и энергии. На гибридном CPU число логических потоков не равно оптимуму; питание, фоновые процессы и throttling фиксируют отдельно. [ORT threading](https://onnxruntime.ai/docs/performance/tune-performance/threading.html).
- **Формы и паддинг.** Часть работы attention растёт как квадрат длины, поэтому вдвое более короткий вход не даёт четырёхкратного ускорения. Группировка по длине убирает паддинг; доля паддинга — `1 − Σреальных токенов / (batch × padded_length)`. Рост batch ради throughput может ухудшить p95 поиска. Фиксированные buckets (например 64/128/256/512) — гипотеза для GPU/NPU: длинная последовательность идёт в следующий допустимый размер, молчаливое усечение — изменение качества; предел embed 8192 без отдельного решения в 512 не превращать. [ORT transformer optimization](https://onnxruntime.ai/docs/performance/transformers-optimization.html).
- **Граф и кэш.** ORT различает Basic/Extended/All; оптимизированный граф можно сохранить, но он зависит от EP, параметров и железа и не равен кэшу compiled engine. Ключ кэша — hash графа и external data, ORT/EP, параметры, формы, версия драйвера и устройство; ошибка кэша ведёт к пересозданию. [ORT graph optimizations](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html).
- **Precision.** FP16 требует kernels и не обязан исполняться на CPU; при потере точности часть узлов оставляют FP32, но casts тоже стоят времени ([ORT mixed precision](https://onnxruntime.ai/docs/performance/model-optimizations/float16.html)). Dynamic INT8 — рекомендуемый ORT исходный вариант для transformer, но без гарантии ускорения; QOperator и QDQ — разные представления, CPU INT8 нельзя автоматически переносить на DirectML/NPU; риск U8S8 saturation на части x86 проверяют через `reduce_range` или U8U8 ([ORT quantization](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)). BF16 на CPU без нужных инструкций эмулируется и может проиграть FP32; weight-only INT4/GGUF снижает память, но требует реализации matmul. Вдвое меньший файл не означает ни двукратного ускорения, ни вдвое меньшего пика.
- **I/O Binding** имеет смысл после доказательства значимых копирований: token IDs возникают на CPU, итоговый вектор нужен CPU-поиску, и полностью обмены не исключить ([ORT I/O Binding](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html)).
- **Меньше работы в rerank.** Порядок: убрать лишний паддинг → FP16/CPU INT8 → меньшая многоязычная модель ([mmarco-mMiniLMv2](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1), кандидат, а не равноценная замена bge-reranker-v2-m3) → только затем K и длина входа. K ограничен recall@K первого этапа: reranker не вернёт отрезанный правильный документ; порог до rerank тоже может уничтожить recall и по малому корпусу bars не выбирается.

Предложение исследования для дальнейшей работы (не принято): сначала профиль и размещение узлов, затем потоки CPU и паддинг rerank, потом buckets и OpenVINO GPU на Intel, статические NPU-графы и GGUF.

## Протокол воспроизведения замеров

Исторические числа разных устройств не смешиваются с текущими сериями. Основа — методика [бенча качества](search-quality.md).

1. Зафиксировать commit bars, CPU/GPU/NPU, ОС, драйвер, runtime/EP, ревизию и хеши модели, tokenizer, pooling, normalization, длины и K; отдельно — фактическое устройство и fallback (fallback не засчитывать как ускорение выбранного EP).
2. Зафиксировать корпус и вопросы. Сначала одинаковый FP32 baseline, затем менять одну переменную; финальную комбинацию повторить целиком. Порядок конфигураций чередовать; тяжёлые прогоны запускать последовательно.
3. Изолированные нагрузки: embed фиксированных текстов, rerank фиксированных пар (пул кандидатов baseline), настоящий `search` на снимке. Изменённый embed проверять на заново построенном собственном индексе: новые query-векторы со старыми document-векторами не полный тест.
4. Cold/load/first-run отдельно от warm: median, p95, число наблюдений; индексация — чанки/с и токены/с, полный и инкрементальный проход отдельно. Скрининг — три прохода train; финалисты — не меньше 100 тёплых наблюдений.
5. Режимы: один запрос, серия, несколько одновременных запросов через worker, запросы при индексации. Публиковать задержку каждого запроса; очередь не выдавать за параллельный Run (DirectML запрещает одновременный Run одной сессии).
6. Память: peak private bytes и working set процесса, VRAM и shared GPU memory ([memory.md](memory.md)); энергия — если цель батарея/NPU.
7. Качество: leader, Hit@3, MRR@10, nDCG@10, recall первого этапа, ложная выдача отрицательных вопросов, список потерь по идентификаторам; и до порога, и при рабочих порогах. Сначала проверить порядок и логиты/векторы, затем метрики поиска. Для эквивалентных оптимизаций правило отбора — нет новых провалов лидера/Hit@3 и нет снижения MRR на замороженном наборе. Для квантованного embed проверять весь retrieval, не косинус нескольких векторов.
8. Сохранять сырые наблюдения и условия (JSONL, хеши, статус complete/failed/unsupported), а не только среднее. Начальные прогоны при недостатке RAM/commit, профили при фоновых сборках и прогоны `quality-only` из выбора по скорости исключаются; тихое окно исключает также `cargo`.

Защита стенда: монитор перед запуском требует тихое окно и запас памяти (ожидание до 120 с); при потере запаса завершается только собственный процесс. Резервы и их происхождение — `memory.md`; это защита измерения, а не требование к продукту.
