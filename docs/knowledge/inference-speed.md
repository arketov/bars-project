# Ускорение инференса bars — замеры, отбор методов и протокол

← База знаний. Результат 18-10-2026: FP16 rerank с batch16 на DirectML ускорил полный поиск в 1,6–1,7 раза без обнаруженных потерь на 138 вопросах; проверены настоящий worker, конкуренция и поиск при индексации. Доказательства. Требования — Т-3, Т-17, НФТ-2; как внедрено и принято в продукте — [встроенные модели](../features/models/local-models.md#приёмка-продуктового-fp16-rerank).

Связанные исследования: [устройства, DirectML и библиотеки](inference-devices.md), память — [memory.md](memory.md), конкуренция за модель — [поиск при индексации](search-during-indexing.md), исторические числа — [спайк поиска](spike-search.md). Сравнение факторов CPU/K/длины, ограничения ноутбука и воспроизведение из сохранившихся файлов — [скорость rerank](rerank-speed.md).

## Условия замеров

i7-11700KF (8 ядер / 16 потоков), RTX 3090 24 ГБ, 32 ГБ RAM, Windows, fastembed 7.1.1 / ort 2.0.0-rc.13 ([hardware.json](quality-2026-10-18/hardware.json)). RTX 3090 не доказывает скорость, объём памяти или корректность Intel Arc, малой VRAM и ноутбуков.

Проверка локального fastembed 7.1.1: оптимизация графа Level3 уже включена; число intra-op потоков без настройки берётся из `available_parallelism`; для DirectML выключены memory pattern и параллельное исполнение; embed уже сортирует чанки по длине UTF-8 и возвращает исходный порядок. Повторное включение этого не является ускорением. Доступны `with_intra_threads` и `with_session_config`; inter-op, ORT profiling, I/O Binding и произвольный session builder стандартный конструктор не открывает — для них нужен минимальный исследовательский адаптер, без правки Cargo registry. Rerank токенизирует каждую пачку отдельно. Исходники проверены локально и не обязательно тождественны чистому архиву crate: хеши существенных файлов сохраняются в доказательствах.

## Полный поиск и качество FP16 rerank

Baseline — настоящий `BuiltinReranker` FP32 Auto/DirectML; кандидат — тот же encoder FP16, batch16, прежние K15 и max_length512. Embed, retrieval и запросы одинаковы. Загрузка модели и первый прогревочный запрос исключены из задержки. В каждой серии один проход по вопросам; p95 описывает этот набор, а не хвосты произвольной нагрузки.

| Набор | Вопросов | FP32 median / p95, с | FP16 median / p95, с | Новые потери |
|---|---:|---:|---:|---:|
| overdrive | 100 | 0,685 / 0,764 | 0,422 / 0,500 | 0 |
| bars | 24 | 0,673 / 0,744 | 0,400 / 0,498 | 0 |
| дополнительный holdout | 14 | 0,816 / 0,864 | 0,475 / 0,606 | 0 |

Проверялись лидер, Hit@3, MRR/nDCG и документные метрики при порогах 0 и 0,1, отрицательные вопросы, конечность оценок и отсутствие fallback. 138 вопросов — ограниченная регрессия, а не гарантия любых текстов и оборудования. Основной набор уже использовался для разработки, поэтому его test здесь — регрессия, не слепая оценка; малый holdout заморожен до просмотра precision/length, затем тоже стал известным.

## Настоящий worker, очередь и общая память

По 22 ответа каждого варианта через настоящий IPC: warm исключён, каждый ответ действительно `rerank`, fallback отсутствует. Восемь запросов каждого варианта начались при подтверждённой активной индексации копии проекта; оригинальный проект и установленный bars не менялись.

| Режим | n на вариант | FP32 median / max, с | FP16 median / max, с |
|---|---:|---:|---:|
| Последовательные | 8 | 0,692 / 0,824 | 0,470 / 0,500 |
| Два одновременных | 2 | 0,794 / 1,343 | 0,456 / 0,780 |
| Четыре одновременных | 4 | 1,236 / 2,490 | 0,772 / 1,400 |
| Во время индексации | 8 | 1,075 / 1,264 | 0,577 / 0,733 |

Все 44 ответа проверены по исходным gold-опорам, новых потерь нет. Очередь остаётся: числа не означают параллельный Run одной DirectML-сессии, а число запросов мало для SLA.

Sampled peak private worker: FP32 7,36 ГиБ → FP16 6,00 ГиБ; dedicated GPU 6,40 → 4,88 ГиБ; shared GPU 1,07 → 0,077 ГиБ. Это сравнение всего процесса с обеими моделями и индексацией; пики разных счётчиков могли возникнуть в разные моменты. Working Set не снизился (около 1,89 → 2,01 ГиБ): снижение private подтверждено, «ноль RAM при GPU» — нет.

CPU-пилот содержит три фиксированных train-вопроса на вариант: FP32 threads 1/2/4/8/16 дали median 40,13/21,97/12,60/9,35/7,97 с. Это не обоснование 16 потоков на любом CPU. Небольшой screen имеет дрейф повторного baseline около 13 %; выигрыш FP16 подтверждён отдельными полными сериями, а доли процента по screen выбирать нельзя.

INT8 контрпример: `od-010`, порог 0,1 — секционный Hit@3 1 → 0, MRR 0,5 → 0. FP32 CPU повторён трижды и сохраняет исходные показатели, поэтому потеря не объясняется только CPU/GPU. Exploratory INT8 остановлен после 10 наблюдений; полных метрик на 100 вопросах нет, timing quality-only не используется. Первая остановка на `od-001` по docMRR была слишком строгой (секционный MRR там улучшился) и сохранена как вспомогательная. Повторная калибровка INT8 — отдельное изменение, а не скрытая смена порога.

## Embed и индексация

Microbenchmark: 10 коротких запросов и 64 фиксированных текста, один проход. CPU FP32: query median 39–46 мс против 118 мс на DirectML; документы CPU16 1,55 текста/с против DirectML batch4 17,63. Переносить весь embed на CPU незачем: индексация существенно медленнее, а вторая постоянная CPU-сессия требует памяти. FP16 DirectML batch8: query 86 мс, документы 28,40 текста/с, минимум cosine с FP32 около 0,99991; INT8 CPU: query 19 мс, документы 4,86 текста/с, min cosine около 0,974. Близость векторов не доказывает качество поиска.

Настоящий `update_index` копии 176 документов / 946 chunks: чистые FP32 DirectML batch4 — 57,34 с, FP16 DirectML batch8 — 35,81 с. INT8 CPU16 по одному тексту (212,98 с) и FP32 CPU16 batch4 (533,70 с) завершены, но монитор обнаружил постороннюю нагрузку: это функциональные проходы, а не чистое сравнение. Все четыре варианта выполнили полный, неизменённый и инкрементальный проходы без problems; изменение одного документа затронуло 2 embeddings и переиспользовало 4 chunks. Загрузка и прогрев модели исключены; проходы одиночные, не распределение latency.

Качество FP16 embed проверяется отдельно от rerank: свой индекс, свой fingerprint, полный retrieval; смешивать FP16 query с FP32-индексом нельзя. Результаты retrieval, память и отказ INT8 — [memory.md](memory.md#embed-fp16-и-int8).

## Переносимость и границы вывода

В режиме DirectML основной инференс идёт на GPU; токенизация, подготовка входов, SQLite и часть служебных узлов графа остаются на CPU, а выбор EP не означает размещение каждого узла на GPU. У интегрированной GPU память общая: перенос вычислений не освобождает физическую RAM автоматически, runtime, копии весов и рабочие буферы требуют системного commit.

CPU-only rerank сохраняет FP32 batch4: INT8 rerank не проходит критерий качества. Вне Windows Auto остаётся CPU. CUDA отсутствует в поставляемом runtime; OpenVINO, NPU и CoreML аппаратно не проверены. НФТ-2 на 5000 chunks результатом не закрывается: реальный индекс серий 18-10-2026 содержал 946 chunks, а синтетический с повторно использованными векторами естественный корпус не заменяет.

## Естественные 5 000 чанков

Статус 23-10-2026: корпус заморожен, стенд собран, 11 проверок без моделей прошли. Одна аппаратная попытка подготовки остановлена Monitor по commit после 7 чанков; полного индекса и наблюдений задержки нет. НФТ-2 остаётся открытым. Изменение продуктовых умолчаний — отдельная работа после результата исследования.

Метод: заморозить существующие Markdown-документы, нарезать штатной `chunk_document` с min250/max6000, выбрать ровно 5 000 разных `embed_hash` без размножения векторов или уменьшения размера чанков. Если одного зарегистрированного проекта недостаточно, исследовательский корпус составляется из документов проектов с указанием происхождения; это ограничение репрезентативности, а не результат на каждом исходном проекте. Совпадающие пути берутся только из первого источника; путь в `embed_text` сохраняется. Готовые векторы разрешено переиспользовать только по точному `embed_hash` и FP32 fingerprint; недостающие считаются настоящей bge-m3. Рабочие индексы открываются только для чтения.

Измеряемый путь — настоящий `bars_core::search::search`, CPU FP32 bge-m3, `None` вместо reranker, штатные 30 кандидатов/5 результатов/порог 0, весь корпус. Загрузка модели и прогрев записываются отдельно. Серия — 25 заранее фиксированных русских вопросов ×4 прохода: идентификаторы, короткие и длинные формулировки, вопрос вне тематики корпуса. При пороге 0 отсутствие ответа не требует пустой выдачи; без gold это только нагрузка, не проверка качества. Сохраняются все наблюдения, median/p95/max, доля ответов <1 с, хеши выдачи и число вызовов embed; ошибка останавливает серию без успешной сводки. Вложенный таймер embed входит в полный таймер; их нельзя складывать. Повторяемость выдачи — проверка стабильности, не размеченная оценка качества.

Первый запрос после загрузки, тёплый core-поиск и IPC — разные границы. Core-проход не подтверждает задержку окна или MCP; для полной приёмки требуется также настоящий Worker/IPC с тем же CPU и корпусом. НФТ-2 не задаёт процентиль: для исследованной серии консервативно проверяются все наблюдения <1с; p95 отдельно описывает распределение. Холодный диск не имитируется очисткой системного кэша. Фоновые процессы и запас commit фиксируются; при недостатке ресурсов серия остаётся неполной, работающий bars и настройки ОС не меняются.

Стенд — `crates/bars-core/examples/bench_search_cpu.rs`: `freeze`, `validate`, `cache-plan`, `preflight`, `prepare`, `run`. Первые четыре режима не загружают модели. Аппаратные режимы используют существующий Windows Monitor: перед подготовкой резерв 8 ГиБ commit, перед CPU-поиском 6 ГиБ; при запасе менее 1 ГиБ завершается только собственный процесс. Это консервативные границы исследования, не системные требования bars. До загрузки проверяется существующий кэш; скачивание весов в задачу не входит. Снимки рабочих индексов освобождаются до инференса. Сжатый корпус и небольшой манифест сохраняются как доказательства, распакованный снимок и временный индекс после проверки убираются.

Одна попытка FP32 DirectML начиналась с запасом commit 8,82 ГиБ. Повтор в этой сессии не выполнялся.

### Проверка и воспроизведение CPU-стенда

`scripts/check-search-cpu.mjs <exe> <evidence-dir> <new-result.json>` самостоятельно восстанавливает собственный временный снимок и убирает его. [11 проверок](search-cpu-2026-10-23/checks.json): исходный корпус, подмена текста, недостаточное число чанков, повтор пути, выход за диапазон, совместимый кэш, уникальность 5000 хешей/баланс кэша, отказ перезаписи и сохранность результата, несовместимая модель и отсутствие ложного результата после отказа. Модели при этих проверках не загружаются.

Для аппаратного продолжения распаковать `corpus.json.gz` и `seed-vectors.sqlite.gz` в новый собственный временный каталог, в копии `inputs.json` заменить только путь `seeds`. Запустить `validate`, `cache-plan`, затем `prepare <corpus.json> <inputs.json> <new-index.sqlite> <готовый-кэш-моделей>`. Только при наличии `<index>.complete.json` — `run <inputs.json> <index.sqlite> <готовый-кэш-моделей> <new-rows.jsonl>`. Для аппаратной попытки нужен `bench_search_cpu`, собранный по действующим [правилам сборки](build.md); новый snapshot исходных документов через `freeze` изменит корпус и потребует отдельной серии. Worker/IPC ещё не проверен и требует отдельного продолжения с теми же текстами, настройками CPU и ревизией индекса.

## Справка по методам ускорения

Ниже — общее знание о методах; какие из них применены и что измерено, показано выше. Внешние ссылки — первичные источники на 18-10-2026; поведение upstream не означает доступность функции в закреплённой сборке bars.

- **Профилирование.** Разложение полного запроса: очередь → токенизация → копирование тензоров → embed → SQLite/FTS/векторы → пары → rerank → постобработка → IPC. Измерять этапы и внешнюю задержку клиента: сумма вложенных таймеров считает время дважды. [ORT profiling](https://onnxruntime.ai/docs/performance/tune-performance/profiling-tools.html) отделяет вычисления от накладных расходов. Режимы: холодная загрузка без скачивания, первый Run, повторные Run прогретой сессии.
- **CPU: потоки.** `intra-op` распараллеливает оператор, `inter-op` — независимые операторы; для последовательной цепочки transformer рост inter-op выигрыш не гарантирует. Пулы нескольких сессий конкурируют; spinning снижает задержку пробуждения ценой CPU и энергии. На гибридном CPU число логических потоков не равно оптимуму; питание, фоновые процессы и throttling фиксируют отдельно. [ORT threading](https://onnxruntime.ai/docs/performance/tune-performance/threading.html).
- **Формы и паддинг.** Часть работы attention растёт как квадрат длины, поэтому вдвое более короткий вход не даёт четырёхкратного ускорения. Группировка по длине убирает паддинг; доля паддинга — `1 − Σреальных токенов / (batch × padded_length)`. Рост batch ради throughput может ухудшить p95 поиска. Фиксированные buckets (например 64/128/256/512) — гипотеза для GPU/NPU: длинная последовательность идёт в следующий допустимый размер, молчаливое усечение — изменение качества; предел embed 8192 без отдельного решения в 512 не превращать. [ORT transformer optimization](https://onnxruntime.ai/docs/performance/transformers-optimization.html).
- **Граф и кэш.** ORT различает Basic/Extended/All; оптимизированный граф можно сохранить, но он зависит от EP, параметров и железа и не равен кэшу compiled engine. Ключ кэша — hash графа и external data, ORT/EP, параметры, формы, версия драйвера и устройство; ошибка кэша ведёт к пересозданию. [ORT graph optimizations](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html).
- **Precision.** FP16 требует kernels и не обязан исполняться на CPU; при потере точности часть узлов оставляют FP32, но casts тоже стоят времени ([ORT mixed precision](https://onnxruntime.ai/docs/performance/model-optimizations/float16.html)). Dynamic INT8 — рекомендуемый ORT исходный вариант для transformer, но без гарантии ускорения; QOperator и QDQ — разные представления, CPU INT8 нельзя автоматически переносить на DirectML/NPU; риск U8S8 saturation на части x86 проверяют через `reduce_range` или U8U8 ([ORT quantization](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)). BF16 на CPU без нужных инструкций эмулируется и может проиграть FP32; weight-only INT4/GGUF снижает память, но требует реализации matmul. Вдвое меньший файл не означает ни двукратного ускорения, ни вдвое меньшего пика.
- **I/O Binding** имеет смысл после доказательства значимых копирований: token IDs возникают на CPU, итоговый вектор нужен CPU-поиску, и полностью обмены не исключить ([ORT I/O Binding](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html)).
- **Меньше работы в rerank.** Порядок: убрать лишний паддинг → FP16/CPU INT8 → меньшая многоязычная модель ([mmarco-mMiniLMv2](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1), кандидат, а не равноценная замена bge-reranker-v2-m3) → только затем K и длина входа. K ограничен recall@K первого этапа: reranker не вернёт отрезанный правильный документ; порог до rerank тоже может уничтожить recall и по малому корпусу bars не выбирается.

Предложение исследования для дальнейшей работы (не принято): сначала профиль и размещение узлов, затем потоки CPU и паддинг rerank, потом buckets и OpenVINO GPU на Intel, статические NPU-графы и GGUF.

## Протокол воспроизведения замеров

Исторические числа разных устройств не смешиваются с текущими сериями. Основа — методика [бенча качества](search-quality.md).

1. Зафиксировать commit bars, CPU/GPU/NPU, ОС, драйвер, runtime/EP, ревизию и хеши модели, tokenizer, pooling, normalization, длины и K; отдельно — фактическое устройство и fallback (fallback не засчитывать как ускорение выбранного EP).
2. Зафиксировать корпус и вопросы. Сначала одинаковый FP32 baseline, затем менять одну переменную; финальную комбинацию повторить целиком. Порядок конфигураций чередовать; тяжёлые прогоны запускать последовательно.
3. Изолированные нагрузки: embed фиксированных текстов, rerank фиксированных пар (пул кандидатов baseline), настоящий `search` на снимке. Изменённый embed проверять на заново построенном собственном индексе: новые query-векторы со старыми document-векторами не полный тест.
4. Cold/load/first-run отдельно от warm: median, p95, число наблюдений; индексация — чанки/с и токены/с, полный и инкрементальный проход отдельно. Скрининг — три прохода train; финалисты — не меньше 100 тёплых наблюдений.
5. Режимы: один запрос, серия, несколько одновременных запросов через worker, запросы при индексации. Публиковать задержку каждого запроса; очередь не выдавать за параллельный Run (DirectML запрещает одновременный Run одной сессии).
6. Память: peak private bytes и working set процесса, VRAM и shared GPU memory ([memory.md](memory.md)); энергия — если цель батарея/NPU.
7. Качество: leader, Hit@3, MRR@10, nDCG@10, recall первого этапа, ложная выдача отрицательных вопросов, список потерь по идентификаторам; и до порога, и при рабочих порогах. Сначала проверить порядок и логиты/векторы, затем метрики поиска. Для эквивалентных оптимизаций правило отбора — нет новых провалов лидера/Hit@3 и нет снижения MRR на замороженном наборе. Для квантованного embed проверять весь retrieval, не косинус нескольких векторов.
8. Сохранять сырые наблюдения и условия (JSONL, хеши, статус complete/failed/unsupported), а не только среднее. Начальные прогоны при недостатке RAM/commit, профили при фоновых сборках и прогоны `quality-only` из выбора по скорости исключаются; тихое окно исключает также `cargo`.

Защита стенда: монитор перед запуском требует тихое окно и запас памяти (ожидание до 120 с); при потере запаса завершается только собственный процесс. Резервы и их происхождение — `memory.md`; это защита измерения, а не требование к продукту.
