# Ускорение инференса bars

Результаты 18-10-2026: FP16 rerank + batch16 на DirectML ускорил полный поиск в 1,6–1,7 раза без обнаруженных потерь на 138 вопросах; проверен настоящий worker, конкуренция и поиск при индексации. [Доказательства](inference-2026-10-18/Index.md). Закреплённый FP16 loader реализован в продуктовом коде; установленное приложение в этой сессии не обновляется. Требования — Т-3, Т-17, НФТ-2; продуктовый контракт — [встроенные модели](../features/models/local-models.md).

Связанные исследования: [CPU, GPU и NPU](inference-devices.md), [DirectML](directml-performance.md), [библиотеки](inference-libraries.md). Исторические числа — [спайк поиска](spike-search.md), конкуренция за модель — [поиск при индексации](search-during-indexing.md).

Проверка локального fastembed 7.1.1, архитектура стенда и воспроизведение — [проект этапа 11](../features/models/inference-plan.md). Level3 и сортировка embed уже включены; повторное включение не является ускорением. Автор 18-10-2026 поручил перейти от широкой сетки к внедрению и допускает полезные микрооптимизации; дополнительные ABBA/binding/cache не являются условием применения уже проверенного результата.

## Полный поиск и качество FP16 rerank

Условия: i7-11700KF, RTX 3090 24 ГБ, 32 ГБ RAM, Windows, fastembed 7.1.1 / ort 2.0.0-rc.13. Baseline — настоящий `BuiltinReranker` FP32 Auto/DirectML; кандидат — тот же encoder FP16, batch16, прежние K15 и max_length512. Embed, retrieval и запросы одинаковы. Загрузка модели и отдельный первый warm-запрос исключены из задержки. В каждой серии один проход по вопросам; p95 описывает этот набор, не гарантирует хвосты произвольной нагрузки.

| Набор | Вопросов | FP32 median / p95, с | FP16 median / p95, с | Новые потери |
|---|---:|---:|---:|---:|
| overdrive | 100 | 0,685 / 0,764 | 0,422 / 0,500 | 0 |
| bars | 24 | 0,673 / 0,744 | 0,400 / 0,498 | 0 |
| дополнительный holdout | 14 | 0,816 / 0,864 | 0,475 / 0,606 | 0 |

Проверялись лидер, Hit@3, MRR/nDCG и документные метрики при порогах 0 и 0,1, отрицательные вопросы, конечность оценок и отсутствие fallback. 138 вопросов — ограниченная регрессия; это не гарантия любых текстов и оборудования. Основной набор этапа 9 уже использовался для разработки, поэтому его test здесь — регрессия, не новая слепая оценка. Малый holdout заморожен до просмотра precision/length, затем тоже стал известным.

## Настоящий worker, очередь и общая память

По 22 ответа каждого варианта через настоящий IPC: warm исключён, каждый ответ действительно `rerank`, fallback отсутствует. Восемь запросов каждого варианта начались при подтверждённой активной индексации копии проекта. Оригинальный проект и установленный bars этим стендом не менялись.

| Режим | n на вариант | FP32 median / max, с | FP16 median / max, с |
|---|---:|---:|---:|
| Последовательные | 8 | 0,692 / 0,824 | 0,470 / 0,500 |
| Два одновременных | 2 | 0,794 / 1,343 | 0,456 / 0,780 |
| Четыре одновременных | 4 | 1,236 / 2,490 | 0,772 / 1,400 |
| Во время индексации | 8 | 1,075 / 1,264 | 0,577 / 0,733 |

Все 44 ответа проверены по исходным gold-опорам, новых потерь не найдено. Очередь остаётся: эти числа не означают параллельный Run одной DirectML-сессии. Число запросов мало для SLA.

Sampled peak private worker: FP32 7,36 ГиБ → FP16 6,00 ГиБ; dedicated GPU 6,40 → 4,88 ГиБ; shared GPU 1,07 → 0,077 ГиБ. Это сравнение всего процесса с обеими моделями и индексацией; пики разных счётчиков могли возникнуть в разные моменты. Working Set не снизился (около 1,89 → 2,01 ГиБ): его нельзя выдавать за private commit или утверждать, что вся RAM освобождена. Снижение private подтверждено, «ноль RAM при GPU» не подтверждён.

CPU-пилот содержит только три фиксированных train-вопроса на вариант: FP32 threads1/2/4/8/16 median 40,13/21,97/12,60/9,35/7,97 с. Это не обоснование 16 потоков на любом CPU. Небольшой screen имеет дрейф повторного baseline около 13%; итоговый выигрыш FP16 подтверждается отдельными полными сериями, но доли процентов по screen выбирать нельзя.

INT8 counterexample: `od-010`, threshold0,1 — секционный Hit@3 1 → 0, MRR 0,5 → 0. FP32 CPU повторён трижды и сохраняет исходные показатели, поэтому потеря не объясняется только CPU/GPU. Exploratory INT8 остановлен после 10 наблюдений; полных метрик на 100 вопросах нет, timing quality-only не используется. Первая остановка на `od-001` по docMRR была слишком строгой: секционный MRR там улучшился. Она сохранена как вспомогательный опыт, а вывод об отклонении основан на новом первичном counterexample. Повторная калибровка INT8 может быть отдельным изменением, не скрытой сменой порога.

## Embed и индексация: полезный кандидат, отдельная приёмка

Microbenchmark: 10 коротких запросов и 64 фиксированных текста, один проход. CPU FP32 query median 39–46 мс против DirectML 118 мс; документы CPU16 1,55 текста/с против DirectML batch4 17,63. Это не основание переносить весь embed на CPU: индексация существенно медленнее, а вторая постоянная CPU-сессия требует дополнительной памяти.

FP16 DirectML batch8: query 86 мс, документы 28,40 текста/с; минимум cosine с FP32 около 0,99991. INT8 CPU: query 19 мс, документы 4,86 текста/с, min cosine около 0,974. Близость векторов не доказывает качество поиска.

Настоящий `update_index` копии 176 документов / 946 chunks: чистые FP32 DirectML batch4 57,34 с и FP16 DirectML batch8 35,81 с. INT8 CPU16 по одному тексту 212,98 с и FP32 CPU16 batch4 533,70 с завершены, но их монитор обнаружил постороннюю нагрузку: это функциональные проходы, не чистое сравнение скорости. Все четыре варианта выполнили полный, неизменённый и инкрементальный проходы без problems; изменение одного документа затронуло 2 embeddings и переиспользовало 4 chunks. Model load/warm исключены. Это одиночные проходы, не распределение latency. Детали и мониторы — в доказательствах.

FP16 embed не включён в продукт: требуется полный retrieval на его собственном индексе и контракт fingerprint/CPU fallback. Смешивать FP16 query с прежним FP32 индексом без этой проверки нельзя. Успешная индексация не закрывает эту приёмку.

## Переносимость и границы вывода

В режиме DirectML основной инференс выполняется на GPU; tokenizer/подготовка входов, SQLite и часть служебных узлов графа остаются CPU. Выбор EP не означает размещение каждого узла на GPU. У интегрированной GPU память общая — перенос вычислений не освобождает физическую RAM автоматически. Runtime, копии весов и рабочие буферы всё равно требуют системного commit. Наиболее узкое практическое внедрение — FP16 rerank, без второй постоянной модели и без сокращения входов.

RTX 3090 не доказывает скорость, объём памяти или корректность Intel Arc, малой VRAM и ноутбуков. CPU-only сохраняет FP32 batch4; INT8 пока не проходит критерий качества. Вне Windows Auto остаётся CPU. CUDA отсутствует в поставляемом runtime, OpenVINO/NPU/CoreML аппаратно не проверены. ISS-03 другой машины остаётся открытой.

НФТ-2 на 5000 chunks этим результатом не закрывается: основной реальный индекс содержит 946 chunks. Подготовленный синтетический индекс с повторно использованными векторами не заменяет естественный корпус и не превращается в приёмку без запуска. Непроверенные платформы и методы — документированные ограничения, не повод задерживать подтверждённое локальное ускорение.

Начальные прогоны при недостатке RAM/commit и профили при фоновых сборках исключены из выбора по скорости. EP trace полезен для размещения узлов, но его длительности не являются чистым CPU/GPU сравнением. Полные данные чужого проекта, SQLite и модели остаются в ignored `spikes/inference`; в Git публикуются числа, структурные строки без тел документов, условия и хеши.

## Продуктовое внедрение и приёмка

`BuiltinReranker` использует FP16 на DirectML и прежний FP32 на CPU; tokenizer работает на CPU. Веса и четыре файла tokenizer/config закреплены и проверяются BLAKE3. Метка GPU-кэша требует атомарного manifest после проверки содержимого; изменение размера/mtime снимает готовность без чтения гигабайта при каждом опросе окна. Loader перед открытием снова проверяет содержимое. Пачка GPU уменьшается 16→4→1 только при ошибке allocation; ветка проверена unit-тестом, а не физическим малым GPU.

Отдельная приёмка продуктового loader: 138 полных ответов core и 22 настоящих IPC-ответа, ноль новых потерь выбранных метрик при порогах 0/0,1, отсутствие CPU fallback. Хеши бинарников/исходников, параметры, мониторы и строки без тел документов — [в доказательствах](inference-2026-10-18/Index.md). Эти прогоны `quality-only`, их timing не добавляется к чистому сравнению скорости. Реальный CPU-тест подтверждает FP32/batch4 и исходный порядок оценок. Финальная метка кэша дополнительно проверяется целевыми тестами и пересборкой; проверенный старый бинарник не объявляется доказательством изменившихся исходников.

Итоговая проверка текущего кода: 197 core и 142 worker lib-теста прошли. За время приёмки другая сессия изменила общий `worker/models.rs`; в доказательствах сохранены `buildSources` и `sourceDrift`, а не утверждение о тождестве всей текущей рабочей копии испытанному бинарнику. Единственная поздняя правка core — распознавание HRESULT OOM и два unit-assert: удаление этих трёх строк даёт точный прежний SHA256, успешный путь инференса не изменён. Она проверена unit-тестом. Новые lifecycle-доработки другой сессии не получают физическую приёмку автоматически от этого бенча.

Воспроизведение: `spikes/inference/seed-product-cache.mjs` создаёт свою копию кэша из уже скачанных весов (hardlinks без изменения источников; hf-hub 0.5 требует `refs/<commit>` даже для полного SHA). `product-source-state.mjs capture` фиксирует входы до сборки; вызов без аргумента сверяет их после сборки и приёмки. Release examples `bench_inference`/`bench_worker_inference`, режимы `full`/`worker`, config `production.json`, новые output-root. `accept-product.mjs <prefix>` проверяет 160 ответов и сохраняет доказательства; `preserve-final.mjs` обновляет SHA256.

Первая копия кэша не содержала refs закреплённых ревизий: началось повторное скачивание, пересекающийся запуск получил lock error и CPU fallback. Эти папки не засчитаны как FP16-приёмка. Исправлена фикстура, повтор выполнен последовательно. Полная свежая загрузка через сеть не считается принятой по кэшированному прогону. Слабые GPU, ноутбук, TTL и FP16 embed остаются отдельными проверками.

## Профилирование до оптимизаций

Предлагаемое разложение полного запроса: очередь → токенизация → выделение и копирование тензоров → embed → SQLite/FTS/векторы → подготовка пар → rerank → постобработка → IPC. Измерять как этапы, так и внешнюю задержку клиента: сумма вложенных таймеров может дважды считать одно время. ORT предоставляет профиль операторов; он помогает отделить вычисления от накладных расходов. [ORT profiling](https://onnxruntime.ai/docs/performance/tune-performance/profiling-tools.html).

Три самостоятельных режима: холодная загрузка без скачивания, первый Run после создания сессии, повторные Run прогретой сессии. Скачивание — отдельный показатель. Сохранять сессию между запросами; прогревать типовые формы, а не только одну короткую строку. Эти предложения требуют проверки фактического пути fastembed, а не добавления повторного прогрева поверх существующего.

## CPU: потоки и конкуренция

`intra-op` распараллеливает один оператор; `inter-op` — независимые операторы при параллельном исполнении графа. Для последовательной цепочки transformer увеличение inter-op не гарантирует выигрыша. Пулы нескольких сессий могут конкурировать; spinning снижает задержку пробуждения ценой CPU и энергии. [ORT threading](https://onnxruntime.ai/docs/performance/tune-performance/threading.html).

Кандидат опыта: default, 1, 2, 4, 8 intra-op потоков; inter-op сначала оставить без изменения. Сравнить одиночный поиск и поиск при индексации. На гибридном CPU число логических потоков не равно оптимальной настройке: отдельно фиксировать питание, фоновые процессы и throttling. Не задавать affinity и не отключать E-ядра без отдельного опыта.

## Формы входа, паддинг и пачки

Для обычного плотного attention часть работы растёт как квадрат длины последовательности; общий transformer содержит и линейные по длине блоки. Поэтому сокращение входа вдвое не обещает четырёхкратного ускорения всей модели. Группировка по длине уменьшает бесполезный паддинг; её эффективность зависит от экспорта и kernels. [ORT transformer optimization](https://onnxruntime.ai/docs/performance/transformers-optimization.html).

В bars сортировка embed-чанков по длине уже описана; индексатор также ограничивает объём пачки. Следующие кандидаты: считать бюджет в токенах, группировать пары rerank по длине, восстанавливать исходное соответствие результатов документам. Полезно сохранять долю паддинга: `1 - sum(real_tokens)/(batch * padded_length)`. Один длинный текст всё равно может занять сессию надолго; увеличение batch ради throughput способно ухудшить p95 поиска.

Фиксированные buckets, например 64/128/256/512 токенов, — гипотеза для GPU/NPU. Последовательность длиннее bucket должна перейти в следующий допустимый размер; молчаливое усечение — изменение качества. Для embed нельзя превратить действующий предел 8192 в 512 ради скорости без отдельного решения.

## Оптимизация графа и кэш

ORT различает Basic, Extended и All: constant folding, устранение лишних узлов, поддерживаемые fusion и преобразования layout. Оптимизированный граф можно сохранить для ускорения следующего старта; он зависит от EP, параметров и совместимого железа. Кэш графа не равен кэшу скомпилированного accelerator engine. [ORT graph optimizations](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html).

Для bars сначала выяснить фактический уровень в fastembed 7.1.1 и уже выполненные преобразования экспорта. Ключ будущего кэша: hash графа и external data, ORT/EP, параметры оптимизации, формы и типы; для кэша драйвера также его версия и устройство. Ошибка кэша должна приводить к пересозданию из исходного артефакта. API настройки сессии в `ort` не означает, что fastembed предоставляет эту настройку без изменения интеграции.

## FP16, BF16, INT8 и INT4

| Вариант | Потенциальная польза | Что проверить |
|---|---|---|
| FP16 / mixed precision | Меньше весов и обменов, GPU kernels | Поддержку всех узлов, casts и чувствительные операции; NaN/Inf и логиты |
| BF16 | Диапазон экспоненты ближе к FP32 | Конкретные инструкции CPU/GPU и EP; эмуляция может проиграть FP32 |
| Dynamic INT8 | Кандидат для CPU transformer; меньше весов | Накладные расходы квантования активаций, покрытие операторов и ranking |
| Static INT8 QDQ | Калибровка под поддерживаемый accelerator | Репрезентативные русские запросы, код и длинные пары; совместимость EP |
| Weight-only INT4 / GGUF | Снижение памяти больших моделей | Реализацию matmul, цену распаковки и качество; GGUF не загружается как ONNX |

ORT рекомендует dynamic quantization как исходный вариант для transformer, но это не гарантия ускорения. QOperator и QDQ — разные представления графа; CPU INT8 нельзя автоматически переносить на DirectML/NPU. Известный риск U8S8 на части x86 — saturation; при потере качества проверяют `reduce_range` или U8U8. [ORT quantization](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html).

FP16 требует подходящих kernels; CPU fallback не обязан исполнять FP16-граф. При потере точности часть операций оставляют FP32, однако дополнительные casts тоже стоят времени. [ORT mixed precision](https://onnxruntime.ai/docs/performance/model-optimizations/float16.html). Размер файла вдвое меньше не означает ни двукратного ускорения, ни вдвое меньшего пика памяти.

## Rerank: уменьшать работу с проверкой качества

Порядок кандидатов: убрать лишний паддинг → проверить FP16/CPU INT8 → сравнить меньшую многоязычную модель → только затем сокращать K или вход. Ограничение K определяется recall@K первого этапа: reranker не вернёт отрезанный правильный документ. Порог до rerank тоже способен уничтожить recall; его нельзя выбирать по маленькому корпусу bars.

Для отдельного сравнения подходит [mmarco-mMiniLMv2-L12-H384-v1](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1): многоязычный cross-encoder меньшей архитектуры. Это кандидат, не равноценная замена bge-reranker-v2-m3; нужны русский технический корпус, проверка ONNX-экспорта и новая оценка порогов. Текущий reranker и его raw-score/sigmoid описаны в [local-models.md](../features/models/local-models.md).

## Протокол воспроизведения замеров

Протокол изолированного исследования дополняет [бенч качества](search-quality-benchmark.md); исторические числа разных устройств не смешиваются с текущими сериями.

1. Зафиксировать commit bars, CPU/GPU/NPU, ОС, драйвер, runtime/EP, ревизию и хеши модели, tokenizer, pooling, normalization, длины и K. Отдельно указать фактическое устройство выполнения и fallback.
2. Зафиксировать корпус и вопросы. Сначала одинаковый FP32 baseline, затем менять одну переменную; финальную комбинацию повторить целиком. Порядок конфигураций чередовать, чтобы прогрев и температура не определяли победителя.
3. Измерять cold/load/first-run отдельно от warm: median, p95, число наблюдений; индексацию — чанки/с и токены/с. Для устойчивого p95 нужны повторения, а не один замер на каждый из 24 вопросов.
4. Режимы: один запрос, серия, конкурентные запросы, поиск во время индексации. Память: private working set/commit, device memory и shared memory; отдельно пиковые значения. Энергию измерять, если цель — батарея/NPU.
5. Качество: recall@K до rerank, MRR/nDCG после, провалы по группам, отсутствие NaN/Inf. Для квантованного embed проверять весь retrieval, а не только косинус нескольких векторов; для rerank — логиты и порядок, а не только сигмоиду.
6. Сохранять сырые наблюдения и условия, не только среднее ускорение. Умолчания менять после проверки качества; уменьшение памяти или энергии можно признать отдельной пользой без ускорения.

## Порядок проверки для bars

Предложение исследования: **P0** — профиль и фактическое размещение узлов; **P1** — потоки CPU, паддинг rerank, FP16 DirectML, CPU INT8; **P2** — buckets и OpenVINO GPU на Intel; **P3** — статические NPU-графы и GGUF. I/O Binding имеет смысл после доказательства значимых копирований: входные token IDs возникают на CPU, итоговый вектор нужен CPU-поиску; полностью исключить эти обмены нельзя. [ORT I/O Binding](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html).
