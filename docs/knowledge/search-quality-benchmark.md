## Сравниваемые режимы

1. Первый этап: векторный, FTS и фактическое слияние RRF с приоритетом идентификаторов. Измерить recall@3/5/8/10/15/20/30/50, долю вопросов с хотя бы одним правильным разделом, ранг первого правильного раздела. Проверить `candidates=30` и `50`; различать глубину исходных списков и глубину rerank.
2. Без rerank: текущий порядок слияния и экспериментальный порядок по косинусу на одинаковом наборе кандидатов. Продакшен-порядок в рамках этого замера не менять: внедрение ISS-02 — отдельный пункт.
3. С rerank: K=3, 5, 8, 10, 15, 20, 30; K=50 — если первый этап покажет полезные ответы глубже 30. Кандидаты — строго из фактического порядка перед rerank. Основные модели: bge-m3 и bge-reranker-v2-m3; сравнение других моделей и оптимизация инференса остаются отдельной работой.
4. Пороги: без отсечения и 0.1/0.3/0.5 для rerank; для косинуса — 0/0.4/0.5/0.6. Подбор только на первой части, затем один итоговый прогон выбранного варианта на проверочной части.

## Метрики и воспроизводимость

- Качество: правильный лидер, Hit@3/5, MRR@10, nDCG@10 с бинарной релевантностью. Дополнительно показатели на уровне документа; основные — по разделам. Для отрицательных вопросов — доля запросов с ложной непустой выдачей; для положительных — потери правильных ответов из-за порога.
- Для глубины — распределение рангов и перечень вопросов, где K=5 теряет ответ, а K=15/30 находит. Если таких вопросов нет, явно признать отсутствие основания сокращать глубину.
- Время: загрузка/прогрев отдельно; полный поиск, embed запроса, получение кандидатов и rerank отдельно; медиана и p95. Сохранить сырые строки на каждый вопрос, порядок кандидатов, оценки и результаты в JSONL/CSV. Повторы для задержек — три, последовательные, после прогрева, без параллельной индексации; указать фоновую нагрузку и устройство.
- Проверки бенча: отсутствующие/изменённые эталоны, несколько правильных разделов, неправильный раздел правильного файла, нулевая релевантность, расчёт recall/MRR/nDCG на маленьких известных списках. Ошибки модели и fallback не засчитывать как успешный rerank.

## Решение об умолчаниях и сдача

Согласованный критерий: уменьшать K лишь при потере не более одного процентного пункта Hit@3 и MRR не более 0.01 относительно K=15 на проверочной части, без потери покрытия вопросов первым этапом; публиковать абсолютные количества и ограничения малого набора. Если данных недостаточно, оставить 15. Увеличение K обосновать найденными ответами и ценой по времени.

Для включения rerank по умолчанию нужны одновременно выигрыш качества и приемлемая задержка. Численного бюджета задержки автор пока не задал: замер должен дать конкретное сравнение, после которого решение фиксируется явно. Порог выбирать с отчётом о потерях ответов и ложной выдаче; отсутствие убедительного выигрыша допускает сохранение умолчаний.

Сдача: воспроизводимый Rust-бенч и разметка, сырые результаты, отчёт в `docs/knowledge/`, обоснованные умолчания в `features/settings/settings.md` и коде при наличии оснований, проверки и согласованный объём коммита. IDEA-06 закрывается после прогона и решения, а не после написания бенча.

## Запуск нового бенча

Реализация: `crates/bars-core/examples/bench_quality.rs`; наборы `examples/quality/overdrive.json` и `bars.json`. В JSON каждого вопроса: `split`, категория, запрос, допустимые разделы (`path`, `heading`), дословная опора `evidence` и обоснование. Основной набор содержит 60/40 вопросов, положительных 48/32, отрицательных 12/8. Набор bars сохраняет прежние 24 вопроса; его сравнивают на уровне документов.

После сборки `cargo build --release -p bars-core --example bench_quality`:

```text
bench_quality prepare <исходный-проект> <новая-папка-стенда> <папка-моделей>
bench_quality validate <папка-стенда>/project <набор.json>
bench_quality run <папка-стенда> <набор.json> <папка-моделей> <папка-результатов> tune 30,50 3,5,8,10,15,20,30 3 auto
node scripts/analyze-quality.mjs <набор.json> <сводка.json> <папка-результатов>
```

`prepare` копирует Markdown, получает согласованную копию существующего SQLite через read-only `VACUUM INTO`, затем обновляет только копию. Проверяет соответствие хешей всех индексируемых документов снимку. Служебный `BARS_INSTRUCTION.md` сохраняется в снимке, но штатный обход исключает его из индекса (Т-8). Хеши, нарезка, модель и число чанков — в `manifest.json`.

`run` проверяет снимок и индекс перед запуском, сохраняет хеши набора, бинарника и файлов моделей в `config.json`, загрузку и прогрев — в `sessions.jsonl`. Каждая строка `rows.jsonl` содержит отдельный настоящий вызов `search`, время всего вызова, embed и rerank, пути, заголовки, строки, оценки и соответствие эталонам. Без rerank сохраняется весь список слияния; с rerank — вся переоценённая K. Лимиты выдачи повышены только внутри бенча для расчёта MRR@10 и порогов; задержка относится к такому вызову ядра, без IPC и отрисовки окна.

FTS, векторный список и слияние диагностируются теми же операциями ядра; порядок слияния обязан в точности совпасть с реальным `search`. Экспериментальная сортировка по косинусу применяется к **всему** тому же набору кандидатов, а не к уже обрезанной десятке прежнего бенча. Пороги пересчитываются по сохранённым оценкам без нового инференса. Реранк для каждого K измеряется отдельно; оценки большого K не подставляются вместо настоящего запуска меньшего K.

В строках диагностики `fts`/`vector`/`fused` поле `score` содержит косинус, как в обычной выдаче без rerank; BM25 и RRF задают порядок, их абсолютные значения не экспортируются. `bench_quality verify <папка-стенда> <папка-моделей>` дополнительно сверяет три переиспользованных вектора со свежим embed тех же чанков и печатает build info ONNX Runtime.

`node scripts/analyze-quality.mjs --self-test` проверяет расчёт метрик. Анализатор отказывается принимать неполный прогон или дубли строк. Правильный раздел определяется путём и наличием опоры в тексте чанка; попадание только в документ учитывается отдельно. Recall считает уникальные эталонные разделы; повторный чанк того же раздела не добавляет gain nDCG. Числа качества берутся из первого повтора; все три повтора используются для распределения задержек.
