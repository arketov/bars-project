# FP16 rerank и lifecycle — приёмка памяти

Основание: Т-17, НФТ-1…3; [проект снижения](../features/models/memory-reduction.md). [Сырые данные и хеши](memory-fp16-2026-10-18/Index.md), [исходный FP32 baseline](memory-results.md). Windows, i7-11700KF, RTX 3090, 32 ГиБ RAM. Измеряется Private Bytes; это не занятая физическая RAM и не сумма с GPU memory.

## Что принято настоящими моделями

Продуктовый `BuiltinReranker`: DirectML FP16/batch16, закреплённая revision `6f5ff65298512715a1e669753bc754d2bc8f367b`. Настоящие `Worker`, слоты и maintenance task; профиль внутри стенда, рабочие настройки/индексы/IPC не используются. Вход совпадает с исходным FP32 опытом: один запрос, 15 документов, K15, max_length512. Embed сохраняет FP32 и штатный padded-лимит 3000 символов. Это фиксированная lifecycle-нагрузка, не репрезентативная оценка релевантности или p95.

Два полных свежих парных процесса прошли без пересечения с Cargo/другими модельными стендами. Числа — диапазон этих двух процессов, не доверительный интервал:

| Метрика | FP32 baseline, один процесс | FP16 + настоящий worker, два процесса |
|---|---:|---:|
| Обе модели после работы, private | 6,87 ГиБ | 5,54–5,56 ГиБ |
| Lifetime peak commit процесса | 7,69 ГиБ | 5,73–5,84 ГиБ |
| Освобождено после rerank | 3,29 ГиБ | 1,79–1,82 ГиБ |
| Остаток после обеих моделей | 225 МиБ | 225–230 МиБ |
| После shutdown worker | — | 135–141 МиБ |
| Тёплый rerank, два последних вызова | 0,532–0,540 с | 0,161–0,175 с |
| Reload вместе с первым inference | 5,184 с | 3,259–3,344 с |

Удержание пары снизилось примерно на 19%; lifetime peak — примерно на 24–25%. Старый baseline — один core-процесс с разбиением как у worker; новые процессы используют настоящий worker, поэтому различия небольших базовых выделений и shutdown не приписываются precision. Скачивание исключено из чистых парных прогонов. Файловый кэш ОС глобально не очищался.

Ускоренные TTL стенда: rerank 3 с, embed 20 с, проверка 100 мс. Продуктовая политика остаётся 300/900 с с проверкой каждые 10 с; реальные 5/15 минут здесь не выжидались. Таймер извлекает модель из слота раньше завершения тяжёлого drop: состояние «выгружена» само по себе не доказывает возврат памяти. Таблица использует плато спустя 2 с после этого состояния. Отключение rerank замечено за 53–119 мс, память проверена отдельным плато. Все 15 оценок после reload совпали точно в обоих процессах.

## Скачивание, кэш и CPU fallback

Отдельный процесс завершил возобновление скачивания в собственном первоначально пустом кэше: оставшаяся часть файла 959 948 334 → 1 136 209 678 байт, затем tokenizer/config, проверка BLAKE3, verified marker и открытие DirectML FP16. Это успешный resumed download, не доказательство непрерывного скачивания с нуля за указанное время. Первый опыт закончился exit 1 без сообщения причины; второй остановлен аварийным guard при внешней сборке. Они сохранены и отклонены анализатором.

Одиночный FP16: удержание 2341 МиБ, lifetime peak 2363 МиБ, после drop 331 МиБ; после обеих загрузок и cleanup 125 МиБ. Все оценки после reload совпали. Этот сетевой процесс пересёкся с компиляцией; его время не используется для сравнения скорости.

В отдельном кэше намеренно повреждён закреплённый `config.json`, а CPU FP32-кэш сохранён исправным. Настоящий worker отклонил BLAKE3, сообщил `actual=cpu`, `precision=fp32` и причину fallback. GPU dedicated/shared в этом процессе — ноль. Все 15 CPU-оценок совпали с исходным CPU baseline и после reload. Удержание 1780 МиБ → 33 МиБ после таймера; после shutdown 37 МиБ. Отключение замечено за 116 мс. Повреждённый GPU-блоб автоматически не исправляется; loader возвращается на CPU, повторная загрузка снова проверяет файл.

Verified marker отдельно проверен unit-тестами: одних файлов недостаточно; атомарная запись после hash-проверки, изменение размера/mtime снимает ready; UI не хеширует гигабайт при каждом опросе. Продуктовый loader всегда проверяет содержимое перед открытием.

## Качество и границы результата

Этап 11 отдельно принял этот FP16 loader: 138 core-ответов и 22 IPC-ответа, без новых потерь выбранных метрик при порогах 0/0,1 и без CPU fallback; [данные приёмки](inference-2026-10-18/Index.md). Эти quality-only времена не смешиваются с чистыми замерами. Здесь дополнительно проверяется неизменность 15 оценок при выгрузке/reload, а не равенство FP16 и FP32 логитов.

Системный commit меняется из-за чужой нагрузки. Один парный процесс остановлен до rerank при старом резерве 6 ГиБ; другой — перед reload при резерве 5 ГиБ. Они не считаются полными успешными повторами. Начальный резерв пары ≥8 ГиБ, одиночного rerank ≥6; длинный embed ≥6, rerank/reload ≥5, аварийно RAM <512 МиБ / commit <1 ГиБ. Резерв 5 выбран после измеренного пика одиночного FP16 2,31 ГиБ и оставляет ещё 2,69 ГиБ; он не отменяет runtime guard.

FP16 rerank снижает активное удержание, TTL — простой, а повторная загрузка остаётся заметной. FP16 embed, отдельный индекс/fingerprint и совместимость CPU fallback ещё не приняты. Атрибуция весов/CPU arena/драйвера, чистый baseline окна, Mac/ноутбук и рекомендации для разных объёмов RAM остаются открытыми. Исходные 8,46 ГиБ объясняются масштабом двух модельных сессий, но точный allocator-состав старого процесса по этим опытам не восстановлен.
