# Перепроверка исследования локальных инструментов документации

Дата: 18-10-2026. Повод: автор усомнился в глубине интернет-исследования. Проверяется [обзор 14 идей](local-documentation-tools.md). Результат — исправленный обзор и проверяемые основания выбора. Исследование не включает внедрение, запуск моделей и новые измерения производительности.

**Граница аудита:** проверка фактов внутри вспомогательного обзора. Она не подтверждает, что направление исследования выбрано верно. После уточнения автора подготовлено основное [исследование графа знаний, GraphRAG и поиска отношений](graph-knowledge-retrieval.md). Приоритеты переходов/ссылок этого аудита не являются рекомендацией вместо смыслового графового слоя.

## Что было недостаточно в первом исследовании

Первый проход действительно использовал интернет, но слабо отделял обзор существующих подходов от отбора инструментов для bars. Часть ссылок подтверждала лишь существование библиотеки. Практически отсутствовало сравнение готовых продуктов; не были разобраны цена поддержки кэшей, варианты fuzzy matching и конкретный алгоритм поиска частичной копипасты. Это делало рекомендацию «лучший первый набор» сильнее её оснований.

Цели задержки 100/200 мс и 1 с были явно помечены предложениями, а не замерами. Однако baseline для их выбора не было. После проверки числа сняты. Список идей сохранился, но порядок опытов изменён: переход по метаданным → ссылки/целостность → связанные разделы; сбор контекста — после проверки отбора.

## Как проходила повторная проверка

- Для библиотек прочитаны официальные README и API, включая предупреждения; для TextRank, MMR и winnowing — оригинальные статьи и конкретные разделы.
- Для сценариев сопоставлены документация Obsidian, Smart Connections, Smart Context Builder, Repomix и Pagefind. Отзывы и рекламные множители скорости не использованы как измерения.
- Для каждого вывода разделены три уровня: подтверждённый механизм; предложение интеграции в bars; непроверенный эффект. Наличие готового продукта не является пользовательским испытанием bars.
- Повторно прочитаны собственные формулировки о стоимости, обновлении данных и ограничениях. Аудит реализации bars не выполнялся; опора на его текущее документированное устройство сохранена явно.

Ни один вывод о задержке нового инструмента не подтверждён прогоном на машине автора. Интернет-проверка этого заменить не может.

Ссылки S01–S19 раскрыты в реестре источников. «Подтверждено» относится только к названному факту, а не ко всей предлагаемой фиче.

## Три выбора алгоритмов, которые первый обзор недоработал

### Переход к заголовку и исправление опечатки — разные задачи

Для палитры нужен быстрый подбор по короткой подпоследовательности, удобные границы пути и корректная подсветка. S07 даёт соответствующий matcher и документирует Unicode-представление. Сначала сравнить с простым проходом по названиям; не заводить дополнительную таблицу только ради наличия trigram.

Для опечаток нужны расстояния/словарный поиск. S14 даёт порог и пакетный comparator; S13 — алгоритм с подготовленными удалениями. Для большого словаря цена памяти/обновления может поменять выбор. S15 — контрпример: быстрый обход автомата не гарантирует дешёвое создание автомата.

Ни один вариант не выбран зависимостью. Репозиторий S07 указывает применение в Helix, но его сравнительный бенч помечен как неполный; он не доказывает задержку на Windows автора. Для выбранного крейта отдельно нужны проверка версии, поддержки, лицензии, MSRV и сборки целевых платформ.

### Точный дубль, скопированный фрагмент и смысловой сосед

У этих трёх случаев разные критерии. Хеш нормализованного раздела найдёт целую совпадающую единицу. Winnowing (S09, §3) выбирает fingerprints скользящих k-грамм: для совпадения нормализованного потока длины не меньше `t = w + k − 1` есть гарантия обнаружения по правилам алгоритма. Перефразирование этой гарантией не покрывается. Совпавший fingerprint — кандидат, который следует подтвердить сравнением исходного текста.

Векторная близость полезна для тематического соседства; название «дубль» на её основании слишком сильное. Для разошедшихся копий нужны сначала подтверждённые соответствующие фрагменты, потом diff S10. Лимит частых fingerprints, игнорирование шаблонов и ограничения числа кандидатов должны быть отражены в измерении полноты, иначе заявленная гарантия теряется.

### Контекст по бюджету и разнообразие — разные критерии

MMR в S11, §2 балансирует релевантность с отличием от уже выбранного. Это не проверка достаточности материалов для задачи. Удалить повторяющуюся инструкцию полезно; удалить похожую инструкцию для другой платформы — потерять важный источник.

Для опыта сравнить одинаковый входной пул: обычный top-K; точные дубли + лимит на файл; MMR; ручной набор. Фиксировать пропущенные условия, платформы и исключения, а не только число разных файлов. Точный бюджет включает пути, заголовки, разделители и метаданные. Проверять уже сериализованный результат, а не сумму длин тел чанков. При бюджете токенов фиксировать токенизатор; «оценка» должна так и называться.

## Издержки обновления, которые нельзя скрывать словом «локально»

- **Соседи.** Добавление документа влияет на top-K старых разделов. Для первого опыта выгоднее вычисление по запросу, чем обещание постоянно готового полного графа.
- **Имена и aliases.** Новый термин может уже встречаться в сотнях старых документов. Изменение только исходящих ссылок нового файла не обновляет unlinked mentions. Возможны фоновый проход и явное состояние готовности.
- **Ссылки.** Изменённый якорь инвалидирует входящие ссылки; перенос каталога меняет разрешение относительных путей. Файловая проверка зависит и от I/O, а не только длины текста.
- **Граф.** Линейный обход O(V+E) может вернуть почти весь проект; нужны лимиты глубины/выдачи и объяснение пропусков. Центральность не равна важности требования.
- **Нормализация.** Unicode case folding, удаление frontmatter и CRLF меняют позиции. Для ссылки на строку нужен путь назад к исходнику. В S16 нечувствительность к регистру помечена именно ASCII; для русского языка её недостаточно.
- **Пакет контекста.** Инференс запроса, чтение источников, сериализация и IPC входят в общую задержку. Быстрый MMR не делает весь инструмент быстрым.

Это выводы из алгоритмов и жизненного цикла данных, не измеренные характеристики реализации bars.

## Какие выводы выдержали проверку

**Высокая уверенность в осуществимости механизма:** переход по метаданным; явные обратные ссылки; проверка путей/якорей при выбранном диалекте; точные дубли. Дополнительная нейросеть для них не обязательна. Цена интеграции ещё не измерена.

**Средняя уверенность в переносимости сценария:** семантические соседи, unlinked mentions, частичная копипаста, управляемый пакет контекста. Есть конкретные алгоритмы и продуктовые аналоги, но качество на русской технической документации bars не проверено.

**Низкая уверенность без специального корпуса:** автоматическое влияние правки, смысловые противоречия, «устаревшие знания», полнота трассировки, полезность кластеров/выжимок. Эти идеи нельзя продвигать как надёжную диагностику только по наличию embedding или графа.

Первая тройка опытов теперь выбирается по проверяемости: метаданные → ссылки/целостность → смысловые соседи. Она не объявляется доказанным продуктовым приоритетом автора. Если нужен именно эффект неожиданного открытия, наиболее подходящий кандидат — соседи; если нужна предсказуемая польза без модели — переходы и целостность.

## Ограничения проверки и достаточный следующий опыт

Несколько первоначально набранных путей документации lychee/Vale не открылись; для нужных утверждений использованы доступные официальные README, найденная страница Anchors и страница substitution. Непрочитанные страницы не считаются доказательствами. Бенчи и отзывы авторов продуктов не перепроверялись на их инфраструктуре.

Для проверки именно обещания скорости нужен отдельный ограниченный спайк с фиксированными корпусом и сборкой. Для проверки «магии» — заранее размеченные полезные связи/дубли и отрицательные примеры. Для сценария №1 минимум: один и тот же список разделов, исходные векторы, top-5, независимая ручная оценка, негативные пары «та же тема, другая платформа/старое решение». Измерять задержку и полезность раздельно. После этого можно обоснованно выбирать интеграцию; сейчас подтверждены механизмы и обнаружены ошибки обзора, но не достигнутые характеристики новых функций.
