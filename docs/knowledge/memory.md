# Память bars — замеры, причины пиков и результаты

[← База знаний](Index.md). Вопрос автора: сколько памяти занимают воркер и окно, чем объясняются пики, что даёт подкачка и как снизить потребление без потери качества и отзывчивости. Основание — Т-1, Т-3, Т-17, НФТ-1…3; численного бюджета RAM требования не задают. Что реализовано в продукте — [встроенные модели](../features/models/local-models.md) (precision, выгрузка по простою) и [архитектура воркера](../architecture/worker.md); что остаётся сделать — [проект снижения памяти](../features/models/memory-plan.md). Сырые данные и хеши — папки [memory-2026-10-18](memory-2026-10-18/Index.md), [memory-fp16-2026-10-18](memory-fp16-2026-10-18/Index.md), [memory-embed-2026-10-18](memory-embed-2026-10-18/Index.md).

Все числа получены на одной машине (Windows 11, i7-11700KF 8c/16t, RTX 3090 24 ГБ, 32 ГБ RAM, fastembed 7.1.1, ort 2.0.0-rc.13, release) и не являются минимальными требованиями. Измеряется Private Bytes процесса; это не занятая физическая RAM и не сумма с GPU-памятью.

## Метрики и как их читать

Windows: Private Bytes (частный commit) и его пик, Working Set (резидентные страницы, включая общие), системные Available/Committed/CommitLimit, Pages Input/sec, занятое в pagefile; GPU dedicated/shared — отдельно. Private Bytes не равен физической памяти, Working Set не равен потребности процесса; разность между ними не объём подкачки. Hard faults могут читать отображённые файлы, поэтому связь с задержкой проверяют трассой, а не одним счётчиком.

macOS: physical footprint процессов и дерева, Memory Pressure, compressed memory, swap used и его изменение во времени; footprint не приравнивать к Private Bytes. Mac в замерах не участвовал: это протокол, а не проверенная поддержка.

Сэмплированный максимум — нижняя оценка пика; пик за жизнь процесса даёт отдельный счётчик lifetime peak commit. Опрос CIM раз в секунду годится для плато и диагностики среды, но пропускает короткие пики; для фаз использовался нативный сэмплер на 100 мс (`GetProcessMemoryInfo`, `GetPerformanceInfo`, максимальный интервал между сэмплами 101–167 мс) с маркерами фаз. Воркер и Tauri — один процесс `bars`, webview — его дочерние процессы ([components.md](../architecture/components.md)): складывать «воркер» и «окно» как независимые процессы нельзя.

Полезные данные векторов малы: 946 векторов dim1024 f32 — 3,70 МиБ, 50 000 — 195 МиБ (расчёт N×dim×4, не измеренная куча). Гигабайты Private Bytes они не объясняют.

## Где расходуется память: FP32-опыты

Стенд `crates/bars-core/examples/bench_memory.rs`: новый процесс на конфигурацию, веса из существующего кэша только для чтения, рабочие профиль, индекс и IPC не используются. Вход — 15 фрагментов документации до 6000 символов, один запрос; rerank K15/batch4/max_length512, embed batch4/max_length8192. Перед стартом запас RAM ≥4 ГиБ и commit ≥8 ГиБ, внутри процесса аварийный выход при RAM <512 МиБ или commit <1 ГиБ. В режиме `auto` выбран DirectML; размещение узлов графа не профилировалось.

Private Bytes, МиБ (одна строка — один процесс):

| Нагрузка | После загрузки | После работы | После выгрузки |
|---|---:|---:|---:|
| Только rerank, CPU | 1497 | 1774 | 27 |
| Только rerank, DirectML | 2623 | 3701 | 200 |
| Только embed, CPU | 1498 | 3756 | 24 |
| Только embed, DirectML | 2616 | 5325 | 226 |
| Обе модели, CPU | 5190 | 5470 | 3772 после rerank; 33 после обеих |
| Обе модели, DirectML | 7832 | 8719 | 5390 после rerank; 249 после обеих |

Embed после трёх коротких запросов — 1503 МиБ на CPU и 2822 на DirectML; четыре длинных текста поднимают до 3756/5325 МиБ. Сохранение гигабайтов связано с жизнью сессии и её рабочих выделений, а не с выходными векторами (16 КиБ).

Режим core4 (четыре длинных текста одним вызовом) превышает padded-лимит воркера 3000 символов и задаёт верхний сценарий ядра. Режим `bounded` делит те же тексты на одиночные вызовы, как воркер: embed удерживает 3614 МиБ, обе модели после rerank — 7036 МиБ (6,87 ГиБ), после удаления rerank — 3670, после обеих — 225 МиБ; lifetime peak commit 7,69 ГиБ. Разбиение снижает удержание embed примерно на 1,67 ГиБ — это подтверждает пользу ограничения пачки. Успешных bounded-процессов один: последующие попытки остановил preflight по запасу commit, повторы с повышенным запасом не стартовали.

Исходные 8,46 ГиБ установленного процесса объясняются масштабом двух живых DirectML-сессий и удержанием рабочих выделений после тяжёлого входа (DirectML-опыт: 8719 МиБ, на 52 МиБ выше). Веса, prepacking, arena и выделения драйвера по отдельности не разделены — называть всю разницу «CPU arena» без allocator/EP-профиля нельзя; точный состав старого процесса не восстановлен.

Для первой индексации важнее throughput embed: screen — около 1,55 текста/с на CPU против 17,63 на DirectML и 26,19 на FP16 DirectML (это throughput модели на фиксированных текстах, а не время индексатора).

| Опыт | Освобождено | Время drop | Повторная загрузка + первый rerank |
|---|---:|---:|---:|
| Только rerank, CPU | 1747 МиБ | 0,372 с | 2,287 + 8,734 с |
| Только rerank, DirectML | 3501 МиБ | 0,183 с | 2,414 + 0,763 с |
| Вместе с embed, CPU | 1698 МиБ | 0,183 с | 2,130 + 8,121 с |
| Вместе с embed, DirectML | 3329 МиБ | 0,169 с | 3,367 + 1,191 с |

Максимум изменения каждой из 15 оценок после reload — 0, NaN/Inf не было. Цена первого запроса после выгрузки заметна, особенно на CPU: выгружать после каждого запроса не стоит. Эти спайки не проверяли таймер и гонки с активными запросами; это сделано в приёмке ниже.

## FP16 rerank и выгрузка по простою: приёмка настоящим worker

Продуктовый `BuiltinReranker` (DirectML FP16, batch16, закреплённая revision `6f5ff65298512715a1e669753bc754d2bc8f367b`), настоящие `Worker`, слоты и maintenance task; профиль внутри стенда. Вход как в FP32-опыте, embed остаётся FP32 с padded-лимитом 3000 символов. Два полных парных процесса без пересечения с Cargo; числа — диапазон двух процессов, не доверительный интервал.

| Метрика | FP32, один процесс | FP16 + worker, два процесса |
|---|---:|---:|
| Обе модели после работы, private | 6,87 ГиБ | 5,54–5,56 ГиБ |
| Lifetime peak commit | 7,69 ГиБ | 5,73–5,84 ГиБ |
| Освобождено после rerank | 3,29 ГиБ | 1,79–1,82 ГиБ |
| Остаток после обеих моделей | 225 МиБ | 225–230 МиБ |
| После shutdown worker | — | 135–141 МиБ |
| Тёплый rerank, два последних вызова | 0,532–0,540 с | 0,161–0,175 с |
| Reload вместе с первым inference | 5,184 с | 3,259–3,344 с |

Удержание пары снизилось примерно на 19 %, пик за жизнь — на 24–25 %. Старый baseline — core-процесс с разбиением как у worker, новые — настоящий worker, поэтому различия небольших базовых выделений и shutdown не приписываются precision. Ускоренные TTL стенда: rerank 3 с, embed 20 с, проверка 100 мс; реальные 5/15 минут не выжидались (продуктовая политика — [local-models.md](../features/models/local-models.md)). Таймер извлекает модель из слота раньше окончания тяжёлого drop, поэтому состояние «выгружена» само по себе не доказывает возврат памяти: таблица использует плато через 2 с. Отключение rerank замечено за 53–119 мс. Все 15 оценок после reload совпали точно.

Одиночный FP16: удержание 2341 МиБ, lifetime peak 2363 МиБ, после drop 331 МиБ. Отдельный процесс завершил возобновлённое скачивание в пустом кэше (959 948 334 → 1 136 209 678 байт, затем tokenizer, BLAKE3, отметка готовности, открытие DirectML FP16); это resumed download, а не доказательство скачивания с нуля за указанное время. Два неуспешных процесса (exit 1 без причины; остановка аварийным guard при внешней сборке) сохранены и отклонены анализатором.

CPU fallback: в отдельном кэше намеренно повреждён закреплённый `config.json`; worker отклонил BLAKE3, сообщил `actual=cpu`, `precision=fp32` и причину. Все 15 CPU-оценок совпали с baseline; удержание 1780 → 33 МиБ после таймера. Повреждённый GPU-блоб автоматически не исправляется — loader уходит на CPU и при следующей загрузке снова проверяет файл.

Качество: продуктовый FP16 loader принят в [замерах скорости](inference-speed.md) (138 core-ответов и 22 IPC-ответа без новых потерь). Здесь проверена неизменность 15 оценок при выгрузке и reload, а не равенство логитов FP16 и FP32. Резервы, использованные стендом: старт пары ≥8 ГиБ commit, одиночного rerank ≥6; перед длинным embed ≥6, перед rerank и reload ≥5 (после измеренного lifetime peak одиночного FP16 2,31 ГиБ), аварийно RAM <512 МиБ / commit <1 ГиБ; это защита измерения, не требование к пользователю.

## Embed: FP16 и INT8

Screen на фиксированных текстах: FP16 DirectML batch4 — пик 3,22 ГиБ против 3,94 ГиБ у FP32 и рост throughput 17,63 → 26,19 текста/с; увеличение batch4 → batch8 у FP32 подняло пик 3,94 → 9,25 ГиБ без выигрыша throughput (отклонено). INT8 CPU: 1,91 ГиБ и 4,86 текста/с против 4,57 ГиБ / 1,55 текста/с у CPU FP32; query 19 мс против 45 мс. Минимальные cosine около 0,99991 / 0,974 — мера изменения векторов, а не качества поиска.

Полный retrieval на 100 вопросах (последовательно: query-векторы, выгрузка embed, затем rerank; данные — [memory-embed-2026-10-18](memory-embed-2026-10-18/Index.md)): FP16 не дал новых потерь top1, Hit@3, MRR@10, nDCG@10 и документных метрик при порогах 0 и 0,1; INT8 потерял правильный раздел `od-001` из top-10 (MRR@10 0,125 → 0) и отклонён независимо от отказа INT8 rerank. Ядровой FP16-путь повторил 100 вопросов, 102 400 компонентов query-векторов совпали с прототипом, lifetime peak 3294 МиБ. Свежие полные FP16-индексы и 138 вопросов bars/overdrive/holdout проверены 20-10-2026; метод и границы — [аппаратное продолжение](#аппаратное-продолжение-20-10-2026). Чистая скорость и естественный корпус НФТ-2 на 5000 chunks не приняты.

Ограниченное хранение оценок точного поиска (heap top-30, удержание оценок текстовых кандидатов): на 50 000 / 500 000 чанков пик 3,38 → 0,68 МиБ и 33,05 → 0,68 МиБ, выбранные id совпали; это малая статья, не объяснение гигабайтов моделей.

Не стоит заводить вторую постоянную CPU embed-модель ради короткого query (экономия десятков миллисекунд способна вернуть гигабайты) и переводить всю индексацию на CPU ради меньшего Working Set (throughput хуже, пик на длинных текстах тоже большой).

## ISS-18: установленная сборка и allocator, 20-10-2026

Установщик из текущей рабочей копии собран штатным `scripts/build-installer.ps1` и установлен через `/S /UPDATE`. Полная индексация настоящего корпуса bars воспроизвела рост private commit процесса `bars` с 184,5 до 6014,7 МиБ; дочерние процессы вместе — максимум 204,2 МиБ. MCP-поиск с rerank вернул ответ при `indexing=true` без `model_loading` (после первоначальной действительной загрузки rerank). Нативные клики окна не выполнялись. Данные — [снимок по процессам](../chats/2026-10-20-indexing-memory/installed-before-memory.json), [статус во время индексации](../chats/2026-10-20-indexing-memory/installed-before-status.json).

Изолированный `probe_embed_arena` на тех же 15 текстах прежнего fixture, FP32 bge-m3/DirectML, одиночные вызовы без усечения: одна embed-сессия держит 4947–4955 МиБ после длинных текстов и 214 МиБ после drop. Поэтому гигабайты воспроизводятся без индексатора, SQLite, корпуса в памяти и rerank. Это причинное исключение этих компонентов для данного опыта, не точное разложение всех выделений установленного процесса.

Перенос initializers через `session.use_device_allocator_for_initializers=1` оставил 4922–4930 МиБ: существенной экономии нет. Отключение graph fusion (`ep.dml.disable_graph_fusion=1`) оставило 4941–4948 МиБ; оба полных опыта сохранили все 31 744 значения векторов побитово относительно baseline. Отключение CPU arena до конца не проверено: прогоны остановлены резервом commit, промежуточный пик остался около 4,8 ГиБ. Без prepacking первый полный проход 15 текстов держал 4936 МиБ, второй проход не допущен по запасу commit; экономии на первом проходе не видно. Незавершённые прогоны не считаются принятыми оптимизациями. Задержки на загруженной рабочей машине не принимаются как доказательство скорости.

Отдельный `probe_dml_arena` задаёт `ep.dml.disable_memory_arena=1` **до** регистрации DirectML и проверяет синтетические входы длиной 32/512/1536/2048. На входе 1536 private commit вырос до 10,9 ГиБ; монитор завершил только стенд при свободном commit <1 ГиБ. Настройка не принята. Контроль с arena на тех же синтетических входах не выполнен: нельзя приписать весь пик отключению arena или сравнивать его напрямую с опытом на 15 текстах. Простая передача этого ключа через `with_session_config` fastembed 7.1.1 неравноценна: библиотека регистрирует EP до применения config, а DML читает ключ при создании factory. Первичный контракт — [ключи DirectML 1.24.2](https://github.com/microsoft/onnxruntime/blob/v1.24.2/onnxruntime/core/providers/dml/dml_session_options_config_keys.h), [создание factory](https://github.com/microsoft/onnxruntime/blob/v1.24.2/onnxruntime/core/providers/dml/dml_provider_factory.cc).

Сырые данные, векторы и результаты отказов — [сессия ISS-18](../chats/2026-10-20-indexing-memory/handoff.md). Открыто: атрибуция выделений CPU/DirectML, полный парный опыт CPU arena, принятая мера ограничения памяти и её проверка в worker/окне. Начальный резерв 8 ГиБ commit; для поздних запусков одиночного `probe_embed_arena` откалиброван до 7 ГиБ (измеренный lifetime peak <5 ГиБ плюс >2 ГиБ запаса), после загрузки — 2 ГиБ; аварийный предел 1 ГиБ сохранён. Синтетический `probe_dml_arena` и парные FP16/FP32-стенды сохраняют прежние резервы. К концу сессии свободно около 3,7 ГиБ commit: новые модели не запускались. OQ-106 повторно закрепил запрет останавливать/переустанавливать рабочий bars ради стенда; системные настройки не менялись.

## Подкачка и ожидания от объёма RAM

Windows расширяет commit limit файлом подкачки; предел commit и физическая RAM — разные ограничения, и приближение к limit приводит к отказам выделения. Частый ввод страниц вместе с ростом задержки — сигнал давления. Размер pagefile выбирается по нагрузке и требованиям crash dump, а не формулой «RAM×1,5»; bars настройки ОС не меняет. Пассивный снимок показывает, что 32 ГиБ сами по себе не гарантируют запас при высокой общей нагрузке (к концу ряда свободный commit приблизился к 0,14 ГиБ).

Проверенного минимального бюджета для 8/16/32 ГиБ нет. Сценарии проверки: на 8 ГиБ — одна локальная модель и внешний провайдер; на 16 ГиБ — совместная загрузка и большой документ; на 32 ГиБ — те же серии при обычной пользовательской нагрузке. Для Apple дополнительно учитывать unified memory и memory pressure. Контролируемую память ограничивают только в отдельной тестовой среде: OOM на рабочем компьютере не вызывают, pagefile не меняют. Защитный порог harness (запас 4 ГиБ RAM и 8 ГиБ commit, остановка новой работы при исчерпании) — не системное требование bars.

## Изоляция стенда и воспроизведение

- `BARS_USER_HOME` разделяет home и канал IPC, но Tauri single-instance (`bars-app/src/main.rs`) не получает отдельного идентификатора стенда: второй Tauri-процесс может попасть в уже работающий экземпляр. Для baseline окна нужна отдельная сборка с уникальным identifier и своим home; запускать установленный bars ради опыта нельзя. `window.rs` создаёт скрытый webview и при `--background`, скрытие окна не равно «процесс без webview».
- Каждый процесс — новая сессия; файловый кэш ОС не очищался. Хеши бинарника, исходника и fixture сохраняются у каждой серии; `bench_memory` отказывается скачивать модели. Исходник первой версии стенда — `spikes/memory/provenance/bench_memory-v1.rs`; хеши четырёх существенных файлов fastembed и `DirectML.dll` 1.15.6 записаны в доказательствах.
- Запуск: `./scripts/run-memory-spike.ps1 -BenchPath <target>/release/examples/bench_memory.exe -ModelsPath <cache>/models -EvidencePath docs/knowledge/memory-2026-10-18 -Modes rerank -Devices cpu,auto -Repeat 3`, затем `node scripts/analyze-memory-spike.mjs docs/knowledge/memory-2026-10-18`. Runner ждёт три достаточных снимка запаса; при недостатке процесс не стартует. Режим `MemoryOnly` допускает фоновые сборки при прежнем запасе — это наблюдение памяти, не чистое сравнение скорости. Для FP16 embed `bench_memory` и `bench_worker_memory` принимают `--fp16-embed`.
- Для каждой фазы записывать базовое плато, максимум наблюдений, прирост к baseline, плато после освобождения, время загрузки/первого/тёплого запроса и число запросов; median/p95 при серии не меньше 100 тёплых запросов. Разложение по статьям: процесс без моделей → одна модель до/после загрузки и коротких/длинных входов → обе модели; точное разделение весов и arena — allocator/ORT profile или VMMap/ETW; размер весов на диске — отдельная колонка.

## Проверка allocator и индексатора 20-10-2026

Статическая проверка закреплённых `fastembed 7.1.1` и `ort 2.0.0-rc.13`; это доступность API, не замер экономии:

| Механизм | Доступность в текущем пути | Следствие |
|---|---|---|
| CPU arena | `ort::ep::CPU::with_arena_allocator(bool)` можно передать через список EP fastembed | Возможен отдельный опыт при неизменных весах/входе; CPU arena не равна памяти DirectML |
| Session config | `TextInitOptions` и `RerankInitOptions` имеют `with_session_config`; `common::init_session_builder` передаёт записи ORT | Это настройки сессии, а не настройки конкретного запуска |
| Arena shrinkage | `ort::RunOptions::set` + `Session::run_with_options` существуют; fastembed хранит `session` как `pub(crate)` и вызывает `session.run(...)` | В текущем публичном API fastembed передать shrinkage при запуске нельзя; одноимённая session config не заменяет RunOptions |
| ORT profiling | ORT предоставляет `with_profiling` и `end_profiling`; сессия fastembed закрыта | Для профиля нужен отдельный ORT-спайк либо изменение обёртки; профилирование узлов само по себе не даёт полного учёта Windows/драйвера |
| Shared allocator | ORT описывает общий allocator нескольких сессий; fastembed не предоставляет такой конструктор сессий | Не внедрять по одной рекомендации; сначала опыт с атрибуцией CPU и GPU |

В [заголовке ONNX Runtime](https://github.com/microsoft/onnxruntime/blob/v1.24.2/include/onnxruntime/core/session/onnxruntime_run_options_config_keys.h) ключ `memory.enable_memory_arena_shrinkage` относится к RunOptions; заявлены типы устройств `cpu` и `gpu`, поддержка allocator DirectML этим не установлена. [Документация DirectML](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html#configuration-options) требует отключённый memory pattern и последовательное выполнение; fastembed уже выставляет оба параметра. [Общий allocator и mimalloc](https://onnxruntime.ai/docs/performance/tune-performance/memory.html) требуют собственного опыта, а mimalloc для ORT на Windows — соответствующей сборки runtime; замена allocator Rust сама по себе не доказывает изменение ORT.

Индексатор (`indexing/indexer.rs`, `run_update`, `embed_and_store`) читает и режет один документ, собирает недостающие векторы этого документа и записывает его транзакцией. Список файлов/метаданные документов остаются на весь проход, но тексты всего корпуса здесь не собираются. Полезные векторы одного документа занимают `число новых уникальных chunks × dim × 4` плюс контейнеры; при dim1024 это 4 КиБ на chunk. Огромный документ может дать большой пик; отсутствие вклада на обычном корпусе нельзя переносить на произвольный файл. Контроль `bench_index_memory` использует настоящий индексатор и SQLite с постоянными векторами без ONNX: измеряет базовые буферы, не качество модели, tokenization или память worker.

Для EP-specific ключей важен порядок: [контракт SessionOptions](https://github.com/microsoft/onnxruntime/blob/v1.24.2/include/onnxruntime/core/session/onnxruntime_session_options_config_keys.h) требует задать их до регистрации EP. Проверенный `fastembed::common::init_session_builder` регистрирует EP до цикла session config. Поэтому наличие `with_session_config` ещё не доказывает действие конкретного DirectML-ключа: отдельный ORT-спайк должен выставлять параметр до EP и проверять память/выходы. Отключение memory arena, prepacking и выбор allocator initializers — разные эксперименты, не одна универсальная настройка.

## Аппаратное продолжение 20-10-2026

Сырые данные, параметры и контроль целостности — [memory-acceptance-2026-10-20](memory-acceptance-2026-10-20/Index.md). Машина занята другой работой; автор не может её остановить. Это замеры памяти, время не принимается как скорость продукта. Файлы подкачки и чужие процессы не менялись.

Третий повтор прежней пары на том же замороженном `bench_worker_memory` (FP32 embed + FP16 rerank): удержание 5680,6 МиБ, сэмплированный пик 5973,0 МиБ, lifetime peak commit 5976,9 МиБ; после обеих моделей 229,8 МиБ, после shutdown 142,8 МиБ. Все 15 оценок при reload совпали точно; максимальный интервал сэмплера 101,8 мс. Новое наблюдение находится в прежнем диапазоне удержания 5,54–5,56 ГиБ; пик 5,84 ГиБ близок к прежней верхней границе. Это контроль прежней пары, не результат двух FP16-моделей.

Baseline отдельной release-сборки Tauri с identifier `io.github.arketov.bars.memory20261020`, пустыми раздельными `BARS_USER_HOME`, без проектов и моделей; UI собран 20-10-2026. После 5 с прогрева — по 6 последовательных снимков. Суммируется Private Bytes дерева, включая WebView; сумма Working Set не используется как расход физической RAM.

| Пустое окно | Bars, МиБ private | Всё дерево, МиБ private |
|---|---:|---:|
| Обычный запуск без `--background` | 8,04–8,11 | 191,15–193,88 |
| `--background`, webview существует | 8,52 | 181,32–183,62 |

Один процесс на режим: разность около 10 МиБ не доказывает устойчивую экономию скрытия. Запуск через `Start-Process -WindowStyle Hidden`; физическая видимость окна отдельно не проверялась. Оба процесса штатно завершены через собственный identifier; установленный bars имел тот же PID/время старта до и после. Наличие, SHA256 и mtime четырёх известных конфигурационных файлов Claude/Codex совпали. Чистый baseline показывает масштаб окна порядка сотен МиБ на этом стенде; многогигабайтные модельные пики он не объясняет. | Корпус | Документы / chunks | Lifetime peak commit, МиБ | После drop индекса, МиБ | Максимум новых векторов одного документа |
|---|---:|---:|---:|---:|

Оба прохода закончились без проблем, число vectors равно числу chunks. Пик процесса включает базовые выделения; максимум — счётчик lifetime, а не только редкие сэмплы короткого прохода. Это отрицательный контроль: на этих корпусах тексты, контейнеры индексатора и SQLite без модели не объясняют гигабайты. ### Свежие FP16-индексы и качество

Полные новые SQLite-индексы созданы ядровым загрузчиком `bge-m3:fp16` на DirectML с закреплённым revision `4de13258303883538bd53b696b452bf8099f0858`, без fallback. Старый индекс и его fingerprint не подменялись. После полного прохода проверены unchanged и incremental. Вход — замороженные корпуса 18-10-2026: bars 103 документа / 482 chunks, overdrive 176 / 946. Исследовательский `index-serial` передаёт полный текст каждого chunk отдельным вызовом; это не обычная пачка worker и не доказательство скорости индексации.

| Проход | Вопросы | Lifetime peak commit, МиБ | Новые потери качества |
|---|---:|---:|---:|
| Полный индекс bars | — | 3351,27 | — |
| Полный индекс overdrive | — | 3361,79 | — |
| Retrieval bars | 24 | 3366,91 | 0 |
| Retrieval overdrive + holdout | 100 + 14 | 3358,73 | 0 |

Сравнение с сохранённым продуктовым FP32 embed + FP16 rerank: каждый вопрос, пороги 0 и 0,1; top1, Hit@3, MRR@10, nDCG@10, документные top1/Hit@3/MRR@10 и ложные непустые ответы для отрицательных вопросов; допуск округления 1e-12. Это не сравнение со старым candidate screen. Анализатор проверяет полный состав вопросов, runtime, нативное завершение и exit code; результат — [precision-summary.json](memory-acceptance-2026-10-20/precision-summary.json). Quality-процесс сначала вычисляет query-векторы, выгружает embed, затем открывает rerank: числа таблицы не являются совместным пиком. Время при фоновой работе не принимается. Один естественный проход меньше 5000 chunks не закрывает НФТ-2.

### Совместный пик двух FP16-моделей

Один новый процесс настоящего worker, fixture из 15 текстов, bounded embed и rerank K15; оба runtime сообщили DirectML/FP16, CPU fallback не было. Начальный reserve 8 ГиБ commit сохранён. После загрузки/работы — плато 2 с; ускоренные TTL стенда 3/20 с, не продуктовые 5/15 минут.

| Фаза | FP32 embed + FP16 rerank, третий повтор, МиБ | FP16 embed + FP16 rerank, МиБ |
|---|---:|---:|
| После embed | 3628,0 | 2175,4 |
| Обе модели после rerank | 5680,6 | 4220,1 |
| Пик за жизнь процесса | 5976,9 | 4571,4 |
| После выгрузки обеих | 229,8 | 373,1 |
| После shutdown worker | 142,8 | 167,6 |

В этом сравнении удержание меньше на 25,7 %, lifetime peak — на 23,5 %. Контроль — прежний замороженный worker, новый процесс собран из текущей рабочей копии; различия базовых выделений не приписываются precision. Сэмплированный пик новой пары 4565,8 МиБ, максимальный интервал 103,7 мс; exit 0, все 15 оценок после reload совпали точно. [summary.json](memory-acceptance-2026-10-20/summary.json) содержит обе серии, хеши и фазы; время обеих серий непригодно для сравнения скорости.

Второй FP16-процесс не стартовал: за 120 с не появилось 8 ГиБ свободного commit. Это отказ предусловия, а не ошибка модели; повторяемость новой пары не установлена. Частичный итог сохранён, `temporary-pipeline.json` честно оставлен `ok=false`. На момент завершения собственный UUID-каталог TEMP, единственный скачанный FP16-артефакт и рабочие профили удалены; общие модели использовались через ссылки без копирования. Сохранено около 10 МиБ доказательств. Удалённый автором `spikes/` не восстанавливался; общий Cargo target не очищался.

### Вывод для следующей реализации

Для исследованных корпусов FP16 embed сохраняет выбранные метрики и снижает совместный пик на этом стенде. Заводской выбор модели этим исследованием не меняется. Буферы индексатора не объясняют гигабайты; проверенные allocator-переключатели не дали принятой меры ([ISS-18 и allocator](#iss-18-установленная-сборка-и-allocator-20-10-2026)). Следующий продуктовый шаг требует выбранной меры и проверки задержек/качества в полном worker под совместной нагрузкой. Одна новая пара не обосновывает рекомендации по минимальной RAM или изменение глобальных очередей.

## Что не доказано

- Точная атрибуция весов, CPU arena и драйвера по отдельности; принятая оптимизация allocator и завершённый парный CPU-arena опыт отсутствуют.
- Baseline окна с проектом и открытыми документами; Mac, ноутбук и слабые GPU.
- Чистая скорость FP16, естественный корпус на 5000 chunks, рекомендации для 8/16/32 ГиБ и совместная нагрузка индексации с 1/2/4 поисками.
- Повторяемость новой FP16-пары: есть один завершённый процесс, второй не допущен по commit. Малые серии не дают статистики.
