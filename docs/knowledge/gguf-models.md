# Этап 22 — проверка llama.cpp и Qwen3 GGUF

Результат 18-10-2026: встроенный loader реализован; обе Qwen Q4_K_M реально работают на CPU и Vulkan/RTX 3090. Полный retrieval проверен на 100 вопросах, по три повтора каждой модели и bge-m3 (900 вызовов). [Проект](../features/models/gguf-plan.md), [ADR-0002](../adr/0002-qwen-gguf.md), [числа и конфигурации](gguf-2026-10-18.json), [строки измерений](gguf-2026-10-18.rows.json.gz). Установленный bars не останавливался и не обновлялся. Настоящий Tauri-клик скачивания, полный NSIS и macOS не проверялись.

## Качество GGUF против bge-m3

Корпус этапа 9: 176 документов / 946 чанков; отдельный SQLite каждой модели, штатные `update_index` и `search`, C30, rerank выключен, порог 0. Три повтора 100 вопросов; известные tune/test не объявляются новой слепой выборкой. Метрики по разделам через общий `quality::pack_hits`; одинаковый BLAKE3 cases и бинарника записан у всех вариантов. Ни частичный прогон, ни пропущенная строка анализатором не принимаются.

| Модель | Лидер test / 32 | Hit@3 / 32 | MRR@10 | Search median / p95, с |

| bge-m3 FP32, Auto | 18 | 26 | 0,6988 | 0,137 / 0,189 |
| Qwen 0.6B Q4_K_M, Vulkan | 18 | 26 | 0,6891 | 0,065 / 0,082 |
| Qwen 4B Q4_K_M, Vulkan | 17 | 25 | 0,6711 | 0,117 / 0,137 |

Устойчивого преимущества качества Qwen не показано: bge-m3 остаётся умолчанием. Одинаковое число лидеров не означает совпадение ответов на каждом вопросе; индивидуальные ранги сохранены. Двадцать отрицательных вопросов при пороге 0 дают непустую выдачу у всех моделей: этот режим не проверяет способность отказать. Дополнительного rerank-бенча или настройки порогов здесь нет.

Задержки предварительные: установленный bars работал, параллельно шли сборки/тесты. Это время ядра до IPC/отрисовки; универсальное ускорение и SLA не заявляются. Полная индексация 4B — 114,14 с, bge — 57,89 с. 0.6B возобновлена после защитной остановки: остаток 54,13 с, 866 новых / 80 переиспользованных векторов; не выдаётся за время индексации с нуля.

## Устройства, память и сосуществование с ORT

Логи подтвердили offload 29/29 слоёв у 0.6B и 37/37 у 4B. CPU compute buffer в полных GGUF-прогонах не появился; CPU fallback не обнаружен. Обе модели дали конечные векторы правильной размерности (1024/2560) на CPU и Vulkan. Пустые, повторные и длинные входы проверены. Векторы 0.6B CPU/Vulkan на коротких входах имеют косинус около 0,998 (пустой около 0,989); на длинной пробе совпали. Побитовое равенство разных устройств не заявляется, полный CPU-корпус не прогонялся.

Sampled peak Private Bytes отдельного процесса: 0.6B 3,08 ГиБ, 4B 5,70 ГиБ, bge 7,02 ГиБ. Sampled Working Set: 1,95 / 4,07 / 2,09 ГиБ соответственно. Это процесс с индексацией и поиском, не размер весов, не физическая VRAM и не измерение всего воркера. Пики VRAM/общего приложения не замерялись. Перенос вычислений на GPU не означает нулевого системного commit.

В одном процессе Qwen 0.6B/Vulkan и настоящий bge-reranker-v2-m3/DirectML FP16 работали одновременно: оценки 0,87810534 и 0,0000167014, fallback отсутствовал; повторный вектор Qwen после ORT совпал точно (max delta 0). Проба использовала также новый упаковываемый Vulkan loader рядом с exe. Дополнительно Auto fallback проверен при скрытом GPU только в дочернем процессе: получен CPU-вектор, runtime сообщает CPU и причину недоступности GPU; ожидаемый GPU-assert стенда завершился кодом 1. Установленный bars это не затронул. CPU-проба 4B: два правильных вектора 2560, повторный запрос около 0,20 с; это не p95 CPU-нагрузки.

## Сборка и найденные ограничения GGUF

MSBuild на чистом каталоге ломал порядок шагов вложенного `vulkan-shaders-gen`; длинные пути усугубляли ошибку. Воспроизводимый путь: короткий target, Ninja, `CMAKE_BUILD_PARALLEL_LEVEL=1`, Developer Shell последнего MSVC 17.14+. Старый 17.9 вызывал неразрешённые `__std_*` из ORT; на машине найден и использован `C:/BuildTools` 17.14. Установщик подготавливает такое окружение автоматически.

Первый спайк резервировал 5027,97 MiB CPU compute при microbatch8192; microbatch512 — 314,25 MiB. Продукт создаёт контекст лениво (256…8192), сохраняет EOS при усечении и освобождает прежний контекст до роста. Ранние искусственные резервные пороги останавливали опыт; после требования автора прогоны выполнены с обычным выделением памяти ОС. В `run.ps1` прежний резерв включается только явным `-EnforceReserve`; установленный bars не закрывался (OQ-90).

Vulkan SDK 1.4.363.0 загружен с LunarG, Authenticode действителен. Отдельный VulkanRT Components ZIP закреплён SHA-256; подпись x64 loader проверена, DLL и лицензия включены в конфигурацию упаковки. Проверена подготовка ресурсов и запуск с этой DLL; полный NSIS и запуск на машине вообще без Vulkan-драйвера ещё требуют ручной проверки.

## Проверки кода GGUF

Модели core 42/42, worker 170/170, UI 95/95; UI check/build и clippy core/worker lib прошли. Проверяются повреждённый файл, отсутствие проверенной метки, инвалидирование метаданных, прежний candle fingerprint, сохранение EOS и недопустимые векторы. После временной ошибки CPU fallback повторный запрос снова пробует загрузку. Полный core-прогон отдельно фиксируется в журнале; параллельный GraphRAG не относится к GGUF-приёмке.
