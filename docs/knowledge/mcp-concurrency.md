# Одновременные вызовы MCP — клиенты, очередь в bars-mcp и «Transport closed»

Статус 01-11-2026: сохранены замер старой установленной сборки от 24-10-2026 и частичный контроль реализации 5.2.5 на IPC-стенде. Финальный срез после исправления ожиданий отмены, общий гейт, настоящие модели и установленная версия не проверены: автор запретил новые тесты и сборку. Текущий контракт — [параллельность и отмена MCP](../features/agent-tools/mcp-tools.md); исторические числа не описывают новую установленную сборку.

Исследование к ISS-69: шлют ли Claude Code и Codex вызовы bars параллельно, сколько короткий вызов ждёт за долгим в `bars-mcp` и связана ли эта очередь с прежним «Transport closed».

## Вывод по сборке MCP из замера 24-10-2026

- **В сборке замера клиенты не слали вызовы bars параллельно.** Проверенные версии Claude Code и Codex выполняли MCP-инструменты по очереди без `readOnlyHint`; исследованная сборка `bars-mcp` аннотаций не объявляла. Поэтому очередь в прокси не добавляла задержки: клиент ждал конца одного вызова, прежде чем послать следующий.
- **Очередь в старом прокси задерживала чтение.** При одновременных вызовах `bars_read` за поиском с rerank ждал 5,2–13,1 с вместо 46–87 мс. Через второе соединение с воркером тот же `bars_read` отвечал за 62–133 мс.
- **Раздельные каналы ускоряли короткие вызовы.** Два поиска на двух соединениях в замере всё равно шли почти друг за другом: модель эмбеддингов и rerank стояли за одним мьютексом в воркере ([worker.md](../architecture/worker.md), «Модели в памяти воркера»). Это не замер новой реализации пула.
- **С «Transport closed» очередь не связана.** У обоих клиентов это текст закрытого канала (процесс сервера завершился или канал оборвался). Долгое ожидание даёт другую ошибку: в Codex — «timed out awaiting tools/call after …». Причина прежнего обрыва по-прежнему не установлена.
- **Аннотации и пул нужно вводить вместе.** В исходном исследовании пул был условным: без параллельной отправки клиентом он не убирал задержку. Автор выбрал совместную реализацию в OQ-182, 24-10-2026; она добавлена в исходники 5.2.5 (`c6cda73`).

## Поведение версий клиентов MCP, проверенных 24-10-2026

**Claude Code 2.1.309** (установленный `claude.exe`). В коде MCP-инструмента: `isConcurrencySafe() { return mayOverlap || (annotations?.readOnlyHint ?? false) }`. `mayOverlap` включается для инструментов из внутреннего списка хоста, у которых есть свои слоты исполнения; признаков, что `bars` в этом списке, не найдено. Инструмент без `readOnlyHint` и без такого слота идёт по одному.

**Codex.** Сервер в `[mcp_servers.<имя>]` получает параллельность ключом `supports_parallel_tool_calls` (строка есть в установленных 0.130.0-alpha.5 и 0.162.0-alpha.17.2). По умолчанию вызовы идут по очереди. По сторонним описаниям ключ появился в 0.121.0, а с 0.134.0 параллельно идут и инструменты с `readOnlyHint` без ключа; официальный журнал изменений называет параллельный запуск независимых read-only инструментов в 0.163.0. У `bars` в `~/.codex/config.toml` ключа нет. Таймаут вызова по умолчанию — 60 с ([контракт MCP Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)).

**Журналы Claude Code за 17–24 октября.** 495 файлов, 519 сообщений модели с вызовами bars; в 173 из них два вызова bars и больше (до 14). В 32 группах «поиск + короткий вызов» с полными отметками времени результаты приходят в порядке вызовов. Если поиск стоит первым, короткий вызов завершается после него (`rag_search` 9,8 с → `read` 11,6 с). Если первым стоит чтение, оно отвечает за 0,2–3,7 с. Так выглядит последовательное исполнение; очередь в прокси дала бы тот же порядок, поэтому выдача журналов сама по себе не различает эти случаи — различает код клиента выше.

**Сервер в сборке замера 24-10-2026.** `rmcp` 3.5.1 запускал каждый входящий `tools/call` отдельной задачей (`spawn_service_task` в `service.rs`), так что запросы доходили до `BarsMcp` одновременно. Дальше их выстраивал `tokio::sync::Mutex` вокруг единственного соединения с воркером (`call_once` в `crates/bars-mcp/src/lib.rs`). Замок держался всё время вызова, до прежнего `CALL_TIMEOUT` = 120 с. Эту схему заменил пул в 5.2.5.

## Замер очереди старой сборки bars-mcp 24-10-2026

**Метод.** Скрипт на Node запускал установленный `%LOCALAPPDATA%\bars\bars-mcp.exe` по stdio, проходил `initialize` и слал `tools/call` к работающему воркеру. Поиск — `bars_rag_search` с `limit` 10 и `candidates` 60, rerank включён по настройкам; чтение — `bars_read` файла `architecture/protocol.md`. В связке второй запрос уходил через 50 мс после первого. «Один прокси» — оба запроса в один процесс `bars-mcp` (одно соединение с воркером), «два прокси» — по процессу на запрос (два соединения, как у пула). Три повтора, корпус bars-project, ноутбук автора, индексация шла в фоне. Время — от отправки запроса до ответа, мс.

| Сценарий | Повтор 1 | Повтор 2 | Повтор 3 |
|---|---|---|---|
| `read` отдельно | 46 | 87 | 49 |
| поиск отдельно | 6 248 | 5 778 | 8 106 |
| один прокси: поиск, затем `read` | 13 096 / **13 039** | 5 600 / **5 596** | 5 218 / **5 257** |
| два прокси: поиск, затем `read` | 6 319 / **82** | 11 563 / **62** | 8 240 / **133** |
| один прокси: два поиска | 6 000 / 17 977 | 11 594 / 17 898 | 10 454 / 20 079 |
| два прокси: два поиска | 16 248 / 11 576 | 13 686 / 18 771 | 6 332 / 11 404 |

**Что видно.** На одном соединении `read` ждёт поиск целиком: его время равно времени поиска. На двух соединениях `read` от поиска не зависит. Два поиска на двух соединениях заканчиваются за 11–19 с против 18–20 с на одном: выигрыш мал, потому что воркер всё равно считает их моделью по одному.

**Длительности в истории MCP** (`~/.bars/mcp-statistics.sqlite3`, 761 попытка за 19–24 октября): `bars_rag_search` — медиана 3,7 с, p90 7,6 с, p99 22,2 с, максимум 27,3 с, 14 вызовов дольше 10 с; `bars_get_similar` — до 22,6 с; `bars_read` и `bars_outline` — медиана 5 мс, максимум 152 мс. Ни один вызов не шёл дольше 60 с.

## Выводы замера 24-10-2026 о «Transport closed»

- **Claude Code.** «Transport closed» — сообщение о закрытом соединении с сервером (`Transport closed: …` с причиной закрытия). Долгий вызов в Claude Code обрывает отдельный таймаут инструмента (`MCP_TOOL_TIMEOUT` или поле сервера), это не закрытие транспорта.
- **Codex.** Таймаут вызова — «timed out awaiting tools/call after …»; «transport closed» — закрытие JSON-RPC канала.
- **Очередь не закрывает канал.** Ожидание в мьютексе не завершает процесс `bars-mcp` и не рвёт stdio. Даже при параллельной отправке очередь привела бы к таймауту, а не к «Transport closed».
- **Таймаут Codex при параллельной отправке.** При клиентском пределе 60 с короткий вызов за тремя поисками по 20 с превысил бы срок. В исследованной сборке клиент слал вызовы bars по одному, а самый долгий вызов в просмотренной истории составил 27,3 с. Настоящие клиентские сессии новой сборки не проверялись.

## Дефекты отмены и срока в старой сборке 24-10-2026

- **Отмена не освобождала очередь.** Старый прокси не смотрел на признак отмены от `rmcp`: отменённый клиентом вызов продолжал держать соединение и замок до ответа воркера или до 120 с. В исходниках 5.2.5 отмена обрабатывается в `ServerHandler::call_tool`.
- **Таймаут старого прокси был длиннее заявленного клиентского.** Прежний `CALL_TIMEOUT` = 120 с превышал заявленное умолчание Codex 60 с. В 5.2.5 срок охватывает весь вызов; это устраняет отдельные бюджеты очереди, подключения и повторов, но не устанавливает неизвестный таймаут произвольного клиента.

## Частичный контроль пула MCP 01-11-2026

Метод: восемь регрессий `crates/bars-mcp/tests/support/pool.rs`, сырой MCP JSON-RPC поверх duplex и настоящий локальный IPC до управляемого `Handler`. Для длительного поиска обработчик ждёт разрешения семафора; модели, реальный корпус и установленный bars не участвуют. Один MCP-сеанс отправляет долгий и короткий запросы независимо, проверяются ID ответов и IPC-сессий.

| Сценарий | Сохранённый результат до запрета автора |
|---|---|
| Чтение при заблокированном поиске, повторное использование исправного канала | Прошёл; чтение завершилось за 1,5963 мс до освобождения поиска |
| Ошибка ответа чтения и неоднозначный результат записи | Прошёл; чтение повторено один раз на другом канале, запись не повторена |
| Подключение и запуск внутри общего срока | Прошёл |
| Время очереди входит в общий срок | Прошёл |
| Аннотации чтения и исключение операций записи | Прошёл |
| Четыре канала, отмена активного и ожидающего вызова | Прежний тест упал, ожидая подавленный ответ отмены; ожидание исправлено, повтор не выполнен |
| Отмена во время ожидания модели | Прежний тест упал по той же причине; ожидание исправлено, повтор не выполнен |
| Общий срок, поздний ответ и ожидание модели | Итог отсутствует в прерванном прогоне |

Число 1,5963 мс — один контрольный отсчёт, а не медиана, p99 или доказательство скорости настоящего поиска. Сравнивать его напрямую с замером моделей 24-10-2026 нельзя. После исправления двух ожиданий выполнен только повторный статический Sol-обзор без замечаний; восемь зелёных тестов и финальная полная проверка не заявляются.

## Подавление ответа отмены в rmcp 3.5.1

Источник: локальные исходники зависимости `rmcp-3.5.1/src/service.rs`. `RequestContext::ct` получает отмену от `notifications/cancelled`; цикл удаляет ID из `local_ct_pool`. В ветке `Event::ToSink` ответ без оставшегося ID отбрасывается (`dropping response for cancelled request`). Поэтому отсутствие ответа отменённого запроса само по себе не доказывает, что обработчик продолжает ждать.

Ошибка двух регрессий 01-11-2026 состояла в ожидании такого ответа. Исправленный способ проверки: отправить отмену и `ping` по тому же MCP-каналу как барьер обработки уведомления; затем проверять события управляемого IPC-обработчика и ответ соседнего вызова. Для активного вызова проверяется новое соединение у соседа, для ожидающего — отсутствие его запуска, для ожидания модели — отсутствие повторной попытки. Исправления разобраны статически, повторный запуск не выполнялся. Границы остановки уже начатой работы воркера принадлежат [контракту MCP](../features/agent-tools/mcp-tools.md).

## Границы исследования одновременных вызовов

- Код клиентов прочитан в установленных сборках; поведение более новых версий может отличаться.
- Сведения о версиях Codex 0.121.0 и 0.134.0 — из сторонних статей, не из официальных документов.
- Замер на одном ноутбуке, при идущей в фоне индексации; числа поиска зависят от модели, устройства и длины запроса.
- Прежний «Transport closed» не воспроизведён; вывод относится только к очереди в прокси.
