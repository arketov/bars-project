# Исследование docking и отдельных окон bars

Статус на 20-10-2026: сравнение пакетов, прямой адаптер Svelte 5 и программная проба в Tauri/WebView2 выполнены. Рекомендация — [ADR-0003](../adr/0003-window-docking.md), статус proposed: это инженерное предложение для следующего макета. Продуктовый docking и редактор не внедрены. Основание — Т-40, Т-43, Т-45 и [проект окна](../features/window/requirements.md).

## Метод сравнения библиотек docking

Версии закреплены; метаданные получены из npm 20-10-2026. Размер — полный публичный API, удержанный через namespace export, Vite 8.3.4/minify и gzip Node 24.16.0; это одинаковый синтетический замер JS, а не прибавка к готовому bars. Исходный CSS Dockview измерен отдельно. Скрипт `ui/scripts/docking-benchmark.mjs` устанавливает альтернативы во временную папку и удаляет её в `finally`; в зависимостях репозитория остаётся только кандидат для стенда. [Сырые числа и ошибка сборки](../chats/2026-10-20-window-docking/bundles.json).

| Кандидат | Лицензия / npm modified | JS min / gzip, байт | Применимость |
|---|---|---|---|
| dockview-core 8.6.1 + dockview 8.6.1 для CSS | MIT / 19-10-2026 | 455902 / 97413; CSS 159552 / 12761 отдельно | Прямой DOM-adapter Svelte, вкладки, split, `toJSON/fromJSON`; рабочая проба в WebView2 |
| Golden Layout 2.6.0 | MIT / 21-02-2023 | 153939 / 32542; CSS в это число не входит | Заметно меньше JS; DOM/virtual binding подходит Svelte, `saveLayout/loadLayout`; полный эквивалент клавиатурного docking не подтверждён |
| dock-spawn-ts 4.4.0 | MIT / 19-10-2026 | Размер JS не получен | Штатный namespace-entry не собирается в Vite: CSS imports с `with { type: 'css' }` не дают default export. Нужен адаптер сборки или другой entry; это не доказательство невозможности интеграции |

У npm-пакетов core/Golden Layout/dock-spawn-ts нет объявленных runtime dependencies. У пакета `dockview` есть зависимость от core. `dist.unpackedSize` включает исходные декларации/другие сборки и не используется как размер загрузки. Современность npm modified — сигнал сопровождения, а не показатель надёжности.

Первичные источники: [Dockview API и возможности](https://dockview.dev/docs/overview/introduction/), [клавиатура и доступность](https://dockview.dev/docs/advanced/accessibility/), [сохранение](https://dockview.dev/docs/core/state/save/), [репозиторий и лицензия Dockview](https://github.com/dockview/dockview), [binding Golden Layout](https://golden-layout.github.io/golden-layout/binding-components/), [Golden Layout v2](https://golden-layout.github.io/golden-layout/version-2/), [dock-spawn-ts](https://github.com/node-projects/dock-spawn-ts). Установленные версии и их типы проверены отдельно от текущих сайтов.

## Проба нынешних компонентов Svelte

`ui/docking.html` и `ui/src/spikes/docking/` — отдельный вход, не подключённый к App.svelte. В панелях монтируются настоящие Sidebar, SearchPane, Viewer и GraphPage; дополнительно — два черновика стенда. Штатная композиция даёт пять групп и шесть вкладок: навигация/граф слева, поиск в центре, документ и дополнительная группа справа. Это проверка интеграции компонентов, не согласованный дизайн.

Адаптер вызывает Svelte `mount` в `IContentRenderer.init`, `unmount` — в dispose. При `moveTo` сохраняются тот же DOM и значение textarea; пересоздание при `fromJSON` ожидаемо. Рабочие тексты/поиск должны жить отдельно от раскладки. В нынешних компонентах один `app.viewer` и один `app.view`: для нескольких документов нужна переработка состояния, библиотека её не выполняет. Вложенные sidebar/page CSS рассчитаны на старый экран, внутренние размеры и прокрутки требуют макета.

В 8.6.1 core не содержит CSS-файла: подключается `dockview/dist/styles/dockview.css`. Адаптеры `dockview-svelte` не нужны. Вкладки имеют ARIA и навигацию стрелками/Home/End; расширенное управление включается `keyboardNavigation: true`, по умолчанию оно выключено. У библиотеки есть keymap и messages; подсказки стенда локализованы. Проверена программная отправка End в группе из двух вкладок. Физические клавиши, перенос через Ctrl+M, screen reader и изменение размеров с клавиатуры ещё не приняты; Т-45 требует собственного реестра команд.

Контейнер раскладки имеет версию приложения, допускает только известные ID/компоненты; повреждение JSON восстанавливает штатный вид с сообщением. В стенде сохранение ручное, localStorage имеет отдельный ключ `bars-docking-probe-v1`; производство должно учитывать проект и роль окна. Тексты документов в сериализацию не включены. Два регрессионных теста проверяют перемещение/round-trip и отказ от повреждённых/чужих данных.

## Проба отдельных окон с общим воркером

`crates/bars-app/examples/docking_probe.rs` создаёт настоящий Worker с FakeProvider, один Shared/WorkerHandler и два WebView2. Вызывается существующая команда `commands::bars_call`, внутренний RPC — `read` (имя MCP `bars_read` в этот транспорт не передаётся). Оба окна читают один временный документ через один PID. После закрытия дочернего окна родитель снова читает документ. [Нативный результат](../chats/2026-10-20-window-docking/webview2.json) фиксирует перенос DOM, split round-trip, localStorage/recovery, клавиатуру и идентичность воркера.

Профиль WorkerConfig и WebView2 лежит в собственном TempDir, serve/endpoint/single-instance/tray не запускаются; реальные веса и клиенты не нужны. Окна видимы только во время автоматического прогона. Штатный bars не останавливается и не устанавливается заново. FakeProvider подтверждает маршрутизацию, но не расход памяти настоящих моделей. Чтение отдельным окном не закрывает редактирование, ревизии, запись и сохранение при закрытии по Т-29/НФТ-5.

Выявленные ограничения стенда: Cargo example требует manifest Common Controls v6 для TaskDialogIndirect; конфигурация должна лежать в отдельной папке с каноническим `tauri.conf.json` — codegen 2.7.2 выбирает конфигурацию по родительской папке, альтернативное имя в общей папке не изолирует UI. Создание дочернего WebView вызывается async-командой. Нужны x64 libclang, MSVC и Vulkan SDK по [условиям сборки](build.md). Системные DLL ради стенда не заменяются.

## Повтор исследования docking

Из `ui/`: `npm run probe:docking:measure`, `npm test -- src/spikes/docking/layout.test.ts`, `npm run probe:docking:build`. Просмотр компонентов с браузерной подделкой воркера: `npm run dev`, затем `/docking.html`. Кнопка отдельного окна в браузере объясняет необходимость Tauri.

Из корня, в отдельном PowerShell: `pwsh -File scripts/probe-window-docking.ps1 -LibclangPath <папка-libclang-x64> -Output <абсолютный-путь-result.json>`. Скрипт собирает собственный example с manifest, запускает во временной папке с CRT и Vulkan loader из существующей сборки, проверяет новый JSON и убирает свою папку. Профиль нативного процесса вложен в папку runner; при уборке предусмотрено до 3 с на освобождение WebView2 lockfile. Последняя правка ожидания прошла синтаксическую проверку, повтор её удаления не выполнялся из-за запрета автоматической проверки среды. Повторный запуск пишет новый временный результат, поэтому старый успех не подменяет проверку. Для этой сессии libclang 21.1.8 из [пакета ClangSharp](https://www.nuget.org/packages/libclang.runtime.win-x64/21.1.8) распакован только во временную папку; удаление остатков вне репозитория заблокировано средой, [список](../chats/2026-10-20-window-docking/cleanup-blocked.json).

## Границы проверки docking

Программные DOM/API-проверки в собранном WebView2 выполнены; drag мышью, физическая клавиатура, обе темы и узкое окно визуально не приняты. macOS не проверялась. Не проверены междуоконная синхронизация правок, IME, автосохранение, восстановление редакторских черновиков и перенос живого графа без изменения камеры. Макет и полный перенос экранов остаются следующими шагами. Замечание автора о непригодности графа и ISS-13…15/17 этот стенд не закрывает.
