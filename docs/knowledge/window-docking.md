# Исследование docking и отдельных окон bars

Статус: сравнение пакетов и проба адаптера Svelte/WebView2 выполнены 20-10-2026, правая зона исследована 24-10-2026; закрытие вкладок по ISS-54 и продуктовый жизненный цикл зон 3.2.4 проверены 26-10-2026 программно в собранном WebView2. Продуктовый каркас и редактор внедрены в рабочей копии; действующее поведение — [главное окно](../features/window/main-window.md). Установка и физические жесты не подтверждены. Основание — Т-40, Т-43, Т-45, [проект окна](../features/window/requirements.md) и [выбор Dockview](../adr/0003-window-docking.md).

## Метод сравнения библиотек docking

Версии закреплены; метаданные получены из npm 20-10-2026. Размер — полный публичный API, удержанный через namespace export, Vite 8.3.4/minify и gzip Node 24.16.0; это одинаковый синтетический замер JS, а не прибавка к готовому bars. Исходный CSS Dockview измерен отдельно. Скрипт `ui/scripts/docking-benchmark.mjs` устанавливает альтернативы во временную папку и удаляет её в `finally`; в зависимостях репозитория остаётся только кандидат для стенда. [Сырые числа и ошибка сборки](../chats/2026-10-20-window-docking/bundles.json).

| Кандидат | Лицензия / npm modified | JS min / gzip, байт | Применимость |
|---|---|---|---|
| dockview-core 8.6.1 + dockview 8.6.1 для CSS | MIT / 19-10-2026 | 455902 / 97413; CSS 159552 / 12761 отдельно | Прямой DOM-adapter Svelte, вкладки, split, `toJSON/fromJSON`; рабочая проба в WebView2 |
| Golden Layout 2.6.0 | MIT / 21-02-2023 | 153939 / 32542; CSS в это число не входит | Заметно меньше JS; DOM/virtual binding подходит Svelte, `saveLayout/loadLayout`; полный эквивалент клавиатурного docking не подтверждён |
| dock-spawn-ts 4.4.0 | MIT / 19-10-2026 | Размер JS не получен | Штатный namespace-entry не собирается в Vite: CSS imports с `with { type: 'css' }` не дают default export. Нужен адаптер сборки или другой entry; это не доказательство невозможности интеграции |

У npm-пакетов core/Golden Layout/dock-spawn-ts нет объявленных runtime dependencies. У пакета `dockview` есть зависимость от core. `dist.unpackedSize` включает исходные декларации/другие сборки и не используется как размер загрузки. Современность npm modified — сигнал сопровождения, а не показатель надёжности.

Первичные источники: [Dockview API и возможности](https://dockview.dev/docs/overview/introduction/), [клавиатура и доступность](https://dockview.dev/docs/advanced/accessibility/), [сохранение](https://dockview.dev/docs/core/state/save/), [репозиторий и лицензия Dockview](https://github.com/dockview/dockview), [binding Golden Layout](https://golden-layout.github.io/golden-layout/binding-components/), [Golden Layout v2](https://golden-layout.github.io/golden-layout/version-2/), [dock-spawn-ts](https://github.com/node-projects/dock-spawn-ts). Установленные версии и их типы проверены отдельно от текущих сайтов.

## Проба нынешних компонентов Svelte

`ui/docking.html` и `ui/src/spikes/docking/` — отдельный вход, не подключённый к App.svelte. В панелях монтируются настоящие Sidebar, SearchPane, Viewer и GraphPage; дополнительно — два черновика стенда. Штатная композиция даёт пять групп и шесть вкладок: навигация/граф слева, поиск в центре, документ и дополнительная группа справа. Это проверка интеграции компонентов, не согласованный дизайн.

Адаптер вызывает Svelte `mount` в `IContentRenderer.init`, `unmount` — в dispose. При `moveTo` сохраняются тот же DOM и значение textarea; пересоздание при `fromJSON` ожидаемо. Рабочие тексты/поиск должны жить отдельно от раскладки. В нынешних компонентах один `app.viewer` и один `app.view`: для нескольких документов нужна переработка состояния, библиотека её не выполняет. Вложенные sidebar/page CSS рассчитаны на старый экран, внутренние размеры и прокрутки требуют макета.

В 8.6.1 core не содержит CSS-файла: подключается `dockview/dist/styles/dockview.css`. Адаптеры `dockview-svelte` не нужны. Вкладки имеют ARIA и навигацию стрелками/Home/End; расширенное управление включается `keyboardNavigation: true`, по умолчанию оно выключено. У библиотеки есть keymap и messages; подсказки стенда локализованы. Проверена программная отправка End в группе из двух вкладок. Физические клавиши, перенос через Ctrl+M, screen reader и изменение размеров с клавиатуры ещё не приняты; Т-45 требует собственного реестра команд.

Контейнер раскладки имеет версию приложения, допускает только известные ID/компоненты; повреждение JSON восстанавливает штатный вид с сообщением. В стенде сохранение ручное, localStorage имеет отдельный ключ `bars-docking-probe-v1`; производство должно учитывать проект и роль окна. Тексты документов в сериализацию не включены. Два регрессионных теста проверяют перемещение/round-trip и отказ от повреждённых/чужих данных.

## Проба отдельных окон с общим воркером

`crates/bars-app/examples/docking_probe.rs` создаёт настоящий Worker с FakeProvider, один Shared/WorkerHandler и два WebView2. Вызывается существующая команда `commands::bars_call`, внутренний RPC — `read` (имя MCP `bars_read` в этот транспорт не передаётся). Оба окна читают один временный документ через один PID. После закрытия дочернего окна родитель снова читает документ. [Нативный результат](../chats/2026-10-20-window-docking/webview2.json) фиксирует перенос DOM, split round-trip, localStorage/recovery, клавиатуру и идентичность воркера.

Профиль WorkerConfig и WebView2 лежит в собственном TempDir, serve/endpoint/single-instance/tray не запускаются; реальные веса и клиенты не нужны. Окна видимы только во время автоматического прогона. Штатный bars не останавливается и не устанавливается заново. FakeProvider подтверждает маршрутизацию, но не расход памяти настоящих моделей. Чтение отдельным окном не закрывает редактирование, ревизии, запись и сохранение при закрытии по Т-29/НФТ-5.

Выявленные ограничения стенда: Cargo example требует manifest Common Controls v6 для TaskDialogIndirect; конфигурация должна лежать в отдельной папке с каноническим `tauri.conf.json` — codegen 2.7.2 выбирает конфигурацию по родительской папке, альтернативное имя в общей папке не изолирует UI. Создание дочернего WebView вызывается async-командой. Нужны x64 libclang, MSVC и Vulkan SDK по [условиям сборки](build.md). Системные DLL ради стенда не заменяются.

## Проба правой зоны по событиям указателя

Вопрос шага 3.2.2: как в Dockview 8.6.1 (`dndStrategy: "pointer"`) сделать правую зону, которая появляется с документом и исчезает с последней вкладкой, показывает при переносе вкладки превью места и делит группу по высоте. Основание — Т-43, ответ автора по OQ-163 (23-10-2026: правая зона только с документом) и [находка А-2 аудита клиента](../audits/client-2026-10-23.md). Стенд — `ui/zones.html` и `ui/src/spikes/zones/main.ts` (настоящий Dockview, вкладки-заглушки, не подключён к App.svelte). Жест — `PointerEvent` с двенадцатью промежуточными движениями и паузой 450 мс перед чтением превью; собранное окно и физическая мышь не проверялись. Прогон 24-10-2026, окно браузерной панели 1200×700.

Результаты:

| Проверка | Итог |
|---|---|
| `dndEdges` (полоса края корня) | Не срабатывает: в режиме указателя цель определяется самым вложенным элементом под курсором, и над группой всегда выигрывает её область содержимого (`dv-drop-target-content`). Событие `edge` не пришло ни при 1199, ни при 1140 px. Корневая полоса достижима только вне групп, поэтому ширина 48 px через `dndEdges` не задаётся |
| Превью у правого края единственной группы | Есть из коробки: при курсоре в правых 20 % содержимого подсвечивается правая половина (600 из 1200 px), сброс даёт две группы по 600 px |
| Полоса и размер превью | `dropOverlayModel` с `location: "content"`, `activationSize: 48 px` и `size: 40 %` применяется на лету через `updateOptions`: при курсоре правее 1152 px подсвечено 480 px (40 %), левее — вставка в центр. Надпись на превью — псевдоэлемент `::after` у `.dv-drop-target-selection.dv-drop-target-right` («Откроется справа»); своего текста Dockview не рисует |
| Ширина зоны после сброса | Превью 40 % расходится с результатом: новая группа получает половину ширины источника (600 из 1200 при превью 480). Чтобы совпало, `size` ставится 50 % либо после сброса вызывается `group.api.setSize({ width })` |
| Деление правой зоны по высоте | Сброс в нижние 48 px содержимого правой группы даёт группу снизу: 350 + 350 из 700 px при общей ширине; верхняя полоса — то же сверху. Превью — половина с подписью. Запретов в Dockview нет |
| Исчезновение пустой зоны | При `closeEmptyGroups: true` (умолчание) пустая группа удаляется сама: закрытие трёх вкладок справа вернуло одну группу на всю ширину; закрытие вкладки в разделённой зоне оставило остальные группы. Структурный разбор `removableEmptyGroups` из `workspace-layout.ts` для этого не нужен |
| Ширина при повторном появлении | `addPanel` с `position: { referencePanel, direction: "right" }` и `initialWidth` создаёт группу запомненной ширины (420 px, центр 780). Ширину читают из `group.width` перед закрытием и хранят в раскладке: Dockview её не помнит |
| Последняя вкладка центра уходит вправо | При `closeEmptyGroups: true` центральная группа исчезает, правая занимает всю ширину; «Открыть поиск» создаёт новую группу слева. Удерживать пустую группу не нужно: приложение восстанавливает центр после завершения операции, сохраняя `closeEmptyGroups: true`; правило выбора вкладки задано OQ-202 |
| Старые раскладки с пустой правой группой | `fromJSON` оставляет пустую группу в обоих режимах. Перевод на новое правило: после `fromJSON` удалить пустые группы, кроме первой, `api.removeGroup(group)`; из «центр + пустая справа» получается одна группа на 1200 px |

Выводы для проектирования: превью и деление по высоте даёт `dropOverlayModel`, а не `dndEdges`; пустая зона уходит сама при умолчании `closeEmptyGroups`, а правило центра задал автор 24-10-2026: «Если в центре ничего не остаётся открываем поиск. Если поиск был перенесён в право, открываем граф». Реализуется без `closeEmptyGroups: false`: после ухода последней вкладки центра приложение открывает «Поиск» слева от оставшейся группы (проверено `addPanel` с `direction: "left"`), а если «Поиск» уже справа — «Граф». Случай с поиском и графом справа согласован автором в OQ-202: существующий граф возвращается в центр без дубликата. Ширину зоны хранит приложение. Жизненный цикл и миграция реализованы в 3.2.4; полный контракт — [проект рабочей области](../features/window/workspace-plan.md). Физический жест в WebView2 остаётся проверкой шага 3.2.5.

## Размеры и роли групп в продуктовом адаптере

В реализации 3.2.4 `addGroup({ initialWidth })` дал половину доступной ширины вместо запрошенной. Для создания пустой группы перед добавлением панели проверен явный `group.api.setSize({ width })`. Это отличается от пробы `addPanel({ initialWidth })`, которая сразу создаёт группу с панелью. Новая правая зона добавляется у корня сетки: привязка к одной группе разделённого центра ограничивала бы её высоту.

При нескольких правых колонках `setSize` отдельной правой группы меняет внутренний разделитель. Для восстановления общей ширины зоны после изменения окна адаптер двигает границу с центром. Верх/низ разделяют одну ширину; сжатие окна не перезаписывает предпочтительный размер. Регрессии проверяют общий размер, уход последней вкладки до отложенного layout-события и сохранность ширины после перезапуска.

Роли центра и правой зоны хранятся явно и не выводятся из наличия «Поиска». Обработка пустого центра выполняется после операции Dockview с защитой от повторного входа. Продуктовая проверка — 44 компонентных сценария и 17 программных проверок WebView2; синтетический ввод не доказывает физическую достижимость полос переноса.

## Закрытие вкладок Dockview: события и проверка ISS-54

В Dockview 8.6.1 `DefaultTab` пропускает закрытие при `event.defaultPrevented`, а обработчик `click` обёртки строки переполнения сначала закрывает всплывающий список. Поэтому перехват крестика документа в `ui/src/lib/Workspace.svelte` вызывает только `preventDefault()`: `stopImmediatePropagation()` лишал обёртку события и оставлял устаревший список. Обработчик bars выполняет `confirmClose` и закрывает панель лишь после разрешения. Для средней кнопки `auxclick` с `button === 1` вызывает тот же крестик через `.click()`, сохраняя единый путь проверки правок и закрытия списка; `mousedown` с той же кнопкой отменяет автопрокрутку. Наблюдение основано на исходнике установленного пакета и программном прогоне 26-10-2026, а не на предположении о новых версиях библиотеки.

Проверка: 33 целевых теста `Workspace.test.ts` и `unsaved.test.ts`, 514 UI-тестов и полный `scripts/check.ps1` прошли. `workspace_probe` с продуктовым `ui/dist` и изолированным воркером подтвердил закрытие вкладки/списка крестиком и средней кнопкой, сохранение правок при отмене и внешней версии файла при закрытии без записи. Физический жест в установленной сборке не проверен.

Нативный стенд должен ждать появления каждой вкладки после клика: чтение асинхронно, следующий запрос может вытеснить прежний. Для повторной проверки списка нужны сохранённое переполнение и свежий DOM-узел кнопки: при ширине 1440 px после удаления одной из девяти коротких вкладок переполнение может исчезнуть. В прогоне использована ширина 1024 px. Это условия воспроизводимости стенда, не новые правила рабочего окна. Подготовка MSVC/Vulkan/LLVM и общий каталог `C:/bt/bars` — по [условиям сборки](build.md); ожидание занятого Cargo-кэша не считается сбоем продукта.

## Повтор исследования docking

Из `ui/`: `npm run probe:docking:measure`, `npm test -- src/spikes/docking/layout.test.ts`, `npm run probe:docking:build`. Просмотр компонентов с браузерной подделкой воркера: `npm run dev`, затем `/docking.html`. Кнопка отдельного окна в браузере объясняет необходимость Tauri.

Правая зона: `npm run dev` из `ui/`, затем `/zones.html` (`?close=false` — без автоудаления пустых групп); в консоли страницы `__zones.drag(panelId, {x, y})`, `__zones.shape()`, `__zones.api`.

Из корня, в отдельном PowerShell: `pwsh -File scripts/probe-window-docking.ps1 -LibclangPath <папка-libclang-x64> -Output <абсолютный-путь-result.json>`. Скрипт собирает собственный example с manifest, запускает во временной папке с CRT и Vulkan loader из существующей сборки, проверяет новый JSON и убирает свою папку. Профиль нативного процесса вложен в папку runner; при уборке предусмотрено до 3 с на освобождение WebView2 lockfile. Последняя правка ожидания прошла синтаксическую проверку, повтор её удаления не выполнялся из-за запрета автоматической проверки среды. Повторный запуск пишет новый временный результат, поэтому старый успех не подменяет проверку. Для этой сессии libclang 21.1.8 из [пакета ClangSharp](https://www.nuget.org/packages/libclang.runtime.win-x64/21.1.8) распакован только во временную папку; удаление остатков вне репозитория заблокировано средой, [список](../chats/2026-10-20-window-docking/cleanup-blocked.json).

## Границы проверки docking

Программные DOM/API-проверки в собранном WebView2 выполнены; проба правой зоны прогнана только в браузерной панели синтетическими `PointerEvent`; drag мышью, физическая клавиатура, обе темы и узкое окно визуально не приняты. macOS не проверялась. Не проверены междуоконная синхронизация правок, IME, автосохранение, восстановление редакторских черновиков и перенос живого графа без изменения камеры. Макет и полный перенос экранов остаются следующими шагами. Замечание автора о непригодности графа и ISS-13…15/17 этот стенд не закрывает.
