# DirectML в bars: диагностика и ускорение

Обзор ограничений на 18-10-2026. Измеренные результаты RTX 3090, FP16 и продуктовая приёмка — [inference-speed.md](inference-speed.md); их нельзя переносить на любой DirectML-адаптер. DirectML используется встроенными ONNX-моделями Windows; candle-модели работают иначе. Другие устройства — [inference-devices.md](inference-devices.md).

## Контракт DirectML EP

DirectML — GPU API поверх DirectX 12. Индекс адаптера следует DXGI; `0` — основной, не обязательно самый быстрый GPU. Это не индекс NPU. Для DML-сессии ORT нужны `ORT_SEQUENTIAL` и выключенный memory pattern. Одновременные Run одной сессии не поддерживаются; разные сессии могут выполнять Run одновременно. Известные при создании сессии формы позволяют больше оптимизаций; динамические размеры можно фиксировать через free-dimension overrides по имени или denotation. Имена берутся из графа, не угадываются. Текущая страница DML EP указывает opset до 20; совместимость проверяется по реально поставляемой версии. [Официальный контракт ORT DirectML](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html).

DirectML поддерживается в режиме sustained engineering; новые возможности Microsoft развивает в Windows ML. Это причина оценить Windows ML при следующем расширении стека, а не отключать рабочий backend. [Официальное уведомление DirectML](https://github.com/MicrosoftDocs/windows-ai-docs/blob/docs/docs/directml/includes/directml-sustained-engineering-note.md).

## Что показывают прежние замеры bars

В [спайке](spike-search.md) разные этапы дают разные результаты: ранний embed 513 мс/чанк на DML при batch 16 против CPU 430 при batch 4; поздний rerank 15 кандидатов — DML 5,3–5,8 с против CPU 8,5 с. Первая пара не контролирует размер пачки, вторая не доказывает поведение на другом железе. Причина ISS-03 с почти нулевыми rerank-оценками на другой машине остаётся неизвестной.

Сравнение 24 векторов и небольшого набора логитов подтверждает только проверенные артефакты и входы. Оно не гарантирует равенства любых CPU/DML результатов, FP16, новых драйверов или другой GPU.

## Почему GPU может не давать прироста

Рабочие гипотезы для bars, не установленная причина:

| Гипотеза | Как отличить |
|---|---|
| Выбран не тот адаптер или сработал запасной CPU | Записать имя/ID адаптера, фактический EP и причину fallback |
| Граф разделён между CPU и GPU | Профиль узлов, переходы между устройствами и время копирования |
| Слишком много паддинга | Сопоставить реальные длины пар, padded shape и время пачки |
| Малые Run тратят время на запуск/синхронизацию | Отдельно измерить короткий запрос и batch одинаковой длины |
| Неподходящие kernels/precision/export | Тот же ввод на FP32 и FP16, профиль и проверка выходов |
| Давление памяти или питания | Device/shared memory, page faults, частоты и время длительной серии |
| Внешняя задержка — очередь модели | Таймер ожидания отделён от Run; сравнение с поиском без индексации |

ORT умеет выдавать профиль операторов; смотреть нужно весь путь, а не только график GPU в Task Manager. GPU может простаивать, пока CPU готовит вход или копирует данные. [ORT profiling](https://onnxruntime.ai/docs/performance/tune-performance/profiling-tools.html).

## Предлагаемые опыты по ускорению DirectML

1. **Правильная базовая конфигурация.** Проверить контракт EP в фактической сборке fastembed/ort; не добавлять `ORT_PARALLEL` как способ ускорения DML. Не создавать сессию на каждый запрос.
2. **Паддинг rerank.** Сравнить текущие пачки с группировкой по токенизированной длине при прежних K=15 и max_length=512. Сохранять исходные индексы документов; сортировка входов не должна менять соответствие score → document.
3. **Фиксированные формы.** Сначала одна форма запроса, затем небольшой набор buckets. Например, длины 64/128/256/512 — сетка опыта, не новые лимиты bars. Для embed длиннее 512 обязателен отдельный допустимый путь; для неполной пачки нужно корректное маскирование и исключение фиктивных результатов. Учесть цену нескольких сессий и tail batch.
4. **FP16/mixed precision.** Протестировать отдельный экспорт с сохранением нужных IO types. Не менять тип целочисленных token IDs. Проверить sensitive ops, casts, raw logits, NaN/Inf и ranking. FP16 может ускорить совместимую GPU, но результат зависит от kernels; при ошибках часть графа оставляют FP32. [ORT FP16](https://onnxruntime.ai/docs/performance/model-optimizations/float16.html).
5. **I/O Binding только по профилю.** Проверить поддержку device buffers именно DML и закреплённым `ort`. Token IDs приходят с CPU, финальные векторы нужны CPU-поиску; binding не отменяет эти обмены и не ускоряет неподдерживаемые узлы. Возможная польза — повторное использование буферов и управление размещением; стоимость синхронизации включать в итог. [ORT I/O Binding](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html).
6. **Сопоставление backend.** На Intel сравнить с OpenVINO GPU, на NVIDIA — с CUDA. До этого сохранить одинаковые precision, входы и quality baseline; иначе измеряется сразу несколько изменений.

Не переносить dynamic INT8-граф для CPU на DML как готовую оптимизацию: сначала проверить покрытие квантованных операторов и отсутствие дорогих переходов. Не увеличивать число сессий без оценки памяти и p95; параллелизм на одной GPU не равен росту throughput.

## Диагностика неверных оценок и ISS-03

Сначала идентифицировать модель: ревизия, граф и все external data с хешами, tokenizer, max_length, input/output names и types. Повторить одинаковые пары на CPU и DML, записать сырые логиты до sigmoid и порядок после неё. Проверить несколько длин, кириллицу и отсутствие NaN/Inf. Почти нулевая sigmoid может скрывать крупную ошибку отрицательных логитов; совпадения финального score недостаточно.

Затем сравнить runtime, драйвер и адаптер. Если один артефакт стабильно корректен на CPU и ошибочен на DML, это сужает область до EP/драйвера/precision, но не определяет виновника. Переключение на CPU — возможный обход, не доказательство причины. Существующая диагностика описана в [local-models.md](../features/models/local-models.md); новых данных с проблемной машины нет.

## Что пока не доказано для bars

Нет измеренного выигрыша buckets, FP16, binding или OpenVINO над текущим DirectML; не установлено размещение всех операторов текущих bge-графов; не проверены изменения API сессии через fastembed 7.1.1. До опытов настройки пользователя и выбор модели сохраняются. Критерии результата — latency, память, качество и фактическое устройство по [протоколу](inference-speed.md#протокол-следующих-замеров).

Все внешние источники проверены 18-10-2026; upstream-документация не заменяет проверку версии runtime внутри bars.
