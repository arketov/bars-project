# Результаты изолированных опытов памяти bars

Стенд `crates/bars-core/examples/bench_memory.rs`, нативные Windows API, отдельный новый процесс на конфигурацию, release. Доказательства и хеши — [memory-2026-10-18](memory-2026-10-18/Index.md), пересчёт — `node scripts/analyze-memory-spike.mjs docs/knowledge/memory-2026-10-18`. Требования и протокол — [memory-usage.md](memory-usage.md), проект — [memory-plan.md](../features/models/memory-plan.md).

## Среда и границы причинного опыта

Windows 11 Pro 10.0.26300, i7-11700KF 8c/16t, RTX 3090, 32 ГиБ RAM; подробности в `manifest.json`. Rust 1.99, MSVC 14.44, SDK 10.0.26100.0, fastembed 7.1.1 и ort rc.13 из текущего workspace. Использованы локальные исходники fastembed с параллельными изменениями исследования инференса; хеши существенных файлов сохранены в `dependency-sources.json`. Это результаты данной сборки, не чистого опубликованного crate и не доказательство идентичности установленному bars.

Профиль, индекс, клиентские настройки и рабочий IPC не используются. Перед началом каждого процесса три проверки запаса RAM ≥4 ГиБ и commit ≥8 ГиБ; внутри процесса preflight перед загрузками и аварийный выход при RAM <512 МиБ либо commit <1 ГиБ. Первые шесть опытов прошли без аварий, минимум доступной RAM был 8,0 ГиБ, commit-запаса — 18,6 ГиБ. Ранее на этой же машине запас падал ниже порогов; эти состояния не использованы для причинного сравнения.

Новый процесс не очищает файловый кэш ОС. 15 фиксированных фрагментов настоящей документации до 6000 символов, один запрос; rerank K15/batch4/max_length512, embed batch4/max_length8192. Хеш входа одинаков во всех шести опытах. Оценки до/после выгрузки сверяются по каждой паре. Это проверка lifecycle, не новый бенч релевантности и не достаточная выборка для p95.

В режиме `auto` выбран `Device::DirectMl`; размещение каждого узла на GPU не профилировалось. Измерены Private Bytes/WS root-процесса; dedicated/shared GPU memory отдельно не измерены. Суммировать эти числа с VRAM нельзя.

## Шесть первичных опытов памяти

Private Bytes, МиБ; округление до единиц. Каждая строка — отдельный процесс и один опыт, не среднее трёх запусков.

| Нагрузка | После загрузки | После работы | После выгрузки |
|---|---:|---:|---:|
| Только rerank, CPU | 1497 | 1774 | 27 |
| Только rerank, DirectML | 2623 | 3701 | 200 |
| Только embed, CPU | 1498 | 3756 | 24 |
| Только embed, DirectML | 2616 | 5325 | 226 |
| Обе модели, CPU | 5190, после embed-пачки и загрузки rerank | 5470 | 3772, после rerank; 33, после обеих |
| Обе модели, DirectML | 7832, после embed-пачки и загрузки rerank | 8719 | 5390, после rerank; 249, после обеих |

Память embed после трёх коротких запросов была 1503 МиБ на CPU и 2822 МиБ на DirectML. Четыре длинных текста поднимают её до 3756/5325 МиБ. Выходные векторы к моменту плато уже удалены; размер их полезных данных — 16 КиБ. Сохранение гигабайтов связано с жизнью сессии и её рабочих выделений, не с этими четырьмя результатами и не с полным списком SQLite-векторов.

**Ограничение режима core4:** непосредственный вызов ядра с четырьмя длинными текстами превышает padded-лимит воркера 3000 символов. Это контролируемый верхний сценарий ядра, а не воспроизведение штатной очереди индексации. Отдельный режим `bounded` разбивает эти же тексты на одиночные вызовы, как воркер для данного входа; его результаты фиксируются отдельно.

## Контроль ограничения пачки воркера

Режим `bounded`, DirectML: те же четыре embed-текста и те же 15 rerank-пар. Каждый из первых четырёх текстов длиннее 1500 символов, поэтому действующий алгоритм `split_batches` с лимитом 3000 неизбежно делает четыре одиночных вызова. Стенд вызывает именно эти четыре последовательных `embed`; настоящий worker/IPC/ModelSlot здесь не запускался.

Первый полный процесс: embed после длинных текстов — **3614 МиБ**, обе модели после rerank — **7036 МиБ (6,87 ГиБ)**, после удаления rerank — **3670 МиБ**, после обеих моделей — **225 МиБ**. Освобождено 3365 МиБ (3,29 ГиБ); изменение 15 оценок после reload — 0. Повторная загрузка 4,114 с плюс первый rerank 1,070 с. Lifetime peak commit — 7,69 ГиБ, max sample gap — 131 мс; минимум запаса commit — 4,45 ГиБ.

Разбиение снижает удерживаемую embed-память примерно на 1,67 ГиБ относительно core4. Это подтверждает пользу уже существующего ограничения пачки. С ним данный вход не достигает 8,46 ГиБ; исторический вход неизвестен, поэтому точная ретроспективная атрибуция исходного процесса остаётся ограниченной.

Следующая попытка `bounded` остановлена штатным preflight перед загрузкой rerank: commit-запас стал меньше 8 ГиБ, embed освобождён через RAII, процесс завершился с `ok=false`. Результат сохранён в `rejected_runs` и не включается в успешные измерения. Для повторов стартовый запас повышен; полная статистическая повторяемость не заявляется до трёх завершённых процессов.

Повторы с повышенным стартовым запасом 8/16, 8/14 и 6/12 ГиБ RAM/commit не прошли три последовательных проверки в пределах 180/180/120 с; ни одного нового процесса моделей эти серии не запустили. Последний системный снимок: около 0,76 ГиБ свободной RAM и 0,39 ГиБ commit-запаса. Итог этой сессии — **7 успешных процессов, 1 прерванный по preflight, 3 серии повторов без запуска моделей**. Bounded-контроль остаётся разовым, а не статистически подтверждённым на трёх процессах.

## Что объясняет исходные 8,46 ГиБ

Совместный DirectML-опыт дал 8719 МиБ (8,51 ГиБ) удерживаемой частной памяти, что на 52 МиБ выше прежних 8667 МиБ (8,46 ГиБ). Внутри одного процесса наблюдалась последовательность:

| Фаза DirectML | Private Bytes, МиБ |
|---|---:|
| Начало | 3 |
| Embed загружен | 2619 |
| После коротких query | 2812 |
| После длинной embed-пачки | 5315 |
| Reranker загружен вместе с embed | 7832 |
| После rerank | 8719 |
| Reranker удалён, embed остаётся | 5390 |
| Обе модели удалены | 249 |

Причинно воспроизведён механизм такого масштаба: одновременно живые ONNX/DirectML-сессии и удержание рабочих выделений после более тяжёлого входа. Изменяемая переменная — жизнь конкретной модели; после `drop` исчезает основная часть памяти. Веса, prepacking, arena и выделения драйвера точно по отдельности этим опытом не разделены. Называть всю разницу «CPU arena» без allocator/EP profile нельзя.

Исторический процесс PID 28388 уже завершился; его точный вход и размещение узлов неизвестны. Совпадение масштаба в режиме core4 не доказывает, что прежний воркер получил именно такую пачку. У нового установленного PID 42368 отдельно обнаружены ~7490 МиБ committed-регионов MEM_PRIVATE, включая блоки 256–512 МиБ; `VirtualQueryEx` читает только метаданные регионов. Этот снимок подтверждает крупные частные выделения, но не владельца каждого блока. Исходный Working Set около 203 МиБ нельзя считать реальной потребностью программы в RAM или вычитать из Private Bytes для расчёта подкачки.

## Выгрузка rerank — экономия и цена

| Опыт | Освобождено Private Bytes | Время drop | Повторная загрузка + первый rerank |
|---|---:|---:|---:|
| Только rerank, CPU | 1747 МиБ | 0,372 с | 2,287 + 8,734 с |
| Только rerank, DirectML | 3501 МиБ | 0,183 с | 2,414 + 0,763 с |
| Вместе с embed, CPU | 1698 МиБ | 0,183 с | 2,130 + 8,121 с |
| Вместе с embed, DirectML | 3329 МиБ | 0,169 с | 3,367 + 1,191 с |

Во всех четырёх опытах максимум изменения каждой из 15 оценок после reload — **0**; NaN/Inf не допускаются. После второй выгрузки освобождение повторяется. Это подтверждает полезность освобождения rerank-сессии и отсутствие необходимости держать её ради неизменности оценок на этом входе. Цена первого запроса после выгрузки заметна, особенно на CPU; выгружать после каждого запроса по этим данным не предлагается.

Эти исходные спайки не проверяли продуктовый таймер и гонки с активными запросами. Позднее разрыв lock между `prepare` и использованием устранён: lazy load/inference/last-used выполняются под одним model-lock, drop вынесен из замков модели/менеджера. Внедрены rerank 300 с / embed 900 с; настоящий worker timer, отключение и reload проверены в [следующей приёмке FP16](memory-fp16-results.md). Эти TTL — инженерный компромисс, не доказанный оптимум реального трафика. Прежние исходные измерения ниже не подменяют позднюю приёмку.

## Точность измерителя и воспроизведение

`GetProcessMemoryInfo` и `GetPerformanceInfo` вызываются из потока стенда каждые 100 мс; каждый JSONL содержит маркеры и flush. В первых шести опытах максимальный интервал между sample составил 101–167 мс. Показанный пик — максимум наблюдений; lifetime peak commit — дополнительный счётчик процесса. Ни один из них не является точным фазовым allocator-профилем. Три warm-вызова и время загрузки приведены как индивидуальные наблюдения; стабильный median/p95 под нагрузкой не заявляются.

После `cargo build --release --locked --offline -j 1 -p bars-core --example bench_memory`:

Первый исходник стенда сохранён в `spikes/memory/provenance/bench_memory-v1.rs`: SHA256 в точности совпал с `run-20261018T085832957Z.json`. Текущий исходник добавляет режим `bounded`; у каждой серии собственный SHA256 бинарника и исходника. Хеши четырёх существенных файлов fastembed повторно сверены и не изменились. `runtime-modules.json` фиксирует DirectML.dll 1.15.6 с SHA256. Добавление `bounded` потребовало отдельной сборки; первичные шесть опытов не выдаются за запуск второго бинарника.

```powershell
./scripts/run-memory-spike.ps1 -BenchPath <target>/release/examples/bench_memory.exe -ModelsPath <cache>/models -EvidencePath docs/knowledge/memory-2026-10-18 -Modes rerank -Devices cpu,auto -Repeat 3
node scripts/analyze-memory-spike.mjs docs/knowledge/memory-2026-10-18
```

Стартовый runner ждёт три достаточных снимка, максимум `WaitSeconds`; при недостатке памяти новый процесс не запускается. Каждый запуск сохраняет SHA256 бинарника, исходника и fixture. Существующие результаты не перезаписываются. Стенд отказывается скачивать отсутствующие модели. Пользовательские процессы, настройки pagefile и реальные индексы не меняются.

## Остаток исследования памяти

Для реального окна есть отдельное условие изоляции: `BARS_USER_HOME` разделяет home/канал, но в `bars-app/src/main.rs` Tauri single-instance не получает отдельный identifier стенда. Поэтому установленное приложение для UI-baseline не запускалось; нужна отдельная сборка с уникальным identifier. `window.rs` создаёт скрытый webview и при `--background`; скрытие окна не является опытом «процесс без webview».

Два дополнительных успешных bounded-процесса после восстановления запаса; затем реальный worker/IPC и окно, большие документы/параллельная индексация с fake и настоящими моделями, полноценные задержки и качество, при необходимости allocator/EP profile. Mac и ноутбук отсутствуют. Память весов/arena/драйвера по отдельности пока не посчитана; рекомендации для 8/16/32 ГиБ не превращены в подтверждённые минимумы. Этап 13 целиком не закрыт.
