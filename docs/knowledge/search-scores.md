Статус: **измерено дважды.** 03-11-2026 — на node (`node:sqlite`, FTS5) по копиям индексов пяти проектов, 168 запросам [бенча](search-quality.md) и сохранённым выдачам `bars-cli` (без векторов запросов, без сборки): нормирование полей, порог по `bm25`, свёртка; данные и скрипты — [search-scores-2026-11-03](search-scores-2026-11-03/Index.md). 05-11-2026 — шаг 2.3.7, одним прогоном `bench_quality` со сборкой и настоящими моделями: дамп пулов кандидатов со всеми сырыми сигналами и подбор весов и порога по нему (раздел «Замер 2.3.7»; данные — [search-scores-2026-11-05](search-scores-2026-11-05/Index.md)). Итог: веса стартовой схемы подтверждены, порог с rerank поднят с 0,1 до 0,2, сигнал связей не включён, схема не проходит строгую приёмку против прежнего слияния RRF (раздел «Схема баллов против прежнего слияния с rerank и приёмка»). Проект схемы, которую эти опыты обосновывают, — [раздел «Проект схемы баллов»](../features/search/hybrid-search.md) в описании гибридного поиска.

## Вопрос и метод

Как нормировать сигналы, чтобы сумма с весами работала не хуже текущего порядка; нужны ли покрытие слов и фраза отдельными слагаемыми; что делать с порогом, когда нет rerank; даёт ли свёртка кусков раздела потери.

Метод. Полнотекстовая часть — четыре колонки FTS5 как в рекомендации токенизации (название и имя файла, заголовки, текст, точная форма; веса bm25 5 / 3 / 1 / 0,3), стемминг — собственная копия Snowball из [search-bench](search-bench-2026-11-03/Index.md), поэтому абсолютные числа отличаются от `tokenization.md` на 1–2 п.п. (там настоящий английский Snowball). Пул кандидатов запроса — первые 100 по составному bm25. Метрики и эталон — как в бенче: первым, Hit@3, MRR@10 (в таблицах «первым % / Hit@3 % / MRR»). Веса выбирались по нечётным запросам (подбор), проверка — на чётных; выбор — по MRR подбора. Опыты с rerank идут на тех же 10 кусках, которые вернул полный конвейер: переставить можно только их, правильный раздел вне десятки не вернуть. 41 из 1 261 куска выдач не сопоставился с чанком копии индекса (границы чанков сдвинулись после снимка) — для них полнотекстовый балл равен нулю.

## Сумма отдельно нормированных полей хуже одного составного bm25

Сигналы «название», «заголовки», «текст», «точная форма» считались раздельно (`bm25` с единственной ненулевой колонкой), нормировались по пулу и суммировались с весами из сетки (`exp1.mjs`). Только FTS, 168 запросов:

| Вариант | Все | Подбор | Проверка |
|---|---|---|---|
| **один bm25(5,3,1,0.3), как в токенизации** | **60 / 78 / 0,696** | 57 / 76 / 0,678 | 62 / 80 / 0,715 |
| сумма полей, ранговое нормирование RRF (`61/(60+место)`) | 51 / 76 / 0,654 | 50 / 74 / 0,644 | 52 / 79 / 0,664 |
| сумма полей, ранговое `1/(1+место/10)` | 56 / 79 / 0,684 | 52 / 75 / 0,658 | 60 / 83 / 0,711 |
| сумма полей, делением на максимум пула | 57 / 77 / 0,691 | 61 / 77 / 0,706 | 54 / 77 / 0,677 |
| сумма полей, насыщение `x/(x+медиана)` | 55 / 80 / 0,678 | 56 / 82 / 0,691 | 55 / 77 / 0,666 |
| сумма полей, z-оценка | 55 / 79 / 0,680 | 58 / 79 / 0,697 | 51 / 79 / 0,663 |
| то же без покрытия и фразы: RRF / ранг10 / максимум / насыщение / z | 41 / 64; 50 / 73; 57 / 76; 47 / 67; 54 / 79 (первым / Hit@3) | | |

- **Составной bm25 остаётся одним сигналом.** FTS5 считает частоту слова по колонкам вместе и нормирует по длине; раздельные нормированные баллы теряют это. Лучшая сумма (деление на максимум) в целом не лучше, а на проверке хуже на 8 п.п. первым.
- Ранговые нормирования (RRF) заметно хуже: они выбрасывают величину разрыва между кандидатами. Лучшее из рангового (`1/(1+место/10)`) даёт 56 %.
- Веса полей остаются внутри `bm25(…)`: колонки и их стартовые веса задаёт [токенизация](tokenization.md).

## Покрытие слов запроса и фраза как добавки к составному bm25

К bm25, поделённому на максимум пула, добавлялись `w_cov × доля основ запроса, найденных в чанке` и `w_phrase × доля пар соседних слов запроса, стоящих подряд в чанке (1, если подряд весь запрос)`. Сетка `w_cov` 0–0,4, `w_phrase` 0–0,4, три нормирования (`exp2.mjs`, часть A). Только FTS, 168 запросов:

| Вариант | Все | Подбор | Проверка |
|---|---|---|---|
| один bm25 | 60 / 78 / 0,696 | 57 / 76 / 0,678 | 62 / 80 / 0,715 |
| + 0,2 · фраза | 60 / 79 / 0,702 | 58 / 77 / 0,691 | 61 / 80 / 0,714 |
| + 0,4 · фраза | 60 / 79 / 0,703 | 60 / 79 / 0,699 | 60 / 80 / 0,707 |
| + 0,2 · покрытие (без фразы) | 60 / 77 / 0,697 | 57 / 76 / 0,679 | 62 / 79 / 0,715 |
| + 0,4 · покрытие (без фразы) | 58 / 77 / 0,693 | 56 / 77 / 0,679 | 61 / 77 / 0,707 |
| + 0,2 · покрытие + 0,1 · фраза (ранговое 10) | 60 / 78 / 0,702 | 58 / 76 / 0,687 | 62 / 79 / 0,718 |

- **Покрытие слов запроса не помогает**: от 0,1 до 0,4 MRR остаётся 0,693–0,697 и не растёт ни на подборе, ни на проверке; насыщение `x/(x+медиана)` с покрытием ухудшает (51–57 % первым). Основная причина — `bm25` с `OR` уже поднимает чанки с большим числом слов запроса.
- **Фраза даёт не больше +0,006 MRR**, на проверке выигрыша нет — в пределах шума (один запрос — 0,6 п.п.). Это не довод против фразы: оператор `"…"` требует дословности независимо от баллов, а голые идентификаторы поднимает колонка точной формы.

- **Слабая добавка полнотекстового сигнала к rerank — +2 п.п. первым и +0,007…0,010 MRR при Hit@3 без изменений** (все, 168). Выигрыш меньше разброса между подбором и проверкой, и сумма не проходит строгую приёмку: по группам (`exp2.txt`) «идентификаторы» Hit@3 83 → 75 %, «опечатки» 60 / 100 → 40 / 80, «синонимы» 45 → 36 % первым, «руководство среди журналов» Hit@3 100 → 93 %; выигрывают «вопросы обычным языком» (65 / 90 → 70 / 92), «два куска» (83 → 100 % первым), «длинный набор слов» (71 → 86 %). Потеряно по правилу 11 запросов (`bp-07 bp-08 bp-17 bp-38 ob-09 ob-14 ob-20 ob-35 rg-07 ag-23 tm-01`), выиграно 15.
- **Ранговое слияние вредит**: RRF вместо суммы теряет 5 п.п. первым (58 против 63 % у одного rerank). Это довод против рангов, но не оценка нынешнего RRF продукта (смысловая и полнотекстовая части без rerank), которая здесь не воспроизводима.
- Чем больше вес полнотекстового сигнала, тем ниже Hit@3: при 0,5 теряются 5 п.п. Hit@3.

## Абсолютная шкала полнотекстового балла не отделяет правильный ответ от неправильного

Чтобы работал порог без rerank и без векторов, bm25 верхнего результата делился на «идеал запроса»: сумму `idf` по основам запроса × 5 (старший вес колонки) × 2,2 (`k1 + 1`), потолок 1 (`exp3.mjs`). Взят верхний результат по каждому из 168 запросов: 100 правильных и 68 неправильных.

| Порог по доле идеала | Остаётся правильных первых | Остаётся неправильных первых |
|---|---|---|
| 0,05 | 100 из 100 | 67 из 68 |
| 0,10 | 92 из 100 | 59 из 68 |
| 0,15 | 71 из 100 | 34 из 68 |
| 0,20 | 43 из 100 | 15 из 68 |
| 0,30 | 5 из 100 | 1 из 68 |

Медианы 0,19 у правильных и 0,15 у неправильных: **полнотекстовый балл не даёт порога с абсолютным смыслом**, как и ожидалось для bm25. Порог на нём отсекает правильные первые почти с той же долей, что и неправильные. Как слагаемое вместе с rerank доля идеала не лучше деления на максимум (65 / 89 / 0,763 при весе 0,3 против 65 / 88 / 0,763 при 0,1).

## Свёртка кусков одного раздела

На тех же выдачах куски с одним путём и цепочкой заголовков сворачивались в раздел; балл раздела — лучшая оценка rerank плюс `бонус × min(1, сумма оценок остальных кусков)`; раздел засчитывается правильным, если любой его кусок содержит опору (для «двух кусков» — объединение текстов) (`exp2.mjs`, часть D).

| Бонус за остальные куски | Все | Среднее число разделов из 10 кусков | Запросов с худшим местом |
|---|---|---|---|
| без свёртки | 63 / 88 / 0,753 | 10 | — |
| 0 (лучший кусок) | 63 / 88 / 0,754 | 7,4 | 0 |
| 0,05 | 63 / 88 / 0,753 | 7,4 | 1 (`tm-13`) |
| 0,1 | 63 / 88 / 0,750 | 7,4 | 2 (`bp-09`, `tm-13`) |
| 0,2 | 63 / 88 / 0,750 | 7,4 | 2 |

- Десять кусков складываются в 7,4 раздела: выдача из N разделов получается из пула примерно в 1,35·N кусков. Повтор раздела среди пяти первых кусков есть у 7 запросов из 168.
- Бонус за остальные куски никому не помогает и 2 запросам вредит: **начальный бонус 0**, балл раздела — лучший кусок. Свёртка без бонуса качество не меняет (метрики считаются по разделам, а не по кускам, поэтому это нижняя граница пользы: освободившиеся места занимает следующий раздел).
- Не проверено: свёртка до rerank (rerank видит лучший по предварительному баллу кусок раздела) и склейка короткого хвоста разрезанного раздела; вопросов «ответ в двух кусках» всего 6 — все найдены в топ-10 и без свёртки.

## Веса: сетка, перекрёстная проверка, чувствительность

**Сетка** `w_c` 0–0,3 × `w_f` 0–0,3 × `w_p` 0–0,2 × `fold_bonus` 0–0,1 × `K` 10/15/20/30 (1 800 схем с rerank) и `w_f` × `w_p` × `fold_bonus` (144 схемы без rerank) по нечётным запросам. Лучшая схема с rerank на подборе — `w_f` 0,15, `w_p` 0,05, `fold` 0,05, `K` 20: 76 / 87 / 0,821 против старта 71 / 87 / 0,793; но **на чётных 64 / 89 / 0,766 против старта 67 / 87 / 0,767**, то есть ничего не выиграно. Разворот деления (подбор на чётных, проверка на нечётных) даёт 67 / 87 / 0,772 против старта 71 / 87 / 0,796 — хуже. Без rerank обе половины выбирают ровно стартовые веса.

| `K = 25`, θ 0,2 (вариант) | 69 / 88 / 0,784 | 71 / 87 / 0,791 | 67 / 89 / 0,777 | 9 % |

- **Добавки `0,1·f + 0,1·p` нужны**: без них 65 / 82 / 0,742, то есть −4 п.п. Hit@3.
- **Приёмка против RRF не пройдена, и честно сказать так.** Новая схема лучше первым (+3,6 п.п., первым −6 / +12 запросов) и по MRR (+0,010, 95 % интервал [−0,020; +0,039], тест знаков p = 0,73), но хуже по Hit@3 на 1,2 п.п. (потеряно 5 запросов: `bp-28 bp-36 bp-38 ob-20 ob-35`; выиграно 3: `rg-05 bp-10 bp-27`). На проверочной половине 61 / 89 / 0,749 против 65 / 86 / 0,755: Hit@3 −3,6 п.п. (4 потери, 1 выигрыш), MRR +0,006. Нарушения правила в группах: «синонимы» (11 запросов: Hit@3 73 → 64 %, `bp-38` с места 2 на 4), «агентские запросы» (14: Hit@3 50 → 43 %); в проектах: bars-project (Hit@3 −2,4 п.п.), overdrive-bots (−5 п.п.). Группы «номера» (Hit@3 100 → 89 %) и «опечатки» (100 → 80 %) теряют по запросу при группах 9 и 5 запросов.
- **Выигрыш — в группах «обычные вопросы» (первым 67 → 73 %, Hit@3 90 → 92 %), «набор слов» (71 → 86 % первым), «руководство среди журналов» (93 → 100 % первым), «где описано» (73 → 82 % первым), «два куска» (83 → 100 % первым).**
- **Почему теряются `bp-28` и `bp-36`**: правильный кусок стоит на 19-м и 25-м месте по `S0` и не попадает в окно rerank при K = 15, а по RRF стоит 12-м и 14-м. `K` 20–30 лечит это ценой rerank. **Потери `bp-38`, `ob-20`, `ob-35`** окном не объясняются: правильный кусок в окне, но у соседей почти равная оценка rerank (0,89–1,00), и добавки `0,1·f + 0,1·p` их переставляют.
- **Из 600 схем** (независимый расчёт, `independent/`; окно `S0` или RRF × K 15–30 × `w_c` × `w_f` × `w_p`) строгую приёмку против RRF проходят две, и это совпадение на тех же данных; группу «синонимы» валит один запрос `bp-38`, на нём проваливаются 572 схемы из 600. Правило «ни одного потерянного запроса в группе» на группах из 5–14 запросов не выполнить: правило само требует около 400 запросов. Автор 05-11-2026 принял обе схемы (с rerank и без) с этими потерями (OQ-284).
- Стартовые веса 0,1 / 0,1 выбраны опытами 03-11-2026 на этих же 168 запросах, поэтому их перевес над RRF отчасти завышен.

## Операторы запроса

Результаты запросов с операторами — первые 3 раздела с rerank, первые 5 без rerank. Точность — доля результатов, выполняющих оператор по проверке бенча (фраза в тексте куска, исключённое слово не встречается, путь под папкой):

- **С rerank 92 из 94 результатов (98 %), без rerank 135 из 139 (97 %); нарушения — только `bo-16` и `bo-17`.** Оба случая — запрос с фразой, которая стоит в **цепочке заголовков** раздела, а не в тексте куска: колонка точной формы, по которой оператор проверяет фразу, объединяет название документа, заголовки и текст ([полнотекстовые сигналы](../features/search/fulltext.md)), а проверка бенча смотрит только текст куска. Это расхождение проверки с контрактом, а не ошибка разбора: фраза в заголовке — законное совпадение. Остальные результаты (исключения, пути) не нарушили ничего.
- **Полнота против парного запроса без оператора: Hit@3 36 из 38 с оператором против 34 из 38 без него (rerank) и 33 из 38 (без rerank).** Потерян против парного один запрос — `bo-14`. По видам (с rerank, первым / Hit@3 / MRR, парный в скобках): фраза 74 / 95 / 0,842 (95 / 0,803); исключение 100 / 100 / 1,000 (100 / 1,000); путь 70 / 90 / 0,825 (70 / 0,628).
- **«Фраза, которой нет»: пустая выдача у 4 из 4 запросов** — оператор делает пул пустым, как и должен.
- **Дефект: фраза с идентификатором внутри не находит ничего.** `"BARS_MCP_CALL_TIMEOUT_MS"` (`bo-14`) даёт пустой пул, хотя раздел с идентификатором есть. Причина: `exact_text` дописывает целую форму идентификатора (`bars_mcp_call_timeout_ms`) **в конец** списка токенов чанка, а `exact_phrase` оператора строит фразу из токенов запроса вместе с этой формой (`"bars mcp call timeout ms bars_mcp_call_timeout_ms"`) и подряд она нигде не стоит. Так же не сработает исключение `-"идентификатор"` и любая фраза со словом с `_`, `.`, `/` или `-` внутри (только `bo-14` из 42 запросов набора содержит такую фразу). Исправление — строить фразу оператора только из слов, без дописанных форм идентификаторов (`TextStemmer::exact_text` без `identifier_forms`); в этом шаге код оператора не менялся и повторно не собирался (OQ-285).

## Пределы и риски

- **Воспроизведение, а не продукт.** Конвейер повторён по формулам `hybrid.rs` на дампе; построчная сверка с настоящим `search()` не делалась (нужен второй прогон с моделями). Возможны расхождения в порядке при равных `S`; два независимых воспроизведения совпали между собой, но не проверены против продукта.
- **Эталоны одного разметчика, неполны** (ограничения [бенча](search-quality.md)): абсолютные числа — нижняя граница; bars-project и RoleGPT — самые неполные. Основной набор снят по индексам 03-11-2026, наборы без ответа и с операторами — по снимку 05-11-2026: корпус bars-project правят параллельные сессии.
- **Размер.** Одна разница в 1 запрос на 84 проверочных запросах — 1,2 п.п.; группы по 5–14 запросов не различимы; ни одна разница между стартом и RRF не значима (интервалы MRR содержат 0).
- **Запросы без ответа:** 54 запроса дают долю ложных ответов с точностью ±8 п.п.; третий проект RoleGPT (OQ-276) и нетехнический корпус не добавлены.
- **Косинус привязан к bge-m3:** кривая порога верна только для модели дампа.
- Тесты `bars-core` не запускались: константа `min_score = 0,2` потребовала правки трёх утверждений в тестах (`params.rs`, `settings/tests.rs`, `search/hybrid/tests.rs`), они не проверены сборкой.

## Что остаётся не измеренным

- **Цена `K` на машине пользователя:** 0,30 с на кусок на iGPU под фоновой нагрузкой; время поиска с `K` = 25 вместо 15 не снималось отдельным прогоном.
- **Свёртка до rerank и склейка короткого хвоста раздела** (раздел «Свёртка кусков одного раздела») и варианты формулы `l`.
- **Группы по 5–14 запросов**: различия внутри группы меньше 7 п.п. не различимы; решения принимаются по правилу приёмки Т-12 и поимённому разбору (OQ-254).
- **Запросы без ответа на третьем проекте и нетехническом корпусе** (OQ-264, OQ-276).
- **Время `linked_documents`** на пуле 30–50 документов: связи не включены, цена не нужна, пока вес нулевой.
