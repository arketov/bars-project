# Память bars

Исследование 18-10-2026. Основание: Т-1, Т-3, Т-17, НФТ-1…3. Задача автора — понять потребление воркера и окна, причины пиков и влияние подкачки; затем снизить память без потери качества и отзывчивости. Численного бюджета RAM требования пока не задают. Оптимизации ниже — предложения агента.

## Что проверено в коде bars

Serena: активирован проект, Rust LSP возвращает символы, тела и ссылки на `Models`. Проверена текущая рабочая копия поверх `a27c63a`, содержащая параллельные изменения; это не чистый release.

| Узел | Наблюдение | Следствие |
|---|---|---|
| `bars-worker/src/worker/models.rs`, `Models`, `SharedReranker::prepare` | Embed и rerank загружаются лениво; `current_rerank` сохраняет `Arc<RerankSlot>`; таймера простоя нет | Загрузка по требованию уже реализована. Нужен опыт с освобождением слота после использования |
| `Models::reranker` | Замена конфигурации создаёт новый слот; старый освобождается после последней ссылки | Пик смены модели может включать обе сессии; проверить активные запросы и фоновую загрузку |
| `bars-worker/src/handler/mod.rs` | При выключенном rerank поиск не вызывает readiness/reranker | Само выключение не гарантирует немедленного освобождения ранее загруженного слота; требуется проверка пути сохранения настроек и опыт |
| `bars-core/src/search/hybrid.rs`, `Scope::cosines` | SQLite-строка → BLOB → один декодированный вектор → запись оценки в `HashMap<i64,f32>` | Полный массив векторов не материализуется. Остаются O(N) оценки и сортировка, а не N×dim резидентных float |
| `bars-core/src/indexing/indexer.rs`, `index_document` | Документ нарезается целиком; результаты embed всех недостающих чанков собираются перед транзакцией | Пачки модели ограничены, но итоговый буфер векторов ограничен размером документа, а не пачкой |
| `models/builtin.rs`, `builtin_rerank.rs` | fastembed создаёт ONNX-сессии; длины 8192/512; модель и временные тензоры — разные статьи | Размер файлов весов не равен Private Bytes или пику инференса |
| `architecture/components.md` | Воркер и Tauri — один процесс `bars`; webview — дочерние процессы | Нельзя складывать «воркер bars» и «окно bars» как независимые процессы. Нужны последовательные состояния и дерево webview |

При dim=1024 полезные данные 946 векторов f32 составляют 3,70 МиБ, 20 000 — 78,13 МиБ, 50 000 — 195,31 МиБ. Это расчёт N×dim×4, не измеренный heap и не текущий способ хранения при запросе. Такая оценка сама по себе не объясняет гигабайты Private Bytes.

## Пассивный замер установленного bars на Windows

Доказательство: [passive.json](memory-2026-10-18/passive.json), 6 наблюдений 18-10-2026, 12:40:21–12:40:49 UTC+5. Скрипт: `scripts/measure-memory.ps1`. PID 28388, версия файла 0.1.0, SHA256 бинарника и время старта записаны в JSON. Бинарник установлен отдельно от checkout; равенство текущим исходникам не установлено. Предшествующая нагрузка, модели, EP, состояние окна и очередь этого процесса неизвестны. Это наблюдение работающего приложения, не idle-baseline и не опыт с причинной атрибуцией.

| Метрика | Диапазон наблюдений |
|---|---:|
| Private Bytes самого `bars` | 8666,7–8666,8 МиБ |
| Working Set самого `bars` | 202,3–205,8 МиБ |
| Свободная физическая память системы | 73,5–615,7 МиБ |
| Системный commit | 110,03–112,41 ГиБ |
| Системный commit limit | 111,54–112,55 ГиБ |
| Занято в файлах подкачки системы | 12 670–12 747 МиБ |
| Pages Input/sec системы | 11 621–42 570 |
| Потомки `bars`, включая webview | 7 |
| Private Bytes потомков (`conhost`, `msedgewebview2`), сумма | 200,4–207,0 МиБ |
| Working Set потомков, сумма с общими страницами | 119,4–144,9 МиБ |

Private Bytes почти постоянны на этом коротком отрезке; утечка не доказана. Малый Working Set не означает, что bars требует лишь 203 МиБ. Разность Private Bytes и Working Set нельзя считать объёмом его подкачки. Системные paging-счётчики включают чужую нагрузку и чтение отображённых файлов; они не доказывают, что диск читает именно bars.

Сбор одного наблюдения занял 1,86–12,36 с. Данные внутри строки не атомарны; пауза 1 с добавляется к сбору. Такой CIM-сэмплер пригоден для длительных плато и диагностики среды, пропускает короткие пики. `peak_working_set_bytes` относится ко всей жизни процесса, а не фазе. Сумма Working Set дерева повторно учитывает общие страницы. Для фазовых пиков нужен быстрый независимый сборщик/ETW.

Дополнительные загрузки моделей и сборки в этой сессии не запускались: к концу ряда свободный commit приблизился к 0,14 ГиБ. Продолжение нагрузочных опытов требует среды с запасом; чужие процессы и системные настройки не менялись.

## Метрики для следующего опыта

Windows: Private Bytes/PrivateUsage и его пик, Working Set, private WS, системные Available/Committed/CommitLimit, Page Reads/Pages Input/Output, занято в pagefile; GPU dedicated/shared memory отдельно. Сохранять PID+время старта и принадлежность дереву. Private Bytes — частный commit, не физическая память; WS содержит общие резидентные страницы. Hard faults могут читать mmap-файлы, поэтому связь с задержкой проверять трассой, а не одним Page Faults/sec.

macOS: physical footprint каждого процесса и дерево, Memory Pressure, compressed memory, swap used и изменение swap-in/out во времени; не приравнивать footprint к Windows Private Bytes. Mac в этой сессии отсутствует: это протокол, не проверенная поддержка и не замер.

В каждой фазе: базовое плато, максимум наблюдений, прирост к baseline, плато после освобождения, время загрузки/первого/тёплого запроса, median/p95 и количество запросов. Сэмплированный максимум — нижняя оценка настоящего пика; сборщик писать отдельно от процесса инференса с monotonic timestamps и маркерами фаз. Начать с 100 мс и проверить накладные расходы; ETW/нативные peak-счётчики дополнить для коротких пиков.

## Как разложить память по статьям

1. Новый процесс без проектов и моделей: runtime/Tauri без окна, затем окно открыто, скрыто, повторно открыто. Скрытие не считать уничтожением webview. Показать вклад root и дерева отдельно.
2. Новый процесс, одна embed-модель, без индекса: до загрузки, после загрузки, после короткого/длинного embed, после освобождения. Повторить отдельно для reranker и затем обеих моделей. Фиксировать фактический EP и хеши весов/tokenizer; CPU и DirectML — раздельные серии.
3. Разность загрузка→первый inference→повторные длины показывает удержание рабочих буферов/arena; это не точное разделение весов и arena. Для точного разделения — allocator/ORT profile или VMMap/ETW; размер весов на диске хранить отдельной колонкой.
4. Векторный проход и индексацию сравнить с fake-моделями через существующий `test-support`: 5/20/50 тыс. векторов, один большой документ против многих маленьких с тем же общим числом чанков. Затем подтвердить на настоящих моделях. Учесть SQLite cache/WAL, текст чанков, выходные векторы, IPC и число одновременных запросов.
5. Завершение owned-процесса — контроль освобождения; `drop` модели сравнить отдельно. Runtime/драйвер может удержать часть памяти после `drop`; не обещать возврат размера файла весов.

## Подкачка и ожидания от объёма RAM

Windows расширяет commit limit файлом подкачки; предел commit и наличие физической RAM — разные ограничения. Приближение к limit может приводить к отказам выделения. Частый ввод страниц вместе с ростом задержки — сигнал давления; размер pagefile выбирается по нагрузке и требованиям crash dump, не формулой «RAM×1,5». bars настройки ОС не меняет.

Для 8/16/32 ГиБ сейчас нет проверенного минимального бюджета. На 8 ГиБ проверить одну локальную модель и внешний провайдер; на 16 ГиБ — совместную загрузку и большой документ; на 32 ГиБ — те же серии с обычной пользовательской нагрузкой. Это сценарии проверки, не обещания работоспособности. Текущий снимок показывает: 32 ГиБ сами по себе не гарантируют запас при высокой общей нагрузке. Для Apple дополнительно учитывать unified memory и memory pressure.

Контролируемую память ограничивать только в отдельной тестовой среде; не вызывать OOM на рабочем компьютере и не менять его pagefile. Для нагрузочного harness до загрузки проверять доступную RAM и commit, прекращать новую работу при исчерпании запаса. Предлагаемый запас 4 ГиБ RAM и 8 ГиБ commit — защитный порог harness до калибровки, не системное требование bars.

## Первичные источники о памяти

Проверены 18-10-2026:

- [Microsoft: page files и системный commit](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/introduction-to-the-page-file) — назначение pagefile, предел commit и риск отказа выделения.
- [Microsoft: Working Set](https://github.com/MicrosoftDocs/win32/blob/docs/desktop-src/Memory/working-set.md) — резидентные страницы и источники hard faults.
- [ONNX Runtime: memory consumption](https://onnxruntime.ai/docs/performance/tune-performance/memory.html) — shared arena и allocator как варианты исследования, не готовая настройка fastembed.
- [ONNX Runtime: arena shrinkage](https://github.com/microsoft/onnxruntime/blob/main/include/onnxruntime/core/session/onnxruntime_run_options_config_keys.h) — механизм RunOptions; доступность в закреплённой обёртке требует отдельного спайка.
- [ONNX Runtime: DirectML](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html) — ограничения memory pattern и параллельного исполнения; CPU-рецепт нельзя автоматически переносить на DirectML.
- [Apple: Activity Monitor memory](https://support.apple.com/guide/activity-monitor/view-memory-usage-actmntr1004/mac) — pressure, compressed memory, swap.
