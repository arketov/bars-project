# Идеи развития bars

Дата исследования и перепроверки: 18-10-2026. Статус: предложения агента, не решения автора и не обязательства на реализацию. Названия DEV-NN действуют только в этом документе; IDEA-NN остаются пожеланиями автора.

Документ охватывает улучшения надёжности и диагностики существующего поиска. Основные новые возможности приложения — [граф знаний, отдельный поиск связей и GraphRAG](graph-research.md). Быстрые локальные инструменты над документацией разобраны отдельно — [local-documentation-tools.md](local-documentation-tools.md). Такой класс развития нельзя было отсеивать вместе с генерацией ответов; графовый retrieval может возвращать только источники и цепочки связей.

## Вывод исследования

После повторной проверки наиболее обоснованы **проверяемая свежесть результата** и **объяснение работы конкретного запроса**. Первая закрывает подтверждённое чтением кода рассогласование версий; вторая — расширение уже начатой диагностики бенча, а не новая подсистема с нуля. Это обоснование по реализации и внешним примерам, не измеренная пользовательская польза. Места кода, внешние основания, контраргументы и исправления первого прохода собраны ниже.

Ещё три направления сохранены как условные: разнообразие выдачи, полнотекстовый режим без модели и локальная фиксация неудачных поисков. Их нельзя честно назвать доказанными улучшениями без опытов. Для каждого приведён критерий, после которого имеет смысл внедрение.

| Идея | Кому помогает | Оценка пользы | Цена относительно текущего устройства |
|---|---|---|---|
| DEV-01. Свежесть конкретного результата | Человек и агент, читающие меняющиеся docs | Обоснована устройством индекса и чтения | Средняя: протокол, проверки файла, окно |
| DEV-02. Объяснение запроса | Пользователь и разработчик, разбирающие плохой поиск | Обосновано как расширение диагностики | Средняя: встраивание в обычный путь запроса |
| DEV-03. Меньше повторов в выдаче | Человек и агент с ограниченным числом результатов | Условная; частота проблемы не измерена | Средняя: отбор результатов и оценка качества |
| DEV-04. Полнотекстовый режим без модели | Пользователь во время загрузки или сбоя embed | Условная; меняет действующий контракт | Средняя–высокая: отдельная семантика режима |
| DEV-05. Сохранить неудачный поиск для проверки | Автор, накапливающий реальные случаи ошибок | Отдельная фича пока не оправдана | Начать с экспорта DEV-02 и существующего бенча |

Оценки цены — относительные, без сроков. Проверка ограниченная: приложение не запускалось, живой интерфейс и пользовательский эффект не проверены.

## Как проверялась полезность идей

Прочитаны требования, документы поиска, нарезки, обновления индекса, MCP, настроек, схемы SQLite и протокола, пожелания автора, закрытые решения в QUESTIONS.md и последний handoff по разбору пожеланий. Проверены текущий Git-статус и последние коммиты. Существующие параллельные изменения не использовались как доказательство завершённой реализации.

Проведён поиск через bars по требованиям и ограничениям; выдача дополнена чтением первичных документов на диске. Повторный интернет-проход включил API Meilisearch и Typesense, README локального поиска QMD, статью с экспериментами и ограничениями, а также проверку SQLite, W3C и Elasticsearch rank evaluation. Существование метода, реализация в другом продукте и польза для bars учитываются как разные уровни доказательств.

Кандидат проходит отбор, если есть конкретный сценарий, пробел текущего поведения, понятная техническая опора, приемлемая граница сложности и способ проверить результат. Совпадение с существующей возможностью или закрытым отказом исключает рекомендацию. Непроверенные предположения оставлены явными.

## DEV-01. Проверяемая свежесть конкретного результата

**Сценарий.** Агент нашёл раздел, затем автор изменил документ. Открытие по старым строкам может показать соседний текст. Пользователь видит высокий score, но не знает, совпадает ли фрагмент с текущим файлом.

**Проверенная опора.** [Протокол](../architecture/protocol.md) возвращает путь и строки результата, `indexing` и `pending`, но не хеш документа, из которого получен чанк. [Схема](../architecture/schema.md) уже хранит `documents.hash`. [Обновление индекса](../features/indexing/updates.md) допускает поиск по старому состоянию во время записи; при некоторых ошибках чтения старая версия сохраняется. [MCP outline](../features/agent-tools/mcp-tools.md) читает текущий файл. Следовательно, версия выдачи и версия файла могут различаться даже при корректной работе bars.

**Предложение.** Возвращать с результатом хеш индексированной версии документа. При открытии результата сверять хеш с прочитанным содержимым; показывать «файл изменился после индексации» и предлагать повторить поиск после проверки индекса. Хеш должен относиться к тому же снимку индекса, что и текст результата. Для MCP — возможность проверки ожидаемого хеша при чтении; старый текст не обозначать текущим.

**Перепроверка реализации.** `SearchHit` и `ReadOutput` в `bars-protocol` не несут версии. `WorkerHandler::document` читает файл с диска, `openDocument` соединяет этот текст с прежним `hit`, а `Viewer.svelte` использует прежние строки. Предупреждение об исчезновении файла уже есть; новизна — обнаружить изменение существующего файла. Хешировать нужно тот же буфер, который возвращается читателю: отдельное чтение для хеша оставит гонку между проверкой и выдачей. Индекс сейчас считает BLAKE3 от UTF-8-текста без предварительной нормализации переводов строк; согласованность этого представления должна сохраниться.

**Почему полезно.** Предотвращает использование устаревших строк как подтверждённой ссылки. Общий индикатор индексации такой гарантии не даёт. Для объяснения проблемы подходит [W3C: Text Position Selector](https://www.w3.org/TR/annotation-model/#text-position-selector): позиционные привязки чувствительны к изменению источника, поэтому полезно учитывать его состояние. Стандарт не предписывает bars конкретный алгоритм хеширования.

**Границы.** Проверка хеша подтверждает соответствие файлу, а не истинность документа. Отсутствие проверки означает «не проверено», а не «актуально». Не хешировать весь корпус на каждый запрос: проверять открываемый файл; ошибки доступа и исчезновение файла показывать явно. Автопоиск похожего абзаца и вечные ссылки между переименованиями в первую версию не включать.

**Проверка перед внедрением.** Найти раздел → вставить строки выше → открыть старый результат: получить предупреждение без неверной подсветки. Повторить с правкой того же размера, удалением файла, ошибкой чтения и завершившейся переиндексацией. Неизменённый файл должен открываться без предупреждения. Проверить задержку открытия на больших документах.

**Вердикт.** Рекомендовать проектирование. Полезность следует из конкретного рассогласования версий; частота таких случаев пока не измерена.

## DEV-02. Объяснение конкретного поискового запроса

**Сценарий.** «Почему ничего не найдено?» или «На что ушло десять секунд?». По одному score нельзя отличить ограниченную область, отсечение порогом, плохой набор кандидатов и медленный rerank.

**Проверенная опора.** [Поиск](../features/search/hybrid-search.md) состоит из FTS, эмбеддинга, векторного отбора, RRF, rerank и порога. [Протокол](../architecture/protocol.md) уже отдаёт применённые параметры и `rerank_error`, но не времена этапов и число отсеянных кандидатов. ISS-02 показал, что порядок и шкала rerank уже требуют диагностики. Реализованные журнал (IDEA-03) и статистика вызовов (IDEA-05) решают другие задачи.

**Уточнение после проверки кода.** В ядре поиска уже есть `candidate_trace` (`hybrid.rs`) и его вызов в бенче IDEA-06. Это сбор списков кандидатов отдельным вызовом, не объяснение того же пользовательского запроса. Новая часть предложения — встроить наблюдение в обычный путь запроса, сохранить существующие поля и не дублировать поиск ради объяснения. Утверждение о полном отсутствии диагностики было бы неверным.

**Предложение.** По запросу показывать краткое объяснение: разрешённый проект и область; кандидаты FTS/векторного этапа/слияния; сколько прошло порог; был ли rerank; длительность ожидания модели и каждого этапа. Для пустой выдачи — конкретно «кандидаты были, все ниже порога» либо «в выбранной области совпадений не найдено». Не утверждать, что нужной информации нет во всей документации.

**Почему полезно.** Позволяет выбрать исправление по причине, вместо случайной смены моделей и настроек. [OpenTelemetry: traces](https://opentelemetry.io/docs/concepts/signals/traces/) описывает представление запроса как последовательности измеряемых операций. Для bars достаточно локальных таймеров и идентификатора запроса; сервер телеметрии и новая зависимость из этого не следуют.

Более прямой продуктовый пример — [Meilisearch Search API](https://www.meilisearch.com/docs/reference/api/search/search-with-post): `showRankingScoreDetails` раскрывает вклад правил, `showPerformanceDetails` — времена обработки. Это подтверждает практическое применение подхода в поиске, но не необходимость отдельного экрана bars. Счётчики должны описывать выбранный набор кандидатов, а не обещать полный охват корпуса. Время очереди, инференса и SQL нельзя произвольно суммировать при перекрытии этапов.

**Границы.** Не выдавать объяснение алгоритма за объяснение смысла ответа. Числа этапов не являются вероятностями правильности. Не сохранять тексты запросов и документов автоматически; подробный экспорт включать явно. В обычной выдаче — короткий статус, детали раскрываются отдельно. Не повторять уже имеющиеся `applied` и `rerank_error` под новыми именами.

**Проверка перед внедрением.** Контролируемые случаи: область без нужного документа, отсечение порогом, недоступный rerank, холодная модель, очередь при индексации. В каждом случае объяснение должно совпасть с причиной; сумма этапов — согласоваться с общей задержкой с учётом накладных расходов. Сравнить задержку с диагностикой и без неё.

**Вердикт.** Рекомендовать компактное расширение существующей диагностики вместе с будущими логами. Сначала машинно читаемый результат или экспорт по запросу; отдельный экран пока не обоснован. Объяснение нельзя строить через повторный запуск поиска: второй запуск может дать другой результат.

## DEV-03. Меньше повторов при том же числе результатов

**Сценарий.** Три карточки пересказывают один раздел, а другой аспект вопроса не попадает в выдачу. Особенно неприятно при ограниченном контексте агента.

**Проверенная опора.** [Нарезка](../features/indexing/chunking.md) допускает несколько чанков одного большого раздела и добор маленького чанка соседним текстом. [Поиск](../features/search/hybrid-search.md) ранжирует чанки, отдельный этап разнообразия не описан. Это возможность повторов, но не доказательство их частоты в реальной выдаче.

**Предложение.** Сначала сравнить исходную выдачу с группировкой совпадающих разделов; сохранять доступ к остальным фрагментам. Только при недостаточности простого подхода — эксперимент с MMR по существующим векторам. [Elasticsearch diversify retriever](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrievers/diversify-retriever) подтверждает применение MMR для уменьшения избыточности найденного контекста; перенос Elasticsearch в bars не предлагается.

**Риск.** Несколько фрагментов одного раздела могут быть нужны для полного ответа. Жёсткое правило «один документ — один результат» выбросит полезные части; сходные тексты могут содержать разные ограничения. Разнообразие ради числа документов не является улучшением качества.

**Перепроверка внешних доказательств.** [Typesense](https://typesense.org/docs/29.0/api/search.html#group-results) показывает более простой вариант — группировку, а не обязательный MMR. [Better RAG using Relevant Information Gain](https://arxiv.org/html/2407.12101v1), таблица 2 и раздел 6: методы сравнивались на одном бенчмарке с подбором параметров, а ограничения переноса прямо признаны авторами. Нельзя переносить их выигрыш в bars или сравнивать MMR на косинусе с обычным cross-encoder так, будто различается только разнообразие. Одноимённые заголовки также не доказывают дублирование: нужно учитывать документ и конкретное вхождение раздела.

**Условие полезности.** На размеченных вопросах сравнить полноту необходимых опор, nDCG и объём повторяющегося текста при одинаковом бюджете выдачи. Включить вопросы, где правильный ответ требует двух частей одного раздела. Внедрять только при уменьшении повторов без потери нужных опор; улучшение не должно сводиться к нескольким удачным примерам. [Текущий бенч](search-quality.md) — возможная база, но результаты этого эксперимента пока отсутствуют.

**Вердикт.** Кандидат на проверку, не рекомендация менять порядок по умолчанию.

## DEV-04. Явный полнотекстовый режим без готовой embed-модели

**Сценарий.** Модель ещё скачивается или внешний embed недоступен, а пользователю нужен известный идентификатор в уже проиндексированной документации.

**Проверенная опора.** В [схеме](../architecture/schema.md) FTS и векторы хранятся отдельно. [SQLite FTS5](https://sqlite.org/fts5.html) умеет самостоятельно искать и ранжировать совпадения; модель для этого не нужна. Однако штатный [поиск bars](../features/search/hybrid-search.md) гибридный, а даже без rerank порог относится к косинусу. Выключить rerank недостаточно, чтобы обойти embed.

**Предложение.** Рассматривать только явно выбранный пользователем режим по словам на уже существующем читаемом FTS. Пометка «по словам; семантический поиск недоступен» обязательна. Отдельный `bars_text_search` не предлагается: OQ-52 фиксирует один гибридный инструмент.

**Перепроверка.** В `WorkerHandler::search` готовность embed проверяется до выполнения поиска; наличие FTS действительно не даёт доступного режима без модели. [QMD](https://github.com/tobi/qmd#search-commands) описывает отдельные полнотекстовый и семантический пути — это близкий продуктовый пример. Однако перенимать его набор команд вопреки OQ-52 нельзя. [SQLite BM25](https://sqlite.org/fts5.html#the_bm25_function) возвращает лучшие совпадения с меньшим численным значением: это особенно наглядная причина не смешивать его оценку с текущим score bars.

**Цена и ограничения.** Нужна отдельная семантика score и порога: BM25 нельзя подставить вместо косинуса и сохранить прежний порог. Пустой индекс режим не спасает. Состояние `reindex_required` и согласие Т-25 обходить нельзя; разрешение режима при таком состоянии потребовало бы отдельного решения автора. Новая независимая FTS-индексация до скачивания модели существенно расширяет задачу и сюда не входит.

**Условие полезности.** На существующем индексе проверить холодный старт и отказ embed: нужные точные идентификаторы находятся без вызова модели, режим указан во всех интерфейсах, пороги не смешаны. Оценить, насколько часто пользователь действительно сталкивается с такой блокировкой. Если редко, ограничиться DEV-02 и сообщением о состоянии модели.

**Вердикт.** Резервное направление. Технически реалистично, но сейчас не рекомендовать как бесспорную маленькую доработку.

## DEV-05. Локально сохранить неудачный поиск как случай для проверки

**Сценарий.** Пользователь видит неправильную выдачу, позже меняются docs или модель, и исходный случай уже нельзя нормально воспроизвести.

**Проверенная опора.** IDEA-06 уже предусматривает бенч; новый смысл здесь — собирать реальные случаи прямо из использования, а не создавать ещё один бенч или ещё один счётчик MCP-вызовов. [Протокол](../architecture/protocol.md) уже знает применённые параметры; [схема](../architecture/schema.md) — отпечаток модели и хеши документов.

**Предложение.** Явная команда «Сохранить случай»: запрос, область, параметры, модель, версия bars, хеши источников, идентификаторы возвращённых разделов. Пользователь по желанию указывает нужный раздел. Хранение локальное; экспорт только после просмотра состава. Автоматический сбор всех запросов не нужен.

**Перепроверка.** [Elasticsearch rank evaluation](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-rank-eval) связывает запросы с ручными оценками документов и отдельно показывает неразмеченные результаты. Это подтверждает пользу оценённых примеров, но не пользу специальной кнопки или собственной базы случаев bars. Поэтому отдельное внедрение не рекомендовано: достаточно небольшого экспорта DEV-02, если реальным сбоям действительно не хватает воспроизводимости.

**Риск.** Хеши позволяют обнаружить изменение, но не восстановить прежнюю документацию. Для полного воспроизведения нужны доступная версия Git или согласованный снимок; иначе экспорт честно отмечается неполным. Нельзя автоматически объявлять выбранный пользователем документ единственным верным ответом или смешивать эти случаи с отложенной проверочной частью бенча.

**Условие полезности.** Попробовать на нескольких реальных сбоях: запись должна давать достаточно данных, чтобы повторить случай либо точно назвать недостающую версию источника. Если хватает CLI-команды и файла, отдельный экран и постоянная база случаев не оправданы.

**Вердикт.** Полезное продолжение DEV-02 при накоплении реальных случаев; отдельная продуктовая фича пока не обоснована.

## Что в первом проходе было недостаточно

Ссылки на W3C, SQLite и OpenTelemetry подтверждали принципы, но не востребованность функций bars; возможности проверялись по документации, а не по реализации. Поэтому «польза обоснована» означает «сценарий проблемы подтверждён», а не «частота и выигрыш измерены». Рекламные обзоры и поисковые сниппеты доказательствами не считались; чужие продукты не устанавливались и не запускались.

## Проверенные пути реализации

Rust-символы проверены через Serena, Svelte/TypeScript — чтением участков.

| Проверка | Место реализации | Наблюдение и граница вывода |
|---|---|---|
| Версия результата | `methods.rs`, `SearchHit`, `SearchOutput` | Есть текст и диапазон строк; нет хеша источника или версии документа. |
| Чтение файла | `handler/mod.rs`, `document`, `read` | Читается текущий файл; ожидаемый хеш не передаётся, версии не сравниваются. |

| Представление для хеша | `indexer.rs`, вычисление `hash`; `walk.rs`, `read_utf8_path` | Индекс считает BLAKE3 от прочитанного UTF-8-текста; чтение сохраняет BOM и переводы строк. Для DEV-01 важно сравнивать одинаковые представления и хешировать возвращаемый буфер. |

Рассогласование версий следует из этих путей статически: вставка строк перед найденным фрагментом меняет его позицию, а viewer продолжает использовать прежний диапазон. Это доказательство возможности ошибки, не зарегистрированное воспроизведение в работающем окне. Тестовый запуск renderer не выполнялся.

## Проверка контрпримеров и собственной интерпретации

У статьи Pickett et al. есть важный предел: таблица 2 сообщает лучшие значения после подбора параметров, а раздел 6 ограничивает перенос результатов одним бенчмарком и одной LLM. Поэтому таблица не задаёт готовое умолчание bars.

Также нельзя брать худший результат MMR на косинусе относительно KNN с cross-encoder как доказательство вреда разнообразия: меняется и способ оценки. При сравнении с одинаковым scorer в таблице 2 MMR повышает NDCG, а на простой QA с cross-encoder процент правильных ответов одинаков. В промежуточном сообщении о перепроверке такое различие было сформулировано слишком кратко; корректный вывод — эффект зависит от метрики, конфигурации и задачи, а ухудшение от одного только MMR здесь не установлено.

DEV-01 тоже имеет контрпример к чрезмерному обещанию: совпадающий хеш не делает документ правильным и не гарантирует неизменность файла после чтения. Он подтверждает только соответствие возвращённого текста индексированной версии. А несовпадение хеша всего документа может быть вызвано правкой другого раздела: это повод снять гарантию старой позиции, не автоматически скрыть найденный текст.

DEV-02 не может по отсутствию FTS-кандидатов заключить отсутствие ответа: семантическое совпадение не обязано содержать те же слова. После ограничения числа кандидатов и порога можно объяснить судьбу обработанного набора, но нельзя утверждать полноту поиска по всем возможным опорам.

DEV-05 не создаёт воспроизводимость одним хешем. Для неё нужны доступный снимок корпуса, конфигурация и модель; иначе результат экспорта — диагностический случай с явно указанными пробелами. Реальные жалобы полезны для развития, но нельзя подмешивать их в неизменяемый проверочный набор и затем заявлять независимое улучшение.

## Исправления рекомендаций после перепроверки

1. **DEV-01 сохранена.** Основание усилено проверкой цепочки от протокола до viewer; новизна сужена до изменения существующего файла. Отдельно оговорены один буфер для чтения/хеша и представление текста.
2. **DEV-02 сужена.** Переиспользовать существующую диагностическую работу; сначала объяснение или экспорт конкретного запроса. Новая подсистема и отдельный экран не обоснованы.
3. **DEV-03 оставлена экспериментом.** Сначала сравнить простую группировку, исходный поиск и MMR. Никаких новых умолчаний по статье или примерам чужих продуктов.
4. **DEV-04 оставлена резервом.** Реализуемость подтверждается, но полезность режима зависит от частоты блокировок и цены изменения контракта. Автоматический скрытый fallback не предлагается.
5. **DEV-05 понижена.** Пока часть диагностического экспорта и существующего бенча; самостоятельная пользовательская функция не оправдана.

Перепроверка не заменяет опыт на работающем приложении: частота проблем, затраты реализации и измеримый выигрыш не измерены. Результат — две узкие рекомендации вместо пяти доказанных улучшений.
