# Поиск во время индексации: замер задержки и очередь к модели

[← База знаний](Index.md).

Замер 16-10-2026 на машине автора, bge-m3 (ONNX, процессор или DirectML по умолчанию), корпус — первые 66 чанков `docs/` bars. Индексация идёт одним потоком, документ за вызов `embed`; запросы — `embed_query` через тот же `SharedEmbedder`, что и поиск воркера, раз в 0,3 с. Бенч: `cargo run --release -p bars-worker --example bench_search_during_index -- 60`.

## Что было

Модель за мьютексом, индексация берёт его на каждую пачку и сразу берёт снова. Мьютекс `std` не честный, поэтому запрос поиска пропускался вперёд не всегда.

| | в покое | во время индексации |
|---|---|---|
| медиана | 0,49 с | 2,9 с |
| p90 | 0,58 с | 9,4 с |
| максимум | 1,15 с | 22,8 с |

Подозрение подтвердилось: запрос ждал много пачек подряд.

## Меры и их эффект

Две меры: запрос поиска встаёт в очередь перед индексацией, а пачка встроенной модели ограничена по объёму (3 000 символов с учётом дополнения до самого длинного текста). Как это устроено в воркере — [architecture/worker.md](../architecture/worker.md#модели-в-памяти-воркера). Причина предела пачки: время пачки растёт быстрее длины — четыре чанка по 900 символов занимают около 0,9 с, два по 4 200 — 5,4 с, четыре по 3 500 — 8,1 с. Запрос ждёт конца текущей пачки, поэтому длинные пачки и давали остаток задержки; внешним моделям предел не нужен (паддинга у них нет).

| | после очереди | после очереди и предела пачки |
|---|---|---|
| медиана запроса при индексации | 0,88 с | 0,75 с |
| p90 | 5,1 с | 2,0 с |
| максимум | 8,4 с | 3,0 с |
| индексация 66 чанков | 40,9 с | 43,7 с |

Остаток — ожидание одной пачки, в худшем случае одного очень длинного чанка (около 3 с). Меньше его не сделать, пока запрос и индексация делят одну модель. Индексация стала медленнее на 7%.

## Полный поиск и управление 20-10-2026

Изолированный временный профиль и проект из 24 коротких Markdown-документов; настоящая bge-m3 FP32 и bge-reranker-v2-m3 FP16, оба слота `ready`, `actual=directml`, без fallback. Машина: Intel Core i7-11700KF, NVIDIA RTX 3090, 32 ГБ RAM; Windows, release, Rust 1.99.0. Стенд: `cargo run --release -p bars-worker --example bench_worker_during_index`; веса должны уже быть готовы, иначе стенд отказывает без скачивания. Пользовательские проекты, настройки и клиенты не меняются. Временный индекс содержит тексты и автоматический граф.

После прогрева моделей строится новый индекс рядом со старым. Поиск читает старый индекс через настоящий IPC (`ClientKind::Mcp`) и обработчик окна. Включён rerank; у каждого запроса три результата, `score_kind=rerank`, `rerank_error=None`. После возврата каждого поиска полная переиндексация всё ещё выполнялась (`running_after=Rebuild`).

| Операция | Первый прогон, мс | Второй прогон, мс |
|---|---:|---:|
| Полный поиск в покое | 241 | 266 |
| Статус через IPC при индексации | 159 | 51 |
| Ход через обработчик окна | не снимался | <1 |
| События операций через обработчик окна | не снимались | <1 |

Два прогона в таблице выполнены до разделения проверки и обновления (исправление приоритета модели уже включено). Там `queued=true` означало только приём проверки, не её завершение.

После принятого OQ-105, реализации `scan` и сокращения read-lock до копирования метаданных выполнен итоговый прогон: после начала полной индексации создан 25-й документ; проверка обнаружила один новый и 24 неизменённых файла. Завершение проверки, а затем оба поисковых ответа получены при всё ещё работающем `Rebuild`.

[Исходные результаты](../chats/2026-10-20-indexing-responsiveness/measurements.txt). Это одиночные измерения, не медиана/p95 и не гарантия для большого корпуса. Rerank работал без ошибок; поиск и проверка не ждали конца индексации. После замера `shutdown` завершает текущее задание и не берёт следующие из очереди. Доставка обнаруженного документа в опубликованный индекс после подмены отдельно проверена IPC-регрессией. В настоящем Tauri-окне установленной сборки этот стенд клики не выполняет.

В допуске модели найдена гонка: пачка проверяла число ожидающих запросов только перед ожиданием мьютекса. Теперь приоритет перепроверяется после его захвата. Новый тест `a_batch_already_waiting_for_the_lock_rechecks_query_priority` падает на прежнем `run` и проходит с исправлением. IPC-регрессия `full_rebuild_keeps_status_window_controls_and_full_ipc_search_responsive` использует управляемую подделку модели, настоящий индекс и rerank: статус/ход/приём проверки отвечают при удерживаемой модели, оба поиска завершаются при идущей индексации. Подделка доказывает порядок блокировок, а не скорость настоящих моделей.

## Что не проверено после замера 20-10-2026

- Длительность ожидания подмены индекса читателями (`Worker::gate`) отдельно не снималась. Временные индексы проверяют ожидание читателей перед подменой и доставку изменений после неё; короткие DirectML-прогоны проверяют чтение старого индекса во время построения нового.
- Для независимой проверки подтверждены отмена/объединение, пауза, смена настроек и регистрации, удаление проекта, Т-25; это регрессионные проверки на временных профилях. Настоящий нативный клик установленного окна не проверялся; контракт — [обновление индекса](../features/indexing/updates.md).
- Большой корпус, параллельные поиски, длинные чанки, CPU и FP16 embed в полном воркере; реальные UI-действия установленного Tauri. Короткий DirectML-прогон не закрывает эти сценарии.
- Внешние модели и candle-модели (Qwen3, Nomic): предел пачки по объёму к ним не применялся.
