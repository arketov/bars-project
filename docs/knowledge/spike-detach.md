# Спайк запуска воркера из bars-mcp

Проверка риска из [stack-research.md](stack-research.md): Claude Code на Windows может держать MCP-серверы в job object и завершать всё дерево процессов вместе с сессией. Тогда воркер, запущенный из `bars-mcp`, умирал бы с сессией. Windows, 14-10-2026. Код — `spikes/detach`, выбрасываемый.

## Как проверяли запуск воркера

`spike-detach` — заглушка stdio-MCP. На `initialize` она запускает свою копию в роли «воркера» так, как описано в [architecture/ipc.md](../architecture/ipc.md): флаги `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` и попытка `CREATE_BREAKAWAY_FROM_JOB`; если отвязаться от job object нельзя — без него. Дочерний процесс 15 минут пишет пульс в лог.

## Результаты запуска воркера

| Кто запустил заглушку | Отвязка от job object | Дочерний процесс после завершения родителя |
|---|---|---|
| shell инструмента Bash внутри Claude Code | запрещена: «Отказано в доступе», запуск без отвязки | жив |
| Claude Code (приложение), MCP-сервер сессии | разрешена | жив, пока сессия идёт |
| `claude mcp list` — CLI запускает сервер, подключается и завершается | разрешена | **жив после завершения `claude`** |

Вывод: на Windows воркер, запущенный из `bars-mcp`, переживает конец сессии Claude Code. Запасной путь через автозапуск воркера с системой (OQ-16) для этого не нужен.

## Что не проверено про запуск воркера

- Выход из интерактивной сессии `claude` через `/exit`: в терминальной сессии автора заглушка не подключилась («Failed to reconnect: CONNECTION_CLOSED»), причина не выяснена. Сценарий `claude mcp list` — тот же жизненный цикл процесса: запуск, подключение, завершение клиента.
- Codex.
- macOS: там вместо job object — группа процессов и SIGHUP; запуск через `open -b` описан, но не проверен.
