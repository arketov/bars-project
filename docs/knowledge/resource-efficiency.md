# Снижение нагрузки bars без потери качества

Статус 03-11-2026: исправление 2.2.9 стоит в установленном bars и убрало повторное чтение `graph_meta`, но публикация графа по-прежнему переписывает граф проекта целиком: одна публикация overdrive-bots — около 6,3 ГБ записи и 6,6 ГБ чтения, и запускается она после каждой индексации. Замер и причины — разделы «Полная перезапись графа после v2» и «Перестройки графа по кругу». Требование автора — НФТ-7 в `MAIN_IDEA.md`, дефекты — ISS-101, ISS-103, ISS-104.

Статус 02-11-2026: в установленном bars подтверждена тяжёлая фоновая публикация графа, ISS-101: около одного ядра и 596 МиБ/с логических чтений. Причина воспроизведена отдельно: большие checkpoint-значения в `graph_meta WITHOUT ROWID` вместе с построчным обновлением ревизии. Код исправления 2.2.9 подготовлен; storage 21/21 и ревью пройдены, окончательная приёмка не завершена. По указанию автора дальнейшие тесты, сборки и замеры остановлены. Исследование 3.6.1 измеряет CPU нового рабочего WebView2 и остаточные таймеры изолированного UI; причина прежнего отсутствия browser/renderer, ISS-102, остаётся неустановленной. Одна белая область `PrintWindow` прежней серии не доказывает историческое падение.

Прежние меры — общий кэш графа, удержание расчёта между квантами, сокращение опроса окон, один обход аудитов и последовательный SQL — реализованы и проверены. Полный `scripts/check.ps1 -Jobs 2` с `RUST_TEST_THREADS=1` и 14 изолированных Tauri/WebView2-проверок прошли 26-10-2026; последующий замер настоящих окон описан в разделе опроса. Эти проверки не исключают новый дефект публикации. Общий ресурсный профиль OQ-191 остаётся открытым.

## Повторное чтение и кэш графа

`crates/bars-worker/src/handler/graph_cache.rs` разделяет Arc проверенного Dataset между `graph_query`, `graph_physical`, mix и проверкой готового графа. Отдельный `physical_similarity` сохраняет рассчитанную близость документов. Отсчёт бюджета `graph_query` перенесён до ожидания замка и загрузки. JSON таблиц разбирается построчно без дополнительного массива всех сериализованных строк; валидация сохранена.

`worker/graph.rs`, `Attempt::run`, проверяет готовность через тот же кэш. Публикация прогревает его отдельно от первого запроса. Прямой синхронный вызов ядра при проверке готовности по-прежнему валидирует хранилище; worker обходит эту загрузку при совпавших входах и готовом снимке. Число таких загрузок до исправления нельзя считать по количеству похожих строк исходников: оно зависело от пути вызова.

Кэш удерживает один проверенный неизменяемый снимок и отдаёт ссылки на него. QueryOverlay отделяет текущий manifest и предупреждения контекста, не клонирует весь Dataset. Триггерная ревизия охватывает публикацию, входы и состояние задания; дополнительно проверяются идентификатор файла ОС, версия схемы и замок регистрации проекта. Между вызовами файл SQLite не остаётся открытым, что необходимо для подмены индекса на Windows. Старый индекс без ревизии не удерживается до штатного обновления схемы графа.

Компромисс: кэш уменьшает повторное чтение и разбор, но увеличивает удерживаемую RAM. Размер JSON в SQLite не равен размеру Rust Dataset. Предел удержания и вытеснение неактивных записей реализованы; активные загрузчики и ожидающие читатели сохраняют общий Slot. Граница удержания, временное превышение при активных загрузках и обязательная свежесть определены в [архитектуре графа](../architecture/graph.md).

Логическое чтение — 22 254,98 МиБ (596,00 МиБ/с), запись — 4,14 МиБ; private commit в конце — 9 828,56 МиБ, Working Set — 882,46 МиБ. Источник — [счётчики процессов и дисков](idle-load-2026-11-01/passive-1.json), расчёт — `summary.json` рядом.

Серия на общей машине: работали чужие компиляторы и Ouroboros. Физический диск C: за эту серию читал 11,40 МиБ/с и писал 19,00 МиБ/с **по всей системе**; доля bars не измерена. Логические чтения процесса включают файловый кэш и IPC, их нельзя объявлять чтением SSD. WPR отказал с `0xc5585011`; системная политика не менялась. Исследователь не запускал поиск во время пассивной серии; в `sample-log.json` нет завершённых поисков, но есть фоновые проверки индекса и изменение одного документа. Наличие чужих незавершённых запросов по этому журналу не исключается; серия не является строгим стендом неизменного простоя. До и после серии выполнялись служебные поиски документации.

У двух проектов работали задания графа: bars-project — `graph:1194`, OVERDRIVE BOTS — `graph:590`; два других проекта были в `idle`. По пяти [снимкам стека горячего потока 56644](idle-load-2026-11-01/stacks.json) путь одинаков: `Attempt::run` → `build_index_graph_step_with_state` → `job::run` → `finish_graph` → `publish_with_errors` → `Connection::execute_batch` → `sqlite3_step` → `ReadFile`. Снимки сделаны после пассивной серии; поток кратко приостанавливался для чтения контекста/стека и возобновлялся в `finally`. Это устанавливает дорогой этап публикации, но не определяет, какой проект обслуживал поток в каждой точке.

### Почему публикация графа перечитывает гигабайты

`crates/bars-graph/src/store.rs` создаёт `graph_meta(key TEXT PRIMARY KEY,value TEXT NOT NULL) WITHOUT ROWID`. В этой таблице одновременно хранятся небольшие `read_revision`, `progress`, `state` и большие `knn_prepared`, `knn_checkpoint`, `knn_complete`. При публикации пакет удаляет старые графовые таблицы; триггеры `graph_read_*` после каждой изменённой строки обновляют `read_revision` в `graph_meta`. В живом OVERDRIVE-индексе `knn_prepared` имел 53 998 830 символов JSON; граф содержал 56 830 связей и 31 221 основание. Схема, размеры и планы DELETE сохранены в `sql-schema.json` (поле `metadata.bytes` содержит результат SQLite `length(TEXT)`, то есть символы, не UTF-8-байты).

На искусственной базе воспроизведены те же имена/длины метаданных и триггер обновления счётчика после удаления строки. Значения заменены ASCII, данные проектов не копировались. Для каждой конфигурации — отдельная WAL-база внутри `.bars/`, ровно 100 удалений, ревизия во всех случаях выросла до 100. Счётчики процесса сняты после подготовки, до/после DELETE; SQLite стенда — 3.53.0 (`node:sqlite`). [Результаты воспроизведения](idle-load-2026-11-01/synthetic.json):

| Конфигурация метаданных | Время DELETE, мс | Логическое чтение | CPU, с |
|---|---:|---:|---:|
| Большие значения, `WITHOUT ROWID` | 23 756,94 | 10 864 222 216 байт, 10,12 ГиБ | 15,484 |
| Значения ограничены 100 символами, `WITHOUT ROWID` | 6,13 | 8 байт | ниже разрешения счётчика |
| Те же большие значения, обычная rowid-таблица | 55,55 | 8 байт | ниже разрешения счётчика |

Стек живого процесса, его схема и парное воспроизведение согласуются: маленькое обновление счётчика в B-tree с большими значениями вызывает повторное чтение overflow-страниц; построчные триггеры умножают его на число удаляемых объектов. Это не необходимость модели или поиска. [SQLite рекомендует обычные rowid-таблицы для больших строк](https://www.sqlite.org/withoutrowid.html); конкретный масштаб повторного чтения установлен нашим стендом, а не документацией SQLite.

Проект исправления 2.2.8 подготовлен 02-11-2026 в [архитектуре графа](../architecture/graph.md), раздел «Проект раздельного хранения checkpoint и ревизий»: там определены размещение, атомарная миграция и критерии сохранности/производительности. Код 2.2.9 подготовлен; результаты и незавершённые проверки приведены в разделе «Парный стенд checkpoint v2». Отключать триггеры или менять рабочую базу вручную по этому опыту нельзя считать исправлением. Для приёмки нужен одинаковый корпус и сравнение до/после по CPU, логическому I/O и времени всей публикации с отдельным учётом миграции; одного уменьшения числа вызовов недостаточно. Стенд из одной серии на конфигурацию — доказательство механизма, не проверка продуктовой миграции, общего времени построения или экономии SSD. Хеши бинарников и принадлежность процессов — в `provenance.json`.

## Парный стенд checkpoint v2

02-11-2026, Rust `checkpoint_probe` с bundled SQLite 3.53.2, WAL, page_size 4096, cache_size −2000 КиБ. Размеры метаданных взяты из второй записи `sql-schema.json`, содержимое синтетическое. Каждый процесс использует собственную базу в `.bars/`, отдельный exe; рабочие индексы не открываются. CPU и логический I/O сняты Win32-счётчиками, память — пиковые Working Set/commit всего процесса, включая подготовку и миграцию. Поэтому это не добавочная RAM одной публикации. После подготовки выполняются checkpoint WAL и shrink_memory. Подготовка исключена из времени DELETE/публикации, миграция измерена отдельно.

Сохранённые [52 успешных измерения](idle-load-2026-11-01/checkpoint-v2.jsonl) и [параметры бинарника](idle-load-2026-11-01/checkpoint-v2-provenance.json) — неполная серия: автор остановил нагрузку. Для DELETE получены пять повторов каждой конфигурации, для полной публикации большого payload — только одна пара. SHA-256 фиксирует бинарник стенда; числа доказывают размещение и горячую инвалидацию, а не приёмку окончательного workspace. Стенд воспроизводится исходником `crates/bars-graph/examples/checkpoint_probe.rs`, новые запуски сейчас не разрешены.

| Опыт | v1 | v2 |
|---|---:|---:|
| DELETE 10 строк, большой payload: медиана | 1130,34 мс; 1 081 049 088 байт чтения | 5,72 мс; 24 576 байт |
| DELETE 100 строк, большой payload: медиана | 12 211,09 мс; 10 810 195 968 байт чтения | 36,19 мс; 24 576 байт |
| DELETE 100 строк, малый payload: медиана | 7,39 мс; 24 576 байт | 6,86 мс; 24 576 байт |
| Вся публикация, 10 документов, большой payload: одна пара | 22 565,32 мс; 22 269 202 432 байт | 19,24 мс; 192 512 байт |

Рост чтения v1 пропорционален числу изменяемых строк и объёму payload; у v2 множитель размера payload в горячем пути отсутствует. На всех завершённых парах публикации совпал hash sources/nodes/edges/evidence; после публикации выполнялось проверенное чтение Dataset. Малые серии не подтверждают ускорение всего процесса: fsync/параллельная нагрузка дают разброс, а новая схема имеет разовую стоимость миграции. Полный гейт, окончательные kNN/cache-регрессии, native/installed-приёмка, p95 поиска и SSD-трафик не подтверждены. Незавершённые серии не считать успешными; никакого автоматического продолжения.

## Полная перезапись графа после v2: замер 03-11-2026

Вопрос: что даёт фоновую нагрузку установленного bars после исправления 2.2.9. Автор: «нагружает ПК (ЦП и ДИСК) не при индексе или поиске, а просто в рандомный момент».

**Сутки работы.** `bars.exe --background`, PID 50860, запущен 02-11-2026 16:55, замер 03-11-2026 около 14:35 по Екатеринбургу (≈21,5 ч): 4046 CPU-секунд (≈5 % одного ядра в среднем), Working Set 2,1 ГБ, 105 потоков. `Win32_Process`: ReadTransferCount 196,6 ГБ, WriteTransferCount 122,7 ГБ, 54,6 млн операций чтения и 58,2 млн записи. Индекс bars-project — 157 МБ. В простое между циклами — 0,2 CPU-секунды за 10 с. Зарегистрировано 11 проектов.

**Один цикл, счётчики каждые 5 с** ([данные](idle-load-2026-11-03/io.csv), время UTC):

| Время | Этап | Ввод-вывод |
|---|---|---|
| 09:50:02–09:52:52 | индексация 29 документов overdrive-bots | чтение до 7 МБ, запись до 1,6 МБ за 5 с |
| 09:52:57–09:53:08 | подготовка графа: чтение всех 1078 документов с диска, ключ входов по текстам и векторам | 190–315 МБ чтения за 5 с |
| 09:53:35 | запись промежуточного снимка `knn_prepared` | WAL вырос до 70,7 МБ |
| 09:53:51–09:54:38 | публикация | 280–1100 МБ записи за 5 с, ≈6,3 ГБ записи и ≈6,6 ГБ чтения за 47 с; CPU 5,1–5,6 с за 5 с; пик WAL 197 МБ |

Отдельный замер 45 с: 6,3 ГБ записи, 7,1 ГБ чтения, 40,7 CPU-секунды.

**Почему так дорого.** `crates/bars-graph/src/store.rs` при публикации удаляет все графовые таблицы одним пакетом и вставляет sources, nodes, edges, evidence построчно — около 224 тыс. строк и 206 МБ страниц для overdrive-bots — в одной транзакции. На каждую строку срабатывают триггеры ревизии (`crates/bars-graph/src/store/schema.rs`). Соединение открывается без `cache_size` (`crates/bars-core/src/storage/index.rs`), то есть с кэшем SQLite 2 МБ. Ключи — случайные хеши blake3 в таблицах `WITHOUT ROWID` с крупными JSON-значениями, на рёбрах два индекса. При пике WAL 197 МБ записано 6,3 ГБ: каждая страница переписывается в WAL около 30 раз — изменённые страницы вытесняются из маленького кэша. Средний размер операции записи 2,2 КБ совпадает с картиной «заголовок кадра WAL + страница».

**Сколько это за сутки.** Счётчик `read_revision` индекса overdrive-bots — 7 568 127; одна публикация добавляет около 447 тыс. Отсюда около 17 публикаций с перехода на v2, 17 × ≈6 ГБ — больше 100 ГБ из 122,7 ГБ записи. Это расчёт: момент начала отсчёта ревизии не проверен.

**Что ещё нагружает.** Поиск перечитывает 35–125 МБ на запрос (ISS-94; время поиска, а не фон). Открытое окно в простое — 1,6–4,6 МБ чтения за 10 с и 0,8–3 CPU-секунды за 10 с. Вложенные проекты tmc-opovechenie за сессию не индексировались; аудит битых ссылок запускался около 35 раз, только по изменению документов и без чтения содержимого — дёшево.

Пределы: физическая запись на SSD не измерена, только логическая через файловый кэш; эффект предложенных правок не замерен; WebView2 отдельно не исследовался (по 3 ГБ у процессов gpu и renderer).

### Дешёвая публикация графа: что изменено и как замерить

Статус 03-11-2026: код шага 1.1.2 написан, не собирался и не запускался по указанию автора; замер «до и после» не проводился. Устройство — в [архитектуре графа](../architecture/graph.md), раздел «Дешёвая публикация поколения».

Изменено три причины из раздела выше: одно приращение `read_revision` на публикацию вместо ≈447 тыс.; кэш страниц SQLite 256 МиБ на время публикации вместо 2 МБ; вставка в порядке ключа с пересозданием индексов рёбер после вставки и хеш-картой источников вместо перебора. Частичное обновление по изменённым документам не делалось.

**Гипотеза, не результат.** Если страницы поколения (≈206 МБ) помещаются в кэш, каждая изменённая страница попадает в WAL один раз при COMMIT: запись ≈6,3 ГБ → порядка размера поколения плюс индексов (≈0,4 ГБ), число приращений ревизии 447 тыс. → 1, время и CPU падают пропорционально. Чтение должно упасть заметно, но величину гипотеза не задаёт. Риски: пик памяти до 256 МиБ на время публикации; пересоздание индексов даёт один проход сортировки.

**Метод замера (нужно разрешение автора).** Копия индекса overdrive-bots во временной папке вне рабочего `.bars`; один стенд, на котором публикуется один и тот же набор до и после правки (прежний код — из коммита перед правкой); одинаковые page/WAL-настройки; не менее пяти повторов, первый отбрасывать как прогрев. Измерять: время, CPU-секунды, `ReadTransferCount`/`WriteTransferCount` процесса, пик WAL, размер БД, число приращений `read_revision`, пик Working Set. Проверить равенство: построчное совпадение графовых таблиц до и после и одинаковый результат `graph_query`. Результат записывать в этот раздел с датой; до того гипотезу нельзя переносить на другие корпуса.

## Перестройки графа по кругу и «случайный момент»

- **После каждой индексации, даже пустой.** Индексация ставит задание графа при `Updated` или `Interrupted` (`crates/bars-worker/src/worker/mod.rs`, после `finish_docs`). `finish_update` всегда вызывает `touch_updated_at`, триггер `graph_read_meta_*` увеличивает `read_revision`, и кэш графа, привязанный к ревизии (`crates/bars-worker/src/handler/graph_cache.rs`), сбрасывается. Задание до трёх раз полностью читает граф. В замере пустые индексации 09:55:28, 09:55:34 и 09:55:43 дали по ≈142 МБ чтения каждая. Когда загрузка не укладывается в бюджет, журнал пишет «Снимок графа не удержан в кэше». ISS-103.
- **Перезапуск при правках подряд.** Пока агент правит файлы проекта каждые несколько секунд, каждая индексация ставит граф заново. Подготовка сверяет хеш файла на диске с индексом и падает с «ссылка на объект устарела» (`crates/bars-core/src/graph/build.rs`), затем повтор и новая подготовка с чтением всех документов. Ожидания тишины и ограничения частоты нет. ISS-104.
- **«Случайный момент» — почасовая проверка.** Таймер проверки проектов идёт раз в час от старта воркера; индексации начинались в 12:55, 13:55, 14:55, 15:55 UTC. Слежение за файлами работает только при открытом окне или в течение часа после MCP-вызова (Т-10). Агенты, правящие overdrive-bots без обращения к bars, накапливают правки, и проверка подхватывает их разом: индексация, загрузка embed-модели, подготовка и публикация графа — около 6 ГБ.
- **Ложные тревоги слежения.** «Слежение молчало: перезапускаю слежение» появляется у проектов, которые никто не наблюдает, и ничего не делает. У проекта без корня документации (agaugu до перерегистрации) окно повторяло запуск слежения каждые 10 с, а расписание аудитов раз в минуту писало ошибку обхода. Нагрузка ничтожная, шум в журнале — ISS-106. Исправление написано 03-11-2026, не проверено: без корня документации слежение не повторяет запуск, расписание аудитов пропускает проект с одной записью при смене состояния, предупреждение о молчании — только у наблюдаемых проектов ([слежение](../features/indexing/updates.md)).

**Исправление 1) написано 03-11-2026, не проверено.** Задание графа не ставится после индексации без изменений при текущем графе; автоматический проход ждёт 90 с тишины и не начинается чаще раза в 5 минут (не больше 12 в час); правка во время подготовки сдвигает начало, повтор один. Пустая проверка не пишет `updated_at`, равное значение `meta` не обновляется, поэтому `read_revision` и кэш графа не сбрасываются. Эффект на нагрузке не замерен. Правила — [архитектура графа](../architecture/graph.md).

**Направление исправления по пользе.** 1) Не ставить граф после индексации без изменений, ждать паузы в правках и ограничить частоту перестроек проекта; не сбрасывать кэш графа из-за `updated_at`. 2) Публикация с одной ревизией на транзакцию, крупным `cache_size`, вставкой в порядке ключа и пересозданием индексов рёбер после массовой вставки — ожидаемо ≈6 ГБ → ≈0,4 ГБ, не проверено. 3) Частичное обновление: удалять и вставлять только строки изменённых документов и их связей, готовить граф из индекса, а не с диска (НФТ-7, слова автора: «Надо блять обновлять»). 4) Довести ISS-94.

## Метод исследования WebView2 3.6.1

Исследование 02-11-2026 разделяет установленный рабочий процесс и изолированный стенд: CPU чужих WebView не складывается с bars, исчезнувшие/новые PID и фоновые компиляторы учитываются явно. Счётчики ОС снимаются до/после одинаковых интервалов видимого и скрытого окна; CPU приводится к одному логическому процессору, память — private commit/Working Set, чтение — только логическое.

Для таймеров используется существующий `workspace_probe` с продуктовым `ui/dist`, FakeProvider и отдельным профилем внутри `.bars/`. CDP доступен только у собственного стенда на loopback. Инструментирование до загрузки UI считает регистрации и исполнения JS-таймеров/кадров, вызовы IPC и сообщения physics worker; отдельные серии без обёрток проверяют влияние измерителя на CPU. Сначала прогрев и завершение индексации, затем чередование видимого/скрытого окна и возврат. Рабочий bars не перезапускается; не выполняются записи его настроек, буферов или SQLite. Изолированный профиль не доказывает исправность рабочего окна или причину прежнего исчезновения renderer.

Для ISS-102 проверяются доступные события Application Error/Windows Error Reporting и наличие Crashpad-отчётов именно профиля bars. Отсутствие событий — недостаток доказательств, а не доказательство отсутствия сбоя. Текущая версия Runtime и время появления её каталога сопоставляются с прежним наблюдением без вывода о причинности. Выбор продуктового усыпления и восстановления остаётся следующим проектированием: сохранить Т-1, Т-29, Т-40 и НФТ-5, уведомления и свежий снимок при показе.

### Отсутствующий renderer: что удалось установить

В [снимке диагностики](webview-lifecycle-2026-11-02/metadata.json) проверены 40 событий Application 1000/1001/1002 за 30-10–02-11-2026: совпадений `bars.exe`/`msedgewebview2.exe` нет. Каталог Crashpad `reports` стандартного профиля bars существует, файлов нет. Путь через `FailureReportFolderPath` рабочего контроллера не запрашивался; очищенный/иной каталог или незарегистрированный сбой этим не исключены. Прежние PID уже завершились, дампа и событий жизненного цикла за тот эпизод нет; тип отказа и момент потери WebView ретроспективно не устанавливаются.

Каталог Runtime 156.0.4314.58 появился 01-11-2026 в 16:19:55 UTC, после старта прежнего bars и до наблюдения отсутствующих процессов. Это лишь временное совпадение. [Документация Microsoft о поставке Runtime](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution) описывает переход работающего приложения на новую версию после перезапуска; наличие обновления не доказывает принудительное завершение старого браузера. Нельзя объявлять обновление, OOM, драйвер или ISS-101 причиной ISS-102 без соответствующего события/дампа.

В `crates/bars-app/src/window.rs` путь показа проверяет существование нативного окна; здоровье WebView не проверяется. В коде bars и используемом Wry 0.57.0 не найдены подписки на `ProcessFailed`/`BrowserProcessExited`, отдельная диагностика или восстановление контроллера. Это объясняет пробел наблюдаемости и отсутствие предусмотренного восстановления при отказе, но не первоначальную причину старого отказа. По [контракту событий WebView2](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-related-events) выход browser, выход renderer и зависание различаются; browser-exit требует пересоздания связанных контроллеров, renderer-exit допускает иной путь. Живой HWND и ответ воркера не подтверждают здоровье renderer.

После серий и профилей выполнен `Browser.crash` только через CDP изолированного стенда. Через 5 с в живом дереве остался native PID 35504 и тот же видимый HWND 16651554. Состояние до/после сохранено в `isolated.json`, `fault_injection`; первый измеритель не искал прежних потомков независимо от уже умершего browser, поэтому один этот снимок не доказывает завершение возможных осиротевших renderer/GPU. Визуальный белый экран и доступность воркера после отказа не проверялись. Собственный host затем завершён, поздняя проверка процессов по профилю не нашла остатков; рабочий bars PID 63148 не затронут. Отдельный renderer-crash, OOM и зависание не инжектировались.

В [отдельном повторе отказа](webview-lifecycle-2026-11-02/fault.json) использован тот же exe по SHA-256. До crash сохранены семь PID+точное время старта, после 5 с ожидания каждый проверен независимо от родства: browser, renderer, GPU и оба utility отсутствуют; прежние native и HWND живы, crashpad-handler ещё жив. Поэтому `expected_failure_observed=false` для строгого условия «все WebView-потомки завершились, прежний native жив» — корректный отрицательный результат, а `success=true` означает завершение сбора данных. Повтор подтверждает сочетание «HWND есть, browser/renderer нет», но не полное исчезновение всех служебных процессов. Поздний контроль `cleanup` после завершения собственного host не нашёл ни одного из семи прежних экземпляров. Историческая причина ISS-102 этим по-прежнему не установлена.

В [незавершённом промежуточном повторе](webview-lifecycle-2026-11-02/fault-incomplete.json) после crash helper не нашёл native PID 20928 и прекратил сбор; причина и точный момент выхода host не установлены. Этот опыт не включён в успешные census и не позволяет обещать, что native обязательно переживает browser-crash. Старый `success=true` был выставлен до неудачного финального снимка; `valid=false` явно помечает неполный результат. Измеритель исправлен: допускает исчезнувший host при независимом census и ставит `success=false` при ошибке сбора. Рабочее приложение этот повтор не затрагивал.

### Основания для следующего проектирования

Рекомендация исследователя: сначала согласовать режим скрытого окна с остановкой ненужных интервалов и декоративной работы, сохраняя самостоятельные уведомления и запись; усыпление оценивать отдельным вариантом. [TrySuspend/Resume](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_3?view=webview2-1.0.4022.49) останавливает таймеры/анимации, но вместе с ними остановятся и нужные JS-обработчики. Успех операции асинхронный; нельзя считать один `hide` или запрос усыпления подтверждением состояния.

До усыпления/пересоздания нужен проект сохранения буферов и конфликтов по [модели редактора](../features/knowledge-base/editor-design.md): `dirty`, `saving`, `conflict`, `deleted`, черновик настроек, несколько окон, выход во время записи. Существующая схема уведомлений читает события в JS каждые 10 с в скрытом окне; простая остановка всего WebView задержит эти обновления. Полный снимок и аренда наблюдения при возврате должны подчиняться [архитектуре обновлений окон](../architecture/window-updates.md).

Для отказов нужен журнал без текстов документов: host/window label, версия Runtime, PID/роль, тип/причина/код выхода, стадии создания/navigation/готовности и признак несохранённого. После renderer-exit и browser-exit — разные действия, ограниченные повторы, доступная пользователю диагностика и сохранение общего воркера. Потерянный только в памяти буфер после crash нельзя обещать восстановить обычным reload. Это предложения для 3.6.2, не новые требования автора и не выполненная оптимизация 3.6.3.

### Как повторить исследование WebView2

Подготовить [окружение сборки](build.md), единственный кэш `C:/bt/bars`; собрать `ui/dist`, затем `cargo build -j 2 --workspace --example workspace_probe` и встроить `crates/bars-app/examples/workspace_probe.manifest` через `mt.exe`. `cargo rustc` не поддерживает `--workspace`; сборка примера в одиночном пакете меняет объединение features и не нужна. Ни профили WebView, ни exe, ни логи сборки в архив измерений не входят.

Из корня проекта, последовательно и без собственных сборок во время серий:

```powershell
pwsh -NoProfile -File docs/knowledge/webview-lifecycle-2026-11-02/installed.ps1 -RootId (Get-Process bars).Id -Output docs/knowledge/webview-lifecycle-2026-11-02/installed.json
node docs/knowledge/webview-lifecycle-2026-11-02/measure.mjs
node docs/knowledge/webview-lifecycle-2026-11-02/summarize.mjs
```

Первая команда предназначена только для одного запущенного установленного bars и временно показывает его окно; скрипт сверяет путь, исходную видимость и возвращает её в `finally`. Изолированный стенд копирует готовый exe внутрь `.bars/`, создаёт свой профиль, проверяет владельца loopback-CDP и в конце намеренно вызывает `Browser.crash` только у этого браузера. Этот отказ выполняется после ресурсных серий. Повтор затрагивает файлы результатов; прежние данные сохраняют отдельно перед новым исследованием.

`node docs/knowledge/webview-lifecycle-2026-11-02/measure.mjs --fault-only` повторяет только отказ, копируя сохранённый измеренный exe из `.bars/webview-361/` в отдельный профиль и записывая `fault.json`. Независимый census сверяет PID и время старта, даже если родитель уже умер; отсутствие native также допускается как наблюдаемый исход. UTF-8 stdout задан явно. После ревью `installed.ps1` проверяет минимизацию на обеих границах, а восстановление видимости и минимизации сообщает отдельно; пользовательское изменение минимизации не маскируется одним `restored=true`. Старые сырые счётчики сохранены, исключение загрязнённой серии выполняет пересчёт, а не ручная правка чисел.

## Опрос окон и обходы каталогов

В реализации 3.5.7 секундный обход и передача дерева заменены [общим снимком и внутренней подпиской](../architecture/window-updates.md), по OQ-232. Сборщик использует настоящий `tree_io::read_tree` и прежние read-only методы `tree/status` только для изменившихся частей или контрольной сверки. Несколько окон проекта разделяют сборку и кэш; данные редактора не заменяются. Отдельное окно подписано на дерево и метаданные для `[[`, без локального debounce и общего опроса.

Видимое главное окно сохраняет секундные `activity/operation_events`; скрытое — те же уведомления раз в 10 секунд. Фактическая видимость host передаётся отдельно от `document.hidden`, останавливая также опрос и раскладку графа. Модели читаются по экрану/операциям. При всех скрытых окнах координатор освобождает запись и прекращает обходы; при показе получает полный снимок. Тесты подтверждают singleflight, вытеснение без сброса ревизий, ошибки, структурные события и порядок аренды/привязки.

[Сравнение настоящих окон 01-11-2026](window-poll-2026-10-28.md) на 10 000 документах: по три минутных серии на сценарий и версию, без компиляторов. Чтения дерева уменьшились с 61 до двух за серию для одного и четырёх окон, до нуля при скрытии. Медианный native CPU видимого окна — 12,99 → 1,02 с/мин; удержание снимка 9,281 МиБ, после скрытия — ноль. Нативные проверки сохранили контрольную свежесть до 2 с и буфер редактора. Debug/FakeProvider, происхождение прежнего UI-артефакта и пределы CPU/IO/RAM описаны в исследовании; общая приёмка памяти этими числами не заменяется.

`audit_schedule_tick` использует один ленивый docs_stamp для всех включённых видов проекта за такт, включая сохранение ошибки обхода. docs_stamp перечисляет пути, размер и mtime, сортирует строки и хеширует список; содержимое файлов не читается. Ошибки логируются, задачи аудитов зарегистрированы в shutdown. Расписание по умолчанию включает «при изменении» только для битых ссылок; экономия трёх обходов применима лишь при включении всех трёх видов.

## Кванты точного расчёта близости

`crates/bars-core/src/graph/build/job.rs` сохраняет Prepared с Dataset и checkpoint в graph_meta для перезапуска. На первом входе создаёт Calculation; между квантами GraphBuildState удерживает Prepared/Calculation в памяти задания. Лёгкая ревизия входов исключает повторное хеширование BLOB, десериализацию и загрузку векторов на неизменившемся продолжении. Двухсекундный лимит относится к advance, а не обслуживанию вокруг него. После отмены сохранённый checkpoint остаётся на диске, память задания освобождается.

До исправления при Q квантах и V байтах векторов повторяемое обслуживание включало порядка Q×V чтения для ключа и Q×V загрузки векторов, плюс Dataset и checkpoint. Теперь этот множитель устранён для удерживаемого активного задания. Это оценка алгоритмического объёма, не физический I/O: кэш ОС, SQLite, повторяемые embed_hash и план SQL меняют фактические числа. Сам точный перебор пар сохраняет прежнюю стоимость и порядок.

Удержание ограничено оценкой 256 МиБ на активное задание; большой набор восстанавливается с диска. Ревизия меняется при записях документов/чанков/векторов и параметров модели/нарезки, включая замену BLOB при прежнем embed_hash; при изменении входов Prepared проверяется полным ключом. Перед публикацией ключ пересчитывается ещё раз. Полный ключ читает доступные BLOB последовательным проходом, отдельно учитывает недостающие ключи. Порог, размер top-k, f64-суммирование и правила ties сохранены.

Проверка: идентичные соседи и оценки для полного запуска, нескольких квантов, отмены/возобновления, удаления чанка и замены вектора; замер загрузки, advance и checkpoint раздельно. Новая реализация параллельно меняется; вывод относится к хешам исходников в отчёте сессии.

## Память моделей и безопасные границы качества

Модельные сессии остаются главным доказанным источником гигабайт private commit в прежних опытах. FP16 embed с rerank на фиксированном срезе дал около 5,0 ГиБ против 6,84 ГиБ FP32 embed; 1200/1200 ответов в матрице корректны, но только 10 из 12 процессов завершены полностью. Это проверка конкретного корпуса, не математическая гарантия одинаковых векторов FP16 и FP32. Подробные ограничения и принятая мера — [исследование памяти](memory.md).

Текущий model_lifecycle уже выгружает embed через 15 минут и rerank через 5 минут простоя по умолчанию; drop выполняется в spawn_blocking. Нельзя повторно предлагать это как отсутствующую реализацию. Агрессивная выгрузка экономит удержание, но читает веса чаще. Постоянный кэш всех векторов тоже требует расчёта: N×dimension×4 байта только полезных f32; для 50 000×1024 это 195,3 МиБ без ключей и контейнеров. Его не стоит добавлять до проверки эффекта последовательного SQL.

Не считать мерами «без потери качества»: отключение rerank, снижение K, обрезание текста, замена точного перебора на ANN, пропуск слоёв графа. Изменение precision требует уже установленного согласия и проверки корпуса. Сериализация моделей может снизить совместный пик, но ухудшить очередь поиска; прежний парный опыт не состоялся, выигрыш не доказан. Увеличение паузы embed ухудшает свежесть; [исследование умолчаний индексации](indexing-defaults.md) показывает небольшой дополнительный выигрыш после 15–30 секунд.

## Измерения, покрытие и следующий проверяемый результат

На отдельном согласованном SQLite-снимке 493 настоящих документов, 5384 узлов и 13111 рёбер выполнено сравнение загрузки: три прямых load — 752,5/771,9/809,4 мс; холодное заполнение кэша — 1120,5 мс; десять попаданий — медиана 0,695 мс, максимум 259,3 мс. Dataset совпал целиком по BLAKE3; удерживается одна и та же Arc. Оценка кэша 48 261 856 байт (46,0 МиБ) вычислена при чтении строк JSON, без повторной сериализации. Это не измеренный Working Set. Общая машина и выброс первого попадания не позволяют обещать такую же задержку каждого обращения. Чтение первого снимка всё ещё существенно; после публикации оно оплачивается прогревом.

Первый диагностический прогон с повторной сериализацией для оценки размера сохранён отдельно: 491 документ, медиана прямой загрузки 782,6 мс, медиана попадания около 0,69 мс. Корпус между прогонами изменился, поэтому разницу холодных загрузок нельзя целиком приписывать удалению сериализации. Оба прохода проверяют совпадение данных внутри своего снимка. Сырые результаты и способ запуска — в отчёте сессии.

Пассивно 25-10-2026 сняты три точки одного bars.exe за 10,35 с: private commit 8,53 ГиБ, Working Set 1,31 ГиБ, прирост логического чтения 288,46 МиБ (27,87 МиБ/с), CPU 1,594 процессорной секунды. Это около 15,4% одного логического процессора, не процент всей машины. Режим приложения и чужая нагрузка не фиксировались; MCP аудита обращался к работающему bars. Снимок не доказывает утечку, простой, принадлежность чтения конкретному методу или соответствие установленного бинарника рабочему дереву. WebView-потомки не включены.

Различать логическое чтение процесса, физический диск, private commit, Working Set и GPU. Для сравнения изменений нужен один корпус и одинаковые запросы: видимое/скрытое окно, четыре окна, повторный поиск, повторный граф, правка документа, полный граф, индексация с поиском, TTL/reload. Сохранять идентичность выдачи, порядка, оценок, областей и свежести; измерять CPU-секунды на работу, I/O, пик/плато памяти и p95 задержки. Рост постоянного кэша нельзя скрывать снижением CPU.

Прочитаны цепочки поиска SQL, запросов/продолжения графа, опроса/дерева, расписания аудитов и lifecycle моделей. У физического графа найдены остановка раскладки и обработка видимости; бесконечная активная физика не установлена. Полное профилирование WebView, редактора, внешних провайдеров, каждого MCP-метода и драйверных выделений не выполнялось. Старые скорости построения нельзя переносить на новый checkpoint-код.

Открытый вопрос общего ресурсного профиля — OQ-191; установочная приёмка памяти остаётся OQ-155. Архив метода, хешей исходников и прежних трёх пассивных точек — `docs/chats/2026-10-25-performance-audit/report.md`; результаты и пределы прежнего замера приведены в этом исследовании. Код 2.2.9 адресует также механизм ISS-101, но окончательная приёмка остановлена автором; величину выигрыша нельзя переносить между корпусами и версиями без сравнения.
