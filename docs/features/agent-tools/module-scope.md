# Выбор модулей агентом — модули проекта в инструкции и описании modules, разбивка выдачи по модулям, замер на бенче

Статус: проект от 23-10-2026, реализации нет. Четыре части по просьбе автора: модули проекта в стартовой инструкции и описании `modules`, новые формулировки выбора области, разбивка выдачи по модулям, замер на бенче. Срок ожидания модулей, порог силы формулировок и судьба `chats` в поиске по умолчанию решены агентом по поручению автора 23-10-2026; обоснования — в разделах о них.

## Зачем агенту видеть модули проекта

Агенты почти не сужают поиск по модулям (Т-14). Счёт по журналу MCP `~/.bars/mcp-statistics.sqlite3` за 18–22-10-2026 — все 226 вызовов `bars_rag_search`:

| Проект | Без фильтра | `modules` | `files` |
|---|---|---|---|
| bars-project | 123 | 26 | 27 |
| overdrive-bots | 43 | 6 | 0 |
| всего (с одним вызовом без проекта) | 167 (74%) | 32 (14%) | 27 (12%) |

Из 50 сессий с поиском `bars_projects` вызывали 11, ни разу не сузили область 22. При этом больше половины корпуса — история сессий: `chats` — 206 из 372 документов bars-project и 149 из 330 в overdrive-bots. Поиск без фильтра по вопросу о текущем поведении конкурирует с ходом прошлых сессий.

Прежний разбор 14 цепочек вызовов ([качество вызовов bars агентами](../../knowledge/agent-tool-usage-2026-10-18.md)) счёл редкое использование `modules` не недостатком, но причинный эффект фильтра не измерял. Гипотеза автора 23-10-2026 — без фильтра падает точность. Её проверяет замер на бенче; сила новых формулировок зависит от его результата.

## Почему агенты не выбирают модуль

1. **Имён модулей нет в контексте.** Стартовая инструкция — константа `INSTRUCTIONS` в `crates/bars-mcp/src/instructions.rs`, описание поля `modules` в `SearchArgs` тоже статично. Агент начинает сессию, не зная, какие модули есть в проекте; чтобы узнать, нужен отдельный вызов `bars_projects`, который выводит все зарегистрированные проекты.
2. **Формулировки делают нормой весь проект.** «Для межслойной задачи ищи по всему проекту», «Filters are optional, not a quota», «A cross-layer task needs no filter» повторяются в инструкции, описании инструмента, `BARS_INSTRUCTION.md` и обоих skills. Почти любую задачу модель может счесть межслойной.
3. **Примеры только для редких случаев.** Фильтр показан на `backlog` и `chats`; основные источники — `features`, `architecture`, `adr` — ни в одном примере не встречаются.

## Модули проекта в стартовой инструкции bars-mcp

Стартовая инструкция (Т-27) собирается при `initialize`, а не берётся из константы. rmcp 3.5.1 позволяет переопределить асинхронный `ServerHandler::initialize`.

- **Откуда данные.** `bars-mcp` спрашивает у воркера проект сессии по cwd (Т-15) и его модули: имя, число документов, `title` из `Index.md` модуля, если файл есть. Запрос только читает реестр и индекс, модели не загружает. Метод IPC выбирается при реализации; данные те же, что у `bars_projects`, плюс `title`.
- **Срок ожидания — 3 с на весь запрос.** Обычно воркер уже работает (автозапуск при входе в систему), и ответ из реестра приходит за миллисекунды. Если воркера нет, `bars-mcp` запускает его, как перед первым вызовом, но ждёт только остаток трёх секунд, а не `LAUNCH_DEADLINE` (15 с): `initialize` задерживает старт сессии агента, и три секунды на это — заметная, но терпимая цена. Не успел, проект не найден или ошибка — инструкция без списка, со строкой «modules — папки первого уровня docs-root, имена даёт bars_projects». Загрузки модели запрос не ждёт.
- **Вид строки.** `Модули проекта <имя>: . (4), adr (6), architecture (11), …`. Порядок по имени, корневой `.` первым. Число документов помогает понять, где большая история.
- **Предел Т-27.** Вся инструкция не длиннее 2 000 знаков. Статическая часть сокращается так, чтобы на список оставалось не меньше 300 знаков. Если список не помещается, модули берутся по убыванию числа документов, остаток — «и ещё N — bars_projects».
- **Инструкция фиксируется на сессию.** Модуль, созданный позже, в ней не появится. Поэтому ошибка `invalid_params` о неизвестном модуле перечисляет существующие: `неизвестный модуль models; есть: ., adr, architecture, …`. Сейчас ошибка списка не даёт.

## Модули проекта в описании параметра modules

`list_tools` тоже собирается для соединения: описание поля `modules` у `bars_rag_search`, `bars_get_similar` и `bars_get_duplicates` дополняется модулями проекта сессии с назначением — `title` их `Index.md`, обрезанным до 60 знаков: `features — Фичи bars — оглавление`. Для чужой раскладки (`decisions`, `kii`, `_online`) назначение видно только отсюда.

- Данные берутся из того же запроса, что и при `initialize`, один раз на соединение. Если он не удался, `list_tools` повторяет его один раз с тем же сроком 3 с: воркер, запущенный при `initialize`, к этому времени часто уже готов. Снова не удался — прежнее статичное описание.
- Список идёт в текст описания, а не в `enum` схемы. `enum` клиент проверяет сам: он отклонил бы модуль, созданный во время сессии, и модули другого проекта, переданного в `project`.
- Описание оговаривает, что список относится к проекту сессии; для другого проекта имена даёт `bars_projects`.

## Формулировки выбора области поиска

Обязательной частоты фильтрации по-прежнему нет: это решение сохраняется из [выбора операции и области агентом](../docs-convention/delivery.md). Меняется умолчание: сначала выбрать модуль по виду нужного знания, весь проект — когда видов несколько или неясно, где искать.

Черновик пункта стартовой инструкции (вместе со списком модулей bars-project — 1 803 знака):

```text
- Контекст неизвестен: bars_rag_search, предметный вопрос на языке пользователя. Выбери modules по виду знания: поведение и контракты — features, устройство — architecture, решения — adr, баги и идеи — backlog, история — chats. Весь проект — когда нужно несколько видов или неясно, где искать; слабая выдача из модуля — расширь область.
- Модули проекта bars-project: . (4), adr (6), architecture (11), backlog (3), chats (206), features (76), knowledge (51), manual (15). Вложенная папка — не модуль.
- files — выбранные индексируемые документы, пути от docs-root без docs/. Не угадывай список.
```

Сокращения статической части, чтобы освободить место: пример `files` уходит в skills и описание параметра; строка раскладки перечисляет папки без пояснений, которые теперь есть в пункте о выборе модуля; про `bars_projects` остаётся «другой проект — его модули даёт bars_projects».

Сила формулировки зависит от бенча, порог — в разделе о замере. Прошёл порог — «выбери modules» остаётся умолчанием. Не прошёл — инструкция только перечисляет модули и виды знания, без побуждения сужать: имена модулей полезны и без него.

Те же правила и примеры на `features`, `architecture`, `adr` переносятся во все каналы доставки: описание `SearchArgs` и инструмента, `BARS_INSTRUCTION.md` (обе копии), skills `bars-docs` и `bars-session-log`, [инструменты MCP](mcp-tools.md), раздел о выборе области в документе доставки.

## Разбивка выдачи bars_rag_search по модулям

Ответ поиска показывает, в какой области искали и из каких модулей пришли кандидаты. По этой строке агент видит, что выдачу забивает история, и сужает её следующим вызовом.

- **Текст.** В блок `APPLIED PARAMETERS` добавляются `scope: whole project` или `scope: modules features, adr` / `files …` и `by_module: candidates chats 14, features 9, knowledge 7; results features 3, chats 2`. Кандидаты — список до rerank (`candidates`), результаты — выданные фрагменты.
- **Подсказка.** Только при поиске по всему проекту, если результаты пришли из двух и больше модулей: `Results span several modules; pass modules to narrow the scope.` Служебный текст рендерера — на английском, по правилу проекта. Модуль за агента подсказка не выбирает.
- **JSON.** `applied.scope` (`modules`, `files`) и `by_module` (`candidates`, `results` — имя модуля → число). Поля добавляются, существующие не меняются, поэтому ответ без `mode` остаётся совместимым ([гибридный поиск](../search/hybrid-search.md)).
- **mix и graph.** `by_module` считается по основной выдаче; связанные источники не входят.

Ядро поиска уже знает модуль каждого кандидата; счёт добавляется в выход `search` и в `applied` журнала MCP.

## Замер на бенче: точнее ли выдача с фильтром по модулю

Вопрос: насколько выдача с правильным модулем точнее поиска по всему проекту и сколько теряется, если агент выбрал один модуль, а ответ лежит в нескольких. Методика и инструмент — [бенч качества поиска](../../knowledge/search-quality.md) (`bench_quality`).

- **Корпус.** Свежие снимки `docs/` bars-project и overdrive-bots через `bench_quality prepare`: в обоих `chats` — больше 45% документов.
- **Вопросы.** Набор `bars.json` (24 вопроса, уровень документов) сверяется со снимком через `validate` и дополняется до 40 положительных вопросов с эталонными разделами на проект. Для overdrive-bots набор составляется заново: `overdrive.json` размечен по ai-mutiplayer-bots. Вопросы и эталоны пишутся до просмотра рангов; разделение на подбор и проверку — как в исходной методике.
- **Варианты области** (запрос, кандидаты, rerank и порог одинаковы):
  - A — весь проект;
  - B — модули всех эталонных разделов вопроса, верхняя граница выигрыша;
  - C — один модуль первого эталонного раздела, как агент, выбравший один вид знания;
  - D — весь проект без `chats` для вопросов, эталон которых не в `chats`. Проверяет решение оставить историю в поиске по умолчанию.
- **Метрики.** Hit@3, MRR@10, nDCG@10 по разделам; доля фрагментов `chats` в первых пяти для вопросов не об истории; потери C на вопросах с эталонами в разных модулях.
- **Изменение бенча.** `bench_quality run` получает вариант области; модуль эталона выводится из его пути.
- **Порог для умолчания «выбери modules».** На проверочной части должны выполниться оба условия:
  1. B лучше A хотя бы на 5 процентных пунктов Hit@3 или на 0,05 MRR@10 — фильтр вообще даёт выигрыш, ради которого стоит менять поведение агентов;
  2. C хуже A не больше чем на 1 процентный пункт Hit@3 на всём наборе — агент, выбравший один модуль, не теряет ответы, лежащие в нескольких. Этот допуск взят из критерия умолчаний исходного бенча.

  Если выигрыш B есть, но C теряет больше, остаётся нейтральная формулировка: настоящий агент выбирает один вид знания, и верхняя граница B для него недостижима.

Результат — новый документ `docs/knowledge/` с датой замера.

## Порядок работ и приёмка выбора модулей

1. Замер на бенче — он задаёт силу формулировок.
2. Модули в `initialize` и описании `modules`, список модулей в ошибке о неизвестном модуле.
3. `scope` и `by_module` в выдаче, текст и JSON.
4. Формулировки во всех каналах доставки, обновление [инструментов MCP](mcp-tools.md).
5. Через неделю работы — повторный счёт по журналу MCP тем же способом, что в разделе о причинах: доля вызовов с `modules`, доля сессий с `bars_projects`. Это наблюдение, а не норма частоты.

Проверки:

- `cargo test -p bars-mcp`: `initialize` в зарегистрированном проекте содержит строку модулей и не длиннее 2 000 знаков, в том числе на проекте с 30 модулями; без воркера и по истечении срока — инструкция без списка в пределах срока; `list_tools` содержит модули в описании `modules`.
- Ошибка о неизвестном модуле перечисляет существующие.
- Рендер `search`: строки `scope` и `by_module`, подсказка только при поиске по всему проекту из нескольких модулей; поля JSON.
- Отчёт бенча с вариантами A–D.
- Доставка инструкции и skills — существующими скриптами из документа доставки.

## История сессий chats остаётся в поиске по умолчанию

`chats` не исключается из поиска по всему проекту и не получает пониженный вес. Причины:

- Т-14 задаёт пустой выбор как весь проект; молча убранный модуль нарушил бы это и запутал агента, который ищет итоги прошлой сессии без фильтра.
- `chats` — модуль только в рекомендуемой раскладке; в чужом проекте папка с таким именем может хранить что угодно, а другие проекты держат историю под иным именем. Правило по имени папки было бы ненадёжным.
- Проблему решают средства этой работы: агент видит модули и их размер, а `by_module` показывает, что выдачу забивает история.

Вариант D бенча проверяет это решение. Если D лучше A на вопросах не об истории так же, как требует порог для B, вопрос о весе истории поднимается заново отдельной задачей.

## Что не входит в выбор модулей агентом

- Исключение `chats` из поиска по умолчанию или понижение его веса — решено не делать.
- `enum` модулей в схеме параметров.
- Выбор модуля сервером за агента.
- Норма частоты фильтрации.
