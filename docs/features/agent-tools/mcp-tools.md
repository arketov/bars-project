# Инструменты bars для агентов — MCP

Что агент получает через `bars-mcp` (Т-19). Все вызовы выполняет воркер; прокси только пересылает их ([architecture/ipc.md](../../architecture/ipc.md)).

Статус на 10-11-2026: четыре агентских инструмента вместо семнадцати — `bars_search`, `bars_read`, `bars_status`, `bars_audit` — реализованы шагом 5.2.1 по [проекту агентского слоя](agent-layer-project.md); шесть графовых инструментов по-прежнему скрыты настройкой `[mcp] graph_tools` (OQ-162). Ступенчатая выдача поиска — шаг 5.1.1 ([search-staging.md](search-staging.md)). Описания инструментов, их параметров и стартовая инструкция `initialize` — на английском (НФТ-4). Параметра `format` у MCP больше нет: ответы текстовые, JSON остаётся у `bars-cli --json`; `bars_reindex` из MCP ушёл — проверку актуальности запускает `refresh=true` у `bars_status`, полная переиндексация остаётся окну и CLI. Сборка и регрессии этим срезом не прогонялись (запрет автора 05-11-2026); код в main, Sol-ревью трёх раундов без замечаний. Историческое основание замены — [исследование изменений после редактора](../../knowledge/mcp-after-workspace.md) и аудит агентского взаимодействия 10-11-2026.

## Соответствие инструментов MCP функциям окна — Т-37

Все инструменты сопоставлены с действиями человека в [таблице функций окна](window-parity.md). Таблица создана в 3.7.1 и переписана под четыре инструмента шагом 5.2.1; наличие компонента не заменяет проверку пользовательского сценария. Т-37 требует функцию пользователя, а не копию имени инструмента или каждого его аргумента. Физическая карта и анализ GraphRAG имеют отдельные маршруты; панель ссылок и граф — отдельные источники данных.

## Четыре инструмента

| Инструмент | Что вбирает (до 5.2.1) | Что меняется для агента |
|---|---|---|
| `bars_search` | `bars_rag_search`, `bars_text_search`, `bars_get_similar` | Один поиск: по вопросу, по образцу раздела (`like`), все вхождения строки (`occurrences`); область — пути-префиксы `in` вместо `modules`/`files` |
| `bars_read` | `bars_read`, `bars_outline`, `bars_links` | Текст, структура (`view=outline`) или ссылки (`view=links`) одного документа; длинный документ без уточнений возвращается структурой; `under` принимает конец цепочки заголовков |
| `bars_status` | `bars_status`, `bars_projects`, `bars_audit_list`, `bars_new_topics_list` | Одна сводка проекта по частям: проект и модули, индекс, версии прокси и воркера, аудиты, новые темы, граф, у проекта с git worktree — WORKTREES; проверка актуальности — параметром `refresh`; `filter` — поиск по реестру проектов, подпроектов и worktree (Т-50; для проектов и подпроектов написан без проверки сборкой, часть worktree — проект); у ленивого подпроекта вместо остальных частей одна строка «not indexed yet» ([подпроекты](../projects/subprojects.md)) |
| `bars_audit` | `bars_audit_findings`, `bars_audit_run`, `bars_audit_cancel`, `bars_get_duplicates`, `bars_new_topics_get`, `bars_new_topics_check` | Вид и действие параметрами; добавлена сводка находок (`action=summary`); дубли — только находки аудита `duplicates` |

Старые имена удалены без псевдонимов (OQ-299): сессия со старым skill получит «неизвестный инструмент» до перезапуска клиента. Параметры поиска `candidates` и `min_score` агенту больше не отдаются. Проект — имя или путь у всех инструментов, включая аудиты и новые темы (ISS-111). Время в ответах аудитов печатается датой, сырый JSON агенту не отдаётся (ISS-113).

### bars_search — один поиск, три вида запроса

```
bars_search(query?, in?, like?, occurrences?, limit?, cursor?, detail?, project?, wt?, diagnostic?)
```

`wt` (Т-48, проект, реализации нет) есть у всех четырёх инструментов рядом с `project`; смысл — раздел «Проект вызова».

- **Вопрос, слова, номер.** `query` — предметный вопрос на языке пользователя после определения задачи; операторы `"точная фраза"` и `-слово`. Ответ — ступенчатая выдача: короткая шапка, полный текст первых мест, строки и отрывки остальных, слабые совпадения вместо пустого ответа ([search-staging.md](search-staging.md)). `detail` — `auto` (по умолчанию), `full` или `brief`.
- **По образцу раздела.** `like: "путь:строки"` из строки результата (`docs/a.md:12-30`) или ID чанка: похожие разделы **других** документов и список документов, ссылающихся на исходный. Один вызов заменяет пару similar + входящие ссылки; разделы исходного документа в ответ не входят (ISS-26). Близость — косинус, не доказательство дубля: читай оба раздела.
- **Все вхождения строки.** `occurrences: true`: `query` — одна конкретная строка, поиск по сохранённым файлам на диске без embed; ответ — строки `путь:строка:колонка`, продолжение одного документа непрозрачным `cursor`. Регулярное выражение записывается как `/…/`. Пределы узкого запроса и ошибка `too_broad` — в разделе «Узкий запрос occurrences».
- **Область `in`.** Список путей-префиксов: `features`, `features/search`, `adr/0007-one-search-scores.md`. Путь принимается от корня документации и от корня проекта, как печатается в выдаче; вложенная папка работает как папка первого уровня; несколько путей объединяются. Путь, под которым нет документов, — `invalid_params` со списком ближайших. Пустой `in` — весь проект.
- **Диагностика.** `diagnostic=true`: выдача обычная, спрос в «Новых темах» не записывается.

Оператор `path:` в запросе остаётся человеку в окне; агенту область задаёт `in`.

### bars_read — текст, структура и ссылки одного документа

```
bars_read(path, lines? | under?, view?, direction?, cursor?, project?)
```

- **Без `view`, `lines` и `under`** документ до 400 строк возвращается целиком с номерами строк; длиннее — структурой с подсказкой, как прочитать часть (`lines`, `under`) или весь текст (`view: "text"`). Правило «длинный план сначала со структуры» выполняется само.
- **`lines`** — часть по исходным номерам: `98-104`, одна строка `98`, до конца `98-`; границы входят, номера — настоящие.
- **`under`** — раздел по цепочке заголовков; достаточно конца цепочки (`Схема баллов` вместо `Поиск/Схема баллов`). Ни одного или несколько разных совпадений — `invalid_params` со списком ближайших заголовков и их строк (ISS-112). Вложенные разделы входят; несколько повторов цепочки выдаются все, по одному блоку на раздел.
- **`view: "outline"`** — заголовки с номерами строк; **`view: "links"`** со `direction: in|out` — ссылки документа, свежая сверка с диска, продолжение через `cursor`.
- **Путь папки** (без `.md` на конце; пустой путь и `.` — корень документации) вместо документа — список её подпапок и документов (раздел «Содержимое папки в bars_read», OQ-320).
- Путь — по общим правилам ниже; читается только `.md` внутри корня проекта, с диска, а не из несохранённого буфера окна.

### bars_status — одна сводка, части с собственными ошибками

```
bars_status(project?, all?, refresh?, filter?, wt?)
```

Ответ — части с явными границами: `PROJECT` (путь, корень документации, модули с числом документов и назначением из оглавлений; у подпроекта — составное имя `главный/путь`, `subproject_of` и происхождение, у главного — список его подпроектов), `WORKTREES` (у проекта с живыми git worktree: имя, ветка, путь, состояние дельты; Т-48, проект, реализации нет), `INDEX` (состояние, обновление, очередь, модели, ошибки; при `reindex_required` — напоминание, что переиндексацию начинает пользователь), `VERSIONS` (версии и сборки прокси и воркера с предупреждением при расхождении, ISS-117), `AUDITS` (вид, состояние, дата словами, число находок), `NEW TOPICS` (счётчик тем), `GRAPH`. Ошибка одной части печатается в этой части и не отменяет остальные (ISS-110); неразрешимый проект — ошибка вызова. При `all=true` часть PROJECT — реестр всех проектов, а аудиты и темы не выводятся: они относятся к одному проекту. `refresh=true` запускает проверку актуальности индекса (то, что делал `bars_reindex` без `full`); ход виден в части INDEX. `filter=text` (Т-50; написано без проверки сборкой, совпадение по worktree — шаги 6.3.x) — подстрока без учёта регистра по имени, составному имени и пути: часть PROJECT содержит только совпавшие записи реестра с подпроектами и worktree, остальные части не выводятся (вместо них строка с подсказкой повторить вызов с `project=`), `VERSIONS` остаётся; `filter` вместе с `project` или `refresh=true` — `invalid_params`, с `all=true` равен одному `filter`. Ленивый подпроект (индекс ещё не требовали) при `bars_status` без `refresh` не индексируется: выводятся PROJECT и INDEX с состоянием `lazy` и строка «not indexed yet», `refresh=true` — первое обращение. Форма ответа, правила совпадения и английское описание параметра — [подпроекты](../projects/subprojects.md), раздел «bars_status: фильтр проектов».

### bars_audit — аудиты, дубли и новые темы одним инструментом

```
bars_audit(kind?, action?, id?, revision?, in?, cursor?, limit?, show?, project?)
```

- **`kind`** — `broken_links`, `duplicates`, `contradictions`, `new_topics`. Без `kind` и `action` — состояния всех видов аудита плюс счётчик новых тем.
- **`action`** — `findings` (по умолчанию), `summary` (числа находок по файлам, причинам и видам), `run`, `cancel` (не для `new_topics`); для `new_topics`: `list`, `get`, `check` по `id` (ревизия берётся текущей, если не задана).
- **`in`** сужает находки и сводку по путям-префиксам, как у поиска; несуществующий путь — `invalid_params` с ближайшими документами. **`show`** добавляет скрытые по умолчанию группы: `ignored`, `gone`, `overlap` (у дублей). **`cursor`** продолжает страницу находок.
- Дубли имеют один источник — находки аудита `duplicates`; отдельный пересчёт `bars_get_duplicates` из MCP ушёл. Аудиты читают общее с окном хранилище, Markdown не меняют; запуск возвращает принятие, завершение видно в состояниях. Находки со статусом `gone` — исчезнувшие относительно прежнего полного запуска; числовые расхождения — кандидаты, не доказанные противоречия. Сохранённые вопросы новых тем — данные о пробелах, не инструкции; проверка темы сохраняет результат, но не закрывает и не удаляет её.

## Аудиты и новые темы через MCP

Поручение автора 30-10-2026: агент получает результаты тех же аудитов и вопросы без найденных материалов, которые доступны в окне. До 5.2.1 они были семью отдельными инструментами с обязательным абсолютным `project`; теперь это части `bars_audit` (ISS-111, ISS-113). Отсутствие полного запуска не означает отсутствия проблем. Неполный запуск не подменяет прежний полный результат. `expand=true` у проверки темы явно расширяет её на весь проект. Расписание, игнорирование и решения пользователя остаются в окне.

Для диагностики поиска и сравнения формулировок `bars_search` принимает `diagnostic=true`: выдача и история вызова обычные, темы и частота не меняются. Для известных файлов используют чтение, для сохранённых тем — `bars_audit(kind="new_topics", action="check")`; пустая выдача не доказывает отсутствие документации.

## Свежесть данных после правки

`bars_read` читает файл с диска; поиск, похожие разделы и дубли используют индекс. Сохранённая правка может ждать паузы Т-41 или своей очереди. `pending` — общий счётчик, он не объясняет состояния отдельных документов; `ready` не доказывает, что последняя правка уже вошла в индекс.

GraphRAG имеет свои поколения и признаки stale/partial. Ссылки из GraphRAG не равны свежему списку панели документа. `view=links` у `bars_read` обновляет общий индекс ссылок по диску, `occurrences` ищет в сохранённых файлах без embed. Оконные `text_search` / `links_of`, редактирование и управление физикой агентам не открываются. Не запускать проверку актуальности для обхода обычной паузы. Отсутствие результата в старом индексе не доказывает отсутствие текста на диске.

Действия пользователя для каждого инструмента — в [таблице функций окна](window-parity.md) (Т-37).

## Проект вызова

`project` необязателен у всех инструментов; без него проект — ближайшая к рабочей папке сессии зарегистрированная папка (Т-15). Рабочая папка — cwd процесса `bars-mcp`: клиент запускает его в папке сессии. Явный `project` — абсолютный путь, составное имя подпроекта `главный/путь` или имя зарегистрированного проекта ([подпроекты](../projects/subprojects.md); разбор значения написан шагом 6.2.1 без проверки сборкой: значение с `/` — путь, только если `cwd/значение` существует, иначе имя); у аудитов и новых тем имя или путь принимается наравне с остальными (ISS-111).

Параметр `wt` (Т-48; написано шагом 6.3.5 без проверки сборкой) выбирает git worktree проекта вызова: имя папки записи `.git/worktrees/<имя>`, абсолютный путь рабочей копии или `"."` — основной checkout; имя ветки не принимается. Без `wt` значение берётся из рабочей папки сессии: внутри живого worktree проекта — этот worktree (поиск по нему видит правки рабочей копии), иначе основной checkout. Явный `project`, не равный владельцу копии, неявного `wt` не даёт. Неизвестное имя — ошибка `worktree_not_found` со списком worktree и их веток. Правила и дельта — [git worktree как вид проекта](../projects/worktrees.md). Если проект не найден, инструмент возвращает ошибку с подсказкой зарегистрировать проект.

## Пути документов во всех инструментах — OQ-169, ISS-25, ISS-89, ISS-90

Реализовано 28-10-2026 (шаг 4.2.3) и сохранено в 5.2.1: обе формы пути на входе, исправленный путь и список модулей в ошибках, граница чтения проектом. Не реализовано: печать путей от корня документации и поле `doc_path` в JSON — выдача печатает путь от корня проекта.

**Две формы на входе.** Каждый вход, принимающий путь документа, понимает обе формы: от корня документации (`features/agent-tools/mcp-tools.md`) и от корня проекта (`docs/features/agent-tools/mcp-tools.md`). Входы: `path` у `bars_read`; префиксы области `in` у `bars_search` и `bars_audit`; `like` принимает путь как печатается в выдаче. Разделители `\` и `/` равнозначны; `./x.md` всегда отсчитывается от корня проекта.

**Исправленный путь в ошибке.** Неизвестный файл или область не заканчивается голой фразой: `invalid_params` со списком до трёх ближайших документов индекса (файл) или существующих путей (область `in`). Вид ошибки не меняется.

**Чтение только внутри проекта — решение автора по OQ-169, 23-10-2026.** `bars_read` работает только внутри корня проекта вызова. Проверка идёт до обращения к диску: путь нормализуется лексически, кандидат канонизируется, результат обязан лежать внутри канонического корня; `../`, абсолютный путь снаружи и symlink наружу — `invalid_params` без сведений о файле снаружи. Те же правила у `bars-cli read`.

## Узкий запрос occurrences — пределы и ошибка too_broad

Слова автора 06-11-2026: «А text_search надо тогда разрешить grep в него передавать но с ограничениями чтоб бот не делал сильных рекурсий и слишком много "или". И возвращать ошибку мол для широкого поиска используй раг». Поиск в bars один — `bars_search` по вопросу ([ADR-0007](../../adr/0007-one-search-scores.md)); режим `occurrences` находит все вхождения одной конкретной строки на диске: переименование, полный список мест, только что записанный текст (ISS-109). Проверка стоит на агентском методе `disk_text`, до обхода диска; оконный и CLI-поиск «В тексте» её не применяют. Разбор шаблона — AST `regex-syntax` 0.8; возвращается первая сработавшая причина.

| Правило | Предел | Код `reason` |
|---|---|---|
| Литерал (`regex=false`) | после обрезки пробелов не меньше 3 знаков и хотя бы одна буква или цифра | `literal_too_short` |
| Длина regex | не больше 256 байт | `regex_too_long` |
| Варианты `\|` | не больше 4 веток во всём шаблоне; `\|` внутри `[...]` не считается | `too_many_branches` |
| Вложенность групп | не больше 2 уровней, `(?:…)` тоже группа | `groups_too_deep` |
| Повтор внутри повтора | запрещён, в том числе `?`: `(a+)+`, `(\w+\s)*`, `(?:ab?)+` | `nested_repetition` |
| Счётчик `{n}`, `{n,m}`, `{n,}` | не больше 64 | `repeat_too_large` |
| Неограниченные `*`, `+`, `{n,}` | не больше 2 | `too_many_unbounded` |
| Обязательный литерал | в каждой ветке подряд идущий кусок от 3 знаков с буквой или цифрой; флаги, якоря и пустые узлы его не рвут; повтор с минимумом 0 его не даёт | `no_anchor` |

Проходят: литералы `some_option`, `Т-39`; regex `ISS-1[0-9]{2}`, `Т-3\d`, `OQ-\d{3}`, `foo|bar|baz|qux`, `рекомендаци\w*`, `(?i)ошибка`, `foo.*bar`, `^#{1,3} Ошибки`. Отклоняются: `foo|bar|baz|qux|quux` и `(a|b|c)(d|e|f)` — ветки; `((foo(bar)))` — группы; `(a+)+` — повтор в повторе; `o{1000}` — счётчик; `foo.*bar.*baz.*` — неограниченные; `.*`, `\w+`, `^`, `(a|b)*c`, `T-\d+`, `foo|.*`, `[0-9a-f]{64}` — нет литерала; литералы `x`, `ab`, `---` — коротко. Пустой, длиннее 8192 байт и ошибочный шаблон (`[`) по-прежнему отклоняет общий matcher: `invalid_regex` остаётся отдельной ошибкой.

Ошибка — `invalid_params`, `data`: `{"kind":"too_broad","reason":"<код>","limit":N,"actual":N?,"use":"bars_search"}`; текст ошибки отсылает к поиску по вопросу. MCP печатает вид из `data.kind`: агент видит `Ошибка bars (too_broad): …`, так же `invalid_regex`. Продолжение (`cursor`) передаёт тот же запрос и проходит ту же проверку; область `in` пределы не ослабляет.

## Ссылки одного документа — view=links у bars_read

Основа — общий [индекс ссылок](../knowledge-base/link-index.md): `LinkIndex::refresh` и разрешение адресатов по документам проекта. Перед каждым вызовом индекс обновляется по диску под существующим замком; ошибка сверки возвращается как ошибка инструмента. Старый результат не выдаётся как свежий.

| Часть | Контракт |
|---|---|
| Вход | `project?`, `path`, `direction=out` (`in|out`), непрозрачный `cursor?` для продолжения |
| Путь | Документ в любой из двух форм; выход за корень проекта или не `.md` — `invalid_params` |
| Исходящая запись | `строка: текст → адресат` с пометкой `BROKEN` для битого |
| Входящая запись | `источник:строка → this document` |
| Порядок | Incoming: source/line; outgoing: line/порядковый номер в строке. Детерминирован |
| Курсор | Связан с проектом, документом, направлением и снимком ссылок; изменение снимка — `stale_cursor`, начать сначала |

`known=false` в шапке означает отсутствие документа в допустимом наборе файлов, а не доказанное отсутствие входящих ссылок. Длинные поля обрезаются с пометкой `(fields truncated)`; полный оригинал читается `bars_read`. Внешние URL не открываются.

## Содержимое папки в bars_read — аналог ls, проект OQ-320

Статус: реализовано 12-11-2026, не проверено сборкой (воркер `handler/folder.rs`, `ReadParams.order`/`cursor`, `ReadOutput.folder`, общий текст `folder_text` для MCP и `bars-cli read`). Решение автора по OQ-320 заменяет отдельный инструмент `bars_list` из OQ-157: просмотр папки — путь папки в `bars_read`, инструментов остаётся четыре.

Зачем: у агента нет просмотра папки (находка А-6 [аудита 23-10-2026](../../audits/agent-usage-2026-10-23.md)). Модули с числом документов в `initialize` и `bars_status` — только верхний уровень; `Index.md` есть не в каждом проекте, bars раскладку не предписывает; поиск ранжирует по смыслу, а не по дате, и «последний handoff по теме» им не находится. Без просмотра агент идёт в `ls` и Glob.

```
bars_read(path=<папка>, order?, cursor?, project?)
```

- **Путь папки** — по общим правилам путей документов: от корня документации или от корня проекта, `\` и `/` равнозначны, выход за корень проекта — `invalid_params`. Корень документации задаётся своим путём от корня проекта (`docs`).
- **Источник — индекс**: вызов воркера `Tree`, тот же, что строит дерево окна (путь, `title`, число чанков), без чтения файлов. В список входит то, что видит поиск: файл, ещё не взятый индексацией, появится после неё, а при очереди ответ добавляет строку `pending: N documents in queue`, как поиск. Документы вложенных проектов не входят — их смотрят в своём проекте.
- **Один уровень, как `ls`.** Сначала подпапки: имя с `/`, число документов во всём поддереве и `title` её `Index.md` (регистр имени не важен), если он проиндексирован. Затем документы самой папки: имя файла и `title`. Глубже — следующим вызовом с путём подпапки.
- **Порядок — по имени**; `order: "desc"` — обратный. Папки сессий начинаются с даты, поэтому `bars_read(path="chats", order="desc")` показывает последние сессии первыми.
- **Ответ** — блок `=== FOLDER <путь> ===` с числом подпапок и документов в шапке, строка на подпапку или документ; страница до 100 строк, продолжение через `cursor`.
- **Ошибки.** Путь, под которым нет проиндексированных документов, — `invalid_params` со списком ближайших папок, как у области `in` поиска. `lines`, `under`, `view` и `direction` вместе с путём папки — `invalid_params`.
- `bars-cli read` принимает папку по тем же правилам. Окно показывает то же деревом документов (Т-37).

## bars_search с графовыми режимами

При включённой настройке `[mcp] graph_tools` схема `bars_search` дополняется опциональным `mode`: `hybrid` — обычный поиск, `mix` — плюс связанные источники графа (объёмно, задай `related_budget`), `graph` — отношения вместо фрагментов. Графовые параметры возвращаются вместе с графовыми инструментами и без настройки из схемы не видны. Если пакет связанных источников не помещается даже пустым в `related_budget`, поиск отвечает обычной выдачей с `fallback_reason`, а не ошибкой (ISS-88). Подробности — [фактический контракт GraphRAG v1](../graphrag/tools.md#фактический-контракт-v1).

## Графовые инструменты по умолчанию скрыты

Решение автора 23-10-2026 по OQ-162: «скрыть из списка по умолчанию, включать настройкой». Причина: шесть операций редки, а их схемы занимали около 61 % списка инструментов (раздел о стоимости списка в [исследовании формата ответов графа](../../knowledge/graph-answer-format.md)).

- **Ключ.** `[mcp] graph_tools` в `~/.bars/settings.toml`, по умолчанию `false` ([ключи настроек](../settings/settings.md), раздел «Графовые инструменты MCP»); в окне — переключатель на вкладке «Клиенты» ([экран настроек](../window/settings-window.md)).
- **Что скрывается.** Шесть инструментов: `bars_relations`, `bars_paths`, `bars_impact`, `bars_context`, `bars_explore`, `bars_graph`. В `tools/list` их нет, вызов по имени клиент получает как неизвестный инструмент, до воркера он не доходит. Остаются четыре: `bars_search`, `bars_read`, `bars_status`, `bars_audit`; с ключом список пополняется шестью графовыми и графовыми режимами `bars_search`.
- **Когда читается.** Прокси читает `settings.toml` один раз при создании сессии MCP (`BarsMcp::new`, поле `Env::bars_home`), без воркера и без `bars-core`: список отдаётся без воркера (НФТ-3). Смена ключа доходит до агента с новой сессией; запущенный клиент список не обновляет. Нет файла, ошибка разбора или не логическое значение — скрыты.
- **Инструкция `initialize`.** Строка о шести графовых инструментах входит в неё только при включённом ключе; обе формы не длиннее 2 000 знаков. Модули проекта сессии с назначениями из оглавлений печатаются в конце инструкции как подсказка областей `in` ([выбор модулей](module-scope.md)).
- **Возврат.** Исправление ISS-22…ISS-24 и приёмка качества GraphRAG; тогда умолчание меняется вместе с новыми схемами операций.
- **История и окно.** Вызовы включённых инструментов попадают в [историю MCP](../window/mcp-statistics.md), как раньше. Окно и CLI работают с графом независимо от ключа.

## Шесть операций чтения GraphRAG

`bars_relations`, `bars_paths`, `bars_impact`, `bars_context`, `bars_explore`, `bars_graph` читают готовый граф выбранного проекта; описанное ниже относится к включённым инструментам. Область применяется до разрешения имён и обхода. Каждый факт/переход содержит evidence с исходными диапазонами; stale refs не заменяются похожими объектами. Структура и similarity различаются от типизированного отношения. Смысловой слой partial: отсутствие извлечённой зависимости не доказывает её отсутствия. MCP не получает write-tools построения/отмены.

Профили контекста: implementation/investigation/decision, сужающие roles и token/byte budget; точный tokenizer пока недоступен. Полный вход/выход, ошибки и ограничения — [GraphRAG v1](../graphrag/tools.md#фактический-контракт-v1). Тесты транспорта не заменяют открытую приёмку качества S1–S8.

### Когда звать каждую графовую операцию

Проект 4.3.2, принят автором 28-10-2026 (OQ-219); своя схема у каждой операции и `timeout_ms` 5000, текстовый вывод, входы документов и основания шагов реализованы в 4.3.3–4.3.6. Описание операции в схеме начинается с задачи из второго столбца и не длиннее 400 знаков; имена полей — в [схеме у каждой операции](../graphrag/tools.md#схема-параметров-у-каждой-графовой-операции).

| Операция | Когда звать | Когда не звать |
|---|---|---|
| `bars_relations` | Что с чем связано явным утверждением («от чего зависит», «что заменяет»): факты с основанием | Нужен текст документа — `bars_search`; точная фраза — `occurrences` |
| `bars_paths` | Как связаны два объекта; имя можно задать подписью или путём документа | Нужна причина: путь — связь, а не объяснение |
| `bars_impact` | Какие документы перепроверить после правки: задать `documents` (пути) или `roots` | Нужны гиперссылки на документ — `bars_read view=links direction=in`; пустой ответ не доказывает отсутствие зависимости |
| `bars_context` | Собрать первичные источники к задаче по ролям; смотреть `state:` с недостающими ролями | Нужен готовый ответ: это список для чтения |
| `bars_explore` | Обзор темы или проекта: темы, изоляты и битые ссылки, пробелы, кандидаты противоречий | Поиск конкретного места — `bars_search` |
| `bars_graph` | Подграф вокруг документов или общий вид: рёбра с происхождением | Выгрузка всего графа не поддерживается |

Умолчание `timeout_ms` у всех шести в MCP — 5000. Пустой ответ, срыв по времени и ошибка графа называют причину и следующий вызов строкой `next:` ([ответ графа для агента](../graphrag/tools.md#пустой-ответ-ошибка-и-следующий-шаг-графа)).

## Как bars-mcp отвечает и ошибается

### Параллельность, отмена и общий срок MCP — ISS-69

Статус 01-11-2026: реализация завершена (`c6cda73`), два статических Sol-ревью без замечаний. Контракт 5.2.5, OQ-182: прокси выдаёт `readOnlyHint=true` для операций чтения, включая поиск и чтение; `bars_audit` получает `false`: вид действия (`run`/`cancel`/`check`) меняет состояние заданий или сохранённой проверки. Аннотации согласованы со спецификацией [инструментов MCP](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

До четырёх вызовов используют независимые соединения с воркером; следующие ждут свободного места. Исправное соединение возвращается в пул после ответа; при отмене, таймауте или ошибке транспорта закрывается. Поздний ответ не может стать ответом другого вызова. Короткое чтение не ждёт долгого поиска при свободном месте; два поиска могут ждать общий замок модели в воркере.

Общий бюджет `tools/call` — 55 секунд: очередь пула, подключение/hello, повторы транспорта, ожидание модели и ответ входят в один срок. `BARS_MCP_CALL_TIMEOUT_MS` задаёт меньший положительный бюджет в миллисекундах; неверное значение — ошибка запуска. Если задан `MCP_TOOL_TIMEOUT` (миллисекунды), прокси ограничивает бюджет и этим значением. MCP не передаёт таймаут хоста при согласовании: для клиента с пределом меньше 55 секунд нужно передать `BARS_MCP_CALL_TIMEOUT_MS` не больше его предела.

`notifications/cancelled` отменяет только соответствующий вызов через признак `rmcp`, включая ожидание места и модели, согласно [отмене MCP](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation). Прокси прекращает ожидание и закрывает занятый канал; уже запущенная работа воркера может закончиться в фоне, выполненная операция записи не откатывается. Отмена не повторяет вызов и не затрагивает другие соединения.

### Локальная история MCP-вызовов

Допущенные worker вызовы учитываются в локальной [истории MCP](../window/mcp-statistics.md): инструмент нового набора (`bars_search`/`bars_read`/`bars_status`/`bars_audit`), исходные разрешённые аргументы (запрос, `like`, `in`, путь, вид, действие — без содержимого), применённые значения и краткий итог, без текстов документов и полных ответов. Исходный вход передаётся во внутреннем `_mcp`-контексте IPC. Ошибки до допуска и получение ответа клиентом не наблюдаются. Политика хранения и API просмотра принадлежат описанию истории; экран отдельных попыток реализован, его нативная приёмка по ISS-14 остаётся открытой.

### Формат ответа, ошибки и соединение MCP

Решение агента, 15-10-2026 (OQ-52); уточнение автора 18-10-2026: служебное оформление текстовых ответов MCP — на английском, содержимое документов и сообщения воркера сохраняют исходный язык (НФТ-4). Решение автора OQ-301 10-11-2026: описания инструментов и стартовая инструкция `initialize` тоже на английском — это инструкции агенту, а кириллица стоит примерно вдвое больше токенов.

- **Ответ.** Ответы текстовые. Поиск печатает ступенчатую выдачу без блоков: шапка, строки результатов, отрывки, хвост только при отклонениях ([search-staging.md](search-staging.md)). `bars_read` — `=== DOCUMENT <путь> ===` с `title` и текстом с номерами строк; структура длинного документа — тот же блок с заголовком `(outline)` и подсказкой. `bars_status` — части `=== PROJECT ===`, `=== INDEX ===`, `=== VERSIONS ===`, `=== AUDITS ===`, `=== NEW TOPICS ===`, `=== GRAPH ===`. `bars_audit` — части `=== FINDINGS ===`, `=== SUMMARY ===`, `=== NEW TOPICS: N ===`, `=== TOPIC id ===`, `=== AUDIT RUN ===`. Ссылки — `=== LINKS ===`, вхождения — `=== OCCURRENCES ===`, похожие — `=== LIKE ===`. Шесть графовых операций и `mode=mix|graph` печатают текст по проекту 4.3.2: `=== GRAPH <operation> ===`, строка на факт с основанием, предел 16 тыс. знаков ([ответ графа для агента](../graphrag/tools.md#ответ-графа-для-агента--текст-предел-пустые-ответы)). Номера строк и заголовки собирают функции `bars-protocol`, общие с CLI.
- **Ошибки.** Ошибка воркера или канала — ответ инструмента с признаком ошибки, а не ошибка протокола MCP: клиент показывает модели только первый вид. Текст начинается с `Ошибка bars (<kind>):` и несёт сообщение воркера. При `reindex_required` и `reindex_needs_consent` добавлено: переиндексацию запускает пользователь, агенту не повторять вызов. При недоступном воркере — повторить позже.
- **Загрузка модели.** Загрузку уже скачанной модели в память поиск ждёт сам до 20 с ([ожидание моделей](../search/hybrid-search.md#ожидание-моделей)); не успел — отвечает без смысловой части, строка `semantic unavailable:` в тексте. Остальное — только для `model_loading` при скачивании: на него прокси повторяет вызов раз в секунду в пределах `MODEL_WAIT` и общего срока вызова (ISS-18). Каждая попытка — отдельный вызов воркера и отдельная запись в истории; номер попытки прокси записан в `applied.proxy_attempt` (1 — первый вызов, 2 и дальше — повтор прокси, а не агента; ISS-31). При исчерпании ожидания модели возвращается `model_loading`; при исчерпании общего срока — ошибка срока. Отмена прекращает повторы.
- **Согласие.** Полную переиндексацию после смены модели агент запустить не может: на неё нужно согласие пользователя (Т-25). Согласие даёт окно или `bars-cli reindex --accept-model-change`; MCP путь закрыт.
- **Соединение.** Пул до четырёх каналов подключается к воркеру по требованию (`connect_or_launch_with`); холодные подключения сериализованы, чтобы не запускать несколько воркеров. Исправные каналы переиспользуются всю сессию. Разные сборки прокси и воркера дают предупреждение в stderr и в части `VERSIONS` сводки (ISS-117), ответы не меняются. После ошибки транспорта чтение повторяется один раз в пределах общего срока; операции записи автоматически не повторяются, поскольку могли выполниться до обрыва. При отмене или истечении общего срока канал закрывается.
- **Стартовая инструкция** — постоянная часть (английская) и модули проекта по cwd через лёгкий `session_info`, один снимок на соединение, без моделей. Общий срок подключения и ответа — 3 с, ошибка даёт статичную инструкцию. Неудачу `list_tools` повторяет один раз. Вся инструкция вместе со списком не длиннее 2 000 знаков; приёмка модулей — [модули проекта](module-scope.md).
- **Лёгкость прокси (НФТ-3).** В `[dependencies]` `bars-mcp` нет `bars-core` и `bars-worker`; без воркера `initialize` и список инструментов отвечают после ограниченной попытки получить метаданные (проверяется настоящим exe).
