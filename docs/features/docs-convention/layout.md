# Рекомендуемая раскладка docs — база знаний, решения, фичи, журнал сессий

Совет bars для документации проекта (Т-8, OQ-39, OQ-73). Любая папка из списка может отсутствовать, рядом могут лежать свои папки и файлы проекта. Сначала агент читает правила и существующую раскладку проекта; совет применяется там, где проект не установил своё место для документа. Пустые папки и документы «на потом» не создаются.

Статус: таблицы и встроенные тексты IDEA-08 реализованы, реестры bars перенесены; четыре чистые AI-сессии подтвердили выбор документов и приоритет правил проекта. Доставка и границы проверки — [verification.md](verification.md).

```text
docs/
  Index.md                     оглавление
  architecture/                общее устройство
  knowledge/                   база знаний
  adr/                         принятые решения
  backlog/                     баги и пожелания
    issues.md
    ideas.md
  features/<name>/             фича
    Index.md                   что это за фича, оглавление
    requirements.md            требования фичи, если есть
    plan.md                    план реализации, пока идёт работа
    <подфича>.md               любые документы фичи
    utils/                     скрипты фичи
  chats/<YYYY-MM-DD>-<тема>/   журнал одной сессии
    log.md
    handoff.md
```

## Выбор документа: вид, папка и содержание

Пути в таблице считаются от корня документации, который задан проектом (Т-7), а не обязательно от папки с именем `docs`. Имена тематических файлов — примеры. Общие требования проекта сохраняют принятое проектом имя и место; в bars это `MAIN_IDEA.md`.

| Вид документа | Куда класть | Как писать и пример |
|---|---|---|
| Общие требования | Существующий главный документ проекта | Только принятые требования, устойчивые номера, критерии приёмки; фичи ссылаются на номера. Пример bars: `MAIN_IDEA.md`, Т-N. Не заводить второй источник требований. |
| Требования фичи | `features/<name>/requirements.md` | Поведение с точки зрения пользователя, ограничения, проверяемая приёмка, ссылки на общие требования; отделять решение автора от предложения. Пример: что видит пользователь при удалении проекта. |
| Описание фичи | `features/<name>/<topic>.md` | Текущее поведение, входы, результат, ошибки, границы проверенного; `Index.md` ведёт к документам фичи. Пример: `features/search/hybrid-search.md`. |
| План фичи | `features/<name>/plan.md` | Оставшиеся шаги, зависимости, проверки; выполненное сокращать, после окончания план сокращать или удалять. Пример: этапы доставки инструкции агенту. |
| Общее устройство | `architecture/<topic>.md` | Ответственность частей и их связи, данные и контракты, общие для нескольких фич. Пример: `architecture/worker.md`; пользовательское поведение остаётся у фичи. |
| Принятое решение с обоснованием | `adr/NNNN-<topic>.md` | Статус, дата, контекст, решение, последствия, отклонённые варианты, «Где применено»; слова автора цитировать дословно с датой. Предложение агента не объявлять принятым ADR. |
| Исследование, сравнение, замер | `knowledge/<topic>.md` | Вопрос, метод, источники и доказательства, результат, ограничения, следующий различающий опыт. Для снимка — дата в имени, например `knowledge/search-2026-10-18.md`; измерение не означает внедрение. |

Требования только одной фичи остаются в её `requirements.md`; главный документ содержит общие требования проекта. Не добавлять в него подробности отдельной фичи, если автор или правила проекта явно этого не требуют. На общие требования — ссылки по номерам.

## Где записывать баги и пожелания автора

Для багов и пожеланий рекомендуется `backlog/` под корнем документации. Баг описывает несоответствие ожидаемому поведению; пожелание — потребность в новом поведении. Существующие реестры и правила проекта имеют приоритет.

| Вид документа | Куда класть | Как писать и пример |
|---|---|---|
| Баг | `backlog/issues.md` | Устойчивый ID, источник и дата, симптом, условия/шаги воспроизведения, ожидаемое и фактическое, состояние, ссылка на исправление и проверку. Пример: ISS-08 — клиент не вызывает bars. Не придумывать неизвестные шаги или причину. |
| Пожелание | `backlog/ideas.md` | Устойчивый ID, источник и дата, потребность автора, состояние, ссылки на проектирование и результат. Пример: IDEA-08 — агенту понятно, куда писать документ. Идея ещё не является требованием или решением. |

## Куда писать журнал сессии и оглавления

Журнал сессии хранит историю работы агента; оглавление помогает найти действующие документы своей папки.

| Вид документа | Куда класть | Как писать и пример |
|---|---|---|
| Находка или смена подхода в сессии | `chats/<YYYY-MM-DD>-<topic>/log.md` | До трёх строк по поводу, дописывать без перечитывания; долгоживущее знание и решение вынести в свой документ, оставить ссылку. Пример: почему опыт пришлось изменить. |
| Передача дел | `chats/<YYYY-MM-DD>-<topic>/handoff.md` | Сделано, не сделано, сложности, дальше; не длиннее экрана. Пример: что следующей сессии проверить после изменения инструкции. |
| Оглавление | `Index.md` своей папки | Ссылка к родителю, каждый файл и подпапка со строкой «когда читать»; менять вместе с составом папки. Папки отдельных сессий — исключение. |

## Как выбирать место при смешанной задаче

Агент ищет существующий документ по теме и обновляет его; новый файл нужен для новой темы, а не для каждой сессии. Например, найденный дефект фиксируется в `backlog/issues.md`, замер его причины — в `knowledge/`, принятое изменение поведения — у фичи, обоснование архитектурного выбора — в ADR. Между записями ставятся ссылки, текст не копируется.

Журнал хранит историю работы; описание фичи — текущее состояние продукта. Непринятое предложение остаётся помеченным предложением в исследовании или плане. Для конкретного проекта его собственное соглашение имеет приоритет над этой таблицей.

## База знаний knowledge

Знание разработки, которое не описывает продукт напрямую: исследования, сравнения библиотек, замеры, соглашения по коду, найденные грабли. Пишется, когда находка пригодится дальше одной сессии.

## Решения adr

Одно решение — один файл `NNNN-<тема>.md` с четырёхзначным номером по порядку. Внутри: статус («принято» или «заменено ADR-NNNN»), дата, контекст, решение, последствия, отклонённые варианты. ADR — запись о том, почему выбрали так; в отличие от остальных документов он не переписывается под текущее состояние. Новое решение, которое отменяет старое, — новый ADR, а у старого меняется только статус.

## Фичи features

Фича — то, что продукт умеет с точки зрения пользователя: «поиск», «индексация», «окно». Это ТЗ проекта, как в Gramax. `Index.md` коротко объясняет фичу и ведёт на остальные файлы. Документы фичи описывают текущее состояние; `plan.md` живёт, пока фичу делают, и сокращается или удаляется, когда она готова.

Устройство, общее для многих фич (стек, процессы, схема данных), удобнее держать отдельной папкой рядом, например `architecture/`.

## Журнал сессий chats

Папка на каждую сессию агента: `log.md` по ходу работы и `handoff.md` в конце. Правила — [session-log.md](session-log.md). Журнал — история, а не описание продукта, поэтому агент включает модуль `chats` в поиск, только когда ищет, что и почему делали раньше.

## Оформление файлов

То же, что в `BARS_INSTRUCTION.md` ([bars-instruction.md](bars-instruction.md)): `title` во frontmatter, ATX-заголовки, разделы, понятные сами по себе. В каждой папке, кроме папок сессий в `chats/`, — `Index.md` с оглавлением; регистр имени не важен (`index.md` тоже годится).
