## Назначение и границы проекта

Пользователь видит карту источников рядом с документом, понимает основание выбранной связи и открывает исходный текст. Плотный клубок, множество рёбер и быстрый renderer сами по себе не решают замечание автора. Общий вид начинает с документов; чанки раскрываются по запросу. Выбор подсвечивает ближайшее окружение, остальные связи приглушаются; камера не делает автоматический fit после каждого изменения. Изоляты сохраняются и доступны через список.

В физическом виде ровно три вида рёбер по Т-46. Решение автора OQ-110 не пересматривается. Принадлежность чанка документу — группировка и навигация, без четвёртого ребра и без пружины `contains`. Сущности, разделы, утверждения и предикаты GR-02 остаются в общем хранилище и аналитических операциях GR-05; их самостоятельные проекции проектируются с полным UX. Переключатель аналитической проекции не расширяет легенду физического вида.

Вид запроса и сила запрос↔результат относятся к отдельному проектированию Т-47; этот документ задаёт переиспользуемую модель источников и физики. Он не меняет ранжирование поиска, `min_score` поиска, extraction или калибровку «Новых тем».

## Узлы, принадлежность и устойчивость идентичности

| Объект | Представление и идентичность | Поведение |
|---|---|---|
| Документ | Существующий `ObjectRef(document,id,revision)`, путь от docs-root, title, модуль, состояние источника | Общий вид; открыть документ; раскрыть чанки. Размер не растёт от числа чанков/входящих ссылок; цвет по Т-38, если назначен |
| Чанк | Существующий `ObjectRef(chunk,id,revision)`, владелец, heading_chain, ordinal, исходные spans | Отличимая форма; открыть диапазон оригинала; показать владельца. Не дублировать узел из-за нескольких spans |
| Группа раскрытого документа | Контейнер над тем же документом и его видимыми чанками; не объект знаний | Подпись владельца и число показанных/доступных чанков; сворачивание не удаляет источник из хранилища |

`parent`, `source_ids` и `contains` должны согласовываться: у чанка ровно один документ-владелец того же снимка. Ошибка исключает чанк из физики с диагностикой; нельзя выбирать первого владельца или прятать дефект под «нет связей». Раздел не подменяет retrieval-чанк. Padding и `other headers` не создают дополнительные узлы или исходные диапазоны.

Раскрытие оставляет документ, его документные связи, выбор и камеру. Чанки появляются возле владельца с детерминированным смещением по ID. Слабое позиционное ограничение удерживает их в области группы; оно не изображается ребром, не входит в легенду и не влияет на другие документы. После сворачивания выбранного чанка выбор переходит к владельцу с сохранением ссылки на прежний диапазон. Pin документа/чанка доступен; сворачивание сохраняет pin скрытого чанка в пределах текущей ревизии.

Документ сохраняет позицию по ID при новой ревизии, но инспектор обновляется. ID чанка включает ordinal и embed_hash: после перерезки нельзя переносить pin/выбор на другой чанк по одному ordinal. Неизменившийся полный ref сохраняет состояние; исчезнувший выбранный чанк переводит выбор к владельцу и показывает причину. Переименование пути не считается тождеством без отдельного подтверждённого механизма.

## Три вида рёбер и их основания

| Вид физической модели | Концы и направление | Основание и агрегация |
|---|---|---|
| `document_similarity` | документ↔документ, без стрелки | Cosine документных представлений по алгоритму ниже. Не максимум пары чанков и не число похожих чанков |
| `markdown_link` | документ→документ; исходное направление сохраняется | Реально разрешённая Markdown-ссылка. Якорь/исходный раздел и каждый диапазон ссылки доступны в инспекторе. Повторы одной направленной пары свёрнуты в одно ребро; обратное направление хранится отдельно |
| `chunk_similarity` | чанк↔чанк, без стрелки | Cosine готовых векторов одного embedding space. Направленные списки kNN объединяются по неориентированной паре; взаимность не удваивает силу |

Self-loop не участвует в физике. Ссылка внутри документа сохраняется как навигация по якорю в инспекторе документа. Внешний URL и выход за разрешённый корень не становятся узлами проекта. Неразрешённый файл/якорь — диагностика с исходным target, не выдуманное ребро к ближайшему похожему имени. Ссылки разрешаются текущим Markdown-парсером; новые синтаксисы требуют отдельного контракта.

В раскрытой группе ссылочные рёбра остаются документными; инспектор позволяет перейти к точному разделу/чанку, покрывающему исходный диапазон. Дублирующая пружина чанк→документ не создаётся. Чанковая близость может связывать чанки одного документа, но в инспекторе отмечается общий владелец; это не новое межфайловое знание.

Для одной пары допустимы разные виды: ссылка и близость не сливаются в «универсальную зависимость». Физика объединяет их отдельно от рисунка. `depends_on`, `co_occurs`, `member_of`, общие цели ссылок и совпавшие названия сущностей не выдаются за один из этих трёх видов.

## Документная близость без новой модели

Инженерный метод `document-centroid-v1`: из существующих векторов чанков; дополнительного инференса нет. Чанковые векторы уже содержат путь/цепочку заголовков и служебный контекст embedding input — это ограничение метода явно указывается, а не обещается «чистый смысл текста».

1. Для каждого документа взять все его чанки и source spans той же ревизии и конфигурации нарезки. Векторы должны иметь одинаковые model fingerprint, размерность и нормализацию; смешивать FP32/FP16 или разные модели без доказанной совместимости нельзя.
2. Вес чанка `a_i` — длина его исходного текста в Unicode-символах. Пересечение spans учитывать один раз: каждому символу, покрытому `m` чанками, дать долю `1/m` каждому из них. Искусственный padding и служебные подписи не увеличивают `a_i`. Это убирает повторный вес диапазона, но не очищает уже вычисленный embedding от контекста.
3. Нормализовать каждый ненулевой конечный вектор `u_i`; вычислить `v_D = normalize(sum(a_i*u_i)/sum(a_i))`. При нулевой норме результата документная близость недоступна. Пустой документ остаётся узлом со ссылками.
4. При отсутствующем/повреждённом векторе любого содержательного чанка не публиковать приблизительный centroid как полный. Вернуть покрытие и причину недоступности слоя для документа; остальные готовые документы продолжают работать. Полнота считается относительно индексированного снимка, а не всех файлов диска.
5. Считать cosine для пар готовых документов. Сохранять raw cosine, метод, fingerprints, refs всех вкладов и покрытие. По нажатию показывать состав расчёта и отдельные наиболее похожие пары чанков как иллюстрацию, не evidence зависимости и не формулу документной силы.

Одинаковые вклады не складываются в «важность» длинного документа; среднее нормализовано. Разные темы длинного файла могут размывать centroid. Альтернатива max cross-chunk отклонена для первого проекта: одна короткая общая тема даёт ложное впечатление близости документов целиком, а существующий partial kNN не содержит всех пар. Проверка качества centroid на обоих проектах обязательна перед приёмкой: короткие/многотемные файлы, оглавления, повторяющиеся инструкции, близкие и явно разные темы. Если метод не различает случаи, пересматривается метод; рисунком это не исправляется.

## Кандидаты близости, фильтры и полнота

Начальные инженерные параметры для макета/реализации: `k=5`, `tau=0.5` отдельно для документов и чанков. Это исходный экспериментальный профиль существующего kNN, не доказанный порог полезности и не решение автора. Cosine ниже `tau` не создаёт ребра; совпавший с `tau` кандидат допускается. Равные scores упорядочиваются по ID; берётся объединение top-k каждого конца, а не пересечение. Из-за входящих соседей степень узла может превышать k — ограничение степени не обещается.

Область применяется до поиска соседей: документный вектор всегда описывает весь разрешённый документ; фильтр модулей/файлов не пересчитывает его по видимым чанкам. Для чанков кандидаты ограничиваются разрешёнными документами. Сворачивание скрывает чанковые узлы/рёбра, но не меняет raw scores. Простой постфильтр глобального top-k не гарантирует top-k внутри области: требуется расчёт для области либо явный `partial` с отсутствием обещания полного соседства.

Точный расчёт документов имеет стоимость `O(D²*d)`; матрицу всех пар хранить не нужно, достаточно bounded heaps. Чанки — отдельный расчёт с отменой и продолжением между завершёнными строками. Старый лимит миллиона сравнений и сохранённый partial kNN не подменяют новый полный расчёт. При достижении бюджета показывать завершённые строки/все строки, причину остановки и доступное продолжение. Незавершённая строка не выдаётся за полный top-k.

Изменение вектора может вытеснить соседа у любого документа/чанка: инкрементальная инвалидизация только непосредственных старых соседей некорректна. Первая реализация пересчитывает соответствующий kNN в фоне с ограничением ресурсов, сохраняя прежний согласованный снимок; не смешивает поколения. Чтение графа не запускает скачивание, extraction или синхронный пересчёт всех пар.

## Сила, видимость и физика — разные величины

| Поле | Смысл |
|---|---|
| `raw_score` | Исходный cosine `[-1,1]` для близости; отсутствует для ссылки |
| `strength` | `s=clamp(cosine,0,1)` для допущенной близости; `s=1` для прямой ссылки как факта наличия |
| `support_count` | Число самостоятельных исходных диапазонов ссылки; только сведения, не множитель силы |
| `spring_strength` | Коэффициент физики после ограничения суммарной нагрузки, не оценка истинности |

Шкала абсолютная в пределах вида, без min/max по текущему экрану и без percentile: добавление слабого ребра не меняет яркость остальных. `tau` управляет отбором, а не пересчитывает силу оставшихся. Ссылки имеют одинаковую силу; частота ссылок не показывает важность и не калибруется как вероятность. В легенде и инспекторе прямо сказано: численные значения разных видов не являются сопоставимой мерой зависимости.

Рисунок получает `s`: толщина `w(s)=0.6+1.8s` CSS px, яркость — монотонное смешение цвета вида с фоном с коэффициентом `b(s)=0.25+0.65s`. Это исходные значения для макета, обе темы и DPR проверяются в дизайне; не использовать min/max экранных scores. Тип также кодируется штрихом/стрелкой и подписью в списке. Выделение добавляется отдельным контуром/ореолом, не заменяет толщину на константу. Цвет документа Т-38 не заменяет тип ребра. Числа s, raw cosine и метод доступны текстом.

Предложенная физика опирается на [ADR-0004 proposed](../../adr/0004-graph-physics-renderer.md). Для логического ребра `q(s)=0.05+0.45s`; базовая длина 60 world units, не меняется от cosine. Чем выше s при прочих равных, тем выше притяжение в одном tick. Длина на сложившейся карте не служит шкалой s.

Для предотвращения эффекта длинного раскрытого документа:

1. Для каждой пары разных владельцев собрать документные и междокументные чанковые рёбра всех трёх видов. Обратные ссылки входят в ту же физическую пару, хотя рисуются направленно.
2. `Q=max(q_e)`; каждой логической пружине назначить `k_e=Q*q_e/sum(q_e)`. Сумма притяжений между владельцами при одинаковой геометрии равна Q, а не числу чанков, ссылок или типов. Одна пружина остаётся q. При изменении s одного ребра его коэффициент не убывает; относительные расстояния/число рёбер при сравнении фиксируются.
3. Внутридокументные чанковые связи нормализуются тем же способом в отдельной корзине владельца. Группирующая сила не суммируется как междокументная связь. Отталкивание дочерних чанков делит фиксированный бюджет владельца между видимыми детьми; раскрытие не умножает суммарный заряд группы.

Раскрытие может менять геометрию и равновесие: это не обещание неизменных координат. Ограничение предотвращает линейное усиление группы от числа детей. Поправки степеней, скрытые усиления renderer и второй проход нормализации не добавляются поверх формулы. Параметры charge/collision/охлаждения настраиваются на настоящей модели, отдельно от семантического s.

## Срез, бюджеты и договор данных

Новая внутренняя проекция окна `PhysicalGraphSlice`, версия метода `physical-v1`; существующий `GraphReply` и аналитические MCP/CLI-контракты не переименовываются и не меняют смысл. Проекция строится в Rust из общего графа/индекса. Renderer не выводит владельца по строке label и не рассчитывает семантические scores.

Срез содержит: canonical project namespace, graph snapshot, source manifest fingerprint, embedding fingerprint, projection method, scope fingerprint; узлы с полными refs/владельцем/spans; рёбра с видом/направлением/raw_score/s/методом/refs оснований; состояния каждого из трёх слоёв, warnings, requested/applied budgets, показанные counts, known totals, `truncated`, причины и cursor. Ссылки на основания раскрываются порциями в том же snapshot: ограничение байт не обрезает молча массив evidence. Ребро близости несёт происхождение расчёта и исходные refs, а не выдуманную цитату `depends_on`.

Начальные пределы UI: 500 узлов / 2000 рёбер / 512 KiB ответа; максимум одновременно 2000 / 10000 / 2 MiB. Это инженерные бюджеты новой проекции, не новые общепродуктовые требования и не изменение default=250 старого `GraphRequest`. Раскрытие документа — порциями по 50 чанков, общий предел остаётся общим. На сохранённых снимках исследования четвёртого вида 305/481 документов укладываются в начальный предел узлов; все 1584/2796 документов+чанков — только первый корпус укладывается в максимум. Число рёбер и байты проверяются независимо.

Общий вид сначала добавляет документы, затем раскрытые чанки; при избытке документов — детерминированный обход модулей по кругу, внутри по пути/ID. Выбранный центр резервируется до остальных. При нехватке места раскрытие не вытесняет молча уже показанные узлы: даёт остаток бюджета и продолжение после сужения области/повышения допустимого предела. Рёбра добавляются только между включёнными концами: ссылки раньше близости, внутри вида — обход исходных узлов по кругу, соседи по убыванию s и ID. Разные направления/виды не теряются при дедупликации. При исчерпании на ссылках слой близости явно усечён; пустой отрисованный слой не называется отсутствующим.

Продолжение добавляет данные того же снимка без дубликатов; fingerprint включает scope, фильтры типов, k/tau, раскрытые документы, лимиты и метод. Изменение этих параметров начинает новый срез. При исчезнувшем snapshot — `snapshot_expired`, без склейки со свежим. Известные total не заменяются размером текущей страницы. Неполнота extraction не блокирует готовые ссылки/близость: состояния слоёв независимы. Увеличение предела или раскрытие запускает короткую физическую адаптацию, не сбрасывает камеру.

## Жизненный цикл физики и состояния окна

Ключ состояния панели: проект + scope + проекция; позиции по ID с проверкой ревизии. Панель хранит камеру, выбор и pins отдельно от данных; сама раскладка панелей сохраняется действующим механизмом workspace. Разные панели имеют независимую камеру. Размер панели меняет viewport, не вызывает fit; явная команда «Вписать» доступна.

Worker получает только индексы узлов, координаты, pins, пружины и групповые коэффициенты. Сообщения содержат `panel_id`, `generation`, `layout_run`, `sequence`. Любая смена проекта/среза инвалидирует generation; stop инвалидирует layout_run до запроса worker. Поздняя порция даже того же снимка не может сдвинуть остановленный граф. Один расчёт на панель, максимум одна неподтверждённая порция координат; ACK/буферы ограничивают накопление. Исходные refs и evidence остаются в модели UI.

Остановка — пользовательский latch. Смена фильтра, получение страницы и возвращение из фона не снимают явный stop. При reduced motion simulation не стартует: сохранённые либо детерминированные статические позиции, навигация и ручное перемещение доступны. Скрытие панели/окна останавливает ticks и rAF; возвращение продолжает только ранее активную simulation при отсутствии stop/reduced motion. Охлаждение завершается с переходом в idle, без постоянного rAF. Закрытие уничтожает worker, observers и renderer. Переход Stop→Start запускает новый layout_run, не использует старые кадры.

Пользовательский pin сохраняется после drag; временная фиксация во время drag не превращается молча в постоянный pin. Новый snapshot сохраняет координаты неизменившихся объектов, добавляет новые около видимых соседей/владельца, удаляет отсутствующие. Выбранный устаревший источник остаётся читаемым как снимок с предупреждением; открыть актуальный диапазон можно только после проверки revision, без прыжка к случайным строкам.

Различать: пустая область; узлы без связей; слой ещё не построен/строится/partial/stale/failed/cancelled; пропущенные векторы; битая ссылка; лимит ответа/вычисления; удалённый источник; отказ renderer. Готовые слои остаются доступны, список и инспектор работают при отказе Canvas. Текст запроса и камера сами не меняют scope поиска. Клавиатура и доступный список используют те же refs и действия, конкретная композиция — GR-05 и будущий макет.

## Модули реализации и порядок переноса

Serena в сессии отсутствует; навигация выполнена чтением исходников. Проверены `bars-core/src/graph/{build,similarity}.rs`, `indexing/chunking.rs`, `bars-graph/src/{model,source,query}.rs`, текущие `graph-renderer.ts`/`GraphPage.svelte` и документы [архитектуры](../../architecture/graph.md). Текущий build сохраняет чанковый kNN k=5/tau=0.5 с пределом сравнений; centroid и описанной проекции нет. Старый renderer не передаёт вес в layout и делает fit при resize.

| Слой | Изменение при реализации |
|---|---|
| `bars-core::graph` | Документные представления, версионированный кэш, bounded kNN/отмена/продолжение, fingerprint по модели и source map |
| `bars-graph` | Чистая физическая проекция, типизированные рёбра/срез, дедупликация/область/пагинация; без векторов и моделей в этом крейте |
| `bars-protocol`, worker, Tauri | Типизированный запрос среза, чтение согласованного поколения, ошибки и отмена; общая логика Rust |
| UI graph model, worker, renderer | Приём срезов, lifecycle, физические коэффициенты, Canvas/hit-testing, сохранение камеры, список/инспектор; интеграция с Workspace и каталогом команд |

До изменения production — макет в панели с теми же тремя видами, обе темы, компактная/центральная панель, длинные названия, изоляты, плотный хаб, раскрытие и усечение. Затем Rust-проекция и проверки данных; затем worker/Canvas и пользовательские действия; затем реальный Tauri на обоих проектах. Старый UI-путь удаляется после переноса его действий; аналитические операции сохраняются по GR-05. Конкретные файлы уточняются по состоянию checkout при начале реализации.

## Проверки проекта и критерии реализации

Проект проверяется отдельным [скриптом модели](../../chats/2026-10-21-physical-graph-design/verify.mjs): монотонность силы/толщины/яркости, ограничение суммарного притяжения, сохранение разных типов/направлений на снимках. Это проверка формул и доступных входов; ни качество centroid, ни рабочий UI не утверждаются.

| Проверка следующего шага | Ожидаемый результат |
|---|---|
| Centroid: неодинаковые длины, пересечения, повтор диапазона, padding, отсутствующий/нулевой вектор, смена embedding space | Верные доли, отсутствие удвоения, недоступность вместо поддельного score; новый fingerprint |
| Близость: одна пара, обратный kNN, равные scores, scope и незаконченная строка | Одна неориентированная связь, детерминированный порядок, честный partial, отсутствие чужих refs |
| Ссылки: повторы, A→B и B→A, self-anchor, broken/external | Точное происхождение, сохранённые направления, повторы не усиливают пружину |
| Сила 0.5/0.9 из одного состояния пары и одинаковой геометрии/зарядов | Больше s — толще/ярче и больше сближение в одном tick; глобальная длина не проверяется как шкала |
| Раскрытие 1/50/500 чанков одного документа | Сумма междокументных коэффициентов ограничена Q; нет нового вида `contains`; камера/выбор сохраняются |
| Документ со ссылкой и близостью; скрытие вида | Оба основания доступны; физическая сумма ограничена; видимый набор и нормализация обновляются согласованно |
| Страница/байты/максимум, snapshot_expired, поздний ответ старого проекта | Усечение явно; концы рёбер существуют; продолжение без дублей, чужое поколение отвергнуто |
| Stop, reduced motion, hidden, destroy; late tick/ACK | Ноль автоматических сдвигов после остановки; idle не потребляет постоянный цикл |
| bars-project и overdrive-bots, реальные модели/окно, поиск и чтение рядом | Понятные основания и переходы, приемлемые CPU/private memory/отклик, обе темы/размеры; macOS отдельно |

Для ручной проверки: выбрать документ → прочитать причину связи → открыть исходник → раскрыть чанки → сравнить силу двух связей одного вида → остановить/переместить/изменить размер → продолжить усечённый срез. Согласование рисунка и нативная приёмка не закрываются этим документом. Новых продуктовых вопросов автору не требуется: неопределённые численные параметры помечены как инженерные исходные значения и проверяются следующим шагом.
