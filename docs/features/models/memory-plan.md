# Снижение памяти моделей bars — проект и оставшаяся работа

Статус 23-10-2026: исследование 4.2.1 завершено — две полные FP16-пары, 1200/1200 поисков при индексации в 12 конфигурациях; 10 полных процессов, два сохранённых выхода по защите. Полной атрибуции DML/драйверных выделений нет. Открыт выбор и реализация меры 4.2.2, а не ожидание выделенного окна ресурсов. Численные данные и границы находятся в исследовании памяти.

Проект агента, а не новые требования автора. Основание — Т-1, Т-3, Т-16…18, Т-25, НФТ-1…3. Измерения, причины пиков и данные — [knowledge/memory.md](../../knowledge/memory.md); то, что уже работает, описано в [встроенных моделях](local-models.md). Системные настройки подкачки остаются решением пользователя: bars их не меняет.

## Что уже сделано

- **FP16 rerank на DirectML** с закреплённым артефактом, проверенной отметкой готовности кэша и FP32 CPU fallback: удержание пары моделей −19 %, пик за жизнь −24…25 %, тёплый rerank 0,53 → 0,17 с.
- **Выгрузка по простою:** rerank через 5 минут, embed через 15, проверка каждые 10 с; занятый слот не прерывается, дорогой drop идёт вне замков ([worker.md](../../architecture/worker.md)). Выгрузка снижает память в простое, но не активный пик, и добавляет цену первого запроса.
- **Профиль `bge-m3:fp16`** для Windows: отдельный fingerprint (precision и revision), отдельный индекс, согласие Т-25 при выборе, без CPU fallback. Заводской выбор остаётся FP32 bge-m3.
- **Скачивание bge-m3 без создания сессии** и ограниченное хранение оценок точного поиска.
- **Ограничение пачки embed** 3000 символов с учётом дополнения — снижает удержание embed примерно на 1,67 ГиБ.
- **Исследование 20-10-2026:** свежие FP16-индексы bars/overdrive, 138 вопросов без новых потерь; один совместный FP16-пик 4,46 ГиБ против 5,84 ГиБ третьего повтора прежней пары. Второй FP16-процесс не допущен по commit. Baseline обычного запуска пустого окна с WebView 191–194 МиБ private, фонового 181–184 МиБ; индексатор без ONNX менее 9 МиБ. Это измерения, не новая продуктовая оптимизация; [метод и границы](../../knowledge/memory.md#аппаратное-продолжение-20-10-2026).
- **4.2.1, 23-10-2026:** release-стенд настоящего Worker/IPC с ORT logger, 1/2/4 клиентами, без/с rerank и FP32/FP16; исправлен порядок lifecycle-проверок пары. Принят FP32 off/2 на полном корпусе, два полных FP16 lifecycle и завершена матрица на фиксированном срезе: 1200/1200 правильных ответов, 10 полных процессов, два защитных выхода после ответов. Числа и границы — в разделе «Продолжение 4.2.1» исследования памяти.

INT8 для rerank и embed отклонён из-за потери качества; длина текста и число кандидатов K ради памяти не сокращаются.

## Что остаётся

### Выбор меры 4.2.2

Метод, результаты и ограничения завершённого исследования находятся в memory.md. FP16 снижает память embed, но совместная индексация с rerank достигает около 5,0 ГиБ private commit; FP32 — около 6,84 ГиБ. Пик короткой пары не представляет настоящую нагрузку. Данные не разделяют вклад длинных входов, high-water allocator и одновременных операций: следующий различающий опыт — те же входы и модели раздельно/вместе, затем выбор меры и проверка настоящим worker. Изменение заводской модели требует согласия Т-25. Рабочий bars не закрывать, профиль и системную подкачку ради эксперимента не менять (OQ-106, OQ-151).

Состоявшиеся замеры не закрывают общую приёмку снижения памяти:

1. Проверка выбранной меры на настоящем worker и разных входах. Совместная нагрузка 47 документов / 620 чанков и два повтора пары уже измерены; качество FP16 принято на двух замороженных корпусах. НФТ-2 на 5000 chunks и чистая скорость не приняты.
2. Выбор продуктовой меры по измерениям. Профиль FP16 уже доступен; заводская модель не меняется автоматически. Пики индексатора без ONNX 7,74/8,30 МиБ не обосновывают оптимизацию его буферов ради модельных гигабайтов.
3. Allocator: RunOptions fastembed не раскрывает; отдельные переключатели не дали принятой экономии. Не отключать кэши вслепую: повторные аллокации и перекомпиляция графа могут съесть ускорение. Огромные документы и транзакции SQLite менять только после подтверждённого вклада.
4. Документация выбранной меры и ожиданий от файла подкачки на машинах с разным объёмом памяти; общие правила уже изложены в memory.md, численные рекомендации без данных не давать.

Приёмку оптимизации по одному drop, screen-медиане или созданному коду подтвердить нельзя. Ноутбук, слабые GPU и Mac в текущей среде недоступны — их замеры остаются открытыми; рекомендации для 8/16/32 ГиБ даются только по данным, неподтверждённое помечается.

Baseline окна получен в пустом профиле Windows; переносить числа на проект с открытыми документами без измерения нельзя. Это граница результата, не новое требование автора.

## Критерии принятия оптимизации

- **Lifecycle-изменение:** те же лидеры, порядок и оценки в допустимом численном допуске, отсутствие потерь и starvation запросов; измерены остаток после простоя (а не факт вызова drop) и цена повторной загрузки.
- **Precision или усечение:** полный согласованный протокол качества ([бенч качества](../../knowledge/search-quality.md)); новых потерянных правильных результатов в выбранных метриках нет.
- **Совместная нагрузка:** настоящий worker и IPC, а не только ядро; поиск без и с rerank, индексация, 1/2/4 запроса во время индексации, повторная загрузка после простоя. Складывать измеренные одновременные пики, а не веса двух моделей из разных процессов. Для median/p95 — не меньше 100 тёплых запросов в серии. Если опасное наложение временных буферов сохраняется — исследовать ограничение тяжёлых GPU-операций с приоритетом запроса; глобальная сериализация без замера задержки не внедряется.
- Сначала решение записывается в `local-models.md`, `settings.md`, `worker.md`, затем меняется код.

## Ограничения стенда

Уточнение автора 20-10-2026 (OQ-107): прежний `spikes/` удалён из-за размера более 40 ГБ. Не восстанавливать архивные кэши, копии моделей и бинарников. Продолжение — один временный каталог вне репозитория; общие веса только для чтения, недостающий FP16-артефакт один, в репозитории остаются небольшие доказательства. Собственный временный каталог удаляется после сохранения результатов, включая неуспешный выход; разделяемые веса и чужой Cargo target не удаляются.

Загрузка/потоковая проверка FP16-файлов без создания сессии использует резерв 2 ГиБ commit: прежняя проверка давала пик 3,52 МиБ, операции загрузчика потоковые. Этот резерв относится только к `download-embed-fp16`; он не разрешает открыть модель. Для `index-serial` остаётся 5 ГиБ, quality — 6 ГиБ, пары — 8 ГиБ; аварийная граница 1 ГиБ сохранена.

- Изолированный `BARS_USER_HOME` внутри каталога стенда, копия корпуса, веса только для чтения; профиль, MCP и клиентские настройки не трогать; установленный bars не закрывать (решение автора).
- Перед каждой загрузкой проверять запас RAM и commit; аварийные границы RAM <512 МиБ / commit <1 ГиБ завершают только собственный процесс. Стартовые резервы и их обоснование — в [замерах памяти](../../knowledge/memory.md#fp16-rerank-и-выгрузка-по-простою-приёмка-настоящим-worker).
- Режим качества вычисляет query-векторы, выгружает embed и только затем открывает rerank, поэтому он не измеряет пик двух моделей и его задержка не используется. Пара моделей проверяется отдельным режимом при достаточном запасе.
- Скачивание исключать из замера загрузки; сетевые прогоны не доказывают чистую скорость.
