# Этап 13 — память моделей, индексации и окна

Статус 18-10-2026: исходный FP32 baseline и два настоящих worker FP16/timer процесса выполнены; [снижение памяти и reload](../../knowledge/memory-fp16-results.md). Продолжается приёмка embed FP16 и INT8 на отдельных индексах; работающий bars по указанию автора не закрывается. Отдельный baseline окна и Mac не получены. Основание: Т-1, Т-3, Т-17, НФТ-1…3. [Исследование и данные](../../knowledge/memory-usage.md). Ниже проект агента, а не новые требования автора.

## Внедрение снижения памяти по поручению автора

Автор 18-10-2026 потребовал сначала анализ критичных расходов и скорости, затем проект решения, после него реализацию; реализация разрешена отдельным сообщением. FP16 rerank внедрён этапом 11, здесь добавлены проверенная готовность кэша и безопасный lifecycle. Рабочая политика — rerank 300 с / embed 900 с, проверка каждые 10 с; прежние 60/300 с не применены. 85 тестов worker-подсистемы, включая timer/reload/disable/shutdown, пройдены; приёмка настоящей памяти и холодного скачивания продолжается. Выгрузка уменьшает простой, но не активный пик и добавляет цену следующего запроса.

Итоговый анализ и последовательность внедрения — [memory-reduction.md](memory-reduction.md): P0 FP16 rerank с общим контрактом артефактов; затем lifecycle и FP16 embed с проверкой индекса; allocator и мелкие структуры — по профилю. Порядок исследовательских опытов ниже не заменяет этот порядок продуктовых изменений.

Отдельная цель — память активного инференса. FP16 reranker уже проверен исследованием инференса на полном retrieval/holdout без потерь выбранных метрик и даёт меньшую память; его интеграция требует закреплённого артефакта, согласованного скачивания/каталога и CPU-пути. До проверки этих контрактов заводской выбор precision не объявляется изменённым. Дополнительно проверяется CPU allocator без удержания arena; не сокращать длину текста или K ради скрытой потери качества.

## Сохранение контрактов памяти

Приёмка embed рассматривает FP16 DirectML и INT8 CPU независимо от результата INT8 rerank. Существующие отдельные индексы и одинаковый замороженный корпус используются повторно. Сначала vector-only screen по сохранённым запросам, затем полный гибридный retrieval/порог. Чтобы проверять качество рядом с работающим bars, режим `quality` стенда вычисляет query-векторы, выгружает embed и только после этого открывает rerank. Одновременный пик двух моделей этим не измеряется; latency такого прохода не используется. Старт RAM ≥4 / commit ≥6 ГиБ для одной тяжёлой сессии, аварийно 512 МиБ/1 ГиБ; прежний одновременный `full` сохраняет более высокие резервы. Запросы и fingerprint не подменяются, saved cache обслуживает только заранее вычисленные запросы.

Сохранить качество, формат индекса, работу поиска при индексации, переиспользование векторов и лёгкий MCP-прокси. Системные настройки подкачки остаются решением пользователя. Ограничение одновременно загруженных моделей, скрытое отключение rerank и смена модели не вводятся без результатов опыта и отдельного описания поведения.

## Порядок работы с памятью

1. **Воспроизводимый стенд.** Изолированный `BARS_USER_HOME` внутри каталога стенда в проекте; копия корпуса и согласованный SQLite snapshot, отдельный канал, общие веса только для чтения. Реальный профиль, MCP и клиентские настройки не трогать. Сначала запас RAM/commit; завершать только owned-процессы. Сохранить commit+dirty patch, хеши бинарников и зависимостей, модели/EP, ОС/железо, корпус/вопросы, PID/starttime и маркеры фаз. Скачивание исключить из замера загрузки. Протокол качества — [search-quality-benchmark.md](../../knowledge/search-quality-benchmark.md).
2. **Фазовый baseline.** Три независимых процесса на конфигурацию: пустой startup, окно hidden/open/hidden, embed load/first/warm, rerank load/first/warm, idle, смена модели. Cold означает новую сессию процесса; файловый кэш ОС отдельно фиксировать, не очищать глобально. Отдельные CPU/DirectML серии и реальные короткие/длинные входы. Пассивный CIM-сэмплер проверить на точность; для пиков использовать быстрый сборщик вне процесса.
3. **Спайк выгрузки rerank.** Сравнить текущий retain, освобождение после запроса и idle TTL 60/300/900 с. Таймер — `tokio`-задача менеджера моделей; время — monotonic. Состояние модели и время последнего завершения/использования хранить в одном защищённом состоянии `RerankSlot`. Удалять только модель из текущего слота; loader и конфигурация остаются для ленивой загрузки. `try_lock`: занятую модель не прерывать, повторить позже. Предусмотреть фоновую загрузку и повторную проверку времени под lock; не брать глобальные замки менеджера во время `drop`. Удалённый объект освобождать вне lock, чтобы дорогой destructor не задерживал запрос. Старые Arc и смена настроек не должны выгружать новую сессию. Внешний HTTP-провайдер не трактовать как память локальной модели.
4. **Спайк ORT.** Если unload не объясняет остаток/пик — profile session/allocator, CPU arena on/off или поддерживаемое shrinkage. Сначала подтвердить API закреплённых fastembed/ort и влияние на EP. Сравнить потребление и повторную аллокацию на следующем запросе. Кванты/precision синхронизировать с [inference-plan.md](inference-plan.md); новый пакет или стек здесь не выбирать.
5. **Буферы и точный поиск.** Fake-модели отделяют Rust/SQLite от ONNX. Не делать повторно уже существующее построчное чтение векторов. Если значим `HashMap` оценок — спайк ограниченного top-C и сохранения оценок FTS/exact-кандидатов; доказать тождественность fusion/threshold/exact-id порядка. Если значим большой документ — временный spool векторов либо запись порциями с сохранением атомарной замены документа; нельзя держать write-транзакцию во время инференса и тем самым ухудшить поиск. Внедрять только подтверждённый узкий участок.
6. **Совместная нагрузка.** Поиск без/с rerank, индексация, 1/2/4 запроса во время индексации, повторная загрузка после idle и окна. Настоящий worker/IPC обязателен: bench_quality измеряет ядро. Для median/p95 — не меньше 100 тёплых запросов в серии; размер серии и raw timings сохранять. Ограничение нагрузки harness останавливает новые задания до OOM.
7. **Принятие оптимизации.** Сравнить фазовые пики и плато, load/first/warm latency, качество на замороженных наборах и ошибки. При lifecycle-only изменении — те же лидеры/порядок/оценки в допустимом численном допуске, отсутствие потерь и starvation. При precision/усечении — полный согласованный quality-протокол. Выбранный TTL/параметр сначала описать в settings/local-models/worker, затем реализовать; не объявлять 300 с умолчанием до сравнения. Внедрение — отдельный измеренный шаг.

## Изолированный спайк 18-10-2026

Окно нельзя изолировать одним `BARS_USER_HOME`: `bars-app/src/main.rs` подключает `tauri-plugin-single-instance` без отдельного идентификатора стенда. IPC/home разделены, но второй Tauri-процесс может попасть в уже работающий экземпляр приложения. Для UI-baseline нужна отдельная сборка с уникальным Tauri identifier и отдельным home; запуск установленного bars ради опыта не использовать. В текущем `window.rs` окно создаётся даже в `--background`, только скрытым; его закрытие также лишь скрывает webview.

Разрешён автором: отдельный `bench_memory` в `bars-core/examples`, без подключения к рабочему IPC. Каждая конфигурация — новый процесс; веса из существующего кэша, только чтение. Нативный Windows-сэмплер 100 мс фиксирует root Private Bytes/WS и системный commit; маркеры startup/load/first/warm/drop/reload. Сначала CPU и DirectML embed/rerank по отдельности, затем совместно при запасе RAM. Спайк освобождает настоящий `BuiltinReranker` через `drop` и сверяет оценки после повторной загрузки; это проверка освобождения сессии, не реализация продуктового TTL. Начальный запас — 4 ГиБ RAM/8 ГиБ commit; аварийная остановка owned-процесса при <512 МиБ RAM или <1 ГиБ commit. Время короткой фазы дополняется peak-счётчиком процесса, сэмплированный максимум не выдаётся за точный.

## Проверки реализации lifecycle

Приёмка продуктового FP16 использует тот же замороженный вход и отдельный каталог доказательств. Для одиночного rerank стартовый резерв — RAM ≥4 ГиБ / свободный commit ≥6 ГиБ: screen FP16/batch16 показал 2,53 ГиБ sampled peak, остаётся более 3 ГиБ на не пойманный короткий пик и внешние колебания. Lifetime peak отдельно проверяется новым стендом; screen не выдаётся за его замену. Для embed и двух сессий стартовый commit остаётся ≥8 ГиБ, дополнительный резерв перед длинным embed — ≥6 ГиБ; перед rerank/reload — ≥5 ГиБ. Последний уточнён после успешного продуктового FP16-прогона: lifetime peak 2,31 ГиБ, запас поверх него 2,69 ГиБ. Уменьшение одиночного резерва не разрешает запускать пару моделей при том же запасе. Аварийные границы 512 МиБ RAM / 1 ГиБ commit сохраняются. Скрипт ждёт отсутствие других бенчей/компиляции, записывает внешнюю GPU dedicated/shared память и отмечает пересечения; загрязнённое время не принимается. Сетевые прогоны не используются как доказательство чистой скорости.

`SharedReranker::rerank` объединяет lazy load и inference под одним model-lock. Прежний промежуток между `prepare` и повторным захватом lock устранён: timer не может забрать занятую модель. Время последнего использования обновляется после операции, включая ошибку; status-проверки его не продлевают. Drop выполняется вне model/manager-lock, под общим load-gate.

Fake provider: проверены lazy load, занятый слот, граница TTL, загрузка параллельно timer, два запроса после выгрузки, отключение rerank, замена конфигурации со старым Arc и ошибка повторной загрузки. Tokio integration: timer/reload, пробуждение при отключении и shutdown, ожидание выполняющегося blocking-drop. Весь worker: 146 тестов пройдены. Настоящая модель: plateau до/после timer, повторный inference и сохранение выдачи проверяются отдельным `bench_worker_memory`; его ускоренные TTL не подменяют продуктовые 300/900 с.

## Что требуется для завершения этапа памяти

Отчёт со всеми фазами, сырыми временными рядами и хешами, сравнение хотя бы одного спайка с baseline, выводы по экономии/цене повторной загрузки и явные статусы Windows/macOS. Рекомендации для 8/16/32 ГиБ только по данным; неподтверждённое маркировать. Проектирование и пассивный снимок этап не закрывают. Mac и ноутбук недоступны в текущей среде; их замеры остаются открытыми.
