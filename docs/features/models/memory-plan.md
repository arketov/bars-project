# Снижение памяти моделей bars — проект и оставшаяся работа

Проект агента, а не новые требования автора. Основание — Т-1, Т-3, Т-16…18, Т-25, НФТ-1…3. Измерения, причины пиков и данные — [knowledge/memory.md](../../knowledge/memory.md); то, что уже работает, описано в [встроенных моделях](local-models.md). Системные настройки подкачки остаются решением пользователя: bars их не меняет.

## Что уже сделано

- **FP16 rerank на DirectML** с закреплённым артефактом, проверенной отметкой готовности кэша и FP32 CPU fallback: удержание пары моделей −19 %, пик за жизнь −24…25 %, тёплый rerank 0,53 → 0,17 с.
- **Выгрузка по простою:** rerank через 5 минут, embed через 15, проверка каждые 10 с; занятый слот не прерывается, дорогой drop идёт вне замков ([worker.md](../../architecture/worker.md)). Выгрузка снижает память в простое, но не активный пик, и добавляет цену первого запроса.
- **Профиль `bge-m3:fp16`** для Windows: отдельный fingerprint (precision и revision), отдельный индекс, согласие Т-25 при выборе, без CPU fallback. Заводской выбор остаётся FP32 bge-m3.
- **Скачивание bge-m3 без создания сессии** и ограниченное хранение оценок точного поиска.
- **Ограничение пачки embed** 3000 символов с учётом дополнения — снижает удержание embed примерно на 1,67 ГиБ.

INT8 для rerank и embed отклонён из-за потери качества; длина текста и число кандидатов K ради памяти не сокращаются.

## Что остаётся

Состояние реализации в рабочей копии прошло проверку по частям, но полная приёмка снижения не закрыта:

1. Полная индексация нового FP16 embed и retrieval на его индексах: bars-регрессия и holdout.
2. Парный пик FP16 embed + FP16 rerank в настоящем worker; третий повтор прежней пары.
3. Baseline памяти окна и webview (отдельная сборка Tauri с уникальным identifier, см. [изоляцию стенда](../../knowledge/memory.md#изоляция-стенда-и-воспроизведение)).
4. Индексатор и allocator: профиль ORT/arena и поддерживаемое shrinkage — сначала подтвердить API закреплённых fastembed и ort и влияние на EP; не отключать все кэши вслепую, повторные аллокации и перекомпиляция графа могут съесть ускорение. Буфер огромного документа и транзакции SQLite менять только после подтверждённого вклада.
5. Документация: чего ждать от файла подкачки на машинах с разным объёмом памяти.

Закрыть этап по одному drop, screen-медиане или созданному коду нельзя. Ноутбук, слабые GPU и Mac в текущей среде недоступны — их замеры остаются открытыми; рекомендации для 8/16/32 ГиБ даются только по данным, неподтверждённое помечается.

## Критерии принятия оптимизации

- **Lifecycle-изменение:** те же лидеры, порядок и оценки в допустимом численном допуске, отсутствие потерь и starvation запросов; измерены остаток после простоя (а не факт вызова drop) и цена повторной загрузки.
- **Precision или усечение:** полный согласованный протокол качества ([бенч качества](../../knowledge/search-quality.md)); новых потерянных правильных результатов в выбранных метриках нет.
- **Совместная нагрузка:** настоящий worker и IPC, а не только ядро; поиск без и с rerank, индексация, 1/2/4 запроса во время индексации, повторная загрузка после простоя. Складывать измеренные одновременные пики, а не веса двух моделей из разных процессов. Для median/p95 — не меньше 100 тёплых запросов в серии. Если опасное наложение временных буферов сохраняется — исследовать ограничение тяжёлых GPU-операций с приоритетом запроса; глобальная сериализация без замера задержки не внедряется.
- Сначала решение записывается в `local-models.md`, `settings.md`, `worker.md`, затем меняется код.

## Ограничения стенда

- Изолированный `BARS_USER_HOME` внутри каталога стенда, копия корпуса, веса только для чтения; профиль, MCP и клиентские настройки не трогать; установленный bars не закрывать (решение автора).
- Перед каждой загрузкой проверять запас RAM и commit; аварийные границы RAM <512 МиБ / commit <1 ГиБ завершают только собственный процесс. Стартовые резервы и их обоснование — в [замерах памяти](../../knowledge/memory.md#fp16-rerank-и-выгрузка-по-простою-приёмка-настоящим-worker).
- Режим качества вычисляет query-векторы, выгружает embed и только затем открывает rerank, поэтому он не измеряет пик двух моделей и его задержка не используется. Пара моделей проверяется отдельным режимом при достаточном запасе.
- Скачивание исключать из замера загрузки; сетевые прогоны не доказывают чистую скорость.
