# Снижение памяти моделей bars

Проект 18-10-2026 по уточнению автора: сначала определить критичные расходы памяти и задержки, затем спроектировать изменения, после этого реализовать. Реализация разрешена автором: FP16 rerank → lifecycle → остальные пункты. FP16 loader внедряется параллельной сессией этапа 11; здесь проверяются его память и lifecycle, общие файлы не заменяются второй реализацией. Основание: Т-1, Т-3, Т-16…18, Т-25, НФТ-1…3. Числа — на текущей машине; это не универсальные минимальные требования.

## Где расходуется память и время

В процессе живут embed и rerank. Два исходных файла весов FP32 занимают вместе 4,23 ГиБ на диске; размер файлов нельзя напрямую приравнивать к Private Bytes или RAM. После загрузки двух DirectML-сессий, обработки длинных текстов и rerank удерживается 6,87 ГиБ с разбиением как у воркера либо 8,51 ГиБ при длинной core4-пачке. Drop одной модели освобождает её основную долю. Точный allocator/драйверный состав не измерен; называть всё CPU arena нельзя.

Доказательства: [изолированные замеры](../../knowledge/memory-results.md), [протокол памяти](../../knowledge/memory-usage.md), [GPU precision-сравнение](../../knowledge/inference-2026-10-18/gpu-screen.json), [варианты пачек](../../knowledge/inference-2026-10-18/gpu-combos.json), [полный retrieval](../../knowledge/inference-2026-10-18/full-retrieval.json), [настоящий worker](../../knowledge/inference-2026-10-18/worker.json). Данные исследований скорости уже существуют; повторять обзор вместо применения результатов не нужно.

| Статья | Наблюдение | Критичность |
|---|---|---|
| FP32 reranker и его рабочие выделения | Отдельный DirectML rerank: около 3,6 ГиБ удержания, пик около 4,2 ГиБ; после drop около 0,2 ГиБ | Высокая: память активного запроса и его основная задержка |
| FP32 embed и длина пачки | После короткого query около 2,75 ГиБ; после длинных одиночных вызовов около 3,53 ГиБ, core4 около 5,2 ГиБ | Высокая: активная индексация и общий запас при поиске |
| Модели после простоя | Сессии сейчас остаются до смены настроек/завершения | Высокая для обычного фонового приложения; TTL не снижает активный пик |
| Одновременные embed/rerank | При индексации и поиске одновременно живут обе сессии и рабочие выделения | Требует общего замера пика; нельзя оценивать бюджет только по одиночной модели |
| Выходные векторы и точный поиск | Четыре вектора dim1024 — 16 КиБ; SQLite-векторы читаются построчно, остаются O(N) оценки | Низкая на текущих корпусах; не объясняет гигабайты |
| Буфер одного огромного документа | Индексатор собирает недостающие векторы перед транзакцией | Проверить отдельно; оптимизировать при подтверждённом крупном вкладе |
| Окно/webview | Порядка сотен МиБ по пассивному снимку; отдельный чистый baseline не получен | Ниже многогигабайтных моделей; не начинать с переделки UI |

Для интерактивного поиска важнее сократить rerank: production worker около 0,69 с serial и 1,08 с при индексации; исследовательский FP16-вариант около 0,47 и 0,58 с. Embed-query — десятки/сотня мс. Для первой индексации важнее throughput embed: отдельный screen показал около 1,55 текста/с CPU против 17,63 DirectML; FP16 DirectML — 26,19 текста/с. Это throughput модели на фиксированных текстах, не время полного индексатора.

## Приоритет P0 — меньше памяти активного rerank

Первое изменение — встроенный reranker FP16 на поддерживаемом DirectML. Уменьшается представление весов и промежуточных тензоров, сохраняются исходные тексты, K и max_length. Не подменять это сокращением кандидатов или незаметным усечением текста.

Сопоставимый screen: FP32 batch4 median 0,702 с, sampled peak private 3,96 ГиБ; FP16 batch4 0,562 с и 2,21 ГиБ. В отдельном сравнении FP16 batch16 дал 0,354 с и 2,53 ГиБ против FP32 batch4 0,788 с и 3,97 ГиБ. FP16 batch4 с fixed padding — 0,425 с и 2,10 ГиБ. Это разные серии: не объединять их в одну оценку ускорения.

Первоначальный компактный кандидат — FP16 batch4. Для внедрения выбран batch16 после общего опыта embed+rerank/очереди этапа 11: он быстрее при меньшем общем пике, чем FP32 batch4. Дополнительные примерно 0,4 ГиБ относительно малого FP16-профиля остаются компромиссом; при GPU allocation error loader снижает batch16 → 4 → 1. Текущий K15 остаётся. FP16 batch16 прошёл исследовательские full retrieval и holdout без потерь выбранных метрик; отдельно принимается новый продуктовый loader. Равенство float-оценок FP32/FP16 не обещается: проверяются порядок, правильность результатов и поведение порога.

## Контракт артефактов и загрузки P0

Продуктовый loader не использует пути из `spikes/` и не выбирает веса по случайному наличию файла. Конструктор, Download, is_downloaded, прогресс и runtime согласованы общим контрактом артефактов:

1. Логическая модель, фактический backend/precision, неизменяемая revision, список файлов, размер и проверочный хеш. FP16 reranker из исследования: `onnx-community/bge-reranker-v2-m3-ONNX`, revision `6f5ff65298512715a1e669753bc754d2bc8f367b`, файл `onnx/model_fp16.onnx`, SHA256 `9b26f9185d2d26051f724c9fc3565e5d9614a9dd459b784c806c246232a70fe3`. Tokenizer/config также закрепить и проверить; совместимость не выводить из одинакового имени модели.
2. `Auto` на поддерживаемом DirectML выбирает FP16 rerank; явно выбранный CPU сохраняет проверенный FP32-путь. Неподдерживаемый backend/граф даёт явную причину fallback, а не скрытый повтор скачивания под прежней отметкой «скачано».
3. UI «скачано» относится к файлам выбранного варианта: CPU `rozgo` FP32 либо закреплённого DirectML FP16. Наличие только прежнего FP32-кэша не считается готовностью GPU FP16. Проверенная отметка включает путь, размер, mtime и ожидаемые BLAKE3; опрос окна не читает гигабайт весов заново.
4. Собственный профиль/manifest в общем кэше моделей; временная загрузка → проверка размера/хеша → атомарная готовность. Старый рабочий артефакт не перезаписывается. Один существующий замок загрузки, остановка и ошибка остаются наблюдаемыми.
5. Индекс reranker не определяет: смена его precision не требует переиндексации. Сохранить логическую модель и настройки поиска; runtime показывает фактические backend/precision/revision. Отдельно проверить обновление с уже скачанным FP32-кэшем и холодную установку.

## Приоритет P1 — память активного embed

Уже существующий padded-лимит 3000 символов сохранить: на нашем входе он уменьшает удержание embed примерно на 1,67 ГиБ. Увеличение batch4 до batch8 в screen подняло пик FP32 DirectML с 3,94 до 9,25 ГиБ без улучшения throughput; такой вариант отклонён.

FP16 DirectML и INT8 CPU проверяются как самостоятельные embed-кандидаты. FP16 batch4: screen дал 3,22 ГиБ пика против 3,94 ГиБ FP32 и рост throughput 17,63 → 26,19 текста/с. INT8 CPU: 1,91 ГиБ и 4,86 текста/с против 4,57 ГиБ / 1,55 текста/с у CPU FP32; query 19 мс против 45 мс. Минимальный cosine около 0,99991 / 0,974 — мера изменения векторов, а не основание принять или отвергнуть качество поиска. Отказ INT8 rerank не переносится на embed. По уточнению автора INT8 оценивается наряду с FP16, выбор определяется retrieval и памятью, а не заранее выбранной precision. Отдельные индексы и инкрементальные проходы уже построены; полная приёмка retrieval/порога продолжается.

Для embed выбран отдельный fingerprint precision+revision. Старые и новые document-векторы не смешиваются; смена профиля использует штатное согласие Т-25 с сохранением рабочего старого индекса до завершения. GPU FP16 → CPU FP32 fallback запрещён для FP16-профиля с понятной ошибкой; обычная bge-m3 сохраняет прежний CPU fallback. Совместимость разных precision этим не объявляется доказанной.

Ядровые кандидаты реализованы отдельными конструкторами: FP16 требует DirectML, INT8 выполняется на CPU динамически по одному тексту. Артефакты Xenova/bge-m3 закреплены revision `4de13258303883538bd53b696b452bf8099f0858`, пять файлов проверяются BLAKE3; ожидаемые размеры весов известны. Fingerprint каждого профиля включает precision и revision и отличается от текущего FP32. INT8-конструктор остаётся исследовательским: в каталог он не включён из-за найденной потери качества.

Полный экспериментальный retrieval: FP16 сохранил все выбранные метрики на 100 вопросах относительно текущего FP32 embed + FP16 rerank; INT8 потерял правильный раздел od-001 из top-10. Отдельный Windows-профиль `BAAI/bge-m3:fp16` подключён к каталогу, provider и окну с предупреждением DirectML/переиндексации, прежним заводским FP32 и штатным согласием Т-25. Скачивание пяти файлов не создаёт ONNX-сессию; атомарная отметка проверенного кэша привязана к revision, хешам, размерам и mtime. Проверки статуса не читают гигабайт весов.

Новый ядровой query-путь также прошёл 100 вопросов без новых потерь; все 102 400 компонентов query-векторов совпали с прототипом. Полная новая индексация, bars/holdout на новых индексах, совместный пик двух FP16-сессий и чистая скорость ещё не приняты: preflight не дал старт. 219 core / 177 worker тестов, 10 UI-тестов и release-сборка прошли; новый clippy не завершён из-за общего build-lock. [Протокол и исходные данные](../../knowledge/memory-embed-2026-10-18/Index.md). Установленное приложение не обновлялось.

Не заводить вторую постоянную CPU embed-модель только ради более быстрого короткого query: экономия десятков мс способна вернуть лишние гигабайты. Не переводить всю индексацию на CPU ради меньшего текущего Working Set: измеренный throughput существенно хуже, а CPU-пик на длинных текстах также большой.

## Приоритет P1 — lifecycle без холодного запроса каждый раз

После P0 добавить освобождение встроенного rerank при отключении и после простоя; embed — после более длинного простоя. Цель этой части — фоновые сотни МиБ вместо постоянно удерживаемых сессий, а не снижение активного пика.

TTL 60/300/900 с — параметры опыта. Сначала повторить загрузку FP16, измерить цену первого запроса и интервалы в фиксированных сериях: burst, пауза, новый burst, индексация. Затем выбрать умолчания с явной ценой cold-запроса; старые 60/300 с не считать уже принятым решением. Отсчёт от завершения фактической работы, runtime/status не продлевают жизнь модели.

State загрузки, inference и last-used защищён одним model-lock. `try_lock` не прерывает занятый слот; извлечение модели под lock, дорогой drop после освобождения lock. Устранить разрыв между `prepare` и `rerank`; сохранить ленивую перезагрузку и error-state. Старые Arc при смене конфигурации не должны очищать новый слот. Фоновая задача входит в существующий shutdown, без зависшего таймера или потерянного cleanup. Внешний HTTP-провайдер не считать локальными гигабайтами.

Рабочая реализация lifecycle: проверка каждые 10 с и сразу после сохранения настроек; rerank — 300 с, embed — 900 с после завершения работы. Это инженерный выбор для burst/пауза: у rerank более короткое удержание, у индексатора — больший запас между документами и запросами. До приёмки продукта подтвердить цену FP16 reload и остаток памяти; значения не выдаются за оптимум реального пользовательского трафика. Общий загрузочный gate берётся через `try_lock` и держится на drop: новый constructor не накладывается на освобождение старой сессии; готовый inference этот gate не использует. Отключённый rerank освобождается при ближайшем свободном проходе, без ожидания TTL. Фоновый blocking cleanup входит в shutdown и дожидается завершения.

## Приоритет P2 — общие пики и менее крупные статьи

После уменьшения точности и ограничения пачек проверить настоящий worker: поиск без/с rerank, индексация, concurrency 1/2/4, смена модели, загрузка и reload. Складывать измеренные одновременные пики, а не веса двух моделей из разных процессов. Если сохраняется опасное наложение временных буферов — исследовать ограничение тяжёлых GPU-операций с приоритетом запроса; глобальная сериализация без измерения задержки не внедряется.

При остаточном удержании исследовать allocator/EP profile и доступный CPU arena off/shrinkage. Нельзя отключать все кэши вслепую: повторные аллокации и повторная компиляция графа могут съесть ускорение. Векторный HashMap, транзакции SQLite и буфер огромного документа менять только после подтверждения вклада; это не первая борьба с 8 ГиБ.

## Порядок реализации и условия принятия

1. Зафиксировать matched baseline текущего продукта и одинаковые входы. Результаты сторонней исследовательской сборки — основание выбора кандидата, не готовая приёмка нового loader.
2. Реализовать общий план FP16-артефакта rerank и тесты cache/download/fallback/проверки целостности. Одинаковая логика для UI и фактического открытия модели.
3. Проверить выбранный продуктовый FP16 batch16 через loader: один процесс модели, затем вместе с embed, три новых процесса. Выбор batch16 уточнён по полному retrieval и настоящему worker: в исследовательской серии общий sampled private peak снизился 7,36 → 6,00 ГиБ; это основание проверить продуктовый вариант, не его приёмка. Batch4 остаётся измеренным более компактным кандидатом и ступенью отката при allocation error. Сохранить private/WS, sampled/lifetime peak, GPU dedicated/shared memory, cold/warm latency, хеши. Цель — подтвердить снижение активного пика и улучшение задержки; screen не является обещанным бюджетом продукта.
4. Прогнать полный фиксированный retrieval, порог, bars-регрессию и holdout. Новых потерянных правильных результатов в выбранных метриках не принимать. Затем worker concurrency/индексация и проверка явного fallback; совместно принять FP16/batch16 по сравнению с исходным FP32/batch4.
5. Внедрить безопасный lifecycle и проверить burst/паузы, отключение, reload failure, фоновые загрузки, занятый слот, смену конфигурации и shutdown. Измерить остаток после idle, а не только факт вызова drop.
6. Перейти к FP16 embed с отдельным индексом и проектом fingerprint/fallback. Только после этого — allocator tuning и меньшие статьи.

Сначала каждый результат фиксируется в документации, затем меняется соответствующий продуктовый путь. Не закрывать этап 13 по одному drop, screen-медиане или созданному файлу кода.
