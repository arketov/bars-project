# Встроенные модели bars

Статус ISS-79 на 01-11-2026: освобождение заменённых сессий вынесено в отдельный поток; Sol-ревью и полный clippy workspace пройдены. Выполнение новых регрессий и полный check не подтверждены; завершение реализации разрешено автором отдельно от общей проверки.

Встроенные модели работают внутри воркера `bars`: ONNX через fastembed-rs, Qwen GGUF через llama.cpp, Nomic через candle (Т-3, Т-17, [ADR-0002](../../adr/0002-qwen-gguf.md)). Обе Qwen проверены на CPU/Vulkan, полный retrieval сравнен с bge-m3; ручные Tauri/NSIS/macOS-проверки остаются открытыми. [Результаты и границы](../../knowledge/gguf-models.md).

## Проект CUDA: статус и границы

Проект 8.1.3 согласован 02-11-2026: автор выбрал «Нужна поддержка cuda 12 и 13», затем «Принять проект и дополнение Т-3» (OQ-224/225/241 закрыты). Т-3 обновлено с записью в журнале раундов. Все разделы с префиксом «Проект CUDA» описывают принятый проект для 8.1.4, **не реализованное поведение**. CUDA пока не входит в продуктовую сборку. Основания — [исследование поставки](../../knowledge/inference-devices.md) и [отбор ускорителей RTX 3090](../../knowledge/inference-speed.md); IDEA-19 и OQ-209 задают потребность и пользовательскую установку CUDA.

Предложение охватывает Windows x86-64, встроенные Qwen GGUF и ONNX embed/rerank. На macOS сохраняются Metal для GGUF и CPU для ONNX; Nomic/candle и внешние HTTP-провайдеры CUDA-путь bars не используют. Слайдер, новые модели GGUF-rerank и пользовательские режимы сжатия относятся к отдельным этапам.

## Проект CUDA: поставка и зависимости

Нужен один установщик с двумя CUDA-комплектами, под major 12 и 13. llama.cpp использует `dynamic-backends`: общие CPU/Vulkan/base DLL одной ревизии и раздельные `cuda12/ggml-cuda.dll`, `cuda13/ggml-cuda.dll`. В процессе открывается только выбранный CUDA-backend. CUDA/cuDNN устанавливает пользователь (OQ-209), bars их не скачивает; готовые нативные библиотеки bars поставляет установщик с лицензиями. Пользователю не нужен `nvcc`.

Для ONNX предлагается `ort 2.0.0-rc.13` с `load-dynamic`, по одному полному согласованному комплекту ORT 1.28.0 на major: `ort/cuda12/` и `ort/cuda13/`. Каждый обязан содержать CPU, DirectML и свой CUDA EP. Загружается ровно один `onnxruntime.dll` через абсолютный `ort::init_from`, до любого вызова ORT из fastembed. Статическое ядро одновременно с динамическим не линкуется. Версия crate и модели сохраняются; на Windows fastembed переключается с default download-binaries на `ort-load-dynamic` с явным сохранением нужных функций hf-hub/Nomic. `fastembed/cuda` для этого не используется: эта фича относится к candle, а не к ONNX CUDA EP.

Автопакет pyke из [таблицы rc.13](https://github.com/pykeio/ort/blob/v2.0.0-rc.13/ort-sys/build/download/dist.tsv) закрывает только CUDA13 и поэтому не подходит как единственная поставка. Официальные динамические GPU-архивы ORT существуют для обеих major, но наличие в них CUDA не доказывает наличие DirectML. Рекомендуемый воспроизводимый путь — два собственных согласованных динамических ORT из одного закреплённого исходника 1.28.0, с CPU + DirectML + CUDA соответствующей major; TensorRT/NVRTX не собираются и не регистрируются. [Параметры CMake ORT 1.28](https://github.com/microsoft/onnxruntime/blob/v1.28.0/cmake/CMakeLists.txt) допускают независимые CUDA/DML-флаги; совместная сборка и исполнение пока не проверены. Нельзя подмешивать provider DLL из другого архива, даже с тем же номером ORT.

| Компонент | Принятый проектный контракт |
|---|---|
| GPU CUDA | Совместима с конкретной сборкой ggml/ORT/cuDNN; первая продуктовая матрица — Turing+ (≥ 7.5). Наличие CUDA12 само по себе не обещает поддержку Pascal/Volta |
| CUDA12 у пользователя | Предлагаемый минимум 12.8, сборки GGUF/ORT под CUDA12 не требуют CUDA13 |
| CUDA13 у пользователя | Предлагаемый минимум 13.0, сборки GGUF/ORT под CUDA13 не требуют CUDA12 |
| cuDNN у пользователя | Только для ONNX: предлагается закрепить cuDNN 9.23, отдельно вариант под выбранную CUDA12 либо CUDA13; для GGUF cuDNN не требуется |
| Драйвер | Совместимый с выбранными runtime, библиотеками и GPU; успешные `cuInit` и запуск модели обязательны. Значение «CUDA Version» у драйвера не означает установленный toolkit |
| Отсутствие CUDA/cuDNN | Приложение запускается; выбирается допустимая следующая ступень с причиной. cuDNN отсутствует — GGUF всё ещё может использовать CUDA |

Минимумы 12.8/13.0 опираются на [зависимости официального ORT 1.28](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html), сверенные 02-11-2026. Это целевые минимумы двух собственных сборок, не приёмка. Прежнее 13.2/cuDNN 9.23 относится к автопакету pyke и не переносится автоматически на другую поставку. Каждая принимаемая сборка получает manifest: исходники/revision, параметры, архитектуры, версии compiler/runtime/cuDNN, список DLL, импорты, размеры и SHA-256. Верхняя minor/версия cuDNN считается поддержанной после проверки, а не только по совпадению major. На машине сборки нужны обе версии toolkit и cuDNN; пользовательские CUDA 12.8 и CUDA13 проверяются отдельно.

Первый технический шаг 8.1.4 — подтвердить обе динамические сборки и DirectML/CPU без CUDA до правки загрузчиков. Цена решения: собственная нативная сборка, больший установщик, две аппаратные матрицы и смена линковки Windows; размер и время сборки пока не измерены. Если сочетание EP/ABI не собирается или обязательные импорты мешают запуску без CUDA, это блокер реализации выбранной схемы. Его устраняют в поставке; CUDA12 не удаляют из задачи и две копии ORT в одном процессе не вводят как скрытый обход. Готовый upstream-комплект допустим вместо собственной сборки только при подтверждении тех же трёх EP, зависимостей, API и численной матрицы.

Точный список DLL установщика снимается с manifest каждого комплекта, а не маской `*.dll`. Проверяется граф импортов: `bars.exe`, обязательные base DLL и CPU/DirectML-части обоих ORT не должны требовать NVIDIA DLL при старте. Потерянная обязательная библиотека — ошибка установки, а не «CUDA не найдена». Обновление заменяет согласованный набор, не оставляя старые backend DLL. Portable-запуск переносит весь набор. Текущий установщик и macOS-линковка этим проектом не изменены.

## Проект CUDA: выбор major и граница процесса

Поддержка обеих major означает работу одной и той же установки bars на машине с CUDA12, CUDA13 либо обеими; одновременное использование разных major разными моделями не требуется. Один общий выбор major применяется к CUDA GGUF и ONNX в процессе. До первого ORT API и CUDA-backend загрузчик собирает кандидатов по каталогам/метаданным зависимостей, без глобальной инициализации двух ORT и без смешивания одноимённых `cudnn64_9.dll` разных вариантов.

Сначала выбираются полные допустимые комплекты для текущих встроенных моделей с `auto`: при наличии ONNX учитывается и соответствующая cuDNN. Из равно допустимых выбирается 13, затем 12; порядок — правило совместимости, не обещание скорости. Неподходящие архитектура, драйвер, версия/вариант DLL исключают кандидата с причиной. Если полного ONNX-комплекта нет, но GGUF имеет рабочую CUDA, выбирается её major: отсутствие cuDNN не лишает GGUF ускорения, ONNX идёт на DirectML. Без CUDA выбирается CPU/DirectML-часть базового комплекта `ort/cuda12/`, не регистрируя CUDA EP. При `cpu` CUDA context не создаётся.

Выбранные библиотека ORT и major фиксируются до конца процесса: `ort` хранит API/библиотеку глобально, а ggml — глобальный backend. После фиксации переключать DLL, подменять provider или грузить второй ORT нельзя. Ошибка последующего Run откатывает на Vulkan/DirectML/CPU внутри выбранного комплекта; она не вызывает горячую смену 13↔12. Смена установленных зависимостей или настроек, требующая другой major, показывает необходимость перезапуска bars. `model_retry` повторяет текущую major и не переинициализирует глобальные библиотеки. Эту границу проверяют также после ранней CPU-сессии, когда позже включают GPU.

## Проект CUDA: обнаружение и выбор устройства

Обнаружение выполняет воркер перед первой встроенной загрузкой под существующей сериализацией загрузки/освобождения. Оно не читает веса, не создаёт модель и не запускается заново при каждом `models_info` или поиске. Результат и безопасные причины кэшируются в процессе. CPU-режим не инициализирует CUDA. Фоновый опрос окна читает снимок; обнаружение не держит общий async-замок состояния во время вызовов драйвера.

Драйвер загружается из System32; CUDA ищется в `CUDA_PATH`, затем в явных каталогах PATH и стандартных каталогах установки подходящей major. Проверяются `bin` и `bin/x64`; cuDNN — в PATH и стандартном каталоге NVIDIA. Кандидаты проверяются детерминированно: первый полный совместимый набор, без смешивания версий cuDNN из разных установок. Сохраняются фактические версии и пути загруженных DLL. Каталог проекта и текущий рабочий каталог не используются как неявный источник DLL. Собственные DLL и предварительно найденные зависимости грузятся по абсолютным путям с управляемым разрешением транзитивных и отложенных импортов; handles удерживаются на время процесса. Окружение PATH не меняется ни системно, ни во время работы воркера. Зависимости каждой backend-группы проверяются независимо; CUDA/cuDNN не становятся обязательными импортами базового загрузчика.

Загрузка backend управляется явно: CPU-only открывает CPU-backend, проба CUDA — только согласованную CUDA-группу. Безусловный `load_backends_from_path`, открывающий все группы при CPU-only и проглатывающий ошибки, не заменяет этот порядок. Для разрешённых групп сохраняются причины загрузчика; обнаружение CUDA не объявляется успешным только потому, что общий загрузчик молча пропустил модуль.

Версии читаются из `cuDriverGetVersion`, `cudaRuntimeGetVersion`, `cudnnGetVersion` и `cudnnGetCudartVersion`. `cuDriverGetVersion < cudaRuntimeGetVersion` само по себе не запрещает CUDA: учитывается [minor-version compatibility NVIDIA](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html) и реальные ошибки инициализации. Совместимость PTX/новых функций проверяется запуском; заранее обещать её для любого драйвера той же major нельзя. Helper `ort::ep::cuda::preload_dylibs` rc.13 перечисляет CUDA12 DLL, поэтому не используется как готовый загрузчик CUDA13. Список необходимых зависимостей берётся из закреплённых артефактов.

| Модель / предпочтение | Порядок попыток после продуктовой приёмки CUDA |
|---|---|
| GGUF, `auto`, NVIDIA | CUDA → Vulkan той же физической карты → CPU |
| GGUF, `auto`, другая GPU | Vulkan → CPU; на macOS Metal → CPU |
| ONNX обычная bge-m3 и rerank, `auto`, NVIDIA | CUDA → DirectML → CPU |
| ONNX `BAAI/bge-m3:fp16`, `auto` | CUDA после отдельной приёмки того же FP16-артефакта → DirectML; CPU запрещён |
| ONNX, `auto`, другая GPU Windows | DirectML → CPU; для FP16 embed CPU запрещён |
| Любая поддерживающая CPU модель, `cpu` | Только CPU; FP16 embed с таким значением отклоняется до скачивания |

GPU выбирается явно, слои не распределяются по всем найденным картам. Для CUDA и Vulkan физическая идентичность сопоставляется по PCI bus id; для ONNX CUDA/DXGI — по проверяемой идентичности адаптера, не по совпадению ordinal `0`. В отсутствие точного сопоставления DirectML использует свой детерминированный выбор и сообщает имя фактической карты, не обещая ту же NVIDIA. На нескольких GPU используется первая подходящая дискретная карта в стабильном порядке идентификаторов; встроенная — если подходящих дискретных нет. Политика не является обещанием наиболее быстрой GPU или подбором по объёму VRAM.

llama.cpp дедуплицирует CUDA/Vulkan одной карты в обычном списке устройств. Поэтому повтор на Vulkan должен брать исходный handle Vulkan из реестра backend, до дедупликации, и передавать его явно через `with_devices`; `supports_gpu_offload()` и повтор прежнего конструктора недостаточны. При необходимости используется узкий FFI-адаптер закреплённого API. Backend живёт весь процесс: выгружать CUDA DLL ради отката или переинициализировать глобальный `OnceLock` нельзя.

## Проект CUDA: ошибки и ограниченный откат

Каждая CUDA EP регистрируется с `error_on_failure`; новая попытка DirectML создаёт отдельную сессию, без списка EP, молча скрывающего сбой CUDA. Перед `ready` загрузчик выполняет короткий проверочный Run без записи в индекс; CUDA считается рабочей после его успеха, не по `is_available()`. Сбой на последующем длинном входе тоже обрабатывается таблицей отката. Имя EP описывает сессию: часть узлов ONNX может исполняться на CPU; полное размещение графа проверяется профилем отдельно.

Ошибки устройства, регистрации EP, выделения памяти или выполнения GPU допускают следующую ступень таблицы. Ошибка чтения/хеша/размерности модели, токенизатора или некорректного входа завершает операцию; смена GPU не должна маскировать повреждение данных. Перед новой сессией освобождаются прежние контекст и модель, завершается очередь освобождения; не держатся два комплекта весов ради пробы. Две модели не загружаются параллельно; нынешние приоритет поиска и граница документа сохраняются.

При OOM у GPU-rerank ограниченное уменьшение пачки 16→4→1 остаётся защитой; после исчерпания допускается следующая ступень. Другие GPU-ошибки не вызывают уменьшение пачки. Одна ступень посещается не больше одного раза за загрузку/операцию; цикла CUDA→DirectML→CUDA нет. Сбой вычисления повторяет целиком текущий embed-вызов или все пары rerank с исходным порядком: частичные векторы/оценки не публикуются и не смешиваются. Запись документа в индекс происходит после полного успешного результата. После окончательного отказа embed возвращает ошибку, rerank отдаёт целую выдачу без rerank с `rerank_error` по Т-24.

Причина хранится для каждого неудачного перехода, даже если окончательный CPU тоже не загрузился: этап, backend, major, безопасный код, краткое объяснение и следующая попытка. После отката рабочая ступень сохраняется до выгрузки; отказавшая CUDA не пробуется каждым запросом и обычной повторной загрузкой в том же процессе. Явное `model_retry` или смена устройства разрешают новую попытку с прежними глобальными библиотеками; другой major/комплект требует нового процесса. Действующая пауза фоновой загрузки сохраняется при полном отказе. После установки/замены уже загруженных CUDA DLL окно предлагает перезапустить bars: загруженный модуль нельзя безопасно заменить в процессе.

## Проект CUDA: ускорители и численная совместимость

Отбор опирается на [ограничения измерений 8.1.2](../../knowledge/inference-speed.md): чистый выигрыш новых ускорителей не доказан, а CUDA и DirectML дали разные оценки около порога. Не обещается тождество векторов или пограничной выдачи. Перенос upstream-измерений на закреплённую сборку не считается приёмкой.

| Метод | Предлагаемый начальный профиль 8.1.4 |
|---|---|
| GGUF CUDA/Vulkan | Тот же Q4_K_M-файл, Last pooling, L2, предел 8192; KV F16, flash attention явно выключен; контекст растёт по потребности, microbatch ≤ 512 |
| ONNX CUDA | Прежние артефакты, tokenizer, длины и K; FP32 embed остаётся FP32; FP16 embed — отдельная модель, только после приёмки; TF32 явно выключен |
| Rerank CUDA | Тот же проверяемый FP16-артефакт, начальная пачка 16 с защитой 16→4→1; CPU сохраняет FP32/batch4. Выбор пачки не объявляется оптимумом CUDA |
| Уже используемые оптимизации | ORT Level3, токенизация на CPU, восстановление порядка embed; прежние FP16/пачки DirectML сохраняются |
| Дополнительные ускорители | Q8/Q4 KV, FA, CUDA Graphs, TensorRT/NVRTX, I/O Binding и новые ONNX attention-экспорты выключены/не подключены; отдельного переключателя в 8.1.4 нет |

Перед разрешением CUDA в `auto` требуется продуктовая численная приёмка каждого профиля. Для embed: полный retrieval на собственном заново построенном индексе и смешанные пары CUDA-query/прежний-index и прежний-query/CUDA-index, включая дальнейшее инкрементальное обновление и CPU/Vulkan/DirectML fallback. Проверяются конечность, размерность, нормирование и метрики до/после порога; нескольких cosine недостаточно. Для rerank: сырые логиты, sigmoid, порядок, отрицательные вопросы, лидер/Hit@3/MRR и все пересечения рабочего порога, включая известный `bars-22`. Порог 0,1, K и длины не подстраиваются ради прохождения.

Чистая смена устройства сохраняет нынешний fingerprint только после этой приёмки. Минимальный критерий на замороженном регрессионном корпусе — нет новых провалов лидера/Hit@3, нет снижения MRR и новых ложных результатов отрицательных вопросов; все различия порогового состава перечисляются отдельно. При неприемлемой регрессии CUDA соответствующего профиля остаётся недоступна, `auto` выбирает прежний backend с объяснением «CUDA для этой модели не прошла проверку качества». Тихая замена весов/precision запрещена; если нужен иной вычислительный рецепт embed, он оформляется отдельным профилем через Т-25. Пересечение порога явно предъявляется автору для оценки; одинаковый top-3 не закрывает этот вопрос.

## Проект CUDA: реализация и критерии приёмки

Последовательность 8.1.4: сначала два согласованных динамических ORT и импорты без CUDA; затем единый выбор major до ORT/ggml и явный GGUF backend; далее отдельные ONNX-попытки и ограниченный откат; затем runtime-диагностика и окно; после этого продуктовая матрица. Модули: `Cargo.toml` и платформенные фичи `bars-core`, `crates/bars-core/src/models/{gguf,builtin,builtin_rerank,execution}.rs`, менеджер `crates/bars-worker/src/worker/models.rs`, `ModelRuntime` в `bars-protocol`, `ui/src/lib/DevicePicker.svelte`, сборка и установщик. Версии зависимостей без отдельной необходимости не повышаются; Cargo registry не редактируется.

1. Проверить запуск собранного и установленного пакета без CUDA, без cuDNN, на не-NVIDIA и CPU-only; отдельно только CUDA12.8, только CUDA13.0 и обе major на Turing+. Проверить неполную 13 при рабочей 12, несовместимые варианты cuDNN, повреждённый provider и неработающий драйвер. Без cuDNN CUDA GGUF остаётся доступной. CPU/DirectML работают в каждом комплекте без CUDA; Mac-путь не получает Windows-зависимостей.
2. Проверить CUDA→Vulkan той же карты и CUDA→DirectML→CPU, две GPU и дедупликацию, загрузку и первый/последующий Run, OOM, полный отказ и `model_retry`. FP16 embed не становится FP32 автоматически; ни один EP/сбой не теряется в диагностике.
3. Проверить две модели в одном процессе и каждой major, холодную загрузку, поиск при индексации, смену настройки во время работы, выгрузку и повтор. Отдельно проверить CPU→GPU после фиксации ORT, необходимость перезапуска при смене major и отсутствие второго ORT/смешанных cuDNN в процессе. Запросы состояния не грузят модель, не читают DLL/веса заново и не продлевают простой.
4. Выполнить численную матрицу каждого профиля из раздела о совместимости. Причинную скорость измерять отдельно: чередующиеся baseline, прогрев, median/p95 полного поиска и индексации, собственная память/VRAM и фоновая нагрузка. Ускорение без тихого окна не заявлять; защиту памяти не ослаблять.
5. Проверить окно на CPU, CUDA и каждом fallback: фактическое устройство, цепочка причин, состояние «ещё не загружена», доступные действия; каталог установленного пакета и portable-набор. Прогон установленной сборки — по отдельному согласованию автора.
6. После ревью реализации исправить замечания, затем выполнить `pwsh -File scripts/check.ps1` с `CARGO_TARGET_DIR=C:/bt/bars`. Численная/аппаратная матрица и полный гейт — разные доказательства; одно не заменяет другое.

## Каталог встроенных embed-моделей

Мера снижения активного расхода памяти — явный переход с FP32 bge-m3 на FP16 в Windows/DirectML. Выбор основан на матрице одного корпуса и протоколе качества в [исследовании памяти](../../knowledge/memory.md); это снижение измеренного расхода, а не жёсткий лимит RAM. Заводская модель и существующие индексы автоматически не меняются. Когда текущая bge-m3 работает на DirectML, вкладка «Модели» предлагает «Выбрать FP16» с предупреждением о переиндексации. Кнопка меняет только черновик настроек; запись — через «Сохранить», переиндексация — отдельно после согласия Т-25. Отмена черновика возвращает прежний выбор.

FP16-профиль bge-m3 для Windows: `BAAI/bge-m3:fp16`, ONNX/DirectML, 1024 измерения, предел 8192 токенов, без префиксов. Заводской выбор — прежняя FP32 bge-m3. FP16 требует отдельного индекса и согласия Т-25; при выборе окно устанавливает DirectML, CPU для этого профиля недоступен. Если GPU-сессия не открылась, возвращается ошибка; переход на обычную bge-m3 выполняется явно с переиндексацией. Это предотвращает смешивание разных энкодеров. Приёмка и ограничения.

| Модель | Backend | Размерность | Префиксы | Статус |
|---|---|---:|---|---|

| `BAAI/bge-m3:fp16` | fastembed / ONNX Runtime FP16 | 1024 | не нужны | Windows/DirectML; отдельный индекс; полная приёмка памяти/индексации открыта |

## GGUF: устройство, контекст и память

Qwen Q4_K_M загружает закреплённый артефакт с проверкой длины/SHA-256; источники, ревизии и хеши — [исследование GGUF](../../knowledge/gguf-models.md). Файл 0.6B — около 396 МБ, 4B — 2,50 ГБ. Это размер файла, не полная RAM/VRAM: память контекста и вычислений добавляется к весам. Непроверенные замеры нельзя заменять оценкой размера кванта.

`Cpu` запрещает offload, `Auto` предпочитает Vulkan на Windows / Metal на macOS. Ошибка GPU при загрузке или вычислении даёт CPU fallback с причиной в runtime; веса, квант и отпечаток те же. Один backend на процесс, по одному контексту на модель; модель/контекст освобождаются штатным lifecycle воркера. macOS не проверена.

Контекст создаётся лениво под фактическую длину входа: степень двойки от 256 до 8192. При росте прежний контекст освобождается до новой allocation. Microbatch не больше 512; между текстами очищается KV-cache. Last-token pooling, EOS, конечный нормализованный вектор ожидаемой размерности. Вход длиннее 8192 токенов усекается с сохранением EOS. Смена устройства не меняет отпечаток, смена артефакта/кванта/инструкции/предела входа меняет.

## candle: Nomic и память

Nomic v2 MoE остаётся на CPU FP32 через fastembed. `embed.accelerator` на Nomic не влияет; окно сохраняет предупреждение про CPU и предел 512 токенов. Перенос на другой runtime требует отдельной проверки encoder/pooling и качества; наличие официального Nomic GGUF само по себе этого не доказывает.

## Встроенная rerank-модель

`BAAI/bge-reranker-v2-m3` (`TextRerank`, ONNX Runtime) — логическая встроенная rerank-модель (Т-17). DirectML использует закреплённый FP16-экспорт `onnx-community/bge-reranker-v2-m3-ONNX@6f5ff65298512715a1e669753bc754d2bc8f367b`, `onnx/model_fp16.onnx` (1 136 209 678 байт); tokenizer/config — `rozgo/bge-reranker-v2-m3@fbd57b17b4db111a9d16813bb08b4c804fac18e9`. Все пять файлов проверяются BLAKE3 перед открытием GPU-сессии. CPU сохраняет штатный FP32 `RerankerModel::BGERerankerV2M3` из `rozgo/bge-reranker-v2-m3`. INT8 не выбран: при текущем пороге обнаружена потеря качества ([результаты](../../knowledge/inference-speed.md)).

## Префиксы запросов и документов

Префикс — часть того, как модель обучена, поэтому bars добавляет его сам, а не пользователь:

- Qwen3-Embedding: к запросу добавляется строка-инструкция `Instruct: Given a search query, retrieve relevant passages from documentation\nQuery: `; документ эмбеддится без префикса.
- Nomic Embed v2 MoE: к запросу — `search_query: `, к чанку — `search_document: `.
- bge-m3: без префиксов.

Префикс документа входит в отпечаток модели (см. «Отпечаток модели»): если он поменяется, понадобится переиндексация.

## Длина входа встроенных моделей

Нарезка таблиц и списков реестров учитывает окно rerank: части до 1500 символов вместе с шапкой таблицы ([контракт нарезки](../indexing/chunking.md)). Предел модели остаётся 512 токенов; длинный запрос, путь или заголовок могут занять часть этого окна.

fastembed по умолчанию обрезает вход до 512 токенов и делает это молча. Для чанка до 6000 символов (Т-18) этого мало: русский текст — примерно 3–4 символа на токен, и хвост большого раздела не попал бы в вектор. Поэтому bars задаёт длину входа явно (`with_max_length`):

| Модель | Предел модели | Длина входа в bars |
|---|---|---|
| `BAAI/bge-m3` | 8192 токена | 8192 |
| Qwen3-Embedding 0.6B / 4B | 32 768 / 40 960 токенов | 8192 |
| Nomic Embed v2 MoE | 512 токенов | 512 |
| `BAAI/bge-reranker-v2-m3` | 8192 токена на пару «запрос + чанк» | 512 |

- **Nomic Embed v2 MoE.** Чанк длиннее примерно 1500 символов в вектор попадает не целиком. Полнотекстовый поиск всё равно видит его весь. При выборе этой модели окно предупреждает об обрезке и предлагает уменьшить `max_chars` ([features/settings/settings.md](../settings/settings.md)).
- **Rerank.** Вход ограничен 512 токенами, а на реранк уходят 15 кандидатов (`rerank_candidates`): на прототипе 30 пар по 1024 токена занимали 15–29 с. Начало чанка — путь, цепочка заголовков и первые абзацы — в оценку попадает, хвост длинного чанка — нет: по замеру 24-10-2026 строка таблицы, начинающаяся дальше примерно 1900-го знака, получает оценку около нуля ([бенч качества](../../knowledge/search-quality.md), «Реестры: почему строки теряются»). Кандидаты на rerank во встроенном llama.cpp с длинным входом отобраны в [исследовании rerank GGUF](../../knowledge/rerank-gguf.md); в продукт они ещё не входят.
- **Пачки.** fastembed дополняет все тексты пачки до самого длинного. Поэтому перед эмбеддингом чанки сортируются по длине, и длинный чанк не заставляет считать короткие соседние как длинные.

## Оценка встроенного реранка

`TextRerank` в fastembed возвращает сырой логит модели и сортирует результаты по убыванию. bars восстанавливает порядок документов и применяет сигмоиду: оценка от 0 до 1 (`BuiltinReranker`). Неконечные логиты, повторные или неверные индексы отклоняются. DirectML FP16 считает пары по 16, CPU FP32 — по 4; вход остаётся 512 токенов. При ошибке выделения GPU-памяти повторяется весь запрос с batch4, затем batch1; уменьшенная пачка сохраняется в сессии, число повторов ограничено. Иные ошибки не скрываются этим повтором. Это защита, а не аппаратная приёмка слабых GPU. Устройство задаётся независимо через `rerank.accelerator`; если GPU не инициализируется, используется CPU FP32 с причиной fallback. Порог и шкала Т-24 сохраняются ([настройки](../settings/settings.md)).

## Где лежат скачанные модели

Все встроенные модели скачиваются в `<домашняя папка>/.bars/models/` (Т-17), а не в `.bars` проекта. Папка задаётся через `with_cache_dir` для ONNX-моделей и `FASTEMBED_CACHE_DIR` для candle-моделей. Переменная окружения `HF_HOME` в fastembed перекрывает обе настройки, поэтому при создании провайдера моделей (`ConfiguredProvider::new`, при старте воркера, до рабочих потоков) bars выставляет `FASTEMBED_CACHE_DIR` и убирает `HF_HOME` из окружения процесса: модели всегда лежат в папке bars, что бы ни было задано у пользователя.

Модель скачивается при первом использовании. Пока идёт скачивание, состояние индекса показывает его ход.

Кнопка «Скачать» для встроенной bge-m3 получает семь файлов через hf-hub без создания ONNX-сессии. Она не проверяет исполнение графа и не переводит runtime в «готова»: модель открывается при первой работе. Для остальных встроенных моделей пока сохраняется загрузка с последующим drop. Пустой файл означает ошибку скачивания; наличие непустых FP32-файлов не гарантирует корректность графа, его исполнение проверяется отдельно.

## Когда модели освобождают память

При смене настроек старый слот сохраняется у выполняющегося запроса. После последнего владельца освобождение сессии уходит в отдельный поток менеджера, поэтому медленный drop не задерживает короткие async-вызовы. Перед новой встроенной загрузкой завершаются уже переданные освобождения: очередь очистки не оставляет старую свободную сессию в памяти на время нового constructor. Освобождение и загрузка разделяют общий замок; shutdown ждёт переданные освобождения (ISS-79).

Встроенный rerank по умолчанию освобождается после 5 минут простоя, embed — после 15 минут. Срок для каждой модели задаётся в настройках (`unload_after_minutes`, окно «Настройки → Модели → Выгрузка из памяти»), `0` — не выгружать ([settings.md](../settings/settings.md)). Отсчёт начинается после завершения работы; опрос окна его не продлевает. Worker проверяет свободные сессии каждые 10 секунд, а сохранение настроек будит проверку сразу. Отключение rerank освобождает его при ближайшем свободном проходе; идущий запрос не прерывается. Внешние HTTP-провайдеры в эту политику не входят.

Следующий запрос заново открывает сессию из кэша; возможны дополнительная задержка и промежуточный `model_loading`. Веса на диске, индекс и параметры поиска сохраняются. Это уменьшает память в простое; активный пик снижается precision/пачками. Устройство и фактическая точность (`FP16`/`FP32`) видны в состоянии сессии, закреплённая GPU-ревизия доступна через `models_info`. Сроки по умолчанию — инженерный компромисс; Mac и слабые GPU отдельно не приняты. Замеры памяти — [knowledge/memory.md](../../knowledge/memory.md), оставшаяся работа — [memory-plan.md](memory-plan.md).

## Когда модель считается скачанной

Embed FP16 использует пять закреплённых файлов Xenova/bge-m3, revision `4de13258303883538bd53b696b452bf8099f0858`: `onnx/model_fp16.onnx` и четыре tokenizer/config файла. Они проверяются BLAKE3 перед записью атомарной отметки с размером/mtime/путём/хешем. Метаданные изменились — готовность сбрасывается. Проверка статуса не хеширует веса; повторное открытие неизменённого проверенного кэша использует отметку. Кнопка «Скачать» не создаёт сессию.

Каталог моделей (`bars-core/src/models/catalog.rs`) знает полный список файлов каждой встроенной модели; модель скачана, когда в одном снимке кэша лежат все эти файлы и ни один не пуст. Одного `model.onnx` мало: у bge-m3 малый граф готов раньше большого файла весов `model.onnx_data`, а hf-hub кладёт файл в снимок только после полного скачивания.

- **bge-m3:** `config.json`, `special_tokens_map.json`, `tokenizer.json`, `tokenizer_config.json`, `onnx/model.onnx`, `onnx/model.onnx_data`, `onnx/Constant_7_attr__value`.
- **Rerank CPU FP32** (кэш `rozgo/bge-reranker-v2-m3`): те же четыре файла токенизатора и `model.onnx`, `model.onnx.data`.
- **Rerank DirectML FP16:** `onnx/model_fp16.onnx` точной ревизии ONNX-community и четыре файла tokenizer/config точной ревизии rozgo. CPU-вариант не требует FP16. Метка окна использует выбранное устройство, а после фактического CPU fallback — CPU-кэш. Прогресс до готовности сессии оценивает предпочитаемый GPU-вариант. Готовность FP16 фиксируется атомарным manifest в `models/bars-verified/` после проверки всех пяти BLAKE3; manifest включает путь, размер, время изменения и ожидаемый хеш каждого файла. Изменённый, неполный или другой snapshot не считается скачанным. Опрос окна сверяет метаданные без повторного чтения гигабайта весов; loader проверяет содержимое перед открытием. 100% означает проверенные файлы предпочитаемого варианта, но сессия ещё может загружаться.
- **candle-модели (Qwen3, Nomic):** `config.json`, `tokenizer.json` и веса `model.safetensors`; у модели с шардами — все файлы из `weight_map` в `model.safetensors.index.json`.

Ход скачивания считается по размеру файлов в `blobs/` кэша выбранного варианта (вместе с недокачанными `.incomplete`) относительно ожидаемого размера; пока нужные файлы не готовы, не больше 99 %. Это приблизительный прогресс, не проверка целостности. Если GPU fallback потребовал CPU-веса, состояние `loading` сохраняется до готовности CPU-сессии. Регистрация DirectML проверяется до скачивания GPU-весов.

## Один замок на скачивание и загрузку

Скачивание кнопкой «Скачать», загрузка модели для поиска и загрузка для индексации идут через один замок воркера: две загрузки не идут одновременно, вторая находит файлы в кэше и не качает их заново. Поиск замок не ждёт: пока модель скачивается или грузится, он сразу отвечает `model_loading` с ходом скачивания в `data.percent`. Загруженная модель, занятая пачкой индексации или другим запросом, считается готовой: поиск встаёт в очередь перед следующей пачкой и `model_loading` не получает (ISS-18). MCP-прокси на `model_loading` сам повторяет вызов до 60 с ([mcp-tools.md](../agent-tools/mcp-tools.md)); если модель не загружена и никто её не грузит, поиск запускает загрузку в фоне и отвечает так же. Ошибка фоновой загрузки возвращается поиску как `provider_error` до конца паузы перед повтором (раздел «Пауза перед повтором загрузки»), после неё поиск пробует снова. Rerank при этом не задерживает поиск: пока его модель скачивается или грузится, выдача идёт без rerank, причина — в `rerank_error` (Т-24).

Qwen GGUF готов только после проверки закреплённого файла по длине и SHA-256; атомарная метка в models/bars-verified/ связывает хеш, размер и время изменения. Изменённые метаданные сбрасывают готовность. Кнопка скачивания не создаёт модель и KV-cache.

## Пауза перед повтором загрузки

Реализовано в шаге 5.2.1 (ISS-71); числа — решение агента по образцу повтора расчёта графа ([реализация GraphRAG](../graphrag/implementation.md)). После неудачной фоновой загрузки модели поиск не запускает её снова сразу: пока идёт пауза, каждый поиск получает ту же ошибку `provider_error`, а загрузка не стартует. Пауза растёт с каждой неудачей подряд: 30 с, 60 с, 120 с, 240 с, дальше 5 минут. Успешная загрузка или скачивание обнуляют счёт. Кнопка «Повторить» на экране ошибки зовёт `model_retry`: паузы всех моделей и счёт сбрасываются, следующий поиск грузит модель сразу. Скачивание кнопкой «Скачать» паузой не ограничено. Проверка «никто не грузит» и запись заявки на фоновую загрузку идут под одним замком, поэтому два одновременных поиска запускают один поток загрузки. Индексация паузу не учитывает: она грузит модель сама и каждая её неудача увеличивает счёт.

## Приёмка продуктового FP16 rerank

Продуктовый `BuiltinReranker` принят отдельной проверкой: 138 полных ответов ядра и 22 настоящих IPC-ответа дали ноль новых потерь выбранных метрик при порогах 0 и 0,1 и не потребовали CPU fallback; реальный CPU-тест подтверждает FP32/batch4 и исходный порядок оценок. Ветка уменьшения пачки 16→4→1 при ошибке allocation проверена unit-тестом, а не физическим малым GPU. Эти прогоны `quality-only`, их время не входит в чистое сравнение скорости (данные и хеши, [результаты](../../knowledge/inference-speed.md)). Проверена только зафиксированная сборка: поздние правки общих исходников воркера не получают физическую приёмку автоматически.

FP16 embed (`bge-m3:fp16`) — отдельный профиль, а не замена заводской модели. 20-10-2026 новым загрузчиком созданы два полных индекса bars/overdrive; 24 + 100 + 14 вопросов без новых потерь. Исследовательская индексация передавала каждый chunk отдельно, без усечения. Один настоящий worker с обеими FP16-моделями дал lifetime peak 4,46 ГиБ; второй процесс не стартовал по commit. Чистая скорость, повторяемость пары и естественные 5000 chunks НФТ-2 не приняты ([метод и данные](../../knowledge/memory.md#аппаратное-продолжение-20-10-2026), [оставшаяся работа](memory-plan.md)). INT8 rerank и embed отклонены из-за потери качества. Слабые GPU, ноутбук и другие EP отдельно не проверены.

## Отпечаток модели

В индексе проекта записан отпечаток модели, которой он построен:

- источник (`builtin`, `remote`, `local-openai`);
- идентификатор модели; для Qwen GGUF — также подпись backend/кванта/repo/revision/файла/хеша/предела входа/инструкции/pooling;
- размерность;
- префикс документа.

Если отпечаток в настройках не совпадает с отпечатком индекса, срабатывает Т-25: предупреждение, переиндексация только по согласию, до неё поиск по проекту не работает.

## Сборка и производительность встроенных моделей

`bars` собирается с fastembed 7.1.1 (`nomic-v2-moe`, Windows `directml`) и llama-cpp-2 0.1.160 (Windows `vulkan`, macOS `metal`), поэтому все модели каталога доступны без пересборки ([architecture/stack.md](../../architecture/stack.md)). ONNX Runtime вшит в `bars` статически; готовые сборки для x86-64 требуют процессор уровня x86-64-v3 (Intel Haswell и новее).

## Устройство встроенных моделей

По умолчанию встроенные модели считаются на видеокарте, если она есть, иначе на CPU (независимые `embed.accelerator` и `rerank.accelerator` в [features/settings/settings.md](../settings/settings.md)):

- ONNX на Windows — DirectML. Работает на любой видеокарте с DirectX 12, в том числе на встроенной Intel Arc.
- ONNX вне Windows использует CPU; CoreML не подключён. GGUF использует Vulkan/Metal либо CPU по правилам раздела о GGUF.
- Если видеокарта не запустилась, воркер пишет это в лог и переходит на CPU.

Диагностика rerank сохраняется в [журнале воркера](../window/logs.md): при загрузке — устройство, precision, batch и файлы модели с размерами (уровень информации); каждый вызов — число пар и пределы сырых логитов до сигмоиды (отладка). Если максимум ниже −8, запись получает уровень предупреждения и пометку «подозрительно». Для полной диагностики в окне выберите «Отладка и выше».

Видеокарта выбрана даже без прироста скорости, потому что снимает нагрузку с процессора (OQ-27). На проверенных 24 чанках косинус CPU/DirectML — 1.000000; устройство не входит в отпечаток модели. Это локальная проверка, не гарантия для новых экспортов, precision и драйверов.

NPU в bars не подключён. Для Intel AI Boost исследуется OpenVINO; для других производителей нужны соответствующие EP. Совместимость с закреплённым runtime и bge-графами не проверена. Ограничения устройств, DirectML и варианты библиотек — [knowledge/inference-devices.md](../../knowledge/inference-devices.md).

## Скорость встроенных моделей

На i7-11700KF / RTX 3090 FP16 rerank на DirectML даёт полный поиск с rerank около 0,4–0,5 с (медиана), FP32 — около 0,7 с ([замеры](../../knowledge/inference-speed.md)). Старые замеры на Intel Core Ultra 5 125H под нагрузкой ([knowledge/spike-search.md](../../knowledge/spike-search.md)):

- bge-m3 эмбеддит около 0,5 с на чанк и на CPU, и на встроенной видеокарте. Проект на 5 000 чанков индексируется в первый раз около 40 минут, в фоне. Дальше переиндексируются только изменения (НФТ-1).
- Эмбеддинг запроса — около 50 мс.
- Встроенный rerank — секунды на запрос, поэтому он по умолчанию выключен.
- Qwen3-Embedding-4B на CPU будет ещё медленнее bge-m3, и окно предупреждает об этом при выборе модели.
- Пачки эмбеддинга — по 4 чанка: на прототипе это быстрее пачек по 16.
