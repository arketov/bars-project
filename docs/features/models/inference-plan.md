# Этап 11 — измерение и ускорение инференса

Статус: исследование завершено 18-10-2026; FP16 rerank внедрён в продуктовом коде и проверен отдельной сборкой. Итог — [inference-speed.md](../../knowledge/inference-speed.md); основание — Т-3, Т-17, НФТ-2. Физическая приёмка других GPU и естественного корпуса5000 не закрыта.

Широкая сетка завершена по приоритету автора. Полный поиск 138 вопросов и IPC 44 ответа прошли; отдельная приёмка продуктового FP16 loader — ещё 138 core и 22 IPC-ответа без новых потерь и CPU fallback. FP16 embed остаётся кандидатом до проверки retrieval своего индекса. Параллельные изменения общих исходников отражены в `sourceDrift` доказательств: приёмка относится к зафиксированной сборке, не автоматически к новым доработкам lifecycle.

## Результат, нужный автору

Уменьшить время embed, индексации и многосекундного rerank, сохранив качество поиска. Нужны измеренные причины задержки, сравнение применимых способов на этой машине и воспроизводимые доказательства. Перечень возможностей ORT сам по себе этап не закрывает.

Связанные задачи: [ISS-09](../../backlog/issues.md#iss-09-проверить-что-индексация-не-мешает-запросам-rag), [ISS-03](../../backlog/issues.md#iss-03-rerank-на-другой-машине-даёт-оценки-меньше-01), [IDEA-01](../../backlog/ideas.md#idea-01-embed-и-rerank-на-разных-устройствах), [IDEA-06](../../backlog/ideas.md#idea-06-реальные-замеры-моделей-с-rerank-и-без-и-настройка-по-ним). Диагноз другой машины требует её логов; успех RTX 3090 не закрывает ISS-03. Замер ноутбука, управление памятью как продуктовая фича и GGUF-интеграция — отдельные работы, здесь фиксируются зависимости.

## Проверенное исходное устройство

Serena Rust LSP проверен запросами символов и ссылок. Просмотрены загрузчики embed/rerank, слоты воркера, `bench_quality`, методика и результаты этапа 9, настройки и закреплённые зависимости. Рабочая копия содержит параллельные изменения; baseline обязан включать ревизию и хеши реально собранных исходников.

Проверка относится к локально установленным исходникам fastembed, не гарантирует их тождественность чистому архиву crate. До бенча сверить checksum/происхождение зависимости; сохранить хеши, включая возможные локальные патчи. Регистрировать фактический EP и размещение узлов: `Device::DirectMl` сообщает выбор сессии, а не доказанное выполнение каждого узла на GPU.

На этой машине подтверждён i7-11700KF, 8 ядер / 16 логических процессоров. RTX 3090 и остальные условия предыдущего замера описаны в [hardware.json](../../knowledge/quality-2026-10-18/hardware.json); перед новыми прогонами обновить сведения, драйвер, память и фоновые нагрузки.

## Архитектура измерительного стенда

Сначала Rust example в `bars-core` для чистых моделей и полного поиска, затем интеграционный контур в `bars-worker` для конкуренции и IPC. Экспериментальные параметры не добавлять в пользовательский `settings.toml` до результатов. Переиспользовать `examples/quality`, `scripts/analyze-quality.mjs` и снимки этапа 9 после проверки манифестов; исходный overdrive-проект не изменять.

Разделить три нагрузки: embed фиксированных текстов; rerank фиксированных пар query/chunk; настоящий `search` на снимке. Изолированный rerank получает один и тот же пул кандидатов baseline. Изменённый embed проверяется на заново построенном собственном индексе: новые query-векторы со старыми document-векторами не являются полным тестом варианта.

Структура результата в новой папке внутри `spikes/`: manifest/config, sessions.jsonl, rows.jsonl, ORT profile, summary, checksums. В итоговой базе знаний сохранить компактные доказательства и оглавление. Файлы этапа 9 не перезаписывать. Для каждого запуска — model/tokenizer hashes, runtime build info, бинарник, конфигурация, аппаратные условия и статус complete/failed/unsupported; fallback не засчитывать как ускорение выбранного EP.

Таймеры: загрузка без скачивания, первый Run, warm Run; токенизация, подготовка тензоров, Run, постобработка; в полном пути — ожидание слота, embed, retrieval, rerank, IPC и внешнее время клиента. Не вычитать результаты разных запусков. Вложенные интервалы не суммировать повторно. Профиль ORT собирать отдельным диагностическим прогоном; итоговую скорость мерить без его накладных расходов.

Сетка ступенчатая: сначала дешёвый отсев на заранее фиксированной части train, затем полный train для лучших вариантов. Не перемножать все параметры. Порядок A/B чередовать, повторять baseline между вариантами; тяжёлые тесты запускать последовательно. Сначала пригодность метода, затем качество и скорость; каждый неприменимый вариант получает конкретную причину, а не обещание будущего ускорения.

ORT profiling, inter-op, I/O Binding и произвольный session builder не считаются открытыми через стандартный конструктор fastembed только потому, что существуют в ORT. Проверить публичный API закреплённой обёртки. Если его недостаточно — минимальный исследовательский адаптер/отдельный спайк, без обходного изменения Cargo registry. Стек Rust сохраняется; готовые ONNX-экспорты проверять по происхождению, не добавлять Python-путь в проект.

## Протокол скорости, памяти и качества

- До опыта заморозить конфигурации, вопросы, порядок запусков и правило выбора. Старый test этапа 9 уже просмотрен: использовать как регрессию, не называть новым независимым подтверждением. Для выбора новой модели/усечения/кванта подготовить свежую отложенную разметку до выдачи.
- Скрининг: три прохода фиксированного train. Финалисты: минимум 100 warm-наблюдений на конфигурацию, распределение по длинам и вопросам; median/p95, n и сырые строки. Cold load и first Run отдельно, с числом запусков. Повторения одного вопроса не увеличивают объём разметки качества.
- Качество: leader/Hit@1, Hit@3, MRR@10, nDCG@10, recall первого этапа, ложная выдача отрицательных вопросов; список потерь по идентификаторам и длинным разделам. Сравнивать и до порога, и при рабочих порогах. Сначала проверить порядок/логиты/векторы, затем метрики поиска.
- Для эквивалентных оптимизаций предложение — отсутствие новых провалов лидера/Hit@3 на замороженном наборе и отсутствие снижения MRR; численные допуски определить до отбора по CPU/GPU-сверке. Потерю качества не скрывать агрегатом. Это правило отбора опыта, не добавленное требование автора.
- Режимы финала: один запрос, серия, несколько одновременных запросов через воркер, запросы при индексации. Публиковать задержку каждого запроса и пропускную способность; очередь не выдавать за параллельный GPU Run. DirectML запрещает одновременный Run одной сессии.
- Индексация: тот же корпус, чанки/с и токены/с, полный wall time; полный и инкрементальный проход отдельно. НФТ-2 проверить отдельным корпусом до 5 000 чанков; 946 чанков этапа 9 не доказывают эту границу.
- Память: peak private bytes/working set процесса, VRAM и shared GPU memory, условия замера; отсутствие OOM и роста после повторов. Pagefile не менять. Постоянную нагрузку установленного bars и посторонние процессы учитывать в манифесте.

Ограничения EP подтверждены по первичным источникам 18-10-2026: [ORT DirectML](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html), [ORT threading](https://onnxruntime.ai/docs/performance/tune-performance/threading.html). Обзор precision и альтернативных библиотек — в [базе исследования](../../knowledge/inference-speed.md). Поддержка EP библиотекой не означает наличие EP в статической сборке bars.

## Внедрение после измерений

Решение автора 18-10-2026: закончить широкую сетку опытов и перейти к практическому ускорению; учитывать слабые машины и отсутствие GPU, отдавать вычисления дискретной GPU ради CPU/RAM, токенизацию оставить на CPU. INT8 применять только при сохранении качества. Результат текущего отбора: FP16 rerank на DirectML; INT8 rerank потерял Hit@3/MRR при пороге 0,1 на `od-010`, поэтому умолчанием не становится.

Первое внедрение: закреплённый FP16 ONNX `onnx-community/bge-reranker-v2-m3-ONNX@6f5ff65298512715a1e669753bc754d2bc8f367b`, тот же проверенный tokenizer `rozgo/bge-reranker-v2-m3@fbd57b17b4db111a9d16813bb08b4c804fac18e9`. Проверка BLAKE3 артефактов; общий кэш hf-hub. DirectML использует FP16 и batch16; при ошибке выделения памяти пачка уменьшается до 4, затем 1 с повтором всего запроса и сохранением уменьшенного размера. CPU использует прежний FP32 и batch4; ошибка инициализации GPU ведёт на CPU. Нельзя держать две рабочие сессии ради коротких запросов или считать результаты RTX 3090 доказательством скорости ноутбука. Кэш и процент скачивания учитывают выбранный вариант; CPU-вариант не требует скачивания FP16. Число кандидатов, длина входа, шкала и пороги сохраняются.

FP16 embed не внедряется до полного retrieval на новом индексе. Микробенч векторов и успешная индексация не доказывают сохранение поиска. Новые ABBA, I/O Binding, cache и дополнительная сетка потоков прекращены по приоритету автора; уже собранные результаты сохраняются. Проверки внедрения — целевые тесты, реальные загрузки GPU/CPU и полный путь поиска; это не новая широкая исследовательская серия.

Для worker/IPC каждый ответ проверяется на rerank fallback; режим при индексации начинается только после подтверждения активного задания с ограниченным ожиданием. Монитор перед запуском требует тихое окно и свободную память; ожидание ограничено 120 секундами. При потере запаса памяти завершается только собственный процесс, серия останавливается; исключения монитора также освобождают собственный дочерний процесс. Это защита измерения, а не управление приложениями пользователя.

После наблюдения peak private около 4 ГБ у одиночного FP32 rerank: preflight `run` требует свободный commit ≥9 ГБ; режимы с embed/worker оставляют ≥12 ГБ. Для всех требуется RAM ≥8 ГБ; аварийные границы RAM 2 ГБ / свободный commit 4 ГБ сохранены. Граница запуска — резерв стенда, не характеристика минимальных требований продукта.

Для функциональной приёмки нового FP16 loader разрешён явный `MinimumCommitGiB=9`: измеренный общий private peak FP16 worker около 6 ГиБ плюс резерв3ГиБ. Параметр записывается в монитор; значения ниже9 запрещены, аварийные границы сохранены. Эти прогоны `quality-only`, их время не добавляется в чистое сравнение скорости. Порог12ГиБ старого FP32-стенда не является минимальным требованием bars.

Если фоновые сборки не дают тихого окна, отдельные прогоны `quality-only` проверяют совместимость/качество при тех же границах памяти. Их timingValid принудительно false независимо от списка фоновых процессов. Они не участвуют в выборе по задержке; финалисты требуют отдельного чистого повтора.

Тихое окно исключает также `cargo`: после завершения rustc cargo может продолжать реальные интеграционные тесты с моделями (наблюдался `search_corpus`, около 3,5 ГБ private). Отсутствие rustc само по себе не означает отсутствие тестовой нагрузки.

Режим `index` стенда выполняет настоящий `update_index` на новой копии замороженных документов: пустой индекс → полный проход → проверка без изменений → изменение одного документа в копии и инкрементальный проход. Загрузка/прогрев модели исключены из времени прохода; число документов/чанков/векторов и проблемы сохраняются. Microbenchmark 64 текстов отдельно не подменяет этот результат.

Отдельный опыт форм: фиксированный padding 512 при прежнем усечении 512, с исходными pad-token/mask параметрами tokenizer. Содержимое пары не укорачивается относительно baseline; измеряются возросший паддинг, логиты/качество и задержка. Это проверка одной формы, не доказательство произвольных оптимальных buckets.

Изолированный `binding` сравнивает обычный Run, новое CPU-input/output binding при каждом Run и постоянно связанные неизменные входы. Последний режим — только верхняя граница для повторения одинаковых входов, не путь новых поисковых запросов. В первых двух учитываются binding/копирование/синхронизация и проверяется совпадение всех логитов; модель и тензоры одинаковы, порядок режимов чередуется.

Полный retrieval оценивается по замороженному `cases.json` с проверкой BLAKE3. Разметка не выводится из прежних top-15: при изменении первого этапа новый кандидат сверяется с исходными gold-опорами. Изменение множества кандидатов записывается отдельно, не скрывается и не принимается автоматически за провал качества.

Precision embed проверяется отдельно от rerank: pinned Xenova/bge-m3 ONNX, CLS и нормализация, 1024 измерения, предел 8192. У пользовательского экспорта отдельный fingerprint по BLAKE3 весов; старый индекс не переиспользуется. Dynamic INT8 считает каждый текст отдельно: fastembed предупреждает о несовместимости векторов при изменении состава dynamic-batch. После полного индексирования сохраняется отдельная копия индекса до инкрементальной правки; полный поиск берёт embedding-конфигурацию из её манифеста. Тексты/SQLite другого проекта остаются в ignored data/runs, в Git — только компактные результаты и хеши.

Медленный exploratory INT8 может прерываться по первому проигрышу leader/Hit@3/MRR раздела либо новой ложной выдаче отрицательного вопроса. Один проигрыш только nDCG или документной метрики не прекращает опыт: все показатели продолжают записываться, компромисс описывается отдельно. Первоначальная остановка INT8 на `od-001` по docMRR помечена вспомогательной; секционный MRR там улучшился, поэтому нужен новый прогон с корректным первичным guard. Это уточнение методики, не изменение требований автора.
