# Подключение bars к агентским клиентам

Что делает установка в клиент (Т-21). Её запускают `bars-cli install`, пункт «Установить» в окне или сам агент по текстовой инструкции. После запуска воркер также обновляет существующие интеграции в фоне (IDEA-10, OQ-75/78). Как проверяется и что не подтверждено — в конце документа. Для пользователя то же изложено в [руководстве по агентам](../../manual/agents.md), а какие инструменты агент получает после установки — в [инструментах MCP](../agent-tools/mcp-tools.md).

## Что прописывается в клиенте

Claude Code, Codex и Kimi Code получают две записи с именем `bars`:

- **MCP-сервер** — команда `bars-mcp` по абсолютному пути, транспорт stdio;
- **хук начала сессии** — команда `bars-cli hook session-start` по абсолютному пути ([features/agent-tools/cli.md](../agent-tools/cli.md)).

## Claude Code

| Запись | Файл |
|---|---|
| MCP-сервер | `~/.claude.json`, раздел `mcpServers.bars` (уровень пользователя) |
| Хук | `~/.claude/settings.json`, `hooks.SessionStart`, срабатывает на `startup` и `resume` |

## Codex

| Запись | Файл |
|---|---|
| MCP-сервер | `~/.codex/config.toml`, таблица `[mcp_servers.bars]` |
| Хук | `~/.codex/hooks.json`, событие `SessionStart`, срабатывает на `startup` и `resume`; формат записи тот же, что у Claude Code |

Codex не запускает новый или изменённый хук, пока пользователь не одобрит его командой `/hooks` в Codex; одобрение привязано к хешу записи. Результат установки напоминает об одобрении только при фактическом изменении хука bars. Изменение MCP, skills или чужого хука не вызывает напоминания. Пока хук не одобрен, MCP работает, а проект регистрируется окном или CLI. Окно пока сохраняет консервативную метку неизвестного одобрения (OQ-63).

Проектный `.codex/` bars не использует: Codex грузит его только для доверенных проектов.

## Kimi Code

| Запись | Файл |
|---|---|
| MCP-сервер | `~/.kimi-code/mcp.json`, раздел `mcpServers.bars` |
| Хук | `~/.kimi-code/config.toml`, элемент массива `[[hooks]]` (`event = "SessionStart"`, `matcher = "startup|resume"`); отдельного одобрения хука нет |

Отдельного файла хуков у Kimi Code нет: хук живёт в общем `config.toml`, рядом с providers, моделями и ключами. bars меняет только элементы `[[hooks]]`, чья команда — хук bars, и пишет только разрешённые Kimi поля `event`, `matcher`, `command`: лишнее поле в записи хука делает весь конфиг нечитаемым для Kimi Code. Как и у других клиентов, файл проверяется целиком до первой записи; при ошибке разбора ничего не пишется. Переменная `KIMI_CODE_HOME` не поддерживается: пути строятся от домашней папки (`~/.kimi-code`), как у остальных клиентов.

## Ouroboros

Клиент `ouroboros` подключает bars к `razzant/ouroboros` (уточнение автора 31-10-2026, OQ-233). Статус: реализованы окно, CLI, автообновление и удаление; `cargo check --workspace --lib --bins` и `npm run check` прошли 31-10-2026. Новые тесты не оставлены, полный прогон остановлен по указанию автора (OQ-234). Настоящая сессия Ouroboros и установленная сборка bars не проверялись.

Конфиг — `~/Ouroboros/data/settings.json`: `MCP_ENABLED = true`, в массиве `MCP_SERVERS` одна запись с `id = "bars"`, `name = "bars"`, `enabled = true`, `transport = "stdio"`, абсолютной `command` и пустым `args`. Установка сохраняет чужие серверы и настройки; повторный запуск не переписывает уже правильный файл. Удаление убирает только запись bars и сохраняет общий `MCP_ENABLED`. Фоновое обновление работает только при существующей записи bars и сохраняет явно выключенные сервер и общий MCP.

Хук `SessionStart` и skills этих трёх клиентов в Ouroboros не устанавливаются: его расширения используют отдельный жизненный цикл. Проект нужно зарегистрировать через окно bars или CLI. Нестандартные корни `OUROBOROS_*`, удалённый Ouroboros и контейнерные пути в первой реализации не поддерживаются: локальный exe bars должен быть доступен процессу Ouroboros. Запись использует общий с Ouroboros файл `settings.json.lock` (`create_new`); занятый замок даёт ошибку конкурентной правки, чужой замок не удаляется.

Источники формата и поведения: [MCP-клиент Ouroboros](https://github.com/razzant/ouroboros/blob/ouroboros/ouroboros/mcp_client.py), [корни данных](https://github.com/razzant/ouroboros/blob/ouroboros/ouroboros/launch_roots.py), [конфигурация](https://github.com/razzant/ouroboros/blob/ouroboros/docs/architecture/07-configuration.md).

## iterion

Клиент `iterion` подключает bars к [iterion](https://github.com/SocialGouv/iterion) — оркестратору агентских workflow (решения автора 05-11-2026, OQ-286…OQ-291, «Принять все»). Статус: установщик (окно, CLI, автообновление, удаление) реализован без проверки сборкой, тесты написаны и не запускались; вид worktree проекта-владельца — отдельный шаг плана ([worktrees](../projects/worktrees.md)). Сам iterion не запускался, контракт составлен по чтению его кода.

**Почему плагин.** iterion запускает Claude Code со `--strict-mcp-config` и передаёт MCP только через `--mcp-config`, поэтому запись `bars` из `~/.claude.json` в узлы workflow не попадает (`pkg/backend/delegate/claude_code.go`). Пользовательские skills узлы по умолчанию не видят: iterion грузит только проектный уровень настроек, пользовательский — при `ambient: all` или `operator` (`claude_code_ambient.go`). Плагин (`pkg/plugin/manifest.go`) доставляет MCP и skills во все запуски разом и не требует правки каждого `.bot`; bars не правит общий `plugins.yaml` (OQ-286). Плагины видят бэкенды `claw`, `claude_code` и `pi`; `codex`, `kimi` и `grok` не видят.

| Запись | Файл |
|---|---|
| Манифест плагина | `<корень>/plugins/bars/plugin.yaml` |
| Skill | `<корень>/plugins/bars/skills/bars-docs/SKILL.md` (путь в манифесте — `skills/bars-docs/SKILL.md`; iterion называет skill по имени папки) |

Корень — `ITERION_HOME`, а без неё `~/.iterion`. bars пишет только папку `plugins/bars/`, общий `plugins.yaml` не трогает; удаление — убрать папку `plugins/bars`.

Манифест: `name: bars`, `default_enabled: true` (плагин включён без правки `plugins.yaml`), `contributes.mcp_servers` — одна запись `name: bars`, `transport: stdio`, абсолютный `command` к `bars-mcp`, пустой `args`; `contributes.skills` — только `bars-docs`. iterion копирует skills включённых плагинов в `.claude/skills/<имя>/SKILL.md` рабочей папки каждого запуска (`pkg/runtime/plugin_skills.go`). `bars-session-log` и `bars-end` не ставятся (OQ-287): в запуске нет человека, который завершает сессию, а журнал `docs/chats/` в рабочей копии запуска не к месту; они появятся, когда будет сценарий.

**Только без песочницы.** При `sandbox: auto` и установленных Docker или Podman запуск идёт в контейнере, где stdio-сервер с путём на хосте недоступен: контейнеру доступны только `http` и `sse` (`wireUserMCP` в `claude_code_hooks.go`). Первая версия поддерживает запуски без песочницы (`sandbox: none` или без Docker); сетевой транспорт `bars-mcp` — отдельная фича по отдельному решению автора (OQ-288).

**Хука и `lifecycle` нет**, как у Ouroboros (OQ-290): хуки плагина вливаются в `.claude/settings.json` рабочей копии запуска, а `lifecycle.index` выполняется перед каждым запуском, и каждая временная копия стала бы проектом. Проект регистрируется окном или `bars-cli register`.

**Как MCP находит проект.** Рабочая копия запуска лежит в `~/.iterion/projects/<ключ>/worktrees/<run-id>` — вне репозитория (`pkg/runtime/worktree.go`, `pkg/store/storedir.go`), и ближайшая зарегистрированная папка вверх от неё не находится. Поэтому проект и вид находятся по записи git worktree в репозитории: сессия в такой копии получает вид проекта-владельца со своими правками, а хук копию не регистрирует (OQ-307, OQ-313; контракт — [git worktree как вид проекта](../projects/worktrees.md); разрешение `cwd` и хук написаны шагом 6.3.1 без проверки сборкой, поиск по виду — ещё нет). В репозитории с управляемой папкой `.iterion/` копия лежит внутри него и проект находится по обычному правилу.

**Признак установки и обновление.** Клиент установлен, если есть `plugins/bars/plugin.yaml`; одна папка `plugins/`, чужие плагины или одни skills установку не запускают. Фоновый проход Claude Code → Codex → Kimi Code → Ouroboros → iterion при существующем манифесте перезаписывает его и `bars-docs` по текущему `bars-mcp` (устаревший `command` помечает `stale`); уже правильные файлы не переписываются, копии `.bars-backup` нет: папка плагина принадлежит bars целиком. Манифест пишется только известными строгому разбору iterion полями: `schema_version`, `name`, `version`, `description`, `default_enabled`, `contributes` (`mcp_servers`, `skills`). Окно показывает папку плагина как файл клиента, подпись объясняет ограничение «только без песочницы».

## OpenCode

Клиент `opencode` подключает bars к [OpenCode](https://opencode.ai/) — AI-агенту для терминала (решение автора 17-11-2026, OQ-323…OQ-326). Статус: реализован MCP, skills, окно, CLI, автообновление и удаление.

| Запись | Файл |
|---|---|
| MCP-сервер | `~/.config/opencode/opencode.json` (или `opencode.jsonc`), раздел `mcp.servers.bars` |
| Skills | `~/.config/opencode/skills/<имя>/SKILL.md` (три skills: `bars-docs`, `bars-session-log`, `bars-end`) |

OpenCode использует глобальный конфиг `~/.config/opencode/opencode.json(c)` (при заданном `XDG_CONFIG_HOME` — от него). MCP-сервер прописывается как `type: "local"`, `command: ["<bars-mcp>"]`. Хука начала сессии нет (в OpenCode их нет — только плагины TS/JS), поэтому проект регистрируется в окне bars или командой `bars-cli register`. Skills кладутся в `~/.config/opencode/skills/` — OpenCode их подхватывает автоматически. Удаление убирает запись `mcp.servers.bars` и папки skills bars. Повторная установка обновляет путь к `bars-mcp`, если он изменился.

Фоновый проход автообновления: Claude Code → Codex → Kimi Code → Ouroboros → iterion → OpenCode.

## Ручное подключение других клиентов

Любой клиент, который умеет запускать stdio-MCP (например, чат Claude Desktop через `claude_desktop_config.json`), подключает `bars-mcp` вручную по текстовой инструкции. Хука у таких клиентов нет: проект регистрируется в окне или через CLI, а актуальность держит воркер (Т-10).

## Как bars правит чужие конфиги

- Библиотечный `WorkerConfig::new` не определяет профиль клиента и не разрешает его изменение: `install_env` по умолчанию `None`. Приложение явно включает `InstallEnv::detect()`; тесты установки передают только временный профиль. Изолированный пример приёмки требует `BARS_USER_HOME` и явно задаёт временный профиль и проверяемые исполняемые файлы. Это защищает настоящий профиль от фонового обновления при запуске тестового воркера (ISS-12).
- Перед правкой bars сохраняет копию файла рядом: `<файл>.bars-backup`.
- Меняются только записи с именем `bars`; остальное содержимое и порядок ключей сохраняются.
- Повторная установка обновляет пути в своих записях и не создаёт дублей.
- Абсолютные пути к `bars-mcp` и `bars-cli` bars строит от расположения своего exe. Установщик Windows сохраняет папку при обновлении ([distribution/installer.md](../distribution/installer.md)); после переезда пути исправляет фоновое автообновление. При удалении установщик сам убирает записи `bars`.
- `~/.claude.json` одновременно пишет сам Claude Code, поэтому bars перечитывает его прямо перед записью и пишет атомарно, через временный файл и переименование.
- Чем правятся файлы: `toml_edit` для TOML-файлов Codex и Kimi Code (комментарии и форматирование сохраняются) и `serde_json` с сохранением порядка ключей для всех JSON-файлов (OQ-53).
- Удаление убирает только записи `bars` (Т-21).
- Если файл не разбирается как JSON или TOML, bars ничего не пишет и сообщает об ошибке.
- Файл, который уже в нужном виде, не перезаписывается и копии не получает: повторная установка ничего не меняет и не затирает прежнюю копию.

## Автообновление существующих интеграций

После готовности воркера запускается один фоновый проход Claude Code → Codex → Kimi Code → Ouroboros → iterion. Признак установки (OQ-78) у первых трёх — MCP-ключ `bars`, даже без команды, или распознанный хук bars в `SessionStart`; у Ouroboros — запись bars в `MCP_SERVERS`; у iterion — манифест `plugins/bars/plugin.yaml`. Папка клиента и одни skills не запускают установку; общая папка `.agents/skills` не доказывает наличие Codex. Недостающие части существующей установки восстанавливаются тем же механизмом, которым пользуются окно и CLI; Ouroboros при фоновом обновлении сохраняет выключенные MCP и запись сервера.

Сравниваются фактические поля MCP, хук и встроенные тексты обоих skills, без фильтра по версии или старому пути. Пользовательские правки skills bars перезаписываются (OQ-75). Чужие skills сохраняются; переход по ссылке папки skills остаётся разрешённым (OQ-54).

Обнаружение и установка одного клиента держат тот же внутрипроцессный замок, что ручные install/uninstall. Поэтому завершённое удаление не восстанавливается от запоздавшего фонового прохода. Файловые операции выполняются через `spawn_blocking`, IPC и старт окна их не ждут. Штатный выход и перезапуск дожидаются фоновой задачи.

Перед первой записью разбираются оба конфига клиента. Ошибка чтения, синтаксиса или структуры — диагностика и переход к другому клиенту, а не признак отсутствия установки. Запись нескольких файлов не является общей транзакцией: отчёт сохраняет успешные изменения перед последующей ошибкой. Следующий запуск доводит оставшееся.

Перед заменой JSON/TOML проверяется исходный текст. При конфликте с внешней правкой файл перечитывается, правка пересобирается; после трёх конфликтов возвращается ошибка. Для Ouroboros дополнительно используется его общий замок `settings.json.lock`. С редакторами, не соблюдающими этот протокол, общей блокировки нет: между последней сверкой и переименованием остаётся окно гонки.

Каждый реально изменённый файл, напоминание `/hooks` и безопасная ошибка передаются через `log` в [файловый журнал воркера](../window/logs.md); содержимое конфигов не печатается. Неизменённые и отсутствующие установки молчат. Процессный стенд включает тот же logger и проверяет события своего PID; отсутствие сообщения в stderr не доказывает отсутствие фонового обновления.

## Гейт чтения документации

Решение агента, 19-10-2026 (OQ-99). Только Claude Code: у Codex проектный `.codex/` bars не использует.

- **Что это.** Запись `hooks.PreToolUse` с командой `"<bars-cli>" hook pre-tool-use --docs-root "<папка документации>"` и шаблоном `Read|Grep|Glob|Bash|PowerShell|mcp__bars__.*`. Поисковые обходы папки документации (Grep, Glob и поисковые команды shell) считаются подряд: каждый шестой и каждая широкая рекурсия по `*.md` отклоняются с подсказкой, какой инструмент bars вызвать, а тот же вызов, повторённый сразу, проходит; любой вызов bars обнуляет счётчик. Чтение известного файла не считается. Логика команды — [cli.md](../agent-tools/cli.md#хук-перед-вызовом-инструмента).
- **Куда ставится.** В `<проект>/.claude/settings.local.json` — личный файл проекта, обычно вне git. Условия: проект есть в реестре bars **и** среди ключей `projects` в `~/.claude.json`, а в `~/.claude.json` есть MCP-запись bars (иначе звать нечего). Папка документации берётся из настроек проекта; смена папки доезжает со следующим проходом.
- **Когда.** Хук начала сессии (`session_start` воркера) ставит гейт в проект сессии, фоновый проход при старте воркера — во все такие проекты. Окно и CLI регистрируют проект без гейта: он появится при ближайшем проходе или сессии.
- **Правка файла.** Те же правила, что у других записей: меняется только запись bars (команда содержит `bars-cli` и `hook pre-tool-use`), остальное сохраняется, повторный проход ничего не пишет, перед заменой лежит копия `<файл>.bars-backup`. Файл проекта, который не разбирается, остаётся нетронутым, ошибка идёт в журнал воркера; другие проекты это не останавливает.
- **Удаление.** `uninstall --client claude-code` убирает запись bars из всех проектов `~/.claude.json`.
- **Чего гейт не делает.** Не трогает код (`*.rs`, semble, serena): это правило конкретного проекта, оно остаётся в его собственном хуке, а проверку документации такой хук не повторяет: в проекте с гейтом bars её делает один гейт. Корень документации `.` гейт не включает: под него попал бы весь проект.

## Текстовая инструкция по установке

Окно показывает, а `bars-cli install --print-instruction` выводит короткий текст для агента: где лежат `bars-mcp` и `bars-cli` и какой командой подключиться (`bars-cli install --client …`). Агент выполняет её сам (Т-21). Текст написан по-английски: его читает агент, а не человек. Текст также запрещает агенту самому передавать `bars-cli reindex --accept-model-change`: это согласие пользователя (Т-25).

## Skills в клиентах

Установка в Claude Code, Codex и Kimi Code кладёт три skills: `bars-docs`, `bars-session-log` и `bars-end` ([delivery.md](../docs-convention/delivery.md)); тексты зашиты в bars. В Ouroboros эти skills не устанавливаются, в iterion кладётся только `bars-docs` (внутри плагина, см. раздел iterion).

| Клиент | Папка skills |
|---|---|
| Claude Code | `~/.claude/skills/<имя>/SKILL.md` |
| Codex | `~/.agents/skills/<имя>/SKILL.md` |
| Kimi Code | `~/.kimi-code/skills/<имя>/SKILL.md` |

Codex читает пользовательские skills из `~/.agents/skills`, а не из `~/.codex/skills` ([документация Codex](https://learn.chatgpt.com/docs/build-skills), обращение 15-10-2026). Удаление убирает только папки `bars-docs`, `bars-session-log` и `bars-end`. Если `~/.claude/skills` или `~/.agents/skills` — ссылка на чужую папку, skills попадут туда (OQ-54).

## Формат записей bars

Решения агента, 15-10-2026.

- **Откуда пути.** Воркер берёт расположение своего exe и ищет рядом `bars-mcp` и `bars-cli`; в записи идёт абсолютный путь. Существование файлов при установке не проверяется.
- **MCP-сервер.** Claude Code: `mcpServers.bars` = `{"type": "stdio", "command": "<bars-mcp>", "args": [], "env": {}}`; у уже существующей записи обновляются `type`, `command` и `args`, остальные её ключи остаются. Codex: `[mcp_servers.bars]` с `command` и пустым `args`. Kimi Code: `mcpServers.bars` в `mcp.json` — тот же вид, что у Claude Code.
- **Хук.** Команда одна: `"<bars-cli>" hook session-start`. Claude Code и Codex: каноническая группа `hooks.SessionStart` = `{"matcher": "startup|resume", "hooks": [{"type": "command", "command": "\"<bars-cli>\" hook session-start"}]}`; формат один для обоих. Kimi Code: элемент `[[hooks]]` с `event = "SessionStart"`, `matcher = "startup|resume"` и той же командой. Распознавание старого хука: команда содержит `bars-cli` и `hook session-start`. При обновлении исправляются type, matcher и команда; дубли сводятся к одной группе (у Kimi Code — к одному элементу в конце массива). Из смешанной группы извлекаются только хуки bars, чужая часть сохраняется. Уже каноническая группа остаётся на месте. Удаление вынимает записи bars и опустевшие контейнеры.
- **Одобрение хука в Codex.** Результат install напоминает про `/hooks` только при фактическом изменении хука bars; узнать сохранённое одобрение bars не умеет.
- **Устаревшие пути.** Исправляются фоновым проходом вместе с остальными полями. `state.stale` остаётся признаком старого пути для окна; полная сверка встроенного содержимого выполняется автообновлением и install.

## Как проверяется установка и автообновление

Повторяемый стенд — `scripts/test-client-refresh.ps1`: шесть отдельных процессов с временным `BARS_USER_HOME`, настоящие `serve_with`, CLI и stdio-MCP, без подмены файловых операций. Воркер без окна — `crates/bars-worker/examples/client_refresh_session.rs`; он требует явный `BARS_USER_HOME` и останавливается сигнальным файлом `stop`.

```powershell
cargo build -p bars-worker --example client_refresh_session --locked
cargo build -p bars-cli -p bars-mcp --bins --locked
./scripts/test-client-refresh.ps1
```

Сессии стенда: обновление старых путей и дублей трёх клиентов при сохранении чужих записей (для Kimi Code — вместе с чужим содержимым `config.toml`: `default_model`, providers, чужие `[[hooks]]`); no-op без изменения байтов, mtime и backup; uninstall настоящим CLI; отсутствие восстановления удалённого после нового запуска; изоляция ошибки (невалидный JSON Claude не мешает обновить Codex; сломанный `config.toml` Kimi не пишется); пустой профиль без создания папок клиентов. Дополнительно проверяется чтение записи установленным Codex (`codex mcp get bars --json`), stdio-вызов `bars_status` и skills через NTFS junction (OQ-54).

Изоляцию профиля (ISS-12) проверяет `scripts/test-client-profile-isolation.ps1`: без `BARS_USER_HOME` он сначала проверяет конструктор воркера, затем снимает SHA-256, mtime и наличие конфигов Codex и Claude, их backup и обоих skills до и после прогона worker, CLI и MCP. Содержимое конфигов в отчёт не попадает; параллельная запись в эти файлы засчитывается как изменение. Журнал приёмки — 2026-10-18-clients-auto-update (`chats/2026-10-18-clients-auto-update`).

## Что не подтверждено

- Интерактивное одобрение и запуск хука командой `/hooks` в Codex: `codex mcp get` подтверждает только чтение конфигурации, не доверие к хуку.
- Claude Code на машине разработки не найден; его файлы проверены на временных копиях, без клиентской AI-сессии.
- Kimi Code: установка и автообновление проверены на временных профилях; на настоящей сессии Kimi Code (Desktop или CLI) хук начала сессии и skills не проверялись. `KIMI_CODE_HOME` не поддерживается: при переезде корня Kimi Code запись надо править руками или подключать клиента вручную по «Копировать конфиг».
- Восстановление файлов не обновляет уже открытое окно клиента: оно может держать старую команду MCP до перезагрузки конфигурации.
- macOS не проверена. Шаблон событий хука — `startup|resume`.
- Реальные профили пользователя и установленная сборка приёмкой не менялись; остальные ручные проверки установки на настоящих `~/.claude`, `~/.codex` и `~/.kimi-code` — в плане работ.
