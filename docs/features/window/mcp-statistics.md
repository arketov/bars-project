## Границы учёта MCP

Список самих инструментов и их параметров — в [инструментах MCP](../agent-tools/mcp-tools.md), операции графа — в [инструментах GraphRAG](../graphrag/tools.md). Worker наблюдает типизированные MCP-вызовы после проверки IPC-сессии. Подробный контракт реализован для `bars_rag_search`, `bars_get_similar`, `bars_read`, `bars_outline`, `bars_projects`, `bars_status`, `bars_reindex`. Для внедряемых GraphRAG-операций собираются общие метаданные и количество `graph_items`; полный набор их аргументов не сохраняется. У `GraphQuery` это явно отмечено `graph_detail_contract_not_recorded`.

Сессия — одно соединение MCP с worker, **не чат клиента**. Переподключение создаёт новую сессию; повтор вызова — новую попытку. Проект — зарегистрированный корень и имя, разрешённые при исполнении. Пустая строка `project` означает «Без проекта»: общий список проектов либо неразрешённая цель.

CLI, хук, окно, `hello`, `tools/list` и фоновые задания в историю не входят. Неверный JSON, ошибка разбора/допуска IPC и недоступный worker также не наблюдаются. `delivery="unknown"` у любой записи: завершение обработчика не доказывает получение ответа клиентом.

## Просмотр статистики MCP

Вкладка «Статистика MCP» показывает отдельные попытки по времени начала, пять совместных серверных фильтров, сводку всей выборки и подробности выбранного ID. По умолчанию последние 24 часа, также доступны «Сегодня» и семь дней. Локальные дата/время подписаны часовым поясом. Страницы по 50; «Ещё 50» продолжает снимок курсором, обновление сохраняет выбор по ID. На узком экране подробности заменяют список; закрытие/Escape возвращают фокус строке.

Нулевой успех, ошибка, неизвестный исход, выполняющийся вызов, предупреждение и принятие в очередь различимы. Подробности показывают исходные/применённые значения и известную причину умолчания/ограничения, безопасную ошибку, количество с единицей; JSON вторичен. Прежние агрегаты доступны отдельно, без смешения со сводкой. Есть повтор чтения, диагностика неполноты, переключатель сбора и подтверждение очистки всех проектов/сессий. [Дизайн и исполняемый стенд](refinement-design.md#анализ-mcp-список-фильтры-и-подробности). Браузерная проверка и компиляция Tauri не означают нативную приёмку.

## Контракт этапа 26: анализ отдельного MCP-вызова

Потребность автора: установить «что вызвано, с чем, чем закончилось, сколько вернулось». Контракт этапа 26 реализован в данных этапа 29 и UI этапа 30; нативная приёмка — этап 32.

| Поля записи v2 | Фактический смысл |
|---|---|
| `id`, `version` | Числовой ID попытки, версия записи 2. ID после очистки не переиспользуется |
| `epoch`, `generation` | Эпоха обработчика worker и поколение сбора/очистки; это разные величины |
| `session`, `tool`, `project`, `project_name` | Соединение, инструмент, разрешённый корень и имя; запрошенный проект остаётся в `requested` |
| `started`, `finished` | UTC Unix seconds; конец отсутствует у выполняющегося или неизвестного вызова |
| `duration_ms` | Длительность по монотонным часам, включая ожидание ресурсов/gate внутри worker, без IPC, форматирования прокси и записи истории; null — длительность не установлена |
| `requested` | Разрешённые исходные MCP-аргументы до умолчаний прокси: пропущенное поле, null, пустое и явное значение различимы |
| `applied` | Значения, зафиксированные при исполнении: формат, cwd/проект, параметры инструмента; неизвестные значения не подставляются из сегодняшних настроек |
| `outcome` | `running`, `success`, `error`, `unknown`; принятие reindex — успех постановки в очередь, не готовый индекс |
| `result` | `count` и `unit`, дополнительные признаки `warning`/`queued`; null с `unknown` отличается от null с `not_applicable` |
| `error` | Код, необязательный kind, безопасный текст из каталога и стадия `worker`. Детализация стадии до конкретного шага сейчас отсутствует |
| `incomplete`, `delivery` | Причины неполноты/усечения; доставка клиенту всегда неизвестна |

Отсутствующий исходный контекст отмечается `original_mcp_input_unavailable`: например, старый/прямой IPC-клиент или пропуск слишком большого контекста. Тогда доступен только разрешённый снимок типизированных параметров; восстановление исходного missing/null и формата не обещается. Исходный ответ инструмента от этого не меняется.

## Контракт этапа 26: охват, исход и измерение MCP

Перед исполнением фиксируется `running`, после него — терминальный исход. Повтор не перезаписывает прежнюю попытку.

| Случай | Что хранится |
|---|---|
| Успех / пустой ответ | `success` и фактическое количество, в том числе 0 |
| Ошибка обработчика / разрешения проекта | `error`, безопасный код/текст; неизвестное количество |
| Обрыв клиента | Итог worker, если исполнение продолжилось; доставка ответа неизвестна |
| Перезапуск с незавершённой записью | `unknown`, причина `worker_restarted`, без выдуманного окончания/полной длительности |
| Отключение сбора во время исполнения | `unknown`, причина `collection_stopped`; последующее завершение не дописывает запись |
| Отказ записи начала | Записи может не быть; ответ инструмента сохраняется, растёт счётчик потерь |
| Отказ записи конца | Сохранённое начало может остаться `running` до восстановления при перезапуске; считать такой исход успехом нельзя. Потеря видна в диагностике |
| Очистка при активном вызове | Запись удаляется; поздний итог не вставляет её заново |

Запись выполняется через `spawn_blocking`, максимум восемь ожидающих/исполняемых записей. Исчерпание лимита не ставит неограниченную очередь с аргументами. Операции одного экземпляра истории воркера последовательно получают соединение: чтение страницы тоже удаляет просроченные записи и занимает writer. Поэтому свои параллельные вызовы не расходуют SQLite busy timeout друг на друга. Для внешнего writer busy timeout остаётся 25 мс; транзакции IMMEDIATE исключают гонку deferred read→write. Начало/конец ожидаются вызывающим кодом, поэтому учёт **добавляет задержку**; отказ учёта не заменяет результат инструмента. Измерение стоимости — в протоколе этапа 29 (`chats/2026-10-18-mcp-history-29`).

Диагностика хранится вне SQLite: `lost_events` и последняя безопасная причина `storage_unavailable` / `writer_capacity_exceeded`, плюс предупреждение без аргументов в техническом логе. Счётчик относится к событиям хранения текущего процесса, не к точному числу потерянных вызовов; после перезапуска прежнее число потерь неизвестно. Отображение этой диагностики в новом экране — этап 30.

## Контракт этапа 26: хранение аргументов и срок MCP-истории

**Решение автора 18-10-2026, OQ-89:** «Историю храним за 7 дней максимум». Остальные ограничения — инженерные решения.

Хранилище — `~/.bars/mcp-statistics.sqlite3`, отдельно от индексов и логов; `BARS_USER_HOME` изолирует его в проверках. SQLite schema v2 использует `attempts` и `history_settings`; `calls` оставлена только для прежних агрегатов. Политика сбора находится в этой БД, не в settings.toml.

- Скользящие 7 × 24 часа по началу попытки, включая незавершённые. Чтение отсекает просроченные записи; очистка выполняется при запуске, обращениях к истории и не реже раза в час при работающем worker. При выключенном bars файл сам не меняется.
- До 10 000 попыток / 32 МиБ сериализованных данных; старые записи вытесняются. Это бюджет данных, не размер SQLite вместе с индексами/WAL. Checkpoint ограничивает WAL, свободные страницы используются повторно.
- Сериализованная запись — до 32 КиБ, с учётом JSON escaping. В `requested`/`applied` строка ограничивается 8 КиБ UTF-8, массив — 100 элементами; суммарный бюджет может усечь раньше. `incomplete` содержит путь поля и исходную/сохранённую длину или число элементов. Это не обещание отдельного лимита 8 КиБ для метаданных `project`/`session`.
- Сбор включён по умолчанию. Выключение прекращает новые записи, оставляя уже сохранённые до очистки/истечения срока; активные становятся неизвестными. Включение не восстанавливает пропущенное.
- Очистка удаляет **все проекты и сессии**, включая прежние агрегаты; исполнение инструментов продолжается. Поколение и обновление только существующего ID не дают позднему итогу вернуть удалённое. Подтверждение пользователем в новом интерфейсе — этап 30.

Миграция сохраняет прежние агрегаты отдельно, отсекая их до семи дней; пограничный UTC-день с неизвестными временами отдельных вызовов удаляется целиком. Подробности из сумм не восстанавливаются, старые и новые числа не складываются. Новые вызовы не дописываются в `calls`. Повреждённая или более новая схема не заменяется пустой БД; инструменты продолжают работать с диагностикой недоступной истории.

Очистка не обещает удаление внешних резервных копий или гарантированное стирание с накопителя. В локальной истории могут быть поисковые запросы и пути; они не дублируются в технический лог.

## API окна для этапа 30

### Подсказки и защита состояния экрана

Экран использует серверные страницы по 50 и сводку всей выборки. Проект/сессия — точные значения с подсказками `mcp_history_options`: поиск по части пути/ID с учётом регистра во всей истории периода, до 200 совпадений каждого вида с флагом ограничения; сессии ограничены выбранным проектом. Payload попыток для подсказок не загружается. Смена проекта проверяет совместимость выбранной сессии отдельным запросом за тот же период.

Смена фильтра закрывает подробности и инвалидирует ожидающие ответы. Обновление перечитывает выбранный ID с теми же фильтрами; вытеснение объясняется явно. Управление хранением не подменяет подтверждение сервера оптимистичным успехом. Вход и применённые значения — читаемая таблица; JSON вторичен. Проверка браузерного экрана не заменяет нативную приёмку этапа 32.

Команды Tauri работают только с worker текущего окна, не принимают произвольный путь к БД и не являются методами MCP/CLI. Регистрация/компиляция и привязки UI проверены; настоящий нативный UI-путь остаётся этапу 32.

| Команда | Аргументы / ответ |
|---|---|
| `mcp_history` | Обязательный объект `filter`, все его поля необязательны. Ответ: `records`, `next`, `summary`, `enabled`, `lost_events`, `last_storage_error`, `coverage` |
| `mcp_history_options` | `filter` с периодом/проектом, `projectQuery`/`sessionQuery` — части пути/ID. Возвращает `projects`/`sessions` и `projects_more`/`sessions_more`; максимум 200 каждого вида |
| `mcp_history_control` | `enabled`: bool или null; обязательный `clearConfirmed`: bool. При true сначала очищается вся история, затем при заданном enabled меняется сбор; это **две отдельные операции**, не общая транзакция. Для однозначного сообщения об ошибке вызывать очистку и переключение отдельно. При false очистки нет. Успех возвращает null, ошибка — безопасную строку |
| `mcp_history_legacy` | Без аргументов; отдельный массив прежних агрегатов, без выдуманных подробностей. Не складывать с новой сводкой |
| `mcp_history_diagnostics` | Без аргументов; `lost_events`, `last_storage_error`, `scope="worker_admitted_calls"`, `delivery="unknown"`, `retention_days=7`; доступна и при неисправной SQLite |
| `mcp_statistics` | Существующая команда старой сводки завершённых вызовов; новый экран использует mcp_history |

### Фильтры и пагинация MCP-истории

`filter.from` / `to` — UTC Unix seconds, интервал `[from,to)`. По умолчанию от now−24 часа до now+1 секунды; нижняя граница ограничивается текущим семидневным cutoff. Совместные точные фильтры: `project`, `session`, `tool`, `outcome`; null/отсутствие снимает фильтр. `project=""` выбирает «Без проекта», `project="*"` не является специальным значением API. `limit` по умолчанию 50, прижимается в 1…100.

Порядок — `(started,id)` по убыванию. `next` — объект курсора либо null; передавать его целиком в `filter.cursor`, не строить заново. Курсор связывает период, фильтры, верхний ID и поколение сбора. Новые вставки не сдвигают страницы; исходы ранее активных записей могут меняться, просроченные/вытесненные записи могут исчезать. Это не замороженная копия истории на всё время просмотра. Новая страница и её сводка читаются в одной транзакции.

Очистка, реальное изменение enabled или набора фильтров делают прежний курсор недопустимым. После такого изменения запрашивать первую страницу. Отдельного API-кода «курсор устарел» сейчас нет: команда возвращает общую безопасную ошибку чтения.

`filter.id` выбирает запись только внутри текущих фильтров; отсутствующая/вытесненная запись даёт пустой records. Summary относится ко всему отфильтрованному набору до пагинации и ограничения id, поэтому не пересчитывается по открытой строке.

### Сводка MCP-истории

`summary.calls`, `success`, `errors`, `unknown`, `running` — числа попыток; `empty_success` — успешные записи с count=0, без неприменимых/неизвестных количеств. `total_ms` и `timed_calls` дают среднее `total_ms/timed_calls`; при нулевом знаменателе среднее неизвестно. Разные единицы результата не суммируются. Ошибка чтения не означает пустую историю; UI должен показывать ошибку и действие повтора.
