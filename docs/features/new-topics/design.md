# Новые темы — поведение окна и устройство фичи

Статус: проект IDEA-14 от 18-10-2026; согласованное расположение строки отделено от предложенного поведения. С 19-10-2026 реализованы сбор в воркере, хранилище и дедупликация (P1–P2), внутренний API окна с проверкой тем (P3; [тесты](plan.md)) и экран с первой строкой дерева (P4; проверено компонентными тестами и в браузере на заглушке воркера, настоящая bge-m3 и собранное окно Tauri не проверялись). Реализованное описано в разделах «Что сделано в воркере», «Внутренний API окна» и «Экран в окне». [Требования](requirements.md), [макет](design/mockup.html).

## Вход в новые темы

Решение автора: файловая строка первой в дереве, выше «(корень)», отдельная иконка. Предложенный рисунок — лист с маленькой искрой: документоподобная форма и обозначение новой потребности. Точное начертание — вариант макета.

Предложение: без чекбокса и стрелки; справа число незакрытых тем, а не чанков. Строка остаётся видна при фильтрации документов: текстовое поле подписывается «Фильтр документов», не обещает фильтровать служебный пункт. Нулевой список тоже открывается. Наведение/выделение соответствуют строкам документов; клавиатура Tab/Enter, видимый фокус и подпись для скринридера. Нажатие не меняет выбранные модули и файлы.

Решение автора (19-10-2026): «Новые темы» — как файл: строка лежит выше всех папок, открывается нажатием как файл и показывается в правой панели, где смотрят файлы, а не отдельным экраном. Слева остаётся обычный поиск со своим черновиком и областью. Внутри панели выбор темы открывает подробности рядом со списком, а в узкой панели — вместо списка с кнопкой «К списку». Существующий документ можно открыть из результата проверки: он заменяет панель, как любой файл. Возврат сохраняет выбранную тему, фильтр и прокрутку.

## Список и карточка темы

Вверху: «Новые темы», пояснение «Вопросы, для которых не нашлись материалы», действия «Проверить все» и меню списка. В меню — переключатель сбора и «Очистить список…». «Проверить все» обрабатывает активные темы последовательно с видимыми N/M и отменой оставшейся очереди; не требует отдельного фонового сервиса.

Фильтры: «Активные», «Есть материалы», «Закрытые»; поиск по тексту внутри списка. «Активные» включает все незакрытые. Сортировка по последнему обращению; альтернативно по числу обращений. Метка количества говорит «обращений», не «пользователей» или «задач».

Строка содержит исходную формулировку, статус, частоту, давность, источник «Окно», «MCP» или оба. Сохранённый текст отображается как текст, без исполнения Markdown/HTML. В карточке — первая/последняя дата, причины, варианты с областями и проверка. Заголовок берётся из первого вопроса; пользователь может его переименовать, исходный запрос остаётся неизменным. Новая генеративная модель для названий не нужна.

Основное действие — «Проверить знания». Найденные материалы показываются как обычные карточки источников с переходом к документу, путём и строками. Для каждого варианта свой итог; вопрос с тремя вариантами нельзя считать покрытым по одному совпадению. Кнопки «Знаний достаточно» и «Всё ещё не хватает» принимают решение пользователя о теме. Автозакрытия по оценке модели нет.

## Состояния экрана новых тем

| Состояние | Представление и действие |
|---|---|
| Нет выбранного проекта | Существующий выбор/добавление проекта; тема не создаётся без адресата |
| Загружается список | Скелет/индикатор; предыдущий проект не остаётся видимым под новым именем |
| Тем ещё нет | «Здесь появятся вопросы, для которых не нашлись материалы»; объяснение источников, без обещания читать весь внешний чат |
| Сбор выключен | Постоянная плашка «Сбор новых тем выключен» с действием включения; старые записи доступны |
| Ошибка чтения | Сообщение и «Повторить»; не нулевой счётчик и не пустое состояние |
| Тема проверяется | Индикатор на выбранной теме, повторная отправка заблокирована; другие действия доступны по правилам операций |
| Найдены материалы | Статус «Есть материалы», дата/область и источники; решение остаётся человеку |
| Пока пусто | «Материалы не найдены при этой проверке», дата, область, порог; тема остаётся активной |
| Проверка неполная | Причина: индексация/ошибка обновления/удалённая область; ни положительного, ни отрицательного окончательного вывода |
| Недоступен worker/модель/проект | Конкретная ошибка и повтор; предыдущие сохранённые материалы остаются помеченными как прежние |
| Есть потери сбора | Плашка с числом известных отказов текущего процесса и действием диагностики; без выдуманного числа пропущенных тем |

Предложение удаления: подтверждение в карточке с текстом «Удалить тему и сохранённые варианты? Новый запрос может добавить её снова». Для очистки — подтверждение числа тем и проекта. Поздняя проверка не восстанавливает удалённую тему. Постоянное «Не собирать этот вопрос» не входит в первый объём; OQ-96 оставляет возможность изменить решение.

## Что создаёт новую тему

Событие создаётся после исполнения поиска, в общем worker. Источник и назначение передаются внутренним контекстом, не дополнительными публичными параметрами, которые должен заполнить агент.

| Условие | Действие |
|---|---|
| Успешно, 0 результатов, индекс готов, нет известной ошибки обновления | Создать/обновить кандидата с реальными параметрами и областью |
| Успешно, 0 при modules/files | То же, причина «Не найдено в выбранной области», не во всём проекте |
| Непусто | Автоматической темы нет; пользователь может нажать «Не хватило знаний» в выдаче |
| Ручная отметка | Использовать контекст именно отображаемого результата, а не уже изменённого поля запроса |
| Индексация/очередь/ошибка обновления | Не создавать подтверждённый пробел; отложить решение до нового обращения или явной проверки |
| model_loading, provider_error, reindex_required, invalid_params | Технический исход, не тема |
| Диагностика/проверка темы/автоповтор | Не собирать и не считать спрос |

Это правило OQ-95 сохраняет наблюдаемый факт, не объявляет отсутствие ответа доказанным. При min_score=0 поиск часто вернёт хоть какой-то фрагмент даже на отсутствующую тему; ручная отметка нужна с первого объёма. Более широкий автоматический детектор слабой выдачи потребует отдельной калибровки и не маскируется случайным порогом.

Для одной отправки окна создаётся `request_id`; его диагностические/загрузочные попытки имеют `parent_request_id` и назначение. Повторное осознанное нажатие «Найти» — новое обращение. MCP использует ID конкретной допущенной попытки вместе с epoch соединения/worker. MCP session не равна внешнему чату; переподключение не даёт права склеивать задачи. Сбой доставки ответа клиенту не меняет известного результата поиска и не доказывает получение ответа.

После OQ-94 адаптер общего чата может передать исходный вопрос, стабильный ID обращения и установленный сигнал отсутствия ответа. Если внешний чат не обращался к поиску bars, готового вектора у bars нет. Нельзя обещать бесплатное переиспользование несуществующего вектора или читать архивы в качестве скрытого адаптера.

## Дедупликация темы

Внутри проекта:
1. Проверить ID события: повторная доставка не меняет счётчик.
2. Найти точное совпадение осторожно нормализованного вопроса и канонической области. Схлопываются пробелы/переносы, но не отрицания, числа, версии, регистр значимых идентификаторов и знаки кода.
3. При наличии готового вектора найти близкие темы только с совместимым embedding-пространством и областью. Один и тот же текст с другой областью сохраняется как отдельное наблюдение; автоматическое объединение через области в первом объёме выключено.
4. Автоматически объединять только выше калиброванного порога и после проверок смысловых отличий. Изменённые числа, версии, идентификаторы, отрицания — основание оставить отдельную тему/предложить ручное объединение, а не доказать эквивалентность по cosine.
5. Сохранить вариант и наблюдение; счётчик темы — число уникальных самостоятельных событий, не число вариантов.

Сравнение вопрос–вопрос — отдельная задача от вопрос–документ; пороги rerank/cosine выдачи сюда не переносятся. Порог измерен для `bge-m3` (fp32 и fp16) на русских вопросах: автослияние — косинус не ниже 0,79 и только если лексические проверки (идентификаторы и цифры, числительные словами, короткий список противоположностей) не видят различия; на 12 552 разных парах ложных слияний нет, перефразы сливаются в 90 % случаев ([замер и пределы](../../knowledge/new-topics-threshold-2026-10-19.md)). Отрицания и противоположности вне списка косинусом и проверками не отделяются: такие пары могут слиться, ручное разъединение обязательно. Порог хранится вместе с `EmbeddingSpace`; для пространства без замера (Qwen3, Nomic) автослияния по вектору нет. Для близких, но сомнительных тем UI может показать «Похожие темы» и ручное объединение. Сохранённые варианты позволяют разъединить тему; наблюдения перемещаются вместе с вариантами, а не создаются заново.

Нельзя наращивать тему цепочкой A≈B≈C без сравнения с устойчивым представителем и сохранёнными отличиями: это объединит разные вопросы через промежуточный. Для малого списка — точный перебор векторов, без новой ANN-зависимости. Измерение размера и задержки определяет необходимость другого индекса.

`EmbeddingSpace` включает модель/артефакт, размерность, префикс и преобразование запроса, нормализацию. Одинаковой размерности недостаточно. При смене пространства тексты и решения остаются; несовместимые векторы не сравниваются. Обновление векторов выполняется по запросу проверки либо ограниченной очередью, не блокируя обычный поиск и не запуская новую обязательную загрузку модели ради списка.

Если корпус пуст, текущий `search_expanded` возвращается до embed. Сохраняется тема без вектора; сначала работает точная дедупликация. Семантическая группировка откладывается, дополнительный embed на критическом пути не требуется. Существующий вектор успешной попытки передаётся внутреннему наблюдателю ядра/worker и не добавляется в публичный ответ MCP.

## Жизненный цикл темы и проверки

У темы три сохраняемых статуса: `open` («Новая тема»), `materials_found` («Есть материалы»), `resolved` («Закрыта»). `checking` — отдельное состояние операции; сбой проверки не становится статусом темы.

| Событие | Переход |
|---|---|
| Новый кандидат или ручная отметка | Создание `open` |
| Самостоятельный неудачный запрос к открытой теме | Обновление частоты/даты; старую проверку отметить устаревшей |
| Тот же спрос к закрытой теме | Предложение OQ-96: вернуть `open`, сохранить прежнее решение и дату |
| Проверка нашла материалы | `materials_found`, сохранить варианты и источники |
| Проверка полностью и успешно дала 0 по всем вариантам | `open`; прежний успешный результат остаётся как предыдущий с датой |
| Проверка частичная или завершилась ошибкой | Статус без автоматического перехода; показать неполноту/ошибку |
| «Знаний достаточно» | `resolved`, сохранить дату решения пользователя |
| «Всё ещё не хватает» | `open`, найденные материалы не стирать |
| Удаление | Удалить тему, варианты и результаты; инвалидировать операции |

Проверка выполняется текущим поиском для каждого исходного варианта, с текущими настройками и явной подписью применённых параметров. Исторические параметры показываются отдельно; это поиск новых знаний сегодня, а не воспроизведение старой конфигурации. Область сохраняется. Пропавший модуль/файл даёт понятное состояние «Область больше недоступна» и кнопку «Проверить по всему проекту»; автоматического расширения нет.

Снимок проверки хранит модель, параметры, время, ревизию/поколение индекса и результаты каждого варианта. Одного времени `updated_at` с точностью до секунды недостаточно для идентичности индекса, поэтому метка проверки — токен успешного обновления: секунды и наносекунды момента, когда воркер зафиксировал обновление (`index_token`), а не RFC 3339. Полная подмена файла индекса тоже его меняет. Если индекс изменился посреди последовательной проверки, итоги маркируются разными ревизиями; общий окончательный вывод не делается.

Карточка результата содержит путь, заголовок, строки, оценку и её вид; полный текст документа в БД темы не сохраняется. Просмотр читает актуальный документ; если файл изменился, пользователь видит предупреждение об устаревших координатах и может повторить проверку. Список тем никогда не служит источником retrieval.

## Данные и хранение новых тем

Предложение OQ-96: `<проект>/.bars/new-topics.sqlite3`, отдельно от заменяемого `index.sqlite`, WAL и транзакции SQLite. Это пользовательская очередь, а не семидневная MCP-история. Очистка истории её не затрагивает; перенос проекта вместе с `.bars` сохраняет относительные области и темы.

| Сущность | Минимальные поля |
|---|---|
| `meta/settings` | Версия схемы, generation, включён ли сбор, политика/бюджет хранения |
| `topics` | ID, revision, display_title, статус, first_seen/last_seen, дата решения пользователя |
| `variants` | ID, topic_id, исходный текст, нормализованный ключ, канонический scope, вектор/EmbeddingSpace при наличии |
| `observations` | Уникальный event_id, variant_id, время, источник, причина, применённые параметры, состояние/идентичность индекса |
| `checks/check_results` | ID, topic_id/revision, время и исход, scope/параметры/model/index token, ссылки на найденные фрагменты по варианту |

Счётчики выводятся из наблюдений либо обновляются той же транзакцией. Не хранить исходный чат, полный ответ MCP, полные документы, секреты провайдеров. Текст вопроса сам может быть чувствительным: существующую фразу об отсутствии личных данных в `.bars` потребуется уточнить при внедрении. Т-5 сохраняется: bars не меняет `.gitignore`. Продуктовое «только пользователю» не равно шифрованию и файловым правам против других процессов.

Для первой реализации определить и замерить пределы числа тем, вариантов и размера БД до нагрузочной приёмки; проект контракта запрещает молча вытеснять пользовательские темы. При достижении лимита остановить новые записи с видимой причиной; существующий список доступен для очистки. Активные темы живут до решения пользователя; автоматическое устаревание не вводится. Проверочные результаты допускают хранение только последнего и предыдущего итога, без бесконечной истории.

При project_delete закрываются соединения/задачи и удаляются только явно принадлежащие фиче файлы БД, WAL/SHM, с существующей защитой ссылок/junction. Контракт удаления проекта и перечень в диалоге обновляются вместе с реализацией; никакой рекурсивной очистки чужих файлов `.bars`.

## Внутренние операции и гонки

Внутренний API окна реализован (P3, 19-10-2026); методы, параметры и ответы — [протокол](../../architecture/protocol.md#методы-новых-тем-только-окно). Ручное объединение и разъединение тем (`new_topics_merge/split`) в первый объём не входит (решение автора, 19-10-2026): остаётся удаление, а слияние по порогу уже работает в воркере.

| Операция | Что делает |
|---|---|
| `new_topics_list/get` | Точный проект; список без проверок и карточка с вариантами и двумя последними проверками, ревизия темы, число обращений, источники, основания, место хранения, потери сбора; ошибка чтения — ошибка, не пустой список |
| `new_topics_mark_missing` | Ручная отметка по отображённой выдаче: текст и область берутся из запроса вызова, `event_id` = `manual:<request_id>`, повтор идемпотентен; вектор не считается, дедупликация только точная |
| `new_topics_check` | Тема + ожидаемая ревизия, исходные области или явное расширение; итог по каждому варианту |
| `new_topics_set_status/rename/delete` | Ожидаемая ревизия; изменившаяся тема даёт `stale_ref`, ничего не перезаписывается |
| `new_topics_clear` | Только с `confirmed: true`; поколение растёт, сбор остаётся |
| `new_topics_settings` | Сбор вкл/выкл; смена меняет поколение, старые незавершённые наблюдения не добавляются |

Методы разрешены только пути окна, по существующему образцу `project_delete`: аудитория `Window` в `bars-protocol` закрывает их каналом для `bars-mcp` и `bars-cli` (`Call::allowed_for` ложь, обработчик канала отвергает вызов ещё раз). Окно — единственный процесс, вызывающий обработчик напрямую (`bars_call`), так что проверка происхождения — это границы Tauri IPC и аудитория метода, а не поле в запросе. Внешний источник может поставлять события сбора после OQ-94, но не получает список тем.

Писатель один — worker. Обработка наблюдений сериализована по проекту, уникальный event_id и транзакция защищают от двух одновременных одинаковых тем. Во время очистки растёт generation; запись с прежним поколением отклоняется. При удалении темы поздняя проверка обновляет только существующий ID с ожидаемой revision. ID не переиспользуются. Настройки сбора проверяются при допуске и записи.

Поиск не ждёт длинной записи списка: ограниченная очередь без неограниченного удержания текстов; запись вне блокировки индекса, короткие транзакции и явная диагностика переполнения/ошибки. Запись может не состояться при аварии процесса до фиксации; гарантия полного аудита не обещается. Бюджеты очереди и времени устанавливаются по замеру P1; при штатном завершении допущенные записи дренируются с ограничением времени.

UI держит project + request_id/revision и отбрасывает поздний ответ после переключения проекта/удаления. Проверка использует существующий model_loading/переиндексационный контракт; не меняет модель и не запускает переиндексацию без положенного согласия Т-25. Ошибка проверки не теряет тему.

## Что сделано в воркере

Проверено тестами на подделке embed-модели, настоящем канале и временных проектах (19-10-2026); настоящая bge-m3 и собранное приложение не проверялись.

- **Ядро** — `bars-core::new_topics`: `TopicStore` (БД `.bars/new-topics.sqlite3`, схема 2, WAL), `guard` (лексические проверки и ключ точного совпадения), `EmbeddingSpace` с порогом 0,79 только для `bge-m3`. `SearchResponse` получил внутренний `query_vector`; в публичную выдачу и MCP он не попадает.
- **Воркер** — `bars-worker::new_topics`: `Collector` с ограниченной очередью (256) и одним потоком записи; допуск (`admit`) берёт поколение списка до поиска, запись — после; переполнение и ошибки БД считаются потерями без текстов в логе. Источник и назначение передаются task-local `SearchContext`: вызов по каналу — `Mcp` или `Cli`, прямой вызов окна — `Window`; окно помечает диагностику служебным полем `_window` в параметрах `bars_call`, которое вырезается до разбора вызова.
- **Что собирается**: источники `Window` и `Mcp`, назначение «обращение», готовый индекс без очереди и ошибки обновления, ноль публичных результатов, без графового расширения. CLI, диагностика и ошибки спроса не создают.
- **Дедупликация**: ключ точного совпадения и область → семантическое слияние с первым вариантом темы, у которого есть вектор этого пространства; вариант остаётся при слиянии. Один и тот же текст в другой области — отдельная тема.
- **Удаление проекта**: `begin_delete` закрывает соединение и блокирует запись, `end_delete` снимает блок; БД и sidecar входят в перечень известных рабочих файлов. Запись не создаёт `.bars`.
- **Пределы (замер, debug-сборка, 2000 тем с векторами 1024)**: БД 9,3 МБ; запись — медиана 52 мс, p95 98 мс, максимум 147 мс, список тем — 10 мс. Запись идёт вне пути поиска, на поиск ложится только поиск в кэше допуска и `try_send`. Пределы кода: 2000 тем и 50 вариантов на тему; при достижении предела новые записи останавливаются с видимой причиной, существующие темы не вытесняются. Замер release и нагрузка при одновременной индексации не проводились.

## Внутренний API окна

Реализован 19-10-2026 (P3); проверено тестами на подделке модели, временных проектах и настоящем обработчике. Настоящая bge-m3, собранное окно и release-замер не проверялись.

- **Схема БД 2**: к схеме 1 добавлены `checks` (тема, ревизия темы при старте, время, расширение, модель, применённые параметры) и `check_results` (вариант, область поиска, исход `found`/`empty`/`incomplete`, причина, метка индекса, найденные фрагменты JSON). Миграция идёт одной транзакцией при открытии; темы, варианты, наблюдения и поколение сохраняются. БД более новой схемы по-прежнему не заменяется. Хранятся последняя и предыдущая проверки темы.
- **Проверка темы**: для каждого варианта идёт текущий поиск по исходной области (или по всему проекту при явном `expand`) с назначением «диагностика», поэтому ни спроса, ни наблюдения не создаёт. Варианты проверяются последовательно (до 50 поисков на тему); повторная проверка не меняет счётчик обращений.
- **Исход варианта**: `found` — есть фрагменты (хранятся путь, заголовок, строки, оценка и её вид, текст документа не хранится); `empty` — поиск успешен, индекс не индексируется и фрагментов нет; `incomplete` — индексация при пустой выдаче (`indexing`), `model_loading`, `reindex_required`, область исчезла (`scope_missing`: поиск отвечает `invalid_params` на несуществующий модуль) или иная ошибка (`error`). Область молча не расширяется.
- **Вывод по проверке (`conclusive`)** есть, только если нет ни одного `incomplete` и все варианты получены при одной метке индекса. Метка — `index_token` обновления: время успешного обновления с наносекундами (замена секундной `updated_at`, 19-10-2026); два обновления внутри одной секунды различаются. Токен сравнивается на равенство и пользователю не показывается; после перезапуска воркера он восстанавливается из секундной метки индекса.
- **Статус по проверке**: найден хотя бы один вариант и тема открыта — `materials_found`; закрытую решение пользователя не трогает, пустой и неполный итог статус не меняют. Если тему удалили или очистили список, пока шла проверка, `new_topics_check` отвечает `stale_ref`, тема не восстанавливается (ID не переиспользуются). Если тема изменилась (ревизия выросла) во время проверки, проверка записывается с ревизией старта, а окно видит `topic_revision` меньше текущей и считает её устаревшей. Переход «Есть материалы» делает сама проверка: пока тему не меняли другие, проверка получает уже новую ревизию и устаревшей не считается.
- **Решения пользователя**: «Знаний достаточно» → `resolved` с датой решения; «Всё ещё не хватает» → `open`, дата прежнего решения и материалы последней проверки сохраняются; переименование меняет заголовок, формулировки вариантов остаются. Ожидаемая ревизия обязательна у каждого изменения: несовпадение — `stale_ref`.
- **«Проверить все»** остаётся делом окна: оно вызывает `new_topics_check` по активным темам последовательно, показывает N/M и прекращает вызовы при отмене. Отдельной очереди в воркере нет.
- **Ручная отметка при выключенном сборе** отклоняется (`invalid_params`): выключение останавливает любые новые записи.

## Экран в окне

Реализован 19-10-2026 (P4, переделан в тот же день после уточнения автора «как файл в правой панели»); проверен компонентными тестами и в браузере на заглушке воркера (обе темы, широкое и узкое окно). Не проверены настоящая bge-m3, собранное окно Tauri и release-замер.

- **Строка дерева** — первой внутри дерева, выше всех папок и корневых документов; свой значок «лист с искрой», без галочки, стрелки и числа чанков; справа число активных тем (прочерк при ошибке чтения или пока списка нет — не ноль). Поле над деревом подписано «Фильтр документов» и строку не скрывает. Нажатие открывает панель справа (`app.topicsOpen`), как открывается файл: просмотр документа в этот момент закрывается, а запрос, результаты и отмеченные модули и файлы слева не меняются. Счётчик обновляется вместе с опросом проектов (раз в 5 секунд) и при выборе проекта.
- **Панель** — `NewTopicsPage.svelte` над состоянием `NewTopicsStore` (`new-topics.svelte.ts`) занимает место просмотра документа (шапка с названием и крестиком закрытия, как у документа); список и карточка стоят рядом, а при ширине панели меньше 760 px (обычно так и есть) сменяют друг друга кнопкой «К списку». При пустом корпусе проекта панель открывается так же, рядом с экраном «нет документов». Фильтры «Активные», «Есть материалы», «Закрытые», поиск по тексту, сортировка по последнему обращению или по числу обращений. Выбранная тема, фильтр, поиск и прокрутка списка сохраняются при уходе в документ и возврате; смена проекта сбрасывает всё, а поздние ответы прежнего проекта, прежнего списка и удалённой темы отбрасываются.
- **Карточка** — формулировки с областями, основания и даты, последняя проверка (итог по каждому варианту, найденные фрагменты с путём, строками и оценкой, «Открыть документ») и прежняя проверка в раскрывающемся блоке. Действия: «Проверить знания», «Проверить по всему проекту» (только если у темы есть исходная область), «Удалить…» с подтверждением, «Переименовать». «Знаний достаточно» и «Всё ещё не хватает» показываются у темы «Есть материалы», у закрытой — «Всё ещё не хватает». Текст вопросов выводится как текст, не как Markdown или HTML.
- **«Проверить все»** — окно вызывает `new_topics_check` по активным темам по одной, показывает «Проверяется N из M» и «Остановить»; отмена дожидается идущей проверки и прекращает остальные.
- **Управление списком** — раскрывающийся блок под списком: переключатель сбора, место хранения (путь к БД) и «Очистить список…» с подтверждением числа тем и проекта. Выключенный сбор виден постоянной плашкой «Включить сбор»; потери сбора — плашкой с числом и причиной без текстов вопросов; ошибка чтения — сообщением и «Повторить» вместо пустого списка.
- **Ручная отметка** — в выдаче поиска строка итогов получила «Не хватило знаний». Каждый поиск окна несёт служебное поле `_window.request_id`; отметка отправляет текст запроса и область именно отображённой выдачи (не поля ввода), повторная отметка того же обращения не отправляется и идемпотентна в воркере. Новый поиск — новое обращение, смена проекта сбрасывает контекст.
- **Не входит в первый объём**: ручное объединение и разъединение тем (OQ-102), постоянное «Не собирать этот вопрос», карточка «Похожие темы».
