## Что это и как называются части

Linked worktree — вторая рабочая копия того же git-репозитория (`git worktree add`). Для bars она не отдельный проект, а **вид** проекта-владельца: те же документы, но с правками своей ветки. Вид не хранит копию индекса: он хранит **дельту** — только документы, которые отличаются от индекса владельца, — и во время поиска сливается с индексом владельца.

| Термин | Что это |
|---|---|
| Владелец | зарегистрированный проект или подпроект, чей репозиторий создал worktree; у него `.bars/index.sqlite`, `docs_root` и модель |
| Основной checkout | папка владельца; в параметре `wt` — значение `"."` |
| W | корень рабочей копии worktree (папка с файлом `.git`) |
| Корень вида | `W/<смещение>`, где смещение — путь корня владельца от корня репозитория (обычно пусто: корень владельца и есть корень репозитория) |
| Запись worktree | папка `<R>/.git/worktrees/<имя>/` в основном репозитории R: git создаёт её при `git worktree add` |
| Дельта | файл `<владелец>/.bars/worktrees/<имя>/index.sqlite` |
| Путь документа | как у владельца: от корня проекта через `/` (`docs/features/search/hybrid-search.md`); у вида — от корня вида. Один и тот же путь означает один и тот же документ в обоих видах |

## Обнаружение worktree

### Что читается и что из этого получается

Список worktree владельца bars берёт из файлов git, команду `git` не запускает (IDEA-16: bars worktree не создаёт, не чинит и не удаляет). Для каждой папки `<R>/.git/worktrees/<имя>/`:

| Файл | Что даёт |
|---|---|
| `gitdir` | путь к файлу `.git` рабочей копии (`C:/…/<папка>/.git`); W — его родитель. Слэши и регистр букв диска приводятся как у реестра (`normalize` и `path_key` в `bars-worker/src/worker/registry.rs`, [есть]); относительный путь отсчитывается от папки записи |
| `HEAD` | `ref: refs/heads/<ветка>` — ветка; другой `ref:` — как есть; сырой хеш — `detached` |
| `locked` | если файл есть, worktree заблокирован git; текст файла — причина, показывается в `bars_status` |
| `commondir` | общий каталог git (`../..`); нужен только для проверки, что запись принадлежит репозиторию R |

Имя worktree — имя папки записи. git держит его уникальным и обычно строит из имени папки W (`worker-wt-quorum`, при совпадении с цифрой в конце). Имя — то, что агент пишет в `wt`.

### Живой, пропавший и оторванный

Для записи считается состояние:

| Состояние | Условие | Что делает bars |
|---|---|---|
| живой | W — папка; в ней файл `.git` с `gitdir:`, который указывает на ту же запись; корень вида существует | показывает worktree, строит дельту при первом обращении |
| пропавший | `gitdir` пуст или ведёт в несуществующее место, либо W — не папка | не показывает, при ближайшей проверке удаляет дельту (ТР-6) |
| оторванный | W есть, но её `.git` не файл или ведёт в другую запись (репозиторий переехал, папку заняли под другое) | как пропавший |
| без вида | W живая, но корня вида в ней нет (владелец с смещением, а в этой ветке такой папки нет) | не показывает |

`locked` на состояние не влияет: заблокированный пропавший worktree удаляется так же. Дельта производная, её потеря стоит только повторного построения, если папка вернётся. Команды `git worktree prune`, `repair` и `lock` bars не вызывает: запись, которую git ещё считает существующей, bars может скрыть, но не тронет.

Реальный пример (чтение 12-11-2026): в `C:\repos\tmc-opovechenie\backend\api\.git\worktrees\api-avatar\gitdir` лежит путь в `…\AppData\Local\Temp\claude\…\scratchpad\api-avatar\.git`. Папки W там давно нет — это пропавший worktree. У `worker-wt-quorum` и `api-wt-quorum` из требований `gitdir` указывает на прежнее место под OneDrive: после переезда репозитория запись тоже пропавшая, а папка `backend/worker-wt-quorum` рядом с `backend/worker` — просто папка, которую bars не считает worktree и не исключает, пока запись не починят (`git worktree repair` делает человек).

### Владелец и корень вида

Для каждого зарегистрированного проекта X bars находит репозиторий: ближайшую вверх от корня X папку, где `.git` — **каталог**. Если по пути вверх раньше встретился файл `.git` (X лежит внутри worktree или подмодуля), у X worktree нет: он самостоятельный проект со своим индексом, bars его с основным не склеивает. Если корень X совпадает с корнем репозитория R, смещение пустое; если X лежит глубже (проект на подпапке монорепозитория), смещение — путь X от R, а корень вида — `W/<смещение>`.

Владелец worktree — каждый такой проект X репозитория R, у которого корень вида живого worktree существует. Типичный случай — один владелец. Подпроект с собственным `.git` (`backend/worker` в `tmc-opovechenie`) владеет worktree своего репозитория, а внешний проект `tmc-opovechenie` их не получает (ТР-10, OQ-313). Кого считать подпроектом, решает `subprojects.md` (Т-49); для worktree важен только `.git`-каталог.

Читать записи нужно по одному разу на репозиторий: если у нескольких проектов общий R, список читается один раз.

Ленивый подпроект (состояние `lazy`, [subprojects.md](subprojects.md)) тоже владелец: его worktree обнаруживаются и видны в `bars_status`, а чтение `.git/worktrees` ни ему, ни дельтам заданий не ставит. Первое обращение к worktree ленивого владельца (сессия в W, вызов с `wt`, открытие в окне) сначала активирует владельца — строит его индекс, — и только потом дельту: дельта сверяется с готовым индексом владельца, до него ответ идёт с пометкой «строится».

### Папка worktree внутри проекта и вне него

- `.worktree/<имя>` и `.claude/worktrees/<имя>` внутри проекта: обход проекта их уже не заходит (папки с точки), но bars теперь знает их как worktree, и сессия в них получает вид, а не «ближайший проект вверх» (раздел «Разрешение цели вызова»).
- Папка без точки внутри чужого проекта (`backend/worker-wt-quorum` рядом с `backend/worker`, `wt-foo/` в корне при `docs_root = .`) — тоже worktree; она исключается из индекса, дерева и слежения каждого проекта, внутри которого лежит, не только владельца.
- Папка вне любого проекта (`~/.iterion/projects/<ключ>/worktrees/<run-id>`): без особого случая. Владелец известен по записи в репозитории, а не по расположению папки; поэтому правило из `projects.md` «worktree вне проекта — по основному checkout» заменяется общим правилом вида.
- Папка с файлом `.git`, у которой нет живой записи в репозитории (остаток после ручной правки, `.claude/worktrees/xenodochial-…` без записи), worktree не считается и ничем не обрабатывается.

### Исключение папок worktree из индекса проектов

Папка W (вся, не только корень документации) исключается из индекса, дерева, слежения, ссылок и графа **каждого** зарегистрированного проекта, чей корень документации её охватывает, так же, как область вложенного проекта (Т-7). Механика та же, что у вложенных ([`bars_core::indexing::nested`](projects.md), раздел «Как исключение устроено в коде»), расширение:

- **[новое]** `nested::publish_worktrees(owners, dirs)` [написано 6.3.1] — воркер после обнаружения публикует папки живых worktree владельцев (список этих владельцев заменяется целиком, остальные не трогаются: хранилище одно на процесс); `nested::areas`/`prefixes`/`is_excluded` [есть] выдают их вместе с областями вложенных проектов, у записи нет `project` (вместо него `worktree`: имя и владелец). Папка W, не пересекающаяся с корнем документации проекта, ему не мешает и в его список не входит.
- `Inner::refresh_nested` [есть, `bars-worker/src/worker/mod.rs`] после обнаружения получает также список worktree; проекту, у которого список исключений изменился, ставится явная проверка: документы, ушедшие в исключение, удаляются из индекса по путям.
- Дерево проекта показывает такую папку серой пометкой «worktree» без галочек; `tree_read` отдаёт её в поле `nested` с видом `worktree` (окно рисует её отдельно, см. «Окно»).
- Папка пропавшего worktree возвращается проекту при ближайшей проверке, если на диске она ещё лежит: исключение действует только пока запись живая.

### Когда идёт обнаружение

| Событие | Что обнаруживается | Цена |
|---|---|---|
| Старт воркера | worktree всех зарегистрированных проектов | чтение `.git/worktrees/*`, файлы по 3–4 на worktree |
| Раз в час (таймер Т-10) | то же, включая ленивых владельцев; пропавшие и оторванные удаляются вместе с дельтой (ТР-6); у живых дельт — проверка актуальности | без чтения содержимого документов вне корней, без заданий без изменений (НТР-3); ленивому владельцу и worktree без дельты заданий не ставит |
| Хук начала сессии в W (`session_start`) | worktree владельца этой сессии | чтение записей одного репозитория |
| Открытие проекта в окне | worktree владельца и вложенных в него подпроектов | то же |
| Вызов с `wt`, который не нашёл имя | список перечитывается один раз, прежде чем отвечать ошибкой | то же |

Результат обнаружения — список `LinkedWorktree` у каждого владельца **[новое]**: `name`, `admin_dir`, `path` (W), `view_root`, `branch` (или `None` при `detached`), `locked`. Хранится в памяти воркера; на диск попадает только дельта.

## Хранилище дельты

### Раскладка файлов

```
<владелец>/.bars/
  index.sqlite                  индекс владельца (не меняется)
  worktrees/
    <имя>/
      index.sqlite              дельта (+ -wal, -shm)
```

Дельта лежит в `.bars/` владельца (Т-5): уходит ли папка в git, решает пользователь. Подпроект владеет своими дельтами в своей `.bars/`. Папку `.bars/worktrees/<имя>/` создаёт воркер при первом обращении к worktree; на диске после обнаружения её нет (ТР-2). Полное удаление проекта убирает `.bars/worktrees/` вместе с остальным ([deletion.md](deletion.md): в список файлов добавляется эта папка); снятие с регистрации её, как и всю `.bars/`, оставляет.

### Таблицы дельты

Дельта открывается тем же `Index::open` [есть, `bars-core/src/storage/index.rs`] и повторяет схему индекса ([schema.md](../../architecture/schema.md)): `meta`, `documents`, `chunks`, `chunks_fts`, `chunks_fts_vocab`, `vectors`. `document_sources` пишется без текста (граф и аудиты у worktree нет). Новое — одна таблица и ключи `meta`:

| Таблица | Колонки | Назначение |
|---|---|---|
| `documents`, `chunks`, `chunks_fts`, `vectors` [есть] | как у индекса владельца | **только** документы, чьё содержимое отличается от владельца или которых у владельца нет; векторы — их чанков |
| `wt_files` **[новое]** | `path` TEXT PK, `size` INTEGER, `modified_ns` INTEGER, `hash` TEXT | **все** документы вида (и совпадающие с владельцем, и отличающиеся): путь, размер, время изменения, blake3 текста. Без текста и без чанков — строка на документ. Служит сверке без чтения файлов и определяет, что в виде есть |

Ключи `meta` дельты: те же, что у индекса владельца и с теми же значениями на момент построения — `schema_version`, `model_source`, `model_id`, `model_dim`, `model_doc_prefix`, `chunk_min_chars`, `chunk_max_chars`, `chunking_version`, `stem_version`, `docs_root` (так `Index::stored_fingerprint`, `stored_layout` и `compatibility` работают на дельте без изменений), плюс **[новое]**:

| Ключ | Значение |
|---|---|
| `delta_version` | версия формата дельты, сейчас `1`; большая версия — дельта не открывается и удаляется (она производная) |
| `worktree_name` | имя worktree |
| `owner_digest` | blake3 по отсортированным парам `(path, hash)` таблицы `documents` владельца на момент последней **полной** сверки; нужен, чтобы после перезапуска воркера увидеть, что владелец ушёл вперёд |
| `ready` | `1` после завершения первого построения; до этого дельта поиском не используется |
| `synced_at` | секунды Unix последней завершённой сверки |

Дельта не хранит абсолютных путей: W берётся из записи worktree при каждом обнаружении. Поэтому переезд владельца вместе с `.bars/` не ломает дельту, а ломает только запись git (она станет пропавшей).

### Что и как копируется

Документ попадает в `documents` дельты, если у владельца нет документа с таким путём или хеши различаются. Чанки такого документа режутся и пишутся в `chunks` и `chunks_fts` тем же кодом нарезки, что у индекса (`chunk_document` [есть], `Index::replace_document` [есть]). Вектор чанка берётся по хешу текста для эмбеддинга в таком порядке: уже есть в дельте → есть в `vectors` владельца (копируется: `Index::vector` читает, `replace_document` нормализует и пишет) → иначе эмбеддится. Хеш включает путь, цепочку заголовков и текст ([schema.md](../../architecture/schema.md)), поэтому неизменившийся раздел правленого документа находит вектор владельца без модели (НФТ-1, НТР-1). Совпадающие документы не нарезаются, в FTS и в `vectors` дельты не попадают; диск дельты растёт с числом отличающихся документов (НТР-2).

Хеш документа считается так же, как в `process_file` [есть, `bars-core/src/indexing/indexer.rs`]: `blake3` по UTF-8-тексту без BOM; другой способ дал бы «различия» там, где их нет. Обе рабочие копии одного репозитория делят настройку `core.autocrlf`, поэтому одинаковые файлы совпадают и побайтно.

### Идентификаторы чанков

`chunks.id` у владельца и у дельты считаются каждый в своей базе и пересекаются. Поиск ведёт обе базы в одном пуле, поэтому **[новое]** `DELTA_ID_OFFSET = 1 << 40`: чанк дельты в пуле, в ответе и в коде ранжирования имеет номер `local_id + DELTA_ID_OFFSET`; номер ≥ смещения означает «читать из дельты, локальный номер — вычесть». Смещение прибавляет и вычитает один слой доступа (раздел «Поиск по worktree»); в самой дельте номера обычные. Результат поиска по worktree несёт такие номера; в `like`, `similar` и `duplicates` по worktree они не принимаются.

## Построение и обновление дельты

### Состояния дельты

| Состояние | Когда | Что отвечает поиск |
|---|---|---|
| нет | worktree найден, к нему не обращались; папки `.bars/worktrees/<имя>/` нет | не ищет по worktree: обращение создаёт дельту |
| строится | первое построение идёт (`ready = 0`) | ответ по владельцу целиком, с пометкой «worktree `<имя>`: индекс строится (N из M документов); ответ по основному checkout» (ТР-7) |
| готова | `ready = 1` | слияние владельца и дельты |
| ошибка | сверка или embed упали (модель недоступна, диск, формат) | ответ по владельцу с пометкой и текстом ошибки; повтор при следующем обращении и в часовую проверку |

Состояние живёт в памяти воркера (как состояния проектов, [worker.md](../../architecture/worker.md)); «готова» восстанавливается чтением `ready` из дельты.

### Первое построение и любая сверка — один алгоритм

Сверка `sync(owner, wt, область)` **[новое]**, область — все документы вида или список путей:

1. **Снимок владельца.** Читаются `path` и `hash` всех `documents` владельца (только чтение, `Index::open_read_only` под замком проекта на чтение, как у `scan`; [worker.md](../../architecture/worker.md), раздел «Запись и чтение индекса воркером»). Замок держится на время чтения снимка и на отдельные пачки копирования векторов, не на всю сверку.
2. **Обход вида.** `walk_docs_excluding(корень вида, docs_root владельца, исключённые области владельца)` [есть, `bars-core/src/indexing/walk.rs`] даёт `DocFile` с тем же `path`, что у владельца, и `fs_path` внутри W. Для списка путей — только эти файлы.
3. **Хеши.** Для документа, у которого размер и время изменения равны записи `wt_files`, хеш не считается. Остальные читаются (`read_utf8`) и хешируются. Нечитаемый как UTF-8 или занятый файл ведёт себя как у индексатора: нечитаемый удаляется из вида, занятый остаётся прежним; в отчёт идёт проблема.
4. **Сравнение.** `wt_files` обновляется по обходу, пропавшие файлы из неё удаляются. Документ **отличается**, если у владельца нет такого `path` или его `hash` другой. Отличающиеся и ещё не записанные в `documents` дельты (или записанные с другим хешем) идут на запись; документы дельты, которые больше не отличаются или пропали из вида, удаляются из `documents` (и из `chunks`, `chunks_fts`).
5. **Запись.** Каждый отличающийся документ — отдельной транзакцией дельты (поиск видит прежнюю или новую версию целиком), векторы — как в разделе «Что и как копируется». Документы без отличий не режутся и не эмбеддятся. После всех — уборка осиротевших векторов дельты (`remove_orphan_vectors` [есть]).
6. **Метка.** Для полной сверки в `meta` пишутся `owner_digest`, `synced_at`; при первом построении — `ready = 1` после последнего документа. Перед меткой снимок владельца читается ещё раз: если его подпись `owner_digest` изменилась (владелец успел подмениться полной переиндексацией или получить правки), сверка повторяется с шага 1 по хешам — не больше трёх проходов (дёшево: `wt_files` уже есть, файлы со старыми размером и временем не читаются). «Поколение» индекса владельца в этой реализации — именно подпись; счётчика подмен у воркера нет.

Вид без отличий (ТР-3): шаги 1–4 дают пустой список записи, шаг 5 ничего не делает, embed не вызывается, `documents` дельты пуста. Время — обход и хеши документов вида (на bars-project 739 `.md`, 5,9 МБ), порядок секунд (НТР-1; замер при реализации, ожидаемый узкий кусок — чтение файлов на диске). Правка одного раздела одного документа: в дельте один документ; эмбеддятся только чанки изменённого раздела, остальные берут вектор владельца.

Метаданные совместимости. Перед любой сверкой и перед каждым поиском сравниваются отпечаток модели, `chunking_version`, параметры нарезки, `stem_version` и `docs_root` в `meta` дельты с `meta` индекса владельца. Любое расхождение — дельта удаляется целиком (Т-25 и смена нарезки или корня владельца: ТР-6), состояние «нет», построение заново при следующем обращении. Если у владельца состояние `reindex_required`, поиск по worktree отвечает так же, как по владельцу (`reindex_required`), дельта не строится.

### Как это устроено в воркере (шаг 6.3.2)

- **Состояния** `none`/`building`/`ready`/`error` — в памяти воркера (`Deltas.entries`, ключ `(владелец, имя)`); «нет» — отсутствие записи. `building` несёт `done` и `total` (просмотрено документов вида из скольких); готовая дельта остаётся `ready`, пока её пересверяют по путям. `Worker::worktree_delta_status` отдаёт часть `delta` строки WORKTREES.
- **Первое обращение** — `Worker::ensure_worktree_delta(владелец, имя)`, приоритет `Explicit`: его вызывают хук `session_start` (сессия в W) и поиск, у которого вид — worktree (по `wt` или из `cwd`; `plan_worktree_search`, шаг 6.3.3). Ленивый владелец при этом сначала активируется (`activate`), и сверка ждёт его индекс; владелец в `reindex_required`, `unavailable` или без индекса заданий не получает. Обнаружение, `bars_status` без `refresh` и часовая проверка дельту не создают. Открытие worktree в окне (шаг 6.3.6) и `bars_status` с `refresh` и `wt` (6.3.5) вызовут тот же метод; пересверка путей (6.3.4) — `Worker::resync_worktree_paths`.
- **Задание** `Inner::delta_job`: снимок владельца читается под замком проекта на чтение (`GateOwner`: замок держится на один вызов — снимок или пачку векторов), отпечаток модели владельца сверяется с настройками, метаданные дельты — с владельцем (`check_delta`); расхождение — дельта удаляется и строится заново в этом же задании. Несовместимость, обнаруженная уже в `sync`, удаляет дельту и ведёт к «нет». Ошибка embed, диска или формата — состояние `error` с текстом, повтор при следующем обращении и в часовую проверку.
- **Проверка старта и часовая** (`Inner::check_deltas`, после обнаружения worktree; на старте — первым делом очереди дельт): для каждой папки `.bars/worktrees/<имя>` — нет живого worktree в записях → удалить; метаданные не сходятся с владельцем (модель, нарезка, `docs_root`, формат новее известного, файл не открывается) → удалить; иначе `ready = 1` из файла восстанавливает «готова», а подпись владельца, отличная от `owner_digest`, или недостроенная дельта ставят сверку `Periodic`. Владелец ленивый, в `reindex_required`, `unavailable` или с моделью в настройках, не совпавшей с индексом, пропускается целиком: удаление по модели случается после переиндексации владельца. Дельта, у которой сверка идёт сейчас, не удаляется до следующего прохода. Нет изменений — нет заданий (НТР-3).
- **Файлы**: `<владелец>/.bars/worktrees/<имя>/index.sqlite` открывает `worktree_delta::open_delta` (`Index::open` в WAL, схема владельца, `wt_files`, `delta_version`, `worktree_name`); при первой сверке в `meta` пишутся отпечаток модели и нарезка владельца. Документы дельты пишутся без текста (`document_sources` пуст).

### Как это устроено в воркере (шаг 6.3.4)

Код — `bars-worker/src/worker/wt_watch.rs`, ключ очереди документов — `DocTarget` (`doc_queue.rs`); написано без проверки сборкой.

- **Слежение за W.** Состояние слежения живёт в памяти по ключу `(владелец, имя)`: аренда MCP (час) и аренды окон (30 с на окно) плюс `ProjectWatcher` на корне документации вида (`W/<смещение>/<docs_root>`). Аренду ставят `Worker::observe_worktree_mcp` и `Worker::observe_worktree_window`; их вызовут MCP и окно в шагах 6.3.5–6.3.6. Слежение поднимается только при аренде **и** состоянии дельты не «нет»: аренда без дельты ничего не запускает, дельта, появившаяся позже (`request_delta`), поднимает его сама. Истёкшие аренды снимает таймер активности вместе с проектными. Состояние «нет» (дельта удалена, сверка пропущена или несовместима) останавливает слежение и снимает записи очереди документов этого worktree.
- **Правка в W.** Событие `Files` отбрасывает пути вне вида и в областях вложенных проектов, существующие `.md` ставит в очередь документов с паузой Т-41 (`Watch`; правка из окна — `Worker::edit_worktree_files`, источник `Edit`), пропавший `.md` — без паузы, папку без расширения — сверкой всего вида. Готовые записи цели одной пачкой уходят из очереди документов (`take_ready`) в очередь дельт как сверка путей; потерянные события (`Rescan`, ошибка слежения) ставят сверку всего вида.
- **Изменение владельца.** Наблюдатель задания проекта собирает пути, которые задание записало или удалило (`document_done` без ошибки); по итогу `Updated` или прерванному обновлению `Inner::owner_changed` ставит сверку этих путей каждой дельте владельца, у которой есть состояние: `Watch`, если у worktree есть аренда, иначе `Periodic`. Полная переиндексация (`rebuild`) и смена нарезки (`full_check` отчёта) публикуют «все документы»; прерванная переиндексация не публикует ничего.
- **Перезапуск.** Подпись `owner_digest` сравнивает проверка старта и часовая (`restore_delta`, шаг 6.3.2): расхождение ставит полную сверку `Periodic` по хешам; вектор берётся у владельца, модель вызывается только для чанков без вектора.
- **Отмена.** Остановка проекта (`Worker::cancel`), снятие и удаление зовут `cancel_deltas`: сверки его дельт отменяются, слежение за W останавливается, записи очереди документов его worktree снимаются.

### Что ставит пересверку затронутых путей

| Источник | Область | Приоритет в очереди |
|---|---|---|
| Первое обращение: сессия в W (`session_start`), поиск с `wt` или из cwd в W, открытие worktree в окне, `bars_status` с `refresh` и `wt` | все документы вида | явный (`Explicit`) |
| Правка в W: слежение за корнем вида (Т-10) или правка из окна | путь документа | `Edit` для окна, `Watch` для слежения; пауза Т-41 как у проекта |
| Изменение владельца: завершение задания индексации владельца (обновление пачки, удаление, полная переиндексация) | пути, которые задание записало или удалило; после полной переиндексации — все | `Watch` для дельты, которой пользуются сейчас (окно открыто, аренда MCP), иначе `Periodic` |
| Часовая проверка и старт воркера | все документы вида; у дельты с другим `owner_digest` — после сверки подпись обновляется | `Periodic` |

Слежение за корнем вида включается и выключается по тем же правилам Т-10, что у проекта: пока открыто окно на этом worktree или идёт час после последнего MCP-вызова по нему. Событие внутри W отбрасывается, если дельта в состоянии «нет». Событие ставит запись в очередь документов с ключом `(владелец, имя, путь)` **[новое]**: `DocQueue` [есть, `bars-worker/src/worker/doc_queue.rs`] ключуется проектом и путём — ключ проекта становится «цель очереди» (`Project(путь)` или `Worktree{владелец, имя}`); пауза Т-41, одна запись на ключ и порядок приоритетов Т-42 ([очередь документов](../indexing/document-queue.md)) действуют без изменений.

Завершение задания владельца — единственное событие владельца, которое **[новое]** публикует `JobQueue` [есть]: список путей, реально записанных или удалённых заданием. Воркер превращает его в задание сверки каждой живой дельты владельца. Правка того же документа в основном checkout меняет `documents.hash` владельца: если вид содержит старую версию (хеш в `wt_files` отличается), документ теперь отличается и его надо записать в дельту; если вид и владелец сошлись, документ из дельты уходит (ТР-5).

### Очередь и конкурентность

- Сверка — задание очереди дельт воркера (`worker/delta.rs`), область которого — не проект, а `(владелец, имя)`; приоритеты те же (`Priority`), равный приоритет сохраняет порядок появления, повторное задание того же ключа сливается (список путей объединяется, «все документы» поглощает список). Выбор (реализация 6.3.2): очередь дельт отдельна от `JobQueue` проектов — та ключуется путём проекта и тесно связана с журналом операций, — но правило «одно задание индексации за раз» сохранено общим флагом: сверка берётся, только когда очередь проектов пуста и ничего не выполняется, а пока она идёт, очередь проектов ждёт её конца (`delta_busy`). Задание проекта поэтому может ждать окончания долгой сверки; сверка владельца идёт после его собственной индексации. Пауза очереди (OQ-55) замораживает и сверку; остановка воркера прерывает её на границе документа. Поиск и вызовы MCP по-прежнему стоят выше всей индексации (замок модели, Т-42).
- Писатель дельты один: замок `(владелец, имя)`. В индекс владельца задание дельты не пишет никогда (`Index::open_read_only`); мешать ему может только полная переиндексация с подменой файла, которая закрывает доступ на чтение на короткое время: сверка ждёт замок на чтение и после подмены перечитывает снимок (шаг 6).
- Владелец индексируется — дельта читает его WAL-снимок и не ждёт. Владелец в `reindex_required` или `unavailable` — задания дельты не ставятся.
- Много worktree у одного владельца строятся по одному: каждое — своё задание, равный приоритет сохраняет порядок появления. iterion, создающий worktree на каждый запуск, нагружает только те, к которым обратились.
- Отмена проекта (снятие, удаление, остановка) отменяет и задания его дельт, и слежение за W; полное удаление проекта ждёт, пока идущая сверка закроет файл дельты.

## Поиск по worktree

### Допустимые документы владельца

Поиск по виду строится так, чтобы кандидаты владельца не смешивали чужие версии. Документ владельца допустим в виде, если одновременно: его `path` есть в `wt_files`; его `hash` в `documents` владельца равен `hash` в `wt_files`; его `path` отсутствует в `documents` дельты. Всё остальное у владельца — **исключённые пути**: это документы, которых в виде нет (удалены в worktree или появились у владельца позже), и документы, чью версию вида даёт дельта, и документы, где владелец успел измениться, а дельта ещё не пересчитана. В последнем случае документ временно не виден вовсе (ни старая версия вида, ни новая версия владельца): ответ называет число таких документов («N документов worktree пересчитываются»); пауза в секунды обычно.

Список исключённых путей считается в памяти из трёх таблиц (порядок сотен или тысяч строк) и кэшируется по паре «поколение индекса владельца, поколение дельты»; поиск его не пересчитывает, пока ни одно не изменилось.

### Слияние кандидатов до rerank

Один поиск Т-12, одна схема баллов ([hybrid-search.md](../search/hybrid-search.md), «Схема баллов»); меняется только сбор пула. Эмбеддинг запроса считается один раз, rerank — один раз по общему пулу.

1. **Каталог области.** Модули, файлы и `in` проверяются и приводятся к путям по объединению документов вида: допустимые документы владельца и документы дельты. Неизвестный модуль или путь — ошибка со списком ближайших, как сейчас. Для этого `Scope::build_with_paths` [есть, `bars-core/src/search/hybrid.rs`] получает каталог вместо `Index` (сейчас он проверяет по `documents` одного индекса). Условие `Scope` для SQL после приведения одинаково для обеих баз.
2. **Проход по владельцу.** Прежние запросы `Scope::text_scored` и `Scope::cosines` [есть], в условие которых добавлено `d.path NOT IN (SELECT path FROM temp.wt_excluded)`. Временная таблица создаётся на читающем соединении (временная база доступна и при `SQLITE_OPEN_READ_ONLY`) и заполняется исключёнными путями; индекс владельца не меняется.
3. **Проход по дельте.** Те же запросы по дельте без исключений: в ней только документы вида. Номера чанков получают смещение.
4. **Объединение.** `text_ids` и `exact_ids` — по списку от каждой базы (по `candidates` штук от каждой), пул — их объединение; `vector_ids` — первые `candidates` по объединённой карте косинусов обеих баз. Косинус (0…1, абсолютный) от базы не зависит, поэтому слияние точное. Пул по сравнению с обычным поиском может вырасти не более чем вдвое: дальше действует предварительная сортировка `Candidate::preliminary` и обрезка до `rerank_candidates` [есть].
5. **Сигналы.** `p` (точное совпадение в колонке `exact`) не зависит от корпуса — считается каждой базой по её чанкам. `f` — см. ниже. `l` не считается: индекса ссылок у вида нет (`w_l = 0`, расширения кандидатов по связям нет).
6. **Загрузка.** Все функции, которые по номеру чанка читают `chunks`, `documents` и `chunks_fts` (`rerank_scores_of`, `load_documents`, `fold_sections`, `fold_weak`, `count_candidate_modules`, `load_hits`, `f_signal`, `p_signal` и `plan.filter.retain` в `hybrid.rs` и `fulltext.rs`), получают слой доступа **[новое]** `IndexView`: источники (владелец с исключёнными путями, дельта со смещением), метод раздаёт номера по источникам и склеивает результаты. Обычный поиск проекта — вид из одного источника без исключений: поведение, баллы и порядок не меняются, а тесты `bars-core/src/search/hybrid/tests.rs` проходят без правок.

### Как сохраняется сопоставимость полнотекстового балла

`f` — сырой балл `bm25` чанка, делённый на лучший балл списка запроса ([полнотекстовые сигналы](../search/fulltext.md)); `bm25` зависит от размера корпуса и частот слов, а у владельца (тысячи чанков) и у дельты (десятки) они разные. Баллы двух баз напрямую складывать нельзя: у слова, которое есть более чем в половине чанков маленькой дельты, вес стремится к нулю.

Выбор (минимальный, сохраняющий смысл схемы): `f` нормируется **внутри своей базы** — чанк владельца делится на лучший балл списка владельца, чанк дельты — на лучший балл списка дельты. Это допустимо, потому что:
- `f` — добавка с весом `w_f = 0,1`, а опора `a` (rerank, без rerank — косинус) — абсолютная и от базы не зависит; искажение любого результата не больше 0,1 в `S`, и порог `min_score` относится к опоре, а не к `S` ([схема баллов](../search/hybrid-search.md));
- на виде без отличий у дельты нет списка, и результаты побитово совпадают с поиском владельца;
- документ вида в дельте — тот, что человек правил: небольшая добавка ему не вредит.

Известное ограничение: лучший по словам чанк дельты всегда получает `f = 1` даже при слабом совпадении. Проверка — тест на «непричастную правку» (раздел «Проверка») и прогон бенча на worktree с одной правкой; если Hit@3 или MRR на неизменённых документах просядут, следующий шаг — перенос оценки `bm25` дельты на шкалу владельца по словарю `chunks_fts_vocab` владельца. До такого результата выбор остаётся нормировкой по базе.

Исправление опечаток (`typo_corrections` [есть, `fulltext.rs`]) берёт словарь индекса владельца; слова, которые есть только в дельте, не исправляются. Это ограничение вида.

### Как устроен поиск по виду в коде

Написано шагом 6.3.3 без проверки сборкой.

- **Слой доступа.** `bars_core::search::IndexView` (`search/hybrid/view.rs`): `IndexView::single(index)` — обычный поиск проекта; `IndexView::worktree(owner, delta, excluded)` — владелец и дельта, исключённые пути кладутся во временную таблицу `temp.wt_excluded` соединения владельца. Номер чанка или документа вида ≥ `DELTA_ID_OFFSET` (`1 << 40`) — дельта, локальный номер — вычесть смещение; `IndexView::source` раздаёт номера, `load_hits`, `chunk_document`, `section_span`, `count_candidate_modules`, `f_signal`, `p_signal`, `retain`, `text_scored`, `cosines` склеивают ответы баз. `search_in_view` — сам поиск по виду; `search`, `search_with_signals`, `search_with_links` — оболочки над ним с `IndexView::single`, бенч (`scored_pool`, `candidate_trace`) тоже.
- **Каталог области.** Трейт `Catalog` (`has_module`, `has_path`, `has_under`, `documents`, `docs_root`): его реализуют `Index` (обычный проект) и `IndexView` (допустимые документы владельца плюс документы дельты). `Scope::build_with_paths` принимает каталог; `Scope::build` по `Index` осталась.
- **Исключённые пути.** `worktree_delta::excluded_paths(owner, delta)` → `ExcludedPaths { paths, pending, delta_documents }` по `documents` владельца, `wt_files` и `documents` дельты. Кэш воркера (`handler/worktree_view.rs`) ключуется `(владелец, имя)`; «поколение» — подпись из длины и времени изменения `index.sqlite` и `index.sqlite-wal` обеих баз (четыре `stat`): счётчика поколений у воркера нет (выбор), подпись, изменившись, лишь пересчитывает список.
- **Пул.** С двумя источниками `text_scored` и идентификаторы берут по `candidates` от каждой базы, косинусы — по базе, дальше общая карта; `f` делится на лучший балл списка своей базы; `l`, расширение связями и графовые бюджеты при слиянии отключены (`expansion` и `links` игнорируются, граф не грузится).
- **Решение воркера.** `plan_worktree_search` ставит первое обращение (`ensure_worktree_delta`) и смотрит состояние дельты: «готова» — слияние; «строится», «нет» или «ошибка» — ответ по владельцу, а в `applied.scope.worktree` (`SearchWorktree`: `name`, `branch`, `state`, `delta_documents`, `pending`, `note`) — состояние и строка пометки («worktree `<имя>`: индекс строится (N из M документов); ответ по основному checkout»). Файл дельты не открылся или список исключённых путей не собрался — тот же ответ по владельцу, `state = error` и текст ошибки в `note`. После слияния `pending` — число пересчитываемых документов, при `pending > 0` в `note` — «N документов worktree пересчитываются». `reindex_required` у владельца проходит как у проекта: дельта не строится. Поиск по виду «Новые темы» не пополняет.
- **Чтение по диску.** `read`, `outline` (`WorkerHandler::document`) и `disk_text` берут корень вида (`worktree_view::view_root`: корень проекта или `view_root` worktree), допуск путей считается от него; `read_folder` перечисляет документы обходом корня вида и читает заголовки файлов (`disk_documents`). Дельта этими вызовами не создаётся. Поиск, чтение и папка идут через `WorkerHandler::usable_view` — проект и вид с проверкой папки проекта.
- **Граф, ссылки, аудиты.** `dispatch` дописывает в JSON-ответ `graph_search`, `graph_query`, `graph_status` и `disk_links` поле `worktree_note` со строкой «worktree `<имя>`: граф, аудиты и ссылки есть только у основного checkout; показан основной checkout», если вид вызова — worktree; вызов выполняется по владельцу. Аудиты и `links_of`/`links_into` принимают `project`, а не `Target`: `wt` у них появится вместе с MCP и CLI (шаг 6.3.5). Ошибку «документа нет у владельца» с этой же строкой шаг не делает.
- **`like`, `similar`, `duplicates`.** С видом worktree (по `wt` или из `cwd`) отвечают `invalid_params` с `data.kind = "worktree_unsupported"`, `data.worktree` и подсказкой `wt="."`; чанк с номером вида (≥ `DELTA_ID_OFFSET`) `similar` не принимает.

### Чтение, структура, точный поиск и содержимое папки

Эти операции не используют индекс и работают по диску W сразу, без дельты и без модели: путь документа принимается обеими формами (от корня документации и от корня проекта, как у `read`), но отсчитывается от корня вида; `docs_root` — владельца. Допуск путей (канонизация, запрет выйти наружу через symlink и junction, как в [допуске путей](../knowledge-base/tree-and-files.md)) считается от корня вида. `read` и `outline` отдают `revision` из текста файла W. `occurrences` (`disk_text`) обходит корень вида без списка областей, как у проекта. Содержимое папки (`bars_read` для папки, OQ-320) перечисляет папку W. Эти вызовы дельту не создают.

### Чего в worktree нет

Граф, аудиты, индекс ссылок, «Новые темы», `like`, `similar` и `duplicates` — только у основного checkout (ТР-9, OQ-314). Поведение:

- Инструменты и команды графа и аудитов, `bars_read(view="links")`: выполняются по владельцу, в начале ответа строка «worktree `<имя>`: граф, аудиты и ссылки есть только у основного checkout; показан основной checkout». Если документа нет у владельца — ошибка с этой же строкой.
- `bars_search(like=…)` и `similar`, `duplicates` с worktree: ошибка `invalid_params` с `data.kind = "worktree_unsupported"` и подсказкой `wt="."`. Выбор: `like` строится на ссылках и векторах основного индекса, а номера чанков вида смещены.
- Поиск по worktree спрос в «Новых темах» не записывает (как `diagnostic`): выдача неполна по определению.

## Разрешение цели вызова

### Параметр wt

`Target` [есть, `bars-protocol/src/methods.rs`] получает поле `wt` **[новое]**: `{cwd, project?, wt?}`. Раз `Target` вложен (`serde(flatten)`) во все методы с проектом, `wt` появляется у `search`, `outline`, `read`, `status`, `projects`, `disk_text` и остальных без правки каждого DTO. Пустая строка равна отсутствию.

Значение `wt` относится к **проекту вызова** (`project` или ближайший к `cwd`, раздел ниже) и принимает:

| Значение | Что значит |
|---|---|
| `"."` | основной checkout, даже если `cwd` лежит в worktree |
| имя | папка записи `.git/worktrees/<имя>` проекта; сравнение точное, на Windows — без учёта регистра |
| абсолютный путь | W или любая папка внутри неё; путь нормализуется как у реестра |
| отсутствует | см. «Умолчание из cwd» |

Имя ветки как значение не принимается (OQ-316: ветка меняется и бывает `detached`). Самая вероятная ошибка агента — передать имя ветки, поэтому в тексте ошибки у каждого worktree названа ветка.

### Умолчание из cwd

Сессия с `cwd` внутри живого worktree и без `wt` работает с этим worktree (ТР-7, OQ-307). Явный `project`, не равный владельцу этой копии, неявного `wt` не даёт: агент спрашивает про другой проект. Явный `project` равный владельцу неявный `wt` сохраняет: агент в worktree, который называет свой проект по имени, хочет свои правки; основной берётся через `wt="."`.

### Изменения в реестре воркера

`Registry::project_of_worktree` и `discover_root` заменены, `project_for_cwd` стала оболочкой, а разбор файла `.git` (прежняя `main_checkout_of_worktree`) переехал в `bars_core::worktree::locate`, чтобы им пользовались и реестр, и обнаружение (написано шагом 6.3.1 без проверки сборкой):

- `Registry::resolve_cwd(cwd) -> Option<CwdTarget>`, где `CwdTarget { project: &ProjectEntry, worktree: Option<WorktreeRef> }`, `WorktreeRef { name, admin_dir, path (W), view_root, repo (R) }`. Порядок: (1) ближайшая вверх от `cwd` папка с файлом `.git` — это W, если запись по её `gitdir:` живая (`worktree::locate`: `gitdir` записи указывает на `W/.git`, запись лежит в `<R>/.git/worktrees/<имя>`, `commondir` ведёт в `R/.git`); (2) владелец — зарегистрированный проект X, лежащий внутри R, для которого R — его репозиторий (`worktree::repository_of`) и `cwd` лежит внутри корня вида `W/<смещение X>`; при нескольких X побеждает тот, чей корень вида ближе к `cwd`; (3) нет владельца или запись мертва — прежний обход: ближайший зарегистрированный проект вверх от `cwd`, затем `None`.
- `worktree::locate` — функция разбора файла `.git`: подмодуль, bare-репозиторий, битый файл и мёртвая запись дают `None`.
- `Registry::project_for_cwd` — оболочка над `resolve_cwd`, возвращающая только проект: ею пользуются `Worker::project_for_cwd`, `session_info` и окно (`bars-app/src/commands.rs`); `Worker::resolve_cwd` отдаёт и вид.
- `WorkerHandler::resolve_view(target)` возвращает проект и `ViewSelector { Main | Worktree(LinkedWorktree) }`: `wt="."` → `Main`; `wt` задан → поиск среди worktree проекта (`Worker::find_worktree`: имя, на Windows без учёта регистра, или абсолютный путь; промах перечитывает список один раз); `wt` не задан и `cwd` в живой W владельца-проекта → `Worktree`; иначе `Main`. `WorkerHandler::resolve` — оболочка, возвращающая только проект (`wt` проверяется везде); поиск, чтение, структура, точный поиск и папка идут по виду через `usable_view` (шаг 6.3.3, раздел «Как устроен поиск по виду в коде»). В историю MCP ([mcp-statistics](../window/mcp-statistics.md)) пишутся применённые поля `resolved_wt` и `wt_source` (`param` / `cwd` / `main`) — через `history::applied_field`.

### Хук начала сессии

`Registry::discover_root` теперь возвращает `Option<Discovered>`: для `cwd` в живой W — владельца как зарегистрированный проект с признаком worktree (`Discovered.worktree`). Хук **не регистрирует** worktree проектом (OQ-307) и не регистрирует его основной checkout, если тот не зарегистрирован: вместо прежнего «основной checkout не зарегистрирован — шаги 2 и 3 по W» результат `None`, реестр не меняется (`Worker::session_start` отвечает `None`). Владелец зарегистрирован: `Worker::session_start` продлевает MCP-активность владельца, ставит проверку владельца и перечитывает worktree владельца и вложенных в него проектов; запрос первого обращения к виду (`Explicit`) появится вместе с дельтой (шаг 6.3.2). Тест `worktree_of_unregistered_main_checkout_keeps_old_rules` заменён на `hook_does_not_register_worktree_or_unregistered_main` (`registry.rs`): хук не регистрирует ни копию, ни основной checkout. Остальные тесты worktree в `registry.rs` (`linked_worktree`, `worktree_outside_project_belongs_to_its_main_checkout`, `worktree_with_relative_gitdir_finds_its_main_checkout`, `worktree_with_project_bars_is_not_registered_separately`, `broken_or_foreign_git_file_is_not_a_worktree`) сохранены; в тех, что проверяли `project_for_cwd`, проверяется и признак worktree.

### Ошибка неизвестного wt

Код −32020, `kind = worktree_not_found` **[новое]** (в таблицу ошибок [протокола](../../architecture/protocol.md) добавляется строка). Текст: `У проекта «<имя>» нет worktree «<значение>». Есть: «<имя1>» (ветка <ветка>, <путь>), «<имя2>» (detached, <путь>). Основной checkout — wt="."`. У проекта без worktree: `У проекта «<имя>» нет worktree; основной checkout — wt="."`. В `data` — список `{name, path, branch, locked}`. `bars-cli` завершается с кодом 1 (как остальные), в `--json` ошибка как есть. Перед ответом список перечитывается один раз (раздел «Когда идёт обнаружение»), чтобы только что созданный worktree не получил ложную ошибку.

## Жизненный цикл

| Событие | Что происходит |
|---|---|
| `git worktree add` | worktree виден после ближайшего обнаружения (час, хук, открытие проекта); индекса нет, `.bars/worktrees/` не создаётся (ТР-1, ТР-2) |
| Первое обращение | создаётся `.bars/worktrees/<имя>/`, первое построение (`строится` → `готова`) |
| Правка в W | пересверка пути после паузы Т-41; документ, ставший равным владельцу, уходит из дельты (ТР-5); при состоянии «нет» событие отбрасывается |
| Изменение документа у владельца | пересверка затронутых путей живых дельт (ТР-5) |
| `git worktree remove`, удаление папки вручную, перенос репозитория | запись пропала или оторвалась: при ближайшей проверке исчезают worktree и `.bars/worktrees/<имя>/` (ТР-6, OQ-308). Если папка W ещё лежит, она возвращается индексу проекта, внутри которого лежит, при пересчёте исключений |
| Смена модели embed у владельца (Т-25) | поиск по worktree отвечает `reindex_required`; после переиндексации владельца отпечаток дельты не совпадает — дельты владельца удаляются при ближайшей проверке и перестраиваются при обращении (ТР-6) |
| Смена нарезки или `docs_root` у владельца | то же: дельты удаляются, строятся заново |
| Владелец снят с регистрации | дельты не обслуживаются (проект не в реестре); файлы в `.bars/worktrees/` остаются как остальная `.bars/` и проходят проверку при повторной регистрации |
| Владелец удалён полностью | `.bars/worktrees/` удаляется вместе с `.bars/` ([deletion.md](deletion.md)) |
| Папки владельца нет (`unavailable`) | вызовы с `wt` отвечают `project_unavailable`; дельты не трогаются |
| Старый `index.sqlite` дельты, `delta_version` новее известной | дельта удаляется (производная); при построении создаётся заново |
| Воркер перезапущен | состояния в памяти пропадают; при проверке старта `ready = 1` восстанавливает «готова», `owner_digest` сравнивается с владельцем, при расхождении идёт полная сверка (хеши, без embed, если вектора есть) |
| Худший случай: владелец ушёл далеко вперёд | сверка записывает в дельту все документы вида, которые отличаются; embed только тем чанкам, у которых нет вектора у владельца |

## MCP, CLI и окно

### MCP

Параметр `wt` — рядом с `project` у всех четырёх инструментов ([agent-layer-project.md](../agent-tools/agent-layer-project.md), [mcp-tools.md](../agent-tools/mcp-tools.md)): `bars_search`, `bars_read`, `bars_status`, `bars_audit`. Описание параметра (на английском, НФТ-4): worktree name from `.git/worktrees/<name>` or an absolute path; `"."` — the main checkout; default — the worktree of the session's cwd. Графовые инструменты (скрытые настройкой `[mcp] graph_tools`) принимают его тоже и ведут себя как в «Чего в worktree нет».

- `bars_search`: поиск по виду; в `applied.scope` (поле `worktree` у `SearchScope` [новое]: `name`, `branch`, `state`, `delta_documents`, `pending`) и в шапке текстовой выдачи видно, по чему искали. Состояние «строится» или «ошибка» — строка пометки над результатами.
- `bars_read`: путь и папка читаются из W; `view="links"` — по правилу «Чего в worktree нет».
- `bars_status`: часть WORKTREES (ниже); с `wt` — только этот worktree, с `refresh=true` — сверка вида (первое обращение, если дельты нет).
- `bars_audit`: по владельцу с пометкой.
- `initialize` (`session_info`): для сессии в worktree имя проекта дополняется «, worktree `<имя>` (ветка …)», модули — владельца.

### CLI

`--wt <имя|путь|.>` у каждой команды `bars-cli`, у которой есть `--project` (`search`, `read`, `outline`, `status`, `reindex`, команды графа и аудитов); смысл тот же, что у `wt`; `reindex --wt` проверяет вид (сверка дельты), `reindex --full --wt` не принимается (`invalid_params`: дельта полной переиндексации не знает, достаточно удалить worktree или сменить модель). `register --wt` не существует: worktree проектом не регистрируется. `--json` печатает ответ метода как есть.

### Как это устроено в MCP и CLI (шаг 6.3.5)

Написано без проверки сборкой.

- **Протокол.** `wt_value` (пустая строка и пробелы — нет значения), `owner_only_note(имя)` — строка пометки для графа, ссылок и аудитов, `view_worktree(wt, worktrees)` — какой worktree назвал ответ `status` (явный `wt` — единственный в списке; `"."` — никакой; без `wt` — отмеченный `current`). `SessionInfoParams` получили необязательные `project` и `wt` (проверка цели без записи в историю; неизвестный `wt` — `worktree_not_found`), `SessionProjectInfo.worktree` — `{name, branch}`.
- **MCP.** `wt` — рядом с `project` у `bars_search` (обе формы), `bars_read`, `bars_status`, `bars_audit` и шести графовых инструментов; значение уходит воркеру как есть (`"."` — не путь от `cwd`, в отличие от `project`). Ответы, к которым воркер дописывает `worktree_note` (граф, `view=links`, `graph_status`), читаются через `call_noted`: текстовый вид получает строку пометки над ответом, JSON графа — поле `worktree_note`. У аудитов и «Новых тем» `Target` нет, поэтому пометку и проверку `wt` даёт `session_info` с `project` и `wt` (без записи в историю); с `wt="."` проверки нет. Шапка текстового поиска — `scope: … ; worktree <имя> (<ветка>, delta <состояние>)`, строка `note: …` из `applied.scope.worktree.note` идёт сразу под шапкой. `bars_status` с `wt` не сочетается с `all` и `filter`; `refresh=true` с `wt` — `ReindexParams` с тем же `wt`; пометка о графе и аудитах стоит перед частью AUDITS.
- **Воркер.** `reindex` с видом worktree ставит сверку всех документов вида (`Worker::resync_worktree`, `Explicit`; у ленивого владельца сначала его индекс); `full` и `accept_model_change` — `invalid_params`, `data.kind = worktree_unsupported`; владелец не готов — `project_unavailable`. Вызов MCP с видом worktree (явным или из `cwd`) продлевает аренду слежения `observe_worktree_mcp` (час, Т-10). В историю MCP `wt` входит в разрешённые поля `requested` у всех инструментов; применённые `resolved_wt` и `wt_source` пишет разрешение цели (6.3.1).
- **CLI.** `--wt` — глобальный флаг рядом с `--project`; у `register`, `unregister`, `projects`, `install`, `uninstall`, `autostart` он отклоняется `invalid_params` до обращения к воркеру (`projects --filter` несовместим с ним на уровне разбора аргументов). `reindex --wt` печатает «Сверка worktree принята…». Строка `worktree_note` ответа печатается над текстом; `--json` печатает ответ как есть. `worktree_not_found` — код выхода 1.

### bars_status: часть WORKTREES

У проекта-владельца ответ получает часть **[новое]** `WORKTREES` (как PROJECT, INDEX и остальные, со своей ошибкой при сбое):

```
WORKTREES (2)
- worker-wt-quorum · ветка feat/quorum · C:\repos\…\worker-wt-quorum · дельта готова, 2 документа отличаются [сессия]
- api-avatar · detached · …\api-avatar · locked: «на флешке» · дельты нет (строится при первом обращении)
```

Поля каждой строки (структура `WorktreeStatus`, JSON `bars-cli status --json`): `name`, `path`, `branch` (или `null` при `detached`), `locked` (причина или `null`), `delta`: `state` (`none`/`building`/`ready`/`error`), `documents` — число документов в дельте, `done` и `total` при `building`, `pending` — пересчитываемые пути, `error`; `current: true`, если это worktree сессии. Живые worktree без дельты перечисляются, но не создают её: `bars_status` без `refresh` дельту не строит. Фильтр `bars_status` по подстроке (Т-50) сопоставляет имя, путь и ветку worktree и возвращает владельца, у которого совпал worktree.

### Окно

- **Дерево.** В дереве проекта-владельца, если у него есть живые worktree, после модулей идёт папка «worktree» (значок ветвления, без галочки, число worktree справа); в ней — по папке на каждый worktree с именем и пометкой ветки и состояния дельты («не проиндексирован», «строится 12 из 40», «готов, 2 отличаются», «ошибка»); внутри — обычное дерево корня документации worktree («модуль → папки → файлы» как у проекта). Узлы строятся `tree_read` с `wt` (`status: ok`, те же поля), без чтения содержимого. Папку worktree в дереве проекта (внутри исключённых областей) окно показывает серой пометкой «worktree» без галочек: её документы — в ветке «worktree».
- **Открытие.** Раскрытие папки worktree, открытие в ней документа и поиск по ней — первое обращение: дельта строится, пока идёт построение, дерево доступно (по диску), а в строке состояния показан ход. Закрытие окна построение не прерывает; слежение за W снимается с окном (Т-10).
- **Галочки.** Выбор хранится вместе с видом (владелец или `(владелец, имя)`): поиск окна идёт по виду, в котором стоят галочки. Поставить галочку в другом виде — прежний выбор снимается, у списка выбора короткая подсказка «поиск идёт по одному виду». Основной checkout и worktree, а также разные worktree, в одном поиске не смешиваются (ТР-11). Результаты поиска по worktree показывают плашку worktree.
- **Редактор.** Документ из worktree открывается вкладкой с пометкой worktree и сохраняется в файл W (`document_write` с `wt`; допуск путей — от корня вида). Ревизия, конфликт версий и автосохранение — как у проекта. Операции дерева (`entry_*`) работают в виде, обновление ссылок при переименовании не выполняется (индекса ссылок у вида нет) — окно говорит об этом в плане переноса.
- **Граф, аудиты, «Новые темы».** У worktree ветка отсутствует: пункты неактивны с подсказкой «только у основного checkout» (ТР-9).
- **Состояние.** `status` окна несёт список worktree владельца (имя, путь, ветка, `delta`) — то же, что `WORKTREES`; `projects` и `tree_read` его не дублируют.

### Как устроено в окне (шаг 6.3.6)

Написано без проверки сборкой; макет — [worktree-view.html](../window/mockups/worktree-view.html), согласован автором 12-11-2026 (с правкой отступа плашки у заголовка карточки).

- **Список worktree** окно берёт из `status` (часть `worktrees` владельца: `StatusOutput.worktrees` в `ui/src/lib/types.ts`) — из снимка окна и раз в тик, пока раскрыт хотя бы один worktree (`App.loadWorktrees`); смена `delta.state`, числа документов или хода перечитывает деревья раскрытых worktree. Исчезнувший worktree снимает выбор в нём и закрывает его дерево.
- **Дерево.** `WorktreeFolder.svelte` стоит в `Sidebar.svelte` после модулей; внутри каждого раскрытого worktree — три неактивные строки «Новые темы», «Аудиты», «Граф» с причиной «только у основного checkout» и `TreeRow` с `wt`. Дерево вида — `buildTree(документы вида, диск W)`: документы берёт воркерный метод `tree` с `wt` (индекс владельца, поверх него документы готовой дельты; дельта ставится первым обращением), а файлы и папки — команда `tree_read` с `wt` по диску W. Вложенные проекты и папки worktree в дереве вида не отдаются. `tree_read` и снимок окна у основного checkout отдают в `nested` и папки worktree с `kind: "worktree"` (`commands::tree_nested_json`), `TreeRow` рисует их серой пометкой «worktree» без галочки и без «Открыть проект».
- **Открытие.** Раскрытие worktree вызывает `tree` и `tree_read` с `wt` (оба ставят дельту: `Worker::ensure_worktree_delta`), `tree_read` продлевает аренду окна (`Worker::observe_worktree_window`); команда `worktree_observe` повторяет аренду каждые 10 секунд вместе с наблюдением за проектом (`App.#watch`, `focusWt` — worktree, который окно сейчас показывает), `wt: null` снимает её.
- **Галочки.** Выбор — один: `App.selected` с `App.selectionView` (`null` — основной checkout, иначе имя worktree). Галочка в другом виде снимает прежний выбор и показывает подсказку («Поиск идёт по одному виду: выбор в … снят»); строки чужого вида галочек не показывают. Поиск окна идёт с `wt = selectionView`, без выбора — по основному checkout. Выдача по worktree носит плашку «worktree · имя» у карточки документа и строку пометки `applied.scope.worktree.note` над результатами; «В графе» и «Похожие разделы» неактивны.
- **Редактор.** Ключ вида (`viewKey(проект, wt)` в `ui/src/lib/view-key.ts`, `проект␀wt:имя`) служит «проектом» буфера редактора и вкладки: буферы, очередь несохранённого и закрытие вкладки работают без правок. Команды окна получают ключ разобранным (`api.ts`: `project` и `wt`). `document_read`, `document_write`, `document_revision` идут от корня вида (допуск путей — `document_io::resolve(корень вида, …)`); сохранение в виде зовёт `Worker::edit_worktree_files` (пауза Т-41 и сверка пути дельты) вместо `documents_edited`. Вкладка документа worktree — своя (id `document:<путь>:wt:<имя>`), с плашкой «worktree · имя» и пояснением «сохраняется в файл этой копии»; ссылки и обратные ссылки у неё не строятся, контекстное меню файла (перенос, удаление, «В графе») для неё не показывается.
- **Операции дерева** (`entry_create_doc`, `entry_create_dir`, `entry_plan_move`, `entry_move`, `entry_trash`, `entry_plan_delete`) принимают `wt` на стороне команд: корень вида, без публикации в подписку проекта; перенос и переименование идут через `tree_io::plan_move_without_links` и `move_without_links` — ссылки не обновляются, ответ плана несёт `links_updated: false`; `entry_plan_delete` не считает входящие ссылки (`links_checked: false`). Пунктов меню для строк в виде worktree окно пока не даёт (у таких строк нет `data-menu-kind`), так что команды доступны вызовам окна, а не меню.
- **Чего нет.** Отдельных строк worktree в переключателе проектов нет: они — папка дерева (решение шага, см. [subprojects.md](subprojects.md)); отдельное окно документа worktree не открывается; раскладка вкладок worktree восстанавливается, но вид, которого уже нет, даёт ошибку чтения в самой вкладке.

- Время первой сверки на bars-project и время часовой проверки на `tmc-opovechenie` не измерены (НТР-1, НТР-3); измеряются при реализации шага 2.

- Приёмка Т-48 говорит «после первого вызова с `wt` дельта есть»; здесь это поиск, хук сессии, открытие в окне и `bars_status` с `refresh`. Чтение, структура, точный поиск и папка по диску дельту не создают: им она не нужна.

## Порядок реализации

Шаги не зависят от окна, пока не дошли до последнего; каждый коммитится отдельно, после каждого — документы фичи сверяются с кодом.

1. Реализация: обнаружение и разрешение цели — `bars-core::worktree` (записи `.git/worktrees`, состояния, владелец и корень вида), `Registry::resolve_cwd`, `Target.wt`, `worktree_not_found`, исключение папок worktree через `nested`, замена правила OQ-289/OQ-291, хук без регистрации, часть WORKTREES в `status`.
2. Реализация: хранилище и сверка дельты — формат файла и `wt_files`, `sync` (все документы и пути), копирование векторов владельца, состояния и первое построение лениво, очередь `(владелец, имя)`, часовая уборка и удаление при смене модели, нарезки и `docs_root`.
3. Реализация: поиск и чтение по виду — `IndexView` и смещение номеров, каталог области, исключённые пути, слияние пула, `f` по базе, пометка «строится», чтение, структура, `occurrences` и папка по диску W.
