## Что такое подпроект и чем он не является

Подпроект (Т-49) — не новая сущность хранения, а зарегистрированный проект с собственной `.bars/` и индексом (Т-5), у которого есть зарегистрированный проект-предок. Новое — три вещи: автоматический поиск таких проектов (раздел «Автопоиск»), составное имя `главный/путь` (раздел «Имена») и ленивый индекс (раздел «Ленивый индекс»). Исключение области подпроекта из индекса главного уже работает по [правилу вложенных проектов](projects.md), раздел «Вложенные проекты»; здесь оно не меняется, меняется только имя в строке агента.

Подпроект не входит в поиск по главному проекту (OQ-312): главный ищет только по себе, подпроект выбирается параметром `project`, модуль — параметром `in`.

## Модель реестра

Запись `[[project]]` в `~/.bars/projects.toml` ([есть] `ProjectEntry` в `crates/bars-worker/src/worker/registry.rs`: `path`, `name`, `registered_at`) получает два необязательных булевых поля [новое]:

| Поле | Значение | По умолчанию |
|---|---|---|
| `discovered` | запись создал автопоиск, человек проект не регистрировал | `false`, при `false` поле в файл не пишется |
| `lazy` | индекса ещё не требовали: проект зарегистрирован, но не проверяется и не индексируется | `false`, при `false` не пишется |

```toml
[[project]]
path = 'C:\repos\tmc-opovechenie\backend\api'
registered_at = "2026-11-12T10:00:00Z"
discovered = true
lazy = true
```

Инварианты:

- `lazy = true` только вместе с `discovered = true`. Любая запись, созданная человеком (окно, CLI, хук сессии), ленивой не бывает: её проверяют сразу, как сейчас.
- Старый файл без полей читается без миграции: все записи — «зарегистрированы человеком». Уже зарегистрированные вложенные проекты (`frontend/web-angular`, `overdrive-bots`) такими и остаются: они становятся подпроектами только по положению пути (следующий пункт), переиндексации и перерегистрации нет (Т-49).
- Старая сборка bars читает новый файл как обычный реестр: неизвестные поля она игнорирует (в `ProjectEntry` нет `deny_unknown_fields`).

### Что вычисляется, а не хранится

Предок, главный и составное имя не хранятся: они считаются по путям всех записей реестра, поэтому не расходятся с реальностью при переносе и переименовании.

| Понятие | Правило | Код |
|---|---|---|
| Предок (`parent`) | ближайшая зарегистрированная папка строго выше корня проекта; сравнение путей как в `path_key` (без учёта регистра на Windows) | `Registry::parent_of(path)` [новое] |
| Главный (`main`) | самый внешний зарегистрированный предок; у проекта без предка — он сам | `Registry::main_of(path)` [новое] |
| Составное имя (`qualified_name`) | у проекта с предком: `<отображаемое имя главного>/<путь от корня главного>`, разделитель `/`, без `.`/`..` | `Registry::qualified_name(path)` [новое] |
| Подпроект | проект, у которого есть предок | `parent_of(...).is_some()` |
| Самостоятельный | запись с `discovered = false` | поле записи |

Составное имя берёт отображаемое имя именно главного (самого внешнего), не ближайшего предка: `tmc-opovechenie/backend/api/vendor/x`, а не `api/vendor/x`. Путь в имени не меняется от переименования подпроекта; переименование главного меняет префикс всех составных имён под ним сразу.

### Своё имя и косая черта в именах

- Подпроект с `discovered = true` своего отображаемого имени не имеет: окно показывает папку (последний сегмент пути) и путь от родителя, агент выбирает его составным именем. «Переименовать…» для него не предлагается; `Registry::rename` возвращает новую ошибку `RegistryError::DiscoveredRename` с текстом «подпроект найден автоматически: его имя — путь от главного проекта; чтобы дать своё имя, зарегистрируйте его отдельным проектом», обработчик отдаёт её как `invalid_params` [новое].
- Самостоятельный подпроект (зарегистрирован человеком) переименовывается по прежним правилам ([есть] «Что хранит реестр проектов» в `projects.md`): своё имя работает в `project` отдельно от составного.
- Косая черта в имени проекта, заданном человеком, остаётся разрешённой: разбора имени по `/` нет, сравнение идёт целой строкой с заранее вычисленным набором имён (раздел «Имена»). Если такое имя совпало с чужим составным именем или с другим именем, это обычная неоднозначность.
- Правила допустимых символов имени (не пустое, без управляющих, обрезка по краям) не меняются.

## Имена и разрешение цели вызова

### Какие строки выбирают проект

Параметр `project` — [есть] в `docs/architecture/protocol.md`, «Разрешение цели вызова»; `Registry::resolve(selector)` [меняется] принимает такие строки:

| Строка | Кого выбирает | Условие |
|---|---|---|
| абсолютный путь | запись с этим корнем | всегда; путь точнее имени (как сейчас) |
| составное имя `главный/путь` | подпроект | у любого проекта с предком; сравнение целой строки, `\` в селекторе приравнивается к `/`, хвостовой `/` отбрасывается |
| отображаемое имя | проект без предка или самостоятельный подпроект | у найденного автоматически подпроекта своего имени-селектора нет, поэтому два `api` в разных главных не мешают друг другу |

Алгоритм: путь → иначе все записи, у которых селектор совпал с любым из своих имён; записи сводятся по пути; ноль — `project_not_found`, одна — она, больше одной — `ResolveError::Ambiguous` с путями (текст прежний: «имя `X` носят несколько проектов: укажите путь»). Модуль и подпапка в `project` не задаются: для них есть `in` (OQ-311), строка `главный/подпроект:модуль` не поддерживается.

`Registry::has_duplicate_name` [меняется] считает повторы только среди имён-селекторов (проекты без предка и самостоятельные подпроекты); окно и `projects` показывают такие проекты с путём, как сейчас.

### Исправление `project_arg` в MCP и CLI

Сейчас `project_arg` ([есть] `crates/bars-mcp/src/lib.rs:408` и `crates/bars-cli/src/lib.rs:350`) превращает любое значение с `/` или `\` в путь от `cwd`. Составное имя `tmc-opovechenie/backend/api` стало бы `<cwd>/tmc-opovechenie/backend/api`, и воркер его не нашёл бы. [меняется] новое правило: значение — путь (приводится к абсолютному от `cwd`), если оно начинается с `.`, абсолютное, или содержит разделитель и `cwd.join(значение)` — существующая папка; иначе строка уходит воркеру как есть и разбирается как имя. Старое поведение для настоящих относительных путей сохраняется; составное имя из `cwd`, где такой папки нет, больше не искажается. Обе копии функции меняются одним шагом реализации и покрываются одним набором тестов.

### Подпроект, которого реестр ещё не знает

Если селектор — абсолютный путь или `<имя главного>/<остаток>`, указывающий на папку строго внутри папки зарегистрированного проекта, и она проходит правило автопоиска (раздел «Автопоиск»), воркер регистрирует её сразу как найденную и ленивую и повторяет разбор [новое: `Worker::resolve` вызывает `subprojects::register_for_selector`]. Это одна проверка путей без обхода дерева: от ближайшего зарегистрированного предка вниз к папке идёт тот же шаг, что в обходе (скрытая папка, `node_modules`, `target`, ссылка, файл `.git` и репозиторий без `docs/` — граница), регистрируется самый внешний репозиторий на пути, затем проверка повторяется от него (до 16 вложенных). Агент, который назвал подпроект до первой проверки, не получает ошибку. Снятие регистрации и удаление проекта разбирают имя без такой регистрации (`Worker::resolve_known`): несуществующий подпроект ради снятия не регистрируется.

### Ошибки

| Случай | Код | Текст |
|---|---|---|
| имя не найдено, префикс совпал с главным проектом | `project_not_found` | «проект `X` не зарегистрирован; подпроекты `main`: a, b, c (до 10, остальные — bars_status(filter=\"main/\"))» |
| имя не найдено, папка `<корень главного>/<остаток>` есть, но правилу не отвечает | `project_not_found` | «папка есть, но это не подпроект: нужны свой каталог `.git` (не файл worktree) и `docs/` хотя бы с одним `.md`, папка вне корня документации `main`; зарегистрировать вручную — bars-cli register <путь>» |
| имя не найдено, префикса нет | `project_not_found` | прежний текст плюс «список — bars_status(all=true)»; для поиска по части имени — `bars_status(filter=\"...\")` |
| имя носят несколько проектов | `project_not_found`/`Ambiguous` как сейчас | прежний, с путями |
| подпроект ленивый, папка не на месте | `project_unavailable` | прежний |

Строка агенту об исключённых вложенных проектах ([есть] `bars_protocol::excluded_projects_line`, `crates/bars-protocol/src/search_scope.rs`) не меняется по форме: «исключены вложенные проекты: tmc-opovechenie/backend/api (ищите project=tmc-opovechenie/backend/api)». Меняется источник имени: `NestedProjectInfo.name` ([меняется] `Worker::nested_projects`, `worker/mod.rs`) становится составным именем, потому что каждый вложенный проект по определению подпроект. Правило «при одинаковых именах вместо имени путь» остаётся на случай, когда составное имя неоднозначно из-за имени, заданного человеком.

## Автопоиск подпроектов

### Правило

Папка `S` — найденный подпроект главного проекта `P` (любой зарегистрированный проект может быть `P`), если выполняются все условия (Т-49, OQ-309):

1. `S` строго внутри папки `P`, вне корня документации `P` (`P/docs_root`); при `docs_root = "."` вне корня документации нет ничего, поэтому у такого проекта автопоиск ничего не находит; папка, внутри которой лежит корень документации `P`, тоже не подпроект (области пересеклись бы);
2. в `S` есть каталог `.git`; файл `.git` (worktree и подмодуль) не в счёт;
3. в `S/docs/` есть хотя бы один `.md` (проверка [есть] `has_markdown`, `registry.rs`: имена файлов, содержимое не читается; папки с точкой в имени внутри `docs/` не считаются);
4. `S` не зарегистрирована.

Правило проверяет только `docs/`: корень документации найденного подпроекта — `docs` (`config.toml` не создаётся до первого обращения, умолчание настроек `DEFAULT_DOCS_ROOT = "docs"`, [есть] `bars-core/src/settings/mod.rs`). Если в `S/.bars/config.toml` уже лежит другой `docs_root`, он действует: воркер существующий `config.toml` не трогает (Т-5).

### Обход

Функция `subprojects::discover(parent, docs_root, registered) -> Discovery` [новое, `crates/bars-worker/src/worker/subprojects.rs`] работает без блокировок реестра и без чтения содержимого файлов, на blocking-потоке:

1. Начать с детей `P`. Папка корня документации `P` не посещается вообще.
2. Для каждой папки `D`: пропустить, если имя начинается с точки, равно `node_modules` или `target`, если `D` — символическая ссылка (`file_type().is_symlink()`; петли junction, которых это не поймало, ограничены глубиной и бюджетом) или если `D` — корень зарегистрированного проекта (его собственный проход обработает его вложенные).
3. Если `D/.git` — файл: worktree или подмодуль; папка пропускается целиком, внутрь обход не заходит. Так `backend/*-wt-quorum` и любые worktree не становятся подпроектами и не обходятся (Т-48 берёт их из `.git/worktrees` владельца, `worktrees.md`).
4. Если `D/.git` — каталог: это репозиторий. Он кандидат, когда `has_markdown(D, "docs")`; кандидат записывается в результат. Внутрь репозитория обход не заходит ни с `docs/`, ни без: найденный подпроект ищет свои вложенные сам, а репозиторий без `docs/` (`deploy`, `backend/liquibase`) считается границей, чтобы не обходить его дерево целиком.
5. Иначе (обычная папка) — рекурсия.

Границы стоимости (НТР-3, НФТ-7), все проверяются в коде и в тестах:

| Предел | Значение | Что при превышении |
|---|---|---|
| глубина от `P` | 6 уровней (дети `P` — первый); папки шестого уровня проверяются как кандидаты, но их содержимое не читается | обычная папка шестого уровня не обходится, обход считается неполным |
| прочитано записей каталогов (файлы и папки) за проход одного `P` | 50 000 | обход прекращается, `Discovery.truncated = true`, одна запись в журнал воркера на проект и состояние `discovery_truncated` в ответе `projects` (необязательное булево поле `ProjectInfo.discovery_truncated`, [новое]); найденное сохраняется |
| одновременные проходы | один на процесс (мьютекс), повторный запрос того же `P` сливается с ожидающим | остальные ждут, очередь индексации не используется |

Неполный обход ничего не удаляет: решение об уборке принимает проверка правила по каждой записи (раздел «Удаление»), а не отсутствие папки в результате обхода. Замер времени прохода по `C:\repos\tmc-opovechenie` фиксируется при реализации в handoff (НТР-3): ориентир — доли секунды, предел бюджета подбирается по замеру.

### Когда идёт поиск

| Событие | Что запускается |
|---|---|
| старт воркера | обход `P` для каждого зарегистрированного и доступного проекта, по очереди, после открытия канала и после запуска проверок файлов; канал не ждёт |
| раз в час | то же, перед `check_all` ([есть] `Inner::check_all`, `worker/mod.rs`): сначала поиск, затем проверка файлов; ленивые проекты в проверке пропускаются (раздел «Ленивый индекс») |
| первое окно на проекте | `Worker::observe_window` при первой аренде проекта окном ставит обход этого проекта; не чаще раза в пять минут на проект (аренда окна — 30 секунд, без предела обход шёл бы при каждом возврате в окно) |
| регистрация проекта и смена его `docs_root` | обход этого проекта (новый главный сразу получает свои подпроекты, смена корня меняет «вне корня документации») |
| снятие проекта, полное удаление | обход бывшего предка (раздел «Удаление») |
| начало сессии агента | не обход, а точечная проверка предков `cwd` (следующий пункт) |
| `project=` с неизвестным именем или путём | точечная проверка одной папки (раздел «Подпроект, которого реестр ещё не знает») |

Точечная проверка при начале сессии ([меняется] `Worker::session_start` и `session_info`): если `cwd` лежит внутри зарегистрированного `P` вне его корня документации, для каждой папки от `cwd` вверх до `P` проверяется правило подпроекта (две-три проверки существования). Нашлась — регистрируется найденной ленивой, и проектом сессии становится она. Для `session_info` (запрос при initialize, без моделей и индексации) регистрация делается, а первое обращение — нет: оно произойдёт первым вызовом инструмента. Так сессия в `backend/api` попадает в `backend/api`, а не в главный проект, не дожидаясь часа. Хук по-прежнему сам регистрирует новую папку вне реестра только по [правилам хука](projects.md), раздел «Корень проекта при регистрации»: сначала ближайший зарегистрированный предок, и точечная проверка стоит между ним и `cwd`.

### Регистрация найденного

`Registry::add_discovered(path)` [новое] добавляет запись с `discovered = true`, `lazy = true`, `registered_at = now`, записывает файл (как `add`). Воркер при этом не создаёт `.bars/` и ничего не пишет в чужой репозиторий; `prepare_project`, `BARS_INSTRUCTION.md` и `config.toml` появляются при первом обращении. В `Inner.projects` создаётся `Runtime` с состоянием `Lazy` (иначе `Worker::projects` покажет проект как `Unavailable`: он берёт состояние из `Runtime`). После пачки регистраций воркер один раз вызывает `refresh_nested` (публикация областей, [есть] `bars_core::indexing::nested::publish`) и публикует обновление `updates::STATUS` для предка, чтобы окно перечитало список.

Найденный подпроект лежит вне корня документации предка по правилу, поэтому его область у предка не исключается (`nested::areas_of` отбрасывает области вне корня документации) и главный индекс не меняется: ни заданий, ни пересчёта.

## Ленивый индекс

### Состояние `lazy`

`ProjectState` ([меняется] `crates/bars-protocol/src/methods.rs:563`) получает значение `Lazy` (`"lazy"` в JSON): проект зарегистрирован, индекс не строится и не проверяется, слежения нет. Тип окна `ProjectState` в `ui/src/lib/types.ts` и `stateDot` в `ui/src/lib/format.ts` [меняется]: точка «ждёт первого обращения» (полая серая, класс `idle`, не `off`: папка на месте). Компилятор укажет все `match` по `ProjectState` (рендер MCP `state_name` в `crates/bars-mcp/src/render.rs`, сводка для трея, окно); везде `Lazy` — не проблема и не ошибка.

Если у ленивого проекта уже есть `.bars/index.sqlite` (папка переехала вместе с индексом или проект когда-то регистрировали), `modules` в ответе берутся из него только для чтения (`Handler::modules` уже так работает), состояние остаётся `lazy`: первый вызов обычной проверкой догонит индекс, а проверка модели (Т-25) пройдёт как у любого проекта.

### Что считается первым обращением

Единая точка — `Inner::activate(path, priority)` ([есть] `worker/mod.rs`, вызывается из `register`, `observe_mcp`, `observe_window`, `check_all`) [меняется]: если запись ленивая и приоритет `Periodic` (старт и час), проект остаётся ленивым и `activate` возвращается; при любом другом приоритете запись переводится в `lazy = false` (файл реестра переписывается), вызывается `prepare_project(path, None)` (создаёт `.bars/config.toml` с `docs_root = docs`, если его нет), и дальше проект идёт обычным путём: слежение, проверка, индексация с нуля.

| Событие | Первое обращение? | Как доходит до `activate` |
|---|---|---|
| сессия агента с `cwd` в подпроекте | да | `session_start` → `observe_mcp` |
| вызов с `project=` подпроекта или `cwd` в нём (поиск, чтение, структура, `similar`, дубли, `reindex`, `bars_status(refresh=true)`, граф, аудиты с запуском) | да | `handle_observed` → `observe_mcp` |
| открытие подпроекта в окне | да | `select` → `project_observe` → `observe_window` |
| человек зарегистрировал подпроект отдельным проектом | да | `register` → `activate(Explicit)` |
| явная проверка или переиндексация (`bars-cli reindex`, меню окна, `reindex`) | да | `Worker::reindex_receipt` будит ленивый проект сам: CLI не проходит через `observe_mcp` |
| список проектов окна, `projects`, `bars_status` без refresh, аудиты и новые темы в режиме списка, `graph_status`, `session_info` | нет | пассивные вызовы |
| старт воркера, часовая проверка | нет | `activate(Periodic)` |
| раскрытие главного в окне, фильтры | нет | только чтение реестра |

Пассивные вызовы [новое] — набор видов вызова в `Handler::handle_observed` (`crates/bars-worker/src/handler/history.rs`): `Status`, `Projects`, `AuditList`, `NewTopicsList`, `GraphStatus`. Для них `observe_mcp` получает признак `passive`; у ленивого проекта пассивный вызов не продлевает аренду и не вызывает `activate`, у остальных проектов поведение прежнее. Для `bars_status` с явным ленивым проектом MCP не вызывает аудиты, новые темы и граф вовсе: часть PROJECT и часть INDEX с состоянием `lazy`, вместо остальных частей — одна строка «not indexed yet: any search, read or refresh=true in this project starts the first index».

Первый вызов поиска по только что активированному проекту идёт по существующему правилу «индекс строится»: ответ с пометкой `indexing`/`pending` и выдачей по тому, что уже в индексе (проект без индекса — пустая выдача с пометкой); нового режима ожидания нет.

### Что делает часовая проверка

Для ленивой записи `check_all` ничего не ставит: ни `scan`, ни слежение, ни задание очереди (НФТ-7: ПК не нагружается). Ленивый проект остаётся в списках, обход автопоиска в нём (поиск его собственных вложенных) продолжает работать.

### Уже зарегистрированные вложенные проекты

Запись с `discovered = false` (старые вложенные, регистрации человеком) ленивой не становится и не меняется: ни переиндексации, ни пересчёта, ни перезаписи `.bars/` (Т-49, критерий «web-angular и overdrive-bots не переиндексировались»). Они получают предка и составное имя вычислением. Автопоиск проходит мимо них (граница из шага 2 обхода).

## Удаление, самостоятельные подпроекты, перенос предка

### Найденный подпроект перестал подходить

На каждом проходе автопоиска (старт, час, открытие проекта) для каждой записи с `discovered = true` проверяется правило по самой записи, а не по результату обхода: предок `P` доступен (`P.is_dir()`), `S` внутри `P`, папка `S` есть, в ней каталог `.git`, в `S/docs/` есть `.md`, а `S` вне корня документации `P`. Не прошла — запись убирается тем же кодом, что `Worker::unregister`: остановка слежения, снятие с очереди, отмена scan, обновление областей. С диска не удаляется ничего: `.bars/`, документы и `BARS_INSTRUCTION.md` остаются (Т-5), в дереве предка вернувшиеся файлы подберёт обычная проверка, если они лежат в его корне документации (ТР-18). Если `P` недоступен (`unavailable`), записи под ним не проверяются и не убираются: отсутствие диска не доказывает, что подпроект исчез.

Следствие, о котором руководство предупреждает: сессия, переключившая репозиторий на ветку без `docs/`, уберёт подпроект из реестра на ближайшей проверке; следующая проверка на ветке с `docs/` вернёт его ленивым, а прежний индекс подхватит первое обращение.

### Сочетания

| Ситуация | Что происходит |
|---|---|
| найденный подпроект, затем человек регистрирует его (окно, CLI) | `register` для существующей записи с `discovered = true` ставит `discovered = false`, `lazy = false`, пишет реестр и вызывает `activate(Explicit)`; запись одна, индекс один; проект виден самостоятельным в списке и под главным (Т-49). `Registered.already` остаётся `true` |
| самостоятельный подпроект, человек его снимает («Убрать из bars», `bars-cli unregister`) | запись удаляется как сейчас; после снятия воркер сразу запускает обход бывшего предка, и если подпроект правилу отвечает, он возвращается как найденный ленивый; окно в диалоге снятия пишет об этом одной строкой |
| найденный подпроект, человек вызывает «Удалить проект» ([удаление](deletion.md)) | данные удаляются, запись убирается; следующий проход при необходимости вернёт его ленивым и пустым. «Убрать из bars» для найденного без самостоятельной регистрации в меню окна не показывается: оно ничего бы не изменило |
| самостоятельный подпроект перестал отвечать правилу (удалили `docs/`) | не убирается, правило пропавших проектов прежнее (`unavailable`, только если нет папки); запись самостоятельная, автопоиск её не трогает |
| найденный подпроект и самостоятельный вариант с тем же путём | записи две быть не может: путь однозначно определяет проект |
| предок снят с регистрации или удалён | после снятия записи предка воркер убирает все найденные записи без зарегистрированного предка (транзитивно по цепочке); самостоятельные подпроекты остаются обычными проектами без предка, их индексы не затронуты |
| предок перенесён (регистрация на новом месте, старая запись `unavailable`, [есть] «Перенесённый проект» в `projects.md`) | под старой записью найденные подпроекты остаются `unavailable` и не убираются (предок недоступен); когда человек убирает старую запись, они убираются как сироты; новый предок находит свои подпроекты ленивыми по новым путям, а переехавшие вместе с папкой `.bars/` подхватывает первое обращение |
| корень документации предка сменили на `.` | найденные подпроекты оказываются внутри корня документации и перестают отвечать правилу: убираются при ближайшей проверке, их документы возвращаются предку, если лежат в его корне; самостоятельные подпроекты остаются и исключаются обычным правилом вложенных |
| подпроект внутри подпроекта | работает транзитивно: обход подпроекта идёт от него самого, главный для имени — самый внешний |

`name` остаётся собственным отображаемым именем (окно и прежние клиенты); MCP и CLI в строке `name:` печатают `qualified_name`, если он есть. Поле `nested` (исключённые области) остаётся как есть.

`ProjectSnapshot` ([есть] `Worker::projects`) получает `parent`, `qualified_name`, `discovered`, `lazy`; состояние `Lazy` берётся из записи реестра, а не из `Runtime`, если проверок ещё не было.

### Метод `projects`

Параметры [меняется]: к необязательному `target` добавляется необязательный `filter: String`. Они взаимоисключающие: `target` вместе с `filter` — `invalid_params` («filter searches the whole registry; drop project»). `filter` после обрезки пробелов пустой считается отсутствующим. Без `target` и без `filter` — весь реестр, как сейчас. Фильтр применяет воркер, а не клиент, чтобы окно и агент читали одинаково. В ответе с `filter` поле `registry_total` — размер всего реестра (нужно пустому результату); без `filter` оно не пишется. Записи в ответе (с `filter` и без) идут так, что предок стоит раньше своих подпроектов, остальное — порядок реестра (`crates/bars-worker/src/handler/project_filter.rs`; здесь же будет подключено совпадение по worktree). Правило совпадения — одна функция `bars_protocol::project_matches_filter` (`crates/bars-protocol/src/project_filter.rs`), её таблица случаев — общая с `matchProject`.

Правило совпадения (Т-50): подстрока без учёта регистра (Unicode lowercase), по трём строкам записи — отображаемое имя, составное имя, абсолютный путь; в путях и в фильтре `\` приравнивается к `/`. Worktree совпадают по имени и пути worktree (контракт — `worktrees.md`).

## bars_status: фильтр проектов

### Параметр

[меняется] `bars_status(project?, all?, refresh?, filter?)` — четыре инструмента остаются (agent-layer-project). Английское описание параметра в схеме: «Case-insensitive substring of a project name, qualified name (main/path) or path. Searches the whole registry and returns only matching projects, subprojects and worktrees; cannot be combined with project.»

Описание инструмента ([есть] `crates/bars-mcp/src/tools/status.rs`) получает фразу: «filter=text lists only registry projects whose name or path contains the text (subprojects and worktrees included).»

### Взаимодействие параметров

| Сочетание | Результат |
|---|---|
| только `filter` | часть PROJECT — совпавшие записи реестра; части INDEX, AUDITS, NEW TOPICS, GRAPH не выводятся (как при `all`), вместо них строка «per-project parts need one project: repeat with project=<name from this list>»; VERSIONS выводится |
| `filter` и `all=true` | то же, что один `filter` (`all` избыточен, ошибки нет) |
| `filter` и `project` | `invalid_params`: «filter cannot be combined with project» |
| `filter` и `refresh=true` | `invalid_params`: refresh относится к одному проекту |
| пустой или пробельный `filter` | как без `filter` |
| `all=true` | весь реестр, как сейчас, теперь с подпроектами |

### Форма ответа

Блоки `=== PROJECT i of N ===` ([есть] `project_block`, `render.rs`) остаются; каждая запись реестра выводится один раз, предок раньше своих подпроектов. Для подпроекта добавляются строки:

```
=== PROJECT 3 of 9 ===
path: C:\repos\tmc-opovechenie\backend\api
name: tmc-opovechenie/backend/api
subproject_of: tmc-opovechenie
origin: discovered
docs_root: docs
state: lazy
modules: none (not indexed yet)
=== END PROJECT 3 ===
```

- `name:` — составное имя (то, что передаётся в `project`); для самостоятельного подпроекта добавляется `also_named: web-angular`, `origin: registered`. Строки `subproject_of:` и `origin:` печатаются у любой записи с предком; `also_named:` — только у не найденного автоматически (`discovered = false`); у ленивого проекта без индекса `modules: none (not indexed yet)`.
- `subproject_of:` — составное имя предка (у подпроекта первого уровня — имя главного). В выдаче с `filter` предок может отсутствовать среди совпавших: строка всё равно называет его, а сам он не выводится (ответ содержит только совпавшие).
- У главного проекта: `subprojects: tmc-opovechenie/backend/api (lazy), … (excluded from this index)` — прямые подпроекты, в скобках состояние и пометка об исключении области (`name (lazy, excluded from this index)`); строка об исключённых проектах `исключены вложенные проекты: …` остаётся и теперь печатает составные имена.
- Worktree проекта печатаются подстроками блока его владельца (формат — `worktrees.md`); при `filter` в блок входят только совпавшие worktree, а владелец, не совпавший сам, выводится с пометкой `matched_by: worktree`.
- Пустой результат: «no project matches `text`; the registry has N projects (bars_status(all=true) lists them)».

Размер ответа при `all=true` и `filter` ограничен существующим общим форматом MCP; сводки модулей ленивых проектов пустые, поэтому подпроекты почти ничего не добавляют.

CLI: `bars-cli projects [--filter <текст>]` [новое] печатает тот же `projects`; `--filter` несовместим с `--project`. JSON-вид — поля `ProjectInfo`.

- Поле — первый элемент меню, получает фокус при открытии; плейсхолдер «Фильтр проектов»; состояние — локальное `$state` в `Sidebar.svelte`, не `app.filter` (тот фильтрует документы дерева); сбрасывается при закрытии меню.

### Группировка подпроектов

- Данные: `app.projects` остаётся плоским списком с `parent`, `qualified_name`, `discovered`; дерево строится в `ui/src/lib/projects.ts` (`buildSwitcher(projects)`) [новое].
- Верхний уровень списка — проекты без `parent` и самостоятельные подпроекты (`discovered = false`); найденные подпроекты на верхнем уровне не показываются. Самостоятельный подпроект поэтому виден дважды: на верхнем уровне под своим именем и под главным; обе строки выбирают один и тот же путь, обе подсвечиваются как текущий.
- У проекта с подпроектами — кнопка раскрытия (шеврон) слева от точки состояния, `aria-expanded`; клик по шевронy раскрывает и сворачивает, не выбирая проект; клик по остальной строке выбирает проект. Подпроекты — под строкой, у второго и глубже уровня отступ на уровень. Подпись строки подпроекта — путь от его непосредственного родителя (`backend/api`, у вложенного глубже — `vendor/x`), всплывающая подсказка — составное имя; точка состояния — своя, у ленивого — `idle` с подписью «ждёт первого обращения».
- Состояние раскрытия — в памяти окна (по пути проекта), по умолчанию свёрнуто; автоматически раскрыты предки текущего проекта и все предки совпавших с фильтром.
- Сортировка подпроектов под одним предком — по пути, алфавитно; верхний уровень — в порядке реестра.
- Worktree отдельными строками переключателя не показываются (выбор шага 6.3.6, [worktrees](worktrees.md), раздел «Окно»): они лежат папкой «worktree» в дереве документов проекта-владельца, а выбор проекта в переключателе остаётся выбором владельца или подпроекта. Механизм шеврона и отступов переключателя нужен только подпроектам.
- Кнопка выбранного проекта (`.proj`) для подпроекта показывает составное имя в первой строке, путь — во второй.
- Автовыбор при пустом `current` (`loadProjects`) выбирает первый проект верхнего уровня, не найденный подпроект: открытие в окне — первое обращение, и неявно запускать индекс ленивого подпроекта нельзя.
- Контекстное меню строки подпроекта — прежнее ([меню проекта](../window/project-menu.md)); у найденного, не зарегистрированного человеком, пункты «Убрать из bars» и «Переименовать…» не показываются, «Проверить проект» и «Удалить проект…» остаются.
- При первом показе окна на проекте (`observe_window`) воркер ставит автопоиск этого проекта, а `app.loadProjects` подхватывает изменение по обычному обновлению состояния; отдельной кнопки «Найти подпроекты» нет.

### Клавиатура

Меню — `role="menu"`, строки — `menuitem` (уже). Добавляется (Т-45, в рамках экрана): стрелки вверх/вниз двигают фокус по видимым строкам и по «Добавить проект…»; Home/End — первая/последняя; стрелка вправо раскрывает проект с подпроектами, влево — сворачивает или переходит к родителю; Enter/пробел выбирают; из поля фильтра стрелка вниз переходит в список; Esc закрывает меню и возвращает фокус на `.proj`. Фокус всегда виден (`focus-visible`).

### Граничные случаи

- Реестр и имена: чтение старого `projects.toml` без новых полей; запись и повторное чтение `discovered`/`lazy`; `lazy` без `discovered` при загрузке нормализуется в `lazy = false` с записью в журнал воркера; предок любой глубины, главный — самый внешний; составное имя после переименования главного; `\` и хвостовой `/` в селекторе; своё имя самостоятельного подпроекта работает, у найденного — нет; два `api` в разных главных не мешают; `rename` найденного — ошибка; имя с `/`, совпавшее с чужим составным, — неоднозначность с путями.
- Обход: `docs_root = "."` — пусто; репозиторий внутри корня документации главного не находится; папка с точкой, `node_modules`, `target` пропущены; файл `.git` пропущен без захода внутрь; вложенный репозиторий внутри найденного не виден из главного, но найден из подпроекта; репозиторий без `docs/` не обходится; `docs/` только с `.md` в папке с точкой не считается; предел глубины и предел записей дают `truncated` без удаления существующих записей; символическая ссылка не обходится (на платформах, где её можно создать без прав); обход не читает содержимое файлов (проверка по счётчику открытых файлов обёртки над `fs`).
- Ленивый индекс: старт и часовая проверка не ставят заданий и не создают `.bars/` у ленивого; пассивные вызовы (`projects`, `status` без refresh, `graph_status`, `session_info`, фильтр) его не активируют; `status(refresh=true)`, `search`, `read`, `outline`, сессия, открытие в окне — активируют; повторное обращение не переписывает реестр; уже существующий `config.toml` с другим `docs_root` не перезаписывается; существующий `index.sqlite` читается для `modules`.
- Удаление и сочетания: регистрация человеком найденного — один экземпляр записи, `discovered = false`, `lazy = false`; снятие предка убирает найденных (транзитивно) и не трогает самостоятельных; предок `unavailable` не убирает найденных; снятие самостоятельного подпроекта, отвечающего правилу, возвращает его ленивым найденным; смена `docs_root` предка на `.`.
- Разрешение цели: неизвестное `main/x` — подсказка со списком подпроектов; папка есть, правилу не отвечает — второй текст; точечная регистрация по `main/path` и по абсолютному пути; `project_arg` в MCP и CLI: составное имя без папки в `cwd` не искажается, `./x`, абсолютный и существующий относительный пути — как раньше.
- `bars_status`: `filter` + `project`, `filter` + `refresh`, `filter` + `all`, пустой `filter`, пустой результат, подпроект при отсутствующем предке среди совпавших, ленивый проект без вызова аудитов, текст схемы и описание на английском.
- Окно: фильтр сбрасывается при закрытии; Enter, Esc, стрелки; автовыбор не выбирает найденный подпроект; точка `idle`; переключение при смене `projects` во время раскрытия.

## Шаги реализации

Предлагаемые шаги для плана (один шаг — один коммит, каждый самостоятельно собирается и не ломает остальное):

1. Реализация: меню проектов в окне — прокрутка в пределах окна, закреплённые фильтр и «Добавить проект…», клавиатура, макет `project-switcher.html` (Т-50, только UI).
2. Реализация: подпроекты в реестре и протоколе — поля `discovered`/`lazy`, `parent_of`/`qualified_name`, разрешение `главный/путь`, `ProjectState::Lazy`, новые поля `ProjectInfo`, правка `project_arg` в MCP и CLI, имя в строке исключённых.
3. Реализация: автопоиск подпроектов — обход, триггеры (старт, час, окно, сессия, селектор), ленивая регистрация и первое обращение, пассивные вызовы, уборка ушедших и сирот, замер обхода на `tmc-opovechenie`.
4. Реализация: фильтр проектов — `filter` в `projects`, `bars_status`, `bars-cli projects --filter`, вывод подпроектов под предками (Т-50, агент).
5. Реализация: переключатель окна с подпроектами — группировка, раскрытие, самостоятельный подпроект дважды, точка `idle`, фильтр по подпроектам, автовыбор верхнего уровня.

Шаг 1 не зависит от остальных. Шаги 2–5 идут по порядку: 3 и 4 опираются на 2; 5 — на 2 и 3 (для 4 нужен только 2).

## Ручная проверка

- 40 проектов в реестре (или фикстура окна): открыть меню в маленьком окне; прокрутка колесом и стрелками до последнего; «Добавить проект…» виден; фильтр `web` оставляет только совпавшие.
- `tmc-opovechenie`: после старта в списке под ним четыре подпроекта, `deploy` и `*-wt-quorum` нет; точки подпроектов серые «ждёт первого обращения»; нагрузка процессора не растёт; `.bars/` у `backend/api` не появилась.
- Открыть `backend/api` в окне или вызвать `project="tmc-opovechenie/backend/api"` — индекс строится; `bars_status(filter="api")` показывает подпроект с родителем.
- Удалить `docs/` в тестовом клоне подпроекта: через час или при открытии главного записи нет.
- Зарегистрировать `backend/api` отдельным проектом: виден в общем списке и под главным, индекс один.

## Решения реализации, не заданные автором

Выбраны исполнителем при проектировании 12-11-2026; автор их не решал, каждое меняется одной правкой этого документа:

1. Автопоиск при `docs_root = "."` у главного ничего не находит: любая папка внутри такого проекта лежит в его корне документации, а автоматическая регистрация перераспределила бы его индекс без участия человека. Такие подпроекты регистрирует человек.
2. Репозиторий без `docs/` — граница обхода, внутрь не заходим (дёшево, предсказуемо); вложенный репозиторий с `docs/` внутри репозитория без `docs/` регистрируется человеком.
3. Найденный подпроект не переименовывается (имя — путь), пункты «Убрать из bars» и «Переименовать…» у него скрыты; снятие самостоятельного, всё ещё подходящего под правило, подпроекта возвращает его как найденного ленивого.
4. Пассивные вызовы (`projects`, `status` без refresh, `graph_status`, списки аудитов и тем, `session_info`) не активируют ленивый проект; `bars_status(project=ленивый)` без `refresh` его не индексирует.
5. Подпись подпроекта глубже первого уровня в окне — путь от непосредственного родителя (составное имя — в подсказке), а не от главного.
6. Пределы обхода (глубина 6, 50 000 записей) — стартовые значения до замера на `tmc-opovechenie`.
7. Фильтр окна и агента совпадает по имени, составному имени и пути (Т-50, критерий приёмки), а не только по имени.
