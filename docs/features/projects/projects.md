# Реестр проектов bars

Какие папки bars считает проектами и что происходит с проектом на протяжении его жизни (Т-5, Т-6, Т-15). Решение агента, 14-10-2026.

## Что хранит реестр проектов

`~/.bars/projects.toml` — список проектов: абсолютный путь к корню проекта и время регистрации. Всё остальное о проекте лежит в его `.bars/` ([architecture/files.md](../../architecture/files.md)). Проект однозначно определяется путём к корню.

Имя проекта по умолчанию — имя папки корня. По запросу автора от 31-10-2026 пользователь может задать своё отображаемое имя через «Переименовать…» в меню проекта. Оно хранится в необязательном поле `name` записи реестра, используется в окне, MCP и CLI, включая выбор параметром `project`. Папка, путь, индекс и открытые документы сохраняются. Старое имя папки после переименования не служит псевдонимом; абсолютный путь продолжает работать. Имя обрезается по краям; пустое имя и управляющие символы запрещены. Ошибка записи оставляет прежнее имя и видна в диалоге. Отмена ничего не меняет.

Если у двух проектов одинаковые отображаемые имена, окно и `projects` показывают их с путём, а параметр `project` с таким именем требует путь ([protocol.md](../../architecture/protocol.md)).

Проверка переименования: задать русское имя с пробелами, проверить список проектов в окне и инструментах, перезапустить bars и найти проект по новому имени и прежнему абсолютному пути. Убедиться, что папка не переименована и поиск по индексу работает. Проверить отмену, пустое имя, совпадающие имена и ошибку сохранения. Статус 31-10-2026: реализовано; 12 целевых UI-тестов и проверка Svelte прошли. Полный гейт остановлен по указанию автора «Без тестов комит и пуш». Нативная проверка и установленная версия не проверены.

## Корень документации при добавлении папки

Проект — любая папка с Markdown: репозиторий кода, заметки, рабочие инструкции, руководства (Т-7, раунд 33, OQ-246). При добавлении папки выбирается корень документации — папка, от которой bars индексирует `**/*.md` и считает модули:

| Выбор | `docs_root` в `.bars/config.toml` | Когда подходит |
|---|---|---|
| «Папка `docs/`» | `docs` | репозиторий кода, где документация лежит в `docs/` |
| «Вся папка» | `.` | заметки, инструкции, руководства без отдельной `docs/` |

Умолчание: если в папке есть `docs/` — отмечена она, иначе вся папка. То же умолчание применяют места, где человек не выбирает: хук начала сессии и `bars-cli register` без параметра.

- **Окно.** После выбора папки диалог «Что считать документацией?» с двумя вариантами и подписью, что найдено в папке; отмечен предложенный. «Добавить» записывает выбор и регистрирует проект, «Отмена» ничего не делает. Тот же выбор — в «Добавить проект на новом месте…».
- **CLI.** `bars-cli register [путь] [--root docs|all]`: `docs` — корень `docs/`, `all` — вся папка. Без `--root` — умолчание. Параметр действует только на проект, у которого ещё нет `.bars/config.toml`.
- **Запись выбора.** Клиент (окно или CLI) создаёт `.bars/config.toml` с ключом `docs_root` до регистрации; воркер существующий `config.toml` не трогает (Т-5). Выбор потом меняется в настройках проекта («Выбрать другую папку документации…»).
- **Уже зарегистрированные и уже настроенные проекты не меняются:** их `docs_root` остаётся прежним, а умолчание «`docs/` или вся папка» применяется только к проекту без `config.toml`.
- **Вся папка и служебное.** При корне `.` папка `.bars/` и любые папки с точки в имени не обходятся и не показываются; `BARS_INSTRUCTION.md` в корне в индекс не попадает. Папки зависимостей и сборки (`node_modules`, `target`) обход не исключает: в проекте-репозитории выбирайте `docs/`.

## Создание проекта

Создание проекта (Т-35) — тот же выбор корня плюс создание файлов: папка проекта, корень документации только если выбрана `docs/`, `index.md` в корне документации (если файла с таким именем без учёта регистра ещё нет) и `.bars/config.toml` с выбранным `docs_root`; затем проект регистрируется как обычно. Если у папки уже есть `.bars/config.toml`, создание отказывает: это уже проект. `BARS_INSTRUCTION.md` появляется по Т-8 и в создании не участвует. Реализация: `bars_protocol::create_project`.

## Корень проекта при регистрации

Окно и `bars-cli register <путь>` регистрируют ровно ту папку, которую указал пользователь.

Хук начала сессии получает только `cwd` агента, а это может быть подпапка проекта или вообще не проект. Поэтому корень ищется по порядку:

1. ближайшая вверх от `cwd` папка, которая уже зарегистрирована или содержит `.bars/` проекта — тогда это она. `.bars/` проекта — та, где есть `config.toml` или `index.sqlite`; домашняя `.bars/` пользователя папку проектом не делает (решение агента, OQ-45). Незарегистрированная папка с `.bars/` проверяется и регистрируется так же, как найденная по шагам 2 и 3;
2. иначе — корень git-репозитория, в котором лежит `cwd`;
3. иначе — сама `cwd`.

Хук регистрирует найденную и ещё не зарегистрированную папку, только если в корне документации по умолчанию (`docs/`, если она есть, иначе вся папка, Т-7) есть хотя бы один `.md`. Иначе хук ничего не делает. Так сессия в домашней папке или в репозитории без документации не засоряет реестр. Для папки без `docs/` корень — вся папка, поэтому сессия агента в папке заметок с `.md` регистрирует её; сессия в папке без единого `.md` — нет.

Первый шаг решает и вопрос worktree: worktree в `.worktree/<имя>` или `.claude/worktrees/<имя>` лежит внутри зарегистрированного проекта, поэтому сессия в нём ищет по основному проекту (OQ-28).

## Вложенные проекты

Проект может лежать внутри другого. Для `cwd` действует ближайший зарегистрированный проект вверх по дереву (Т-15), индексы у проектов свои. Сейчас bars не исключает вложенный проект из внешнего: если его `.md` лежат в корне документации внешнего, они попадают в оба индекса. Ниже — проект решения шага 3.1.5, вариант (а) принят автором 03-11-2026 (OQ-255: «Да, вариант (а)»); пометка в дереве и строка агенту (OQ-256) и хранилища без проекта (OQ-257) ждут решения, правки требований в MAIN_IDEA не внесены, реализации нет.

### Что считается вложенным проектом

Проект B вложен в A, если корень B — зарегистрированная папка строго внутри папки A. Пересечение индексов возникает только там, где корень документации A охватывает папку B. bars видит это по реестру: при обходе A, слежении, построении дерева, ссылок и графа достаточно сравнить пути корней из `projects.toml` и `docs_root` каждого проекта.

Данные реестра на 03-11-2026 (`projects.toml` и `.bars/config.toml` проектов, только чтение):

| Внешний проект | Вложенные | Корень внешнего сейчас | Что даст «вся папка» у внешнего |
|---|---|---|---|
| `tmc-opovechenie` | `frontend/web-angular`, `frontend/web-design`, `backend/worker` | `docs` (13 `.md`); три вложенных лежат вне `docs/`, пересечения нет | 2115 `.md` вместо 13: 1346 из них в `gramax/` (хранилище без проекта) и все `.md` трёх вложенных (в их `docs/` — 50, 2 и 6 файлов) |
| `overdrive` | `overdrive-bots` | `docs` (33 `.md`), пересечения нет | 1129 `.md` `overdrive-bots` попали бы во второй индекс |

То есть ошибка не в текущих данных: выбор корня «вся папка» (Т-7, раунд 33) превращает любую вложенность в двойную индексацию. Порядок регистрации не защищает: хук, найдя репозиторий R вокруг уже зарегистрированной папки A, регистрирует R внешним проектом с теми же последствиями.

### Рекомендация: вариант (а), область вложенного проекта

Принято автором 03-11-2026 (OQ-255); подробности пунктов «Агент», «Окно» и «Хранилища» — предложения до ответов на OQ-256 и OQ-257.

- **Правило.** Файл не входит в индекс проекта A, если он лежит в корне документации любого другого зарегистрированного проекта, чья папка находится внутри A; учитываются все потомки по реестру, любой глубины. Исключается только индексируемая область вложенного (его `docs_root`): `README.md` и `REQUIREMENTS.md` в `backend/worker` вне его `docs/` остаются в индексе внешнего «всей папки» и не пропадают из поиска совсем. Проще, но с потерей — исключать вложенную папку целиком (вариант B в OQ-255).
- **Где действует.** Обход и индексация, слежение (событие внутри исключённой области не ставит задание внешнему), дерево, индекс ссылок и граф внешнего. Чтение и `bars_text_search` работают по диску и этим правилом не ограничены.
- **Когда пересчитывается.** Регистрация, снятие, полное удаление, перенос и смена `docs_root` вложенного проекта ставят внешнему проверку. Ушедшие в исключение файлы убираются из индекса внешнего по путям, вернувшиеся добавляются: это работа над затронутыми путями, а не пересборка графа (НФТ-7). С диска файл не удаляется, поэтому Т-22 получает второе основание: «ушёл в область другого проекта».
- **Пропавший вложенный проект** (`unavailable`) остаётся исключённым, пока запись в реестре есть: внешний не должен то дублировать документы, то терять их из-за отключённого диска. Запись убирает человек.
- **Агент.** Т-15 не меняется: из подпапки — ближайший проект вверх, из внешнего вне подпапки — внешний. Чтобы исключённое не пропадало молча, предлагается строка в ответе `projects` и в `scope` поиска: «исключены вложенные проекты: B (ищите project=B)» (OQ-256).
- **Окно.** Папка вложенного проекта в дереве внешнего показана серой с пометкой и действием «Открыть проект», без галочек. В диалоге добавления папки внутри зарегистрированного проекта — строка «Эта папка внутри проекта A: её документы (N файлов) уйдут из индекса A»; в диалоге внешнего — «найдены вложенные проекты, они исключены» (OQ-256).
- **Ссылки.** Ссылка из внешнего во вложенный `.md` ведёт за пределы индекса внешнего и не считается битой, пока файл есть на диске; как ссылки на файлы вне корня документации.
- **Хук и OQ-253.** Репозиторий R вокруг зарегистрированной A хук регистрирует по обычному умолчанию, A исключается автоматически. Рекомендация OQ-253 (хук регистрирует только при `docs/` или `.bars/`) вложенность не затрагивает.
- **Хранилища вроде `gramax/`.** Каталог без проекта внутри репозитория при корне «вся папка» целиком входит во внешний (1346 из 2115 файлов `tmc-opovechenie`). Отдельного списка исключений не вводим: человек регистрирует такую папку проектом, и правило (а) исключает её из внешнего. Предупреждение: регистрация создаёт `.bars/` внутри хранилища; уходит ли она в git, решает владелец (Т-5). Альтернатива — список `exclude` в `.bars/config.toml` внешнего проекта (OQ-257).

### Правки требований (предложение, MAIN_IDEA не правится)

- **Т-6.** Добавить: «Проект внутри другого проекта регистрируется как обычно».
- **Т-7.** Добавить: «Из индекса и дерева проекта исключается индексируемая область каждого зарегистрированного проекта, лежащего в его папке; исключение пересчитывается при регистрации, снятии, удалении, переносе и смене корня вложенного проекта».
- **Т-15.** Добавить: «Если у проекта исключены вложенные проекты, ответ называет их, чтобы агент мог выбрать нужный параметром `project`».
- **Т-22.** Добавить второе основание удаления из индекса: файл ушёл в область другого проекта.
- **Приёмка Т-7.** Проект A («вся папка») с вложенным B (`docs/x.md`, `README.md`): в индексе A нет `docs/x.md` и есть `README.md`; после снятия B с регистрации `docs/x.md` появляется в A при ближайшей проверке без пересборки графа; правка `x.md` не ставит задание A.
- **Приёмка Т-15.** Вызов без проекта из `B/docs` ищет только в B; вызов из A вне B — только в A и называет исключённый B.

## Пропавший проект

Если отсутствие папки обнаружено при старте, часовой проверке, начале активности MCP или событии слежения активного проекта, проект получает состояние `unavailable` ([worker.md](../../architecture/worker.md)):

- из реестра он не удаляется: папка может быть на отключённом диске или в выгруженной папке OneDrive;
- индексация и слежение для него останавливаются;
- поиск и другие методы по нему возвращают `project_unavailable`;
- окно показывает его с пометкой и кнопкой «Убрать из bars».

Папка снова появилась — проект возвращается в работу при ближайшей проверке. Только найденные расхождения создают задание обновления; слежение поднимается при наличии открытого окна или действующего часа MCP-активности. Регистрация сама по себе постоянное слежение не включает; правила активности — [обновление индекса](../indexing/updates.md).

## Перенесённый проект

Индекс хранит пути документов относительно корня проекта, а `.bars/` переезжает вместе с папкой. Поэтому перенос — это регистрация на новом месте: bars подхватывает существующую `.bars/` без переэмбеддинга (Т-6), если модель индекса совпадает с настройками (иначе Т-25). Старая запись в реестре становится `unavailable`, и пользователь убирает её.

## Снятие проекта с регистрации

Команда `bars-cli unregister [--project <путь>]` и кнопка «Убрать из bars» в окне:

- удаляют проект из `projects.toml`;
- останавливают слежение и снимают проект с очереди.

Папку `.bars/` и `BARS_INSTRUCTION.md` в проекте bars не удаляет: это файлы пользователя (Т-5). Если `.bars/` осталась, следующая регистрация подхватит её как есть.

Агенту снятие с регистрации через MCP недоступно: в списке инструментов агента его нет (Т-19).

## Полное удаление данных проекта

Пункт «Удалить проект» в контекстном меню окна — отдельная операция с подтверждением. Очищает регистрацию, индекс, локальные настройки и задания, сохраняя документацию по OQ-83. Состав файлов, ожидание индексации и ошибки — [deletion.md](deletion.md). Семантика CLI `unregister` не меняется.
