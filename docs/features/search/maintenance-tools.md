# Похожие чанки и дубликаты для поддержки документации

Статус: назначение и входные параметры согласованы автором 18-10-2026. `get_similar` реализован 19-10-2026 (ядро, воркер, MCP, CLI) и проверен тестами на временных индексах с подделкой embed-модели; на настоящей модели и живом приложении не проверялся. `get_duplicates` реализован 19-10-2026 (ядро, воркер, MCP, CLI) и проверен тестами на временных индексах с подделкой embed-модели и замером на индексе bars; на настоящей модели в живом приложении и на отдельном приёмочном наборе не проверялся. Пожелания — IDEA-12 и IDEA-13 в [реестре](../../backlog/ideas.md).

## Общая область поиска

Оба инструмента работают внутри одного проекта и принимают необязательный список `modules` с той же семантикой, что [область rag_search](hybrid-search.md#область-поиска): перечисленные модули объединяются, `.` обозначает корневой модуль; отсутствие или пустой список означает весь проект, неизвестный модуль — `invalid_params`. Фильтр применяется до отбора результатов; пары дублей целиком принадлежат выбранной области.

## get_similar: похожие чанки по ID

Назначение: перед правкой найти похожие описания и разделы для проверки; перед добавлением текста — найти уже существующее описание.

Вход: ID индексированного чанка, проект и необязательный список `modules`. Проект можно определить из сессии, как у `rag_search`. Фильтр модулей ограничивает область кандидатов, исходный чанк может находиться в другом модуле того же проекта.

Результат: несколько наиболее похожих чанков из выбранной области, исключая исходный. Каждый результат содержит ID, путь, модуль, заголовки, строки, текст и оценку близости. Готовый вектор исходного чанка позволяет обойтись без нового embed. Смысловая близость сама по себе не доказывает дублирование, согласие или зависимость документов.

Имена: метод протокола `similar`, инструмент MCP `bars_get_similar`, команда `bars-cli similar <ID>` ([MCP](../agent-tools/mcp-tools.md#bars_get_similar--похожие-чанки), [CLI](../agent-tools/cli.md)). Формат, срок действия и ошибки ID — в разделе «Идентификатор чанка для get_similar» ниже.

Лимит: по умолчанию `search.results` (5), максимум `search.max_results` (20); значение выше максимума прижимается, ответ несёт применённый `limit` и `clamped`. Оценка — косинус к исходному чанку (точный перебор готовых векторов области, модель не загружается). Порога нет: выдаются ближайшие чанки, даже слабо похожие. Порог на реальных разделах не подобран (порог поиска «вопрос → документ» не заимствуется); подбор — в исследовании дублей, [duplicates.md](../../knowledge/duplicates.md).

## Идентификатор чанка для get_similar

Статус: реализовано 19-10-2026; детали ID автор оставил реализации (handoff (`chats/2026-10-18-similar-duplicates`)), формат принят автором 19-10-2026.

**Почему не голый номер.** Чанк в индексе — строка `chunks` с `id INTEGER PRIMARY KEY` без `AUTOINCREMENT` ([схема](../../architecture/schema.md)). Любое изменение документа удаляет его чанки и вставляет заново ([обновления](../indexing/updates.md)), поэтому голый номер строки ненадёжен: после правки хвоста таблицы SQLite выдаёт освободившийся номер новому чанку, и старый ID молча указал бы на чужой текст.

**Формат.** Непрозрачная строка `<номер>-<контроль>`, например `1842-9f3a1c07`: номер строки `chunks.id` и восемь шестнадцатеричных знаков BLAKE3 от `documents.hash`, пути документа, `ordinal` и `embed_hash` чанка. Новая таблица и смена схемы не нужны. Агент не разбирает ID и не строит его сам.

**Срок действия.** ID верен, пока не изменился документ чанка:

| Событие | ID |
|---|---|
| Правка документа в любом месте (смена `hash`) | все чанки документа устаревают, даже неизменённые по тексту: нарезка пересчитана, соответствие чанков не отслеживается |
| Только время файла (`touch_document`) | действует |
| Удаление или переименование документа | устаревает |
| Полная переиндексация, смена модели | устаревают все |
| Закрытие и открытие окна, перезапуск воркера | действует |

ID не переживает обновления индекса и не предназначен для хранения: агент берёт его из свежей выдачи и использует сразу.

**Ошибки.** Строка не формата `<номер>-<контроль>` — `invalid_params`. Строки с таким номером нет или контроль не совпал — одна ошибка `chunk_not_found` с текстом «ID неизвестен или устарел после обновления индекса; найди чанк поиском заново». Неизвестный и устаревший ID не различаются: для этого пришлось бы хранить историю ID. Случайное совпадение контроля на чужом тексте — порядка 2⁻³² на обращение; принимается. Состояния проекта (`indexing`, `reindex_required`, недоступен) обрабатываются так же, как у `rag_search`.

**Видимость в выдаче.** `id` выдаётся у каждого фрагмента основной выдачи `rag_search`: строка `id:` после `path:` в тексте MCP и под строкой пути в CLI, поле `chunk_id` в JSON и в `SearchHit` протокола; окно ID не показывает. Это расширение публичного формата: прежние поля и порядок сохранены, поле добавлено (у клиента со старым воркером оно пустое). ID не выдаётся в `related` и `graph_results` GraphRAG (там свои `ObjectRef` из [графа](../../architecture/graph.md#идентичность-диапазоны-и-снимок)) и не принимается от них; статистика MCP хранит вызов `bars_get_similar` (запрошенный `chunk_id`, применённый `limit`, количество, ошибку `chunk_not_found`), но не тексты найденных чанков ([статистика](../window/mcp-statistics.md#контракт-этапа-26-матрица-основных-mcp-инструментов)). У `bars_read` и `bars_outline` чанков нет — ID там не появляется.

**Вектор.** Готовый вектор берётся из `vectors` по `embed_hash` чанка; если его нет, это ошибка целостности индекса, а не пустой результат. Новый embed не выполняется.

**Отвергнутые варианты.**
- Голый `chunks.id` — молча указывает на чужой чанк после правки.
- `embed_hash` как ID — одинаковый текст в разных местах (шаблоны) даёт один ID, документ и строки не определены.
- `ObjectRef` чанка из графа — зависит от построенного актуального слоя графа, а `get_similar` должен работать и без него; оставлен для связей GraphRAG.
- Хранение истории ID ради различения «неизвестен» и «устарел» — лишняя таблица без пользы для агента.

## get_duplicates: аудит дублей проекта

Назначение: ревизия повторяющихся описаний и разошедшихся копий для выбора основного источника и замены повторов ссылками. Автоматическое удаление или объединение документов не входит в инструмент.

Имена: метод протокола `duplicates`, инструмент MCP `bars_get_duplicates`, команда `bars-cli duplicates` ([MCP](../agent-tools/mcp-tools.md#bars_get_duplicates--аудит-дублей-проекта), [CLI](../agent-tools/cli.md)). Способ и пороги — [исследование](../../knowledge/duplicates.md) (предложение агента, не решение автора).

Вход: у MCP обязательный явный `project`; у CLI проект определяется, как у остальных команд. Необязательные `modules` (область, см. выше) и `limit`: по умолчанию 20 записей, максимум `search.max_results`; значение выше максимума прижимается, ответ несёт применённый `limit` и `clamped`. Исходный чанк не нужен. Модель не загружается: используются готовые тексты и векторы индекса.

Что сравнивается: собственный текст чанка без заголовков и служебного списка подзаголовков; слова в нижнем регистре, `ё` как `е`, знаки и разметка не учитываются. Чанки короче 15 слов не сравниваются, их число — `chunks_skipped_short`. Чанки сравниваются между собой по всей области, в том числе чанки одного документа.

| Вид (`kind`) | Условие | Мера `score` |
|---|---|---|
| `exact` | совпадает весь нормализованный текст | 1 |
| `near` | Жаккар общих окон из пяти слов не ниже 0,6 | Жаккар |
| `contained` | доля общих окон меньшего чанка не ниже 0,9, Жаккар ниже 0,6 | доля |
| `partial` | доля общих окон меньшего чанка не ниже 0,25 | доля |
| `semantic` | косинус не ниже 0,8, есть общие трёхсловные окна (не меньше 5 % у меньшего чанка), копией пара не признана | косинус |

Для `near`, `contained` и `partial` нужно не меньше десяти общих окон. Точные повторы выдаются группой из двух и больше чанков; остальные виды — парами. Одна высокая векторная близость без общих слов дублем не считается: `semantic` — только повод прочитать оба раздела.

Порядок выдачи: точные группы (большие первыми), затем близкие, содержащиеся, частичные по убыванию меры и смысловые по убыванию косинуса. До ограничения числа записей ответ сообщает `total` и `counts` по видам.

Запись содержит ID, путь, модуль, заголовки и строки каждого чанка; `score`; `shared` — до трёх самых длинных совпавших отрывков (не больше 300 знаков, у лексических видов); `differences` — у пар: пословные замены `changes` (только у `near`, до 12; признак `changes_truncated`), числа и идентификаторы с цифрами, которых нет в другом чанке, и число слов отрицания («не», «нет», «без» и подобных) в каждом. Изменённые число и отрицание видны в сравнении, но не объявляются противоречием.

Шаблоны: окно из пяти слов, которое есть в четырёх и больше чанках области, не участвует в парах (то же для трёхсловных окон смыслового условия). Одинаковый текст в четырёх и больше чанках выдаётся одной группой с признаком `repeated_block` — скорее шаблон, чем случайная копия. Абзац, скопированный в четыре и больше разных чанков, не совпадающих целиком, пары не даёт.

Область и состояния проекта обрабатываются как у `similar`: неизвестный модуль — `invalid_params`, `reindex_required` и недоступный проект — те же ошибки; во время индексации ответ помечен `indexing` и может быть неполным.

Не проверено и не подобрано: пороги получены на 94 автоматически построенных разделах и 569 чанках bars, число слов 15 и порог десяти общих окон — отдельным опытом не подбирались; смысловой вид на настоящем корпусе даёт много кандидатов (на индексе bars из 1 066 чанков — 94 пары), настоящих повторов среди них доли; блок, скопированный в четыре и больше разных чанков, не виден; качество на независимой разметке не измерялось.

## Реализация и приёмка

Два отдельных результата: `get_similar` и `get_duplicates`. Для каждого — ядро, вызов через воркер/MCP/CLI, описание инструмента и проверки на временных проектах: фильтры модулей, отсутствие результатов, ошибки параметров, ограничение числа записей. Для `get_similar` дополнительно проверены смена индекса (`chunk_not_found` после правки документа с повторным использованием номера строки) и запись вызова в статистику MCP через настоящий канал (единица `fragments`, ошибка `chunk_not_found`). Для `get_duplicates` проверены точные группы с разным регистром и разметкой, шаблонный блок в четырёх чанках, изменённое число и убранное «не», частичная копия, раздел внутри большего, шаблон без повтора, смысловая пара, короткие чанки и порядок выдачи.

Замер задержки `get_duplicates`: индекс bars из 1 066 чанков, `cargo run --release -p bars-core --example bench_duplicates`, 7 прогонов на одной машине — минимум 282 мс, медиана 362 мс, максимум 818 мс (чтение текстов и векторов из SQLite входит). На корпусе в тысячи чанков и на зафиксированном корпусе замер не выполнялся. Не сделано: приёмка на настоящей модели и в живом приложении, замер задержки и подбор порога `get_similar`, независимая разметка и подбор порогов `get_duplicates`.

Основание для выбора алгоритмов — [исследование локальных инструментов](../../knowledge/local-documentation-tools.md) (включает перепроверку источников); конкретные алгоритмы и зависимости этим решением не утверждены. Различение точных, близких, частичных, смысловых и шаблонных повторов, пороги и задержка проверены на размеченном наборе и корпусе bars: [duplicates.md](../../knowledge/duplicates.md) (предложение агента, не решение автора).
