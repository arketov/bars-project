# Полнотекстовые сигналы поиска

Статус 05-11-2026: **написано и покрыто тестами по критериям приёмки, но не собрано и не запущено** (сессии шага 2.3.3 сборки запрещены; сборку и `check.ps1` запускает автор). Бенч на настоящих запросах и подбор весов — шаг 2.3.7. Обоснование выбора — [исследование токенизации](../../knowledge/tokenization.md); место сигнала в сумме баллов — [схема баллов](hybrid-search.md) (раздел «Проект схемы баллов»); решение — [ADR-0007](../../adr/0007-one-search-scores.md).

Полнотекстовая часть поиска остаётся на FTS5 в том же файле индекса: токены готовятся в Rust до записи и перед запросом одним и тем же кодом, второго хранилища и своего токенизатора внутри SQLite нет.

## Колонки `chunks_fts`

Таблица `chunks_fts` ([схема индекса](../../architecture/schema.md)) имеет четыре колонки; `rowid` равен `chunks.id`:

| Колонка | Что в ней | Вес `bm25` |
|---|---|---|
| `name` | основы слов названия документа и имени файла без расширения (`hybrid-search`) | 5 |
| `heading_chain` | основы слов цепочки заголовков | 3 |
| `body` | основы слов текста чанка | 1 |
| `exact` | точная форма названия, имени файла, заголовков и текста: слова без стемминга и целые формы идентификаторов | 0,3 |

Составной балл — `bm25(chunks_fts, 5, 3, 1, 0.3)` (константа `BM25` в `search/fulltext.rs`). Веса стартовые: подбирает их шаг 2.3.4 по нечётным запросам бенча и проверяет по чётным. Токенайзер таблицы — `unicode61 remove_diacritics 2 tokenchars '_'`: колонки уже разобраны, токенайзер только режет по пробелам, а `_` оставляет внутри токена, чтобы целая форма идентификатора (`rag_query`) была одним словом. Рядом лежит таблица `chunks_fts_vocab` (`fts5vocab`, тип `row`) — словарь индекса для исправления опечаток; своего хранилища он не занимает.

## Разбор слов

Один код (`storage/stem.rs`, `TextStemmer`) разбирает и текст при индексации, и слова запроса. Язык — свойство слова, а не документа:

- **Основа (`stem_text`).** Слово из кириллицы без `і ї є ґ` идёт в русский Snowball, слово из латиницы — в английский. `ё` приводится к `е`, регистр не важен.
- **Не стеммятся:** слова ПРОПИСНЫМИ из двух и больше букв (`ОПИ`, `КИИ`), слова короче четырёх знаков, слова с цифрой, слова с буквами `іїєґ` (украинского стеммера нет), слова другого письма и смесь письменностей — они остаются в нижнем регистре как есть.
- **Точная форма (`exact_text`).** Те же слова без стемминга и целые формы идентификаторов. Слово с `_`, `.`, `/` или `-` внутри даёт токен из частей, склеенных `_`: `settings.toml` → `settings_toml`, `Т-12` → `т_12`, `274-ФЗ` → `274_фз`. Слово без разделителя и знаки по краям идентификатором не считаются; идентификатор длиннее восьми частей не записывается.
- **Китайский и японский.** Сплошной отрезок китайских знаков и японской кана режется на пары соседних знаков (`向量检索` → `向量 量检 检索`) и в основе, и в точной форме; знак, стоящий отдельно, остаётся одним токеном. Одиночный знак в запросе находит только документы, где этот знак стоит отдельно: пара знаков — минимальный запрос. Корейский и другие письменности без пробелов не покрыты.
- **Не используются:** лемма (нет выигрыша, словарь 11 МБ), префиксные основы, стоп-слова, разрезание camelCase, триграммная таблица, множитель покрытия слов запроса.

Версия разбора — `STEM_VERSION` (сейчас 2), её значение лежит в `meta` как `stem_version`. При несовпадении первое открытие индекса на запись пересоздаёт `chunks_fts` и `chunks_fts_vocab` из `chunks` и `documents` (секунды на тысячи чанков), эмбеддинги и согласие по Т-25 не нужны. Пока таблицу не пересоздали, поиск отвечает ошибкой «полнотекстовый индекс перестраивается… повторите запрос позже», а не читает старую таблицу: читатель индекс не чинит ([воркер](../../architecture/worker.md)). Размер полнотекстовой части вырастет примерно вдвое (принято автором, OQ-263).

## Запрос к FTS5

Из запроса пользователя собирается выражение (`FtsQuery`, `search/fulltext.rs`):

- `all` — все слова через `OR`: основы по колонкам `name heading_chain body` и слова без стемминга с формами идентификаторов по колонке `exact`. Слово, которое разбор разрезал на несколько токенов (`agent_min_score`, `по-русски`, китайская строка), идёт ещё и фразой из основ. `bm25` сам поднимает чанки, где совпало больше слов; множителя покрытия нет.
- `identifiers` — только слова запроса с `_`, `.` или `/` внутри: фраза из их основ и целая форма в колонке `exact`. Это отдельный список кандидатов пула; правило «чанки с идентификатором идут впереди» (OQ-31) заменил сигнал `p`.

Слов нет — `invalid_params` «в запросе нет ни одного слова». Операторы запроса (`"фраза"`, `-слово`, `path:`) здесь не разбираются: их снимает `search/operators.rs` до этого модуля, сюда приходят слова без операторов, а условия фраз и исключений оборачивают выражения `all` и `identifiers` ([операторы](hybrid-search.md#схема-баллов-операторы-запроса)).

## Опечатки

Второй проход по словарю индекса — до сборки выражения (`fts_query_for`):

1. Берётся основа слова запроса от четырёх знаков, целиком из букв, которой нет в `chunks_fts_vocab`.
2. Из словаря читаются слова с той же первой буквой; расстояние Дамерау—Левенштейна (перестановка соседних знаков — одна правка) не больше 1 для основ до 7 знаков и не больше 2 для 8 и длиннее.
3. К основе добавляются три лучших слова: сначала ближайшие, затем встречающиеся в большем числе чанков. Исходное слово остаётся в выражении.

Опечатка в первой букве слова так не исправляется. Короткие слова, слова с цифрами и слова, которые в индексе есть, не трогаются. Индекс без таблицы словаря (записан читателем до пересборки) ищет без исправлений. Замер на бенче: по настоящим опечаткам Hit@3 с 60 % до 80 %, по синтетическим — с 65 % до 76 % ([токенизация](../../knowledge/tokenization.md), раздел «Опечатки»); время обхода словаря в сотни тысяч слов не измерено.

## Балл `f` для схемы баллов

Сложение баллов в `search/hybrid.rs` берёт сигнал `f` отсюда; слияния RRF больше нет ([гибридный поиск](hybrid-search.md)).

- `p_signal(conn, пробы, чанки)` считает точное совпадение по колонке `exact`: 1, если в чанке есть все идентификаторы запроса целиком или все слова запроса подряд, иначе доля пар соседних слов запроса, найденных подряд (не больше 12 пар, по одному запросу к FTS5 на пару); выражения собирает `QueryTerms::exact_probe`.
- `Scope::text_scored` отдаёт первые N чанков области с сырым баллом `-bm25` (больше — лучше), по убыванию.
- `f_signal(conn, выражение, список, чанки)` делит сырой балл на лучший балл списка FTS этого запроса и даёт число от 0 до 1. Чанку вне списка `bm25` считается одним запросом по `rowid`; чанку, в котором не совпало ни одно слово, достаётся 0.

## Что не проверено

- Тесты (`search/fulltext/tests.rs`, `search/operators/tests.rs`, `storage/stem.rs`, `storage/index.rs`, `search/hybrid/tests.rs`) написаны, не запускались: сборка запрещена.
- Метрики шага («первым» 60 % / Hit@3 77 % на 168 запросах, вариант «поля, точная 0,3») получены на node по копиям индексов, а не на этом коде. Бенч `bench_quality` на продукте и разбор 16 ухудшившихся запросов — шаг 2.3.7.
- Размер индекса, скорость записи и скорость запроса с `fts5vocab` на реальных проектах — не измерены.
- Языки кроме русского, английского и китайского с японским — только точная форма (OQ-261).
- Запрос из одного китайского знака находит только знак, стоящий отдельно, а заголовок ПРОПИСНЫМИ не стеммится: так решено до реального CJK-корпуса (OQ-277, 05-11-2026); прописные заголовки проверяются на бенче.
