# Гибридный поиск bars — от запроса до выдачи

Статус 03-11-2026: описано текущее поведение. Автор решил заменить слияние RRF одним поиском на сумме баллов сигналов с весами по бенчу, операторами запроса и свёрткой кусков раздела ([ADR-0007](../../adr/0007-one-search-scores.md), раунд 33 Т-12); проект схемы — раздел «Проект схемы баллов» ниже (принят автором 03-11-2026), реализации ещё нет. Загрузку моделей поиск ждёт до предела и не отвечает ошибкой (ISS-105, раздел «Ожидание моделей»).

Как воркер отвечает на поисковый запрос (Т-12…Т-15, Т-18, Т-24, Т-25). Все числа ниже — значения по умолчанию из Т-18; их меняют настройки и вызов агента.

## Область поиска

Этот документ описывает обычный режим поиска (`hybrid`). Режимы `mix` и `graph`, которые добавляют к нему связи документов, — в [инструментах GraphRAG](../graphrag/tools.md).

1. **Проект.** Явно заданный проект или проект сессии: ближайшая к cwd агента папка, которая зарегистрирована в bars (Т-15). Поиск никогда не выходит за один проект (урок 9 образца).
2. **Отбор внутри проекта.** Список модулей и/или файлов (Т-14). Модуль — имя папки первого уровня, корневой — `.`; файл — путь от корня документации или проекта, как в выдаче. Модули и файлы объединяются: ищется по всему отмеченному. Неизвестный модуль или файл — `invalid_params` с подсказкой. Пустой отбор — весь проект.
3. **Состояние проекта.** Если проекту нужна переиндексация из-за смены модели, поиск возвращает ошибку «нужна переиндексация» и ничего не ищет (Т-25).

## Согласованность чтения поиска

Поиск открывает готовый индекс только для чтения и удерживает одну транзакцию чтения от проверки совместимости и области до загрузки выдачи. Публикация схемы графа и обновление документов в другом соединении не меняют снимок уже начатого поиска. Уже открытая вызывающим кодом транзакция сохраняется; поиск не завершает её. Миграции и создание индекса поисковый вызов не запускает: так же открывают индекс `similar`, `duplicates`, список модулей, дерево и аудиты ([воркер bars](../../architecture/worker.md), раздел «Запись и чтение индекса воркером bars»).

Контролируемая публикация SQLite-схемы во время открытия FTS воспроизвела `SchemaChanged (17): vtable constructor failed: chunks_fts` (OQ-205). Закреплённый снимок предотвращает этот класс отказа; ошибки FTS не скрываются и пустой выдачей не заменяются.

## Ожидание моделей

Встроенные модели выгружаются по таймеру простоя ([local-models.md](../models/local-models.md)); решение автора — выгрузку сохранить, а поиск не должен из-за неё падать (OQ-245, ISS-105). Поэтому поиск, которому нужна выгруженная или загружающаяся модель, запускает её загрузку и ждёт.

- **Предел — 20 секунд на обе модели вместе** (константа `MODEL_WAIT` воркера, настройки нет). Загрузка bge-m3 занимала 3,5 с, rerank — 5,6 с ([бенч качества](../../knowledge/search-quality.md)); загрузки идут по очереди под одним замком, вместе около 9 с, предел оставляет двукратный запас на холодный диск и инициализацию GPU и остаётся заметно короче срока вызова MCP (55 с).
- **Embed-модель не успела** — выдача строится только по полнотекстовой части, без векторного списка и без косинуса. Ответ несёт пометку `semantic_error` «смысловая близость не учтена: модель загружается» (окно показывает баннер, MCP — строку `semantic_error:`, CLI — строку «Внимание»). Порядок — `bm25` с поднятием точных идентификаторов (Т-12). Порог косинуса не применяется, потому что косинуса нет: `min_score` в `applied` равен 0, у результатов оценка 0, окно её не рисует. Если rerank при этом готов, он переоценивает кандидатов как обычно и применяется `min_score_rerank`. Связанные источники режима `mix` без вектора не добавляются, причина — в `fallback_reason`.
- **Rerank-модель не успела** — выдача без rerank после честного ожидания, как при ошибке rerank (раздел «Реранк кандидатов»): причина в `rerank_error`.
- **Параллельные поиски** ждут одну загрузку: заявка на загрузку модели в воркере одна, поиск её только ждёт и не блокирует остальные вызовы воркера (ожидание асинхронное, без занятого потока).
- **Без ожидания остаются:** ошибка загрузки (`Failed`), нужная переиндексация (Т-25) и модель, которая ещё не скачана (`data.percent` меньше 100). Они возвращают прежние ошибки `provider_error`, `reindex_required`, `model_loading`: ждать нечего или ждать минуты.

## Кандидаты из двух поисков

Таблицы и списки реестров получают более короткие чанки с повтором шапки таблицы ([нарезка реестров](../indexing/chunking.md)), чтобы строки из хвоста раздела попадали в окно rerank. Порог `min_score_rerank=0.1` сохраняется. Это не меняет приоритет упоминаний голого номера: точное определение требования ищется через `bars_text_search` или «В тексте».

- **Полнотекстовый:** FTS5 по цепочке заголовков и тексту чанков, ранжирование `bm25`, первые 30. У FTS5 нет русской морфологии, поэтому текст чанков при индексации и слова запроса при поиске проходят один и тот же стемминг Snowball для русского и английского (`rust-stemmers`): «настройки» и «настройка» дают одну основу. Слова, которые стеммер не меняет (числа, латиница в коде), ищутся как есть. Слова запроса соединяются через `OR`: `bm25` сам поднимает чанки, где совпало больше слов. На корпусе bars стемминг ставил нужный раздел первым чаще префиксного поиска ([knowledge/spike-search.md](../../knowledge/spike-search.md)).
- **Идентификаторы в запросе.** Токенайзер режет `some_option_name` на слова `some`, `option`, `name`, а они общие: по `OR` документ с этими словами порознь обгоняет документ с самим идентификатором. Поэтому слово запроса, которое стемминг разрезал на несколько, идёт в FTS ещё и фразой: `"some option name"` ищет эти слова подряд.
- **Векторный:** запрос эмбеддится моделью проекта (с префиксом запроса, если он у модели есть); точный перебор по косинусной близости, первые 30 ([architecture/vector-search.md](../../architecture/vector-search.md)).

## Слияние и порядок кандидатов

Оба списка сливаются через Reciprocal Rank Fusion: оценка кандидата — сумма `1 / (60 + место)` по спискам, где он есть. При равной сумме выше тот, кто стоит выше в полнотекстовом списке: зеркальные места «первый и второй» в двух списках дают ровно равные суммы, а точное совпадение поднимает именно полнотекстовый поиск (Т-12).

Порядок без rerank остаётся гибридным намеренно (решение автора OQ-77, ISS-02): глобальная сортировка по косинусу и отдельные группы точных совпадений отклонены. Сортировка полного пула по косинусу выигрывает правильного лидера на одних наборах и проигрывает на других ([бенч качества](../../knowledge/search-quality.md)), а точный идентификатор она может опустить ниже, нарушив Т-12. Поэтому окно показывает числовую оценку честно и объясняет, почему близость может возрастать вниз по списку (ниже, «Оценка результата и порог»).

Одного RRF для Т-12 мало: чанк с точным идентификатором, который первый в полнотекстовом списке, но далеко в векторном, проигрывает чанку, который просто второй в обоих. Поэтому чанки, в которых есть идентификатор из запроса, идут впереди остальных; внутри каждой группы порядок слияния сохраняется. Идентификатор — слово запроса с `_`, `.` или `/` внутри (`some_option_name`, `settings.toml`); точка в конце предложения и дефис в слове (`по-русски`) идентификатором не считаются. Запрос без идентификаторов этим правилом не затрагивается. Решение агента (`QUESTIONS.md`, OQ-31).

## Реранк кандидатов

Если rerank включён, лучшие кандидаты в порядке слияния (`rerank_candidates`, по умолчанию 15) переоцениваются rerank-моделью, и выдача упорядочивается по её оценке. Ей уходят путь, цепочка заголовков и текст чанка; модель читает из них только первые 512 токенов вместе с запросом, поэтому хвост длинного чанка на оценку не влияет ([длина входа](../models/local-models.md#длина-входа-встроенных-моделей)). По умолчанию возвращается 3 результата. Без реранка — 5 в порядке слияния. Если rerank включён, но не отработал (недоступен, вернул не то число оценок), поиск возвращается без него: оценка — косинус, применены параметры без реранка, причина — в ответе ([features/models/external-models.md](../models/external-models.md)).

## Оценка результата и порог

Порог применяется к оценке, у которой есть абсолютный смысл. Оценка RRF его не имеет:

- **С реранком** — оценка реранка, порог `min_score_rerank`.
- **Без реранка** — косинусная близость чанка к запросу, порог `min_score_vector`. Близость считается для всех кандидатов, включая найденных только полнотекстовым поиском.
- **Без rerank и без embed** (модель не успела загрузиться, «Ожидание моделей») — оценки нет, порога нет: выдаётся первые результаты в порядке `bm25`, число — по параметрам без rerank.

Обе оценки лежат в диапазоне от 0 до 1 ([features/settings/settings.md](../settings/settings.md)). Порог задаёт пользователь в настройках, там же — пределы, в которых его может менять агент (Т-24). Порог агента вне пределов прижимается к ближайшей границе, и в ответе сказано, какой порог применён. Так же прижимаются число результатов и кандидатов сверх `max_results` и `max_candidates`.

В окне процент и полоска показывают эту числовую оценку, умноженную на 100: «Оценка по близости» без rerank, «Оценка модели» с ним. Это не вероятность правильного ответа. Без rerank порядок остаётся гибридным, поэтому косинусная близость может возрастать вниз по списку; окно объясняет это над карточками. Словесные категории «частично/хорошо подходит» не используются: замер не калибровал такие границы. Решение автора — OQ-77, проценты и полоска сохранены: полоска и проценты — шкала фактической оценки, окно не нормирует RRF и не вычисляет процент из места результата. Для косинуса используется акцентный цвет без категорий, для rerank — цвета числовых диапазонов с подписью вида оценки; доступное имя полоски называет измеряемую величину. При ошибке rerank карточки показываются как косинусные по фактическому `score_kind`.

## Состав результата

JSON каждого результата также содержит `source_hash`: blake3 полного документа в снимке поиска. [Граф запроса](../graphrag/query-graph.md) использует его для проверки версии файла; оценка, порядок и идентификатор чанка от этого поля не меняются. Хеш читается вместе с фрагментом в той же транзакции, а не вычисляется по текущему файлу после поиска.

Запрос без слов (пустой или из одних знаков) — ошибка `invalid_params`.

Каждый результат (Т-13): ID чанка (`id` в тексте MCP, `chunk_id` в JSON; для `get_similar`, [формат и срок действия](maintenance-tools.md#идентификатор-чанка-для-get_similar)), путь, модуль, `title` документа, цепочка заголовков, строки начала и конца, текст чанка, оценка и её вид (`rerank` или `cosine`). Ответ в целом несёт применённые параметры, флаг «идёт индексация» и число документов в очереди; насколько поиск задерживается, пока идёт индексация, и как запрос обгоняет пачки модели — в [замере ISS-09](../../knowledge/search-during-indexing.md). Текста, сгенерированного LLM, в ответе нет.

## Область и состав выдачи по модулям

В ответе `applied.scope` содержит списки `modules` и `files` вызова; они объединены, пустые списки означают весь проект. `by_module.candidates` считает уникальный пул после слияния FTS и векторов, до rerank, порога и лимита выдачи; это фактический счёт, а не параметр `candidates`. `by_module.results` считает только выданные чанки. В `mix` учитывается основная выдача, связанные источники не входят. В режиме `graph` основная выдача пуста и обе карты пусты. Счёт выполняется в том же снимке индекса, без чтения текстов всего пула.

MCP печатает строки `scope` и `by_module`; CLI — русские подписи. Только широкий поиск с результатами из нескольких модулей предлагает сузить область. Пустой поиск в модулях предлагает весь проект и поясняет, что ноль не доказывает отсутствие. Машинные поля одинаковы для MCP, CLI и окна; отображение подсказок — контракт агентских каналов ([выбор модулей](../agent-tools/module-scope.md)).

## Скорость поиска без rerank

Полный поиск читает таблицу векторов последовательным проходом; поиск в отмеченных файлах и модулях сохраняет предварительный отбор. Это уменьшает повторное чтение SQLite без изменения точности и порядка выдачи. Причина лишней дисковой нагрузки и границы замера — [устройство векторного поиска](../../architecture/vector-search.md).

НФТ-2 не подтверждено полным CPU-запросом на естественных 5 000 чанках. Индекс и стенды для такого замера готовы, но прогон 26-10-2026 шёл под меняющейся нагрузкой рабочей машины и скорость не показывает; что из него верно — [исследование скорости](../../knowledge/inference-speed.md), раздел «Естественные 5 000 чанков». Умолчания поиска не менялись.

### Схема баллов: итоговая оценка результата

Результат поиска — кусок (чанк) с итоговой оценкой `S`. **Оценка складывается из «опорного» сигнала с абсолютным смыслом и небольших добавок от остальных сигналов:**

`S = a + w_c·c + w_f·f + w_p·p + w_l·l`, где `a` — опора: оценка rerank `r`, а когда rerank недоступен, косинус `c`.

Это взвешенная сумма Т-12, у которой вес опоры равен 1. Результаты сортируются по `S`; окно и агент видят `min(1, S)`. Опора нужна, чтобы шкала и порог сохраняли смысл: `r` и `c` лежат в диапазоне 0…1 и значат одно и то же для любого запроса, а полнотекстовый балл нормировать абсолютно не удалось (опыты, раздел про абсолютную шкалу).

| Сигнал | Откуда | Шкала | Нормирование | Стартовый вес |
|---|---|---|---|---|
| `r` — rerank | rerank-модель, только кандидатам, ушедшим в rerank | 0…1, абсолютная | без изменений | опора, 1 |
| `c` — смысловая близость | косинус вектора запроса и чанка, считается для всех чанков области | 0…1, абсолютная (отрицательные — 0) | без изменений | опора без rerank; с rerank `w_c = 0` |
| `f` — слова запроса по полям | составной `bm25` FTS5 по четырём колонкам (название и имя файла 5, заголовки 3, текст 1, точная форма 0,3), язык и опечатки — шаг 2.3.3 | 0…1, относительная | деление на максимум по списку FTS запроса; чанку вне списка FTS — его `bm25` одним запросом по `rowid`, у не совпавшего слов — 0 | 0,1 |
| `p` — точное совпадение | в колонке точной формы: все идентификаторы запроса целиком, фраза запроса, доля пар соседних слов подряд | 0…1 | `p = 1`, если в чанке есть все идентификаторы запроса или запрос целиком; иначе доля пар слов подряд | 0,1 |
| `l` — связи | индекс ссылок: документ чанка связан ссылкой с документом одного из трёх лучших результатов до добавки связей | 0 или 1 | — | 0 до бенча |

Почему так, а не «все сигналы нормировать и сложить»:

- **Поля `bm25` не складываются по отдельности.** Сумма отдельно нормированных баллов четырёх полей хуже одного составного `bm25` с весами колонок: на 168 запросах 57 % первым против 60 %, на проверочной части 54 % против 62 %; ранговое нормирование (то, что делает RRF) — 51 %. Поэтому поля остаются внутри `bm25`, а их веса колонок — настройка токенизации.
- **Ранги не годятся как баллы.** Слияние rerank с полнотекстовым списком через RRF даёт 58 % первым против 63 % у одного rerank; сумма `r + 0,1·f` — 65 %. Деление на максимум лучше насыщения `x/(x+медиана)` (60–64 %) и z-оценки.
- **Покрытие слов запроса отдельным слагаемым не нужно**: добавка 0,1–0,4 доли покрытых слов не меняла MRR (0,693–0,697 против 0,696); множитель разрушал поиск ещё в замере токенизации. `bm25` с `OR` уже поднимает чанки с большим числом слов. Покрытие в схему не входит.
- **Идентификаторы больше не поднимаются принудительно**: правило «чанки с идентификатором запроса идут впереди» (OQ-31) заменяет сигнал `p` и колонка точной формы. Чанк с идентификатором попадает в кандидатов на rerank через `p` в предварительном порядке. Достаточно ли этого, решает бенч группы «идентификаторы» (12 запросов, первым 42 %); если нет — правило остаётся.

Равные `S` упорядочиваются по `f`, затем по пути документа и номеру куска.

### Схема баллов: что делается, когда сигнал недоступен

| Недоступно | Опора | Что меняется | Что сказано в ответе |
|---|---|---|---|
| rerank (выключен, ошибка, не успел загрузиться) | `c` | `S = c + w_f·f + w_p·p`; порог — `min_score` по `c` | `rerank_error`, как сейчас |
| embed-модель (не успела загрузиться) | нет | порядок `f + w_p·p`; вектора нет, `c = 0`; если rerank готов, он переоценивает кандидатов полнотекстового пула и становится опорой | `semantic_error`, как сейчас; оценка в окне не рисуется, если опоры нет |
| rerank и embed | нет | порядок по `f + w_p·p`; порога нет, оценки нет — как сегодня; на абсолютной шкале полнотекстовый балл правильный первый от неправильного не отделяет | оба поля ошибок |
| связи (нет индекса ссылок) | — | `l = 0`, сигнал просто не участвует | ничего: сигнал по умолчанию с нулевым весом |

Недоступный сигнал **не** заменяется нулём в сумме с перенормировкой: опора определяет шкалу, и порог относится к ней. Ожидание моделей — как сейчас (раздел «Ожидание моделей»).

### Схема баллов: кандидаты и rerank

1. **Пул.** Объединение первых `candidates` (по умолчанию 30) по составному `bm25`, первых `candidates` по косинусу и, как сегодня, слов-идентификаторов. Расширение кандидатов режима `mix` в поиск не входит (графовых режимов в поиске нет, ADR-0007).
2. **Предварительная оценка** `S0 = c + w_f·f + w_p·p` для каждого кандидата; без embed — `f + w_p·p`.
3. **В rerank** уходят первые `rerank_candidates` (по умолчанию 15) по `S0` вместо порядка RRF. Вход rerank — путь, цепочка заголовков, текст чанка (первые 512 токенов), как сейчас.
4. **Итог** — `S` с опорой `r`. Кусков, не попавших в rerank, в выдаче нет, как сегодня.

Замена RRF порядком `S0` на бенче **не измерена**: для неё нужны векторы запросов (OQ-267). Измерена только перестановка уже выданных десяти кусков.

### Схема баллов: порог и оценка в выдаче

- **Порог — одна настройка `min_score`** вместо `min_score_rerank` и `min_score_vector` (Т-24), по умолчанию 0,1. Он относится к опоре `a`, а не к `S`: добавки `f`, `p`, `l` не могут вытащить чужой результат выше порога. Пределы агента, прижим к границам и сообщение «какой порог применён» — как сейчас (OQ-266: одна настройка или две).
- **На бенче порог 0,1 по rerank ничего не отсекает** (0 из 1 261 куска), порог 0,2 отнимает 3 правильных куска у 2 запросов и убирает 13 % лишних. Запросов без ответа в бенче нет, поэтому значение выше 0,1 не обосновано (OQ-269). При опоре `c` порог — прежний `min_score_vector`, переносится в `min_score` при переходе.
- **«Оценка» человеку** — `min(1, S)` одним числом и полоской; цвета и вид оценки («модель», «близость») — дело дизайна выдачи (шаг 2.4.1). Разбор по сигналам (`rerank`, близость, слова, точное совпадение, связи) — по наведению в окне и строкой в ответе агента.
- **Ответ поиска.** У результата — `score` (`min(1, S)`), `score_kind` опоры (`rerank`, `cosine`, `none`) и `signals` с числами `r`, `c`, `f`, `p`, `l`, у которых они есть. `applied` — `min_score`, веса и список использованных сигналов. Остальное — как в разделе «Состав результата».

### Схема баллов: операторы запроса

Операторы разбираются до всего остального и работают в окне, MCP и CLI одинаково. Формат — «как в Google», по словам автора ADR-0007.

| Оператор | Смысл | В полнотекстовой части | В смысловой части |
|---|---|---|---|
| `"точная фраза"` | слова подряд, без стемминга, регистр и `ё` не важны | обязательное условие `{точная форма} : "a b c"`; чанк без фразы в выдачу не попадает | слова фразы остаются в тексте для вектора, кавычки снимаются; кандидат из векторов проверяется по колонке точной формы |
| `-слово`, `-"фраза"` | исключить чанки, где слово есть | `NOT` по основе слова в колонках названия, заголовков, текста и по точной форме; проверка любого кандидата одним запросом по `rowid` | слово не входит в вектор запроса |
| `path:папка`, `папка:папка` | ограничить областью: префикс пути от корня документации или проекта, как у `files` | фильтр по пути документа | тот же фильтр на полный перебор векторов |

Правила разбора:

- Оператор — слово, которое начинается с `-` и дальше идёт буква, либо `path:`/`папка:` в начале слова, либо пара кавычек. `-5`, `по-русски`, `274-ФЗ`, одиночная кавычка и дефис внутри слова — обычные символы. Пути и фраза с пробелом — в кавычках: `path:"features/search"`.
- Несколько `path:` — «или»; фильтры `path:` **сужают** область из галочек и параметра `modules`/`files` (пересечение, а не объединение: оператор не расширяет то, что отмечено); неизвестный путь — `invalid_params` с подсказкой, как у неизвестного модуля.
- Запрос без слов, где остались только исключения или фильтр, — `invalid_params` «в запросе нет ни одного слова». Фраза в кавычках считается словами.
- Слова операторов не попадают в `OR`-запрос FTS, исключения и фильтры не меняют `c`, `f` и `p`; фраза даёт сигналу `p` единицу.
- Бенч не содержит ни одного запроса с операторами (проверено: 0 из 168), поэтому для приёмки нужны запросы с `"…"`, `-` и `path:` (OQ-269).
- Синтаксис и пересечение с галочками — OQ-265.

### Схема баллов: свёртка кусков раздела

Решение автора OQ-248, рекомендация исследования — [повторы раздела в выдаче](../../knowledge/search-quality.md).

- **Раздел** — куски одного документа с одной цепочкой заголовков (они идут подряд: разрез раздела на несколько чанков делает нарезка реестров и предел 6000 знаков).
- **Когда сворачивается.** После итоговой оценки: куски одного раздела дают один результат; `S` раздела — `S` лучшего куска, **бонус за остальные куски 0**. Бонус 0,05–0,2 на выдачах бенча никому не помогал и ухудшил порядок у двух запросов (`bp-09`, `tm-13`); оставлен параметром `fold_bonus` = 0 для подбора в 2.3.4.
- **Порог по куску, N по разделам.** Порог применяется к опоре куска до свёртки; «результатов» (3 с rerank, 5 без) — число разделов. В пуле 15 кусков остаётся в среднем 11 разделов, поэтому добор нужен редко; если разделов меньше N, добираются следующие кандидаты пула.
- **Документ не штрафуется:** несколько разделов одного документа остаются отдельными результатами (ограничение числа результатов на документ снижало Hit@3).
- **MCP.** Один результат на раздел: `id` лучшего куска (для `get_similar`), путь, модуль, цепочка заголовков, строки начала и конца всего раздела, текст лучшего куска, `parts` — сколько кусков в разделе и сколько из них нашлось. Остальной текст раздела читается через `bars_read` с `lines`.
- **Окно.** Дизайн (карточка документа с разделами внутри) — шаг 2.4.1; данные для него: порядок разделов, документ, лучший раздел, `parts`.
- На выдачах бенча сворачивание не меняет метрики (63 % / 88 % / 0,754 против 0,753) и сокращает 10 кусков до 7,4 разделов. Свёртка до rerank (представитель — лучший кусок по `S0`) и склейка короткого хвоста не измерены.

### Схема баллов: стартовые веса и подбор в шаге 2.3.4

- **Стартовые значения:** `w_c = 0` при rerank, `w_f = 0,1`, `w_p = 0,1`, `w_l = 0`, `fold_bonus = 0`, `min_score = 0,1`, веса колонок FTS 5 / 3 / 1 / 0,3. Для `w_f` это значение лучшее по нечётным запросам в опытах ([опыты схемы баллов](../../knowledge/search-scores.md)): сумма `r + 0,1·f + 0,1·p` на выдачах полного конвейера даёт первым 65 % против 63 % и MRR 0,760 против 0,753, на проверочной части — первым 62 % против 60 %.
- **Подбор:** сетка по нечётным запросам (`w_f` 0–0,3, `w_p` 0–0,2, `w_c` 0–0,3 при rerank, `w_l` 0–0,1, `fold_bonus` 0–0,1, `rerank_candidates` 15 / 20 / 30); целевая — MRR, затем «первым»; один раз проверка на чётных. Прогон — установленным `bars-cli`, по одному запросу подряд, с rerank и отдельно без rerank (нужны сборка и векторы, OQ-267).
- **Приёмка (OQ-254, раунд 34):** не хуже базового полного конвейера (63 % / 88 % / 0,747) в сумме и в каждой группе от 10 запросов с допуском 1 п.п. и 0,01 MRR; группы меньше 10 — ручной разбор каждого ухудшившегося запроса; то же для проектов; журналы в топ-3 и повторы раздела и документа в топ-5 не растут без объяснения. Прибавка добавок к rerank на выдачах бенча (11 запросов потеряно, 15 выиграно; потери — «идентификаторы», «опечатки», «синонимы», «руководство среди журналов») строгую приёмку **не проходит**: вполне возможно, что 2.3.4 оставит `w_f = 0` и выберет схему по другим причинам (операторы, свёртка, порог, ожидание моделей, режим без rerank).

### Схема баллов: ожидаемый эффект и что не доказано

- **Режим без модели, только полнотекстовая часть:** составной `bm25` с четырьмя полями — 60 % / 78 % / 0,696 против 52 % / 75 % / 0,653 у нынешнего («как сейчас»), то есть +8 п.п. первым ([токенизация](../../knowledge/tokenization.md)). Это эффект шага 2.3.3, а не схемы баллов.
- **Полный конвейер с rerank:** схема даёт 0…+2 п.п. первым, Hit@3 без изменений, внутри шума одного запроса; польза схемы — операторы, свёртка разделов, единая шкала и порог, замена принудительного поднятия идентификаторов.
- **Не измерено:** косинус как слагаемое и замена RRF порядком `S0` (без векторов запросов), связи, операторы, запросы без ответа, свёртка до rerank. Для этих решений нужна сессия со сборкой (OQ-267), расширение бенча (OQ-269) и решение по связям (OQ-268).
