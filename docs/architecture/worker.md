# Воркер bars — запуск, задачи внутри процесса, очередь, завершение

Как устроен процесс `bars`: единственный процесс, который читает и пишет индексы и загружает модели (Т-1, НФТ-3). Решение агента, 14-10-2026.

## Запуск воркера bars

| Как запущен | Что происходит |
|---|---|
| `bars` — пользователь открыл приложение | воркер стартует и показывает окно |
| `bars --background` — запустил `bars-mcp` или `bars-cli` ([ipc.md](ipc.md)) | воркер стартует только с иконкой в трее |
| второй запуск, когда воркер уже работает | `tauri-plugin-single-instance` передаёт запуск работающему воркеру; тот показывает окно, если запуск был без `--background`, а новый процесс завершается (Т-1) |

Порядок старта:

1. Логи, затем `~/.bars/settings.toml` и `~/.bars/projects.toml` ([architecture/files.md](files.md)).
2. Открывается канал. Воркер принимает вызовы сразу, ещё до проверки проектов: клиент, который его запустил, не ждёт индексации.
3. Для каждого зарегистрированного проекта: проверяется, что папка на месте ([projects.md](../features/projects/projects.md)); файлы индекса восстанавливаются после прерванной подмены (раздел «Восстановление файлов индекса при старте»); запускается независимая проверка файлов. Только обнаруженные расхождения создают задание обновления (Т-10).
4. Запускается таймер проверки всех проектов раз в час. Слежение включается только при активности MCP или открытом проекте UI (OQ-206).

Модели при старте не загружаются: embed-модель грузится при первом эмбеддинге, rerank — при первом реранке.

## Задачи внутри воркера bars

Внутренние ревизии диска, опубликованного индекса и состояния находятся в `worker/updates.rs`; последнее значение хранится отдельно для каждого проекта, `watch` только будит потребителя и не копит события. Публикация не читает файлы и не ждёт UI. Общий координатор и восстановление окон — [обновления окон](window-updates.md). UI-чтения не продлевают MCP-активность; аренда окна остаётся прежней, 10/30 секунд.

Воркер — один процесс на tokio, внутри работают независимые задачи:

| Задача | Что делает |
|---|---|
| Сервер канала | принимает соединения `bars-mcp` и `bars-cli`, на каждое соединение — своя задача |
| Окно и трей | Tauri; команды окна вызывают те же обработчики, что и канал ([protocol.md](protocol.md)) |
| Очередь индексации | одна задача, индексирует по одному проекту за раз |
| Слежение за файлами | `notify` только для открытых в UI проектов и проектов с MCP-активностью за последний час; события копятся 500 мс |
| Таймер | раз в час запускает независимую проверку всех проектов; без расхождений очередь обновления не пополняется |
| Чтение настроек | `settings.toml` и `.bars/config.toml` перечитываются при обработке заданий и запросов; отдельного слежения за этими файлами нет |
| Менеджер моделей | загружает модели, держит их в памяти, выгружает |
| История MCP | обработчик фиксирует начало/итог допущенной попытки вне async-потока; отдельная SQLite не влияет на индекс. Сбор ограничен, потери диагностируются; обслуживание истории идёт раз в час. [Данные, хранение и API](../features/window/mcp-statistics.md) |

Поиск выполняется в задаче соединения, которое его запросило. Он не стоит в очереди индексации и не ждёт её.

## Очередь индексации воркера bars

Журнал операций снимает согласованный снимок активных заданий, завершений, ключей настроек и поколений регистрации под короткими замками. Чтение настроек и процента скачивания выполняется после их освобождения и дополняет только этот снимок: позднее завершение попадёт в следующий курсор. При постановке задания ключ настроек вычисляется до захвата замков проектов, очереди и журнала; слияние сохраняет ключ и ID исходной попытки (ISS-78).

У scan блокировка индекса ограничена копированием метаданных (`ScanSnapshot`): после чтения путей, stat/hash и layout SQLite закрывается и read-lock освобождается. Обход диска не удерживает SQLite или gate, поэтому ожидающий writer подмены не ставит новые поиски за долгим обходом. После удаления проекта scan ничего не открывает заново; отмена и проверка поколения не дают опубликовать поздний результат.

Явный `reindex` без `full` и без подтверждения смены модели запускает отдельную задачу `scan`, а не становится в очередь индексации. Она читает согласованный снимок опубликованного SQLite через read-only connection под read-lock проекта, обходит диск без модели и пишет результат только в журнал операций. Счётчики означают найденные различия; `index_applied=false`. Только при изменениях, смене layout или ошибках проверки ставится обычное обновление с явным приоритетом; оно повторно сверяет диск после возможной подмены индекса. Пауза индексации не задерживает scan. Отмена и публикация результата сериализованы projects-lock; поколение регистрации и ключ настроек защищают от устаревшего продолжения. Задачи учитываются в `is_idle`/shutdown, удаление проекта отменяет scan и ждёт освобождения read-lock. Публичный `status` показывает `indexing`, пока scan активен; подробная стадия и итог находятся в операции `scan`. Проверки активности и таймера используют независимый scan; применение изменений и начальная индексация идут через очередь обновления.

- В очереди — проекты, у каждого область: весь проект или перечисленные файлы/каталоги. Повторное ожидающее задание сливается с прежним и сохраняет ID операции. Готовность `job_gate` проверяется до снятия задания: занятый проект остаётся в очереди, остальные выполняются. Граф уступает ожидающему обновлению между квантами. Область ограничивает разбор и embed; изменение layout требует полного обновления с повторным использованием векторов.
- Приоритет: явная переиндексация и хук начала сессии → правка в окне → события слежения → проверка при старте и периодическая (Т-42).
- Перед этой очередью стоит [очередь документов](../features/indexing/document-queue.md): правка документа сначала ждёт паузу Т-41 и только потом попадает в задание проекта.
- Порядок проверки проекта описан в [features/indexing/updates.md](../features/indexing/updates.md).
- Ход индексации — число обработанных и оставшихся документов — виден в `status` и в окне.

## Модели в памяти воркера

Ключ встроенного слота — source/model/accelerator (для embed также сверяется fingerprint). URL, ссылки на ключи API и размер HTTP-пачки не используются встроенным loader и не создают другую сессию. Иначе различие неиспользуемых настроек проектов могло оставлять одновременно две копии одной встроенной модели у активных читателей. Для внешнего embed URL, ссылки на ключи и batch участвуют в ключе; accelerator не участвует. Включение rerank не меняет его слот. Это предотвращает лишние загрузки, но не ограничивает стоимость одной сессии на длинном входе.

Приоритет ожидающего поискового запроса проверяется также после получения model-lock: пачка индексации могла начать ждать замок ещё до появления запроса. Если запрос уже ждёт, пачка освобождает замок и уступает ему (ISS-16). Это ограничивает ожидание текущей пачкой при отсутствии других поисков, но не задаёт универсальный предел в секундах: он зависит от модели, устройства и длины входа.

У модели fastembed метод `embed` требует исключительного доступа (`&mut self`): одна модель считает один вызов за раз. Поэтому:

- каждая загруженная модель лежит за мьютексом;
- индексация эмбеддит чанки пачками по 4 и отпускает модель между пачками; пачка встроенной модели ещё и не больше 3 000 символов с учётом дополнения до самого длинного текста, потому что время пачки растёт быстрее длины;
- эмбеддинг поискового запроса идёт вне очереди: пока запрос ждёт модель, индексация не берёт мьютекс (он не честный и без этого пропускал запрос не сразу). В коде это счётчик ждущих запросов у слота модели (`ModelSlot::with_priority`) и предел `BATCH_CHARS` в `bars-worker/src/worker/models.rs`. Запрос ждёт не дольше одной пачки — в худшем случае одного очень длинного чанка, около 3 с: пока запрос и индексация делят одну модель, меньше не сделать. На замере 66 чанков очередь снизила медиану запроса при индексации с 2,9 до 0,88 с, а предел пачки — до 0,75 с (p90 9,4 → 2,0 с, максимум 22,8 → 3,0 с) ценой замедления индексации на 7 % ([замер](../knowledge/search-during-indexing.md)).

Свободные встроенные сессии выгружаются после простоя: по умолчанию rerank — 5 минут, embed — 15 минут; проверка каждые 10 секунд. Срок каждая проверка берёт из `unload_after_minutes` в `settings.toml` ([settings.md](../features/settings/settings.md)); `0` — не выгружать, незаданный ключ — срок из `WorkerConfig::model_idle`. Время считается от завершения работы, опрос состояния его не продлевает. Сохранение настроек будит проверку сразу: отключённый rerank освобождается, когда закончит текущий вызов. Внешние HTTP-модели не выгружаются по этой политике. Первый запрос после выгрузки заново загружает сессию; поиск ждёт загрузку скачанной модели до 20 с, а при неудаче идёт без недоступного сигнала ([ожидание моделей](../features/search/hybrid-search.md#ожидание-моделей)); `model_loading` остаётся для скачивания ([local-models.md](../features/models/local-models.md)). Индекс, файлы весов и настройки поиска сохраняются.

Загрузка, inference и время использования защищены одним model-lock; занятый слот reaper пропускает. Дорогой drop идёт вне замков модели и менеджера, под общим загрузочным gate: новый constructor не накладывается на освобождение старой сессии. Смена конфигурации сохраняет старый Arc до завершения использующего его запроса. Последний владелец слота передаёт сессию отдельному потоку менеджера, поэтому освобождение при замене и после старого читателя не блокирует async-поток (ISS-79). Выгрузка по простою выполняется в `spawn_blocking`. Shutdown будит и дожидается задачи очистки, освобождает владение слотами и ждёт уже переданные освобождения. Скачивание и загрузка моделей идут через тот же gate; поиск во время скачивания получает `model_loading` с ходом скачивания, а загрузку скачанной модели в память ждёт (`MODEL_WAIT`, асинхронно, одна заявка на загрузку на всех). Готовность слота проверяется без ожидания замка: занятый model-lock при состоянии слота `ready` означает inference, а не загрузку, и поиск идёт дальше, вставая в очередь перед пачкой индексации ([protocol.md](protocol.md), `local-models.md`, «Один замок на скачивание и загрузку»).

## Индекс проекта в воркере bars

- Индекс открывается в режиме WAL: поиск читает, пока очередь индексации пишет.
- Пишет в индекс только писатель под замком задания проекта; каждый документ записывается одной транзакцией ([features/indexing/updates.md](../features/indexing/updates.md)). Правила — раздел «Запись и чтение индекса воркером bars».
- Чтения открывают соединение только для чтения. Каждое соединение чтения своё и короткое.

Полная переиндексация строит индекс в `index.sqlite.new`. В конце воркер ненадолго закрывает доступ к проекту на запись и чтение: новые поиски ждут, текущие дочитывают. Затем воркер закрывает все соединения со старым файлом и подменяет его новым: старый файл уходит в `index.sqlite.old`, новый встаёт на место `index.sqlite`, `.old` удаляется. Без закрытия соединений подмена не сработает: на Windows нельзя переименовать файл поверх открытого.

## Запись и чтение индекса воркером bars

Проектирование 28-10-2026 по ожиданиям ISS-67 и ISS-68. Где код ещё расходится с правилом, это сказано в строке правила.

- **Один писатель на проект.** `index.sqlite` проекта открывается на запись (`Index::open`) только под замком задания проекта (`job_gate`). Писателей два: задание очереди индексации — обновление, полная переиндексация, подмена файла, миграции схемы и перестройка FTS — и построение графа, которое берёт тот же замок и уступает ожидающему заданию между квантами ([graph.md](graph.md)).
- **Чтения без записи.** Все остальные пути — поиск и `mix`, `similar`, `duplicates`, список модулей, дерево, аудиты, чтения графа, scan, сводка трея — открывают индекс через `Index::open_read_only` под замком проекта на чтение. Читатель не создаёт файл, не меняет режим журнала и не мигрирует. Нет файла индекса — ответ строится как для проекта без индекса, файл не появляется.- **Перестройка только заданием.** Устаревшая схема (`SchemaOutdated`) по-прежнему переводит проект в `reindex_required` (Т-25). Устаревший разбор FTS (`stem_version`) читатель не чинит: поиск отвечает ошибкой «полнотекстовый индекс перестраивается», старую таблицу с другими колонками он не читает, а scan считает такой индекс расхождением и ставит обычное задание обновления, которое перестраивает FTS при открытии на запись. Сверка — `Index::stem_outdated` в scan; задание обновления перестраивает FTS при открытии индекса на запись.
- **Индекс ссылок не входит.** `links.sqlite3` — отдельная база, производная только от текста на диске ([link-index.md](../features/knowledge-base/link-index.md)); её открытие и пересоздание правилами индекса поиска не ограничены.

## Восстановление файлов индекса при старте

Проектирование 28-10-2026 по ожиданиям ISS-67 и ISS-76.

Подмену может прервать сбой, выключение ОС или неудачный откат. Восстановление смотрит на три файла проекта — `index.sqlite`, `index.sqlite.old`, `index.sqlite.new` — и приводит их к одному индексу. Служебные файлы SQLite (`-wal`, `-shm`, `-journal`) удаляются вместе со своим файлом.

| `index.sqlite` | `.old` | Действие |
|---|---|---|
| есть | есть | подмена дошла до конца: `.old` удаляется |
| нет | есть | подмена прервана или откат не удался: `.old` возвращается на место `index.sqlite` |
| любой | нет | старого файла нет, возвращать нечего |

`index.sqlite.new` при восстановлении удаляется всегда: недописанная или неподменённая переиндексация не применяется, явную полную переиндексацию пользователь запускает снова, а проверка при старте доиндексирует изменения. Прежний индекс предпочтён новому, потому что полноту `.new` дёшево не проверить, а старый файл согласован со своей моделью.

Когда восстановление идёт:

- при старте воркера — для каждого зарегистрированного проекта до запуска очереди и проверок;
- в начале каждого задания очереди под `job_gate`, до открытия индекса: проект, оставшийся без индекса после неудачного отката, получает `.old` обратно со следующим заданием, без перезапуска.

Периодическая проверка, активность MCP и окна, регистрация и сохранение настроек файлы индекса не трогают. Код — `recover_index_files` в `bars-core/src/indexing/indexer.rs`; воркер зовёт её в `Worker::start` и в начале `job::run`.

## Ошибка отката подмены индекса

Проектирование 28-10-2026 по ожиданию ISS-76.

Не встал новый файл — `swap` возвращает старый на место. Если и это не удалось, ошибка не глотается: `IndexingError::Swap { cause, rollback }` несёт обе причины (установки и отката), воркер пишет их в лог уровнем `error` с путями файлов и ставит `last_error` проекта «Подмена индекса не удалась, прежний индекс не возвращён». Следующее задание или старт возвращает `.old` по правилам восстановления.
## Реализация очереди и состояния воркера

Решение агента, 15-10-2026; код — `crates/bars-worker/src/worker/`.

- **Задание на проект.** Очередь хранит не больше одного задания на проект: повторное сливается с ожидающим, место в очереди сохраняется. При слиянии больший приоритет побеждает, полная проверка поглощает список файлов, переиндексация поглощает проверку, согласие хотя бы одного задания сохраняется. Приоритеты: явная переиндексация, хук и регистрация → слежение → старт и периодическая проверка.
- **Список файлов.** Задание «только перечисленные файлы» выполняет ту же проверку по размеру и времени, что и полная; список нужен слиянию и счётчику `pending` (OQ-44).
- **Очередь документов.** `DocQueue` (`worker/doc_queue.rs`) за мьютексом воркера хранит по записи на документ: `waiting` → `queued` → `indexing` → запись снимается или остаётся с `error`. Слежение и правка из окна (`Worker::documents_edited`, её зовёт `document_write`) назначают паузу `[indexing] edit_pause_seconds`; таймер `run_doc_timer` ставит готовые документы заданием `Files` с приоритетом источника. После обхода индексатор передаёт `IndexObserver::discovered` список расхождений: недостающие записи создаются без паузы с источником задания. `priority` задаёт порядок внутри прохода, `file` переводит одну запись в обработку, `document_done` снимает завершённую запись или сохраняет ошибку; при rebuild успех снимается только после применения индекса. Наблюдатель `defer` пропускает ждущих паузы и явного повтора ошибки. Явная команда снимает ожидание в своей области, полная переиндексация обрабатывает всё. Удаление не ждёт паузы. Итог задания учитывает только ещё не завершённые записи и не снимает новую правку уже обработанного документа. В `reindex_required` записей нет; остановка и удаление проекта снимают их. `is_idle` ждёт документов без ошибки, `pending` в `status` не считает ошибки. Подробный контракт — в описании [очереди документов](../features/indexing/document-queue.md).
- **Индекс на время задания.** Задание открывает индекс в режиме WAL и закрывает в конце. Постоянных соединений записи у воркера нет, поэтому перед подменой файла закрывать нечего.
- **Доступ к проекту.** У каждого проекта есть замок «читатели — писатель». Поиск держит его на чтение, пока открывает индекс. Полная переиндексация строит `index.sqlite.new` без замка и берёт его на запись только на подмену файла: новые поиски ждут, текущие дочитывают.
- **Модель.** Отпечаток модели берётся из настроек и не требует загрузки: проверка Т-25 модель не загружает. Сама модель загружается при первом эмбеддинге и лежит за мьютексом, который берётся на пачку из 4 текстов. Смена модели в настройках заменяет её при ближайшем задании; старая выгружается, когда её отпустят все, кто с ней работает.
- **Т-25.** Проверка, увидевшая другой отпечаток, переводит проект в `reindex_required` и ничего не пишет. Состояние не меняют ни слежение, ни периодическая проверка, ни хук. `reindex` в этом состоянии без согласия возвращает `reindex_needs_consent` при любом `full`; с согласием строит индекс заново новой моделью. Полная переиндексация без согласия по проекту, чей индекс построен другой моделью, тоже не заменяет индекс.
- **Слежение.** Один `notify-debouncer-full` (500 мс) работает по корню документации при активности MCP или открытом проекте UI. Структурные события сначала инвалидируют дисковое дерево; тип события сохраняет папки с точкой и исчезнувшие пути без обращения к ссылкам за пределами корня. Индексационный фильтр отбрасывает известные обычные файлы не `.md`, скрытые папки и служебный `BARS_INSTRUCTION.md` без учёта регистра; событие внутри области вложенного проекта до постановки задания отбрасывает `on_watch_event` (области — `Inner::refresh_nested`: пересчёт по реестру при старте, регистрации, снятии, удалении и смене `docs_root`, проверка внешнему проекту при изменении списка; [вложенные проекты](../features/projects/projects.md)). Ошибка `notify` или пропавший проект ставят `watching: false`; слежение поднимается заново проверкой через 5 секунд либо почасовой проверкой. `Rescan` и ошибка уведомляют координатор о необходимости немедленной полной сверки. Потери индексирования дополнительно ловит прежняя проверка хвоста ([features/indexing/updates.md](../features/indexing/updates.md)). Нет корня документации — слежения нет, ошибка доступна в `last_error`.
- **Настройки.** Настройки читаются заново при каждом задании: правка `settings.toml` или `config.toml` руками подхватывается со следующей проверкой. Отдельного слежения за этими файлами пока нет.
- **Завершение.** `shutdown` не берёт новых заданий, останавливает текущее на границе документа и снимает слежение (раздел «Завершение воркера bars»).

## Обработчики методов воркера bars

Решение агента, 15-10-2026; код — `crates/bars-worker/src/handler/` (`mod.rs`, `errors.rs`) и `serve.rs`.

- **Одна реализация на всех.** `WorkerHandler` выполняет все методы протокола поверх `Worker` и `bars-core`; цикл соединения (`bars-protocol`) отдаёт ему вызовы после `hello` и проверки прав. Окно вызовет тот же `dispatch` без канала (Т-20).
- **Проект вызова.** Явный `project` разбирается реестром (путь или однозначное имя), иначе берётся ближайший зарегистрированный проект вверх от `cwd` (Т-15). Не нашёлся — `project_not_found` с подсказкой `bars-cli register`; имя у нескольких проектов — `invalid_params`.
- **Поиск.** Берёт замок проекта на чтение на всё время поиска (иначе подмена индекса при полной переиндексации не получила бы файл на Windows), открывает индекс и эмбеддит запрос моделью воркера в блокирующей задаче. `indexing` в ответе — проект в состоянии `indexing` или стоит в очереди; `pending` — документы в ждущем задании. Проект в состоянии `reindex_required` получает ошибку до открытия индекса. Если `rerank.enabled`, воркер берёт rerank-модель по настройкам (`Models::reranker`; грузится при первом реранке и держится, пока `[rerank]` и устройство те же) и передаёт её поиску. Не загрузилась или не ответила — выдача идёт без реранка, причина в `rerank_error`.
- **Структура и чтение.** `outline` и `read` читают файл с диска, путь разрешается общей функцией ядра ([agent-tools/mcp-tools.md](../features/agent-tools/mcp-tools.md)); `title` для `read` извлекается из frontmatter либо имени файла без нарезки чанков. `read` выбирает исходные строки через `lines` или разделы через `under`, сохраняет переводы строк и считает `revision` по всему тому же прочитанному буферу. Выбор и границы разделов линейны по размеру документа; embed и граф не запускаются. У `outline` сочетание `under` с `under_line`, у `read` сочетание `lines` с `under` — `invalid_params`.
- **Проекты.** Модули и число документов читаются из индекса под замком на чтение; у проекта без индекса и у недоступного проекта список модулей пуст.
- **`reindex`.** Проект в состоянии `unavailable` — `project_unavailable`, `reindex_required` без согласия — `reindex_needs_consent` (согласие от `bars-mcp` цикл соединения сбрасывает до обработчика).
- **`session_start`.** Отвечает `accepted: true` сразу: проверка зарегистрированного проекта запускается независимо от очереди обновления и включает час MCP-наблюдения. Новая регистрация сохраняет начальное задание индексации; папка без проекта и без документации реестр не засоряет.
- **`install` и `uninstall`.** Правят файлы клиентов через `spawn_blocking` и общий с автообновлением замок ([clients.md](../features/clients/clients.md)); пути берутся из `WorkerConfig.install_env` (по умолчанию — домашняя папка и соседние с exe `bars-mcp`, `bars-cli`); тесты подставляют временную папку. Файл клиента не разбирается — внутренняя ошибка `-32603` с именем файла, файл не тронут. После `ready` один фоновый проход обновляет клиентов с существующим MCP или хуком bars; отсутствие установки пропускается. Задача входит в жизненный цикл `Worker::shutdown`, включая выход из трея и перезапуск.
- **Запуск процесса.** `bars` открывает канал первым (он же защита от второго воркера, [ipc.md](ipc.md)), затем читает реестр и запускает независимые проверки проектов. С `--background` окно создаётся скрытым, а без него показывается; оболочку окна и трея описывает [features/window/implementation.md](../features/window/implementation.md). `serve_with` отдаёт оболочке обработчик, как только воркер поднят: окно вызывает его напрямую.

## Пауза, остановка и ход индексации

Решение автора по умолчанию (OQ-55), код — `crates/bars-worker/src/worker/control.rs`, `crates/bars-core/src/indexing/indexer.rs`.

- **Наблюдатель.** Индексатор принимает `IndexObserver`: после обхода он сообщает число документов, перед каждым документом спрашивает `should_stop`, после — сколько документов и чанков обработано. Чанки считаются и посчитанные моделью, и взятые из индекса.
- **Пауза** — одна на воркер. Идущее задание замирает в `should_stop` перед следующим документом (текущий дописывается), очередь не берёт новых заданий. `index_resume` снимает паузу и будит очередь.
- **Остановка** проекта: идущее задание получает флаг и заканчивается ошибкой `Cancelled` на границе документа, ждущее снимается с очереди. Проверка актуальности оставляет записанные документы, полная переиндексация удаляет `index.sqlite.new` и не трогает старый индекс; проект остаётся в прежнем состоянии, `last_error` не ставится.
- **Завершение.** `shutdown` останавливает задание так же, как «Остановить», на паузе и без неё (OQ-168). Общий флаг выхода доступен наблюдателю индексации, включая задание, которое начало исполняться одновременно с выходом.
- **Ход** — `activity`: число документов в обходе (0 до его конца), обработано, чанков, скорость с начала задания, текущий файл. Оценку оставшегося времени окно считает само по скорости. Устройство (видеокарта или CPU) воркер пока не сообщает; в окне плитка показывает «—» (OQ-62).
- **Ошибки файлов.** Показываются проблемы отчёта последней проверки (файл не читается, не UTF-8, папка недоступна). Ошибка провайдера, как и раньше, прерывает проверку целиком и видна как `last_error` проекта: на повтор по документу воркер пока не переходит.

## Сводка для трея

`Worker::summary` (`crates/bars-worker/src/worker/summary.rs`) отвечает, что нарисовать в трее, и не открывает индексы: общее состояние, подсказка и две строки меню — про индексацию и про то, что требует внимания. Решение агента, срез 5.

| Состояние | Когда | Иконка |
|---|---|---|
| `Attention` | есть проект в `reindex_required` или у проекта остались проблемы последней проверки (файлы с ошибкой, `last_error`) | жёлтая |
| `Busy` | идёт или ждёт задание и внимания не требуется | малиновая, мигает |
| `Idle` | иначе | серая |

Внимание важнее индексации: желтизна означает, что от пользователя ждут действия. Подсказка: «bars · проект N %, ждут M» при индексации и «bars · нужно внимание: …» иначе. Проект в `unavailable` внимания в трее не требует: он серый в списке окна.

## Настройки, ключи и модели из окна

Решение агента, срез 5; код — `crates/bars-worker/src/settings_io.rs`, `handler/mod.rs`.

- **Запись настроек.** `settings_get` и `settings_save` сериализованы общим замком воркера. Снимок настроек и ревизия вычисляются из одного чтения. `settings_save` сверяет ревизию и сравнивает изменённые поля с `base`: независимые внешние правки сливаются, конфликт возвращает текущий снимок и значения полей без записи. `toml_edit` сохраняет комментарии и порядок, итог проверяется тем же разбором, что при чтении; битый файл не заменяется. Перед атомарной записью текст повторно сверяется с диском. Замок упорядочивает окна одного воркера; ручной редактор его не использует, короткий интервал между последней сверкой и rename остаётся. Контракт — [настройки](../features/settings/settings.md). После успеха воркер ставит проекты на проверку по Т-25.
- **Корень документации.** `set_docs_root` правит `.bars/config.toml` проекта так же, останавливает прежнее слежение, запускает новое и ставит проект на полную проверку.
- **Ключи.** `secret_set` пишет в хранилище ОС, которое воркер получает в `WorkerConfig.secrets` (по умолчанию `OsSecrets`; тесты подставляют память). Ключ окну не возвращается.
- **Скачивание моделей.** `model_download` в блокирующей задаче загружает модель так же, как при первом использовании, и отпускает её: файлы остаются в кэше. Идущие скачивания видны в `models_info`; хода в байтах пока нет (OQ-63).

## Завершение воркера bars

- Закрытие окна прячет его, воркер остаётся в трее (Т-1).
- Выключение ОС и аварийное завершение безопасны. Документ в индексе либо старый, либо новый; файлы прерванной подмены приводятся в порядок при следующем старте (раздел «Восстановление файлов индекса при старте»), а проверка при старте доиндексирует всё, что не успело попасть в индекс.

### Выход на границе документа

Решение автора OQ-168 (23-10-2026), проектирование 28-10-2026. Реализация 5.1.3 в `ac52757` устраняет ожидание всего задания (ISS-66). Статус 01-11-2026: повторное ревью sol без замечаний, `fmt` и `clippy --workspace --all-targets -D warnings` прошли; полный гейт не завершён, выполнение регрессий и установленная сборка не подтверждены. Автор поручил завершить пункт без ожидания соседних правок (OQ-236).

«Выход» трея, перезапуск после обновления или смены настроек и просьба установщика `--quit` останавливают воркер одинаково — как кнопка «Остановить» для идущего задания:

1. Воркер ставит флаг остановки и перестаёт брать задания; `should_stop` индексатора видит этот флаг так же, как флаг остановки проекта. Задание, начавшееся одновременно с выходом, проверяет флаг до открытия индекса и подготовки модели; перед lazy-подготовкой свежего индекса и полной перестройки есть повторная проверка. Уже начавшийся конструктор модели не прерывается.
2. Текущий документ дописывается своей транзакцией, следующий не начинается. Проверка актуальности оставляет записанные документы; полная переиндексация удаляет `index.sqlite.new` под своим `job_gate` и не трогает старый индекс. Состояние проекта не меняется, `last_error` не ставится.
3. Ждущие задания и очередь документов не сохраняются: проверка при следующем старте находит недоиндексированное сама.
4. Воркер закрывает индексы, снимает слежение, выгружает модели и завершается.

Выход ждёт не дольше одного документа: его эмбеддинга встроенной моделью или HTTP-запросов внешней, ограниченных их таймаутом. От размера проекта время выхода не зависит.

Почему ожидание паузы отделено от проверки отмены, какие гонки закрывают ранние проверки и как их перепроверять — [границы отмены индексатора](../knowledge/worker-shutdown.md).

### Остановка фоновых задач воркера

Каждая долгая задача воркера лежит в списке задач воркера (`Inner::tasks`; снаружи модуля — через `Worker::spawn_task`) и после флага остановки заканчивается на своей границе; `shutdown` дожидается их всех. Короткие отложенные проверки держат воркер через `Weak` и после остановки ничего не делают.

| Задача | Где заканчивается |
|---|---|
| очередь индексации | на границе документа |
| scan | отменяется до или во время обхода, результат не публикуется |
| построение графа | на границе кванта; опубликованный граф остаётся прежним |
| аудиты и их расписание | по сигналу остановки, без опроса (ISS-72 закрыт) |
| таймеры: периодическая проверка, паузы документов, активность, обслуживание моделей | снимаются сразу или выходят по сигналу остановки |
| обновление клиентов после старта | дописывает текущий файл клиента |

Скачивание модели выход не ждёт: недокачанный файл не должен считаться скачанной моделью, это проверяется при реализации выхода. Новая фоновая задача, которую нельзя остановить на границе, в воркер не добавляется.

## Ошибка приёма соединения канала

Решение 28-10-2026 по ISS-70, реализовано в шаге 5.2.1 (`ipc/mod.rs`, `accept_loop`); числа — предложение агента, ждут ответа автора (OQ-226).

- Ошибка `listener.accept()` не завершает сервер канала: она пишется в лог уровнем `warn`, приём повторяется после паузы. Пауза начинается со 100 мс и удваивается до 5 с; успешный приём сбрасывает её и счётчик.
- 20 ошибок подряд без единого успешного приёма (не меньше минуты) — канал считается сломанным: ошибка в лог уровнем `error`, воркер завершается по правилам выхода. Следующий `bars-mcp` или `bars-cli` запустит `bars --background`, и новый процесс откроет канал заново ([ipc.md](ipc.md)).
- Обрыв клиента посреди вызова — не ошибка приёма: он касается только своего соединения, как и раньше.

## Логи воркера bars

Приложение после проверки единственного экземпляра устанавливает файловый logger; события воркера и диагностика rerank сохраняются в `~/.bars/logs`. Уровни, ротация, защита данных и вкладка настроек описаны в [logs.md](../features/window/logs.md). При отказе записи остаётся резервное сообщение stderr. Библиотечные тестовые воркеры глобальный logger не устанавливают. Диагностика не содержит ключи провайдеров ([secrets.md](secrets.md)).
