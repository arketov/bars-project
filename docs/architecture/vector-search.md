# Векторный поиск bars

Решение агента. Точный перебор выбран 14-10-2026 по OQ-11: автор не знал разницы между вариантами и выбор не задал. Реализация своим кодом вместо sqlite-vec выбрана тогда же, по исследованию стека ([knowledge/stack-research.md](../knowledge/stack-research.md)).

## Точный перебор и ANN — в чём разница

- **Точный перебор** сравнивает вектор запроса с каждым вектором индекса и возвращает действительно ближайшие. Время растёт линейно с числом чанков.
- **ANN** (approximate nearest neighbours: HNSW, IVF) строит дополнительную структуру и проверяет только часть векторов. Это быстро на миллионах векторов, но иногда пропускает настоящих соседей, требует памяти и перестройки при изменениях.

## Почему bars использует точный перебор

Индекс bars — один проект, тысячи чанков, а не миллионы. Для сравнения: образец перебирал 3 897 векторов размерности 4096 за 70–76 мс в pgvector, а у bge-m3 (Т-17) размерность 1024 — вчетверо меньше данных на вектор.

Точный перебор ничего не теряет и не требует обслуживать индекс при инкрементальной индексации (Т-9). Урок 7 образца (размерность исключила ANN) здесь не мешает.

## Как устроен перебор в bars

- Векторы хранятся в таблице `vectors` индекса проекта как BLOB из `float32` ([architecture/schema.md](schema.md)). При записи вектор нормализуется до длины 1.
- Для нормализованных векторов косинусная близость — это скалярное произведение. Воркер считает его в Rust для каждого вектора области поиска и держит 30 лучших.
- Полный поиск читает `vectors` последовательным проходом и находит связанные чанки по `chunks_embed_hash`. Поиск с областью (модули и файлы, Т-14) начинает с отобранных чанков, чтобы ради одного файла не читать все векторы проекта.

## Дисковое чтение при поиске

Причина лишнего I/O подтверждена 25-10-2026 на рабочем индексе: SQLite начинал полный поиск с `chunks`, затем выполнял отдельный поиск BLOB по первичному ключу `vectors` для каждого чанка. При 3515 чанках и 36 МБ полезных векторов один проход давал около 446 МиБ логического чтения и 141,5 тысячи операций. Малый страничный кэш соединения повторно читал страницы B-tree и overflow. Фиксированный порядок `vectors CROSS JOIN chunks CROSS JOIN documents` дал 47,9 МиБ и 14,4 тысячи операций; модель, точный cosine и правила ранжирования не меняются.

Измерение `GetProcessIoCounters` учитывает чтение через файловый кэш: это не объём физического чтения SSD. Физическая нагрузка зависит от памяти и параллельной работы. Стенд `scripts/probe-sqlite-io.cjs` открывает индекс только для чтения; результаты аппаратной проверки полного приложения после сборки фиксируются отдельно. Этот замер не закрывает НФТ-2.

Проверка доступных векторов для статуса и входов графа тоже проходит от `vectors` к `chunks` по покрывающему индексу, читая только ключи. На том же корпусе прежний `JOIN` давал 430 МиБ и 137,4 тысячи операций, последовательный вариант — 2,39 МиБ и 615 операций. SHA-256 отсортированных результатов совпал для обеих пар запросов, включая содержимое BLOB поиска. Доказательства — [замер SQLite](../chats/2026-10-25-disk-load/sqlite-io-final.json); повтор — `pwsh -File scripts/probe-sqlite-io.ps1 -Index <путь к индексу>`.

## Почему не расширение sqlite-vec

sqlite-vec на таком объёме тоже делает точный перебор, поэтому быстрее не будет. При этом:

- версия 0.1.x;
- сборка под Windows MSVC не подтверждена: issue #21 открыт;
- синтаксис косинусной метрики в `vec0` не задокументирован.

Свой перебор — около десятка строк кода и ни одной C-зависимости.

## Скорость перебора на прототипе

Замер на синтетике, размерность 1024 ([knowledge/spike-search.md](../knowledge/spike-search.md)): 5 000 векторов — 22 мс при чтении из SQLite и 3 мс в памяти; 50 000 — 221 мс и 33 мс. Это таймер перебора, без полного CPU-запроса и естественного корпуса; НФТ-2 этим замером не подтверждено. Проверка полного поиска — [исследование скорости](../knowledge/inference-speed.md), раздел «Естественные 5 000 чанков».

## Когда пересматривать векторный поиск

Векторы читаются из SQLite на каждый запрос, по одной строке (`Scope::cosines` в `bars-core/src/search/hybrid.rs`). Постоянного кэша векторов нет. Хранение оценок ограничено: heap лучших K и оценки текстовых/точных кандидатов; итоговый объём не более 3K, независимо от числа чанков N. Все N векторов по-прежнему проверяются; это точный поиск без потери recall. Равные оценки упорядочиваются по id, как прежде; исходные float32-оценки сохраняются для порога и fallback после ошибки rerank. BLOB читается на время строки без двух временных Vec для каждого вектора.

Проверено сравнение с прежним полным сбором/сортировкой, включая ties, нулевой K и текстовые кандидаты вне top-K; пройдены 33 проверки поиска. Синтетический опыт оценивает именно сбор оценок, не время inference. Это малая статья относительно моделей; она не объясняет исходные 8,46 ГиБ. Переход к ANN по-прежнему требует замеров качества и большого индекса; [протокол исследования памяти](../knowledge/memory.md).
