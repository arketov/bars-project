# Локальный канал bars

Решение агента: автор делегировал его 14-10-2026 (OQ-03). Методы, параметры и ошибки, которые идут по каналу, — в [протоколе](protocol.md); проверка прав доступа к каналу на Windows — в [спайке канала](../knowledge/spike-ipc.md).

## Транспорт канала bars

`bars-mcp` и `bars-cli` говорят с воркером `bars` через локальный канал ОС, без сетевого порта:

- Windows — именованный канал `\\.\pipe\bars-<имя пользователя>`;
- macOS — Unix-сокет `~/.bars/run/bars.sock` с правами только для владельца.

Реализация — крейт `interprocess` поверх tokio ([stack.md](stack.md)). Доступ к каналу ограничивается явно, потому что умолчания ОС этого не гарантируют:

- Windows: дескриптор безопасности канала по умолчанию даёт группе Everyone право чтения, поэтому воркер создаёт канал с явным DACL — доступ только у SID текущего пользователя; удалённые клиенты отклоняются;
- macOS: сокет создаётся с правами `0600` в папке `~/.bars/run/` с правами `0700`.

К каналу может подключиться только тот же пользователь ОС, поэтому отдельный токен не нужен. Это закрывает урок 12 для канала: секрета, который можно было бы вшить или утечь, нет.

Отклонено: HTTP на `127.0.0.1` — к нему может подключиться любой локальный процесс, а для защиты нужен токен в файле.

## Где живёт код канала bars

- `bars-protocol` — всё, что нужно и клиенту, и воркеру: адрес канала (`Endpoint`), чтение и запись строк с ограничением длины, клиент воркера (`Client`: подключение, `hello`, вызовы, повтор подключения с паузой) и цикл соединения на стороне воркера (`serve_connection` с трейтом `Handler`; он делает `hello` и проверку прав сам, остальные вызовы отдаёт обработчику).
- `bars-worker` — слушатель с ограничением доступа (`bind`) и приём соединений (`run_server`). SID, DACL и права на сокет — политика воркера, клиентам она не нужна, поэтому `bars-mcp` и `bars-cli` не получают код безопасности.

Мёртвый сокет на macOS: если файл сокета остался от упавшего воркера, воркер подключается к нему и при `ConnectionRefused` удаляет файл; если подключение удалось — воркер уже работает, и новый `bars` не стартует. Ветка macOS не проверена: нужен Mac.

Проверка владельца сервера на Windows (OQ-38): имя канала предсказуемо, и чужой пользователь мог создать канал с этим именем раньше воркера. Поэтому клиент сразу после подключения, до `hello`, узнаёт процесс сервера (`peer_creds` у `interprocess`, на Windows это `GetNamedPipeServerProcessId`) и сверяет SID владельца этого процесса со своим. Не совпал или не удалось определить — клиент закрывает соединение, ничего не отправив, и возвращает `ClientError::UntrustedServer`; к недоступному воркеру это не относится и воркер по требованию в таком случае не запускается. На macOS такой проверки нет: сокет лежит в папке `0700`, создать в ней файл может только владелец.

Занятое имя на Windows `interprocess` сообщает как `PermissionDenied` (os error 5), а не `AddrInUse`: у защищённого DACL канала чужой процесс не может открыть второй экземпляр. Воркер считает обе ошибки признаком «воркер уже работает».

## Протокол канала bars

JSON-RPC 2.0, одно сообщение на строку, сериализация `serde_json`; готовая JSON-RPC-библиотека не нужна. Первое сообщение клиента — `hello` с версией протокола. Если версии несовместимы, воркер отвечает ошибкой с текстом «обновите bars», и клиент показывает её пользователю или агенту.

## Длина строки в канале bars

Без ограничения локальный клиент мог бы заставить воркер копить память, поэтому строка читается с лимитом:

- запрос — не длиннее 1 МиБ; на более длинную строку воркер отвечает `-32600` и закрывает соединение, потому что хвост такой строки неотличим от следующего вызова;
- ответ — не длиннее 64 МиБ: `read` возвращает документ целиком; клиент, получив более длинную строку, возвращает ошибку канала.

Таймаут ожидания ответа в клиенте не зашит: его ставит вызывающий (`bars-mcp` и `bars-cli`).

## Запуск воркера по требованию

Клиент подключается к каналу. Если не получилось:

1. запускает `bars --background` из той же папки, где лежит сам клиент, отвязанным от себя процессом, чтобы воркер пережил завершение клиента и сессии агента:
   - Windows — флаги `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB`; если job object клиента запрещает отвязку, повтор без `CREATE_BREAKAWAY_FROM_JOB`. Проверено с Claude Code: MCP-серверу отвязка разрешена, и воркер переживает конец сессии ([knowledge/spike-detach.md](../knowledge/spike-detach.md));
   - macOS — через LaunchServices: `open -b <bundle id> --args --background`;
2. повторяет подключение с нарастающей паузой до 15 секунд;
3. если за 15 секунд не подключился — возвращает ошибку с путём к логу воркера.

Канал заодно не даёт запустить второй воркер: если имя канала уже занято, новый `bars` завершается (Т-1). Команду «показать окно» работающему воркеру второй запуск передаст, когда появится окно (срез 5); какой замок главный — канал или `tauri-plugin-single-instance` — OQ-47.

Клиентская часть — `bars-protocol/src/launch.rs` (решение агента, 15-10-2026): `connect_or_launch` подключается, при `Unavailable` запускает `bars --background` из папки текущего exe (`spawn_worker`) и повторяет подключение до 15 секунд (`connect_with_retry`). Канал, занятый чужим процессом (`UntrustedServer`), воркера не запускает. Ошибка запуска и тайм-аут — `Unavailable` (код выхода CLI 2) с текстом; папка `~/.bars/logs` в тексте названа, сами логи воркер начнёт писать позже. `connect_or_launch_with` принимает способ запуска и срок: на нём построены тесты.

## Метаданные сессии при старте bars-mcp

`bars-mcp` запрашивает `session_info` по cwd: реестр и метаданные индекса только одного проекта, без моделей, регистрации и запуска индексации. Весь путь подключения, возможного запуска воркера, hello и ответа ограничен тремя секундами. При ошибке или неизвестном проекте `initialize` всё равно отвечает статичной инструкцией. `list_tools` повторяет неудавшееся получение один раз с тем же сроком; успешный снимок сохраняется на соединение ([модули проекта](../features/agent-tools/module-scope.md)).

У метаданных отдельное короткое соединение: отменённый по сроку запрос не оставляет поздний ответ в канале обычных инструментов. Инструменты используют пул до четырёх каналов; подключение ограничено 15 секундами и общим бюджетом вызова 55 секунд. Отмена `rmcp` или общий таймаут закрывает занятый канал без возврата в пул. Бюджет включает очередь, подключение и повторы; меньший клиентский предел задаётся окружением прокси. Контракт и настройка — [вызовы MCP](../features/agent-tools/mcp-tools.md), раздел «Параллельность, отмена и общий срок MCP». Прокси не получает зависимостей ядра и моделей.

## Поиск во время индексации

Воркер принимает вызовы с самого старта. Пока проект индексируется, поиск возвращает то, что уже есть в индексе, и в ответе помечает `indexing: true` и сколько документов ждёт очереди. Агент видит, что выдача может быть неполной, и при необходимости может узнать состояние (Т-19).
