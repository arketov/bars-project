# Аудит нагрузки bars — срез и доказательства 25-10-2026

## Объём и метод

Запрос: «Проведи аудит производительности. Приоритет уменьшение нагрузки на компьютер, чтения диска оперативной памяти без потери качества», затем «исправляй всё». Вызван bars-end; после аудита выполнено исправление кода. HEAD при старте 4738aa0; рабочее дерево с параллельными изменениями графа, поиска и документов. Коммитов этой сессии нет. Serena отсутствует в каталоге инструментов; использованы rg/PowerShell и bars MCP. Исторические исследования относятся к своим версиям.

Итоговые механизмы, порядок и ограничения — [снижение нагрузки](../../knowledge/resource-efficiency.md). Задачи ISS-38/39/72/77 уже существовали; ISS-94 реализуется другой сессией. Новая находка ISS-95 относится к обслуживанию квантов близости.

## Исправление и проверки

- ISS-38/39: окно документа без общего опроса, дерево по сохранению/переносу; каталог моделей по экрану и операциям; скрытое главное окно получает только уведомления раз в 10 секунд. Принудительный refresh после занятого тика не теряется.
- ISS-77: общий Arc снимка, ревизия входов/состояния и идентификатор файла, LRU 256 МиБ / 8 проектов; JSON разбирается построчно. Бюджет включает ожидание и загрузку, ошибка до целого набора — graph_timeout; mix сохраняет обычный поиск с причиной fallback.
- ISS-95: Prepared/Calculation сохраняются между квантами; checkpoint для перезапуска остаётся в SQLite. Триггеры входов обнаруживают замену BLOB при прежнем ключе; перед публикацией проверяется полный ключ. Точный cosine, k=5, tau=0,5 и ties сохранены.
- ISS-72: одна ленивая метка на проект за такт, ошибки в лог; задания/планировщик зарегистрированы в shutdown, остановка по Notify без частого опроса. Кэш освобождается и после завершения фоновых задач.
- SQL-исправление ISS-94 сохранено и включено в общий прогон. Precision моделей, пороги, длины входа, K поиска и рабочий профиль не менялись; встроенная FP16-политика и выгрузка уже существовали.

Регрессии кэша проверяют совместных читателей, смену статуса, правку источника, повреждение данных, новую регистрацию и замену SQLite-файла. Регрессии активного расчёта проверяют тождество соседей и повторное использование векторов, инвалидирование при замене BLOB с прежним ключом. Опрос — четыре новые UI-проверки; полный набор окна — 505 тестов, типы 0/0. Изолированный собранный Tauri/WebView2 прошёл 14 проверок (`native-final-check/result.json`); рабочий bars не останавливался и не обновлялся.

Полный check не объявляется зелёным. В `check-verified.log` worker прошёл 298 тестов, остальные кодовые наборы прошли; единственный отказ — размер чанка после добавления раздела в руководство. Раздел исправлен, все три теста chunking_corpus повторно прошли. Финальный clippy — exit 0 (`clippy-final.log`). Дублирующий `check-complete.log` остановлен, когда обнаружен уже работающий общий прогон второй сессии. Его результат сохранён в `shared-check-observed.log`: два отказа (`contradictions_and_ignore_round_trip_without_changing_files`: partial вместо complete; `local_openai_address_works_without_a_key`: vtable constructor failed: chunks_fts). Оба теста прошли в собственном `check-verified.log` на том же кодовом срезе; точная причина различия не установлена, отказы не скрываются. Новые полные прогоны этой сессией не запускаются, чтобы не создавать новое перекрытие.

## Ресурсный замер на настоящем графе

Игнорируемый по умолчанию тест `handler::graph_cache::tests::frozen_graph_resource_probe` запущен отдельно с `BARS_RESOURCE_INDEX=<проект>/.bars/index.sqlite`. Исходная БД открывается read-only, `VACUUM INTO` создаёт согласованную копию в TempDir внутри этой сессии; схема меняется только в копии. После теста TempDir удаляется штатно. Весов и inference нет.

`graph-cache-resources.json`: 493 документа, 5384 узла, 13111 рёбер. Три прямых загрузки: 752,5–809,4 мс, медиана 771,9 мс; холодное заполнение 1120,5 мс; десять попаданий — медиана 0,695 мс, максимум 259,3 мс. Оценённое удержание 46,0 МиБ, не Working Set. Целый Dataset совпал по BLAKE3, попадания разделяют одну Arc. Общая машина; это скорость загрузки, не всего MCP-запроса, SSD или модели. Первый проход на другом снимке и с сериализацией оценки сохранён в `graph-cache-resources-serialized-size.json`; чистое сравнение холодных времён между ними невозможно.

## Сложности и разрешение

- LNK1180 при нулевом запасе C:. После появления свободного места сборка продолжена; общий target не очищался.
- DLL clang найдена в старом каталоге BuildTools; компилятор/линковщик выбираются из последнего MSVC. Воспроизведение — `build-env.ps1`, знание внесено в build.md.
- Перекрывающиеся Cargo-прогоны одного target и прямой запуск тестового exe мешали повторной линковке (LNK1104). Итоговый прогон запущен последовательно после завершения остальных процессов.
- Один прогон дал Windows sharing violation при подготовке теста исчезнувшего проекта. Ожидание до 5 с добавлено только для ошибки 32 удаления временного проекта; проверки unavailable/watching не изменены, остальные ошибки немедленно проваливают тест. Конкретный владелец краткого handle не установлен.
- Нативный exe без штатного manifest/runtime завершился 0xC0000139. Собственная копия с manifest Common-Controls v6 и локальным MSVC runtime прошла 14 проверок. Изменены только файлы стенда, не системные DLL; единственная причина между этими двумя условиями не выделена.

## Воспроизводимость и пределы

`source-hashes.json` фиксирует исходный аудит, `source-hashes-final.json` — исправленный срез. Файлы остаются незакоммиченными; соседние сессии могут менять их дальше. OQ-191 остаётся открытым для общего замера CPU/I/O/пика памяти и нескольких настоящих окон; OQ-155 сохраняет отложенную установочную приёмку. Предложение коммита: `perf: снизить фоновую нагрузку и повторное чтение графа`.
