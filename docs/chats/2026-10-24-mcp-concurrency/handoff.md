# Одновременные вызовы MCP (шаг 5.2.4) — итог сессии 24-10-2026

## Сделано
- Исследование [одновременные вызовы MCP](../../knowledge/mcp-concurrency.md): поведение Claude Code 2.1.309 и Codex 0.130/0.162 по коду установленных сборок, разбор 519 сообщений с вызовами bars в журналах Claude Code, замер очереди на установленном `bars-mcp.exe` (одно и два соединения, три повтора), длительности из истории MCP, связь с «Transport closed».
- Главное: клиенты шлют инструменты bars по одному, потому что у них нет `readOnlyHint`; очередь в прокси сегодня ничего не добавляет. При одновременной отправке `bars_read` за поиском ждёт 5,2–13,1 с, через второе соединение — 62–133 мс. Два поиска пул не ускоряет — модель в воркере за мьютексом. «Transport closed» — закрытие канала, а не таймаут; с очередью не связан.
- Вопрос OQ-182 о судьбе 5.2.5 в QUESTIONS.md, факты в ISS-69 (`docs/backlog/issues.md`), строка в `docs/knowledge/Index.md`.

## Не сделано
- Код не менялся. Решения по 5.2.5 нет — ждёт OQ-182.
- Причина прежнего «Transport closed» не установлена; исследование только исключило очередь в прокси.

## Трудности
- Из журналов клиентов нельзя отличить последовательную отправку от очереди в прокси: порядок ответов одинаков. Ответ дал код клиентов.
- Сведения о версиях Codex, в которых появились ключ `supports_parallel_tool_calls` и параллельность по `readOnlyHint`, — из сторонних статей; в установленных сборках найден только ключ.

## Дальше
- Ответ автора на OQ-182, затем 5.2.5: вариант 1 — `readOnlyHint` на инструментах чтения, пул до 4 соединений, отмена вызова и таймаут прокси не длиннее клиентского; проверка — два параллельных вызова через один `bars-mcp`, короткий не ждёт долгого.
