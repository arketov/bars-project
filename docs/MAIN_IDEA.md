# bars — локальная база знаний и RAG по документации проектов для людей и агентов

Рабочее название приложения — **bars** («Приложение называться будет bars это пока что», раунд 6).

Статус: зафиксирован 14-10-2026 (OQ-01) · раунд 16 — база знаний; раунд 17 — рабочая область, уточнения автора 20-10-2026, OQ-109/OQ-111 закрыты

Проектирование и первые срезы реализации завершены; текущее состояние и оставшиеся проверки — [project-status.md](project-status.md). Назначение продукта — [overview.md](overview.md).

## Проблема

Семантический поиск по документации сейчас есть только для одного корпуса: gramax ЦТМ-Регион / ЦТМ-СО, руководства, OpenAPI, НПА. Он завязан на инфраструктуру Firetech и на произвольный локальный проект не переносится:

- **Индексатор** `scripts_sandbox/tz_rag_search` — Python-скрипты. Проекты и каталоги зашиты в код (`common.PROJECTS`, `common.py:231`), нарезка подогнана под разметку Gramax (`common.py:597-662`). Индекс лежит в общем PostgreSQL (`DB_SCHEMA = "rag_tz"`, `common.py:44-45`), эмбеддинг и реранк идут через routerai (`common.py:56`), индексацию запускают руками (`run.ps1 -Index`).
- **Инструмент для агентов** `rag_query`/`rag_documents` работает на сервере `firetech-tmc-mcp` в k8s и читает тот же `rag_tz` (`firetech-tmc-mcp/src/firetech_tmc_mcp/tools/rag.py:75-117`). Число результатов фиксировано сервером (`rag.py:89-91`).
- **Окно** `scripts_sandbox/rag_explorer` (Go + WebView2) — тонкий клиент к тому же MCP. Своего индекса у него нет, проекты приходят с сервера (`rag_explorer/main.go:143-183`).

Документацию `docs/<module>/**/*.md` в локальных репозиториях этой системой не проиндексировать. Актуальность индекса держится на ручном прогоне.

Раунд 16: найти знания мало — их нужно вести. До раунда 16 bars только искал и показывал документы; чтобы создать, связать и проверить документацию, нужен был внешний редактор или агент-исполнитель. Окно только читало, дерево строилось из индекса, ссылки в просмотре не открывались, а часть возможностей инструментов агента (`bars_outline`) человеку была недоступна. Разбор и факты — [требования базы знаний](features/knowledge-base/requirements.md#проблема).

## Границы

**В скоупе:**
- Локальный индекс и гибридный поиск по Markdown-документации любых проектов на машине пользователя.
- Окно для пользователя, MCP для агентов и CLI — все над одним и тем же индексом.
- Автоматическое поддержание актуальности индекса.
- Подключение bars к агентским клиентам: Claude Code, Codex, любой MCP-клиент.
- Windows и macOS.
- Ведение базы знаний в окне по образцу Obsidian (раунд 16): редактор, ссылки между документами, файл папки `index.md`, создание и переименование файлов и папок, аудиты знаний, создание проекта.

**Вне скоупа:**
- Генерация ответа LLM поверх найденного (В-7: «Нет, только поиск»).
- Разметка Gramax: `:::`, `{% %}`, таблицы-списки (В-9).
- PostgreSQL / pgvector (В-2).
- Корпус Firetech (gramax, руководства, НПА, OpenAPI), замена `rag_query` и rag_explorer (В-17).
- Реализация на Python (В-15).
- Хуки в чат-приложении Claude Desktop: под «claude desktop» имелся в виду Claude Code (В-28: «код код»). Чат Claude Desktop может подключить bars как обычный MCP-клиент, но без хука.
- Правка `.gitignore` проекта (В-21).
- git — clone, pull, commit, push (раунд 16): идея автора записана как IDEA-16, требования собираются отдельно.
- MCP-инструменты записи файлов для агентов (раунд 16): агенты работают с файлами напрямую.
- Генерация текста документов моделью bars: аудиты только дают пользователю сведения (раунд 16).

## Требования

Требования подтверждены ответами постановщика; в скобках указан вопрос, где это решено. Рамка Т-43…Т-47 раунда 17 согласована с уточнениями автора OQ-109/OQ-111; конкретные библиотеки, макеты и численные шкалы этим согласованием не выбраны.

**Процессы и запуск**
- **Т-1.** На машине работает один общий процесс-воркер. Он держит индексы всех зарегистрированных проектов, с ним работают окно, CLI и все сессии агентов (В-1). Воркер и окно — один exe: воркер живёт в трее, окно открывается из трея, сам воркер не завершается (В-11).
- **Т-2.** Агент подключается через stdio-MCP — отдельный маленький exe, который клиент запускает на каждую сессию (В-14). Прокси пересылает вызовы в общий воркер; если воркер не запущен, прокси запускает его и ждёт готовности (В-10).
- **Т-3.** Стек: Rust, Tauri для окна и трея, fastembed-rs для ONNX/Nomic и встроенный llama.cpp для Qwen GGUF (OQ-60, ADR-0002); Python не используется (В-15, В-18).
- **Т-4.** Платформы: Windows и macOS (В-8).

**Проекты и хранение**
- **Т-5.** Настройки и индекс проекта лежат в папке `.bars` в корне проекта (В-12). Индекс — отдельный файл SQLite в `.bars` этого проекта (В-2, В-22). Окно читает настройки проекта из `.bars` и туда же записывает правки (В-12, В-21). `.bars` — локальные рабочие файлы, как `.serena` или `.claude`; уходит ли папка в git, решает пользователь, bars `.gitignore` проекта не трогает (В-21, OQ-05).
- **Т-6.** Проект регистрируется тремя путями: хук при старте сессии агента в папке проекта; добавление в окне; команда CLI (В-3, В-25, В-29). Проект, в котором уже есть `.bars`, подхватывается без настройки (В-3).
- **Т-7.** Корень документации задаётся в настройках проекта, по умолчанию `docs/`. Модуль — подпапка первого уровня под корнем, всё глубже принадлежит модулю. Индексируются файлы `**/*.md` (В-3б).
- **Т-8.** При регистрации проекта в корень документации кладётся `BARS_INSTRUCTION.md` — инструкция для модели, как вести документы, чтобы их можно было качественно индексировать (В-9, В-16, В-23). При проверке актуальности bars сверяет хеш файла с хешем своей текущей версии инструкции; не совпадает — файл перезаписывается (OQ-14). Инструкция также советует раскладку документации — база знаний, решения, фичи, журнал сессий — и правила журнала. Это совет, а не требование: bars не проверяет и не навязывает структуру `docs/`, на оформление файлов влияет только просьбой (OQ-39, OQ-41).

**Индексация и актуальность**
- **Т-9.** Первый раз проект индексируется целиком, дальше переиндексируются только изменившиеся документы (исходная формулировка).
- **Т-10.** Воркер сам находит изменения: проверка всех проектов при старте и раз в час; проверка проекта при начале активности MCP и по хуку сессии; слежение за файлами открытого в UI проекта и в течение часа после последнего MCP-вызова проекта. Повторные MCP-вызовы продлевают наблюдение без полного обхода на каждый запрос. Проверка без изменений не создаёт задания индексации (В-4, уточнение автора 26-10-2026, OQ-206).
- **Т-11.** Документы — обычный Markdown; заголовок документа берётся из frontmatter `title` (В-9).
- **Т-22.** Документ, которого больше нет на диске, удаляется из индекса. Отдельной защиты от массового удаления нет: индекс следует за диском (OQ-08: «если их удалили, значит и нам надо удалять»).
- **Т-23.** Нарезка — как в образце `rag_query`: по заголовкам, с настраиваемым ограничением размера чанка в символах (OQ-13). Каждый чанк несёт путь к файлу, номер строки, с которой он начинается, и цепочку заголовков `Заголовок 1/Заголовок 2/Заголовок 3.1`. Раздел больше ограничения режется на несколько чанков с той же цепочкой заголовков. Совсем маленький раздел — короче настраиваемого минимального размера чанка (Т-18) — склеивается со следующим (OQ-20). Чанк раздела, у которого есть подразделы, содержит собственный текст раздела и список заголовков подразделов («other headers»). В векторизации участвует весь чанк, кроме номера строки: номер строки — метаданные для выдачи, иначе вставка строки в начало файла заставила бы заново эмбеддить все чанки ниже (OQ-19, НФТ-1). Образец автора:

  ```text
  path: docs/test/test_file.md
  line: 25
  Заголовок 1/Заголовок 2/Заголовок 3.1
  В этом разделе суть
  <очень много слов>
  ```

  ```text
  path: docs/test/test_file.md
  line: 5
  Заголовок 1/Заголовок 2/
  В этом разделе уточнение бла бла
  other headers:
  ### Заголовок 3.1
  ### Заголовок 3.2
  ```

  Правило для разделов с подразделами автор отметил как предварительное («скорее всего так же»).

- **Т-41. Отложенный embed.** Сохранение документа не запускает embed сразу. Изменённый документ (в bars или на диске) по умолчанию ждёт 15 с без новых правок; новая правка перезапускает ожидание; пауза — настройка пользователя. Поиск «В тексте» видит правку сразу, «По смыслу» — после embed. Умолчание выбрано автором по замеру потока правок агентов (OQ-183); явно сохранённое значение пользователя или проекта сохраняет силу.
- **Т-42. Полноценная очередь индексации.** Очередь хранит документы, а не проекты. У каждого документа своя запись с состоянием «ждёт паузы», «в очереди», «индексируется», «ошибка»; новая правка заменяет ждущую запись того же документа. Список виден пользователю на странице индексации. Приоритет: поисковый запрос пользователя и вызов MCP выполняются раньше индексации; внутри индексации — явная команда, затем правка в bars, затем слежение, затем периодическая проверка.

**Поиск**
- **Т-12.** Поиск гибридный: полнотекстовый плюс векторный, результаты сливаются в один ранжированный список; после слияния, если включён, работает реранк (раунд 4, принято из «Улучшений сверх запроса»).
- **Т-13.** Результат поиска — фрагменты документов с путём, модулем, заголовком раздела и оценкой релевантности. Ответа LLM нет (В-7).
- **Т-14.** В окне документы проекта показаны деревом «модуль → папки → файлы» с галочками; поиск идёт только по отмеченному. Агент передаёт список модулей. Пустой выбор у обоих означает весь выбранный проект (исходная формулировка; В-3б). В окне галочки видны всегда (Т-34).
- **Т-15.** Без явного проекта агент ищет в проекте своей сессии (по cwd); параметром можно указать любой зарегистрированный проект (В-13).

**Модели и настройки**
- **Т-16.** В настройках приложения задаются: embed-модель; rerank-модель; включён ли rerank; числовые параметры поиска и нарезки (исходная формулировка).
- **Т-17.** Embed-модель подключается одним из трёх способов: удалённый провайдер; встроенная локальная модель через fastembed-rs или llama.cpp (OQ-60); внешний локальный OpenAI-совместимый адрес (исходная формулировка; В-5: «и то и другое»). Встроенная модель по умолчанию — `BAAI/bge-m3`; на выбор с самого начала также Qwen3-Embedding-0.6B, Qwen3-Embedding-4B, Nomic Embed v2 MoE (OQ-12). Скачанные модели хранятся в `<домашняя папка пользователя>/.bars/`, а не в `.bars` проекта (OQ-12). Встроенная rerank-модель по умолчанию — `BAAI/bge-reranker-v2-m3` (OQ-22).
- **Т-18.** Числовые параметры имеют значения по умолчанию из настроек, агент может переопределить их в вызове (В-6). Заводские значения взяты из образца (В-27): кандидатов на реранк — 30; результатов — 5 без реранка и 3 с реранком; размер чанка — от 250 до 6000 знаков.
- **Т-24.** Порог релевантности — настройка пользователя: результаты с оценкой ниже порога в выдачу не попадают (OQ-09). Агент может передать свой порог в вызове, но только в пределах, которые пользователь задал в настройках (OQ-23).
- **Т-25.** Если embed-модель в настройках не совпадает с моделью, которой построен индекс, пользователь получает предупреждение, что нужна переиндексация. Переиндексация запускается только после его согласия (OQ-06). До переиндексации поиск по этому проекту не работает и возвращает сообщение, что нужна переиндексация (OQ-21: «Никак»).

**База знаний и редактор** (раунд 16; обсуждение и решения по каждому пункту — [требования базы знаний](features/knowledge-base/requirements.md#журнал-раундов))
- **Т-29. Редактор.** Нажатие на документ в дереве сразу открывает его в редакторе исходного Markdown с подсветкой разметки. Кнопка с глазом в каждой рабочей панели переключает тот же документ между исходным Markdown и рендером, сохраняя правки, позицию и подсветку найденного отрывка. Структура документа показана плавающей панелью внутри редактора в правом верхнем углу; пользователь может скрыть её и открыть снова. Правки сохраняются на диск автоматически через 1 с после последнего изменения. Если файл изменили на диске, пока в редакторе есть несохранённые правки, bars не перезаписывает ни одну из версий молча и предлагает выбрать. Помощники разметки — панель над редактором и горячие клавиши: заголовки 1–3, жирный, курсив, код, блок кода, маркированный и нумерованный список, задача `- [ ]`, цитата, таблица, ссылка на документ; `Ctrl+B`, `Ctrl+I`, `Ctrl+K`. Помощь с синтаксисом: подсветка всех элементов CommonMark и GFM — заголовки, выделение, списки, задачи, цитаты, код и блоки кода по языку, таблицы, ссылки, frontmatter; продолжение списка и задачи по `Enter`; автозакрытие парных `**`, `` ` ``, `(`, `[`; в таблице `Tab` переходит к следующей ячейке и выравнивает столбцы; шпаргалка по синтаксису в меню панели.
- **Т-30. Ссылка на документ.** Ввод `[[` в редакторе открывает выбор документа проекта; выбранный документ вставляется в файл так же, как в Obsidian, — `[[Название]]` (имя файла без `.md`); если в проекте есть другой файл с тем же именем, вставляется `[[папка/Название]]` с путём от корня документации. Список предлагается по мере набора: сначала документы, чьё название, имя файла или путь совпадает с набранным, ниже — документы из поиска по смыслу (тот же поиск bars, Т-12); совпадение по названию всегда выше результата поиска по смыслу (уточнение автора 22-10-2026; его же слова в раунде 1: «поиск у нас и раг и полнотекстовый надо как то хитро это сделать»). Выбор допускает и название, которого нет среди документов: пункт «Создать ссылку на «название»» вставляет `[[название]]`; файл не создаётся, ссылка остаётся битой (аудит Т-36) до создания документа. Обычные Markdown-ссылки `[текст](путь.md)` продолжают работать наравне с `[[…]]`; `[[Название|текст]]` задаёт показываемый текст. Ссылка с якорем (`[[Название#раздел]]`, `file.md#раздел`) ссылкой индекса не считается — в индексе она ведёт на документ без раздела. Решение автора 22-10-2026: «посмотри как ссылки делаются в файле в obsidian вот надо так же»; оно отменяет отклонение `[[…]]` в раунде 16.
- **Т-31. Индекс ссылок.** Для каждого документа bars знает исходящие и входящие ссылки на документы проекта. Переименование или перемещение документа в bars обновляет ссылки на него во всех документах проекта. Если в каком-то документе ссылку обновить не удалось, переименование не откатывается, а пользователь видит список таких документов. После переименования вне bars ссылки становятся битыми и попадают в аудит.
- **Т-32. Файл папки `index.md`.** Новая папка создаётся вместе с `index.md` (имя строчными). Файл папки распознаётся без учёта регистра имени (`Index.md`, `INDEX.md`). Нажатие на имя папки открывает её файл. Если файла нет, открывается пустой документ, а на диске файл появляется при первой правке.
- **Т-33. Файлы и папки в дереве.** Пользователь создаёт, переименовывает, перемещает и удаляет папки и документы в дереве. Удаление отправляет в корзину ОС. Созданная папка или документ сразу видны в дереве, до индексации.
- **Т-34. Галочки области поиска.** Галочки области поиска (Т-14) в дереве видны всегда, в том числе когда в фокусе документ или граф; нажатие на имя документа открывает его и область не меняет.
- **Т-35. Создание проекта.** Пользователь выбирает папку; bars создаёт в ней `docs/`, `docs/index.md`, `docs/BARS_INSTRUCTION.md` и `.bars/` и регистрирует проект. `BARS_INSTRUCTION.md` в дереве не показывается. Модули пользователь создаёт сам.
- **Т-36. Аудиты.** Аудит — процесс, который даёт пользователю сведения о документации и не меняет файлы. Аудиты запускаются в фоне по настройке и вручную. Подтверждённый состав: битые ссылки, дубли, противоречия. Обязательно также: новые темы — вопросы, на которые поиск не нашёл ответа (IDEA-14). Аудит «документ не упомянут в `index.md`» в первую версию не входит.
- **Т-37. Функции агента доступны пользователю.** Всё, что агент получает от MCP-инструмента bars, пользователь может сделать в окне. В `docs/features/` ведётся таблица «инструмент MCP → что может пользователь → где в окне»; инструмент без строки в таблице не принимается.
- **Т-38. Цвета и иконки.** У документа настраивается цвет; у папки модуля и у её подпапок (второй уровень под корнем документации, не глубже) — цвет и иконка, как у проектов в ChatGPT. Иконка — из встроенного набора, цвет — из палитры окна. Видны в дереве, во вкладках, на карточках поиска и в графе. Документ без своего цвета берёт цвет ближайшей папки с цветом, поэтому цвет модуля переходит на точки его документов в графе. Выбор — в контекстном меню строки дерева. Цвет и иконка модуля хранятся во frontmatter его `Index.md` внутри корня документации и переносятся вместе с модулем. Оформление документов и подпапок второго уровня остаётся в `.bars/` проекта.
- **Т-39. Поиск «В тексте» и «По смыслу».** Одно поле запроса даёт два раздела выдачи: «В тексте» — все вхождения строки в документах проекта на диске, с учётом регистра по выбору, регулярными выражениями и фильтром по пути, включая ещё не проиндексированные правки; «По смыслу» — нынешний гибридный поиск (Т-12). Область поиска — галочки Т-34.
- **Т-40. Вкладки, панели и отдельные окна.** Несколько документов открыты вкладками; `Ctrl+O` открывает документ по имени. Основное окно bars делится на панели, в каждой — свои вкладки. Каждый документ также можно открыть командой контекстного меню «Открыть в новом окне» и редактировать в отдельном окне bars. Уточнение автора 20-10-2026 отменяет прежний запрет отдельных окон ОС; сохранение и конфликты версий подчиняются Т-29 и НФТ-5.

**Рабочая область и граф — раунд 17, OQ-109/OQ-111**

- **Т-43. Перемещаемые панели.** Основная композиция остаётся примерно как сейчас: слева навигационная зона, по центру рабочая область (редактор, граф, поиск), справа дополнительная зона (уточнение автора OQ-111). Навигация всегда присутствует и не является вкладкой; под ней мини-граф — часть навигации, разделитель регулирует высоту двух частей, ни одна из них не скрывается (OQ-117). Мини-граф следует сценарию использования: при открытом документе это локальный граф документа — сам документ и его соседи по связям текущего режима, как боковая панель Obsidian (раунд 27); после поиска — вид запроса, как в полном графе; без открытого документа и поиска — общий вид проекта. Полный граф открывается вкладкой рабочей области. Правая зона появляется при открытии документа справа или переносе вкладки к правому краю, исчезает после закрытия или переноса её последней вкладки и запоминает ширину (OQ-163 заменяет OQ-117, ответ 3). При переносе видны принимающая область и превью будущего места; правую группу можно разделить на две части по высоте. Пользователь перемещает вкладки центральной и правой рабочих областей, в том числе жестом в правую зону, разделяет рабочую область и меняет размеры; раскладка сохраняется между открытиями bars. Граф доступен рядом с поиском и документом, без обязательного переключения на отдельный экран. Узкая раскладка и перенос остальных экранов уточняются в дизайне окна; открытие документа в отдельном окне — Т-40.
- **Т-44. Глобальный поиск.** Лупа и настраиваемое сочетание клавиш открывают поиск поверх любого экрана bars. До выдачи поле расположено по центру, после получения результатов поднимается вверх. Главный экран поиска сохраняется; оба входа используют один поиск с одинаковыми запросом, областью и параметрами. Из результата пользователь открывает документ и показывает результат в графе.
- **Т-45. Сочетания клавиш.** Действия окна доступны сочетаниями клавиш; пользователь переназначает их в настройках. Список действий, умолчания и разрешение конфликтов с системой, WebView и редактором проектируются отдельно. Уже принятые сочетания Т-29 и Т-40 сохраняются как исходные умолчания.
- **Т-46. Физический граф проекта.** Граф документов и чанков — часть рабочей области, почти всегда видимая при обычной работе. Узлы располагаются физической раскладкой; сила связи видна по толщине и яркости ребра и определяет притяжение. Три вида связей: близость документ↔документ по смыслу, прямые ссылки, близость чанк↔чанк по смыслу. Близость не выдаётся за доказанную зависимость; тип и происхождение связи доступны пользователю. Панель сохраняет остановку движения и reduced motion по GR-05. Ссылка между двумя документами рисуется одной линией со стрелкой на конце, куда ведёт ссылка; у взаимных ссылок стрелки на обоих концах (OQ-118). На карте виды связей переключаются кнопкой по кругу: «ссылки», «по смыслу» и комбинированный «все связи»; на уровне документов их три, режим близости чанков добавляется при раскрытых чанках. В каждом режиме на раскладку влияют только связи этого режима. После переключения коротко показывается название режима. У режима «по смыслу» порог силы повышен. По умолчанию показаны документы, уровень подписан. Граф показывает только настоящие ссылки текстов. В меню карты есть настройки: притяжение по связям, отталкивание узлов, общее притяжение всех узлов друг к другу и длина связи. Движение не вязнет и не замораживается раньше времени; ссылки и близость собираются в цепочки (OQ-118). Карта читается при любом числе связей, как граф Obsidian (раунд 27): узлы главнее линий — линии тонкие и приглушённые, размер узла растёт с числом связей, цвет узла — цвет модуля, подписи появляются с приближением, документы без связей стоят кольцом вокруг карты.
- **Т-47. Граф от запроса.** При поиске с главного экрана и из глобального поиска тот же граф показывает запрос точкой, найденные результаты и их связи по смыслу и ссылкам: от каждого результата идут связи по смыслу и по ссылкам, и они переключаются тем же режимом, что в общем виде (раунд 23). Пользователь возвращается к общему виду проекта. Глубина, предел узлов, сила связи с запросом и поведение режимов поиска определяются в проектировании графа; усечение и недоступные слои показаны явно.

**Агенты, CLI, установка**
- **Т-19.** Агенту через MCP доступны: поиск; список проектов и их модулей; состояние индекса проекта (когда обновлён, идёт ли индексация, сколько документов ждёт); переиндексация по запросу; чтение документа целиком по пути (В-13, В-26); быстрое чтение структуры документа (Т-26).
- **Т-26.** Инструмент быстрого чтения структуры Markdown-документа: список заголовков документа с номерами строк. Режимы: все заголовки; только заданные уровни; только заголовки внутри заданного заголовка. Это полноценный инструмент, а не побочный вывод поиска (раунд 11: «сделать как полноценный инструмент»). Доступен через MCP и CLI (OQ-24). Работает с любым `.md`; относительный путь по умолчанию отсчитывается от корня документации проекта (OQ-25). Структура читается прямо с файла, поэтому номера строк всегда совпадают с диском. Отдельного чтения раздела по заголовку или по строкам нет: чтение по диапазону строк у агентов уже есть (OQ-26).
- **Т-20.** У bars есть CLI с командами: установка в клиенты (Claude Code, Codex) и удаление оттуда; регистрация проекта; переиндексация; состояние; поиск (В-29: «Ну вроде так»). CLI — отдельный exe, чтобы агент мог через него тестировать приложение и пользоваться им (OQ-04).
- **Т-21.** Подключение к агентским клиентам делается тремя путями: командой CLI; пунктом «Установить» в настройках окна; текстовой инструкцией по установке, которую можно передать агенту (В-25). Установка прописывает MCP-прокси и хук начала сессии в Claude Code и в Codex. В любом другом MCP-клиенте прокси работает без хука (В-24, В-28).
- **Т-27.** При подключении агента прокси отдаёт короткую стартовую инструкцию, как serena: что такое bars, когда искать в документации и как вести документы по совету из Т-8 (OQ-40: «возвращать Initial-instruction как делает это serena», «initial-instruction должны быть компактными»).
- **Т-28.** Установка в Claude Code и Codex (Т-21) ставит и skills bars для ведения документации по совету из Т-8; удаление их убирает (OQ-40: «можем пред установить скилы», «надо написать скилы»).

## Нефункциональные требования

- **НФТ-4.** Интерфейс, сообщения поиска, документация и поисковые запросы оформляются на языке пользователя; для автора bars — на русском. Исключение: служебное оформление текстовых ответов MCP — на английском (уточнение автора 18-10-2026). Документы с инструкциями для агентов (BARS_INSTRUCTION.md, skills) пишутся на английском: язык этих инструкций не меняет язык создаваемых документов и запросов. Названия продуктов, моделей, API и идентификаторы сохраняются. Документы пользователя индексируются в исходном виде, без принудительного перевода. Решение автора 18-10-2026; прежняя трактовка ISS-11 о переводе поиска на английский отменена.

- **НФТ-5.** Правки в редакторе не теряются при закрытии вкладки, окна и выходе из bars: несохранённое записывается на диск до закрытия.
- **НФТ-6.** Выдача «В тексте» на проекте размером с bars-project появляется быстрее 300 мс. Спайк 22-10-2026 подтвердил число в тёплом кэше ОС ([замер](knowledge/text-search-2026-10-22.md)); холодный кэш не измерен.

- **НФТ-1.** Правка одного раздела документа не вызывает повторного эмбеддинга неизменившихся чанков этого документа. Обоснование: в образце повторное использование по `embedded_text` сэкономило ~55% объёма на реальной истории правок (README `tz_rag_search`, «Переиспользование чанков»).
- **НФТ-2.** Поиск без реранка на проекте до 5 000 чанков на CPU отвечает быстрее 1 с. Решено по умолчанию; **требует подтверждения** на прототипе. Опора: точный скан 3 897 векторов размерности 4096 в pgvector занимал 70–76 мс (`firetech-tmc-mcp/.../rag/store.py`, docstring); для SQLite и встроенной модели замеров нет.
- **НФТ-3.** Прокси (Т-2) не держит индекс в памяти и не грузит модели: вся тяжёлая работа идёт в воркере. Следует из Т-1/Т-2.

## Решение

Устройство реализации описано в [architecture/](architecture/Index.md). Этот раздел связывает требования с архитектурными документами; требования Т-N и НФТ задаются в своих разделах.

- **bars (воркер + окно)**, Rust + Tauri. Реестр проектов, индексатор, поиск, слежение и проверка раз в 15 минут — [worker.md](architecture/worker.md). Канал клиентов к воркеру — [ipc.md](architecture/ipc.md).
- **bars-mcp (прокси)**, маленький Rust-exe, stdio-MCP. При первом вызове проверяет, жив ли воркер; если нет — запускает `bars` и ждёт готовности.
- **CLI** — отдельный exe с командами из Т-20 (OQ-04). Хук начала сессии вызывает CLI-команду «зарегистрировать проект по cwd и проверить актуальность».
- **Индекс** — SQLite в `<проект>/.bars/`: FTS5 и точный перебор векторов в Rust; sqlite-vec не используется. Схема — [schema.md](architecture/schema.md), выбор векторного поиска — [vector-search.md](architecture/vector-search.md).
- **Модели**: встроенная — fastembed-rs (`TextEmbedding`, `TextRerank` на ONNX Runtime; Qwen3 — через встроенный llama.cpp, GGUF Q4_K_M). Внешняя — OpenAI-совместимый `/v1/embeddings` и rerank в формате Cohere `/rerank` (так работают routerai в образце и llama-server).
- **База знаний** (раунд 16): редактор CodeMirror 6 в окне, дерево по диску, индекс ссылок и аудиты в воркере, очередь документов с паузой перед embed — [набросок устройства](features/knowledge-base/requirements.md#решение); подробное проектирование — отдельный проход.
- **Что берётся из образца как идея, не как код**: нарезка по заголовкам с дорезкой и склейкой; текст для эмбеддинга «документ + раздел + чанк» с сохранением `embedded_text`; повторное использование векторов по `embedded_text`; гейт по хешу файла и модели.

Решено по умолчанию (мои решения, не требования постановщика — их можно отменить):
- В индексе записано, какой моделью он построен; несовпадение обрабатывается по Т-25.
- Ключи провайдеров хранятся вне `.bars`, в хранилище ОС; способ — в `docs/architecture/` (OQ-07 делегирован).
- `BARS_INSTRUCTION.md` сам в индекс не попадает; текст зашит в bars; обновление — по Т-8.

Решения по устройству, которые постановщик делегировал (OQ-02, OQ-03, OQ-07, OQ-11, OQ-15), описаны в `docs/architecture/`.

## Уроки образца

Ошибки, которые прошёл `tz_rag_search` / `rag_query` / rag_explorer. По указанию постановщика они записаны как знание для проектирования, **а не как требования** (В-20: «Ты главное зафиксируй их, но не как требования»).

1. Регулярки нарезки, закреплённые на `$`, молча не срабатывали на CRLF (94% файлов корпуса) → битые чанки. README `tz_rag_search`, «Нарезка: что было починено 31.08.2026».
2. Удаление «пропавших» документов выходило за свою область и сносило чужие источники → полный переэмбеддинг. README, «Инкрементальная индексация», «Изоляция прогонов».
3. Неверный корень → массовое удаление документов. Сейчас стоит только предупреждение при доле > 0.5 (`common.py:1411`).
4. Смена embed-модели делает старые векторы несравнимыми, а полный пересбор запускается только вручную (`-Force`).
5. Сначала при любой правке файл переэмбеддился целиком; повторное использование неизменившихся чанков добавили позже (~55% экономии).
6. Мелкие чанки (< 100 знаков) засоряли выдачу, гигантские под одним заголовком уходили в эмбеддинг целиком.
7. Размерность 4096 исключила ANN-индекс в pgvector (README, «ANN-индекса нет»).
8. Фиксированное число результатов без порога → в хвост выдачи попадает шум (`rerank_score < 0.4`).
9. Пустой фильтр документов означал «весь корпус», включая чужие проекты (README, «Проекты и каталоги»).
10. Черновики ранжируются наравне с актуальными документами (CLAUDE.md воркспейса; плашка «Черновик» в rag_explorer).
11. Индекс обновлялся вручную и незаметно устаревал (CLAUDE.md: «manual snapshot … refreshed by hand»).
12. Токен вшит в exe и лежит открытым текстом в конфиге рядом с ним (`rag_explorer/main.go:24-31`).

## Отклонённые альтернативы

- **Процесс на каждую сессию, как serena** — отклонён (В-1): несколько процессов писали бы в один индекс и переиндексировали бы одновременно.
- **MCP по HTTP на localhost без прокси** — отклонён (В-10): «приложение может быть не запущенно изначально, и его надо запустить».
- **Прокси — тот же exe в режиме `mcp`** — отклонён (В-14): выбран отдельный маленький exe.
- **PostgreSQL / pgvector** — отклонён (В-2): нужен запущенный сервер БД, это уже не «один exe».
- **Один общий индекс на все проекты** — отклонён (В-22): «Свой файл в .bars».
- **Python + PyInstaller** — отклонён (В-15): «Питон точно не быстрый».
- **Go + hugot (развитие rag_explorer)** — отклонён (В-18): меньше инференсных библиотек, сборка под Mac не проверена.
- **Ответ LLM в окне** — отклонён (В-7).
- **Хранить `[[wikilinks]]`, как в Obsidian** — был отклонён в раунде 16 (GitHub и GitLab их не отрисуют), принят автором 22-10-2026 (раунд 25): в файле стоят `[[…]]`, граф и окно читают их наравне с обычными ссылками.
- **Исправление одним кликом в аудите** — отклонено (раунд 16): аудит только даёт сведения.
- **Аудиты «без `title`», «без входящих ссылок», «папка без `index.md`», «не упомянут в `index.md`»** — отклонены (раунд 16).
- **Поддержка разметки Gramax** — отклонена (В-9).

## Критерии приёмки

- **Т-1.** При открытых окне и двух сессиях агентов в системе работает ровно один процесс `bars`; после закрытия окна процесс остаётся в трее.
- **Т-2.** Воркер не запущен → сессия агента вызывает поиск → воркер запускается, вызов возвращает результат без ручных действий.
- **Т-3.** Сборка — Rust/Tauri, fastembed-rs и llama-cpp-2 в зависимостях, Python отсутствует.
- **Т-4.** Т-1, Т-2, Т-14 проходят на Windows и на macOS.
- **Т-5.** После регистрации в проекте есть `.bars/` с настройками и SQLite-файлом; правка корня docs в окне меняет файл в `.bars/`; `.gitignore` не изменён.
- **Т-6.** Проект регистрируется каждым из трёх путей: хук, окно, CLI. Проект, скопированный вместе с `.bars`, появляется в окне без настройки.
- **Т-7.** В проекте с `docs/a/x.md`, `docs/a/b/y.md`, `docs/c/z.md` видны модули `a` и `c`; `y.md` относится к `a`. Корень `documentation/` из настроек работает так же.
- **Т-8.** После регистрации есть `<корень docs>/BARS_INSTRUCTION.md`. Если файл отличается от текущей версии bars (по хешу), после проверки актуальности он совпадает с ней; если не отличается — не переписывается.
- **Т-9.** Правка одного файла → переиндексируется только он; число вызовов эмбеддинга равно числу изменившихся чанков (НФТ-1).
- **Т-10.** У открытого в UI проекта и в течение часа после последнего MCP-вызова правка попадает в выдачу без ручных действий. Неактивный проект проверяется раз в час. Начало активности MCP запускает проверку сразу; продление активности не создаёт повторного обхода. После закрытия последнего окна и окончания MCP-активности слежение снимается. Проверка неизменённого проекта не создаёт задания обновления. Правка при выключенном воркере обнаруживается при старте.
- **Т-11.** Документ с `title:` во frontmatter показан в выдаче с этим заголовком.
- **Т-12.** Запрос с точным идентификатором из документа, которого нет в соседних документах, находит этот документ первым при выключенном реранке.
- **Т-13.** У каждого результата есть путь, модуль, раздел и оценка; текста, сгенерированного LLM, нет.
- **Т-14.** При отмеченном модуле `a` нет результатов из `c`; при пустом выборе есть результаты из обоих модулей и нет результатов из других проектов.
- **Т-15.** Вызов без проекта из сессии в проекте P ищет только в P; с явным проектом Q — только в Q.
- **Т-16, Т-17.** Поиск работает на каждом из трёх способов подключения embed-модели; переключение rerank в окне меняет число результатов по умолчанию с 5 на 3.
- **Т-18.** Вызов агента с явным числом результатов возвращает это число; без него — значение из настроек.
- **Т-19.** Каждый из шести инструментов агента вызывается и возвращает ответ; состояние индекса показывает время последнего обновления.
- **Т-20.** Каждая команда CLI из списка выполняется и даёт тот же результат, что то же действие в окне.
- **Т-21.** После установки командой CLI или из окна в Claude Code и Codex есть MCP bars и хук; удаление их убирает и не трогает чужие записи. Агент, получив текстовую инструкцию, сам подключает bars.
- **Т-27.** Агент, подключившийся к `bars-mcp`, получает стартовую инструкцию без отдельного вызова; инструкция не длиннее 2 000 знаков.
- **Т-28.** После установки в Claude Code и Codex skills bars доступны агенту; после удаления их нет, чужие skills не тронуты.
- **Т-22.** Удалённый с диска документ пропадает из выдачи после ближайшей проверки актуальности; удаление всех документов модуля убирает модуль из списка.
- **Т-23.** Для файла из образца автора выдача содержит чанки с путём, номером строки начала и цепочкой заголовков; раздел больше ограничения дан несколькими чанками с одной цепочкой; чанк родительского раздела перечисляет заголовки подразделов. Изменение ограничения размера в настройках меняет нарезку после переиндексации.
- **Т-23 (номер строки).** Вставка строки в начало файла меняет номера строк в выдаче, но не вызывает повторного эмбеддинга ни одного чанка.
- **Т-24.** При пороге выше оценки части результатов эти результаты не возвращаются ни окну, ни агенту, ни CLI. Порог агента внутри пределов настроек применяется; порог вне пределов отклоняется или прижимается к границе.
- **Т-25.** После смены embed-модели в настройках пользователь видит предупреждение; до согласия переиндексация не запускается, эмбеддинг документов не вызывается, поиск по проекту возвращает сообщение о необходимости переиндексации; после согласия проект переиндексирован новой моделью и поиск работает.
- **Т-29.** Клик по документу открывает его в редакторе. Глаз переключает исходный текст и рендер в центральной и правой рабочих панелях; правки и подсветка найденного отрывка сохраняются. Плавающая структура находится внутри редактора справа сверху; скрытие, повторный показ и переходы к заголовкам работают для своего документа. Правка сохраняется на диск через 1 с после остановки ввода. Работают кнопки панели и `Ctrl+B`, `Ctrl+I`, `Ctrl+K`, подсветка элементов из Т-29, продолжение списка по `Enter`, `Tab` в таблице. Если файл изменили на диске при несохранённой правке, появляется выбор версии, и ни одна версия не пропадает.
- **Т-30.** `[[` открывает выбор документа; по мере набора первыми идут совпадения по названию, имени файла и пути, ниже документы из поиска по смыслу без повторов; после выбора в файле стоит `[[Название]]` (при одинаковых именах — `[[папка/Название]]`). Для названия, которого нет среди документов, выбор предлагает «Создать ссылку»; в файле остаётся `[[название]]`, файл не создан, ссылка попадает в битые. `[[Название]]` и `[текст](путь.md)` дают одно и то же ребро в графе и входящую ссылку у документа; ссылка в блоке кода ссылкой не считается.
- **Т-31.** У документа видны входящие и исходящие ссылки. Переименование документа, на который ссылаются три других, меняет ссылки во всех трёх. Если один из файлов занят, остальные два обновлены, а занятый показан в списке. Переименование файла в Проводнике даёт битые ссылки в аудите.
- **Т-32.** Новая папка содержит `index.md`. Папка с `Index.md` открывает его по клику на имя. Папка без файла открывает пустой документ; файл появляется на диске только после первой правки.
- **Т-33.** Созданные папка и документ видны в дереве сразу, до индексации. Переименование и перемещение работают. Удалённый файл лежит в корзине Windows.
- **Т-34.** Галочки в дереве есть всегда, поиск идёт только по отмеченному (Т-14); при открытом документе или графе они не пропадают.
- **Т-35.** После создания проекта в выбранной папке есть `docs/`, `docs/index.md`, `docs/BARS_INSTRUCTION.md` и `.bars/`; проект в списке; `BARS_INSTRUCTION.md` в дереве не виден.
- **Т-36.** Аудит битых ссылок, дублей, противоречий и новых тем запускается вручную и по расписанию из настроек; итог виден пользователю; файлы проекта после аудита не изменены (хеши совпадают).
- **Т-37.** Для каждого инструмента `bars-mcp` в таблице в `docs/features/` есть строка с действием пользователя, и это действие выполняется в окне.
- **Т-38.** Цвет документа, цвет и иконка модуля и его подпапки видны в дереве, во вкладках, на карточках поиска и в графе; у папки третьего уровня выбора иконки нет; документ без своего цвета в дереве и в графе окрашен цветом ближайшей папки с цветом; цвет и иконка выбираются в контекстном меню строки дерева; у модуля меняются только поля оформления в его `Index.md`; копирование модуля в другой проект сохраняет оформление.
- **Т-39.** Запрос даёт разделы «В тексте» и «По смыслу». Слово, только что набранное в документе, находится «В тексте» до индексации. Работают учёт регистра, регулярное выражение и фильтр по пути.
- **Т-40.** Открыты три документа вкладками; окно разделено на две панели с разными документами; `Ctrl+O` открывает документ по имени. Контекстное меню любого документа открывает его в отдельном окне bars, где доступно редактирование. Правки одного файла в основном и отдельном окнах не перезаписываются молча; закрытие любого окна сохраняет правки по Т-29/НФТ-5, остальные окна и общий воркер продолжают работать.
- **Т-41.** Пять правок с интервалом 2 с вызывают один embed документа — через 15 с после последней правки при умолчании. До истечения паузы embed не вызывается. Пауза меняется в настройках; явно заданные значения пользователя и проекта сохраняются.
- **Т-42.** Страница индексации показывает документы очереди с состояниями. Повторная правка не создаёт второй записи. Поиск окна и вызов MCP во время индексации отвечают, не дожидаясь конца индексации.
- **НФТ-5.** Закрытие окна сразу после правки оставляет правку на диске.
- **НФТ-6.** Замер «В тексте» на bars-project: p95 меньше 300 мс.
- **Т-43.** В основном окне сохранены левая навигационная, центральная рабочая и правая дополнительная зоны. Правая зона также является рабочей областью: результат поиска открывает документ справа, оставляя выдачу видимой; найденный отрывок подсвечен и прокручен в поле зрения в исходном тексте и в рендере. Навигация и мини-граф под ней всегда видны, не перетаскиваются и не закрываются как вкладки; разделитель меняет высоту обеих частей. Мини-граф при открытом документе показывает его локальный граф и следует за активной вкладкой документа, после поиска — вид запроса; кнопка «Граф» открывает полный граф вкладкой, а не активирует мини-граф. В штатной раскладке без документов пустой правой зоны нет. Открытие документа справа или перенос вкладки к правому краю создаёт зону; уход последней вкладки удаляет её. Ширина восстанавливается при повторном появлении, правую группу можно разделить по высоте. Превью показывает фактическое место и размер после сброса. Старые раскладки переводятся без потери непустых вкладок; центр показывает редактор, граф или поиск. Вкладка мышью переносится между зонами, в правую зону и к краю группы с разделением; размеры меняются. Повторное открытие восстанавливает раскладку. Проверяются обе темы и согласованная узкая раскладка; содержимое и функции панелей остаются доступны.
- **Т-44.** Из документа, графа, настроек и хода индексации лупа и сочетание открывают поиск поверх текущего экрана. До результатов поле по центру, после — вверху; одинаковые запрос, проект, область и параметры дают ту же выдачу, что главный экран. Из результата доступны документ и граф.
- **Т-45.** Каждое действие из согласованного списка выполняется с клавиатуры. Переназначение сохраняется после перезапуска; конфликт показан до применения. Ввод текста и сочетания редактора проверены отдельно от команд рабочей области.
- **Т-46.** На bars-project и overdrive-bots граф работает рядом с документом: доступны документы и чанки, легенда трёх видов по Т-46, основания рёбер. При одинаковом типе большая сила даёт более толстое/яркое ребро и большее притяжение в контролируемой проверке. Стоп и reduced motion прекращают движение без потери навигации. Кнопка режима переключает «ссылки», «по смыслу» и «все связи», появляется подсказка режима, граф перекладывается только по связям режима; четыре ползунка (притяжение связей, отталкивание, общее притяжение, длина связи) меняют раскладку, но не толщину и яркость рёбер; взаимные ссылки — одна линия со стрелками на обоих концах; граф не показывает ссылок, которых нет в текстах. На снимках bars-project и overdrive-bots общий план и приближение читаются как граф Obsidian: линии не закрывают узлы, хабы видны крупными узлами, узлы окрашены по модулю, подписи на общем плане не наползают друг на друга, одиночки стоят кольцом; приёмку по снимкам делает автор.
- **Т-47.** Один запрос с обоих входов даёт одинаковый вид запроса на том же снимке: запрос, допустимые результаты и связи. Документ открывается из узла; возврат к общему виду сохраняет возможность вернуться к выдаче. Проверяются пустая выдача, усечение, старый ответ, недоступный граф и смена проекта.
- **Т-26.** Для документа с заголовками `#`, `##`, `###` инструмент возвращает: все заголовки с номерами строк; только уровень `##`; только заголовки внутри заданного `##`. Номера строк совпадают с файлом на диске. Вызов с путём `a/x.md` читает `<корень документации>/a/x.md`; файл вне документации читается по явному пути. Инструмент вызывается и через MCP, и через CLI с одинаковым результатом.
