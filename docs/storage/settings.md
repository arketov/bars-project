# Настройки bars

Какие настройки есть у bars, где они лежат и что делает их изменение (Т-16, Т-18, Т-24). Где лежат файлы и в каком порядке берутся значения — [files.md](files.md). Окно правит эти же файлы через воркер, ручная правка тоже допустима: воркер её замечает ([architecture/worker.md](../architecture/worker.md)).

## Embed-модель в settings.toml

Таблица `[embed]` — модель для всех проектов (Т-16, Т-17):

| Ключ | По умолчанию | Значение |
|---|---|---|
| `source` | `builtin` | `builtin` — встроенная; `remote` — удалённый провайдер; `local-openai` — локальный OpenAI-совместимый адрес |
| `model` | `BAAI/bge-m3` | для `builtin` — модель из каталога [models/local-models.md](../models/local-models.md); для остальных — имя модели у провайдера |
| `base_url` | — | адрес провайдера для `remote` и `local-openai` |
| `api_key_name` | — | имя записи в хранилище ОС ([architecture/secrets.md](../architecture/secrets.md)) |
| `api_key_env` | — | имя переменной окружения, которая перекрывает ключ из хранилища |
| `batch_size` | `32` | сколько чанков в одном запросе к внешнему провайдеру |

## Rerank-модель в settings.toml

Таблица `[rerank]` — те же ключи, что у `[embed]`, кроме `batch_size`, плюс `enabled`:

| Ключ | По умолчанию | Значение |
|---|---|---|
| `enabled` | `false` | включён ли реранк (Т-16) |
| `source` | `builtin` | как у embed |
| `model` | `BAAI/bge-reranker-v2-m3` | Т-17 |

Реранк по умолчанию выключен: на прототипе встроенный rerank тратил секунды на запрос и на CPU, и на встроенной видеокарте, а поиск без него — десятки миллисекунд ([knowledge/spike-search.md](../knowledge/spike-search.md)). Включить его — одна галочка в окне. Он заметно поднимает качество, поэтому окно подсказывает: быстрый реранк даёт внешний rerank по API.

## Параметры поиска в settings.toml

Таблица `[search]` (Т-18, Т-24):

| Ключ | По умолчанию | Значение |
|---|---|---|
| `candidates` | `30` | сколько кандидатов берёт каждый из двух поисков |
| `rerank_candidates` | `15` | сколько лучших после слияния уходит в реранк |
| `results` | `5` | результатов без реранка |
| `results_reranked` | `3` | результатов с реранком |
| `min_score_vector` | `0.0` | порог по косинусной близости без реранка |
| `min_score_rerank` | `0.1` | порог по оценке реранка |
| `agent_min_score` | `[0.0, 1.0]` | пределы, в которых агент может задать свой порог (Т-24) |
| `max_results` | `20` | больше этого числа результатов агент запросить не может |
| `max_candidates` | `100` | больше этого числа кандидатов агент запросить не может |
| `max_rerank_candidates` | `50` | больше этого числа кандидатов на реранк агент запросить не может |

Пороги подобраны на корпусе `docs/` bars ([knowledge/spike-search.md](../knowledge/spike-search.md)). У реранка релевантное получает 0,6–0,99, хвост — обычно ниже 0,1, отсюда порог `0.1`. Косинусная близость шум не отделяет (релевантное 0,55–0,73, нерелевантное 0,45–0,6), поэтому порог по косинусу по умолчанию выключен.

Обе оценки лежат в диапазоне от 0 до 1. Косинусная близость нормализованных векторов на практике не бывает отрицательной. Встроенный rerank возвращает сырой логит, поэтому bars пропускает его через сигмоиду. Внешний rerank в формате Cohere уже отдаёт `relevance_score` от 0 до 1. Поэтому у порога и его пределов один масштаб, какой бы ни была модель.

Число результатов и кандидатов из вызова агента сверх `max_results`, `max_candidates` и `max_rerank_candidates` прижимается к пределу, как и порог (Т-18, Т-24).

## Устройство для встроенных моделей в settings.toml

Таблица `[device]`:

| Ключ | По умолчанию | Значение |
|---|---|---|
| `accelerator` | `auto` | `auto` — видеокарта, если она есть (DirectML на Windows), иначе CPU; `cpu` — только процессор |

Видеокарта выбрана по умолчанию даже без прироста скорости: она снимает нагрузку с процессора (OQ-27). Векторы на CPU и на видеокарте совпадают, поэтому смена устройства не требует переиндексации ([models/local-models.md](../models/local-models.md)).

## Параметры нарезки в settings.toml

Таблица `[chunking]` (Т-18, Т-23):

| Ключ | По умолчанию | Значение |
|---|---|---|
| `min_chars` | `250` | раздел короче склеивается со следующим |
| `max_chars` | `6000` | раздел длиннее режется на несколько чанков |

## Настройки проекта в .bars/config.toml

| Ключ | По умолчанию | Значение |
|---|---|---|
| `docs_root` | `docs` | корень документации относительно корня проекта (Т-7) |
| `[search]`, `[chunking]` | — | любые ключи этих таблиц из `settings.toml`; перекрывают их для проекта |

Модели задаются только в `settings.toml`, для всех проектов сразу (Т-16).

## Что происходит при изменении настроек bars

| Что изменили | Что делает воркер |
|---|---|
| `[embed]` так, что изменился отпечаток модели | проекты переходят в `reindex_required` (Т-25) |
| `[rerank]` | новая модель грузится при следующем реранке; индекс не трогается |
| `[device]` | встроенные модели перезагружаются на новом устройстве; индекс не трогается |
| `[search]` | действует со следующего поиска |
| `[chunking]` или `docs_root` | проект ставится на полную проверку: все документы режутся заново. Векторы неизменившихся чанков переиспользуются по хешу (НФТ-1); согласие не нужно, потому что модель та же |

Параметры нарезки, которыми построен индекс, записаны в `meta` индекса ([schema.md](schema.md)). По ним воркер и узнаёт, что нарезка изменилась, даже если файл правили при выключенном воркере.
